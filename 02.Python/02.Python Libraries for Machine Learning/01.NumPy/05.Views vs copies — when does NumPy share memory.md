# 05. Views vs Copies — When Does NumPy Share Memory?

> _A view is a different window into the same room. A copy is a different room entirely. Confusing the two is how you spend three hours debugging a neural network that corrupts its own weights._

---

## The Fundamental Distinction

Every NumPy array has two parts — the **metadata** (shape, dtype, strides) and the **data buffer** (the raw bytes in memory).

- A **view** has its own metadata but **shares the data buffer** with another array. Modifying the view modifies the original.
- A **copy** has its own metadata **and** its own independent data buffer. Modifying the copy leaves the original untouched.

```python
import numpy as np

original = np.array([1, 2, 3, 4, 5])

# --- View ---
view = original[1:4]                    # slice → view
view[0] = 99
print(original)   # [ 1 99  3  4  5]   ← original changed!

# --- Copy ---
copy = original[1:4].copy()             # explicit copy
copy[0] = 77
print(original)   # [ 1 99  3  4  5]   ← original unchanged
```

This single distinction is responsible for more silent bugs in NumPy code than anything else.

---

## How to Check — `np.shares_memory()` and `base`

```python
a = np.array([1, 2, 3, 4, 5])
b = a[1:4]          # view
c = a[1:4].copy()   # copy

# Method 1: shares_memory — definitive check
print(np.shares_memory(a, b))   # True  ← same buffer
print(np.shares_memory(a, c))   # False ← different buffers

# Method 2: .base attribute
# If array is a view, .base points to the array that owns the buffer
print(b.base is a)   # True  ← b's buffer is owned by a
print(c.base is None)  # True  ← c owns its own buffer

# Method 3: flags
print(b.flags['OWNDATA'])   # False ← does not own its data
print(c.flags['OWNDATA'])   # True  ← owns its data
print(a.flags['OWNDATA'])   # True  ← original owns its data
```

**The hierarchy of trust:**

1. `np.shares_memory(a, b)` — most reliable, checks actual byte overlap
2. `b.base is a` — works for direct views, may be misleading for views-of-views
3. `b.flags['OWNDATA']` — only tells you if _this_ array owns the buffer, not who does

## What Produces a View?

### 1. Basic Slicing — Always a View

```python
a = np.arange(10)

b = a[2:7]        # view — contiguous slice
c = a[::2]        # view — strided slice (every other element)
d = a[:]          # view — full slice
e = a[..., :3]    # view — ellipsis slice

print(np.shares_memory(a, b))   # True
print(np.shares_memory(a, c))   # True

# All of these are views — modifying any of them modifies a
c[0] = 99
print(a)   # [99  1  2  3  4  5  6  7  8  9]
```

Slicing is a view because it can be expressed purely through strides — no data movement needed. The slice `a[::2]` is just the same buffer with a stride of 2 elements instead of 1.

### 2. Reshape — Usually a View

```python
a = np.arange(12)
b = a.reshape(3, 4)    # view — same data, new shape+strides

print(np.shares_memory(a, b))   # True

b[0, 0] = 99
print(a[0])   # 99 ← original changed

# BUT: reshape on a non-contiguous array forces a copy
c = a[::2]            # strided view, shape (6,)
d = c.reshape(2, 3)   # cannot be expressed as a view → copy made
print(np.shares_memory(c, d))   # False
```

### 3. Transpose — Always a View

```python
a = np.zeros((3, 4))
b = a.T               # view — strides swapped, no data copy

print(np.shares_memory(a, b))    # True
print(b.base is a)               # True
print(a.strides)                 # (32, 8)
print(b.strides)                 # (8, 32)  ← swapped
```

### 4. `np.squeeze()` and `np.expand_dims()` — Views

```python
a = np.zeros((1, 3, 1, 4))
b = np.squeeze(a)           # view — removes size-1 axes
c = np.expand_dims(a, 0)    # view — adds a size-1 axis

print(np.shares_memory(a, b))   # True
print(np.shares_memory(a, c))   # True
```

### 5. `ravel()` — View When Possible, Copy Otherwise

```python
a = np.arange(12).reshape(3, 4)   # C-contiguous
b = a.ravel()                      # view — already contiguous

print(np.shares_memory(a, b))    # True

c = a.T                            # F-order, not C-contiguous
d = c.ravel()                      # copy — cannot ravel non-contiguous as view

print(np.shares_memory(c, d))    # False
```

`flatten()` always returns a copy. `ravel()` returns a view when possible.

## What Produces a Copy?

### 1. Fancy Indexing — Always a Copy

```python
a = np.array([10, 20, 30, 40, 50])

# Fancy indexing: indexing with an integer array or list
b = a[[0, 2, 4]]      # copy — cannot be expressed as strides
print(np.shares_memory(a, b))   # False

b[0] = 99
print(a)   # [10 20 30 40 50]  ← unchanged
```

This is the most important asymmetry to memorise:

- `a[1:4]` → **view**
- `a[[1, 2, 3]]` → **copy**

They look nearly identical but behave completely differently.

### 2. Boolean Indexing — Always a Copy

```python
a = np.array([1, 2, 3, 4, 5])
mask = a > 2

b = a[mask]           # copy — result size not known until mask is evaluated
print(np.shares_memory(a, b))   # False

b[0] = 99
print(a)   # [1 2 3 4 5]  ← unchanged
```

### 3. Explicit `.copy()` — Always a Copy

```python
a = np.arange(5)
b = a.copy()          # explicit copy
c = np.array(a)       # also a copy (np.array copies by default)
d = np.array(a, copy=False)  # view if possible

print(np.shares_memory(a, b))   # False
print(np.shares_memory(a, c))   # False
print(np.shares_memory(a, d))   # True (no copy made)
```

### 4. Arithmetic Operations — Always a Copy

```python
a = np.array([1, 2, 3])

b = a * 2       # copy — new array with doubled values
c = a + 0       # copy — even adding zero creates a new array
d = -a          # copy

print(np.shares_memory(a, b))   # False
print(np.shares_memory(a, c))   # False
```

In-place operations (`+=`, `*=`) write back to the same buffer:

```python
a = np.array([1, 2, 3])
b = a               # b and a point to same object (not even a view — same array)
a += 1
print(b)   # [2 3 4]  ← b changed because b IS a, same object

# In-place on a view
c = np.arange(6)
d = c[1:4]          # view
d += 10
print(c)   # [ 0 11 12 13  4  5]  ← c changed through view d
```

## The Complete Decision Table

```
Operation                          View or Copy?
─────────────────────────────────────────────────────
a[i:j]          basic slice        VIEW  (always)
a[::k]          strided slice      VIEW  (always)
a[:]            full slice         VIEW  (always)
a.T             transpose          VIEW  (always)
a.reshape(...)  reshape            VIEW  if contiguous, else COPY
a.ravel()       ravel              VIEW  if contiguous, else COPY
a.flatten()     flatten            COPY  (always)
a[[i,j,k]]      fancy index        COPY  (always)
a[bool_mask]    boolean index      COPY  (always)
a.copy()        explicit copy      COPY  (always)
np.array(a)     np.array()         COPY  (default)
a + b           arithmetic         COPY  (always)
a += b          in-place arith     VIEW  (modifies in place)
np.squeeze(a)   squeeze            VIEW  (always)
np.expand_dims  expand_dims        VIEW  (always)
np.concatenate  concatenate        COPY  (always — new buffer)
```

## Views of Views — The `.base` Chain

When you take a view of a view, `.base` points to the **original owner** of the buffer, not the intermediate view.

```python
a = np.arange(10)       # owns buffer
b = a[::2]              # view of a
c = b[1:3]              # view of view of a

print(c.base is b)      # False — NumPy resolves to root owner
print(c.base is a)      # True  ← base always points to root
print(np.shares_memory(a, c))  # True

c[0] = 99
print(a)   # [ 0  1  2  3 99  5  6  7  8  9]
```

The buffer ownership chain always resolves to the array that called `np.array()`, `np.zeros()`, `np.empty()`, etc. — the one with `OWNDATA=True`.

## Shallow Copy vs Deep Copy

NumPy's `.copy()` is a **shallow copy** for object arrays but a **deep copy** for numerical arrays (since numerical elements are values, not references).

```python
# Numerical array — .copy() is a complete independent copy
a = np.array([1, 2, 3])
b = a.copy()
b[0] = 99
print(a)   # [1 2 3]  ← fully independent

# Object array — .copy() copies references, not objects
class Box:
    def __init__(self, v): self.v = v

a = np.array([Box(1), Box(2), Box(3)], dtype=object)
b = a.copy()
b[0].v = 99              # modifies the Box object itself
print(a[0].v)            # 99 ← both a and b point to same Box!

# True deep copy for object arrays
import copy
c = copy.deepcopy(a)
c[0].v = 77
print(a[0].v)            # 99 ← unchanged
```

In practice, you almost never use object arrays for ML work. All numerical dtypes behave as full deep copies.

## Memory Efficiency — Why Views Matter

Views are not just a quirk — they are a deliberate performance design:

```python
# 1 GB array
a = np.zeros((1000, 1000, 125), dtype=np.float64)
print(f"{a.nbytes / 1e9:.1f} GB")   # 1.0 GB

# These are all free — no memory allocation, no data copy
b = a.T                    # view
c = a[::2]                 # view
d = a.reshape(1000, -1)    # view (if contiguous)
e = a[:500]                # view

# These allocate new memory
f = a.copy()               # 1.0 GB allocated
g = a.flatten()            # 1.0 GB allocated
h = a[[0, 1, 2]]           # small, but still a copy
```

In a deep learning pipeline processing large tensors, knowing which operations are free (views) and which allocate memory (copies) directly impacts GPU memory usage and training speed.

## The Write-back Trap

The most dangerous consequence of views: **you can corrupt your data without knowing it**.

```python
# Training loop trap
weights = np.random.randn(784, 256)

def get_first_layer(W):
    return W[:100]          # returns a view, not a copy!

layer_view = get_first_layer(weights)
layer_view *= 0             # DESTROYS the first 100 rows of weights
print(weights[:3])          # [[0, 0, ...], [0, 0, ...], [0, 0, ...]]
# Your model's weights are now corrupted — silently
```

Fix:

```python
def get_first_layer(W):
    return W[:100].copy()   # explicit copy — safe
```

Or detect the problem:

```python
def get_first_layer(W):
    result = W[:100]
    assert result.flags['OWNDATA'], "Returning a view — is this intended?"
    return result
```

## `np.asarray()` vs `np.array()` — The Copy vs View Shorthand

```python
a = np.array([1, 2, 3])

# np.array() — always copies (default copy=True)
b = np.array(a)
print(np.shares_memory(a, b))   # False

# np.asarray() — view if already correct dtype, else copy
c = np.asarray(a)               # view (same dtype, already ndarray)
print(np.shares_memory(a, c))   # True

# np.asarray() copies when dtype conversion needed
d = np.asarray(a, dtype=np.float64)
print(np.shares_memory(a, d))   # False (int64 → float64 requires copy)
```

`np.asarray()` is the idiomatic way to say: _"give me an ndarray, copy only if you must."_ You see this in every library's internal code.

## Connection to AI / ML / Deep Learning

### PyTorch mirrors this exactly

```python
import torch
import numpy as np

a = np.array([1.0, 2.0, 3.0])

# torch.from_numpy → view (shares memory)
t = torch.from_numpy(a)
t[0] = 99
print(a)   # [99.  2.  3.]  ← numpy array corrupted by torch write

# .numpy() on a CPU tensor → view
x = torch.tensor([1.0, 2.0, 3.0])
n = x.numpy()                   # view
x[0] = 77
print(n)   # [77.  2.  3.]  ← moves both ways

# Safe pattern: copy explicitly at the boundary
n_safe = x.numpy().copy()       # independent
```

The NumPy ↔ PyTorch boundary is one of the most common places view-related bugs appear in real ML code. A preprocessing pipeline that returns a NumPy view, which then gets wrapped in a tensor, which then gets modified in-place by an optimiser step — that is a real bug that corrupts your dataset.

### In-place operations and autograd

PyTorch's autograd engine tracks operations to compute gradients. In-place operations on views can corrupt the computation graph:

```python
# This is why PyTorch warns about in-place ops on leaf tensors
x = torch.tensor([1.0, 2.0], requires_grad=True)
# x += 1   ← RuntimeError: in-place op on leaf variable with grad
```

Understanding that `+=` is an in-place view operation — not a copy — is why this error exists and what it is protecting.

### Gradient arrays as views

In NumPy-based backpropagation (e.g. implementing a network from scratch), gradients are accumulated in-place into arrays that may be views of a larger parameter buffer. If you accidentally copy where you should view, gradients do not propagate. If you accidentally view where you should copy, you overwrite the wrong thing.

```python
# Correct: accumulate gradient into the view (writes back to param buffer)
param_buffer = np.zeros(1000)
grad_W = param_buffer[:784].reshape(28, 28)   # view into buffer
grad_W += compute_gradient()                  # writes back correctly

# Wrong: copy breaks the connection to param_buffer
grad_W = param_buffer[:784].reshape(28, 28).copy()  # now disconnected
grad_W += compute_gradient()   # lost — param_buffer never updated
```

### Data augmentation pipelines

```python
# Loading a batch — images come as views of a memory-mapped file
images = np.load('data.npy', mmap_mode='r')   # memory-mapped, read-only
batch = images[idx]                            # view — do NOT modify

# Augment: must copy first
batch_aug = batch.copy()
batch_aug = random_flip(batch_aug)             # safe — independent copy
```

## Summary

|Question|Answer|
|---|---|
|Is `a[i:j]` a view or copy?|**View** — always|
|Is `a[[i,j]]` a view or copy?|**Copy** — always|
|Is `a[mask]` a view or copy?|**Copy** — always|
|Is `a.T` a view or copy?|**View** — always|
|Is `a.reshape()` a view or copy?|**View** if contiguous, else **copy**|
|Is `a.ravel()` a view or copy?|**View** if contiguous, else **copy**|
|Is `a.flatten()` a view or copy?|**Copy** — always|
|Is `a + b` a view or copy?|**Copy** — always|
|How to check?|`np.shares_memory(a, b)`|
|How to force a copy?|`a.copy()` or `np.array(a)`|
|How to force a view?|`np.asarray(a)` (no-copy if possible)|

**The one rule to remember when in doubt:**

> Basic slicing (`:`) → view. Everything else → assume copy until proven otherwise. When the answer matters, check with `np.shares_memory()`.

## Common Mistakes

```python
# Mistake 1: Thinking fancy indexing returns a view
a = np.array([1, 2, 3, 4, 5])
b = a[[0, 2, 4]]
b[0] = 99
print(a)   # [1 2 3 4 5]  ← unchanged — b was a copy!
# If you wanted to modify a through fancy indexing, use np.put() or
# a[[0, 2, 4]] = [99, 99, 99] directly (this writes back)

# Mistake 2: Modifying a slice and expecting independence
def process(data):
    result = data[:100]    # view — not a safe local copy!
    result += 1            # mutates the input!
    return result
# Fix:
def process(data):
    result = data[:100].copy()
    result += 1
    return result

# Mistake 3: Assigning to a slice vs assigning the variable
a = np.arange(5)
b = a[1:4]       # b is a view

b = b * 2        # b now points to a NEW array — view is broken!
print(a)         # [0 1 2 3 4]  ← a unchanged
                 # because b = b * 2 reassigned b, not modified in place

b[:] = b * 2    # correct way to modify in place through view
# or
b *= 2          # in-place — modifies a through the view

# Mistake 4: Trusting .base for views of views
a = np.arange(10)
b = a[::2]
c = b[1:]
print(c.base is b)   # False! — base resolves to root owner
print(c.base is a)   # True

# Mistake 5: Returning views from functions (silent aliasing)
def bad_normalise(X):
    row = X[0]        # view!
    row -= row.mean() # modifies X[0] in place — side effect!
    return row

# Fix: copy inside the function
def good_normalise(X):
    row = X[0].copy()
    row -= row.mean()
    return row
```
