## The Core Idea

A **module** is any `.py` file. A **package** is a directory of modules. The `import` system is how Python finds them, loads them into memory, executes them exactly once, and makes their names available in your namespace.

The word _namespace_ is the key concept. Every import is fundamentally an answer to the question: **which names become visible in my current scope, and under what label?**

---

## What Actually Happens When You Import

This is not hand-waving — this is the exact sequence:

```
1. Python checks sys.modules (the import cache)
   → If found: return the cached module object. Done. No re-execution.
   → If not found: proceed.

2. Python locates the module file using sys.path
   (a list of directories searched in order)

3. Python creates a new module object

4. Python adds it to sys.modules immediately
   (before execution — handles circular imports)

5. Python executes the module's source code
   top-to-bottom, in the module's own namespace

6. The resulting module object is bound to a name in
   the importing scope
```

The critical invariant: **a module's code runs exactly once**, no matter how many files import it. All importers share the same module object.

```python
import sys

import numpy as np
print(sys.modules["numpy"])   # <module 'numpy' from '...'>

import numpy as np2
print(np is np2)              # True — same object
```

## The Four Import Forms

### Form 1 — `import module`

```python
import os
import math
import pathlib
```

This binds the **top-level module name** in your namespace. To access anything inside it, you use dot notation:

```python
import os
import math

print(os.getcwd())
print(math.sqrt(2))
print(math.pi)
```

**What goes into your namespace:** one name — `os`, `math`, etc. Everything else is accessed through the module object.

**Advantage:** explicit origin. When you read `os.path.join(...)` three hundred lines into a file, you know exactly where `join` came from.

---

### Form 2 — `from module import name`

```python
from math import sqrt, pi
from os.path import join, exists
from pathlib import Path
```

This executes the module (same as above) but only binds the specified names in your namespace:

```python
from math import sqrt, pi

print(sqrt(2))    # no 'math.' prefix needed
print(pi)
```

**What goes into your namespace:** only the names you listed — `sqrt`, `pi`. The module object `math` is not bound.

**Advantage:** less typing, cleaner code for heavily-used names.

**Danger:** name collisions are invisible:

```python
from math import sqrt
from cmath import sqrt   # silently overwrites the previous sqrt
```

Now `sqrt` refers to the complex version and you will not get an error — just wrong results.

---

### Form 3 — `import module as alias`

```python
import numpy as np
import pandas as pd
import matplotlib.pyplot as plt
import tensorflow as tf
import torch
```

This is identical to `import module` but binds the module to a different name. The aliases above are **universal conventions** in ML/data science — use them exactly as written.

```python
import numpy as np

x = np.array([1, 2, 3])
print(np.mean(x))
```

**What goes into your namespace:** one name — the alias.

**Use it for:** long module names, universal conventions, and avoiding collisions between two modules with the same short name.

---

### Form 4 — `from module import name as alias`

```python
from datetime import datetime as dt
from collections import defaultdict as dd
from sklearn.linear_model import LinearRegression as LR
```

Imports one name and immediately renames it:

```python
from datetime import datetime as dt

now = dt.now()
```

**What goes into your namespace:** one name — the alias.

**Use it for:** disambiguation when two modules export the same name, or shortening a frequently-typed name.

## The Wildcard Import — `from module import *`

```python
from math import *      # imports everything not starting with _
```

This pulls every public name from the module into your namespace. It is almost always wrong:

- You cannot tell where any name came from
- It silently overwrites existing names
- It makes static analysis and autocomplete unreliable
- It pollutes your namespace with names you do not need

**The one legitimate use:** interactive REPL sessions and small scripts where you genuinely want everything from a specific module (e.g. `from tkinter import *` in a GUI tutorial). Never in production code.

A module can control what `import *` exports by defining `__all__`:

```python
# inside mymodule.py
__all__ = ["PublicClass", "public_function"]
# private_helper will NOT be exported by import *
```

## The `sys.path` Search Order

When you write `import foo`, Python searches these locations in order:

```
1. sys.modules          — the import cache (already-loaded modules)
2. Built-in modules     — compiled into the interpreter (sys, builtins, etc.)
3. Frozen modules       — modules frozen into the interpreter
4. sys.path             — a list of directories, searched left to right:
   a. The directory of the script being run (or '' for interactive)
   b. PYTHONPATH environment variable entries
   c. Installation-dependent defaults (site-packages, stdlib)
```

```python
import sys
for p in sys.path:
    print(p)
```

This is why `import numpy` works: `numpy` lives in `site-packages`, which is on `sys.path`.

You can add directories at runtime:

```python
import sys
sys.path.insert(0, "/path/to/my/project")   # prepend — searched first
```

But in practice, the right solution is proper package structure (see [[51.Understanding **init**.py and package structure]]) or `pip install -e .` for editable installs.

## Importing Submodules and Nested Packages

```python
# Import the submodule — os.path becomes available
import os.path
result = os.path.join("data", "train.csv")

# Import a name from a submodule
from os.path import join
result = join("data", "train.csv")

# Import a deeply nested name
from urllib.parse import urlparse, urlencode

# Import a submodule with an alias
import xml.etree.ElementTree as ET
tree = ET.parse("config.xml")
```

When you write `import os.path`, Python imports `os` first (if not cached), then imports `os.path` as an attribute of `os`. Both `os` and `os.path` end up in `sys.modules`.

## Lazy and Conditional Imports

### Conditional import (compatibility)

```python
try:
    import ujson as json        # fast C implementation
except ImportError:
    import json                 # fall back to stdlib
```

Use this when offering an optional faster backend without making it a hard dependency.

### Version-conditional import

```python
import sys

if sys.version_info >= (3, 11):
    import tomllib              # built-in in 3.11+
else:
    import tomli as tomllib     # third-party backport
```

### Lazy import (defer until needed)

```python
def load_model():
    import torch                # only imported when this function is called
    import torchvision
    model = torchvision.models.resnet50(pretrained=True)
    return model
```

Placing imports inside functions delays loading until the function is actually called. This is useful when:

- A module is expensive to import (TensorFlow, PyTorch take seconds)
- A module is only needed in one code path
- You want to avoid circular imports (see below)

The module is still cached in `sys.modules` after the first call — subsequent calls pay no import cost.

## Circular Imports — The Trap

A circular import occurs when module A imports module B, and module B imports module A:

```
# a.py
from b import func_b

# b.py
from a import func_a     # a is partially initialised — func_a may not exist yet
```

Python handles this by inserting the partially-initialised module into `sys.modules` immediately (step 4 above). When B tries to import from A, it gets the half-built module — which may be missing names that haven't been defined yet.

**Fix 1:** restructure so the dependency is one-directional.

**Fix 2:** move the import inside the function that needs it:

```python
# b.py
def func_b():
    from a import func_a    # imported at call time, not module load time
    return func_a()
```

**Fix 3:** import the module, not the name:

```python
# b.py
import a                    # a may be incomplete, but the object exists
def func_b():
    return a.func_a()       # accessed at call time, when a is fully initialised
```

## Reloading a Module

In normal execution, each module runs once. In interactive development (REPL, Jupyter), you sometimes want to re-execute after editing:

```python
import importlib
import mymodule

# After editing mymodule.py:
importlib.reload(mymodule)
```

This re-executes the module's code, but existing references to objects from the old module still point to the old objects. Use with caution. In Jupyter, `%autoreload 2` is the practical solution.

## The Standard ML Import Block

Every ML script you write will begin with a block that looks approximately like this. Learn to read and write it fluently:

```python
# ── Standard library ──────────────────────────────────────
import os
import sys
import json
import time
import random
import argparse
from pathlib import Path
from typing import Optional, List, Tuple, Dict

# ── Numerical computing ────────────────────────────────────
import numpy as np
import pandas as pd

# ── Visualisation ──────────────────────────────────────────
import matplotlib.pyplot as plt
import seaborn as sns

# ── Machine learning ───────────────────────────────────────
from sklearn.model_selection import train_test_split
from sklearn.preprocessing import StandardScaler
from sklearn.metrics import accuracy_score, classification_report

# ── Deep learning ──────────────────────────────────────────
import torch
import torch.nn as nn
import torch.nn.functional as F
from torch.utils.data import Dataset, DataLoader
import torchvision.transforms as transforms

# ── Experiment tracking ────────────────────────────────────
import mlflow
import mlflow.pytorch
```

The grouping and ordering is conventional (PEP 8): stdlib → third-party → local. Blank lines between groups. Alphabetical within groups is optional but common.

The aliases `np`, `pd`, `plt`, `nn`, `F` are **not optional style choices** — they are industry-wide conventions. Writing `import numpy` instead of `import numpy as np` will confuse every ML practitioner who reads your code.

## Connection to AI / Machine Learning / Deep Learning

### Why `torch.nn as nn` and `torch.nn.functional as F`

```python
import torch.nn as nn
import torch.nn.functional as F
```

`torch.nn` contains **stateful** building blocks — layers that hold parameters (weights and biases):

```python
self.conv1 = nn.Conv2d(3, 64, kernel_size=3)
self.bn1   = nn.BatchNorm2d(64)
self.fc    = nn.Linear(512, 10)
```

`torch.nn.functional` contains **stateless** functions — the same mathematical operations but without stored parameters:

```python
x = F.relu(x)             # no parameters — just the function
x = F.dropout(x, p=0.5, training=self.training)
x = F.cross_entropy(logits, targets)
```

The convention is: use `nn.X` for layers you define in `__init__`, use `F.X` for operations you apply in `forward`. This distinction is architectural — blurring it leads to broken gradient flow or parameters that don't update.

### Selective imports reduce startup time

```python
# Bad — imports all of sklearn (slow)
import sklearn

# Good — imports only what you need
from sklearn.linear_model import LogisticRegression
from sklearn.preprocessing import StandardScaler
```

TensorFlow is the extreme case — `import tensorflow as tf` takes 3–8 seconds on first import due to its enormous C++ backend. In a script that only uses one function, lazy imports or selective imports save meaningful time.

### `__init__.py` and what `from torch import ...` actually means

When you write:

```python
from torch.utils.data import Dataset, DataLoader
```

Python is navigating a package hierarchy:

```
torch/
├── __init__.py
└── utils/
    ├── __init__.py
    └── data/
        ├── __init__.py      ← re-exports Dataset and DataLoader
        ├── dataset.py       ← defines Dataset
        └── dataloader.py    ← defines DataLoader
```

`Dataset` is not defined in `__init__.py` — it is defined in `dataset.py` and re-exported through `data/__init__.py`. The `from ... import` syntax lets you address the public API without knowing the internal file layout. This pattern (see [[51.Understanding **init**.py]]) is how every large Python library is organised.

### Namespace hygiene matters in Jupyter notebooks

Jupyter cells share a global namespace. Wildcard imports in one cell corrupt the namespace for all subsequent cells:

```python
# Cell 1 — DON'T DO THIS
from numpy import *
from math import *     # 'log' now refers to math.log, not numpy.log
                       # numpy.log was silently overwritten

# Cell 1 — DO THIS
import numpy as np
import math
# now np.log and math.log are unambiguous
```

In long notebook sessions, restarting the kernel and re-running from the top is the only way to guarantee a clean namespace. Explicit imports make this reproducible.

## Common Mistakes and Pitfalls

**1. Naming your file after a standard library module**

```
# You create a file called:
random.py

# Then in another file:
import random           # imports YOUR random.py, not the stdlib
random.randint(0, 10)  # AttributeError — your file has no randint
```

The current directory is first on `sys.path`. Never name your files `os.py`, `math.py`, `random.py`, `json.py`, etc. In ML projects, also avoid `model.py` and `data.py` if they shadow names you import elsewhere.

**2. Mutating a module-level object and expecting isolation**

```python
import config
config.LEARNING_RATE = 0.01   # modifies the shared module object
                               # all other importers see this change
```

Modules are singletons. If module A modifies a mutable object in module B, module C sees the change. Use this intentionally (shared state) or avoid it (pass values explicitly).

**3. `from module import name` does not stay in sync**

```python
from math import pi

# Later, if something reassigned math.pi (hypothetically):
# your local 'pi' still holds the original value
# 'import math; math.pi' would give the new value

# This is why mutable globals should be imported as the module, not the name:
import config             # if config.VALUE changes, you always get current
# not:
from config import VALUE  # a snapshot of VALUE at import time
```

**4. Circular imports from poor project structure**

The moment you have `models.py` importing from `utils.py` and `utils.py` importing from `models.py`, you have a design problem. The fix is almost always to extract shared definitions into a third module that neither imports from the other two.

## Summary

|Form|Syntax|Adds to namespace|Access|
|---|---|---|---|
|Module import|`import math`|`math`|`math.sqrt()`|
|Aliased import|`import numpy as np`|`np`|`np.array()`|
|Name import|`from math import sqrt`|`sqrt`|`sqrt()`|
|Aliased name|`from math import sqrt as sq`|`sq`|`sq()`|
|Wildcard|`from math import *`|everything public|`sqrt()` — avoid|

**The invariant that governs everything:** a module's code runs exactly once. All importers share one module object. `import` is a namespace operation — it controls which names are visible in your scope and under what label.
