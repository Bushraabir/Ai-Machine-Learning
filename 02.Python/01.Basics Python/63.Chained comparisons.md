# 63. Chained Comparisons

## What Are Chained Comparisons?

Python allows comparison operators to be **chained** in a single expression, reading left to right the way mathematical notation works.

```python
# Mathematics:  0 < x < 10
# Most languages require:
x = 5
if x > 0 and x < 10:
    print("in range")

# Python allows:
if 0 < x < 10:
    print("in range")
```

Both are equivalent. The chained form is not syntactic sugar that secretly expands to something else -- it evaluates each comparison once and short-circuits.

---

## How Python Evaluates Chains

Given `a < b < c`, Python evaluates it as `a < b and b < c`, with one critical difference: **`b` is only evaluated once**.

```python
def val(x, label):
    print(f"evaluating {label}")
    return x

# b is evaluated once, not twice
result = val(1, "a") < val(5, "b") < val(10, "c")
# evaluating a
# evaluating b
# evaluating c
print(result)   # True
```

If `b` were a function call with side effects, the chained form calls it once. The `and` expansion would call it twice. This is the semantic difference.

### Short-circuit evaluation

If an early comparison is `False`, the rest is not evaluated.

```python
def expensive():
    print("called")
    return 100

5 < 3 < expensive()
# "called" is never printed -- short-circuits after 5 < 3 is False
```

---

## Syntax -- What Can Be Chained

Any comparison operator can appear in a chain, and you can mix them freely.

```python
# All valid
0 < x < 10
0 <= x <= 10
a < b < c < d
a == b == c          # all three equal
a != b != c          # b differs from both a and c -- NOT that a != c
1 < x <= 5
low <= value < high
```

### The != trap

`a != b != c` does NOT mean "all three are different". It means `a != b and b != c`. `a` and `c` could be equal.

```python
a, b, c = 1, 2, 1

print(a != b != c)         # True  -- 1!=2 and 2!=1
print(a != b and b != c)   # True
print(a != c)              # False -- a and c ARE equal
```

If you need "all distinct", use `len(set(...))`:

```python
values = [1, 2, 1]
all_distinct = len(set(values)) == len(values)   # False
```

## Practical Usage

### Range checks

```python
age = 25

# Without chaining
if age >= 18 and age <= 65:
    print("working age")

# With chaining -- reads like math
if 18 <= age <= 65:
    print("working age")
```

### Bounds checking in algorithms

```python
def in_grid(row, col, rows, cols):
    return 0 <= row < rows and 0 <= col < cols

# Used in BFS/DFS on 2D grids
grid = [[0]*5 for _ in range(4)]
print(in_grid(2, 3, 4, 5))    # True
print(in_grid(4, 3, 4, 5))    # False
```

### Validating sorted order

```python
def is_sorted_triple(a, b, c):
    return a <= b <= c

print(is_sorted_triple(1, 2, 3))   # True
print(is_sorted_triple(1, 3, 2))   # False
```

### ML -- clamping and threshold checks

```python
confidence = 0.87

if 0.0 <= confidence <= 1.0:
    print("valid probability")

# Checking a value is within training bounds
if x_min <= sample <= x_max:
    process(sample)
```

## What Cannot Be Chained

Not everything is a comparison operator. Assignment, membership, and identity tests each have their own rules.

### `in` and `not in` can be chained -- but rarely usefully

```python
# Valid Python -- but reads poorly
1 in [1, 2] in [[1, 2], [3, 4]]
# means: (1 in [1,2]) and ([1,2] in [[1,2],[3,4]])
# True and True -> True
```

This is almost never what you want. Avoid chaining `in`.

### `is` and `is not`

```python
# Valid but unusual
a = b = None
a is b is None    # True -- means (a is b) and (b is None)
```

Stick to explicit `and` for identity checks. The chained form is too easy to misread.

### Cannot chain across assignment

```python
# This is NOT a chained comparison -- it is two assignments
a = b = 5    # assigns 5 to both a and b

# This is a SyntaxError
# (a = 5) < 10    -- walrus operator is a separate topic
```

## Comparison Operators Reference

|Operator|Meaning|
|---|---|
|`<`|strictly less than|
|`<=`|less than or equal|
|`>`|strictly greater than|
|`>=`|greater than or equal|
|`==`|equal in value|
|`!=`|not equal in value|
|`is`|same object in memory|
|`is not`|different objects in memory|
|`in`|membership|
|`not in`|non-membership|

All of the above can appear in chains. The semantic risk is highest with `!=`, `is`, and `in` as noted above.

---

## Comparison Table -- Chained vs Explicit

|Chained|Explicit equivalent|Notes|
|---|---|---|
|`a < b < c`|`a < b and b < c`|`b` evaluated once|
|`a == b == c`|`a == b and b == c`|all three must be equal|
|`a != b != c`|`a != b and b != c`|does NOT ensure `a != c`|
|`0 <= x < n`|`x >= 0 and x < n`|canonical array bounds check|

## Common Pitfalls

```python
# Pitfall 1 -- != does not mean "all different"
x, y, z = 1, 2, 1
x != y != z    # True -- misleading, x == z
```

```python
# Pitfall 2 -- chaining is and == together
x = 1
x is 1 == True    # evaluated as (x is 1) and (1 == True)
                  # True and True -> True
                  # but this is fragile and unreadable -- avoid
```

```python
# Pitfall 3 -- confusing chained comparison with two separate expressions
# This is a chained comparison:
print(1 < 2 < 3)      # True

# This is NOT -- it is (1 < 2) then comparing bool to 3:
# (True) < 3   ->   1 < 3   ->   True  (since True == 1)
# Looks right but for the wrong reason
```

## Style Guidelines

Use chained comparisons when:

- Expressing a mathematical range: `0 <= x < n`, `low < val <= high`
- The chain is at most three terms
- All operators point the same direction (strictly increasing or decreasing bounds)

Avoid chained comparisons when:

- Mixing `!=` with other operators
- Chaining more than three terms -- breaks readability
- Using `is`, `in`, or `not in` -- use explicit `and` instead

```python
# Clear -- use chaining
if 0 <= index < len(array):
    return array[index]

# Unclear -- use explicit and
if a is not None and b is not None:
    compute(a, b)
```
