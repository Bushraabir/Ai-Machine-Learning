# 20. Default and Keyword Arguments

---

## Core Idea

Default arguments let callers omit parameters that have sensible fallback values. Keyword arguments let callers name the parameters they are supplying, regardless of order. Together they make function interfaces flexible, readable, and self-documenting.

Without them, every caller must supply every argument in the exact correct order — fragile and verbose. With them, a function can have a simple common case and a rich set of options for advanced use.

```python
# Without defaults — caller must supply everything every time
def connect(host, port, timeout, ssl, retries):
    ...

connect("localhost", 5432, 30, False, 3)   # what does False mean here?

# With defaults and keyword arguments — clear, flexible
def connect(host, port, timeout=30, ssl=False, retries=3):
    ...

connect("localhost", 5432)                  # common case — clean
connect("localhost", 5432, ssl=True)        # one option changed — obvious
connect("prod.server.com", 5432, timeout=60, ssl=True, retries=5)  # full config
```

---

## Default Arguments

### Syntax

```python
def function(param=default_value):
    ...
```

Any parameter can have a default. Parameters with defaults are optional at call time. If the caller omits them, the default is used.

```python
def greet(name, greeting="Hello", punctuation="!"):
    return f"{greeting}, {name}{punctuation}"

print(greet("Alice"))                        # Hello, Alice!
print(greet("Alice", "Hi"))                  # Hi, Alice!
print(greet("Alice", "Hey", "."))            # Hey, Alice.
```

---

### Ordering Rule

Parameters without defaults must come before parameters with defaults.

```python
# Valid
def f(a, b, c=3, d=4): ...

# SyntaxError — non-default after default
def f(a=1, b, c=3): ...
```

This is enforced by Python's parser. If you could have `a=1` before `b`, calling `f(2)` would be ambiguous — does `2` fill `a` or `b`?

---

### When Defaults Are Evaluated — The Critical Detail

Default values are evaluated **once**, when the `def` statement is executed — not each time the function is called.

```python
import datetime

def log(message, timestamp=datetime.datetime.now()):
    print(f"{timestamp}: {message}")

log("first call")    # timestamp: <time when module was loaded>
log("second call")   # timestamp: same fixed time — not "now"
```

The `datetime.datetime.now()` is called once at function definition time. Both calls get the same timestamp. This is almost never what you want for mutable or time-dependent defaults.

**For dynamic defaults, use `None` as sentinel:**

```python
def log(message, timestamp=None):
    if timestamp is None:
        timestamp = datetime.datetime.now()    # evaluated each call
    print(f"{timestamp}: {message}")
```

---

### The Mutable Default Argument Trap

The most dangerous consequence of "evaluated once". Mutable objects (lists, dicts, sets) accumulate state across calls.

```python
# Wrong
def add_item(item, container=[]):
    container.append(item)
    return container

print(add_item("a"))    # ["a"]
print(add_item("b"))    # ["a", "b"]  — not ["b"]
print(add_item("c"))    # ["a", "b", "c"]  — keeps growing

# The list [] was created once — every call shares it
```

```python
# Correct — None sentinel pattern
def add_item(item, container=None):
    if container is None:
        container = []
    container.append(item)
    return container

print(add_item("a"))    # ["a"]
print(add_item("b"))    # ["b"]  — fresh list each time
```

This applies to all mutable defaults:

```python
# Wrong
def f(data={}): ...
def f(data=set()): ...

# Correct
def f(data=None):
    if data is None:
        data = {}
```

In ML code, this bug surfaces when a default list accumulates samples or metrics across multiple training runs in the same session. The list grows unbounded and results from run 1 pollute run 2. Always use `None`.

---

### Inspecting Defaults

Python stores defaults on the function object:

```python
def f(a, b=10, c=20):
    pass

print(f.__defaults__)    # (10, 20) — defaults for b and c
```

This is rarely needed in application code but useful for debugging and in frameworks that introspect function signatures.

## Keyword Arguments

### Syntax

At the call site, you can name the parameter you are supplying:

```python
def power(base, exponent):
    return base ** exponent

power(2, 10)                      # positional — base=2, exponent=10
power(base=2, exponent=10)        # keyword — same result
power(exponent=10, base=2)        # keyword — order doesn't matter
power(2, exponent=10)             # mixed — positional first, then keyword
```

Positional arguments must always come before keyword arguments:

```python
power(base=2, 10)    # SyntaxError — positional after keyword
```

---

### Clarity at the Call Site

Keyword arguments make function calls self-documenting. For functions with many parameters or boolean flags, they are essential for readability.

```python
# Positional — what do these mean?
train(model, data, 0.001, 32, 100, True, False)

# Keyword — immediately clear
train(
    model        = model,
    data         = data,
    lr           = 0.001,
    batch_size   = 32,
    epochs       = 100,
    shuffle      = True,
    verbose      = False,
)
```

The second form takes more lines but is unambiguous. When reviewing or debugging code six months later, this difference is enormous.

---

### Combining Positional and Keyword Arguments

```python
def connect(host, port, timeout=30, ssl=False, retries=3):
    ...

# These are all valid
connect("localhost", 5432)
connect("localhost", 5432, timeout=60)
connect("localhost", 5432, 60)               # timeout by position
connect("localhost", 5432, ssl=True)
connect("localhost", 5432, retries=5, ssl=True)   # keyword order irrelevant
connect("localhost", port=5432, timeout=60)
```

## Keyword-Only Arguments

Forcing callers to use keyword syntax for specific parameters is done with a bare `*` in the signature or by placing parameters after `*args`.

### Bare Star `*` — Keyword-Only Separator

```python
def create_model(architecture, *, lr=0.001, epochs=100, dropout=0.5):
    ...
```

Parameters after `*` can only be passed by name. The `*` itself absorbs no arguments — it is a positional barrier.

```python
create_model("resnet50")                          # defaults for all
create_model("resnet50", lr=0.01)                 # one keyword
create_model("resnet50", 0.01, 100, 0.5)         # TypeError — no positional after *
create_model("resnet50", lr=0.01, epochs=50)      # correct
```

### Why Force Keyword-Only?

```python
# Without keyword-only — easy to pass args in wrong order silently
def resize(image, width, height):
    ...

resize(img, 800, 600)    # width=800 or height=800? must check signature

# With keyword-only — order cannot matter
def resize(image, *, width, height):
    ...

resize(img, width=800, height=600)    # unambiguous — always
resize(img, height=600, width=800)    # same result
resize(img, 800, 600)                 # TypeError — forced to name them
```

Keyword-only is especially important for:

- Functions with many optional parameters
- Boolean flags that would be confusing positionally
- API design where adding parameters later should not break existing callers

---

### After `*args` — Also Keyword-Only

```python
def f(*args, separator=", "):
    return separator.join(str(a) for a in args)

print(f(1, 2, 3))                  # "1, 2, 3"  — uses default
print(f(1, 2, 3, separator=" | ")) # "1 | 2 | 3"
print(f(1, 2, 3, " | "))           # TypeError — separator is keyword-only
```

`separator` cannot be passed positionally because `*args` would absorb it.

---

## Positional-Only Arguments — `/`

The mirror of keyword-only. Parameters before `/` cannot be passed by name.

```python
def f(a, b, /, c, d):
    print(a, b, c, d)

f(1, 2, 3, 4)          # valid
f(1, 2, c=3, d=4)      # valid — c and d can be keyword
f(1, b=2, c=3, d=4)    # TypeError — b is positional-only
f(a=1, b=2, c=3, d=4)  # TypeError — a and b are positional-only
```

Used primarily in built-in functions and library APIs where parameter names are implementation details and should not be part of the public interface.

```python
# These built-ins use positional-only
abs(-5)          # abs(x, /) — x is positional-only
len([1,2,3])     # len(obj, /) — obj is positional-only
```

---

## Full Parameter Ordering Reference

When all types appear together:

```
def f(pos_only, /, standard, *args, kw_only, **kwargs):
```

```python
def f(a, b, /, c, d=10, *args, kw1, kw2=20, **kwargs):
    print(f"a={a}, b={b}, c={c}, d={d}")
    print(f"args={args}")
    print(f"kw1={kw1}, kw2={kw2}")
    print(f"kwargs={kwargs}")

f(1, 2, 3, 4, 5, 6, kw1="x", extra="y")
# a=1, b=2, c=3, d=4
# args=(5, 6)
# kw1="x", kw2=20
# kwargs={"extra": "y"}
```

In practice, most functions use only two or three of these types. Knowing the full order lets you read any function signature without confusion.

## Passing Dicts and Lists as Arguments

### Unpacking a Dict as Keyword Arguments

```python
def connect(host, port, timeout=30):
    print(host, port, timeout)

config = {"host": "localhost", "port": 5432, "timeout": 60}
connect(**config)    # equivalent to connect(host="localhost", port=5432, timeout=60)
```

This pattern appears constantly in ML config management:

```python
model_config = {
    "architecture": "resnet50",
    "pretrained": True,
    "num_classes": 10,
}

model = build_model(**model_config)
# equivalent to build_model(architecture="resnet50", pretrained=True, num_classes=10)
```

### Unpacking a List as Positional Arguments

```python
def add(a, b, c):
    return a + b + c

args = [1, 2, 3]
print(add(*args))    # 6
```

### Mixing Both

```python
def f(a, b, c, d):
    print(a, b, c, d)

f(*[1, 2], **{"c": 3, "d": 4})    # 1 2 3 4
```

## Practical Design Patterns

### Configuration Object Pattern

For functions with many parameters, accept a config object or dict:

```python
from dataclasses import dataclass

@dataclass
class TrainConfig:
    lr:         float = 0.001
    epochs:     int   = 100
    batch_size: int   = 32
    optimizer:  str   = "adam"
    verbose:    bool  = True

def train(model, data, config=None):
    if config is None:
        config = TrainConfig()
    # use config.lr, config.epochs, etc.
```

### Fluent Override Pattern

Accept `**kwargs` to allow overriding a subset of defaults:

```python
DEFAULT_CONFIG = {
    "lr":         0.001,
    "epochs":     100,
    "batch_size": 32,
    "optimizer":  "adam",
}

def train(model, data, **overrides):
    config = {**DEFAULT_CONFIG, **overrides}    # merge, overrides win
    print(config)

train(model, data, lr=0.01, epochs=50)
# {"lr": 0.01, "epochs": 50, "batch_size": 32, "optimizer": "adam"}
```

### Forwarding All Arguments

```python
def wrapper(func, *args, **kwargs):
    print("before")
    result = func(*args, **kwargs)
    print("after")
    return result

wrapper(connect, "localhost", 5432, timeout=60)
```

## Summary

|Feature|Syntax|Effect|
|---|---|---|
|Default value|`def f(x=10)`|x is optional — uses 10 if omitted|
|Keyword argument|`f(x=5)`|Pass by name at call site|
|Keyword-only|`def f(*, x)`|x must be named at call site|
|Positional-only|`def f(x, /)`|x cannot be named at call site|
|Mutable default|Never — use `None` sentinel|Shared state across calls — bug|
|Unpack dict|`f(**d)`|Dict keys become keyword arguments|
|Unpack list|`f(*lst)`|List elements become positional arguments|

## Common Mistakes to Avoid

```python
# Mistake 1: mutable default argument
def f(data=[]):          # wrong — list persists across calls
def f(data=None):        # correct — use None sentinel
    if data is None:
        data = []

# Mistake 2: time-sensitive default evaluated once
def log(msg, t=datetime.now()):   # wrong — same timestamp every call
def log(msg, t=None):             # correct
    if t is None:
        t = datetime.now()

# Mistake 3: positional argument after keyword argument
f(1, key="x", 2)         # SyntaxError

# Mistake 4: passing wrong type to keyword-only parameter
def f(*, n=10): ...
f(5)                      # TypeError — n is keyword-only, cannot pass positionally
f(n=5)                    # correct

# Mistake 5: duplicate argument
def f(a, b=2): ...
f(1, a=5)                 # TypeError: f() got multiple values for argument 'a'

# Mistake 6: expecting **kwargs to preserve insertion order in old Python
# (Python 3.7+ guarantees dict insertion order — this is safe in modern Python)

# Mistake 7: forgetting that keyword args can still be passed positionally
def f(a, b=10, c=20): ...
f(1, 2)    # b=2, not a keyword arg — can still be positional
# to force keyword: def f(a, *, b=10, c=20)
```
