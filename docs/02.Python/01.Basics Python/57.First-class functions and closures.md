# 57. First-Class Functions and Closures

> _"A language that treats functions as first-class objects is a language where computation itself becomes a value you can store, pass, and transform. Closures are what happens when a function carries its birthplace with it."_

---

## Part I — First-Class Functions

### What "First-Class" Means

An entity is **first-class** in a language if it can be:

1. Assigned to a variable
2. Passed as an argument to a function
3. Returned from a function
4. Stored in a data structure

In Python, **functions satisfy all four**. They are objects — instances of the type `function` — with identity, attributes, and a refcount like any other object.

```python
def square(x):
    return x ** 2

print(type(square))     # <class 'function'>
print(square.__name__)  # 'square'
print(id(square))       # some memory address
```

The name `square` is just a label bound to a function object. It is not special. You can rebind it, delete it, or ignore it entirely.

---

### 1. Assigning Functions to Variables

```python
def greet(name):
    return f"Hello, {name}"

say_hello = greet       # say_hello and greet point to the same object

print(say_hello("Alice"))   # "Hello, Alice"
print(say_hello is greet)   # True — same function object
```

```
Memory:

    greet    ──────────────► function object (greet)
    say_hello ─────────────────────────────────────┘
```

Deleting `greet` does not destroy the function — `say_hello` still holds a reference.

```python
del greet
print(say_hello("Bob"))   # "Hello, Bob" — still works
```

---

### 2. Passing Functions as Arguments (Higher-Order Functions)

A function that **accepts another function as an argument** is a **higher-order function**.

```python
def apply(func, value):
    return func(value)

def double(x):
    return x * 2

def square(x):
    return x ** 2

print(apply(double, 5))   # 10
print(apply(square, 5))   # 25
```

This is the mechanism behind `map`, `filter`, `sorted`:

```python
data = [3, 1, 4, 1, 5, 9, 2, 6]

# sorted accepts a key function
sorted_data = sorted(data, key=lambda x: -x)   # descending
print(sorted_data)   # [9, 6, 5, 4, 3, 2, 1, 1]

# map applies a function to every element
squares = list(map(square, data))
print(squares)       # [9, 1, 16, 1, 25, 81, 4, 36]

# filter keeps elements where function returns True
evens = list(filter(lambda x: x % 2 == 0, data))
print(evens)         # [4, 2, 6]
```

---

### 3. Returning Functions from Functions

A function can produce another function as its output.

```python
def make_multiplier(n):
    def multiplier(x):
        return x * n
    return multiplier          # return the inner function object

triple = make_multiplier(3)
print(triple(10))   # 30
print(triple(7))    # 21

double = make_multiplier(2)
print(double(10))   # 20
```

`make_multiplier` is a **function factory** — a function whose purpose is to manufacture and return other functions. `triple` and `double` are independent function objects, each carrying their own value of `n`. This is a closure — explained in depth in Part II.

---

### 4. Storing Functions in Data Structures

```python
operations = {
    "add":      lambda a, b: a + b,
    "subtract": lambda a, b: a - b,
    "multiply": lambda a, b: a * b,
    "divide":   lambda a, b: a / b,
}

op = "multiply"
result = operations[op](6, 7)
print(result)    # 42
```

This pattern — a dispatch table — replaces long `if/elif` chains with a dictionary lookup. It is $O(1)$ instead of $O(n)$ and far more extensible.

```python
# Pipeline as a list of functions
pipeline = [str.strip, str.lower, lambda s: s.replace(" ", "_")]

def run_pipeline(text, steps):
    for step in steps:
        text = step(text)
    return text

print(run_pipeline("  Hello World  ", pipeline))   # "hello_world"
```

### Function Attributes and Introspection

Because functions are objects, they have attributes you can read — and set.

```python
def train(model, epochs=10):
    """Train the model for a given number of epochs."""
    pass

print(train.__name__)       # 'train'
print(train.__doc__)        # 'Train the model for a given number of epochs.'
print(train.__defaults__)   # (10,)
print(train.__code__.co_varnames)  # ('model', 'epochs')

# You can attach arbitrary attributes
train.version = "1.0"
print(train.version)        # "1.0"
```

This is useful in frameworks. Flask uses `func.__name__` as the default route name. pytest uses function names to identify tests. Decorators use `functools.wraps` to preserve these attributes when wrapping functions.

## Part II — Closures

### The Problem Closures Solve

When an inner function references a variable from the enclosing function's scope, what happens after the enclosing function returns? Normally, local variables are destroyed when a function exits. But if an inner function holds a reference to them, they cannot be destroyed — they must live on.

A **closure** is a function object that **captures and retains the variables from the scope in which it was defined**, even after that scope has exited.

---

### Anatomy of a Closure

```python
def make_counter():
    count = 0                   # free variable — lives in the enclosing scope

    def increment():
        nonlocal count
        count += 1
        return count

    return increment            # return the inner function

counter = make_counter()        # make_counter's frame exits here
                                # but count is NOT destroyed

print(counter())   # 1
print(counter())   # 2
print(counter())   # 3
```

After `make_counter()` returns, its local frame is gone. But `increment` holds a reference to `count` via its **closure cell**. As long as `counter` (the returned function) is alive, `count` is alive.

```
make_counter() frame exits:
    ┌──────────────────────────────────────────────────────┐
    │  closure cell: { count = 0 }                         │
    │       ▲                                              │
    │       │  referenced by                               │
    │  increment function object ◄── counter (in caller)   │
    └──────────────────────────────────────────────────────┘
```

---

### Inspecting Closure Cells

Python exposes closures through the `__closure__` attribute:

```python
def make_adder(n):
    def adder(x):
        return x + n
    return adder

add5 = make_adder(5)
add10 = make_adder(10)

print(add5.__closure__)                    # (<cell at 0x...>,)
print(add5.__closure__[0].cell_contents)   # 5
print(add10.__closure__[0].cell_contents)  # 10
```

Each call to `make_adder` creates a **new closure cell** with its own value of `n`. `add5` and `add10` are independent — they do not share state.

```python
print(add5(3))    # 8
print(add10(3))   # 13
```

---

### `nonlocal` — Rebinding Enclosing Variables

Inside a closure, you can **read** an enclosing variable freely. But to **rebind** it (assignment, `+=`, etc.), you must declare it `nonlocal`. Without `nonlocal`, Python treats the assignment as creating a new local variable, shadowing the enclosing one.

```python
def make_counter():
    count = 0

    def increment():
        count += 1      # UnboundLocalError! Python sees assignment → local variable
                        # but count has no local value yet
        return count

    return increment
```

```python
def make_counter():
    count = 0

    def increment():
        nonlocal count  # tell Python: count lives in the enclosing scope
        count += 1      # now this rebinds the enclosing count
        return count

    return increment
```

Contrast with `global`, which reaches all the way to the module level. `nonlocal` reaches only to the nearest enclosing scope that has the variable.

```
Scope resolution (LEGB):
    Local → Enclosing → Global → Built-in

nonlocal → Enclosing
global   → Global
(neither) → Local (new variable created on assignment)
```

---

### The Late-Binding Trap

One of the most common closure bugs in Python. Variables in a closure are looked up **at call time**, not at definition time.

```python
# Intention: create 5 functions that return 0, 1, 2, 3, 4
functions = []
for i in range(5):
    def f():
        return i        # i is a free variable — looked up when f() is called
    functions.append(f)

print([f() for f in functions])   # [4, 4, 4, 4, 4]  ← NOT [0, 1, 2, 3, 4]
```

Why? All five functions close over the **same variable `i`** in the enclosing scope (the module/function scope containing the loop). By the time any of them is called, the loop has finished and `i = 4`.

```
After loop:
    functions[0].__closure__[0] ──► cell containing i
    functions[1].__closure__[0] ──► same cell
    functions[2].__closure__[0] ──► same cell
    ...
    cell value: 4   ← loop finished here
```

**Fix 1: Default argument captures value at definition time**

```python
functions = []
for i in range(5):
    def f(i=i):         # default argument evaluated NOW, not at call time
        return i
    functions.append(f)

print([f() for f in functions])   # [0, 1, 2, 3, 4]  ← correct
```

**Fix 2: Factory function creates a new scope per iteration**

```python
def make_f(i):
    def f():
        return i        # i is now in a fresh enclosing scope each time
    return f

functions = [make_f(i) for i in range(5)]
print([f() for f in functions])   # [0, 1, 2, 3, 4]
```

Fix 2 is cleaner and more explicit. Each call to `make_f` creates a new scope with its own `i`. Fix 1 is a common idiom but can be confusing — a default argument has different semantics from a free variable.

### Multiple Closures Over Shared State

Two inner functions can close over the **same** enclosing variable, sharing mutable state:

```python
def make_account(balance):
    def deposit(amount):
        nonlocal balance
        balance += amount
        return balance

    def withdraw(amount):
        nonlocal balance
        if amount > balance:
            raise ValueError("Insufficient funds")
        balance -= amount
        return balance

    def get_balance():
        return balance          # read-only, no nonlocal needed

    return deposit, withdraw, get_balance

deposit, withdraw, get_balance = make_account(100)

print(deposit(50))      # 150
print(withdraw(30))     # 120
print(get_balance())    # 120
```

All three functions close over the **same `balance` cell**. This is a lightweight alternative to a class — stateful behaviour with no class definition. In functional programming, this pattern is called a **closure-based object**.

## Part III — The ML and Framework Connection

### Callbacks and Training Loops

The most pervasive use of first-class functions in ML code:

```python
import math

def make_lr_scheduler(initial_lr, decay_rate, decay_steps):
    """Returns a function: step → learning_rate"""
    def scheduler(step):
        return initial_lr * (decay_rate ** (step / decay_steps))
    return scheduler

scheduler = make_lr_scheduler(initial_lr=0.1, decay_rate=0.5, decay_steps=1000)

for step in range(0, 3001, 1000):
    print(f"Step {step}: lr = {scheduler(step):.6f}")

# Step 0:    lr = 0.100000
# Step 1000: lr = 0.050000
# Step 2000: lr = 0.025000
# Step 3000: lr = 0.012500
```

PyTorch's `torch.optim.lr_scheduler.LambdaLR` takes exactly this: a function from step number to a multiplier. You pass a closure.

```python
import torch

optimizer = torch.optim.SGD(model.parameters(), lr=0.1)
scheduler = torch.optim.lr_scheduler.LambdaLR(
    optimizer,
    lr_lambda=lambda step: 0.95 ** step   # closure over nothing, but a first-class function
)
```

### Loss Functions as First-Class Objects

```python
def make_weighted_loss(alpha):
    """Returns a loss function with baked-in class weight."""
    def weighted_bce(y_pred, y_true):
        bce = -(y_true * torch.log(y_pred) + (1 - y_true) * torch.log(1 - y_pred))
        weights = y_true * alpha + (1 - y_true) * 1.0
        return (weights * bce).mean()
    return weighted_bce

# For a dataset where positive class is 10x rarer
loss_fn = make_weighted_loss(alpha=10.0)
loss = loss_fn(predictions, targets)
```

The loss function is a closure — it carries `alpha` with it. You can create multiple loss functions with different weights and pass them around like any other value.

### Hooks in PyTorch

PyTorch's hook system is entirely built on first-class functions. A hook is a function you register to be called at a specific point in the forward or backward pass.

```python
activations = {}

def make_hook(layer_name):
    def hook(module, input, output):
        activations[layer_name] = output.detach()   # closes over layer_name and activations
    return hook

model.layer1.register_forward_hook(make_hook("layer1"))
model.layer2.register_forward_hook(make_hook("layer2"))

output = model(input_tensor)
# activations["layer1"] and activations["layer2"] are now populated
```

Each hook is a closure capturing `layer_name`. The factory `make_hook` avoids the late-binding trap — each call creates a new scope with its own `layer_name`.

### Decorators Are Built on This Entirely

This note is the prerequisite for [[58. Writing and Applying Decorators]]. A decorator is a higher-order function that takes a function, returns a function (usually a closure), and attaches behaviour:

```python
def timer(func):                        # higher-order function
    import time
    def wrapper(*args, **kwargs):       # closure over func
        start = time.time()
        result = func(*args, **kwargs)  # func is a free variable
        end = time.time()
        print(f"{func.__name__} took {end - start:.4f}s")
        return result
    return wrapper                      # return the closure

@timer
def train_epoch(model, data):
    pass
# equivalent to: train_epoch = timer(train_epoch)
```

`wrapper` is a closure over `func`. Every concept here — first-class functions, enclosing scope, free variables, returning functions — is operating at once.

## Summary

```
First-class functions:
    Functions are objects. They have identity, attributes, refcounts.
    They can be assigned, passed, returned, stored — like any value.

Higher-order functions:
    Functions that accept or return other functions.
    map, filter, sorted, decorators are all built on this.

Closures:
    An inner function that captures variables from its enclosing scope.
    Those variables (free variables) are stored in closure cells.
    They survive after the enclosing function's frame exits.
    Accessed via func.__closure__[i].cell_contents.

nonlocal:
    Required to rebind (not just read) an enclosing variable.
    Without it, assignment creates a new local variable, shadowing the enclosing one.

Late-binding trap:
    Free variables are resolved at CALL TIME, not definition time.
    All closures in a loop share the same variable cell.
    Fix: default argument (captures at definition) or factory function (new scope).

Shared mutable state:
    Multiple closures over the same cell share state.
    This is the functional alternative to a class with instance variables.
```
