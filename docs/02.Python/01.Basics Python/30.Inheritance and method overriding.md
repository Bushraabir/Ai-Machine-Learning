# 30. Inheritance and Method Overriding

## What Inheritance Is

Inheritance is a mechanism where one class (the **subclass** or **child**) automatically receives all the attributes and methods of another class (the **superclass** or **parent**), without rewriting them. The subclass can then extend or replace any of that inherited behavior.

The fundamental purpose is **code reuse with specialization**. You define common behavior once on the parent, then build specialized variants as children.

```python
class Animal:
    def __init__(self, name):
        self.name = name

    def breathe(self):
        return f"{self.name} breathes oxygen"

    def speak(self):
        return "..."

class Dog(Animal):     # Dog inherits from Animal
    pass               # nothing added yet

d = Dog("Rex")
print(d.breathe())    # Rex breathes oxygen  — inherited from Animal
print(d.name)         # Rex                  — inherited __init__
```

`Dog` inherits everything. You wrote zero methods on it and it already works — because the lookup chain climbs to `Animal` when it cannot find the attribute on `Dog`.

---

## Syntax

```python
class Parent:
    pass

class Child(Parent):       # single inheritance
    pass

class Child(Parent1, Parent2):   # multiple inheritance
    pass
```

Every class in Python implicitly inherits from `object` if no parent is specified:

```python
class Foo:
    pass

print(Foo.__bases__)    # (<class 'object'>,)
print(isinstance(Foo(), object))   # True
```

`object` is the root of all Python classes. It provides default implementations of `__repr__`, `__str__`, `__eq__`, `__hash__`, and others.

## Method Overriding

**Overriding** means defining a method in the subclass with the same name as a method in the parent. Python's lookup chain finds the subclass version first, so the parent's version is replaced for that class.

```python
class Animal:
    def speak(self):
        return "..."

class Dog(Animal):
    def speak(self):         # overrides Animal.speak
        return "Woof"

class Cat(Animal):
    def speak(self):         # overrides Animal.speak
        return "Meow"

class Fish(Animal):
    pass                     # inherits Animal.speak unchanged

animals = [Dog("Rex"), Cat("Luna"), Fish("Nemo")]
for a in animals:
    print(a.speak())
# Woof
# Meow
# ...
```

Each subclass provides its own version of `speak`. The caller does not need to know which subclass it has — it just calls `speak()` and gets the right behavior. This is **polymorphism**.

---

## The Method Resolution Order (MRO)

When Python looks up an attribute, it follows a deterministic sequence called the **MRO** — the order in which it searches classes. For single inheritance it is linear. For multiple inheritance, Python uses the **C3 linearization algorithm**.

```python
class A:
    def hello(self):
        return "A"

class B(A):
    def hello(self):
        return "B"

class C(A):
    def hello(self):
        return "C"

class D(B, C):
    pass

print(D.__mro__)
# (<class 'D'>, <class 'B'>, <class 'C'>, <class 'A'>, <class 'object'>)

print(D().hello())   # B — first class in MRO that defines hello
```

Inspect MRO at any time:

```python
print(D.__mro__)        # tuple of classes in resolution order
print(D.mro())          # same, as a list
```

The rule: **left to right, depth before breadth, no class appears twice**.

## Extending the Parent — Calling `super()`

Often you want to **extend** the parent's method rather than completely replace it. You keep the parent's logic and add to it. `super()` gives you a proxy to the parent class in MRO order.

```python
class Animal:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def describe(self):
        return f"{self.name}, age {self.age}"

class Dog(Animal):
    def __init__(self, name, age, breed):
        super().__init__(name, age)    # run Animal.__init__ first
        self.breed = breed             # then add Dog-specific attribute

    def describe(self):
        base = super().describe()      # get Animal's description
        return f"{base}, breed: {self.breed}"  # extend it

d = Dog("Rex", 3, "Labrador")
print(d.describe())   # Rex, age 3, breed: Labrador
```

Without `super().__init__()`, `self.name` and `self.age` would never be set — Dog's `__init__` would need to duplicate that code. `super()` eliminates that duplication. See [[31. super()]] for the full treatment.

## Three Patterns of Override

### 1. Full Replacement — Ignore the Parent Entirely

```python
class Shape:
    def area(self):
        return 0

class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius

    def area(self):
        import math
        return math.pi * self.radius ** 2   # completely replaces Shape.area
```

Use when the parent's implementation has nothing useful to offer.

### 2. Extension — Call Parent, Then Add

```python
class Vehicle:
    def start(self):
        print("Engine on")

class ElectricVehicle(Vehicle):
    def start(self):
        super().start()             # parent runs first
        print("Battery check done")  # then child adds

ev = ElectricVehicle()
ev.start()
# Engine on
# Battery check done
```

Use when the parent's logic must still run — you are adding to it, not replacing it.

### 3. Pre-processing — Add First, Then Call Parent

```python
class LoggedDict(dict):
    def __setitem__(self, key, value):
        print(f"Setting {key} = {value}")
        super().__setitem__(key, value)   # parent runs after logging

d = LoggedDict()
d["x"] = 10   # Setting x = 10
print(d["x"]) # 10
```

Use when you need to validate, transform, or log before delegating to the parent.

## `isinstance()` and `issubclass()`

These two functions expose the inheritance hierarchy at runtime.

```python
class Animal: pass
class Dog(Animal): pass
class Cat(Animal): pass

d = Dog()

print(isinstance(d, Dog))     # True  — d is a Dog
print(isinstance(d, Animal))  # True  — Dog IS-A Animal
print(isinstance(d, Cat))     # False

print(issubclass(Dog, Animal))  # True
print(issubclass(Dog, object))  # True  — everything is a subclass of object
print(issubclass(Animal, Dog))  # False — not the other direction
```

`isinstance` is preferred over `type(obj) == SomeClass` because it respects the inheritance hierarchy. A `Dog` IS-A `Animal` — `isinstance` knows this, `type() ==` does not.

## A Complete Hierarchy — The IS-A Test

Before creating an inheritance relationship, apply the **IS-A test**: does the child genuinely IS-A parent?

- ✅ `Dog` IS-A `Animal` — valid
- ✅ `CheckingAccount` IS-A `BankAccount` — valid
- ✅ `LinearLayer` IS-A `Module` — valid (PyTorch's design)
- ❌ `Engine` IS-A `Car` — wrong. Engine HAS-A relationship with Car (use composition instead)

```python
class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("Deposit must be positive")
        self.balance += amount
        return self.balance

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("Insufficient funds")
        self.balance -= amount
        return self.balance

    def __repr__(self):
        return f"{self.__class__.__name__}(owner={self.owner}, balance={self.balance})"


class SavingsAccount(BankAccount):
    def __init__(self, owner, balance=0, interest_rate=0.03):
        super().__init__(owner, balance)
        self.interest_rate = interest_rate

    def apply_interest(self):
        interest = self.balance * self.interest_rate
        self.balance += interest
        return interest


class CheckingAccount(BankAccount):
    def __init__(self, owner, balance=0, overdraft_limit=500):
        super().__init__(owner, balance)
        self.overdraft_limit = overdraft_limit

    def withdraw(self, amount):          # overrides — allows overdraft
        if amount > self.balance + self.overdraft_limit:
            raise ValueError("Exceeds overdraft limit")
        self.balance -= amount
        return self.balance


s = SavingsAccount("Alice", 1000, 0.05)
s.deposit(500)               # inherited from BankAccount
s.apply_interest()           # only on SavingsAccount
print(s)                     # SavingsAccount(owner=Alice, balance=1575.0)

c = CheckingAccount("Bob", 100, overdraft_limit=200)
c.withdraw(250)              # uses CheckingAccount.withdraw — overdraft allowed
print(c)                     # CheckingAccount(owner=Bob, balance=-150)
```

`__repr__` uses `self.__class__.__name__` — so it prints `SavingsAccount` for savings instances and `CheckingAccount` for checking instances, even though the method is defined only once on `BankAccount`.

## Multiple Inheritance

Python supports inheriting from more than one parent. The MRO resolves conflicts.

```python
class Flyable:
    def move(self):
        return "flying"

    def describe(self):
        return "I can fly"

class Swimmable:
    def move(self):
        return "swimming"

    def describe(self):
        return "I can swim"

class Duck(Flyable, Swimmable):
    pass

d = Duck()
print(d.move())      # flying — Flyable is first in MRO
print(d.describe())  # I can fly

print(Duck.__mro__)
# (<class 'Duck'>, <class 'Flyable'>, <class 'Swimmable'>, <class 'object'>)
```

**The diamond problem** — when two parents share a grandparent, the MRO ensures the grandparent's method runs exactly once:

```python
class A:
    def greet(self):
        return "A"

class B(A):
    def greet(self):
        return "B → " + super().greet()

class C(A):
    def greet(self):
        return "C → " + super().greet()

class D(B, C):
    def greet(self):
        return "D → " + super().greet()

print(D().greet())   # D → B → C → A
print(D.__mro__)     # D, B, C, A, object
```

`super()` in each class calls the **next class in the MRO**, not the literal parent. This ensures `A.greet` runs once, not twice. This cooperative `super()` pattern is the correct way to handle multiple inheritance.

## Inheritance in ML Frameworks — Why This Matters Now

PyTorch's entire model system is built on inheritance:

```python
# Simplified version of how PyTorch nn.Module works

class Module:
    def __init__(self):
        self._parameters = {}
        self._modules = {}

    def forward(self, x):
        raise NotImplementedError

    def __call__(self, x):
        return self.forward(x)   # calls the subclass's forward


class Linear(Module):
    def __init__(self, in_features, out_features):
        super().__init__()       # sets up _parameters, _modules
        self.in_features = in_features
        self.out_features = out_features

    def forward(self, x):
        # matrix multiply x by weights
        return x   # simplified


class MyNetwork(Module):
    def __init__(self):
        super().__init__()
        self.layer1 = Linear(784, 128)
        self.layer2 = Linear(128, 10)

    def forward(self, x):
        x = self.layer1(x)
        x = self.layer2(x)
        return x
```

When you write `class MyNetwork(nn.Module)` in real PyTorch, this is exactly what you are doing — inheriting from `Module`, calling `super().__init__()`, and overriding `forward`. The `forward` method is the prototypical override: `nn.Module` defines it as an abstract interface, and every model you write replaces it.

## Abstract Base Classes — Enforcing the Interface

Python's `abc` module lets you define methods that **must** be overridden by subclasses. If a subclass does not implement them, instantiation raises a `TypeError`.

```python
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self):
        pass

    @abstractmethod
    def perimeter(self):
        pass

    def describe(self):
        return f"Area: {self.area():.2f}, Perimeter: {self.perimeter():.2f}"

class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius

    def area(self):
        import math
        return math.pi * self.radius ** 2

    def perimeter(self):
        import math
        return 2 * math.pi * self.radius

class Square(Shape):
    def __init__(self, side):
        self.side = side

    def area(self):
        return self.side ** 2

    def perimeter(self):
        return 4 * self.side

# Shape()   ← TypeError: Can't instantiate abstract class
c = Circle(5)
print(c.describe())   # Area: 78.54, Perimeter: 31.42

s = Square(4)
print(s.describe())   # Area: 16.00, Perimeter: 16.00
```

Abstract base classes are the Pythonic way to define an **interface** — a contract that subclasses must fulfill. PyTorch's `nn.Module.forward` is effectively abstract (raises `NotImplementedError`), following the same pattern.

## Common Errors

```python
# 1. Forgetting super().__init__() — parent attributes never set
class Animal:
    def __init__(self, name):
        self.name = name

class Dog(Animal):
    def __init__(self, name, breed):
        self.breed = breed   # forgot super().__init__(name)

d = Dog("Rex", "Lab")
print(d.breed)   # Lab
print(d.name)    # AttributeError: 'Dog' has no attribute 'name'

# 2. Overriding without calling super() when extension was intended
class Dog(Animal):
    def __init__(self, name, breed):
        super().__init__(name)   # correct
        self.breed = breed

# 3. IS-A violation — using inheritance when composition is correct
class Engine:
    def start(self):
        return "Vroom"

class Car(Engine):           # wrong — Car is not an Engine
    pass

# Should be:
class Car:
    def __init__(self):
        self.engine = Engine()   # Car HAS-A Engine (composition)

# 4. Shadowing a class attribute accidentally via inheritance
class Parent:
    data = [1, 2, 3]

class Child(Parent):
    pass

Child.data.append(4)   # mutates Parent.data — shared mutable class attr
print(Parent.data)     # [1, 2, 3, 4]  — unintended
```

## Summary Table

|Concept|Key Point|
|---|---|
|Inheritance|Child gets all parent attributes and methods automatically|
|Override|Define same method name in child — child version wins|
|`super()`|Calls next class in MRO — used to extend, not replace|
|MRO|Left-to-right, depth-first, C3 linearization — no class appears twice|
|`isinstance`|Respects inheritance — `isinstance(Dog(), Animal)` is `True`|
|IS-A test|Only inherit if child genuinely IS-A parent — else use composition|
|`abstractmethod`|Forces subclasses to override — `TypeError` if they don't|
|Multiple inheritance|Python supports it — MRO handles diamond conflicts|
