## The Central Claim

In Python, **every value is an object**, and every object is either mutable or immutable. This is not a style preference or a performance hint — it is a fundamental property of the object that governs how assignment, function calls, container operations, and memory sharing behave.

Misunderstanding mutability is the source of an entire class of bugs that are silent, hard to reproduce, and devastating in ML pipelines where data flows through many transformations.

---

## What Mutability Means, Precisely

An object is **immutable** if its value cannot change after it is created. The bits that represent its content are fixed for its lifetime.

An object is **mutable** if its internal state can be modified in-place — without creating a new object, without changing the object's identity.

Python's identity operator `is` checks identity — whether two names point to the **same object in memory**, as measured by `id()`:

```python
a = [1, 2, 3]
b = a              # b and a point to the same list object
b.append(4)

print(a)           # [1, 2, 3, 4] — a sees the change
print(a is b)      # True — same object
print(id(a) == id(b))  # True — same memory address
```

The list was mutated. Its identity (`id`) did not change. The object at that address now contains different data.

Compare with an immutable object:

```python
x = "hello"
y = x
y = y + " world"   # creates a NEW string object

print(x)           # "hello" — unchanged
print(x is y)      # False — different objects
```

`y + " world"` did not modify the string at `y`'s address. It created a fresh string and rebound the name `y` to it. The original `"hello"` object is untouched.

## Identity, Equality, and the Integer Cache

Python caches small integers (typically −5 to 256) as singletons. This is a CPython implementation detail, not a language guarantee:

```python
a = 256
b = 256
print(a is b)    # True  — same cached object

a = 257
b = 257
print(a is b)    # False — separate objects (outside cache range)
print(a == b)    # True  — same value
```

The rule this enforces: **use `==` for value comparison, `is` for identity comparison**. The only objects you should check identity for are `None`, `True`, and `False` (which are singletons):

```python
if x is None:     # correct
if x == None:     # works but misleading — suggests value comparison
```

String interning is another caching mechanism — Python may intern string literals that look like identifiers:

```python
a = "hello"
b = "hello"
print(a is b)     # True  — interned (CPython, compile-time constant)

a = "hello world"
b = "hello world"
print(a is b)     # False (usually) — spaces make interning less likely
```

Never rely on string interning for correctness. Use `==`.

## The Aliasing Problem — Mutable Objects and Shared References

The most consequential consequence of mutability:

```python
original = [1, 2, 3]
alias    = original      # both names point to the same list

alias.append(4)
print(original)          # [1, 2, 3, 4] — you modified 'original' via 'alias'
```

This is **aliasing**: two names bound to the same object. With immutable objects, aliasing is harmless — you cannot modify the shared object, so both names always see the same value. With mutable objects, aliasing means any modification through one name is visible through all others.

```python
def add_element(lst):
    lst.append(99)        # modifies the object in place

data = [1, 2, 3]
add_element(data)
print(data)              # [1, 2, 3, 99] — the caller's list was modified
```

This is Python's pass-by-object-reference semantics (covered in depth in [[55.Pass-by-object-reference behavior]]). The function received the same list object — it did not receive a copy.

## Tuples — Immutability with a Caveat

A tuple is immutable: you cannot add, remove, or replace its elements. But if a tuple contains a mutable object, that object can still be mutated:

```python
t = ([1, 2], [3, 4])

t[0].append(99)      # legal — we're mutating the list, not the tuple
print(t)             # ([1, 2, 99], [3, 4])

t[0] = [5, 6]        # TypeError — cannot rebind tuple element
```

The tuple guarantees that the **references it holds** do not change. It does not guarantee that the **objects those references point to** do not change. The tuple at a fixed memory address always contains the same two references — but the list at the other end of the first reference can be arbitrarily modified.

This distinction matters for hashing: tuples are hashable (usable as dict keys) only if all their contained objects are also hashable:

```python
t1 = (1, 2, 3)
hash(t1)             # works — all ints are hashable

t2 = ([1, 2], 3)
hash(t2)             # TypeError: unhashable type: 'list'
```

## Immutability and Hashability

Only immutable objects can be used as dictionary keys or set members. The invariant: if an object's value could change, its hash could change, which would break the hash table's ability to find it.

```python
d = {}
d[(1, 2)] = "a tuple key"      # works
d[[1, 2]] = "a list key"        # TypeError: unhashable type: 'list'

s = {1, "hello", (1, 2)}        # works — int, str, tuple are hashable
s = {1, [1, 2]}                 # TypeError
```

Custom class instances are hashable by default (using `id()` as the hash). If you override `__eq__`, you must also override `__hash__` — or Python sets `__hash__ = None`, making your object unhashable. This is the correctness invariant: equal objects must have equal hashes.

## Rebinding vs. Mutating — The Critical Distinction

These two operations look similar but are fundamentally different:

```python
# REBINDING — creates a new object, changes what the name points to
x = 5
x = x + 1          # x now points to the integer 6; the integer 5 still exists

lst = [1, 2, 3]
lst = lst + [4]     # creates a new list; the original [1, 2, 3] is unchanged


# MUTATING — modifies the existing object in place
lst = [1, 2, 3]
lst.append(4)       # same list object, now containing [1, 2, 3, 4]
lst += [5]          # += on lists calls __iadd__ → in-place mutation, NOT rebinding
```

The `+=` behaviour is subtle and bites even experienced programmers:

```python
# For immutable types: += rebinds
x = 5
print(id(x))        # some address
x += 1
print(id(x))        # different address — new int object

# For mutable types: += mutates in place
lst = [1, 2, 3]
print(id(lst))      # some address
lst += [4]          # calls lst.__iadd__([4]) → extends in place
print(id(lst))      # same address — same list object
```

This creates an asymmetry: `lst += [4]` and `lst = lst + [4]` both result in `lst` containing `[1, 2, 3, 4]`, but:

- `lst += [4]` mutates the original list (visible to all aliases)
- `lst = lst + [4]` creates a new list (aliases still see the original)

```python
a = [1, 2, 3]
b = a

a += [4]            # mutates in place
print(b)            # [1, 2, 3, 4] — b sees it

a = a + [5]         # rebinds a to a new list
print(b)            # [1, 2, 3, 4] — b does NOT see this
```

## Mutable Default Arguments — The Classic Trap

This is one of the most notorious Python gotchas, rooted entirely in mutability:

```python
def append_to(element, lst=[]):    # lst=[] created ONCE when function is defined
    lst.append(element)
    return lst

print(append_to(1))    # [1]
print(append_to(2))    # [2] — expected, but...
print(append_to(3))    # [3] — wait
# Actually:
# [1]
# [1, 2]
# [1, 2, 3]
```

The default value `[]` is a mutable object created **once** when the `def` statement executes. It persists as an attribute of the function object (`append_to.__defaults__`) and is shared across all calls that use the default. Every call that does not pass `lst` mutates the same list.

The fix: use `None` as the sentinel and create a fresh list inside the function:

```python
def append_to(element, lst=None):
    if lst is None:
        lst = []
    lst.append(element)
    return lst

print(append_to(1))    # [1]
print(append_to(2))    # [2]
print(append_to(3))    # [3]
```

This applies to any mutable default: `[]`, `{}`, `set()`, custom class instances. Immutable defaults (`None`, `0`, `""`, `()`) are safe because they cannot be modified.

## Immutability for Correctness — Using `tuple` and `frozenset`

When you want to guarantee data is not modified, reach for immutable types:

```python
# Coordinates should not change — tuple over list
point = (3.14, 2.71)

# A fixed set of allowed labels — frozenset over set
VALID_LABELS = frozenset({"cat", "dog", "bird"})

# Config values that should not be mutated after setup
Config = collections.namedtuple("Config", ["lr", "epochs", "batch_size"])
cfg = Config(lr=0.001, epochs=90, batch_size=256)
cfg.lr = 0.01    # AttributeError — namedtuple is immutable
```

`frozenset` is hashable, so it can be used as a dict key or set member — useful for caching results keyed on sets of features.

## Visualisation — Object Model

```
Immutable (int, str, tuple, ...):

  name ──► [ object | value: fixed ]
              id: 0x7f1a

  rebinding:
  name ──► [ object | value: fixed ]   (new object, new id)
              id: 0x7f2b

  the old object at 0x7f1a is unchanged


Mutable (list, dict, set, ndarray, ...):

  name_a ──┐
            ├──► [ object | state: changeable ]
  name_b ──┘       id: 0x7f1a

  mutation:
  name_a ──┐
            ├──► [ object | state: CHANGED ]
  name_b ──┘       id: 0x7f1a  (same address — same object)

  name_a and name_b both see the change
```

## Connection to AI / Machine Learning / Deep Learning

Mutability is not an abstract Python concern in ML — it is the mechanism behind how tensors work, why gradient computation is correct, and how data pipelines can silently corrupt themselves.

### NumPy — Views vs. Copies

NumPy arrays are mutable. More critically, many NumPy operations return **views** — objects that share the underlying memory buffer with the original array:

```python
import numpy as np

a = np.array([1, 2, 3, 4, 5])
b = a[1:4]          # b is a VIEW of a, not a copy

b[0] = 99
print(a)            # [1, 99, 3, 4, 5] — a was modified through b
print(np.shares_memory(a, b))  # True
```

Slicing a NumPy array returns a view. Fancy indexing (boolean mask, integer array) returns a copy. This asymmetry is the source of countless ML bugs:

```python
# Which one gives you a view?
b = a[1:3]          # view — slice notation
b = a[[1, 2]]       # copy — fancy indexing
b = a[a > 2]        # copy — boolean mask
b = a.reshape(1, -1)  # view (if possible)
b = a.T             # view — transpose shares memory

# To guarantee a copy:
b = a.copy()
b = a[1:3].copy()
```

In a preprocessing pipeline, if you slice a batch and then normalise the slice in-place, you normalise the original data too. This corrupts your dataset silently.

```python
# Dangerous pattern in a data pipeline
def normalize(batch):
    batch -= batch.mean()      # in-place on the view
    batch /= batch.std()
    return batch

data = np.random.randn(1000, 128)
sample = data[:32]             # view
normalized = normalize(sample) # mutates data[:32] in place
# data is now partially normalised — the rest of it is not
```

Fix: either pass `data[:32].copy()` or use `batch = batch - batch.mean()` (rebinding, creates a new array).

### PyTorch — In-Place Operations and Autograd

PyTorch tensors are mutable, and in-place operations are marked with a trailing underscore by convention:

```python
import torch

x = torch.tensor([1.0, 2.0, 3.0])

x.add_(1)       # in-place — modifies x, same storage
x.mul_(2)       # in-place
x.zero_()       # in-place — zeros all elements
x.fill_(5.0)    # in-place

x = x + 1      # out-of-place — creates a new tensor, rebinds x
x = x * 2      # out-of-place
```

**Critical:** in-place operations on tensors that are part of the computation graph will raise a `RuntimeError` or silently corrupt gradients:

```python
x = torch.tensor([1.0, 2.0], requires_grad=True)
y = x * 2
x.add_(1)       # RuntimeError: a leaf Variable that requires grad
                # has been used in an in-place operation
```

PyTorch tracks the computation graph by recording operations. An in-place mutation changes the value that an earlier node in the graph depended on — making the stored value wrong for backward pass computation. PyTorch detects this and raises an error for leaf tensors, but not always for intermediate tensors, where silent gradient corruption is possible.

The rule: **never mutate tensors in-place if they require gradients or if they are inputs to a computation you will differentiate through.** Use out-of-place operations in `forward()` and reserve in-place for operations where you are certain no gradient flows through the mutated tensor (e.g., weight initialisation, zeroing gradients).

```python
# Correct: zero gradients after stepping
optimizer.zero_grad()          # calls grad.zero_() — safe, no backward after this

# Correct: weight initialisation before any forward pass
with torch.no_grad():
    model.fc.weight.fill_(0.0) # in-place, no graph built
```

### PyTorch — Shared Memory in DataLoader

When `num_workers > 0`, PyTorch's `DataLoader` passes tensors between processes using shared memory. Tensors from the same batch may share an underlying storage buffer. If your `collate_fn` or dataset's `__getitem__` mutates the tensor in-place:

```python
def collate_fn(batch):
    images, labels = zip(*batch)
    images = torch.stack(images)
    images -= images.mean()    # in-place normalisation on shared memory
    return images, torch.tensor(labels)
```

The mutation may be visible in the worker process's memory and cause corrupted batches in subsequent iterations. Use out-of-place operations in data loading code.

### Immutable Configs — Protecting Hyperparameters

```python
from typing import NamedTuple

class TrainConfig(NamedTuple):
    learning_rate: float = 1e-3
    batch_size:    int   = 256
    epochs:        int   = 90
    weight_decay:  float = 1e-4

cfg = TrainConfig(learning_rate=0.01, epochs=50)
cfg.learning_rate = 0.001    # AttributeError — immutable

# Dataclasses with frozen=True:
from dataclasses import dataclass

@dataclass(frozen=True)
class ModelConfig:
    num_layers:  int   = 12
    hidden_dim:  int   = 768
    dropout:     float = 0.1

mcfg = ModelConfig()
mcfg.num_layers = 24    # FrozenInstanceError — immutable
```

Experiment configs should be immutable after construction. If training code can mutate the config object, you cannot trust the config file to accurately record what a run actually used.

### Caching with Immutable Keys — `functools.lru_cache`

```python
import functools
import numpy as np

@functools.lru_cache(maxsize=128)
def compute_kernel(sigma: float, size: int) -> tuple:
    # Returns a tuple (immutable) for safe caching
    x = np.arange(size) - size // 2
    kernel = np.exp(-x**2 / (2 * sigma**2))
    kernel /= kernel.sum()
    return tuple(kernel)    # convert to tuple — hashable and immutable
```

`lru_cache` requires hashable arguments. NumPy arrays are mutable and unhashable — you cannot cache on them directly. The pattern: convert to tuples or use the relevant immutable parameters as keys.

## Common Mistakes and Pitfalls

**1. Confusing `==` and `is`**

```python
a = [1, 2, 3]
b = [1, 2, 3]
print(a == b)    # True  — same value
print(a is b)    # False — different objects
```

**2. Mutable default arguments** (covered above — the canonical Python gotcha)

**3. Assuming `tuple` prevents all mutation**

```python
t = ([1, 2], [3, 4])
t[0].append(99)   # legal — tuple's references are fixed, contents are not
```

**4. NumPy slice is a view, not a copy**

```python
b = a[1:4]
b[0] = 99         # modifies a — use a[1:4].copy() if you need isolation
```

**5. In-place PyTorch ops breaking autograd**

```python
x.add_(1)         # RuntimeError if x is a leaf with requires_grad=True
```

**6. `+=` on lists mutates; `+=` on ints rebinds**

```python
a = b = [1, 2, 3]
a += [4]          # mutates — b sees it
a = a + [5]       # rebinds a — b does not see it
```

## Summary

|Concept|Rule|
|---|---|
|Mutable objects|`list`, `dict`, `set`, `ndarray`, class instances — modified in place|
|Immutable objects|`int`, `float`, `str`, `tuple`, `frozenset`, `bytes` — never modified|
|Aliasing|Two names → same mutable object → mutation visible through both|
|Rebinding|Name points to a new object — other names are unaffected|
|`+=` on mutables|Calls `__iadd__` → mutates in place → same `id`|
|`+=` on immutables|Creates new object → rebinds name → new `id`|
|Mutable defaults|Use `None` sentinel — never `[]`, `{}`, or other mutables|
|Tuples|References fixed; contained mutables can still change|
|NumPy slices|Views by default — use `.copy()` to guarantee isolation|
|PyTorch in-place|Trailing `_` convention; illegal on graph-participating tensors|

The governing principle: **names are labels, not containers.** Assignment always binds a label to an object. Whether that object can change is a property of the object, not the label. Understanding this — deeply, not superficially — is what separates programmers who debug mutability bugs in ten minutes from those who spend three days on them.
