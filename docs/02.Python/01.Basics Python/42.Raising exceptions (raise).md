# 42. Raising Exceptions (`raise`)

> _"Raising an exception is an assertion. It says: this function's contract has been violated, and I refuse to proceed on false premises. A function that silently accepts bad input is not being kind — it is deferring a lie."_

---

## The Core Idea

A `raise` statement does one thing: it interrupts normal control flow and hands a signal — an exception object — up the call stack until something catches it or the program terminates.

This is not error-handling. That is `try/except`. `raise` is the other side: **deliberately signalling that a precondition has been violated**.

The mental model: every function has an implicit contract.

```
precondition  →  function executes  →  postcondition
```

When the precondition is violated, the function should not silently proceed toward a wrong postcondition. It should raise — loudly, early, with a precise message — and let the caller decide what to do.

---

## Syntax: Three Forms

### Form 1 — Raise a new exception

```python
raise ExceptionType("message")
```

This is the standard form. Instantiate an exception class with a message string and raise it.

```python
def sqrt(x):
    if x < 0:
        raise ValueError(f"sqrt requires a non-negative argument, got {x}")
    return x ** 0.5
```

### Form 2 — Re-raise the current exception

```python
raise
```

Used inside an `except` block. Re-raises the exception that is currently being handled, preserving its original traceback.

```python
try:
    result = risky_operation()
except ValueError as e:
    log_error(e)    # do something — log, record, alert
    raise           # then let it propagate unchanged
```

### Form 3 — Raise with explicit cause (`raise ... from`)

```python
raise NewException("message") from original_exception
```

Chains exceptions explicitly. The new exception carries a `__cause__` attribute pointing to the original. The traceback displays both.

```python
try:
    value = int(user_input)
except ValueError as e:
    raise TypeError(f"Expected an integer string, got {user_input!r}") from e
```

Output:

```
ValueError: invalid literal for int() with base 10: 'hello'

The above exception was the direct cause of the following exception:

TypeError: Expected an integer string, got 'hello'
```

---

## Raise is Not `return`

A raised exception does not return a value. It unwinds the call stack frame by frame, looking for an `except` clause that matches. If none is found, the program terminates and prints the traceback.

```
f() calls g() calls h()
                  ↓
              h() raises ValueError
                  ↓
         g() has no matching except → unwinds
                  ↓
    f() has except ValueError → caught here
```

Every frame between the `raise` and the `except` is unwound. Local variables in those frames are lost. This is why re-raising with `raise` (not `raise e`) is important — it preserves the original traceback all the way down to the actual source.

---

## When to Raise: The Fail-Fast Principle

Raise early. Do not let bad data travel through your code until it produces a misleading error elsewhere.

**Bad — silent propagation:**

```python
def train_step(model, X, y, lr):
    if lr <= 0:
        lr = 0.001    # silently "fix" the problem

    # 50 lines later... the model converges to a strange solution
    # and you have no idea why
```

**Good — fail fast:**

```python
def train_step(model, X, y, lr):
    if lr <= 0:
        raise ValueError(
            f"Learning rate must be strictly positive, got {lr}. "
            f"Typical values are in [1e-5, 1e-1]."
        )
```

The rule: **raise at the boundary where you first detect the violation**, not deep inside where the consequence eventually surfaces.

---

## What to Raise: Choosing the Right Exception

Always raise the most semantically accurate exception from the standard hierarchy. Never raise `Exception` directly when a subclass fits.

|Condition|Raise|
|---|---|
|Argument has the right type but wrong value|`ValueError`|
|Argument has the wrong type entirely|`TypeError`|
|A required dict key is absent|`KeyError`|
|An index is out of range|`IndexError`|
|An attribute or method does not exist|`AttributeError`|
|A file cannot be found|`FileNotFoundError`|
|An abstract method is not implemented|`NotImplementedError`|
|A general programming contract is violated|`RuntimeError`|
|Anything that does not fit above|Custom exception (see [[43.Custom exception classes]])|

```python
def set_activation(name):
    valid = {"relu", "sigmoid", "tanh", "gelu"}
    if not isinstance(name, str):
        raise TypeError(f"Activation name must be a str, got {type(name).__name__!r}")
    if name not in valid:
        raise ValueError(f"Unknown activation {name!r}. Valid options: {sorted(valid)}")
```

Two checks, two different exception types, for two different kinds of violation.

## Writing Good Exception Messages

An exception message is documentation that appears at the worst possible moment — when something is broken. Write it for the person debugging at 2am.

**Minimum viable message:**

```python
raise ValueError("x must be positive")             # acceptable
raise ValueError(f"x must be positive, got {x}")   # better
```

**Complete message — what, why, what to do:**

```python
raise ValueError(
    f"Learning rate {lr} is outside the valid range (0, 1). "
    f"Values above 0.1 often cause training instability. "
    f"Try lr=1e-3 as a starting point."
)
```

**Always include the actual value.** "x must be positive" without showing `x = -7.3` forces the debugger to add a print statement and re-run. Show the value in the message.

```python
# Bad
raise ValueError("Shape mismatch")

# Good
raise ValueError(
    f"Weight matrix shape {W.shape} is incompatible with input shape {x.shape}. "
    f"Expected W to have {x.shape[-1]} columns, got {W.shape[-1]}."
)
```

## `raise` Inside a Function: Guard Clauses

The guard clause pattern places all precondition checks at the top of the function before any work is done. The function's main logic is then written assuming all preconditions hold.

```python
def matrix_multiply(A, B):
    # Guard clauses — all preconditions up front
    if not isinstance(A, list) or not isinstance(B, list):
        raise TypeError(f"Expected list inputs, got {type(A).__name__} and {type(B).__name__}")
    if len(A) == 0 or len(B) == 0:
        raise ValueError("Matrix arguments must be non-empty")
    if len(A[0]) != len(B):
        raise ValueError(
            f"Incompatible dimensions: A has {len(A[0])} columns "
            f"but B has {len(B)} rows"
        )

    # Main logic — written without defensive checks because guards already fired
    result = [[sum(A[i][k] * B[k][j] for k in range(len(B)))
               for j in range(len(B[0]))]
              for i in range(len(A))]
    return result
```

Contrast with the alternative: sprinkling `if` checks throughout the body. Guard clauses centralise all precondition logic, make the contract explicit, and keep the main logic clean.

## Re-Raising: Preserving the Original Traceback

Inside an `except` block, bare `raise` re-raises the caught exception with its full original traceback intact.

```python
def load_config(path):
    try:
        with open(path) as f:
            return json.load(f)
    except FileNotFoundError:
        logger.error(f"Config file not found: {path}")
        raise    # caller sees the original FileNotFoundError with its traceback
```

**The critical difference — `raise` vs `raise e`:**

```python
try:
    risky()
except ValueError as e:
    raise e    # BAD: traceback starts here — original location is lost
    raise      # GOOD: traceback preserved back to the original raise site
```

`raise e` creates a new traceback starting at the current line. `raise` continues the original traceback. Always use bare `raise` when re-raising.

## Exception Chaining: `raise ... from`

Python tracks two kinds of exception relationships:

|Syntax|Attribute set|Meaning|
|---|---|---|
|`raise B from A`|`B.__cause__ = A`|B was explicitly caused by A|
|Exception during `except A:`|`B.__context__ = A`|B happened while handling A (implicit)|
|`raise B from None`|`B.__cause__ = None`, suppresses context|B replaces A completely|

### Explicit chaining — `raise ... from`

Use when a low-level exception should be re-expressed as a higher-level domain exception, but you want to preserve the original cause.

```python
class ConfigError(Exception):
    pass

def load_config(path):
    try:
        with open(path) as f:
            return json.load(f)
    except FileNotFoundError as e:
        raise ConfigError(f"Configuration file missing: {path}") from e
```

The traceback shows:

```
FileNotFoundError: [Errno 2] No such file or directory: 'config.json'

The above exception was the direct cause of the following exception:

ConfigError: Configuration file missing: config.json
```

Both exceptions are visible. The caller sees `ConfigError` (the domain-level problem) and can trace it back to `FileNotFoundError` (the system-level cause).

### Suppressing context — `raise ... from None`

Use when the original exception is an implementation detail that should not appear in the user-facing traceback.

```python
def get_user(user_id):
    try:
        return db_query(f"SELECT * FROM users WHERE id={user_id}")
    except DatabaseConnectionError as e:
        raise RuntimeError("User lookup failed — service temporarily unavailable") from None
```

The `from None` suppresses the `DatabaseConnectionError` from the traceback. The caller sees only a clean `RuntimeError`. Use this when the original exception contains internal details (SQL queries, internal service names) you do not want exposed.

---

## Implicit Chaining — The Automatic Case

If an exception is raised while another is being handled, Python automatically sets `__context__`:

```python
try:
    int("hello")
except ValueError:
    open("nonexistent.txt")    # raises FileNotFoundError
```

```
ValueError: invalid literal for int() with base 10: 'hello'

During handling of the above exception, another exception occurred:

FileNotFoundError: [Errno 2] No such file or directory: 'nonexistent.txt'
```

Python shows both automatically. This is the "implicit chain" — no `from` keyword needed. It appears in tracebacks when your exception handler itself crashes.

## Raising in Abstract Base Classes

The canonical use of `raise NotImplementedError` is enforcing method contracts on subclasses.

```python
class Optimizer:
    def step(self, gradients):
        raise NotImplementedError(
            f"{type(self).__name__} must implement step(). "
            f"See SGD or Adam for reference implementations."
        )

    def zero_grad(self):
        raise NotImplementedError(f"{type(self).__name__} must implement zero_grad()")


class SGD(Optimizer):
    def __init__(self, lr=0.01):
        self.lr = lr

    def step(self, params, gradients):
        for p, g in zip(params, gradients):
            p -= self.lr * g

    def zero_grad(self):
        pass    # stateless optimizer — nothing to zero
```

`NotImplementedError` (not `NotImplemented`, which is a special singleton for rich comparisons) signals an incomplete inheritance — a subclass that forgot to implement a required method.

## Raise in Assertions vs. Explicit Raise

Python has an `assert` statement:

```python
assert x > 0, f"x must be positive, got {x}"
```

This raises `AssertionError` if the condition is false. It is **not** a substitute for `raise`.

||`assert`|`raise`|
|---|---|---|
|Purpose|Debugging, invariant checking|Enforcing contracts, validating input|
|Disabled by|`python -O` (optimise flag)|Never — always runs|
|Exception type|Always `AssertionError`|Any exception you choose|
|Use in production|No|Yes|

`assert` is for invariants that should never fail if your code is correct — internal consistency checks during development. `raise` is for conditions that can fail depending on external input and must be handled in production.

```python
# WRONG — assert for user input
def set_learning_rate(lr):
    assert lr > 0, "lr must be positive"   # disabled with -O; wrong exception type

# CORRECT — raise for user input
def set_learning_rate(lr):
    if lr <= 0:
        raise ValueError(f"lr must be positive, got {lr}")

# OK — assert for internal invariant
def _compute_gradient(loss, params):
    grad = autograd(loss, params)
    assert grad is not None, "autograd returned None — this is a bug in _compute_gradient"
    return grad
```

## Raise Inside Context Managers

Raising inside a `with` block triggers `__exit__` on the context manager before the exception propagates. This ensures cleanup always runs.

```python
with open("data.csv") as f:
    line = f.readline()
    if not line:
        raise ValueError("Data file is empty — cannot proceed with training")
# File is closed here even though an exception was raised
```

If `__exit__` returns `True`, the exception is suppressed. If it returns `False` or `None`, the exception continues propagating. Standard context managers (`open`, `Lock`, etc.) do not suppress exceptions.

## Practical Patterns in ML Code

### Input validation at API boundaries

```python
import numpy as np

def fit(X, y, epochs=10, lr=0.01):
    # Type checks
    if not isinstance(X, np.ndarray):
        raise TypeError(f"X must be a numpy array, got {type(X).__name__}")
    if not isinstance(y, np.ndarray):
        raise TypeError(f"y must be a numpy array, got {type(y).__name__}")

    # Shape checks
    if X.ndim != 2:
        raise ValueError(f"X must be 2-dimensional (n_samples, n_features), got shape {X.shape}")
    if y.ndim != 1:
        raise ValueError(f"y must be 1-dimensional (n_samples,), got shape {y.shape}")
    if X.shape[0] != y.shape[0]:
        raise ValueError(
            f"X and y must have the same number of samples. "
            f"Got X: {X.shape[0]}, y: {y.shape[0]}"
        )

    # Value checks
    if epochs <= 0:
        raise ValueError(f"epochs must be a positive integer, got {epochs}")
    if not (0 < lr < 1):
        raise ValueError(f"lr must be in (0, 1), got {lr}")

    # Main logic below — all preconditions guaranteed
    ...
```

### Re-raising with context in training loops

```python
def train_epoch(model, dataloader, optimizer):
    for batch_idx, (X, y) in enumerate(dataloader):
        try:
            loss = train_step(model, X, y)
        except RuntimeError as e:
            raise RuntimeError(
                f"Training failed at batch {batch_idx}. "
                f"Input shape: {X.shape}, Target shape: {y.shape}. "
                f"Original error: {e}"
            ) from e
```

### Signalling unimplemented features cleanly

```python
class Model:
    def predict(self, X):
        raise NotImplementedError

    def predict_proba(self, X):
        raise NotImplementedError(
            f"{type(self).__name__} does not support probability estimates. "
            f"Use a probabilistic model such as LogisticRegression."
        )

    def save(self, path):
        raise NotImplementedError(
            f"Serialization not yet implemented. "
            f"Track progress at github.com/org/repo/issues/42."
        )
```

## The Full Raise Decision Tree

```
Something is wrong in my function.
           │
           ▼
Is this a violation of MY function's contract
(bad input, impossible state)?
    │                  │
   YES                 NO → handle it internally or let it propagate
    │
    ▼
Is there an accurate standard exception (ValueError,
TypeError, KeyError, etc.)?
    │                       │
   YES                      NO → raise a custom exception (note 43)
    │
    ▼
raise SpecificException(
    f"What was wrong: {actual_value}. "
    f"What was expected: <constraint>. "
    f"What to do: <hint>."
)
```

## Common Mistakes

**Raising the base `Exception` class:**

```python
raise Exception("something went wrong")    # too vague — use a specific subclass
```

**Swallowing and re-raising incorrectly:**

```python
except ValueError as e:
    raise ValueError("wrapped") from e   # creates a chain — fine if intentional
    raise ValueError("wrapped")          # implicit chain — traceback looks odd
    raise e                              # loses original traceback location
    raise                                # correct bare re-raise
```

**Raising a string instead of an exception:**

```python
raise "this is wrong"    # TypeError in Python 3 — must raise an exception instance
```

**Using `assert` for user-facing validation:**

```python
assert lr > 0    # silently disabled with python -O; wrong exception type
```
