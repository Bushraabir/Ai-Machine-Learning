# 36. Generator Expressions

> _"A generator expression is a list comprehension that forgot to materialise. The syntax is identical — the brackets are the only difference — but the behaviour is fundamentally different: lazy vs. eager, $O(1)$ vs. $O(n)$ memory."_

**Prerequisites:** [[35.Generator functions]] · [[16.Comprehensions]] · [[34.iter() and next()]]

---

## Syntax — One Character of Difference

```python
# List comprehension — eager, allocates all values immediately
squares_list = [x ** 2 for x in range(10)]   # square brackets

# Generator expression — lazy, computes one value at a time
squares_gen  = (x ** 2 for x in range(10))   # parentheses

print(type(squares_list))   # <class 'list'>
print(type(squares_gen))    # <class 'generator'>
```

That is the complete syntactic difference. The semantics diverge entirely.

**Full syntax — mirrors list comprehension exactly:**

```python
# [expr for var in iterable if condition]  ← list comprehension
# (expr for var in iterable if condition)  ← generator expression

evens = (x for x in range(20) if x % 2 == 0)

# Nested loops — same as in list comprehension:
pairs = ((x, y) for x in range(3) for y in range(3) if x != y)

# Calling a function on each element:
words = ["hello", "world", "python"]
lengths = (len(w) for w in words)
upper   = (w.upper() for w in words)
```

## What a Generator Expression Actually Is

A generator expression is syntactic sugar for a generator function. The following two are exactly equivalent:

```python
# Generator expression:
gen = (x ** 2 for x in range(5))

# Equivalent generator function:
def _gen():
    for x in range(5):
        if True:       # the implicit condition (no filter here)
            yield x ** 2

gen = _gen()
```

With a filter:

```python
# Generator expression:
gen = (x ** 2 for x in range(10) if x % 2 == 0)

# Equivalent generator function:
def _gen():
    for x in range(10):
        if x % 2 == 0:
            yield x ** 2

gen = _gen()
```

Every property from [[35.Generator functions]] applies: single-pass, stateful, lazy, $O(1)$ memory, implements the full iterator protocol.

## Memory — The Core Advantage

```python
import sys

n = 1_000_000

lst = [x ** 2 for x in range(n)]
gen = (x ** 2 for x in range(n))

print(sys.getsizeof(lst))   # ~8,697,464 bytes  (~8.3 MB)
print(sys.getsizeof(gen))   # 104 bytes          (constant, regardless of n)
```

The list holds one million integers in memory simultaneously. The generator holds its internal state — a reference to the `range` iterator and the current value of `x` — nothing more.

**Visualised:**

```
List comprehension [x**2 for x in range(6)]:

  Memory: [0, 1, 4, 9, 16, 25]
           ↑  ↑  ↑  ↑   ↑   ↑
           all six values exist simultaneously


Generator expression (x**2 for x in range(6)):

  Memory: [state: x=0, range_iter]
          
  next() → 0  ,  [state: x=1, range_iter]
  next() → 1  ,  [state: x=2, range_iter]
  next() → 4  ,  [state: x=3, range_iter]
  ...
  Only one value exists at any time
```

## Implicit Parentheses Inside Function Calls

When a generator expression is the **sole argument** to a function, the outer parentheses of the function call serve double duty — you do not need a second pair:

```python
# These two are identical:
total = sum((x ** 2 for x in range(10)))   # explicit extra parens
total = sum(x ** 2 for x in range(10))    # implicit — preferred

# Works with any function taking an iterable:
maximum  = max(abs(x) for x in [-3, 1, -7, 2])   # 7
joined   = ",".join(str(x) for x in [1, 2, 3])   # "1,2,3"
any_neg  = any(x < 0 for x in [1, -2, 3])        # True
all_pos  = all(x > 0 for x in [1, 2, 3])         # True
count    = sum(1 for x in data if x > threshold)  # count elements passing filter
```

The `sum(1 for x in data if condition)` pattern is idiomatic Python for counting elements satisfying a predicate — without building a filtered list.

**When there are multiple arguments, you need explicit parentheses:**

```python
# Multiple arguments — explicit parens required:
result = sorted((x ** 2 for x in range(5)), reverse=True)
#               ^^^^^^^^^^^^^^^^^^^^^^^^^ explicit parens needed
```

## Early Termination — Where Generators Beat Lists

If you only need the first element satisfying a condition, a list comprehension wastes work building the entire list before you inspect it. A generator short-circuits.

```python
data = range(10_000_000)

# List comprehension: builds 10M-element list, then takes first
first_large = [x for x in data if x ** 3 > 100][0]   # expensive

# Generator expression: stops immediately after finding the first match
first_large = next(x for x in data if x ** 3 > 100)  # cheap — stops at x=5

# With a default if nothing matches:
first_large = next((x for x in data if x > 1e20), None)  # None if not found
```

`next()` on a generator expression is the idiomatic `find_first` in Python.

## Chaining Generator Expressions — Lazy Pipelines

Generator expressions compose naturally into pipelines, each stage consuming the previous lazily:

```python
# Read a CSV file of numbers, skip headers/comments, square valid entries
lines    = (line.strip() for line in open("data.csv"))
filtered = (line for line in lines if line and not line.startswith('#'))
parsed   = (float(line) for line in filtered)
squares  = (x ** 2 for x in parsed)

# Nothing executes until iteration:
for val in squares:
    print(val)
```

At each `next()` call on `squares`, it calls `next()` on `parsed`, which calls `next()` on `filtered`, which calls `next()` on `lines`, which reads one line from the file. The entire pipeline processes one line at a time, with $O(1)$ memory at every stage.

This is identical in structure to the generator function pipeline in [[35.Generator functions]] — generator expressions are just the compact syntax for simple transformations.

## Generator Expression vs. List Comprehension — Decision Rules

This is the most practically important part of the note.

```
Do you need random access by index?
    data[i]  → list   (generators have no __getitem__)

Do you need the length before iterating?
    len(data)  → list   (generators have no __len__)

Will you iterate more than once?
    for x in data ... for x in data ...  → list
    (exhausted generators don't restart)

Will you only iterate once?
    → generator expression

Is n large (>~10,000 elements)?
    → generator expression (memory savings matter)

Do you need early termination?
    next(x for x in data if condition)  → generator expression

Are you passing to sum(), any(), all(), max(), min(), join()?
    → generator expression (they consume lazily, no list needed)

Are you passing to sorted(), list(), tuple()?
    → list comprehension (they materialise anyway — same cost)
```

```python
# Cases where list comprehension is correct:
indices = [i for i, x in enumerate(data) if x > 0]
print(indices[2])          # needs indexing → list

result = [transform(x) for x in data]
for x in result: ...       # iterated twice
for x in result: ...       # → list

# Cases where generator expression is correct:
total = sum(x ** 2 for x in data)          # sum consumes once
found = any(is_valid(x) for x in data)    # short-circuits on first True
first = next(x for x in data if p(x))     # stop at first match
```

## The Scoping Rule — Variable Binding

The loop variable in a generator expression is scoped to the expression — it does not leak into the enclosing scope, unlike Python 2 list comprehensions.

```python
x = 100
gen = (x for x in range(5))   # x inside is local to the generator
print(x)                       # 100 — outer x unchanged

# The iterable is evaluated immediately at definition time:
data = [1, 2, 3]
gen = (x * 2 for x in data)   # `data` is captured here
data = [4, 5, 6]               # reassigning data does NOT affect gen
print(list(gen))               # [2, 4, 6]  — original data
```

**Critical — the iterable expression is evaluated eagerly at creation, but the body is lazy:**

```python
# The range(n) is evaluated NOW:
n = 5
gen = (x ** 2 for x in range(n))
n = 100   # changing n has no effect — range(5) already captured
print(list(gen))   # [0, 1, 4, 9, 16]

# But if iterable is a mutable object, mutations ARE visible:
nums = [1, 2, 3]
gen = (x * 2 for x in nums)
nums.append(4)     # mutation of the list IS visible
print(list(gen))   # [2, 4, 6, 8]  — includes 4
```

This is one of the subtler behaviours: the reference to `nums` is captured at definition time, but the list's contents are read lazily as iteration proceeds.

## Nested Generator Expressions

```python
# Nested comprehension — matrix flattening:
matrix = [[1, 2, 3], [4, 5, 6], [7, 8, 9]]

flat_list = [x for row in matrix for x in row]    # list
flat_gen  = (x for row in matrix for x in row)    # generator

# Nested generator expressions for Cartesian product:
pairs = ((x, y) for x in range(3) for y in range(3))
for p in pairs:
    print(p)   # (0,0), (0,1), (0,2), (1,0), ...

# Generator of generators — a 2D lazy structure:
rows = ((x * y for x in range(1, 4)) for y in range(1, 4))
for row_gen in rows:
    print(list(row_gen))
# [1, 2, 3]
# [2, 4, 6]
# [3, 6, 9]
```

## Common Pitfalls

```python
# PITFALL 1: Treating a generator expression like a list
gen = (x ** 2 for x in range(5))
print(len(gen))    # TypeError: object of type 'generator' has no len()
print(gen[2])      # TypeError: 'generator' object is not subscriptable

# If you need both lazy computation AND indexing, compute lazily but
# materialise only what you need:
import itertools
third = next(itertools.islice((x**2 for x in range(100)), 2, None))  # 4


# PITFALL 2: Iterating twice over an exhausted generator
gen = (x for x in range(3))
print(list(gen))   # [0, 1, 2]
print(list(gen))   # []  — silent, not an error, just empty
# Fix: use a list comprehension if you need multiple passes


# PITFALL 3: Late binding of mutable variables
funcs = [lambda: x for x in range(3)]   # classic closure issue
# All lambdas capture x by reference — x is 2 after loop
print([f() for f in funcs])   # [2, 2, 2]

# Generator expressions have the same issue with function calls inside:
multipliers = [2, 3, 4]
gens = [(x * m for x in range(3)) for m in multipliers]
# Each generator captures m lazily — but m is a loop variable
# By the time you consume the generators, m may have changed
# Safe pattern: consume immediately, or use default argument binding


# PITFALL 4: Using a generator expression where sorted/list is inevitable
# sorted() must consume the entire iterable to sort it:
result = sorted(x**2 for x in range(10))   # generator materialised anyway
# Here a list comprehension is equally correct and slightly clearer


# PITFALL 5: Forgetting next() default for empty generators
gen = (x for x in [] if x > 0)
val = next(gen)         # StopIteration — crashes
val = next(gen, None)   # None — safe
```

## Performance — When Lists Win

```python
import timeit

# Sum of squares — generator wins (lazy, early exit not relevant here but memory matters)
t_list = timeit.timeit("[x**2 for x in range(1000)]", number=10000)
t_gen  = timeit.timeit("sum(x**2 for x in range(1000))", number=10000)
# gen is slightly slower per element (function call overhead per next())
# but uses constant memory

# For small n where you need all values, lists are faster:
# list comprehension: one bulk allocation
# generator: one function call per element
# Crossover: roughly n > 10,000 where memory pressure dominates
```

Generator expressions have per-element overhead from the iterator protocol (one `next()` call per element). For small, fully-consumed sequences, list comprehensions are measurably faster. For large data or partial consumption, generators win on both memory and overall time.

## Connection to AI/ML and Deep Learning

### NumPy and Generators — An Important Boundary

NumPy functions generally do **not** accept generator expressions — they expect array-like objects or iterables they can fully materialise.

```python
import numpy as np

# This works — np.fromiter consumes a generator:
arr = np.fromiter((x ** 2 for x in range(10)), dtype=np.float32, count=10)
print(arr)   # [0. 1. 4. 9. 16. 25. 36. 49. 64. 81.]

# np.array() also materialises a generator, but without count you lose efficiency:
arr = np.array(list(x ** 2 for x in range(10)))   # explicit list first

# Passing a generator to np.sum — works but materialises internally:
np.sum(x ** 2 for x in range(10))   # returns a generator object — WRONG
np.sum([x ** 2 for x in range(10)]) # correct
# Rule: for NumPy reductions, use list comprehensions
```

**The boundary:** use generator expressions for pure-Python pipelines and `sum()`, `any()`, `all()`, `max()`, `min()`. Switch to list comprehensions (or direct NumPy vectorisation) the moment you pass data to NumPy.

### Lazy Feature Engineering Pipelines

In ML preprocessing, generator expressions appear naturally in data pipelines:

```python
import numpy as np

def preprocess_pipeline(raw_records):
    """
    A pipeline of generator expressions over raw data records.
    raw_records: iterable of dicts, e.g. from a database cursor or CSV reader
    """
    # Each line is a generator expression — lazy, $O(1)$ memory
    numeric    = (r for r in raw_records if r['label'] is not None)
    normalised = ({**r, 'value': r['value'] / 255.0} for r in numeric)
    features   = (np.array([r['value'], r['value']**2, np.log1p(r['value'])])
                  for r in normalised)
    return features

# Usage — only one record in memory at a time:
records = load_from_database()   # returns a cursor (also lazy)
for feature_vec in preprocess_pipeline(records):
    model.partial_fit(feature_vec.reshape(1, -1))
```

### Counting Patterns in Data — Idioms for EDA

```python
import csv

# Count lines matching a condition without loading the file:
with open("training_data.csv") as f:
    reader = csv.DictReader(f)
    n_positive = sum(1 for row in reader if row['label'] == '1')
    # One pass, O(1) memory

# Compute mean of a column without loading all values:
with open("training_data.csv") as f:
    reader = csv.DictReader(f)
    values = (float(row['feature_1']) for row in reader)
    # Can't do mean in one pass with a generator alone — need two passes or online algorithm

# Online mean (Welford's algorithm) with a generator:
def online_mean(values):
    mean = 0.0
    for n, x in enumerate(values, 1):
        mean += (x - mean) / n
    return mean

with open("training_data.csv") as f:
    reader = csv.DictReader(f)
    mean_f1 = online_mean(float(row['feature_1']) for row in reader)
```

### Generator Expressions in Loss Computation

In custom training loops, generator expressions appear in aggregating metrics:

```python
# Collect per-sample losses across batches without storing all of them:
def evaluate(model, dataloader, criterion):
    total_loss = 0.0
    n_batches  = 0

    # Generator over batches — only one batch in memory:
    losses = (
        criterion(model(X_batch), y_batch).item()
        for X_batch, y_batch in dataloader
    )

    for loss in losses:
        total_loss += loss
        n_batches  += 1

    return total_loss / n_batches

# Or more concisely:
def evaluate_compact(model, dataloader, criterion):
    batch_losses = (
        criterion(model(X), y).item()
        for X, y in dataloader
    )
    losses_list = list(batch_losses)   # materialise once for mean + std
    return np.mean(losses_list), np.std(losses_list)
```

## The Full Comprehension Family — Comparison

|Syntax|Type|Lazy?|Mutable?|Re-iterable?|
|---|---|---|---|---|
|`[x for x in it]`|`list`|No|Yes|Yes|
|`(x for x in it)`|`generator`|Yes|No|No|
|`{x for x in it}`|`set`|No|Yes|Yes|
|`{k: v for k, v in it}`|`dict`|No|Yes|Yes|

Generator expressions are the only lazy member of the comprehension family. The others are all eager — they materialise immediately into their respective container type.

## Summary

A generator expression is `(expr for var in iterable if condition)`. It is syntactic sugar for a generator function containing `yield`. It is lazy: values are produced one at a time on `next()` calls, never all at once. Memory is $O(1)$ regardless of iterable size. It implements the full iterator protocol — single-pass, stateful, exhaustible. Use it when you iterate once, when data is large, or when early termination is possible. Switch to list comprehensions when you need indexing, `len()`, or multiple passes.

||Generator Expression|List Comprehension|
|---|---|---|
|**Memory**|$O(1)$|$O(n)$|
|**Speed**|Slower per-element|Faster (bulk allocation)|
|**Indexing**|No|Yes|
|**`len()`**|No|Yes|
|**Re-iterable**|No|Yes|
|**Best for**|Large data, one pass, early exit|Small data, multiple uses, indexing|
