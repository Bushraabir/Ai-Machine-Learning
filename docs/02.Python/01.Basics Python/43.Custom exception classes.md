# 43. Custom Exception Classes

> _"The standard exceptions are a vocabulary. Custom exceptions are the domain-specific dialect you invent when that vocabulary is not precise enough. A well-named exception is a compressed bug report — it tells you not just that something went wrong, but what kind of thing, in what layer, under what assumption."_

---

## Why Custom Exceptions Exist

The standard library gives you `ValueError`, `TypeError`, `KeyError`, and a dozen others. These are sufficient for generic operations. They are not sufficient for domain reasoning.

Consider:

```python
# Generic — tells you nothing about the domain
raise ValueError("invalid learning rate")

# Domain-specific — tells you exactly what failed and where
raise HyperparameterError("learning_rate", value=lr, constraint="must be in (0, 1)")
```

The second form lets you catch `HyperparameterError` specifically, write handlers only for configuration failures, and leave other `ValueError`s to propagate. Without custom exceptions, every `ValueError` is the same — you cannot distinguish "bad user input" from "numerical domain error" from "malformed config file" without parsing the message string. That is fragile.

**Custom exceptions give you:**

- Caller-side `except` clauses that match intent, not just type
- Structured error data (not just a string message)
- An exception hierarchy that mirrors your domain hierarchy
- Self-documenting code — the exception name is part of the API

---

## The Minimal Custom Exception

```python
class ValidationError(Exception):
    pass
```

That is a complete, usable custom exception. It inherits everything from `Exception` — the message, the traceback, `__str__`, `__repr__`. Raise it exactly like a standard exception:

```python
raise ValidationError("Input failed schema check")
```

Catch it specifically:

```python
try:
    validate(data)
except ValidationError:
    # only runs for ValidationError, not for TypeError or ValueError
    ...
```

The `pass` body is not laziness. For many exceptions, the name alone is the information. `class DataPipelineError(Exception): pass` is a complete design decision — you are saying the exception carries a string message and nothing else.

## The Exception Inheritance Contract

Every custom exception should inherit from `Exception`, not `BaseException`.

```
BaseException
└── Exception          ← inherit from here
    ├── ValueError
    ├── TypeError
    └── YourCustomError ← you are here
```

`BaseException` is the root of everything, including `KeyboardInterrupt` and `SystemExit`. Code that does `except Exception` is a common pattern for "catch all application errors". If your exception inherits from `BaseException` directly, it escapes that net silently. Never do this unless you are building something that deliberately should not be catchable by normal `except Exception` blocks — which is almost never.

```python
# WRONG
class MyError(BaseException):   # escapes except Exception — almost certainly wrong
    pass

# CORRECT
class MyError(Exception):
    pass
```

## Adding Structure: Custom `__init__`

When the exception needs to carry more than a string, define `__init__`.

```python
class ShapeMismatchError(ValueError):
    def __init__(self, expected_shape, actual_shape, context=""):
        self.expected_shape = expected_shape
        self.actual_shape   = actual_shape
        self.context        = context
        message = (
            f"Shape mismatch: expected {expected_shape}, got {actual_shape}"
            + (f" ({context})" if context else "")
        )
        super().__init__(message)
```

Three things to notice:

1. **Inherit from `ValueError`**, not `Exception` — because a shape mismatch is semantically a value error. Callers catching `ValueError` will still catch this.
2. **Store the structured data as attributes** — the caller can access `e.expected_shape` and `e.actual_shape` programmatically, not by parsing a string.
3. **Call `super().__init__(message)`** — this sets `args[0]`, which is what `str(e)` and `repr(e)` display. Without it, the string representation is empty.

```python
try:
    result = model(X)
except ShapeMismatchError as e:
    print(f"Expected: {e.expected_shape}")     # (32, 128)
    print(f"Got:      {e.actual_shape}")       # (32, 64)
    print(str(e))    # Shape mismatch: expected (32, 128), got (32, 64) (in linear layer 3)
```

## `__str__` and `__repr__`

If the default message format from `super().__init__` is insufficient, override `__str__`.

```python
class ConfigError(Exception):
    def __init__(self, key, value, reason):
        self.key    = key
        self.value  = value
        self.reason = reason
        super().__init__(f"Invalid config: {key}={value!r} — {reason}")

    def __str__(self):
        return (
            f"ConfigError\n"
            f"  Key:    {self.key}\n"
            f"  Value:  {self.value!r}\n"
            f"  Reason: {self.reason}"
        )
```

Note: `__repr__` on exceptions is handled by the base class and generally does not need overriding. Override `__str__` when you want a formatted, multi-line display.

## Building a Domain Exception Hierarchy

For any non-trivial system, exceptions should form a tree that mirrors the domain structure. This lets callers choose how specific to be when catching.

```python
# Root of the hierarchy — catch-all for the entire domain
class MLError(Exception):
    """Base exception for all errors in this ML library."""
    pass


# Second tier — broad categories
class DataError(MLError):
    """Errors in data loading, validation, or preprocessing."""
    pass

class ModelError(MLError):
    """Errors in model construction or configuration."""
    pass

class TrainingError(MLError):
    """Errors that occur during the training loop."""
    pass


# Third tier — specific conditions
class ShapeMismatchError(DataError):
    """Feature matrix shape does not match expected dimensions."""
    def __init__(self, expected, actual, location=""):
        self.expected = expected
        self.actual   = actual
        super().__init__(
            f"Shape mismatch at {location!r}: expected {expected}, got {actual}"
            if location else
            f"Shape mismatch: expected {expected}, got {actual}"
        )

class MissingFeatureError(DataError):
    """A required feature column is absent from the dataset."""
    def __init__(self, feature_name, available):
        self.feature_name = feature_name
        self.available    = available
        super().__init__(
            f"Required feature {feature_name!r} not found. "
            f"Available: {sorted(available)}"
        )

class InvalidActivationError(ModelError):
    """An unknown or unsupported activation function was requested."""
    VALID = {"relu", "sigmoid", "tanh", "gelu", "selu"}

    def __init__(self, name):
        self.name = name
        super().__init__(
            f"Unknown activation {name!r}. "
            f"Supported activations: {sorted(self.VALID)}"
        )

class GradientExplosionError(TrainingError):
    """Gradient norm exceeded the threshold, indicating unstable training."""
    def __init__(self, norm, threshold, step):
        self.norm      = norm
        self.threshold = threshold
        self.step      = step
        super().__init__(
            f"Gradient explosion at step {step}: "
            f"norm={norm:.2f} exceeded threshold={threshold:.2f}"
        )
```

**How callers use this hierarchy:**

```python
# Catch everything from the library
except MLError as e:
    log_and_abort(e)

# Catch only data-related problems
except DataError as e:
    request_new_data(e)

# Catch only this specific condition
except ShapeMismatchError as e:
    reshape_input(e.expected)

# Catch two unrelated specific exceptions
except (InvalidActivationError, MissingFeatureError) as e:
    fix_config(e)
```

This is the core payoff of the hierarchy. The caller controls granularity.

## Exceptions as Data Carriers

For failures in iterative processes — training loops, batch processing, pipeline stages — an exception that carries structured context is far more useful than a string.

```python
class BatchProcessingError(TrainingError):
    """Raised when a specific batch causes a failure during training."""

    def __init__(self, batch_idx, epoch, cause, X_shape, y_shape):
        self.batch_idx = batch_idx
        self.epoch     = epoch
        self.cause     = cause     # the original exception
        self.X_shape   = X_shape
        self.y_shape   = y_shape

        super().__init__(
            f"Batch {batch_idx} in epoch {epoch} failed. "
            f"Input shape: {X_shape}, Target shape: {y_shape}. "
            f"Cause: {type(cause).__name__}: {cause}"
        )


# In the training loop:
for batch_idx, (X, y) in enumerate(dataloader):
    try:
        loss = train_step(model, X, y)
    except Exception as e:
        raise BatchProcessingError(
            batch_idx=batch_idx,
            epoch=current_epoch,
            cause=e,
            X_shape=X.shape,
            y_shape=y.shape,
        ) from e
```

The caller catching `BatchProcessingError` can log `e.batch_idx`, skip to the next epoch, or write the bad batch to disk for inspection — all without parsing a string.

## The `__init_subclass__` Pattern: Self-Registering Exceptions

For large libraries, you can build a registry that maps exception names to classes automatically.

```python
class MLError(Exception):
    _registry = {}

    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        MLError._registry[cls.__name__] = cls

class DataError(MLError): pass
class ModelError(MLError): pass
class TrainingError(MLError): pass

# After class definitions:
MLError._registry
# {'DataError': <class 'DataError'>,
#  'ModelError': <class 'ModelError'>,
#  'TrainingError': <class 'TrainingError'>}
```

This enables deserialising exceptions from logs or network messages by name, without a manual lookup table. It is an advanced pattern — note it for later.

## Organising Custom Exceptions in a Module

For any project beyond a single file, exceptions belong in their own module.

```
project/
├── exceptions.py       ← all custom exceptions live here
├── data/
│   ├── loader.py       ← from project.exceptions import DataError
│   └── pipeline.py
├── models/
│   └── base.py         ← from project.exceptions import ModelError
└── training/
    └── loop.py         ← from project.exceptions import TrainingError
```

`exceptions.py`:

```python
"""
project.exceptions
~~~~~~~~~~~~~~~~~~
All custom exceptions for the project, organised by domain layer.
Import from here, not from individual submodules.
"""

class MLError(Exception):
    """Base class for all project exceptions."""

class DataError(MLError):
    """Data loading, validation, and preprocessing failures."""

class ModelError(MLError):
    """Model construction and configuration failures."""

class TrainingError(MLError):
    """Training loop and optimisation failures."""

class ShapeMismatchError(DataError):
    def __init__(self, expected, actual, location=""):
        self.expected = expected
        self.actual   = actual
        super().__init__(
            f"Shape mismatch{f' at {location!r}' if location else ''}: "
            f"expected {expected}, got {actual}"
        )

# ... rest of hierarchy
```

This single-module pattern means any file in the project can do:

```python
from project.exceptions import ShapeMismatchError, TrainingError
```

And users of the library see a clean, documented exception surface.

## `__cause__`, `__context__`, and Custom Exceptions

Custom exceptions participate in exception chaining exactly like standard ones.

```python
class PipelineError(MLError):
    pass

# Translate a low-level OS error into a domain error
try:
    data = load_from_disk(path)
except OSError as e:
    raise PipelineError(f"Failed to load dataset from {path}") from e
```

```
OSError: [Errno 2] No such file or directory: 'data/train.csv'

The above exception was the direct cause of the following exception:

PipelineError: Failed to load dataset from data/train.csv
```

The caller sees the domain-level `PipelineError`. The `__cause__` attribute preserves the underlying `OSError` for debugging. The traceback shows both. This is the full exception chaining pattern from [[42.Raising Exceptions (raise)]] applied to your own hierarchy.

## Exceptions vs. Return Codes — The Design Choice

Some languages (C, Go) signal errors via return values. Python's idiomatic approach is exceptions. The practical question is: when does a condition merit a custom exception vs. returning `None` or a sentinel value?

**Use a custom exception when:**

- The condition represents a violated contract — the caller passed something invalid
- Recovery requires knowledge of the failure type (which `except` gives you)
- The failure should propagate unless explicitly handled
- The error occurs deep in a call stack and returning it would pollute every intermediate function

**Return a sentinel value (`None`, empty list, `False`) when:**

- Absence is a normal, expected outcome — not a failure
- The caller always handles the "nothing found" case immediately
- The operation is a query: "does this exist?" — `False` is the right answer

```python
# Exception — contract violation: the user explicitly asked for a key that must exist
def get_required_config(key):
    if key not in config:
        raise ConfigError(f"Required key {key!r} absent from configuration")
    return config[key]

# Return None — absence is normal: the user is probing, not asserting
def find_checkpoint(epoch):
    path = f"checkpoints/epoch_{epoch}.pt"
    return path if os.path.exists(path) else None
```

---

## Summary: The Design Checklist

When designing a custom exception:

1. **Where in the hierarchy?** Inherit from the most specific standard exception that fits, or from your domain root. Never from `BaseException`.
2. **What does it carry?** Decide what structured data the caller will need — beyond the string message. Add those as `__init__` parameters stored as attributes.
3. **What is its name?** The name should be a noun or noun-phrase describing the violated condition: `ShapeMismatchError`, `MissingFeatureError`, `GradientExplosionError`. Not `BadInputError` (too vague) or `Error` (meaningless).
4. **Does `super().__init__(message)` get called?** It must. Otherwise `str(e)` is empty.
5. **Is it in `exceptions.py`?** If the project has more than one file, yes.

## Full Working Example: A Mini ML Library

```python
# exceptions.py

class MLError(Exception):
    """Base class for all library exceptions."""


class DataError(MLError):
    """Raised for data validation and preprocessing failures."""


class ModelError(MLError):
    """Raised for model construction and configuration failures."""


class TrainingError(MLError):
    """Raised during training loop execution."""


class ShapeMismatchError(DataError):
    def __init__(self, expected, actual, location=""):
        self.expected = expected
        self.actual   = actual
        self.location = location
        msg = f"Shape mismatch: expected {expected}, got {actual}"
        if location:
            msg += f" (at {location})"
        super().__init__(msg)


class NaNLossError(TrainingError):
    def __init__(self, step, loss_value):
        self.step       = step
        self.loss_value = loss_value
        super().__init__(
            f"Loss became NaN at step {step}. "
            f"Check learning rate, gradient clipping, and input normalisation."
        )


class InvalidArchitectureError(ModelError):
    def __init__(self, layer_name, reason):
        self.layer_name = layer_name
        self.reason     = reason
        super().__init__(f"Invalid layer {layer_name!r}: {reason}")


# ── model.py ──────────────────────────────────────────────────────────────

from exceptions import ShapeMismatchError, NaNLossError, InvalidArchitectureError
import math

class LinearLayer:
    def __init__(self, in_features, out_features):
        if in_features <= 0:
            raise InvalidArchitectureError(
                "LinearLayer",
                f"in_features must be positive, got {in_features}"
            )
        if out_features <= 0:
            raise InvalidArchitectureError(
                "LinearLayer",
                f"out_features must be positive, got {out_features}"
            )
        self.W = [[0.0] * in_features for _ in range(out_features)]
        self.b = [0.0] * out_features
        self.in_features  = in_features
        self.out_features = out_features

    def forward(self, x):
        if len(x) != self.in_features:
            raise ShapeMismatchError(
                expected=(self.in_features,),
                actual=(len(x),),
                location=f"LinearLayer(in={self.in_features}, out={self.out_features})"
            )
        out = [
            sum(self.W[i][j] * x[j] for j in range(self.in_features)) + self.b[i]
            for i in range(self.out_features)
        ]
        if any(math.isnan(v) for v in out):
            raise NaNLossError(step=0, loss_value=float("nan"))
        return out


# ── Usage ─────────────────────────────────────────────────────────────────

layer = LinearLayer(4, 2)

try:
    output = layer.forward([1.0, 2.0, 3.0])  # only 3 values, expects 4
except ShapeMismatchError as e:
    print(f"Shape error caught. Expected: {e.expected}, Got: {e.actual}")
    # Shape error caught. Expected: (4,), Got: (3,)

try:
    bad_layer = LinearLayer(-1, 2)
except InvalidArchitectureError as e:
    print(f"Architecture error: {e}")
    # Architecture error: Invalid layer 'LinearLayer': in_features must be positive, got -1
```

## Connection to AI, Machine Learning, and Deep Learning

Custom exceptions in ML are not optional polish — they are architectural decisions that determine how debuggable your system is under real failure conditions.

### PyTorch's Own Exception Design

PyTorch uses `RuntimeError` for most of its own failures — shape mismatches, device mismatches, missing gradients. This is a design choice you can improve upon in your own code by wrapping PyTorch errors in domain exceptions:

```python
import torch
from exceptions import ShapeMismatchError

def safe_matmul(A, B):
    try:
        return A @ B
    except RuntimeError as e:
        if "size mismatch" in str(e):
            raise ShapeMismatchError(
                expected=f"(..., {A.shape[-1]})",
                actual=str(B.shape),
                location="matmul"
            ) from e
        raise   # re-raise anything else unchanged
```

### Gradient Health Monitoring

```python
class GradientError(TrainingError):
    pass

class VanishingGradientError(GradientError):
    def __init__(self, layer_name, norm, threshold=1e-7):
        self.layer_name = layer_name
        self.norm       = norm
        self.threshold  = threshold
        super().__init__(
            f"Vanishing gradient in {layer_name!r}: "
            f"norm={norm:.2e} < threshold={threshold:.2e}. "
            f"Consider skip connections, batch normalisation, or a different initialisation."
        )

class ExplodingGradientError(GradientError):
    def __init__(self, layer_name, norm, threshold=1e3):
        self.layer_name = layer_name
        self.norm       = norm
        self.threshold  = threshold
        super().__init__(
            f"Exploding gradient in {layer_name!r}: "
            f"norm={norm:.2e} > threshold={threshold:.2e}. "
            f"Apply gradient clipping: torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)"
        )

def check_gradients(model):
    for name, param in model.named_parameters():
        if param.grad is None:
            continue
        norm = param.grad.norm().item()
        if norm < 1e-7:
            raise VanishingGradientError(name, norm)
        if norm > 1e3:
            raise ExplodingGradientError(name, norm)
```

### Configuration Validation

Config validation at startup is cheaper than debugging a run that crashed 8 hours in.

```python
class ConfigError(MLError):
    def __init__(self, field, value, constraint):
        self.field      = field
        self.value      = value
        self.constraint = constraint
        super().__init__(
            f"Invalid config field {field!r}={value!r}: {constraint}"
        )

def validate_config(cfg):
    validations = [
        ("learning_rate", cfg.get("learning_rate"),
         lambda v: 0 < v < 1,
         "must be in (0, 1)"),
        ("batch_size", cfg.get("batch_size"),
         lambda v: isinstance(v, int) and v > 0,
         "must be a positive integer"),
        ("optimizer", cfg.get("optimizer"),
         lambda v: v in {"sgd", "adam", "adamw", "rmsprop"},
         "must be one of sgd, adam, adamw, rmsprop"),
    ]
    for field, value, check, constraint in validations:
        if value is None:
            raise ConfigError(field, None, "is required but missing")
        if not check(value):
            raise ConfigError(field, value, constraint)
```

### The Exception Hierarchy as an API Contract

When you publish a library, your exception hierarchy is part of the public API. Users write `except YourLibrary.DataError` in their code. If you rename or restructure exceptions in a patch release, you break their handlers silently. Treat exception class names with the same stability guarantees as function signatures.
