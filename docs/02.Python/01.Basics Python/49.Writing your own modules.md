## The Core Idea

A **module** is any `.py` file. The moment you save a file called `utils.py`, it is a module. Any other Python file in the same directory can do `import utils` and access everything defined inside it.

That is the whole mechanism. What takes thought is not the syntax — it is the **design**: how to divide your code across files so that each module has a clear responsibility, a clean public interface, and no hidden dependencies that make it impossible to reuse or test in isolation.

This note covers both the mechanics and the design discipline.

---

## The Minimal Example

```
project/
├── geometry.py
└── main.py
```

```python
# geometry.py

PI = 3.141592653589793

def circle_area(radius: float) -> float:
    """Return the area of a circle with the given radius."""
    return PI * radius ** 2

def circle_circumference(radius: float) -> float:
    """Return the circumference of a circle with the given radius."""
    return 2 * PI * radius

class Circle:
    def __init__(self, radius: float):
        self.radius = radius

    def area(self) -> float:
        return circle_area(self.radius)

    def __repr__(self) -> str:
        return f"Circle(radius={self.radius})"
```

```python
# main.py

import geometry

c = geometry.Circle(5.0)
print(c.area())                          # 78.539...
print(geometry.circle_circumference(5)) # 31.415...
print(geometry.PI)                       # 3.14159...
```

Or with selective imports:

```python
from geometry import Circle, circle_area

c = Circle(5.0)
print(circle_area(3.0))
```

Every name defined at the top level of `geometry.py` — functions, classes, constants, even other imported names — is accessible as an attribute of the module object.

## What a Module's Namespace Contains

When Python executes `geometry.py`, it runs the file top-to-bottom in a fresh namespace. Everything that gets defined or imported at module level becomes an attribute of the resulting module object:

```python
# geometry.py

import math                   # math is now an attribute of geometry
PI = math.pi                  # PI is an attribute
_TOLERANCE = 1e-9             # _TOLERANCE is an attribute (but private by convention)

def circle_area(r):           # circle_area is an attribute
    ...

class Circle:                 # Circle is an attribute
    ...
```

After `import geometry`:

```python
geometry.math          # the math module — accessible but unintended
geometry.PI            # 3.14159...
geometry._TOLERANCE    # 1e-9 — accessible but signals "don't use this"
geometry.circle_area   # the function
geometry.Circle        # the class
```

The leading underscore on `_TOLERANCE` is a **convention** — it signals to readers (and to `import *`) that this name is an implementation detail, not part of the public interface. Python does not enforce it; discipline does.

---

## Controlling the Public Interface with `__all__`

`__all__` is a list of strings that explicitly declares what your module exports. It has two effects:

1. `from geometry import *` only imports names in `__all__`
2. It serves as machine-readable documentation of your public API

```python
# geometry.py

__all__ = ["Circle", "circle_area", "circle_circumference", "PI"]

PI = 3.141592653589793
_TOLERANCE = 1e-9          # not in __all__ — excluded from import *

def circle_area(radius):
    ...

def circle_circumference(radius):
    ...

def _validate_radius(r):   # not in __all__ — internal helper
    if r < 0:
        raise ValueError(f"Radius must be non-negative, got {r}")

class Circle:
    ...
```

**When to define `__all__`:** whenever your module is intended to be used by others — which means any module in an ML project that other files import. It forces you to think about what is public and prevents accidental exposure of internals.

## Module-Level Code — What Runs at Import Time

Every statement at the top level of a module runs when it is imported. This is both powerful and dangerous:

```python
# constants.py — safe: only defines values
LEARNING_RATE = 1e-3
BATCH_SIZE = 256
MAX_EPOCHS = 100
```

```python
# bad_module.py — dangerous: side effects at import time
import time

print("Loading model...")        # printed every import — annoying
model = load_huge_model()        # runs at import — slow, may fail
time.sleep(2)                    # blocks for 2 seconds at import
```

**The rule:** module-level code should only define things — functions, classes, constants. It should not do things — load files, make network requests, print output, or modify global state. Side effects belong inside functions that are called explicitly.

The one canonical exception is the `if __name__ == "__main__":` guard (see [[50.**name** == **main** pattern]]).

## Private vs. Public — The Convention System

Python has no access modifiers (`private`, `protected`). It has conventions:

|Name pattern|Meaning|Effect on `import *`|
|---|---|---|
|`name`|Public — part of the interface|Exported|
|`_name`|Internal — implementation detail|Not exported|
|`__name`|Name-mangled — avoid accidental override in subclasses|Not exported|
|`__name__`|Dunder — Python's own special protocol names|Not exported|

```python
# metrics.py

def accuracy(y_true, y_pred):           # public — use this
    return _correct(y_true, y_pred) / len(y_true)

def _correct(y_true, y_pred):           # internal — don't depend on this
    return sum(a == b for a, b in zip(y_true, y_pred))

EPSILON = 1e-8                          # public constant
_CACHE = {}                             # internal cache — implementation detail
```

When you call `from metrics import *`, only `accuracy` and `EPSILON` come through (assuming no `__all__` — underscore names are excluded). With `import metrics`, everything is accessible as `metrics._correct`, but the underscore is a social contract: _"I might rename or remove this without warning."_

## Docstrings at Module Level

The first string literal in a module, if it is a string expression (not assigned to anything), becomes the module's `__doc__`:

```python
# metrics.py

"""
metrics.py
----------
Evaluation metrics for classification and regression tasks.

Public API:
    accuracy(y_true, y_pred)     — classification accuracy
    f1_score(y_true, y_pred)     — F1 score (binary)
    mean_squared_error(y, y_hat) — MSE for regression
"""

__all__ = ["accuracy", "f1_score", "mean_squared_error"]

...
```

```python
import metrics
help(metrics)         # displays the docstring + all public names
print(metrics.__doc__)
```

Write a module docstring for any file that will be imported by others. It should state what the module contains and list the public API. This is the first thing a reader sees.

## A Real Example — A Metrics Module

This is what a well-structured module looks like in practice:

```python
# metrics.py

"""
metrics.py
----------
Evaluation metrics for binary classification.

Public API:
    accuracy        — fraction of correct predictions
    precision       — TP / (TP + FP)
    recall          — TP / (TP + FN)
    f1_score        — harmonic mean of precision and recall
    confusion_matrix — 2x2 confusion matrix as a dict
"""

__all__ = [
    "accuracy",
    "precision",
    "recall",
    "f1_score",
    "confusion_matrix",
]

# ── Internal helpers ───────────────────────────────────────────────────

def _check_inputs(y_true: list, y_pred: list) -> None:
    if len(y_true) != len(y_pred):
        raise ValueError(
            f"Length mismatch: y_true has {len(y_true)} elements, "
            f"y_pred has {len(y_pred)}."
        )
    if not y_true:
        raise ValueError("Inputs must not be empty.")


def _counts(y_true: list, y_pred: list) -> tuple[int, int, int, int]:
    """Return (TP, FP, TN, FN) for binary labels."""
    _check_inputs(y_true, y_pred)
    tp = sum(t == 1 and p == 1 for t, p in zip(y_true, y_pred))
    fp = sum(t == 0 and p == 1 for t, p in zip(y_true, y_pred))
    tn = sum(t == 0 and p == 0 for t, p in zip(y_true, y_pred))
    fn = sum(t == 1 and p == 0 for t, p in zip(y_true, y_pred))
    return tp, fp, tn, fn


# ── Public API ─────────────────────────────────────────────────────────

def accuracy(y_true: list, y_pred: list) -> float:
    """Return the fraction of predictions that are correct."""
    _check_inputs(y_true, y_pred)
    return sum(t == p for t, p in zip(y_true, y_pred)) / len(y_true)


def precision(y_true: list, y_pred: list) -> float:
    """Return TP / (TP + FP). Returns 0.0 if no positive predictions."""
    tp, fp, _, _ = _counts(y_true, y_pred)
    return tp / (tp + fp) if (tp + fp) > 0 else 0.0


def recall(y_true: list, y_pred: list) -> float:
    """Return TP / (TP + FN). Returns 0.0 if no positive ground truths."""
    tp, _, _, fn = _counts(y_true, y_pred)
    return tp / (tp + fn) if (tp + fn) > 0 else 0.0


def f1_score(y_true: list, y_pred: list) -> float:
    """Return the harmonic mean of precision and recall."""
    p = precision(y_true, y_pred)
    r = recall(y_true, y_pred)
    return 2 * p * r / (p + r) if (p + r) > 0 else 0.0


def confusion_matrix(y_true: list, y_pred: list) -> dict:
    """Return a dict with keys TP, FP, TN, FN."""
    tp, fp, tn, fn = _counts(y_true, y_pred)
    return {"TP": tp, "FP": fp, "TN": tn, "FN": fn}
```

Notice the structure:

- Module docstring first
- `__all__` immediately after — the public contract
- Internal helpers in a clearly labelled section, all prefixed with `_`
- Public functions in a clearly labelled section, all with docstrings
- No side effects anywhere at module level

## Module Design Principles

These are not style preferences. They are engineering principles that determine whether your code survives contact with a real project.

**1. Single responsibility.** Each module should have one clear reason to exist. `metrics.py` computes metrics. `data.py` loads data. `model.py` defines the model architecture. If you cannot state a module's purpose in one sentence, it is doing too much.

**2. Depend inward, not outward.** Low-level utility modules (`utils.py`, `metrics.py`) should not import high-level modules (`trainer.py`, `experiment.py`). The dependency graph should be a DAG, not a cycle. If you find yourself needing a circular import, the design is wrong.

**3. No side effects at import time.** Module-level code defines, does not do. Loading data, initialising hardware, printing, sleeping — all of this goes inside functions.

**4. Explicit public interface.** Define `__all__`. Use `_` prefixes for internals. A module with no explicit interface is one where every internal detail becomes a dependency others rely on, making refactoring impossible.

**5. Keep modules importable in isolation.** If importing `model.py` requires a GPU, a specific file to exist, and a database connection, you cannot test it, you cannot import it in a notebook, and you cannot use it anywhere that context is absent. Guard hardware and I/O behind functions.

```
metrics.py
┌─────────────────────────────────────────────────────────┐
│  """Module docstring"""              ← __doc__          │
│                                                         │
│  __all__ = [...]                     ← public contract  │
│                                                         │
│  import math                         ← dependencies     │
│  from pathlib import Path                               │
│                                                         │
│  EPSILON = 1e-8                      ← public constant  │
│  _CACHE = {}                         ← internal state   │
│                                                         │
│  def _helper():   ...                ← internal         │
│  def _validate(): ...                ← internal         │
│                                                         │
│  def public_fn(): ...                ← public API       │
│  class PublicClass: ...              ← public API       │
└─────────────────────────────────────────────────────────┘

When another file does:
    import metrics
    
    metrics.__doc__       → module docstring
    metrics.__all__       → ['accuracy', 'f1_score', ...]
    metrics.__file__      → '/path/to/metrics.py'
    metrics.__name__      → 'metrics'
    metrics.accuracy      → <function accuracy>
    metrics._helper       → <function _helper>  (accessible but private)
    metrics.EPSILON       → 1e-8
```

## Connection to AI / Machine Learning / Deep Learning

### Every ML project is a collection of modules

A mature ML codebase splits naturally into modules by responsibility. Here is the canonical layout:

```
project/
├── data.py          # Dataset classes, data loading, transforms
├── model.py         # Network architecture definitions
├── train.py         # Training loop, optimiser step, gradient clipping
├── evaluate.py      # Metric computation, validation loop
├── utils.py         # Logging, checkpointing, reproducibility helpers
└── config.py        # Hyperparameters and paths as named constants
```

Each of these is a module you write. The discipline of [[49]] is what makes them composable — you can run `evaluate.py` standalone, import `model.py` into a notebook, and test `data.py` without a GPU.

### `config.py` — the module as a configuration object

Instead of scattering magic numbers through your code:

```python
# config.py

"""
config.py
---------
All hyperparameters and paths in one place.
Change here; effects propagate everywhere.
"""

from pathlib import Path

__all__ = ["DATA", "TRAIN", "MODEL"]

# ── Paths ──────────────────────────────────
DATA_ROOT   = Path("data")
TRAIN_DIR   = DATA_ROOT / "train"
VAL_DIR     = DATA_ROOT / "val"
CKPT_DIR    = Path("checkpoints")

# ── Data ───────────────────────────────────
IMAGE_SIZE  = 224
BATCH_SIZE  = 256
NUM_WORKERS = 8

# ── Model ──────────────────────────────────
NUM_CLASSES = 1000
DROPOUT     = 0.2

# ── Training ───────────────────────────────
LEARNING_RATE = 1e-3
WEIGHT_DECAY  = 1e-4
MAX_EPOCHS    = 90
WARMUP_EPOCHS = 5
```

Every other module imports from `config`:

```python
# train.py
from config import LEARNING_RATE, WEIGHT_DECAY, MAX_EPOCHS, CKPT_DIR
```

When you want to try `LEARNING_RATE = 1e-4`, you change one file. This is the modularity dividend.

### `model.py` — architecture as a module

```python
# model.py

"""
model.py
--------
Neural network architecture definitions.

Public API:
    build_model(num_classes, dropout) — returns a compiled nn.Module
    ResNet                            — the base architecture class
"""

__all__ = ["build_model", "ResNet"]

import torch
import torch.nn as nn
import torch.nn.functional as F


class _ResidualBlock(nn.Module):       # internal — not exported
    """A single residual block. Implementation detail of ResNet."""
    def __init__(self, channels: int):
        super().__init__()
        self.conv1 = nn.Conv2d(channels, channels, 3, padding=1, bias=False)
        self.bn1   = nn.BatchNorm2d(channels)
        self.conv2 = nn.Conv2d(channels, channels, 3, padding=1, bias=False)
        self.bn2   = nn.BatchNorm2d(channels)

    def forward(self, x):
        residual = x
        x = F.relu(self.bn1(self.conv1(x)))
        x = self.bn2(self.conv2(x))
        return F.relu(x + residual)


class ResNet(nn.Module):               # public — exported
    """A minimal ResNet-style classifier."""
    def __init__(self, num_classes: int = 10, dropout: float = 0.2):
        super().__init__()
        self.stem   = nn.Conv2d(3, 64, 7, stride=2, padding=3, bias=False)
        self.blocks = nn.Sequential(
            _ResidualBlock(64),
            _ResidualBlock(64),
        )
        self.pool   = nn.AdaptiveAvgPool2d(1)
        self.drop   = nn.Dropout(dropout)
        self.fc     = nn.Linear(64, num_classes)

    def forward(self, x):
        x = F.relu(self.stem(x))
        x = self.blocks(x)
        x = self.pool(x).flatten(1)
        x = self.drop(x)
        return self.fc(x)


def build_model(num_classes: int = 10, dropout: float = 0.2) -> ResNet:
    """Construct and return a ResNet classifier."""
    return ResNet(num_classes=num_classes, dropout=dropout)
```

`_ResidualBlock` is an internal implementation detail. Users of `model.py` import `ResNet` and `build_model`. If you later replace `_ResidualBlock` with a better implementation, the public interface is unchanged — all importing code continues to work without modification.

### Writing a reusable `data.py`

```python
# data.py

"""
data.py
-------
Dataset and DataLoader construction for image classification.

Public API:
    ImageDataset          — torch Dataset for a directory of images
    build_dataloaders     — returns (train_loader, val_loader)
"""

__all__ = ["ImageDataset", "build_dataloaders"]

from pathlib import Path
from typing import Callable, Optional

import torch
from torch.utils.data import Dataset, DataLoader
from PIL import Image
import torchvision.transforms as T


class ImageDataset(Dataset):
    """Load images from a directory. Each subdirectory is a class."""
    def __init__(self, root: Path, transform: Optional[Callable] = None):
        self.root      = Path(root)
        self.transform = transform
        self.samples   = sorted(self.root.rglob("*.jpg"))

    def __len__(self) -> int:
        return len(self.samples)

    def __getitem__(self, idx: int):
        path  = self.samples[idx]
        image = Image.open(path).convert("RGB")
        if self.transform:
            image = self.transform(image)
        return image


def _default_transform(image_size: int = 224) -> T.Compose:
    return T.Compose([
        T.Resize(image_size),
        T.CenterCrop(image_size),
        T.ToTensor(),
        T.Normalize(mean=[0.485, 0.456, 0.406],
                    std=[0.229, 0.224, 0.225]),
    ])


def build_dataloaders(
    train_dir: Path,
    val_dir:   Path,
    batch_size: int = 256,
    num_workers: int = 8,
    image_size: int = 224,
) -> tuple[DataLoader, DataLoader]:
    """Construct train and validation DataLoaders."""
    transform = _default_transform(image_size)
    train_ds  = ImageDataset(train_dir, transform=transform)
    val_ds    = ImageDataset(val_dir,   transform=transform)
    train_loader = DataLoader(train_ds, batch_size=batch_size,
                              shuffle=True,  num_workers=num_workers)
    val_loader   = DataLoader(val_ds,   batch_size=batch_size,
                              shuffle=False, num_workers=num_workers)
    return train_loader, val_loader
```

In `train.py`:

```python
from data import build_dataloaders
from config import TRAIN_DIR, VAL_DIR, BATCH_SIZE, NUM_WORKERS

train_loader, val_loader = build_dataloaders(
    TRAIN_DIR, VAL_DIR, BATCH_SIZE, NUM_WORKERS
)
```

`train.py` does not need to know how images are loaded, how transforms are constructed, or what `_default_transform` does. It calls one function and gets two DataLoaders.

## Common Mistakes and Pitfalls

**1. Putting everything in one file**

A single `main.py` with 800 lines containing model definition, data loading, training loop, evaluation, and visualisation is not a program — it is a script that cannot be reused, tested, or read. Split by responsibility from the start.

**2. Making modules that import each other**

```
model.py  → imports from  train.py
train.py  → imports from  model.py   ← circular import
```

The fix is always the same: extract the shared dependency into a third module that neither imports from the other two. Usually this is `utils.py` or `config.py`.

**3. Module-level code with side effects**

```python
# bad_data.py

import pandas as pd

# This runs at import time — slow, may fail if file absent
df = pd.read_csv("data/train.csv")      # ← side effect at module level
print(f"Loaded {len(df)} rows")         # ← output at import time
```

Anyone who imports `bad_data` to use one of its functions pays the full cost of loading the CSV, even if they never use `df`. Wrap it in a function.

**4. Importing everything into one namespace**

```python
# bad_utils.py — becomes a dumping ground
from model import *
from data import *
from metrics import *
from config import *
```

Now `bad_utils` has a namespace full of names from four other modules, none of them clearly attributed. Use explicit imports and explicit names.

**5. Forgetting that imported names are module attributes**

```python
# a.py
VALUE = 10

# b.py
from a import VALUE

# elsewhere
import a
a.VALUE = 99    # modifies the module attribute

# back in b.py
print(VALUE)    # still 10 — b.py holds a reference to the original int
                # it does not hold a reference to a.VALUE
```

This is the mutable-vs-immutable import distinction. If `VALUE` were a list, `a.VALUE.append(...)` would be visible to `b.py` (same object). But reassigning `a.VALUE = 99` is not visible to `b.py`'s local binding `VALUE`. Import the module (not the name) when you need to see mutations.

## Summary

|Concept|What to remember|
|---|---|
|A module is|Any `.py` file|
|Module namespace|Every top-level name: functions, classes, constants, imports|
|`__all__`|Explicit public contract; controls `import *`|
|`_name` convention|Internal — implementation detail, may change|
|Module-level code|Should only define, never do|
|Single responsibility|One module, one clear purpose|
|No circular imports|Fix by restructuring, not by working around|
|Module docstring|First string literal; becomes `__doc__`|

**The central discipline:** a module is a unit of encapsulation. Its public interface (what it exports) should be stable and intentional. Its internals (prefixed with `_`) should be free to change. Every file you write in an ML project that another file imports is a module, and it deserves the design care this implies.
