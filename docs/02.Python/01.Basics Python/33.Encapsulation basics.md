## What Is Encapsulation?

Encapsulation is one of the four pillars of object-oriented programming (alongside abstraction, inheritance, and polymorphism). It has two inseparable ideas:

1. **Bundling** — data (attributes) and the operations on that data (methods) are packaged together inside a class.
2. **Access control** — the internal state of an object is hidden from the outside world; the outside world interacts only through a controlled interface.

The mental model: an object is a _capsule_. The interior is its private state. The surface is its public interface. You can press the buttons on the surface without knowing the machinery inside.

```
┌─────────────────────────────────────┐
│              BankAccount            │
│                                     │
│  ┌─────────────────────────────┐    │
│  │  PRIVATE (hidden interior)  │    │
│  │  __balance = 1000.00        │    │
│  │  __transaction_log = [...]  │    │
│  └─────────────────────────────┘    │
│                                     │
│  PUBLIC INTERFACE (the surface)     │
│  deposit(amount)                    │
│  withdraw(amount)                   │
│  get_balance()                      │
└─────────────────────────────────────┘
```

Without encapsulation, any external code could reach in and set `account.__balance = -999999`. The object's internal _invariants_ — the rules that must always hold — would be unenforceable.

## Python's Convention: Name Mangling, Not True Privacy

Unlike Java or C++, **Python has no hard access enforcement**. It uses naming conventions as a contract, relying on programmer discipline. This is a deliberate design choice: Python treats developers as adults.

There are three levels:

|Convention|Syntax|Meaning|
|---|---|---|
|Public|`self.name`|Freely accessible from anywhere|
|Protected|`self._name`|"Internal use" — accessible but by convention only|
|Private|`self.__name`|Name-mangled — hard to access accidentally|

---

### Public Attributes

No underscore. Open to everyone.

```python
class Circle:
    def __init__(self, radius):
        self.radius = radius   # public

c = Circle(5)
print(c.radius)    # 5   — perfectly fine
c.radius = 10      # also fine
```

---

### Protected Attributes — Single Underscore `_`

A single leading underscore is a _social contract_: "this is an implementation detail, please don't touch it from outside." Python does not enforce this in any way.

```python
class Stack:
    def __init__(self):
        self._items = []     # protected by convention

    def push(self, item):
        self._items.append(item)

    def pop(self):
        if not self._items:
            raise IndexError("pop from empty stack")
        return self._items.pop()

s = Stack()
s.push(1)
print(s._items)   # [1]  — Python lets you do this
                  # but you are violating the convention
```

Use `_name` when building a library or framework to signal: _"subclasses may use this, external users should not."_

---

### Private Attributes — Double Underscore `__` (Name Mangling)

A double leading underscore triggers **name mangling**. Python rewrites the attribute name to `_ClassName__name` at compile time.

```python
class BankAccount:
    def __init__(self, balance):
        self.__balance = balance    # stored as _BankAccount__balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("Deposit must be positive")
        self.__balance += amount

    def withdraw(self, amount):
        if amount > self.__balance:
            raise ValueError("Insufficient funds")
        self.__balance -= amount

    def get_balance(self):
        return self.__balance


acc = BankAccount(1000)
acc.deposit(500)
acc.withdraw(200)
print(acc.get_balance())   # 1300

# Attempt direct access:
print(acc.__balance)       # AttributeError: 'BankAccount' has no attribute '__balance'

# The real name after mangling:
print(acc._BankAccount__balance)   # 1300  — still accessible if you know the trick
```

**Name mangling is not encryption.** It is a speed bump to prevent _accidental_ access and name collisions in inheritance hierarchies. A determined programmer can always reach it via `_ClassName__name`.

> The Python philosophy: _"We are all consenting adults here."_ There is no true private. There is only clear signalling of intent.

## Why Encapsulation Matters — Invariant Protection

The core benefit of encapsulation is protecting _class invariants_: conditions that must always be true for an object to be in a valid state.

```python
class Temperature:
    """Invariant: temperature in Kelvin is always >= 0."""

    def __init__(self, kelvin):
        self.__kelvin = None
        self.set_kelvin(kelvin)

    def set_kelvin(self, value):
        if value < 0:
            raise ValueError(f"Temperature cannot be {value}K — below absolute zero.")
        self.__kelvin = value

    def get_kelvin(self):
        return self.__kelvin

    def get_celsius(self):
        return self.__kelvin - 273.15

    def get_fahrenheit(self):
        return self.__kelvin * 9/5 - 459.67


t = Temperature(300)
print(t.get_celsius())     # 26.85

t.set_kelvin(-10)          # ValueError: Temperature cannot be -10K — below absolute zero.
```

Without encapsulation, someone could do `t.__kelvin = -273` and the invariant silently breaks.

## The Pythonic Way — Properties

Raw getters and setters (`get_balance()`, `set_balance()`) are verbose and un-Pythonic. Python provides the `@property` decorator to give you getter/setter semantics with clean attribute-access syntax.

```python
class Temperature:
    def __init__(self, kelvin):
        self._kelvin = None
        self.kelvin = kelvin     # triggers the setter

    @property
    def kelvin(self):
        """Get temperature in Kelvin."""
        return self._kelvin

    @kelvin.setter
    def kelvin(self, value):
        """Set temperature — enforces Kelvin >= 0."""
        if value < 0:
            raise ValueError(f"Kelvin cannot be negative: {value}")
        self._kelvin = value

    @property
    def celsius(self):
        """Read-only derived property."""
        return self._kelvin - 273.15


t = Temperature(300)
print(t.kelvin)      # 300      — clean attribute syntax, calls getter
print(t.celsius)     # 26.85   — read-only

t.kelvin = 350       # calls setter, validates
t.kelvin = -5        # ValueError

t.celsius = 100      # AttributeError: can't set attribute — no setter defined
```

**The anatomy of `@property`:**

```
@property
def attr(self):           ← the getter; defines 'attr' as a managed attribute
    return self._attr

@attr.setter
def attr(self, value):    ← the setter; called on assignment: obj.attr = x
    self._attr = value

@attr.deleter
def attr(self):           ← called on: del obj.attr
    del self._attr
```

This is the canonical Python approach to encapsulation. You start with a simple public attribute, and if you later need validation or computed logic, you retrofit a property _without changing the public interface_. This is the **Uniform Access Principle** in practice.

## A Complete Example — Encapsulated Class with Properties

```python
class Student:
    """
    Invariants:
    - name must be a non-empty string
    - gpa must be in [0.0, 4.0]
    - credits must be a non-negative integer
    """

    def __init__(self, name, gpa=0.0):
        self.name = name       # triggers setter
        self.gpa = gpa         # triggers setter
        self.__credits = 0     # private — external code shouldn't set this directly

    @property
    def name(self):
        return self._name

    @name.setter
    def name(self, value):
        if not isinstance(value, str) or not value.strip():
            raise ValueError("Name must be a non-empty string")
        self._name = value.strip()

    @property
    def gpa(self):
        return self._gpa

    @gpa.setter
    def gpa(self, value):
        if not (0.0 <= value <= 4.0):
            raise ValueError(f"GPA must be in [0.0, 4.0], got {value}")
        self._gpa = round(value, 2)

    @property
    def credits(self):
        return self.__credits

    def complete_course(self, credit_hours):
        """The only sanctioned way to increase credits."""
        if credit_hours <= 0:
            raise ValueError("Credit hours must be positive")
        self.__credits += credit_hours

    def __repr__(self):
        return f"Student(name={self._name!r}, gpa={self._gpa}, credits={self.__credits})"


s = Student("Alice", gpa=3.85)
s.complete_course(3)
s.complete_course(4)
print(s)               # Student(name='Alice', gpa=3.85, credits=7)

s.gpa = 5.0            # ValueError: GPA must be in [0.0, 4.0]
s.name = ""            # ValueError: Name must be a non-empty string
```

## Encapsulation and Inheritance — Why `__` Is Stronger Than `_`

Name mangling exists primarily to prevent _accidental_ attribute name collisions when subclassing.

```python
class Base:
    def __init__(self):
        self.__value = 10      # stored as _Base__value

class Child(Base):
    def __init__(self):
        super().__init__()
        self.__value = 99      # stored as _Child__value — DIFFERENT attribute

c = Child()
print(c._Base__value)    # 10 — Base's copy, untouched
print(c._Child__value)   # 99 — Child's copy
```

With a single underscore, both `self._value` assignments would refer to the _same_ attribute and the child would clobber the parent. Name mangling protects the parent's internal state.

## Encapsulation in AI/ML — Why It Matters Here

Encapsulation is not just good software hygiene — it is structurally embedded in the libraries you will use every day.

**`sklearn` estimators** are a textbook example:

```python
from sklearn.linear_model import LogisticRegression

model = LogisticRegression(C=1.0)
model.fit(X_train, y_train)

# After fitting, learned parameters are exposed as public attributes:
print(model.coef_)           # the weight vector w
print(model.intercept_)      # the bias b

# But the optimisation internals — solver state, iteration history — are hidden.
# You interact only through the interface: fit(), predict(), score()
```

The sklearn API contract (`fit`, `transform`, `predict`) _is_ an encapsulated interface. You can swap `LogisticRegression` for `SVC` or `RandomForestClassifier` without changing a line of your pipeline code — because they all expose the same surface.

**PyTorch `nn.Module`** takes this further:

```python
import torch.nn as nn

class MLP(nn.Module):
    def __init__(self, input_dim, hidden_dim, output_dim):
        super().__init__()
        self.fc1 = nn.Linear(input_dim, hidden_dim)  # weights encapsulated inside Linear
        self.relu = nn.ReLU()
        self.fc2 = nn.Linear(hidden_dim, output_dim)

    def forward(self, x):
        return self.fc2(self.relu(self.fc1(x)))
```

The weight tensors inside `nn.Linear` are managed internally. You access them via `model.parameters()` for the optimiser, not by reaching into the layer directly. The gradient computation (`backward()`) happens inside the module's internal graph — you never touch it. The entire autograd engine is encapsulated behind `loss.backward()`.

**The practical lesson:** when you design a custom `nn.Module` or a custom sklearn transformer, _encapsulate your state_. The buffers, running statistics, internal counters — keep them private. Expose only what a user of your component needs to interact with. This is what makes a component composable inside a larger `Pipeline` or `nn.Sequential`.

## Summary — Decision Rules

```
Does external code need to read and write this attribute freely?
    → public:    self.name

Does it need read access but should not write directly?
    → @property (getter only, no setter)

Does it need write access with validation?
    → @property with getter + setter

Is it purely an internal implementation detail?
    → protected:  self._name   (convention)
    → private:    self.__name  (name mangling, stronger signal)

Is it a constant that defines the class, not an instance?
    → class attribute (see [[29.Attributes- instance vs class]])
```

## Common Pitfalls

```python
# PITFALL 1: Forgetting that __ is not truly private
class Secret:
    def __init__(self):
        self.__data = 42

s = Secret()
# s.__data            → AttributeError  (appears private)
# s._Secret__data     → 42              (actually accessible)

# PITFALL 2: Inconsistency — mixing raw attribute + property
class Bad:
    def __init__(self):
        self.x = 10          # public attribute set here

    @property
    def x(self):             # property with same name
        return self._x       # _x never set → AttributeError on init
    # Solution: use self._x in __init__, expose x as property

# CORRECT:
class Good:
    def __init__(self):
        self._x = 10         # use _x internally

    @property
    def x(self):
        return self._x

    @x.setter
    def x(self, value):
        self._x = value

# PITFALL 3: Over-encapsulating trivial state
# If an attribute has no invariant to protect and no logic on access,
# a plain public attribute is the right choice.
# Don't write getters/setters for everything — that's Java-brain.
```

## Summary Table

|Syntax|Stored As|Accessible From|Use When|
|---|---|---|---|
|`self.x`|`x`|Anywhere|Default; no protection needed|
|`self._x`|`_x`|Anywhere (convention)|Internal/subclass use; signal intent|
|`self.__x`|`_Class__x`|Mangled name only|Prevent inheritance collision; strong privacy signal|
|`@property`|`_x` (typically)|Clean attribute syntax|Validation, computed values, read-only|
