# 56. Variable Unpacking and Assignment Mechanics

> _"Unpacking is not syntactic sugar. It is a window into how Python's assignment protocol works at the bytecode level — and once you see it clearly, you start using it everywhere, correctly."_

---

## What Assignment Actually Does

Before unpacking makes sense, the assignment statement itself needs a precise definition.

```python
x = expression
```

Python:

1. Evaluates the right-hand side fully — produces an object
2. Binds the name on the left to that object in the current namespace

The left-hand side is called a **target**. Targets can be:

- A simple name: `x`
- A subscript: `lst[0]`, `dct["key"]`
- An attribute: `obj.attr`
- A **tuple or list of targets** — this is unpacking

```python
# All of these are valid assignment targets:
x = 10
lst[0] = 10
obj.attr = 10
x, y = 1, 2       # tuple of targets
[a, b] = [1, 2]   # list of targets — identical semantics
```

---

## Basic Sequence Unpacking

The fundamental rule: **the right-hand side is iterated, and its elements are bound to the left-hand side targets one-to-one**.

```python
a, b, c = [1, 2, 3]
a, b, c = (1, 2, 3)
a, b, c = "xyz"       # strings are iterable
a, b, c = range(3)    # any iterable works

print(a, b, c)        # 0 1 2  (for range case)
```

The count must match exactly. If not:

```python
a, b = [1, 2, 3]   # ValueError: too many values to unpack (expected 2)
a, b, c = [1, 2]   # ValueError: not enough values to unpack (expected 3, got 2)
```

The left-hand side tuple does **not** need parentheses — Python parses comma-separated names on the left of `=` as an implicit tuple of targets.

```python
a, b = 1, 2       # equivalent to (a, b) = (1, 2)
```

## The Swap Idiom — Why It Works

```python
a, b = b, a
```

This is not magic. Here is exactly what happens:

1. Right-hand side `b, a` is evaluated **fully** — produces a tuple `(old_b, old_a)`
2. The tuple is unpacked into `a, b` — `a` gets `old_b`, `b` gets `old_a`

The right-hand side is **always evaluated completely before any binding occurs**. This is what makes the swap safe without a temporary variable.

```python
# In C you need a temp:
# int tmp = a; a = b; b = tmp;

# In Python the RHS evaluation IS the temp:
a, b = b, a    # clean, no temp, no risk of reading a partially-updated value
```

This generalises:

```python
a, b, c = c, a, b    # cyclic rotation — all three evaluated first, then bound
```

## Extended Unpacking: The Star Expression

Python 3 introduced `*name` on the left-hand side. It captures **all remaining elements** as a list.

```python
first, *rest = [1, 2, 3, 4, 5]
print(first)    # 1
print(rest)     # [2, 3, 4, 5]

*init, last = [1, 2, 3, 4, 5]
print(init)     # [1, 2, 3, 4]
print(last)     # 5

first, *middle, last = [1, 2, 3, 4, 5]
print(first)    # 1
print(middle)   # [2, 3, 4]
print(last)     # 5
```

**The starred variable always captures a list**, even if zero or one elements remain:

```python
first, *rest = [1]
print(rest)     # []   ← empty list, not an error

a, *b, c = [1, 2]
print(b)        # []   ← middle captured nothing
```

Only **one** star is allowed per unpacking expression — Python would have no way to resolve ambiguity with two.

```python
*a, *b = [1, 2, 3]    # SyntaxError: two starred expressions in assignment
```

## Nested Unpacking

Targets can be nested to match the structure of nested iterables:

```python
(a, b), c = (1, 2), 3
print(a, b, c)    # 1 2 3

(a, b), (c, d) = (1, 2), (3, 4)
print(a, b, c, d)    # 1 2 3 4
```

This is used constantly when iterating over structured data:

```python
points = [(1, 2), (3, 4), (5, 6)]

for x, y in points:             # nested unpack per iteration
    print(f"x={x}, y={y}")

pairs = [((1, 2), "A"), ((3, 4), "B")]

for (x, y), label in pairs:    # doubly nested
    print(f"({x},{y}) → {label}")
```

---

## Unpacking in For Loops

The `for` loop's target is an assignment target — the same rules apply.

```python
# Simple
for x in [1, 2, 3]:
    ...

# Tuple unpacking — extremely common with enumerate, zip, dict.items()
for i, val in enumerate(["a", "b", "c"]):
    print(i, val)

for key, value in {"x": 1, "y": 2}.items():
    print(key, value)

for (a, b), label in [((1, 2), "A"), ((3, 4), "B")]:
    print(a, b, label)

# Star unpacking in for loops
for first, *rest in [(1, 2, 3), (4, 5, 6, 7)]:
    print(first, rest)
# 1 [2, 3]
# 4 [5, 6, 7]
```

## Unpacking in Function Calls: `*` and `**`

This is the **inverse operation**: instead of unpacking an iterable into names, you unpack a container into function arguments.

```python
def f(a, b, c):
    print(a, b, c)

args = [1, 2, 3]
f(*args)            # equivalent to f(1, 2, 3)

kwargs = {"a": 1, "b": 2, "c": 3}
f(**kwargs)         # equivalent to f(a=1, b=2, c=3)

# Both together:
positional = [1]
keyword    = {"b": 2, "c": 3}
f(*positional, **keyword)    # f(1, b=2, c=3)
```

### Merging Collections with Unpacking (Python 3.5+)

```python
# Merge lists
a = [1, 2, 3]
b = [4, 5, 6]
merged = [*a, *b]           # [1, 2, 3, 4, 5, 6]

# Merge dicts (later keys win on conflict)
d1 = {"x": 1, "y": 2}
d2 = {"y": 99, "z": 3}
merged = {**d1, **d2}       # {"x": 1, "y": 99, "z": 3}
```

This is cleaner and faster than explicit `list.extend` or `dict.update` for constructing new collections inline.

## Ignoring Values with `_`

`_` is a valid Python name. By convention it signals "I am intentionally discarding this value."

```python
first, _, last = (1, 2, 3)    # discard middle value

for _ in range(5):             # loop body doesn't need the index
    print("hello")

_, (x, y) = "A", (3, 4)       # discard the string, keep the pair
```

`_` is also used in the REPL to hold the result of the last expression. In real code it is purely a convention signal — Python treats it as a regular name.

For multiple discards, `*_` absorbs everything unwanted:

```python
first, *_, last = [1, 2, 3, 4, 5, 6]
print(first, last)    # 1 6
```

## Augmented Assignment: `+=`, `-=`, etc.

Augmented assignment is **not** the same as assignment followed by an operation. It is a distinct protocol.

```python
x += y
```

Python:

1. Evaluates the target (`x`) to get the current object
2. Calls `type(x).__iadd__(x, y)` — the in-place method
3. Binds the result back to `x`

If `__iadd__` is not defined, Python falls back to `x = x + y`.

For **mutable** objects that define `__iadd__` (like `list`), step 2 mutates the object and returns `self`. The rebind in step 3 puts the same object back. Net effect: **in-place mutation**, no new object.

For **immutable** objects (like `int`, `str`, `tuple`), `__iadd__` is not defined. Python falls back to `x = x + y`, which creates a new object. Net effect: **rebind**, identical to `x = x + y`.

```python
# Mutable: list
a = [1, 2]
b = a
a += [3]          # __iadd__ → in-place mutation
print(b)          # [1, 2, 3]   ← b sees it (same object)
print(a is b)     # True        ← still same object

# Immutable: int
a = 10
b = a
a += 5            # no __iadd__ → a = a + 5 → new int
print(b)          # 10          ← b unchanged
print(a is b)     # False       ← different objects
```

This is the same mutation-vs-rebinding distinction from [[55. Pass-by-Object-Reference Behavior]], now visible at the assignment level.

## Chained Assignment

```python
a = b = c = 0
```

Python evaluates `0` once, then binds all three names to the **same object**.

```
a ──────┐
b ──────┼──────► int(0)
c ──────┘
```

For immutables this is harmless — `a += 1` rebinds `a` to a new int, leaving `b` and `c` pointing at `0`.

For mutables this is a trap:

```python
a = b = c = []      # ALL THREE point to the SAME list

a.append(1)
print(b)            # [1]   ← surprise
print(c)            # [1]   ← surprise

# Fix: create independent objects
a, b, c = [], [], []
```

The same trap appears in matrix initialisation:

```python
# WRONG: all rows are the same list object
matrix = [[0] * 3] * 3
matrix[0][0] = 99
print(matrix)
# [[99, 0, 0], [99, 0, 0], [99, 0, 0]]  ← all rows changed

# CORRECT: list comprehension creates a new list per row
matrix = [[0] * 3 for _ in range(3)]
matrix[0][0] = 99
print(matrix)
# [[99, 0, 0], [0, 0, 0], [0, 0, 0]]   ← only first row changed
```

## Multiple Assignment Targets (Not the Same as Chained)

```python
a = b = 0    # chained — one evaluation, binds both

a, b = 0, 0  # unpacking — two independent evaluations of literals
             # for literals, same effect; for complex expressions, different
```

```python
import random

# Chained: random() called ONCE, both get same value
a = b = random.random()
print(a == b)    # True (always)

# Unpacking: random() called TWICE, independent values
a, b = random.random(), random.random()
print(a == b)    # False (almost certainly)
```

This distinction matters whenever the right-hand side has side effects or is non-deterministic.

## The Walrus Operator `:=` (Assignment Expression)

Python 3.8 introduced `:=`, which assigns AND returns the value as an expression. It can appear inside conditions, comprehensions, and other expression contexts where `=` cannot.

```python
# Without walrus: compute twice
if len(data) > 10:
    print(f"Long list: {len(data)} elements")

# With walrus: compute once, bind, use
if (n := len(data)) > 10:
    print(f"Long list: {n} elements")
```

```python
# Useful in while loops reading input or processing chunks
while chunk := file.read(8192):
    process(chunk)

# Useful in comprehensions to avoid recomputing expensive expressions
results = [y for x in data if (y := expensive(x)) > threshold]
#          ↑ y is already computed, no need to call expensive(x) again in body
```

`:=` assigns to the **enclosing scope** — not the comprehension's local scope. This is a deliberate design choice so the value is accessible after the comprehension.

```python
filtered = [y for x in range(10) if (y := x ** 2) < 50]
print(y)    # 49 — the last value assigned, accessible outside the comprehension
```

Use `:=` when a value is computed in a condition and needed in the body. Do not use it gratuitously — it reduces readability when the value is only needed once inside a simple condition.

## Bytecode: What Python Actually Executes

For the rigorously curious — here is what `a, b = 1, 2` compiles to:

```python
import dis
dis.dis("a, b = 1, 2")
```

```
  1           0 LOAD_CONST               0 ((1, 2))   ← push tuple onto stack
              2 UNPACK_SEQUENCE          2            ← pop tuple, push elements right-to-left
              4 STORE_NAME               0 (a)        ← bind a
              6 STORE_NAME               1 (b)        ← bind b
```

`UNPACK_SEQUENCE` is the bytecode instruction for unpacking. It pops the iterable from the stack and pushes its elements in **reverse order** (so the first `STORE_NAME` picks up the first element). The extended star form uses `UNPACK_EX` instead.

```python
dis.dis("a, *b, c = [1, 2, 3, 4]")
```

```
  1           0 LOAD_CONST               0 ([1, 2, 3, 4])
              2 UNPACK_EX                1 (1 before, 1 after)
              ...
```

Understanding this confirms that unpacking is a **first-class language operation**, not a macro or transform — it has dedicated bytecode with specific semantics.

## The ML Connection: Data Loading, Batches, and Tuple Returns

### Unpacking Model Outputs

```python
# Most PyTorch models return tuples or namedtuples
logits, hidden = model(x)           # unpack two outputs

# Transformers-style: many outputs, take only what you need
loss, logits, *_ = model(input_ids=ids, labels=labels)
```

### Unpacking DataLoader Batches

```python
for images, labels in dataloader:       # standard supervised batch
    outputs = model(images)
    loss = criterion(outputs, labels)

for (images, masks), labels in loader:  # nested: (input pair, target)
    ...

# Ignoring labels for self-supervised training
for images, _ in dataloader:
    representations = encoder(images)
```

### Unpacking in Training Loops

```python
# Enumerate gives (index, batch) — unpack naturally
for step, (x, y) in enumerate(dataloader):
    loss = model(x, y)
    if step % 100 == 0:
        print(f"Step {step}, loss {loss:.4f}")
```

### Returning Multiple Values from Training Functions

```python
def train_epoch(model, loader, optimizer):
    total_loss, total_acc = 0.0, 0.0
    for x, y in loader:
        loss, acc = compute_loss_and_acc(model, x, y)
        loss.backward()
        optimizer.step()
        optimizer.zero_grad()
        total_loss += loss.item()
        total_acc  += acc.item()
    return total_loss / len(loader), total_acc / len(loader)

train_loss, train_acc = train_epoch(model, train_loader, optimizer)
```

Python functions return one object — but that object can be a tuple, and tuple unpacking makes multiple return values idiomatic and zero-cost.

### Star Unpacking for Flexible Architectures

```python
# Unpack layer sizes from config
first, *hidden, last = [784, 256, 128, 64, 10]

layers = []
in_dim = first
for out_dim in hidden:
    layers += [nn.Linear(in_dim, out_dim), nn.ReLU()]
    in_dim = out_dim
layers.append(nn.Linear(in_dim, last))
model = nn.Sequential(*layers)
```

## Summary

```
Assignment binds a name (or target) to an object. The RHS is always
evaluated completely before any binding begins.

Sequence unpacking: a, b, c = iterable
    → iterates the RHS, binds elements to targets one-to-one
    → count must match unless a star target is present

Extended unpacking: first, *rest = iterable
    → star target captures remaining elements as a list
    → exactly one star allowed per expression

Nested unpacking: (a, b), c = (1, 2), 3
    → matches structure of RHS recursively

Augmented assignment (+=, -=, ...):
    → calls __iadd__ (or equivalent) first
    → mutable objects with __iadd__: mutates in place, rebinds to same object
    → immutable objects: falls back to x = x + y, creates new object

Chained assignment (a = b = expr):
    → expr evaluated once, all targets bound to same object
    → safe for immutables, trap for mutables

Walrus operator (n := expr):
    → assigns and returns in expression context
    → assigns to enclosing scope, not local comprehension scope
```
