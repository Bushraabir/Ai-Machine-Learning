## The One-Line Version

```python
if __name__ == "__main__":
    main()
```

This block runs **only when the file is executed directly** — not when it is imported as a module. Understanding why requires understanding what `__name__` is and how Python sets it.

---

## What Is `__name__`?

`__name__` is a **dunder attribute** that Python sets automatically on every module before executing it. Its value depends on _how_ the module is being run:

|How the file is loaded|`__name__` value|
|---|---|
|Run directly: `python train.py`|`"__main__"`|
|Imported: `import train`|`"train"`|
|Imported as: `from train import X`|`"train"`|
|Run as package: `python -m train`|`"__main__"`|

There is no magic here. Python simply sets `__name__ = "__main__"` before executing the entry-point file, and `__name__ = "<module_name>"` before executing any imported file. The `if` block is just a standard conditional — it checks which case applies.

---

## The Problem It Solves

Consider a file with no guard:

```python
# utils.py — NO guard

def compute_loss(predictions, targets):
    return sum((p - t) ** 2 for p, t in zip(predictions, targets))

# "test" code written at the bottom during development
predictions = [1.0, 2.0, 3.0]
targets     = [1.1, 2.1, 2.9]
print("Loss:", compute_loss(predictions, targets))
```

When you run `utils.py` directly, this works fine. But the moment another file imports it:

```python
# train.py
from utils import compute_loss   # importing triggers execution of utils.py
```

Python executes `utils.py` top to bottom. The test code at the bottom runs. You see:

```
Loss: 0.030000000000000013
```

printed in the middle of your training run — for no reason, with hardcoded dummy data. In a large project, this could mean:

- Unwanted print output contaminating logs
- Database connections being opened
- Files being written
- Slow initialisation code running unnecessarily
- Tests failing because side effects fire on import

The guard prevents this entirely:

```python
# utils.py — WITH guard

def compute_loss(predictions, targets):
    return sum((p - t) ** 2 for p, t in zip(predictions, targets))

if __name__ == "__main__":
    predictions = [1.0, 2.0, 3.0]
    targets     = [1.1, 2.1, 2.9]
    print("Loss:", compute_loss(predictions, targets))
```

Now `from utils import compute_loss` is clean — the test block is skipped entirely.

## Anatomy of the Pattern — Three Roles in One File

The pattern enables a single `.py` file to serve **three roles simultaneously**:

```python
# solver.py

# ── Role 1: Library ──────────────────────────────────────────
# Functions and classes importable by other modules
# These are always defined, regardless of how the file is loaded

def solve(matrix, vector):
    """Solve Ax = b via Gaussian elimination."""
    ...

class GradientDescent:
    def __init__(self, lr=0.01):
        self.lr = lr
    def step(self, params, grads):
        return [p - self.lr * g for p, g in zip(params, grads)]


# ── Role 2: Entry point ──────────────────────────────────────
# Executable behaviour when run as a script

def main():
    import argparse
    parser = argparse.ArgumentParser(description="Run solver")
    parser.add_argument("--lr", type=float, default=0.01)
    parser.add_argument("--steps", type=int, default=100)
    args = parser.parse_args()

    optimizer = GradientDescent(lr=args.lr)
    # ... run the solver ...
    print(f"Solved in {args.steps} steps")


# ── Role 3: Guard ────────────────────────────────────────────
# The switch that activates Role 2 only when appropriate

if __name__ == "__main__":
    main()
```

Usage:

```bash
# As a script — main() runs
python solver.py --lr 0.001 --steps 500

# As a module — main() does not run, only definitions are loaded
python -m pytest test_solver.py
```

## Why Define a `main()` Function?

You could put code directly in the guard:

```python
if __name__ == "__main__":
    # 200 lines of training code here
```

This works but is worse for four reasons:

**1. Scope:** Variables defined directly in the `if` block are module-level globals. Variables inside `main()` are local — they do not persist in the module namespace and cannot accidentally shadow imports.

**2. Testability:** You cannot call `if __name__ == "__main__":` from a test. You can call `main()` — or better, the subfunctions that `main()` delegates to.

**3. Readability:** The function name documents intent. `def main()` signals "this is the entry point."

**4. Profiling:** `python -m cProfile -s cumtime train.py` profiles cleanly when `main()` is a real function — you can see `main` in the call graph.

The discipline is: **keep the guard thin**. The guard calls `main()`. `main()` orchestrates. Individual functions do the real work.

---

## `__name__` Is a Module Attribute — Not Special Syntax

There is nothing syntactically special about `__name__`. It is an ordinary string attribute on the module object:

```python
# In any file, you can inspect it:
print(__name__)        # "__main__" if run directly, module name if imported

# You can inspect other modules' __name__:
import math
print(math.__name__)   # "math"

import os.path
print(os.path.__name__) # "posixpath"  (the actual file behind os.path on Unix)
```

Every module has it. The `if __name__ == "__main__":` pattern is just a conditional that exploits the difference Python sets between these two cases.

---

## `python -m` — Running a Module as a Script

The `-m` flag tells Python to run a module from `sys.path` as a script, setting `__name__ = "__main__"`:

```bash
python -m train          # runs train.py, __name__ == "__main__"
python -m pytest         # runs pytest as a module
python -m pip install X  # runs pip
python -m http.server    # starts a local HTTP server
python -m cProfile train.py  # profiles train.py
```

`python -m module` vs `python module.py` — the key difference is that `-m` imports the module through the normal import system, so relative imports work correctly. Running a file directly as `python script.py` does not go through the package system, which breaks relative imports inside packages.

**Implication for ML projects:** always run your training scripts with `python -m src.train` rather than `python src/train.py`. This ensures your package imports resolve correctly.

## The `__spec__` Check — A Stricter Alternative

In some library code, you need to distinguish between three cases:

1. Run directly: `python script.py`
2. Run as module: `python -m script`
3. Imported: `import script`

`__name__ == "__main__"` catches cases 1 and 2, but not 3. If you need to distinguish case 1 from case 2:

```python
import sys

if __name__ == "__main__":
    if sys.argv[0].endswith("__main__.py"):
        # case 2: python -m package
        ...
    else:
        # case 1: python script.py
        ...
```

Or use `__spec__`:

```python
if __name__ == "__main__" and __spec__ is None:
    # Run directly as a script — NOT via python -m
    ...
```

`__spec__` is `None` when a file is run directly. It is a `ModuleSpec` object when run via `-m`. This distinction rarely matters in application code but appears in framework internals (pytest, multiprocessing).

---

## Multiprocessing — Where the Guard Is Not Optional

On Windows and macOS (with the `spawn` start method), the `multiprocessing` module starts new processes by importing the main module. If there is no guard, every child process re-executes the top-level code — spawning more children, which spawn more children, until the system runs out of resources.

```python
# WRONG on Windows — infinite process explosion
import multiprocessing

def worker(x):
    return x ** 2

pool = multiprocessing.Pool(4)       # spawns 4 processes
results = pool.map(worker, range(10))  # each imports this file → spawns 4 more → ...
print(results)
```

```python
# CORRECT — the guard prevents re-execution in child processes
import multiprocessing

def worker(x):
    return x ** 2

if __name__ == "__main__":
    pool = multiprocessing.Pool(4)
    results = pool.map(worker, range(10))
    print(results)
```

This is not a style issue. On Windows, the incorrect version crashes with a `RuntimeError` and a message telling you to use the guard. PyTorch's `DataLoader` with `num_workers > 0` has the same requirement for the same reason.

## Connection to AI / Machine Learning / Deep Learning

### Training scripts

Every real ML training script follows this structure:

```python
# train.py
import argparse
import torch
import torch.nn as nn
from pathlib import Path
from torch.utils.data import DataLoader

from src.model import ResNet50
from src.data import ImageDataset
from src.utils import save_checkpoint, AverageMeter


def build_model(num_classes: int) -> nn.Module:
    model = ResNet50(num_classes=num_classes)
    return model


def train_one_epoch(model, loader, optimizer, criterion, device):
    model.train()
    loss_meter = AverageMeter()
    for images, labels in loader:
        images, labels = images.to(device), labels.to(device)
        optimizer.zero_grad()
        outputs = model(images)
        loss = criterion(outputs, labels)
        loss.backward()
        optimizer.step()
        loss_meter.update(loss.item(), images.size(0))
    return loss_meter.avg


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--data-dir",    type=Path,  default=Path("data"))
    parser.add_argument("--epochs",      type=int,   default=90)
    parser.add_argument("--lr",          type=float, default=0.1)
    parser.add_argument("--batch-size",  type=int,   default=256)
    parser.add_argument("--num-classes", type=int,   default=1000)
    parser.add_argument("--checkpoint-dir", type=Path, default=Path("checkpoints"))
    args = parser.parse_args()

    device = torch.device("cuda" if torch.cuda.is_available() else "cpu")

    model     = build_model(args.num_classes).to(device)
    optimizer = torch.optim.SGD(model.parameters(), lr=args.lr, momentum=0.9)
    criterion = nn.CrossEntropyLoss()

    train_dataset = ImageDataset(args.data_dir / "train")
    train_loader  = DataLoader(train_dataset,
                               batch_size=args.batch_size,
                               num_workers=4,     # requires the guard on Windows
                               shuffle=True)

    for epoch in range(args.epochs):
        loss = train_one_epoch(model, train_loader, optimizer, criterion, device)
        print(f"Epoch {epoch+1}/{args.epochs}  loss={loss:.4f}")
        save_checkpoint(model, optimizer, epoch, loss, args.checkpoint_dir)


if __name__ == "__main__":
    main()
```

Note what this enables:

- `from train import build_model` works cleanly in a test — no training loop fires
- `DataLoader(num_workers=4)` works on Windows — the guard prevents subprocess explosion
- `python -m train --lr 0.01 --epochs 200` works from any directory via `-m`
- `argparse` inside `main()` does not interfere with imports — `sys.argv` is not touched at import time

### Pytest and test discovery

```python
# test_model.py
from train import build_model   # safe — guard prevents main() from running

def test_output_shape():
    model = build_model(num_classes=10)
    x = torch.randn(4, 3, 224, 224)
    y = model(x)
    assert y.shape == (4, 10)
```

Without the guard, `import train` would immediately start a training run whenever pytest collects the test file. With the guard, only the definitions are loaded — exactly what the test needs.

### Hugging Face training scripts

The official Hugging Face example scripts (`run_clm.py`, `run_glue.py`, etc.) all use this exact structure: functions defined at module level, `main()` orchestrates, `if __name__ == "__main__": main()` at the bottom. They are designed to be both run directly and imported in notebooks or sweep scripts.

### `torch.multiprocessing` and `DataLoader`

```python
# Required when num_workers > 0 on Windows/macOS with spawn
if __name__ == "__main__":
    loader = DataLoader(dataset, num_workers=8, batch_size=64)
    for batch in loader:
        ...
```

PyTorch's documentation explicitly states this requirement. The underlying reason is identical to the `multiprocessing` case above — the `spawn` start method re-imports the main module in each worker process.

## Common Mistakes and Pitfalls

**1. Putting imports inside the guard**

```python
# Wrong — torch is only importable when run directly
if __name__ == "__main__":
    import torch
    import numpy as np

    model = torch.nn.Linear(10, 1)
```

Imports belong at the top of the file. Other modules that import this file need those names too. Only _execution logic_ belongs inside the guard.

**2. Writing the guard without `main()`**

```python
if __name__ == "__main__":
    # 300 lines of code
    data = load_data(...)
    model = build_model(...)
    for epoch in range(100):
        ...
```

Technically correct but untestable and unreadable. Extract into `main()` (and sub-functions). Keep the guard to one line.

**3. Misspelling the dunder strings**

```python
if __name__ == "__main__":    # correct
if __name__ == '__main__':    # also correct — single quotes are fine
if __name__ == "__main_ _":   # wrong — space inside — always False, silently
if __Name__ == "__main__":    # wrong — capital N — NameError
```

Python will not warn you. The block simply never runs.

**4. Expecting the guard to prevent execution in subprocesses on Unix**

On Linux with the `fork` start method (the default), child processes are forked — they do not re-import the main module. The guard is not strictly required for `multiprocessing` on Linux. But write it anyway: your code should be platform-agnostic, and the guard is free.

## Summary

|Concept|What to remember|
|---|---|
|`__name__`|A string attribute Python sets on every module automatically|
|When run directly|`__name__ == "__main__"` → `True` → guard block executes|
|When imported|`__name__ == "<module_name>"` → `False` → guard block skipped|
|`python -m module`|Also sets `__name__ = "__main__"` — use for package entry points|
|`main()` function|Keep the guard thin — one line that calls `main()`|
|Multiprocessing|Guard is **required** on Windows with `spawn`; `DataLoader(num_workers>0)` same|
|Core invariant|Definitions always load. Side effects only fire when appropriate.|

The pattern enforces one discipline that scales from a 50-line utility script to a 50,000-line ML framework: **define behaviour in functions, trigger behaviour explicitly.** Importability is not an afterthought — it is a design constraint. Every `.py` file you write should be safely importable, and the guard is the mechanism that guarantees it.
