# 34. iter() and next()

> _"An iterator is a machine that produces one value at a time, on demand. Understanding it is understanding how Python's entire for loop works under the hood."_

**Prerequisites:** [[26.Classes and objects]] · [[27.init, self]] · [[32.Dunder or magic methods]] · [[33.Encapsulation basics]]

---

## The Problem Iterators Solve

Suppose you have a billion-element dataset. Loading it all into a list and then looping over it requires a billion elements in memory simultaneously. An iterator gives you one element at a time — the next element is computed only when asked for. Memory usage stays constant regardless of dataset size.

This is the **lazy evaluation** model. It is foundational to how Python handles `for` loops, file reading, database cursors, and — critically — how PyTorch `DataLoader` feeds batches to a neural network.

---

## Two Distinct Protocols

Python separates two concerns cleanly:

|Protocol|Dunder Methods|Role|
|---|---|---|
|**Iterable**|`__iter__`|_"I can produce an iterator"_|
|**Iterator**|`__iter__` + `__next__`|_"I am the thing that yields values one by one"_|

Every iterator is also an iterable (it returns itself from `__iter__`). Not every iterable is an iterator — a list is iterable but not an iterator; it produces a fresh iterator each time you iterate over it.

```
┌─────────────────────────────────────────────┐
│                  ITERABLES                  │
│  list, tuple, str, dict, set, range, file   │
│                                             │
│   ┌─────────────────────────────────────┐   │
│   │            ITERATORS                │   │
│   │  list_iterator, file object,        │   │
│   │  generator, zip, map, enumerate     │   │
│   └─────────────────────────────────────┘   │
└─────────────────────────────────────────────┘
```

## `iter()` — Obtaining an Iterator

`iter(obj)` calls `obj.__iter__()` and returns an iterator object.

```python
nums = [10, 20, 30]

it = iter(nums)
print(type(it))    # <class 'list_iterator'>
print(it)          # <list_iterator object at 0x...>
```

The list `nums` itself has not changed. `it` is a _separate object_ that maintains a position pointer into `nums`.

**Each call to `iter()` on an iterable gives a fresh, independent iterator:**

```python
nums = [1, 2, 3]

it1 = iter(nums)
it2 = iter(nums)

next(it1)   # 1
next(it1)   # 2
next(it2)   # 1  — it2 is completely independent
```

## `next()` — Advancing the Iterator

`next(it)` calls `it.__next__()`. It returns the next value and advances the internal pointer. When exhausted, it raises `StopIteration`.

```python
nums = [10, 20, 30]
it = iter(nums)

print(next(it))   # 10
print(next(it))   # 20
print(next(it))   # 30
print(next(it))   # StopIteration — the iterator is exhausted
```

`StopIteration` is not an error to be alarmed by — it is the _signal_ Python's `for` loop uses to know when to stop.

**Optional default value — avoids StopIteration:**

```python
it = iter([1, 2])
print(next(it, None))   # 1
print(next(it, None))   # 2
print(next(it, None))   # None — default returned instead of raising
print(next(it, -1))     # -1
```

This is useful when you want to peek at the first element of an iterator without crashing.

## What a `for` Loop Actually Does

Every Python `for` loop is syntactic sugar for the iterator protocol. The following two blocks are exactly equivalent:

```python
# What you write:
for x in [10, 20, 30]:
    print(x)

# What Python executes:
_iter = iter([10, 20, 30])     # call __iter__
while True:
    try:
        x = next(_iter)        # call __next__
        print(x)
    except StopIteration:
        break                  # loop ends when exhausted
```

This is the complete mental model. Every `for` loop — over a list, a string, a file, a `range`, a generator, a PyTorch `DataLoader` — uses exactly this protocol.

## Building Your Own Iterable and Iterator

### Case 1 — Separate iterable and iterator classes

This is the cleanest separation. The iterable holds the data; the iterator holds the traversal state.

```python
class CountUp:
    """An iterable that counts from start to stop (inclusive)."""

    def __init__(self, start, stop):
        self.start = start
        self.stop = stop

    def __iter__(self):
        return CountUpIterator(self.start, self.stop)


class CountUpIterator:
    """The iterator: holds the current position."""

    def __init__(self, current, stop):
        self.current = current
        self.stop = stop

    def __iter__(self):
        return self   # an iterator must return itself

    def __next__(self):
        if self.current > self.stop:
            raise StopIteration
        value = self.current
        self.current += 1
        return value


counter = CountUp(1, 4)

for n in counter:
    print(n)          # 1  2  3  4

# Can iterate again — fresh iterator each time
for n in counter:
    print(n)          # 1  2  3  4  — starts over
```

**Why separate classes?** Because you can iterate `counter` multiple times independently. Each `for` loop calls `iter(counter)` and gets a brand-new `CountUpIterator` with `current` reset.

---

### Case 2 — Object is its own iterator

When the object should only be traversed once (like a file or a network stream), collapse both roles into one class.

```python
class FileLines:
    """
    Reads a file line by line — one pass only.
    The object is its own iterator.
    """

    def __init__(self, path):
        self._file = open(path, 'r')

    def __iter__(self):
        return self          # returns itself — it IS the iterator

    def __next__(self):
        line = self._file.readline()
        if line == '':
            self._file.close()
            raise StopIteration
        return line.rstrip('\n')
```

This object cannot be re-iterated once exhausted — the file pointer is at the end. That is intentional for one-pass data sources.

## `iter()` with a Sentinel — The Two-Argument Form

`iter(callable, sentinel)` is a lesser-known but powerful pattern. It calls `callable()` repeatedly and stops when the return value equals `sentinel`.

```python
import random

# Simulate rolling a die until you roll a 6
roll = iter(lambda: random.randint(1, 6), 6)
results = list(roll)
print(results)   # e.g. [3, 1, 4, 1, 5]  — all rolls before the 6

# Reading a binary file in fixed-size chunks:
with open("data.bin", "rb") as f:
    for chunk in iter(lambda: f.read(1024), b''):
        process(chunk)   # each iteration gives 1024 bytes, stops at EOF
```

The sentinel form is elegant for consuming streams where you don't know the length in advance.

## Iterators Are Stateful and Single-Pass

This is the most important pitfall. **An exhausted iterator stays exhausted.**

```python
nums = [1, 2, 3]
it = iter(nums)

print(list(it))   # [1, 2, 3]
print(list(it))   # []  — already exhausted, nothing left

# Compare: the list itself is re-iterable
print(list(nums)) # [1, 2, 3]
print(list(nums)) # [1, 2, 3]
```

```python
# Calling iter() on an iterator returns the same object — it doesn't reset
it = iter([1, 2, 3])
next(it)          # 1
it2 = iter(it)    # same object, not a new one
next(it2)         # 2  — continues from where it left off
print(it is it2)  # True
```

This matters enormously in practice. If you pass an iterator to a function that consumes it, it is gone. Pass the original iterable if you need to iterate multiple times.

## Worked Example — Sliding Window Iterator

A sliding window produces consecutive overlapping subsequences. This is used constantly in time-series ML preprocessing.

```python
class SlidingWindow:
    """
    Produces windows of fixed size over a sequence.

    SlidingWindow([1, 2, 3, 4, 5], size=3)
    → (1, 2, 3), (2, 3, 4), (3, 4, 5)
    """

    def __init__(self, sequence, size):
        if size > len(sequence):
            raise ValueError("Window size cannot exceed sequence length")
        self._seq = sequence
        self._size = size
        self._start = 0

    def __iter__(self):
        self._start = 0    # reset so it's re-iterable
        return self

    def __next__(self):
        end = self._start + self._size
        if end > len(self._seq):
            raise StopIteration
        window = tuple(self._seq[self._start:end])
        self._start += 1
        return window

    def __len__(self):
        return max(0, len(self._seq) - self._size + 1)


prices = [100, 102, 98, 105, 110, 107]
windows = SlidingWindow(prices, size=3)

for w in windows:
    print(w)

# (100, 102, 98)
# (102, 98, 105)
# (98, 105, 110)
# (105, 110, 107)

print(f"Total windows: {len(windows)}")   # 4
```

## Inspecting Iterators

```python
from collections.abc import Iterable, Iterator

nums = [1, 2, 3]
it = iter(nums)

print(isinstance(nums, Iterable))   # True  — list is iterable
print(isinstance(nums, Iterator))   # False — list is NOT an iterator

print(isinstance(it, Iterable))     # True  — iterator is also iterable
print(isinstance(it, Iterator))     # True  — and it is an iterator

# Checking what protocol an object supports:
print(hasattr(nums, '__iter__'))    # True
print(hasattr(nums, '__next__'))    # False — no __next__, not an iterator
print(hasattr(it, '__next__'))      # True
```

Use `collections.abc` for proper type checking — it handles all the edge cases including virtual subclasses.

## Common Pitfalls

```python
# PITFALL 1: Forgetting StopIteration in __next__
class Broken:
    def __init__(self):
        self.data = [1, 2, 3]
        self.i = 0

    def __iter__(self): return self

    def __next__(self):
        val = self.data[self.i]   # IndexError instead of StopIteration!
        self.i += 1
        return val
# Fix: check self.i >= len(self.data) first, then raise StopIteration


# PITFALL 2: Consuming an iterator twice
def total_and_mean(it):
    total = sum(it)         # consumes the iterator
    count = sum(1 for _ in it)  # it is now empty! count = 0
    return total, total / count  # ZeroDivisionError
# Fix: convert to list first, or pass the iterable not the iterator


# PITFALL 3: Modifying a collection while iterating
d = {'a': 1, 'b': 2, 'c': 3}
for key in d:
    if d[key] == 2:
        del d[key]   # RuntimeError: dictionary changed size during iteration
# Fix: iterate over list(d.keys()) or collect keys to delete, then delete after


# PITFALL 4: Thinking iter() on an iterator resets it
it = iter([1, 2, 3])
next(it)        # 1
it_again = iter(it)
next(it_again)  # 2  — NOT 1. iter() on an iterator returns the same object.
```

## Relation to Built-ins That Return Iterators

Many Python built-ins return iterators, not lists. This is intentional — they are lazy.

```python
m = map(str, [1, 2, 3])        # map object — iterator
f = filter(None, [0, 1, 2])    # filter object — iterator
z = zip([1, 2], ['a', 'b'])    # zip object — iterator
e = enumerate(['x', 'y'])      # enumerate object — iterator
r = reversed([1, 2, 3])        # list_reverseiterator — iterator

# All consumed by: list(), tuple(), for loop, or next()
print(list(m))   # ['1', '2', '3']
```

This is why you can write `for i, val in enumerate(data)` directly — `enumerate` produces an iterator of `(index, value)` tuples on demand.

## Connection to AI/ML and Deep Learning

### PyTorch DataLoader — Industrial Iterator

The most important iterator you will use in deep learning is `torch.utils.data.DataLoader`. It is an iterator over your dataset that handles batching, shuffling, and parallel data loading.

```python
from torch.utils.data import DataLoader, TensorDataset
import torch

X = torch.randn(1000, 28 * 28)   # 1000 MNIST-like images
y = torch.randint(0, 10, (1000,))

dataset = TensorDataset(X, y)
loader = DataLoader(dataset, batch_size=32, shuffle=True)

# loader IS an iterator (technically an iterable that produces iterators)
for batch_X, batch_y in loader:
    # batch_X.shape: (32, 784)
    # Only 32 samples in memory at once — not all 1000
    outputs = model(batch_X)
    loss = criterion(outputs, batch_y)
    loss.backward()
    optimizer.step()
    optimizer.zero_grad()
```

Under the hood, `DataLoader.__iter__` returns a `_SingleProcessDataLoaderIter` or `_MultiProcessingDataLoaderIter`. Each `__next__` call collates a batch from the dataset. The `for` loop drives this via the exact protocol you just learned.

**Why lazy loading matters at scale:** ImageNet has 1.2 million high-resolution images. Loading the full dataset into RAM is impossible. The DataLoader iterator reads only the current batch from disk, preprocesses it, and yields it. Memory usage is bounded by `batch_size`, not dataset size.

### Infinite Iterators for Online Learning

Some training loops never fully exhaust data — they sample indefinitely:

```python
class InfiniteLoader:
    """Wraps a DataLoader to cycle forever — useful for online learning."""

    def __init__(self, loader):
        self._loader = loader
        self._iter = iter(loader)

    def __iter__(self):
        return self

    def __next__(self):
        try:
            return next(self._iter)
        except StopIteration:
            self._iter = iter(self._loader)   # restart
            return next(self._iter)

# Usage in a training loop driven by steps, not epochs:
loader = DataLoader(dataset, batch_size=32, shuffle=True)
inf = InfiniteLoader(loader)

for step in range(10_000):
    batch_X, batch_y = next(inf)   # never raises StopIteration
    # ... train ...
```

This pattern is idiomatic in reinforcement learning and large-scale pretraining where you measure progress in steps, not epochs.

### Streaming Data Pipelines — The Iterator Chain Pattern

In production ML, you often need to apply a sequence of transformations to data lazily:

```python
def load_records(path):
    """Yields raw records from disk one at a time."""
    with open(path) as f:
        for line in f:               # file objects are iterators
            yield line.strip()

def parse(records):
    """Lazily parses each record."""
    for record in records:
        yield record.split(',')

def normalize(rows):
    """Lazily normalises numeric fields."""
    for row in rows:
        yield [float(x) / 255.0 for x in row]

# Chain: nothing loads until you call next()
pipeline = normalize(parse(load_records("data.csv")))

for row in pipeline:
    feed_to_model(row)
```

Each stage is a generator (covered in [[35.Generator functions]]). The iterator protocol is the glue that connects them. This is exactly how `tf.data.Dataset` and similar streaming pipelines are designed.

## Summary

The iterator protocol is two dunder methods: `__iter__` returns an iterator, `__next__` returns the next value and raises `StopIteration` when done. Every `for` loop, every comprehension, every `map`, `filter`, `zip`, and `enumerate` runs on this protocol. The distinction between an _iterable_ (can produce an iterator) and an _iterator_ (is the thing producing values) is the most important conceptual boundary in this note.

|Concept|Key Point|
|---|---|
|`iter(x)`|Calls `x.__iter__()`, returns an iterator|
|`next(it)`|Calls `it.__next__()`, raises `StopIteration` when done|
|`for` loop|Sugar for `iter()` + `next()` in a `while True` + `try/except`|
|Iterable|Has `__iter__`; can be iterated multiple times|
|Iterator|Has `__iter__` + `__next__`; single-pass, stateful|
|Exhausted iterator|Stays exhausted; `iter()` on it returns itself|
|`iter(callable, sentinel)`|Calls `callable()` until it returns `sentinel`|
