# 31. `super()`

## What `super()` Is

`super()` returns a **proxy object** that delegates method calls to the next class in the MRO (Method Resolution Order). It is the correct, robust way to call a parent class's method from a child class — without hardcoding the parent's name.

The naive alternative — calling `ParentClass.method(self, ...)` directly — works in simple single inheritance but silently breaks in multiple inheritance and during refactoring. `super()` is the general solution.

```python
class Animal:
    def __init__(self, name):
        self.name = name

class Dog(Animal):
    def __init__(self, name, breed):
        super().__init__(name)   # delegates to Animal.__init__
        self.breed = breed

d = Dog("Rex", "Labrador")
print(d.name)    # Rex    — set by Animal.__init__ via super()
print(d.breed)   # Labrador — set by Dog.__init__
```

---

## The Mechanical Reality — What `super()` Actually Does

`super()` does **not** simply call the parent class. It calls the **next class in the MRO of the instance's actual class**. These are different things in multiple inheritance.

```python
super()
# is equivalent to:
super(__class__, self)
```

Two arguments:

- `__class__` — the class where this `super()` call is written (determined at compile time, not runtime)
- `self` — the instance (determines which MRO to use)

Python finds `__class__` in the MRO, then returns a proxy that starts searching **one step after** `__class__` in that MRO.

```python
class A:
    def greet(self):
        return "A"

class B(A):
    def greet(self):
        # __class__ is B, self is a D instance
        # MRO of D: D → B → C → A
        # super() starts after B → finds C.greet
        return "B + " + super().greet()

class C(A):
    def greet(self):
        return "C + " + super().greet()

class D(B, C):
    def greet(self):
        return "D + " + super().greet()

print(D().greet())      # D + B + C + A
print(D.__mro__)        # D, B, C, A, object
```

Each `super()` call hands off to the next class in the MRO — not to the literal parent. This is the cooperative multiple inheritance pattern.

## Why Not Just Hardcode the Parent Name

```python
# Fragile — hardcodes the parent name
class Dog(Animal):
    def __init__(self, name, breed):
        Animal.__init__(self, name)   # works, but brittle
        self.breed = breed
```

**Problem 1 — Refactoring breaks silently:**

If you rename `Animal` to `Creature`, every hardcoded call breaks. `super()` is always correct regardless of class name.

**Problem 2 — Multiple inheritance calls the grandparent twice:**

```python
class A:
    def __init__(self):
        print("A init")

class B(A):
    def __init__(self):
        A.__init__(self)   # hardcoded
        print("B init")

class C(A):
    def __init__(self):
        A.__init__(self)   # hardcoded
        print("C init")

class D(B, C):
    def __init__(self):
        B.__init__(self)
        C.__init__(self)
        print("D init")

D()
# A init   ← called by B
# B init
# A init   ← called again by C — wrong
# C init
# D init
```

`A.__init__` runs twice. With `super()`, each class in the MRO runs exactly once:

```python
class A:
    def __init__(self):
        super().__init__()
        print("A init")

class B(A):
    def __init__(self):
        super().__init__()
        print("B init")

class C(A):
    def __init__(self):
        super().__init__()
        print("C init")

class D(B, C):
    def __init__(self):
        super().__init__()
        print("D init")

D()
# A init   ← called exactly once
# C init
# B init
# D init
```

MRO for D: `D → B → C → A → object`. Each `super()` hands off to the next — no class runs twice.

## `super()` in `__init__` — The Most Common Use

The most frequent use of `super()` is in `__init__` to ensure the parent sets up its attributes before the child adds its own.

```python
class Shape:
    def __init__(self, color="black"):
        self.color = color
        self.visible = True

class Circle(Shape):
    def __init__(self, radius, color="black"):
        super().__init__(color)      # Shape sets self.color, self.visible
        self.radius = radius         # Circle adds self.radius

    def area(self):
        import math
        return math.pi * self.radius ** 2

class ColoredCircle(Circle):
    def __init__(self, radius, color, opacity=1.0):
        super().__init__(radius, color)   # Circle's __init__, which calls Shape's
        self.opacity = opacity

c = ColoredCircle(5, "red", 0.8)
print(c.color)    # red     — set by Shape.__init__
print(c.radius)   # 5       — set by Circle.__init__
print(c.opacity)  # 0.8     — set by ColoredCircle.__init__
```

The chain: `ColoredCircle.__init__` → `super()` → `Circle.__init__` → `super()` → `Shape.__init__`. Each level adds its own attributes. No duplication, no missed initialization.

## `super()` for Method Extension

Beyond `__init__`, `super()` is used to extend any method — run the parent's version, then add child behavior.

```python
class Logger:
    def log(self, msg):
        print(f"[LOG] {msg}")

class TimestampLogger(Logger):
    def log(self, msg):
        import datetime
        timestamp = datetime.datetime.now().strftime("%H:%M:%S")
        super().log(f"{timestamp} — {msg}")   # extend, not replace

class PrefixLogger(TimestampLogger):
    def log(self, msg):
        super().log(f"[APP] {msg}")

p = PrefixLogger()
p.log("Server started")
# [LOG] 14:32:07 — [APP] Server started
```

The call chain: `PrefixLogger.log` → `TimestampLogger.log` → `Logger.log`. Each layer adds its transformation. The output is the composition of all three.

## `super()` with `@classmethod`

`super()` works inside class methods too. `cls` replaces `self`, and `super()` still uses the MRO correctly.

```python
class Animal:
    @classmethod
    def create(cls, name):
        print(f"Animal.create called with cls={cls.__name__}")
        return cls(name)

    def __init__(self, name):
        self.name = name

class Dog(Animal):
    def __init__(self, name, breed="unknown"):
        super().__init__(name)
        self.breed = breed

    @classmethod
    def create_puppy(cls):
        instance = super().create("Puppy")   # calls Animal.create with cls=Dog
        instance.breed = "Mixed"
        return instance

d = Dog.create_puppy()
print(d.name)    # Puppy
print(d.breed)   # Mixed
```

## `super()` with `@staticmethod`

Static methods do not receive `cls` or `self`, so `super()` cannot be called inside them using the zero-argument form. You must use the explicit two-argument form or restructure as a class method.

```python
class A:
    @staticmethod
    def helper():
        return "A helper"

class B(A):
    @staticmethod
    def helper():
        # super().helper()   ← NameError: super() without args needs __class__
        return A.helper() + " + B"   # only option for static methods
```

This is a known limitation. If you find yourself needing `super()` in a static method, that is a signal to reconsider whether it should be a class method instead.

---

## Explicit Two-Argument Form — `super(Class, obj)`

The zero-argument `super()` (Python 3) is shorthand for `super(__class__, self)`. You can also call it explicitly, which is useful in some dynamic scenarios.

```python
class A:
    def greet(self):
        return "A"

class B(A):
    def greet(self):
        return "B + " + super(B, self).greet()   # explicit form

class C(B):
    def greet(self):
        return "C + " + super(C, self).greet()

print(C().greet())   # C + B + A
```

The explicit form is occasionally needed when:

- Working outside a method body (in a function, not a method)
- Writing Python 2 compatible code (Python 2 requires the explicit form)
- Deliberately skipping a class in the MRO (rare, usually a design smell)

In modern Python 3, always use `super()` with no arguments.

## `super()` and `object`

At the top of every MRO sits `object`. When `super()` reaches `object`, it calls `object.__init__()` — which accepts no arguments beyond `self`. This is usually harmless, but in cooperative multiple inheritance it requires care.

```python
class A:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)   # passes remaining kwargs up the chain

class B:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)

class C(A, B):
    def __init__(self, x, y):
        super().__init__(x=x, y=y)   # all kwargs forwarded

# Eventually object.__init__() is called with no kwargs — fine if they're consumed
```

The pattern: use `**kwargs` to pass unhandled arguments up the MRO. Each class pops the arguments it knows about and passes the rest up. `object.__init__` is called with an empty dict at the end.

## Full ML Example — Layer System

```python
class Module:
    def __init__(self):
        self.training = True
        self._layers = []

    def forward(self, x):
        raise NotImplementedError

    def __call__(self, x):
        return self.forward(x)

    def parameters(self):
        return []


class TrainableModule(Module):
    def __init__(self, lr=0.01):
        super().__init__()           # Module sets training, _layers
        self.lr = lr
        self.grad = None

    def zero_grad(self):
        self.grad = None


class Linear(TrainableModule):
    def __init__(self, in_features, out_features, lr=0.01):
        super().__init__(lr=lr)      # TrainableModule sets lr, grad; Module sets training
        self.weights = [0.0] * in_features
        self.bias = 0.0
        self.in_features = in_features
        self.out_features = out_features

    def forward(self, x):
        return sum(w * xi for w, xi in zip(self.weights, x)) + self.bias

    def __repr__(self):
        return f"Linear({self.in_features} → {self.out_features}, lr={self.lr})"


layer = Linear(4, 1, lr=0.001)
print(layer)            # Linear(4 → 1, lr=0.001)
print(layer.training)   # True    — from Module via super() chain
print(layer.lr)         # 0.001   — from TrainableModule
print(layer.weights)    # [0.0, 0.0, 0.0, 0.0] — from Linear
```

The `super()` chain: `Linear.__init__` → `TrainableModule.__init__` → `Module.__init__`. Each level sets its own attributes. No duplication. No missed initialization.

## Common Errors

```python
# 1. Forgetting super().__init__() entirely
class Dog(Animal):
    def __init__(self, name, breed):
        self.breed = breed    # Animal.__init__ never called
        # self.name never set — AttributeError later

# 2. Calling super() after setting attributes that depend on parent state
class Dog(Animal):
    def __init__(self, name, breed):
        self.full_info = f"{self.name} the {breed}"  # AttributeError — name not set yet
        super().__init__(name)   # too late

# Fix: super().__init__ first, always
class Dog(Animal):
    def __init__(self, name, breed):
        super().__init__(name)
        self.full_info = f"{self.name} the {breed}"   # fine now

# 3. super() outside a method — zero-arg form fails
def standalone():
    super()   # RuntimeError: super(): no arguments

# 4. Wrong argument count passed to super().__init__
class Animal:
    def __init__(self, name, age):
        self.name = name
        self.age = age

class Dog(Animal):
    def __init__(self, name, breed):
        super().__init__(name)    # TypeError: missing 'age'

# 5. Forgetting super() in cooperative multiple inheritance
class B(A):
    def __init__(self):
        # super().__init__() missing — C.__init__ never called in diamond
        print("B init")
```

## Decision Guide — When to Use `super()`

```
Are you overriding __init__ and the parent has state to set up?
    YES → call super().__init__() — always, as the first line

Are you overriding a method but want to keep the parent's behavior?
    YES → call super().method_name() — either before or after your additions

Are you completely replacing the parent's method?
    NO super() needed — you own the entire behavior

Are you using multiple inheritance?
    YES → every class in the chain should call super() — cooperative pattern
```
