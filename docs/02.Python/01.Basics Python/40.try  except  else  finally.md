# 40. `try` / `except` / `else` / `finally`

> _"An exception is not an error in the pejorative sense. It is a signal — a formal notification that the normal flow of execution cannot continue. The question is not whether to handle it, but where, and how precisely."_

---

## The Core Idea

Python's exception handling is a **structured control flow mechanism**. When something goes wrong inside a `try` block, Python unwinds the call stack looking for a matching `except` clause. If it finds one, execution transfers there. If it doesn't, the program terminates with a traceback.

The full four-clause structure:

```python
try:
    # code that might raise an exception
except SomeException:
    # runs if SomeException (or a subclass) was raised in try
else:
    # runs only if NO exception was raised in try
finally:
    # runs ALWAYS — exception or not, return or not
```

Each clause has a precise, non-overlapping role. The confusion comes from not understanding `else` and `finally`. We will fix that.

---

## How Python Raises and Propagates Exceptions

Before handling, understand the mechanism.

When an exception is raised:

1. Python creates an **exception object** (an instance of some `Exception` subclass)
2. Normal execution stops immediately at that line
3. Python walks **up the call stack** frame by frame, looking for a matching `except`
4. If found — execution transfers to that handler
5. If not found — the exception is **unhandled**; Python prints a traceback and exits

```python
def c():
    raise ValueError("something went wrong")

def b():
    c()           # exception propagates up from c()

def a():
    b()           # exception propagates up from b()

try:
    a()           # caught here
except ValueError as e:
    print(f"Caught: {e}")
```

The exception does not stop at `c()` — it bubbles up through `b()`, through `a()`, until a handler is found. This is **stack unwinding**.

## `try` / `except` — The Minimum

```python
try:
    result = int("not a number")
except ValueError:
    print("conversion failed")
```

**Catching the exception object:**

```python
try:
    result = int("abc")
except ValueError as e:
    print(type(e))    # <class 'ValueError'>
    print(e)          # invalid literal for int() with base 10: 'abc'
    print(e.args)     # ('invalid literal for int() with base 10: \'abc\'',)
```

The `as e` binding gives you the exception instance. `e.args` is always a tuple of the arguments passed to the exception constructor.

## Catching Multiple Exception Types

**Multiple `except` clauses — checked in order, first match wins:**

```python
try:
    value = data[key]
except KeyError:
    print("key not found")
except TypeError:
    print("data is not subscriptable")
```

**Catching multiple types in one clause:**

```python
try:
    result = int(user_input) / divisor
except (ValueError, ZeroDivisionError) as e:
    print(f"Input error: {e}")
```

**Catching any exception — use sparingly:**

```python
try:
    risky_operation()
except Exception as e:
    print(f"Unexpected error: {type(e).__name__}: {e}")
```

Do **not** write `except:` with no type. This catches everything including `KeyboardInterrupt`, `SystemExit`, and `GeneratorExit` — signals that are meant to propagate. Always catch at least `Exception`.

```python
# BAD — swallows Ctrl+C, sys.exit(), everything
try:
    ...
except:
    pass

# CORRECT — lets system signals through
try:
    ...
except Exception:
    pass
```

## The Exception Hierarchy

The `except` clause matches the named type **and all its subclasses**. This is why catching order matters.

```
BaseException
├── SystemExit
├── KeyboardInterrupt
├── GeneratorExit
└── Exception
    ├── ArithmeticError
    │   ├── ZeroDivisionError
    │   ├── OverflowError
    │   └── FloatingPointError
    ├── LookupError
    │   ├── IndexError
    │   └── KeyError
    ├── ValueError
    ├── TypeError
    ├── AttributeError
    ├── NameError
    ├── OSError
    │   ├── FileNotFoundError
    │   ├── PermissionError
    │   └── TimeoutError
    ├── RuntimeError
    ├── StopIteration
    └── ... (many more)
```

**Catch more specific exceptions first:**

```python
# BAD — LookupError catches both IndexError and KeyError
# The specific clauses below it are unreachable
try:
    ...
except LookupError:
    ...
except IndexError:   # DEAD CODE — never reached
    ...

# CORRECT — specific first, general last
try:
    ...
except IndexError:
    ...
except KeyError:
    ...
except LookupError:   # catches anything else in the LookupError family
    ...
```

## `else` — The Most Misunderstood Clause

The `else` clause runs **only if the `try` block completed without raising any exception**.

```python
try:
    result = int(user_input)
except ValueError:
    print("Not a valid integer")
else:
    print(f"Got: {result}")   # only runs if int() succeeded
```

**Why `else` exists — the precise semantic distinction:**

```python
# Without else — ambiguous
try:
    result = int(user_input)
    print(f"Got: {result}")   # did this fail, or did int() fail?
except ValueError:
    print("error")

# With else — unambiguous
try:
    result = int(user_input)  # only this is "protected"
except ValueError:
    print("error")
else:
    print(f"Got: {result}")   # this runs only on success
```

The `else` clause narrows the scope of what the `except` is guarding. Code in `else` is not protected by the `except` above it — if `else` raises, that exception propagates normally.

```python
try:
    f = open("data.txt")
except FileNotFoundError:
    print("file missing")
else:
    data = f.read()   # if THIS raises, FileNotFoundError above does NOT catch it
    f.close()
```

This is the correct design — you only want `FileNotFoundError` to guard the `open()` call, not everything that follows.

---

## `finally` — The Guarantee

The `finally` clause runs **unconditionally** — whether an exception was raised or not, whether it was caught or not, even if there is a `return` statement inside `try`.

```python
try:
    result = 10 / 0
except ZeroDivisionError:
    print("division by zero")
finally:
    print("this always runs")

# Output:
# division by zero
# this always runs
```

**`finally` runs even when an exception is NOT caught:**

```python
try:
    raise RuntimeError("uncaught")
finally:
    print("cleanup")   # prints before the program crashes

# Output:
# cleanup
# Traceback (most recent call last):
#   ...
# RuntimeError: uncaught
```

**`finally` runs even through a `return`:**

```python
def f():
    try:
        return 1
    finally:
        print("finally runs")   # runs before the return

f()
# Output: finally runs
# Returns: 1
```

**`finally` can override a `return`:**

```python
def f():
    try:
        return 1
    finally:
        return 2   # overrides the return 1

print(f())   # 2
```

This is almost always unintentional. Avoid `return`, `break`, or `continue` inside `finally` — they suppress exceptions silently.

## Full Four-Clause Flow — Execution Map

```
Enter try block
    │
    ├── No exception raised
    │       │
    │       ├── except: SKIPPED
    │       ├── else:   RUNS
    │       └── finally: RUNS
    │
    └── Exception raised
            │
            ├── Matching except found
            │       │
            │       ├── except: RUNS
            │       ├── else:   SKIPPED
            │       └── finally: RUNS
            │
            └── No matching except
                    │
                    ├── except: SKIPPED
                    ├── else:   SKIPPED
                    ├── finally: RUNS
                    └── Exception propagates up the call stack
```

## Resource Management — The Primary Use Case for `finally`

The canonical pattern: acquire a resource in `try`, release it in `finally`.

```python
f = open("data.txt")
try:
    data = f.read()
    process(data)
except OSError as e:
    print(f"IO error: {e}")
finally:
    f.close()   # guaranteed to run even if process() raises
```

This pattern is so common that Python formalised it into the **context manager protocol** (`with` statement — see note [[46. Context manager]]). The `with` statement desugars to exactly this `try/finally` structure.

```python
# This:
with open("data.txt") as f:
    data = f.read()

# Is equivalent to:
f = open("data.txt")
try:
    data = f.read()
finally:
    f.close()
```

Whenever you see a resource that must be released — file handles, database connections, network sockets, locks, GPU memory — `finally` is the mechanism. `with` is the ergonomic wrapper.

## Re-raising Exceptions

Sometimes you want to handle an exception partially and then let it continue propagating.

**Bare `raise` — re-raises the current exception:**

```python
try:
    result = int(user_input)
except ValueError as e:
    log.error(f"Bad input: {e}")   # log it
    raise                           # re-raise unchanged
```

**Raise a different exception — exception chaining:**

```python
try:
    data = json.loads(raw)
except json.JSONDecodeError as e:
    raise ValueError(f"Invalid config format") from e
```

The `from e` attaches the original exception as `__cause__`, preserving the full chain in tracebacks. Without `from e`, Python still chains automatically via `__context__`, but `from` makes it explicit and semantically intentional.

```
ValueError: Invalid config format

The above exception was the direct cause of the following exception:
  ...
json.decoder.JSONDecodeError: ...
```

**Suppress the chain — `from None`:**

```python
try:
    value = d[key]
except KeyError:
    raise ValueError(f"Unknown key: {key}") from None
# Traceback shows only ValueError, not the KeyError
```

## Nested `try` Blocks

`try` blocks nest. Inner handlers get first chance; unhandled exceptions propagate to outer handlers.

```python
try:
    try:
        result = int("abc")
    except ValueError:
        print("inner caught ValueError")
        raise RuntimeError("converted") from None
except RuntimeError as e:
    print(f"outer caught: {e}")

# Output:
# inner caught ValueError
# outer caught: converted
```

## Common Patterns in Practice

### Pattern 1 — Try/Except/Else for Clean Success Path

```python
def load_config(path):
    try:
        f = open(path)
    except FileNotFoundError:
        return default_config()
    else:
        with f:
            return json.load(f)
```

### Pattern 2 — Retry Logic

```python
import time

def fetch_with_retry(url, retries=3, delay=1.0):
    for attempt in range(retries):
        try:
            return requests.get(url, timeout=5)
        except requests.Timeout:
            if attempt == retries - 1:
                raise
            time.sleep(delay)
```

### Pattern 3 — Safe Conversion

```python
def safe_int(value, default=None):
    try:
        return int(value)
    except (ValueError, TypeError):
        return default

safe_int("42")         # 42
safe_int("abc")        # None
safe_int(None, -1)     # -1
```

### Pattern 4 — Transaction-Style Commit/Rollback

```python
def execute_transaction(conn, queries):
    cursor = conn.cursor()
    try:
        for q in queries:
            cursor.execute(q)
    except Exception:
        conn.rollback()
        raise
    else:
        conn.commit()   # only commit if everything succeeded
    finally:
        cursor.close()  # always release
```

This is the four-clause pattern at its most expressive:

- `try` — attempt the work
- `except` — rollback on failure
- `else` — commit on success
- `finally` — always release resources

## What Not to Do

**Swallowing exceptions silently:**

```python
# BAD — you will never know why your program is wrong
try:
    train_model()
except Exception:
    pass
```

**Using exceptions as control flow for predictable cases:**

```python
# BAD — LBYL (Look Before You Leap) is clearer here
try:
    value = d[key]
except KeyError:
    value = 0

# BETTER for this case
value = d.get(key, 0)
```

Python culture is EAFP (Easier to Ask Forgiveness than Permission) — use exceptions for _exceptional_ situations, not as an `if/else` substitute for routine cases. However, EAFP is not a license to ignore exceptions. It means: try the operation, handle failure cleanly.

**Catching too broadly:**

```python
# BAD — catches MemoryError, RecursionError, everything
try:
    complex_operation()
except Exception:
    print("something went wrong")   # useless diagnostic

# BETTER — catch what you can actually handle
try:
    complex_operation()
except (ValueError, KeyError) as e:
    handle_input_error(e)
except OSError as e:
    handle_io_error(e)
```

## Connection to AI, Machine Learning, and Deep Learning

Exception handling is not boilerplate in ML — it is architecture. The difference between a research script and production ML code is largely in how exceptions are handled.

### 1. Training Loop Robustness

```python
for epoch in range(num_epochs):
    for batch_idx, (X, y) in enumerate(dataloader):
        try:
            optimizer.zero_grad()
            outputs = model(X)
            loss = criterion(outputs, y)
            loss.backward()
            optimizer.step()
        except RuntimeError as e:
            if "out of memory" in str(e):
                # OOM — clear cache and skip this batch
                torch.cuda.empty_cache()
                print(f"OOM at batch {batch_idx}, skipping")
                continue
            raise   # re-raise anything else
        else:
            # Only log if no exception
            writer.add_scalar("loss", loss.item(), global_step)
```

`torch.cuda.OutOfMemoryError` (a subclass of `RuntimeError`) is one of the most common exceptions in deep learning. Catching it, clearing GPU memory, and continuing is standard practice.

### 2. Data Loading — Corrupt Samples

```python
class RobustDataset(torch.utils.data.Dataset):
    def __getitem__(self, idx):
        try:
            return self.load_sample(idx)
        except (OSError, PIL.UnidentifiedImageError) as e:
            # Corrupt image — return a neighbouring sample
            print(f"Corrupt sample at {idx}: {e}")
            return self.__getitem__((idx + 1) % len(self))
        finally:
            self.access_log.append(idx)   # always log access
```

### 3. Model Serving — Never Crash on Bad Input

```python
@app.route("/predict", methods=["POST"])
def predict():
    try:
        data = request.json
        tensor = preprocess(data)
    except (KeyError, TypeError) as e:
        return {"error": f"Invalid input: {e}"}, 400
    except ValueError as e:
        return {"error": f"Preprocessing failed: {e}"}, 422

    try:
        with torch.no_grad():
            output = model(tensor)
    except Exception as e:
        log.exception("Inference failed")
        return {"error": "Internal model error"}, 500

    else:
        return {"prediction": output.tolist()}, 200
```

The `else` clause here is exactly right: return the result only if no exception occurred at inference time. The two `try` blocks separate input validation errors (client's fault, 4xx) from inference errors (server's fault, 5xx).

### 4. Checkpoint Saving — `finally` as Guarantee

```python
def train_with_checkpoint(model, config):
    checkpoint_saved = False
    try:
        train(model, config)
        checkpoint_saved = True
    except KeyboardInterrupt:
        print("Training interrupted — saving checkpoint")
    except Exception as e:
        print(f"Training failed: {e}")
        raise
    finally:
        if not checkpoint_saved:
            # Attempt to save even on failure
            try:
                save_checkpoint(model, "emergency_checkpoint.pt")
            except Exception:
                print("Could not save emergency checkpoint")
```

This is a nested `try/finally` inside `finally` — valid and sometimes necessary when cleanup itself can fail.

### 5. NaN/Inf Detection During Training

```python
def safe_loss_step(loss):
    try:
        if not torch.isfinite(loss):
            raise ValueError(f"Non-finite loss: {loss.item()}")
        loss.backward()
    except ValueError as e:
        print(f"Loss explosion detected: {e}")
        # Could trigger learning rate reduction, gradient clipping, etc.
        raise
```

## The `else` Clause — Why It Is Underused and Undervalued

A significant fraction of Python programmers never use `else` in `try` statements. The reason is that the following two patterns appear equivalent:

```python
# Pattern A — no else
try:
    result = compute()
    use(result)
except SomeError:
    handle()

# Pattern B — with else
try:
    result = compute()
except SomeError:
    handle()
else:
    use(result)
```

They are **not** equivalent. In Pattern A, if `use(result)` raises `SomeError`, the `except` clause catches it — silently merging two different failure modes. In Pattern B, only `compute()` is guarded. A `SomeError` from `use(result)` propagates up.

The `else` clause is a precision tool. Use it whenever you want to narrowly scope what the `except` is guarding.

---

## Summary Table

|Clause|When it runs|Typical use|
|---|---|---|
|`try`|Always (it's the attempt)|The code that might fail|
|`except`|Only if a matching exception was raised|Handle the failure|
|`else`|Only if NO exception was raised|Code that belongs after success|
|`finally`|Always, unconditionally|Resource cleanup, logging|

**The four rules:**

1. `except` — catch the most specific exception you can actually handle
2. `else` — use it to narrow the scope of what your `except` guards
3. `finally` — the only place to put cleanup that must always run
4. Never swallow exceptions silently — if you catch it, handle it or re-raise it
