01.Train Validation and Test Sets

01.Train Validation and Test Sets

Apr 24, 202612 min read

“The test set is a one-time voucher. You spend it, you get a number. If you then modify your model, that number is no longer valid — but you won’t get another voucher. Treat it accordingly.”

✦ The Fundamental Problem

You have a dataset D=(xi​,yi​)i=1n​ drawn i.i.d. from some unknown distribution P. You fit a model f^​ on D. You want to know: how well does f^​ generalise to new data from P?

The quantity you care about is the population risk (generalisation error):

R(f^​)=E(x,y)∼P​[ℓ(f^​(x),y)]

You cannot compute this directly — P is unknown. So you estimate it using held-out data.

The core tension: any data you use to make decisions about the model (choose features, tune hyperparameters, select architecture) is data you can no longer use for an unbiased estimate of R(f^​). This forces the three-way split.

✦ Why Two Sets Are Not Enough

Suppose you split your data into only train and test, then iterate: train a model, evaluate on test, adjust, re-evaluate, adjust…

Each time you look at the test error and modify the model in response, the test set leaks information into your modelling decisions. Your model is, in a subtle way, being fitted to the test set. The test error becomes an optimistic estimate of true generalisation performance.

This is not hypothetical. It is the mechanism behind:

  • Researchers reporting inflated numbers by testing dozens of variants and reporting the best
  • Kaggle competitors who overfit to the public leaderboard (which is a de facto validation set)
  • Production models that underperform after deployment because model selection was based on a metric computed on “unseen” data that was, in fact, seen

The fix is to introduce a validation set for all decisions made during development, reserving the test set for a single final evaluation.

✦ The Three Sets — Formal Roles

Partition D into three disjoint sets Dtrain​,Dval​,Dtest​:

D=Dtrain​∪Dval​∪Dtest​,pairwise disjoint

SetUsed ForWho Touches ItHow Often
TrainFitting model parameters θOptimiserEvery iteration
ValidationSelecting hyperparameters; comparing model variants; early stoppingYouRepeatedly
TestFinal, unbiased estimate of R(f^​)YouOnce

The critical discipline: once you look at the test set, development is over. If you use the test error to make even one subsequent decision (tweak a threshold, add a feature, change the architecture), the test estimate is compromised.

At large n, the validation and test sets need to be large enough for statistical reliability of the metric, not large in proportion to total data. A test set of 10,000 points gives a 95% confidence interval of width ≈±2 on accuracy — usually sufficient.

✦ The Bias of the Validation Estimate

When you select the best model from M candidates based on validation performance, the selected model’s validation error is a biased (optimistic) estimate of its true generalisation error.

Formally: let R^val​(f^​m​) be the validation error of model m, and let f^​∗=argminm​R^val​(f^​m​) be the selected model. Then:

\mathbb{E}\left[\hat{R}_{\text{val}}(\hat{f}^_)\right] \leq R(\hat{f}^_)

The validation estimate of the winner is optimistically biased — you selected it partly because of favourable noise in R^val​. The more candidates M you evaluate, the larger this bias.

This is why you need an independent test set: the test error of \hat{f}^_ is an unbiased estimate of R(\hat{f}^_), because no decision was made using it.

The bias scales with M and inversely with ∣Dval​∣. Large validation sets, or cross-validation (see Cross-Validation), mitigate this.

✦ Stratified Splits

For classification, random splitting can produce validation/test sets with a different class distribution than the training set — especially under class imbalance.

Stratified splitting preserves the class proportions across all three splits.

Why it matters: suppose your dataset is 95% class 0 and 5% class 1 (e.g., fraud detection). A random split of 1000 samples might put all 50 class-1 examples in the training set, leaving zero in validation. Your validation metric (accuracy) would be 95% for a model that predicts class 0 always — completely misleading.

Implementation:

Stratification applies equally to regression if the target is heavily skewed — bin the target, stratify on bins.

✦ Data Leakage — The Most Common Failure Mode

Data leakage occurs when information from outside the training set contaminates the model, causing the training/validation error to be unrealistically optimistic and the model to fail in production.

This is not always obvious. Here are the canonical forms:

Type 1: Feature Leakage (Target Leakage)

A feature is computed using the target variable, or using information that would not be available at prediction time.

Example: predicting hospital readmission. You include “number of discharge medications” as a feature. But this number is only finalised after the discharge decision — which itself correlates with readmission risk. In production (when you must predict before discharge), this feature is unavailable.

Example: predicting loan default. You include “account closed” as a feature. Defaulters often close accounts; non-defaulters don’t. The feature is a consequence of the label, not a predictor.

Fix: enforce a strict temporal cutoff. Features must be computed using only information available at prediction time — before the event you’re predicting.

Type 2: Preprocessing Leakage

Preprocessing steps that use statistics of the full dataset (including validation and test) before splitting.

The same principle applies to: imputation (fit on train only), PCA (fit on train only), feature selection (fit on train only), oversampling with SMOTE (apply to train only).

The correct abstraction: a Pipeline in sklearn enforces this discipline automatically by fitting preprocessing only on the training fold during cross-validation.

Type 3: Sample Leakage (Group Leakage)

Multiple samples from the same entity (patient, user, time window) end up in both train and test. The model learns entity-specific patterns that don’t generalise to new entities.

Example: medical imaging with 10 scans per patient. Random split puts 8 scans in train and 2 in test for the same patient. The model overfits to patient-specific anatomy. In production (new patients), it fails.

Fix: split by group (patient, user, document), not by sample.

Type 4: Temporal Leakage

Future information used to predict the past. Standard random splitting of time-series data violates temporal ordering.

Fix: always split time series by time — train on all data before time t0​, validate/test on data after t0​. See Cross-Validation for time-series CV details.

✦ Concrete Workflow — End-to-End

✦ The Test Set as a Statistical Estimator

The test error R^test​ is an unbiased estimator of the true risk R(f^​) — but it has variance. How much can you trust it?

For accuracy on ntest​ i.i.d. samples, the standard error is:

SE=ntest​R^test​(1−R^test​)​​

And the 95% confidence interval (using the normal approximation, valid for ntest​≥30):

R^test​±1.96⋅SE

Worked example: ntest​=1000, test accuracy =92.

SE=10000.92×0.08​​=0.0000736​≈0.0086

\text{95% CI} = [0.92 - 0.017, 0.92 + 0.017] = [0.903, 0.937]

Your “92% accuracy” claim has ±1.7 uncertainty. If your competitor reports 93.5%, you cannot distinguish the models based on test performance alone.

Implication: for reliable model comparison, you need large test sets or statistical tests (McNemar’s test for paired classifiers on the same test set).

✦ Retraining on Train + Val After Selection

A common question: after selecting the best model using validation performance, should you retrain it on Dtrain​∪Dval​ before final evaluation?

Yes, in practice. More data generally improves performance. In deployment, you will train on all available data anyway.

But: the test error of the model retrained on train+val is, in principle, biased — hyperparameters were chosen optimistically on the validation set. In practice, this bias is small when ∣Dtrain​∣ is large relative to ∣Dval​∣.

The cleaner approach is nested cross-validation (see Cross-Validation) which gives an unbiased estimate of the whole model selection + training pipeline, not just the final model.

✦ Connection to AI, Machine Learning, and Deep Learning

The Train/Val/Test Discipline in Practice

In deep learning, the three-way split is not optional — it is the foundation of reproducible research. Every paper that claims a state-of-the-art result on ImageNet, GLUE, or SuperGLUE is reporting test-set performance on a held-out benchmark. The benchmark is the shared “test set” for the community.

Benchmark saturation is what happens when the community collectively overfits to the benchmark: researchers tune architectures and hyperparameters based on public leaderboard scores (which are the test set), the benchmark’s test error becomes an overly optimistic estimate of real-world performance, and a new, harder benchmark must be created. This has happened repeatedly: ImageNet → ObjectNet, GLUE → SuperGLUE → BIG-Bench.

The Holdout Principle in LLM Evaluation

Large language models add a new dimension: training data contamination. If the pretraining corpus contains examples from the test set (e.g., famous math competition problems, standardised exam questions), the “held-out” test set is not actually held out — the model saw it during training.

This is the benchmark contamination problem in LLM research (2023–present). It is the same logical failure as fitting a scaler on the full dataset: the supposed held-out set has leaked into the model.

Validation Loss as a Training Signal

In deep learning, the validation loss drives early stopping: training halts when the validation loss stops improving (or begins to increase), preventing overfitting. The validation set is used at every epoch — it is deeply embedded in the training loop, not separate from it. This makes the distinction between train/val/test not just a one-time data split but a live signal during optimisation.

✦ Summary of Principles

1. The test set is finite and non-renewable. Every time you use it to make a decision, you consume its validity as an unbiased estimator.

2. All preprocessing must be fitted on training data only. Validation and test sets are transformed, not fitted. Use Pipeline to enforce this.

3. Stratify splits for imbalanced classes. Check that class proportions match across all three splits.

4. Use group splits when samples are not i.i.d. Group by patient, user, document, or any entity that could cause leakage.

5. Time-series data must be split by time. Never random-shuffle a time series before splitting.

6. The validation estimate of the selected model is optimistically biased. The test estimate is not — this is why the separation exists.

✦ You Know This When…

  • You can explain, without hand-waving, why using the test set more than once compromises its validity as an estimator
  • You can implement a three-way stratified split from scratch and verify the proportions
  • You can identify all four types of data leakage in a given ML pipeline and explain how to fix each one
  • You can compute the 95% confidence interval on a test accuracy and interpret what it means for model comparison
  • You can explain benchmark saturation in LLM research as an instance of the same principle
  • You can implement early stopping in a deep learning training loop correctly — saving and restoring the best checkpoint, evaluating on test exactly once
