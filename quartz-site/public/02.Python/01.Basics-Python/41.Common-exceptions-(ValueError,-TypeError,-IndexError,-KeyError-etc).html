41. Common Exceptions (ValueError, TypeError, IndexError, KeyError etc.)

“An exception is not an error in the moral sense. It is the runtime asserting a mathematical precondition has been violated. Read it as a proof that your assumptions were wrong.”

The Exception Hierarchy — Read This First

Python exceptions are not a flat list. They form an inheritance tree. Understanding the tree tells you which except clauses catch which exceptions — and why catching Exception is almost always too broad.

BaseException
├── SystemExit              ← raised by sys.exit()
├── KeyboardInterrupt       ← Ctrl+C
├── GeneratorExit           ← generator .close() called
└── Exception               ← everything you normally handle
    ├── ArithmeticError
    │   ├── ZeroDivisionError
    │   ├── OverflowError
    │   └── FloatingPointError
    ├── LookupError         ← the "wrong key/index" superclass
    │   ├── IndexError
    │   └── KeyError
    ├── TypeError
    ├── ValueError
    │   └── UnicodeError
    │       ├── UnicodeDecodeError
    │       └── UnicodeEncodeError
    ├── AttributeError
    ├── NameError
    │   └── UnboundLocalError
    ├── OSError             ← also aliased as IOError, EnvironmentError
    │   ├── FileNotFoundError
    │   ├── PermissionError
    │   └── TimeoutError
    ├── RuntimeError
    │   └── RecursionError
    ├── StopIteration
    ├── MemoryError
    └── NotImplementedError

Critical design rule: except LookupError catches both IndexError and KeyError. except Exception catches almost everything. These are not equivalent choices — catch the most specific exception you can name.

Reading an Exception

Before cataloguing individual exceptions, know how to read a traceback. Every piece of it is information.

Traceback (most recent call last):
  File "train.py", line 47, in load_batch
    x = dataset[idx]
  File "dataset.py", line 23, in __getitem__
    return self.samples[idx]
IndexError: list index out of range

Reading order: bottom up. The last line is the actual error. The stack frames above it, from bottom to top, trace the call path from the site of the exception back to where your code entered. load_batch called __getitem__, which raised IndexError at self.samples[idx]. The bug is in load_batch passing an out-of-range idx.

NameError

Raised when: a name (variable, function) is used before it has been defined in the current scope.

UnboundLocalError — a subtle subcase:

Python determines at compile time whether a name is local or global. If you assign to a name anywhere in a function, it is local for the entire function — even before the assignment.

This is not a runtime check. Python’s bytecode compiler sees the assignment on line 3 and marks x as a local variable for all of f. The print then tries to read an unbound local.

StopIteration

Raised when: next() is called on an exhausted iterator.

StopIteration is the protocol by which Python’s for loop knows when to stop. The loop calls next() internally and catches StopIteration to exit cleanly. You will rarely see it in normal code; when you do, it almost always means you tried to advance an iterator manually beyond its end.

Inside generators — important subtlety:

In Python 3.7+, if StopIteration propagates out of a generator function, it becomes RuntimeError: generator raised StopIteration. This was a deliberate language change (PEP 479). If you are manually raising StopIteration inside a generator to signal completion, use return instead.

FileNotFoundError

Raised when: a file or directory operation is attempted on a path that does not exist.

FileNotFoundError is a subclass of OSError. You can catch either, but catching the specific subclass is clearer intent.

RecursionError

Raised when: the call stack exceeds Python’s recursion limit (default: 1000 frames).

In Python, deep recursion on large inputs is a design smell. For production ML code — traversing deep trees, processing large graphs — convert to explicit stack-based iteration.

MemoryError

Raised when: an allocation fails because there is not enough memory.

In ML, this appears when:

  • Loading a dataset that does not fit in RAM
  • Allocating a full attention matrix for a very long sequence (O(n2) space)
  • Creating an intermediate tensor that is larger than GPU VRAM

MemoryError is unrecoverable in most practical scenarios. The fix is architectural — use data generators, batching, memory-mapped files, or gradient checkpointing.

NotImplementedError

Raised when: an abstract method or intentionally unfinished functionality is called.

This is not an error condition in the conventional sense — it is a design contract. In PyTorch, nn.Module uses exactly this pattern for forward(). In Python 3.4+, you can also use abc.abstractmethod which enforces the contract at instantiation time rather than at call time.

Connection to AI, Machine Learning, and Deep Learning

Exceptions in ML code are not edge cases — they are the primary debugging mechanism. Understanding which exception maps to which failure mode saves hours.

ValueError in ML — shape mismatches

Shape errors in NumPy and PyTorch surface as ValueError. This is the single most common exception you will see when writing neural network code.

IndexError — batch indexing and dataset access

The DataLoader calls __getitem__ with indices from a sampler. If your sampler generates indices without respecting len(dataset), you get IndexError. This is a real failure mode in custom samplers.

AttributeError — the unbuilt model

RuntimeError in PyTorch — the GPU exception family

PyTorch uses RuntimeError for most of its internal errors, including:

RuntimeError: Expected all tensors to be on the same device
RuntimeError: CUDA out of memory
RuntimeError: Expected input batch_size (32) to match target batch_size (64)

These are not in Python’s standard library, but they follow the same principle: a precondition was violated. Read the message, check the shapes and devices.

Exceptions as a debugging strategy

In a training loop, wrapping the entire loop in a broad except catches everything but tells you nothing. The discipline is:

Catch specifically, log the context, then re-raise. Swallowing exceptions in ML training loops is how bugs become silent convergence failures that waste GPU hours.
