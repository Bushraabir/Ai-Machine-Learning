40. try / except / else / finally

“An exception is not an error in the pejorative sense. It is a signal — a formal notification that the normal flow of execution cannot continue. The question is not whether to handle it, but where, and how precisely.”

The Core Idea

Python’s exception handling is a structured control flow mechanism. When something goes wrong inside a try block, Python unwinds the call stack looking for a matching except clause. If it finds one, execution transfers there. If it doesn’t, the program terminates with a traceback.

The full four-clause structure:

Each clause has a precise, non-overlapping role. The confusion comes from not understanding else and finally. We will fix that.

How Python Raises and Propagates Exceptions

Before handling, understand the mechanism.

When an exception is raised:

  1. Python creates an exception object (an instance of some Exception subclass)
  2. Normal execution stops immediately at that line
  3. Python walks up the call stack frame by frame, looking for a matching except
  4. If found — execution transfers to that handler
  5. If not found — the exception is unhandled; Python prints a traceback and exits

The exception does not stop at c() — it bubbles up through b(), through a(), until a handler is found. This is stack unwinding.

else — The Most Misunderstood Clause

The else clause runs only if the try block completed without raising any exception.

Why else exists — the precise semantic distinction:

The else clause narrows the scope of what the except is guarding. Code in else is not protected by the except above it — if else raises, that exception propagates normally.

This is the correct design — you only want FileNotFoundError to guard the open() call, not everything that follows.

finally — The Guarantee

The finally clause runs unconditionally — whether an exception was raised or not, whether it was caught or not, even if there is a return statement inside try.

Resource Management — The Primary Use Case for finally

The canonical pattern: acquire a resource in try, release it in finally.

This pattern is so common that Python formalised it into the context manager protocol (with statement — see note 46. Context manager). The with statement desugars to exactly this try/finally structure.

Whenever you see a resource that must be released — file handles, database connections, network sockets, locks, GPU memory — finally is the mechanism. with is the ergonomic wrapper.

The else Clause — Why It Is Underused and Undervalued

A significant fraction of Python programmers never use else in try statements. The reason is that the following two patterns appear equivalent:

They are not equivalent. In Pattern A, if use(result) raises SomeError, the except clause catches it — silently merging two different failure modes. In Pattern B, only compute() is guarded. A SomeError from use(result) propagates up.

The else clause is a precision tool. Use it whenever you want to narrowly scope what the except is guarding.

Summary Table

ClauseWhen it runsTypical use
tryAlways (it’s the attempt)The code that might fail
exceptOnly if a matching exception was raisedHandle the failure
elseOnly if NO exception was raisedCode that belongs after success
finallyAlways, unconditionallyResource cleanup, logging

The four rules:

  1. except — catch the most specific exception you can actually handle
  2. else — use it to narrow the scope of what your except guards
  3. finally — the only place to put cleanup that must always run
  4. Never swallow exceptions silently — if you catch it, handle it or re-raise it
