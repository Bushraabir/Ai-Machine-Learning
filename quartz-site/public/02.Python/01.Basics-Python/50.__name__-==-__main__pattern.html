The One-Line Version

This block runs only when the file is executed directly — not when it is imported as a module. Understanding why requires understanding what __name__ is and how Python sets it.

What Is __name__?

__name__ is a dunder attribute that Python sets automatically on every module before executing it. Its value depends on how the module is being run:

How the file is loaded__name__ value
Run directly: python train.py"__main__"
Imported: import train"train"
Imported as: from train import X"train"
Run as package: python -m train"__main__"

There is no magic here. Python simply sets __name__ = "__main__" before executing the entry-point file, and __name__ = "<module_name>" before executing any imported file. The if block is just a standard conditional — it checks which case applies.

Why Define a main() Function?

You could put code directly in the guard:

This works but is worse for four reasons:

1. Scope: Variables defined directly in the if block are module-level globals. Variables inside main() are local — they do not persist in the module namespace and cannot accidentally shadow imports.

2. Testability: You cannot call if __name__ == "__main__": from a test. You can call main() — or better, the subfunctions that main() delegates to.

3. Readability: The function name documents intent. def main() signals “this is the entry point.”

4. Profiling: python -m cProfile -s cumtime train.py profiles cleanly when main() is a real function — you can see main in the call graph.

The discipline is: keep the guard thin. The guard calls main(). main() orchestrates. Individual functions do the real work.

__name__ Is a Module Attribute — Not Special Syntax

There is nothing syntactically special about __name__. It is an ordinary string attribute on the module object:

Every module has it. The if __name__ == "__main__": pattern is just a conditional that exploits the difference Python sets between these two cases.

python -m — Running a Module as a Script

The -m flag tells Python to run a module from sys.path as a script, setting __name__ = "__main__":

python -m module vs python module.py — the key difference is that -m imports the module through the normal import system, so relative imports work correctly. Running a file directly as python script.py does not go through the package system, which breaks relative imports inside packages.

Implication for ML projects: always run your training scripts with python -m src.train rather than python src/train.py. This ensures your package imports resolve correctly.

The __spec__ Check — A Stricter Alternative

In some library code, you need to distinguish between three cases:

  1. Run directly: python script.py
  2. Run as module: python -m script
  3. Imported: import script

Multiprocessing — Where the Guard Is Not Optional

On Windows and macOS (with the spawn start method), the multiprocessing module starts new processes by importing the main module. If there is no guard, every child process re-executes the top-level code — spawning more children, which spawn more children, until the system runs out of resources.

This is not a style issue. On Windows, the incorrect version crashes with a RuntimeError and a message telling you to use the guard. PyTorch’s DataLoader with num_workers > 0 has the same requirement for the same reason.

Training scripts

  • python -m train --lr 0.01 --epochs 200 works from any directory via -m

Pytest and test discovery

Without the guard, import train would immediately start a training run whenever pytest collects the test file. With the guard, only the definitions are loaded — exactly what the test needs.

Hugging Face training scripts

The official Hugging Face example scripts (run_clm.py, run_glue.py, etc.) all use this exact structure: functions defined at module level, main() orchestrates, if __name__ == "__main__": main() at the bottom. They are designed to be both run directly and imported in notebooks or sweep scripts.

torch.multiprocessing and DataLoader

PyTorch’s documentation explicitly states this requirement. The underlying reason is identical to the multiprocessing case above — the spawn start method re-imports the main module in each worker process.

Common Mistakes and Pitfalls

1. Putting imports inside the guard

Imports belong at the top of the file. Other modules that import this file need those names too. Only execution logic belongs inside the guard.

2. Writing the guard without main()

Technically correct but untestable and unreadable. Extract into main() (and sub-functions). Keep the guard to one line.

3. Misspelling the dunder strings

Python will not warn you. The block simply never runs.

4. Expecting the guard to prevent execution in subprocesses on Unix

On Linux with the fork start method (the default), child processes are forked — they do not re-import the main module. The guard is not strictly required for multiprocessing on Linux. But write it anyway: your code should be platform-agnostic, and the guard is free.

The pattern enforces one discipline that scales from a 50-line utility script to a 50,000-line ML framework: define behaviour in functions, trigger behaviour explicitly. Importability is not an afterthought — it is a design constraint. Every .py file you write should be safely importable, and the guard is the mechanism that guarantees it.
