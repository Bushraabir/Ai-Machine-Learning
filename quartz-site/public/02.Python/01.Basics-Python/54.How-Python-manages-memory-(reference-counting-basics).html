54. How Python Manages Memory (Reference Counting Basics)

“Python does not give you manual control over memory — but if you do not understand what it is doing automatically, you will write code that is silently slower, leaks, or behaves in ways that seem like magic.”

The Central Idea

In C or C++, you call malloc to request memory and free to release it. You are the memory manager. In Python, you never call free. Instead, Python tracks how many names (references) point to each object. When that count hits zero, the object is destroyed and its memory is reclaimed automatically. This mechanism is called reference counting.

Everything else in this note is a consequence of that one design decision.

Objects, Not Variables

First, the mental model must be right. Python does not store values inside variables. It stores values in objects, and variables are labels (references) that point to objects.

Memory heap:

    int object (value=300, refcount=2)
         ▲       ▲
         │       │
         x       y

Both x and y point to the same integer object. The refcount is 2 because two names reference it.

    int object (value=300, refcount=1)   ← refcount dropped to 1
         ▲
         │
         y

    str object (value="hello", refcount=1)
         ▲
         │
         x

When y also gets reassigned or goes out of scope, the int object’s refcount drops to 0, and Python immediately deallocates it.

When the refcount hits zero, Python calls the object’s destructor (__del__ if defined), frees the memory back to Python’s internal allocator, and — when the allocator sees fit — returns it to the OS.

Small Integer Caching and String Interning

Python pre-creates objects for integers −5 through 256 and reuses them. This is called the integer cache (or small int cache).

For 100:
    a ──────► int(100)  [cached singleton]
    b ──────► int(100)  [same object]

For 300:
    a ──────► int(300)  [object A]
    b ──────► int(300)  [object B, independent]

This is why you must never use is to compare integers (or strings). Use ==. The is operator tests object identity (same memory address), not equality.

Python also interns short strings that look like identifiers (letters, digits, underscores). String literals in the same compilation unit may be deduplicated.

Rule: never rely on string identity. The interning behaviour is an implementation detail, not a language guarantee.

The Garbage Collector: Handling Cycles

Reference counting has one fundamental weakness: circular references.

    list A  ──────────────────► list B
      ▲                            │
      └────────────────────────────┘

    refcount(A) = 1  (held by b's slot)
    refcount(B) = 1  (held by a's slot)

Now delete both names:

Both objects still have refcount 1 — they reference each other. Neither will ever reach refcount 0. This is a reference cycle, and pure reference counting cannot collect it.

Python solves this with a supplemental cyclic garbage collector (gc module) that runs periodically on top of reference counting. It identifies groups of objects that are only reachable from each other (not from any live root), and collects them.

The GC uses a generational strategy: most objects die young (short-lived temporaries), so it scans “generation 0” (recently allocated) frequently and older generations less often. This reduces overhead.

Generation 0 → collected most often   (new objects)
Generation 1 → collected occasionally  (survived gen 0)
Generation 2 → collected rarely        (long-lived objects)

Objects with __del__ methods were historically exempt from the cyclic GC (since Python couldn’t safely decide destruction order). Since Python 3.4, this is no longer a restriction — __del__ cycles are handled correctly.

__del__: The Finaliser

When a Python object’s refcount drops to 0, Python calls __del__ if it exists, before freeing memory.

__del__ is not a reliable destructor. You cannot count on when it runs (the GC may delay it), and it will not run at all if there is a reference cycle. Never rely on __del__ to release critical resources like file handles or network connections. Use context managers (with statement) instead — they are deterministic.

Memory Arenas, Pools, and Blocks (CPython Internals)

Python does not call malloc for every object. That would be too slow. Instead, CPython has a three-level internal allocator sitting between your Python code and the OS:

Your Python code
        │
        ▼
  Object-specific allocators  (e.g., int freelist, list freelist)
        │
        ▼
  PyMalloc — Python's private heap
  ┌──────────────────────────────────────────────────────┐
  │  Arena (256 KB)                                      │
  │  ┌──────────────────────────────────────────────┐   │
  │  │  Pool (4 KB)  — fixed size class (e.g., 32B) │   │
  │  │  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐        │   │
  │  │  │Block │ │Block │ │Block │ │ free │  ...    │   │
  │  │  └──────┘ └──────┘ └──────┘ └──────┘        │   │
  │  └──────────────────────────────────────────────┘   │
  │  ┌────────────────────────────────────────────── ┐  │
  │  │  Pool (4 KB)  — different size class (e.g., 64B) │
  │  └──────────────────────────────────────────────┘   │
  └──────────────────────────────────────────────────────┘
        │
        ▼
  OS (malloc / mmap)
  • Block: smallest unit, holds one object of a given size class
  • Pool: 4 KB page of same-size blocks
  • Arena: 256 KB region of pools

PyMalloc handles allocations up to 512 bytes. Larger objects go directly to the OS malloc. This means Python processes often hold onto memory even after objects are deleted — the arena is returned to the OS only when it is entirely empty, which is rare for long-running processes.

This is why memory_profiler may show your Python process’s RSS holding steady even after a large object is deleted: the memory is free from Python’s perspective but has not been returned to the OS yet.

The ML / NumPy Angle

NumPy Arrays Bypass PyMalloc

NumPy allocates array data buffers directly via malloc (not PyMalloc). The Python object wrapper has a refcount like any Python object, but the large memory block storing the actual numbers is managed by NumPy’s own allocator.

This is why b = a for a large NumPy array is not a 800 MB copy — it is a pointer. And it is why forgetting a reference (leaving b alive in a list somewhere) keeps that 800 MB buffer alive indefinitely.

PyTorch and the Computation Graph

In PyTorch, tensors with requires_grad=True maintain a reference to their entire computation graph (the chain of operations that produced them). This graph holds references to intermediate tensors, which hold references to their data buffers.

Forgetting to call .backward() or forgetting to del the loss in a loop accumulates graph memory across iterations — a common source of GPU OOM errors.

Summary: The Reference Counting Contract

1. Every object has a refcount.
2. Refcount increases when a new name/slot references the object.
3. Refcount decreases when a name is deleted, reassigned, or goes out of scope.
4. When refcount == 0, the object is immediately destroyed.
5. Circular references defeat pure refcounting → supplemental GC handles them.
6. Small integers (−5 to 256) and short identifier-like strings are cached singletons.
7. Never use `is` for value comparison. Use `==`.
8. NumPy and PyTorch have their own buffer management on top of this.
9. Slices and views keep the source buffer alive — use .copy() if you want independence.
10. For critical resources, use context managers, not __del__.
