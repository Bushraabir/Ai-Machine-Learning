The Central Claim

In Python, every value is an object, and every object is either mutable or immutable. This is not a style preference or a performance hint — it is a fundamental property of the object that governs how assignment, function calls, container operations, and memory sharing behave.

Misunderstanding mutability is the source of an entire class of bugs that are silent, hard to reproduce, and devastating in ML pipelines where data flows through many transformations.

What Mutability Means, Precisely

An object is immutable if its value cannot change after it is created. The bits that represent its content are fixed for its lifetime.

An object is mutable if its internal state can be modified in-place — without creating a new object, without changing the object’s identity.

Python’s identity operator is checks identity — whether two names point to the same object in memory, as measured by id():

The list was mutated. Its identity (id) did not change. The object at that address now contains different data.

This is aliasing: two names bound to the same object. With immutable objects, aliasing is harmless — you cannot modify the shared object, so both names always see the same value. With mutable objects, aliasing means any modification through one name is visible through all others.

This is Python’s pass-by-object-reference semantics (covered in depth in 55.Pass-by-object-reference behavior). The function received the same list object — it did not receive a copy.

Tuples — Immutability with a Caveat

A tuple is immutable: you cannot add, remove, or replace its elements. But if a tuple contains a mutable object, that object can still be mutated:

The tuple guarantees that the references it holds do not change. It does not guarantee that the objects those references point to do not change. The tuple at a fixed memory address always contains the same two references — but the list at the other end of the first reference can be arbitrarily modified.

This distinction matters for hashing: tuples are hashable (usable as dict keys) only if all their contained objects are also hashable:

Immutability and Hashability

Only immutable objects can be used as dictionary keys or set members. The invariant: if an object’s value could change, its hash could change, which would break the hash table’s ability to find it.

Custom class instances are hashable by default (using id() as the hash). If you override __eq__, you must also override __hash__ — or Python sets __hash__ = None, making your object unhashable. This is the correctness invariant: equal objects must have equal hashes.

  • lst += [4] mutates the original list (visible to all aliases)
  • lst = lst + [4] creates a new list (aliases still see the original)

Mutable Default Arguments — The Classic Trap

This is one of the most notorious Python gotchas, rooted entirely in mutability:

The default value [] is a mutable object created once when the def statement executes. It persists as an attribute of the function object (append_to.__defaults__) and is shared across all calls that use the default. Every call that does not pass lst mutates the same list.

Visualisation — Object Model

Immutable (int, str, tuple, ...):

  name ──► [ object | value: fixed ]
              id: 0x7f1a

  rebinding:
  name ──► [ object | value: fixed ]   (new object, new id)
              id: 0x7f2b

  the old object at 0x7f1a is unchanged


Mutable (list, dict, set, ndarray, ...):

  name_a ──┐
            ├──► [ object | state: changeable ]
  name_b ──┘       id: 0x7f1a

  mutation:
  name_a ──┐
            ├──► [ object | state: CHANGED ]
  name_b ──┘       id: 0x7f1a  (same address — same object)

  name_a and name_b both see the change

Connection to AI / Machine Learning / Deep Learning

Mutability is not an abstract Python concern in ML — it is the mechanism behind how tensors work, why gradient computation is correct, and how data pipelines can silently corrupt themselves.

NumPy — Views vs. Copies

NumPy arrays are mutable. More critically, many NumPy operations return views — objects that share the underlying memory buffer with the original array:

Slicing a NumPy array returns a view. Fancy indexing (boolean mask, integer array) returns a copy. This asymmetry is the source of countless ML bugs:

In a preprocessing pipeline, if you slice a batch and then normalise the slice in-place, you normalise the original data too. This corrupts your dataset silently.

Fix: either pass data[:32].copy() or use batch = batch - batch.mean() (rebinding, creates a new array).

PyTorch — In-Place Operations and Autograd

PyTorch tensors are mutable, and in-place operations are marked with a trailing underscore by convention:

Critical: in-place operations on tensors that are part of the computation graph will raise a RuntimeError or silently corrupt gradients:

PyTorch tracks the computation graph by recording operations. An in-place mutation changes the value that an earlier node in the graph depended on — making the stored value wrong for backward pass computation. PyTorch detects this and raises an error for leaf tensors, but not always for intermediate tensors, where silent gradient corruption is possible.

The rule: never mutate tensors in-place if they require gradients or if they are inputs to a computation you will differentiate through. Use out-of-place operations in forward() and reserve in-place for operations where you are certain no gradient flows through the mutated tensor (e.g., weight initialisation, zeroing gradients).

PyTorch — Shared Memory in DataLoader

When num_workers > 0, PyTorch’s DataLoader passes tensors between processes using shared memory. Tensors from the same batch may share an underlying storage buffer. If your collate_fn or dataset’s __getitem__ mutates the tensor in-place:

The mutation may be visible in the worker process’s memory and cause corrupted batches in subsequent iterations. Use out-of-place operations in data loading code.

Immutable Configs — Protecting Hyperparameters

Experiment configs should be immutable after construction. If training code can mutate the config object, you cannot trust the config file to accurately record what a run actually used.

Caching with Immutable Keys — functools.lru_cache

lru_cache requires hashable arguments. NumPy arrays are mutable and unhashable — you cannot cache on them directly. The pattern: convert to tuples or use the relevant immutable parameters as keys.

Summary

ConceptRule
Mutable objectslist, dict, set, ndarray, class instances — modified in place
Immutable objectsint, float, str, tuple, frozenset, bytes — never modified
AliasingTwo names → same mutable object → mutation visible through both
RebindingName points to a new object — other names are unaffected
+= on mutablesCalls __iadd__ → mutates in place → same id
+= on immutablesCreates new object → rebinds name → new id

TuplesReferences fixed; contained mutables can still change
NumPy slicesViews by default — use .copy() to guarantee isolation

The governing principle: names are labels, not containers. Assignment always binds a label to an object. Whether that object can change is a property of the object, not the label. Understanding this — deeply, not superficially — is what separates programmers who debug mutability bugs in ten minutes from those who spend three days on them.
