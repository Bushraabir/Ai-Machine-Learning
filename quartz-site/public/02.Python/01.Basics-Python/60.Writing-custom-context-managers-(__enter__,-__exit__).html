60. Writing Custom Context Managers (__enter__, __exit__)

What Is a Context Manager?

A context manager is an object that defines what happens when entering and exiting a block of code introduced by the with statement. It guarantees that setup and teardown logic run correctly — even if an exception occurs inside the block.

open() returns a context manager. You can write your own for any resource or pattern that requires matched setup and teardown.

The with Statement — What Actually Happens

Python executes this in four steps:

  1. Evaluate expression to get the context manager object
  2. Call __enter__() on it — the return value is bound to name
  3. Execute body
  4. Call __exit__() on it — always, whether body succeeded or raised

The finally guarantees __exit__ runs no matter what. That is the entire value proposition.

The Two Methods

__enter__(self)

Called at the start of the with block. Returns the value that gets bound to the as target.

  • If you have nothing useful to return, return self or None
  • The as clause is optional — if omitted, the return value is discarded

__exit__(self, exc_type, exc_val, exc_tb)

Called at the end of the with block. Receives three arguments describing any exception that occurred.

ParameterWhat it contains
exc_typeThe exception class, e.g. ValueError
exc_valThe exception instance
exc_tbThe traceback object

If no exception occurred, all three are None.

Return value controls exception propagation:

  • Return True — exception is suppressed, execution continues after the with block
  • Return False or None — exception propagates normally

The contextlib.contextmanager Decorator

The class-based approach requires two methods and an __init__. For simpler cases, contextlib.contextmanager lets you write a context manager as a generator function with a single yield.

The try/finally around yield is what guarantees teardown runs even on exception. Without it, an exception in the with body would skip the cleanup code.

Class-Based vs contextmanager Decorator

ConsiderationClass-based@contextmanager
Lines of codeMore verboseConcise
State between enter/exitInstance attributesLocal variables around yield
Exception handlingFull control in __exit__try/except/finally around yield
ReusabilitySubclassableNot subclassable
Best forComplex resources, reusable objectsSimple patterns, one-off managers

Both approaches are correct. Use the decorator for simple cases. Use the class when you need to store state, subclass, or provide methods on the context manager object itself.
