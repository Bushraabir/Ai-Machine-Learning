58. Writing and Applying Decorators (@decorator)

“A decorator is not syntax sugar for a clever trick. It is the formal mechanism by which Python lets you separate what a function does from how it is instrumented, wrapped, or transformed — without touching the function’s source code.”

Part V — Stacking Decorators

Multiple decorators stack bottom-up. The decorator closest to def is applied first.

Application order (inside-out):
    C(func)       → func_c
    B(func_c)     → func_bc
    A(func_bc)    → func_abc   ← what the name 'func' now points to

Call order (outside-in):
    func_abc called → A's wrapper runs
                      → B's wrapper runs
                        → C's wrapper runs
                          → original func runs
                        → C's wrapper continues
                      → B's wrapper continues
                    → A's wrapper continues

The order matters when decorators interact. Putting @timer outside @log_calls would time the logging overhead too.

Part VI — Class-Based Decorators

A class can be a decorator if it implements __call__. This is useful when the decorator needs to maintain richer state than a closure easily allows.

The class-based form shines when you need methods to manipulate the decorator’s state, or when you want to expose that state as attributes.

Part VII — The ML and Deep Learning Connection

PyTorch @torch.no_grad() — A Decorator in Production

torch.no_grad() is a context manager and a decorator. When used as @torch.no_grad(), it wraps the function so that no gradient tape is built during its execution — saving memory and compute during evaluation loops. The implementation is exactly the class-based decorator pattern above.

Skeleton Reference

Common Mistakes — Checklist

□ Forgot *args, **kwargs in wrapper     → breaks on any non-zero-arg function
□ Forgot functools.wraps                → __name__, __doc__ are wrong; frameworks break
□ Forgot to return result               → decorated function always returns None
□ Forgot the extra layer for arguments  → @decorator(n) raises TypeError
□ Stacked decorators in wrong order     → outer decorator runs outermost at call time
□ Mutable state in closure (not cell)   → shared across all calls unexpectedly
□ Used func() instead of func(*args)    → silently drops all arguments

Summary

@decorator is syntactic sugar for: func = decorator(func)

The skeleton is always:
    outer function  → receives configuration (optional layer)
    decorator       → receives func, returns wrapper
    wrapper         → the new function; closes over func

functools.wraps copies __name__, __doc__, __module__ from func to wrapper.
It is mandatory. Without it, decorated functions lose their identity.

*args, **kwargs in wrapper makes the decorator signature-agnostic.
Without it, the decorator breaks on any function it wasn't written for.

Stacking: @A @B @C applies C first, then B, then A.
Call order is the reverse: A's wrapper runs first.

Class-based decorators use __call__ instead of a closure.
Prefer them when the decorator needs persistent state with rich access.

In ML: @torch.no_grad(), @property, @staticmethod, @classmethod are
all decorators. The mechanism is identical to anything you write yourself.
