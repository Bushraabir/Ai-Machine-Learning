The Core Idea

A module is any .py file. The moment you save a file called utils.py, it is a module. Any other Python file in the same directory can do import utils and access everything defined inside it.

That is the whole mechanism. What takes thought is not the syntax — it is the design: how to divide your code across files so that each module has a clear responsibility, a clean public interface, and no hidden dependencies that make it impossible to reuse or test in isolation.

This note covers both the mechanics and the design discipline.

The leading underscore on _TOLERANCE is a convention — it signals to readers (and to import *) that this name is an implementation detail, not part of the public interface. Python does not enforce it; discipline does.

Controlling the Public Interface with __all__

__all__ is a list of strings that explicitly declares what your module exports. It has two effects:

  1. from geometry import * only imports names in __all__
  2. It serves as machine-readable documentation of your public API

When to define __all__: whenever your module is intended to be used by others — which means any module in an ML project that other files import. It forces you to think about what is public and prevents accidental exposure of internals.

Module-Level Code — What Runs at Import Time

Every statement at the top level of a module runs when it is imported. This is both powerful and dangerous:

The rule: module-level code should only define things — functions, classes, constants. It should not do things — load files, make network requests, print output, or modify global state. Side effects belong inside functions that are called explicitly.

The one canonical exception is the if __name__ == "__main__": guard (see [[50.name == main pattern]]).

Private vs. Public — The Convention System

Python has no access modifiers (private, protected). It has conventions:

Name patternMeaningEffect on import *
namePublic — part of the interfaceExported
_nameInternal — implementation detailNot exported
__nameName-mangled — avoid accidental override in subclassesNot exported
__name__Dunder — Python’s own special protocol namesNot exported

When you call from metrics import *, only accuracy and EPSILON come through (assuming no __all__ — underscore names are excluded). With import metrics, everything is accessible as metrics._correct, but the underscore is a social contract: “I might rename or remove this without warning.”

Module Design Principles

These are not style preferences. They are engineering principles that determine whether your code survives contact with a real project.

1. Single responsibility. Each module should have one clear reason to exist. metrics.py computes metrics. data.py loads data. model.py defines the model architecture. If you cannot state a module’s purpose in one sentence, it is doing too much.

2. Depend inward, not outward. Low-level utility modules (utils.py, metrics.py) should not import high-level modules (trainer.py, experiment.py). The dependency graph should be a DAG, not a cycle. If you find yourself needing a circular import, the design is wrong.

3. No side effects at import time. Module-level code defines, does not do. Loading data, initialising hardware, printing, sleeping — all of this goes inside functions.

4. Explicit public interface. Define __all__. Use _ prefixes for internals. A module with no explicit interface is one where every internal detail becomes a dependency others rely on, making refactoring impossible.

5. Keep modules importable in isolation. If importing model.py requires a GPU, a specific file to exist, and a database connection, you cannot test it, you cannot import it in a notebook, and you cannot use it anywhere that context is absent. Guard hardware and I/O behind functions.

    metrics.__name__      → 'metrics'
    metrics.accuracy      → <function accuracy>

    metrics.EPSILON       → 1e-8

Connection to AI / Machine Learning / Deep Learning

Every ML project is a collection of modules

A mature ML codebase splits naturally into modules by responsibility. Here is the canonical layout:

project/
├── data.py          # Dataset classes, data loading, transforms
├── model.py         # Network architecture definitions
├── train.py         # Training loop, optimiser step, gradient clipping
├── evaluate.py      # Metric computation, validation loop
├── utils.py         # Logging, checkpointing, reproducibility helpers
└── config.py        # Hyperparameters and paths as named constants

Each of these is a module you write. The discipline of 49 is what makes them composable — you can run evaluate.py standalone, import model.py into a notebook, and test data.py without a GPU.

Common Mistakes and Pitfalls

1. Putting everything in one file

A single main.py with 800 lines containing model definition, data loading, training loop, evaluation, and visualisation is not a program — it is a script that cannot be reused, tested, or read. Split by responsibility from the start.

2. Making modules that import each other

model.py  → imports from  train.py
train.py  → imports from  model.py   ← circular import

The fix is always the same: extract the shared dependency into a third module that neither imports from the other two. Usually this is utils.py or config.py.

3. Module-level code with side effects

Anyone who imports bad_data to use one of its functions pays the full cost of loading the CSV, even if they never use df. Wrap it in a function.

4. Importing everything into one namespace

Now bad_utils has a namespace full of names from four other modules, none of them clearly attributed. Use explicit imports and explicit names.

5. Forgetting that imported names are module attributes

This is the mutable-vs-immutable import distinction. If VALUE were a list, a.VALUE.append(...) would be visible to b.py (same object). But reassigning a.VALUE = 99 is not visible to b.py’s local binding VALUE. Import the module (not the name) when you need to see mutations.

Summary

ConceptWhat to remember
A module isAny .py file
Module namespaceEvery top-level name: functions, classes, constants, imports
__all__Explicit public contract; controls import *
_name conventionInternal — implementation detail, may change
Module-level codeShould only define, never do
Single responsibilityOne module, one clear purpose
No circular importsFix by restructuring, not by working around
Module docstringFirst string literal; becomes __doc__

The central discipline: a module is a unit of encapsulation. Its public interface (what it exports) should be stable and intentional. Its internals (prefixed with _) should be free to change. Every file you write in an ML project that another file imports is a module, and it deserves the design care this implies.
