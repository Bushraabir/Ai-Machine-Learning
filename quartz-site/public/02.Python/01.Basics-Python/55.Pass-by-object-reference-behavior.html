55. Pass-by-Object-Reference Behavior

“Python is neither pass-by-value nor pass-by-reference. It is pass-by-object-reference — and the confusion between these three things is the source of an entire class of bugs that vanish the moment the model is clear.”

The Question That Causes All the Confusion

Both functions receive one argument. Neither returns anything. Yet one modifies the caller’s variable and the other does not. Understanding exactly why requires understanding what Python actually passes.

The Three Models — and Which One Python Uses

Pass-by-Value (C, Java primitives)

A copy of the value is made. The function works on the copy. The caller’s variable is never touched.

caller:  a = 5
         ┌───┐
         │ 5 │  ← copy made
         └───┘
              │
              ▼
function: x = 5  (independent copy)
          x = 10  (only local copy changes)

caller:  a = 5  (unchanged)

Pass-by-Reference (C++ references, ref in C#)

The function receives the memory address of the caller’s variable. Reassigning the parameter changes the caller’s variable.

caller:  a = 5
         │
         ▼ (address passed)
function: x  →  same storage as a
          x = 10  →  a is now 10

caller:  a = 10  (changed by reassignment inside function)

Python does not work this way. Reassigning a parameter never changes the caller’s variable.

Pass-by-Object-Reference (Python)

Python passes a reference to the object — not a copy of the value, and not the address of the caller’s variable. The parameter becomes a new label pointing to the same object.

caller:    a ──────────────► [10, 20]
                                ▲
function:  lst ─────────────────┘   (same object, new label)

The function can mutate the object through its label. But if it rebinds the label to a new object, the caller’s label is unaffected.

The Core Distinction: Mutation vs. Rebinding

This is the entire note in two lines:

  • Mutating the object → caller sees the change (same object in memory)
  • Rebinding the parameter → caller does not see the change (parameter now points elsewhere)

Draw it:

Before mutate():
    original ──────────────► [10, 20]
                                 ▲
    lst (inside mutate) ─────────┘

After lst.append(99):
    original ──────────────► [10, 20, 99]   ← same object, now modified
    lst ───────────────────────────────────► same

Inside rebind(), after lst = [1, 2, 3]:
    original ──────────────► [10, 20, 99]   ← unchanged
    lst ───────────────────► [1, 2, 3]      ← new object, local only

The caller’s label original is never touched by rebinding. It still points where it always pointed.

Immutable Objects: Why “Pass-by-Value” Feels True

For immutable types (int, float, str, tuple, frozenset), mutation is impossible by definition. Every operation that appears to modify the value actually produces a new object.

Before:
    x ──────────────► int(10)  [refcount includes x and n]
    n ──────────────────────────────────► same int(10)

After n = n + 1:
    x ──────────────► int(10)  [untouched]
    n ──────────────────────────────────► int(11)  [new object]

It looks like pass-by-value, but it is not. The mechanism is identical to the mutable case — the parameter is a reference to the same object. It is just that you cannot mutate the object, so every “modification” is really a rebind, which the caller never sees.

Mutable Objects: The Full Taxonomy of Operations

For a mutable object, every operation falls into one of two categories:

In-Place Mutations (caller sees these)

Rebinding Operations (caller does NOT see these)

The + vs += distinction is subtle and important:

lst += x on a list calls list.__iadd__, which mutates in place and returns self. The label lst is rebound to the same object it already pointed to. The caller sees the mutation.

lst = lst + x creates a brand-new list object. lst is rebound to the new one. The caller’s label never moves.

For immutable types like str and tuple, += also creates a new object (because mutation is impossible), so it behaves like = in this context.

The Mutable Default Argument: Classic Python Trap

Why? The default [] is a single list object created when the function is defined, not when it is called. Every call that uses the default is mutating the same object.

Function definition time:
    append_to.__defaults__ = ([],)   ← one list object, lives forever

Call 1: target ──────────────► []   → append(1) → [1]
Call 2: target ──────────────► [1]  → append(2) → [1, 2]  (same object)
Call 3: target ──────────────► [1, 2] → ...

The canonical fix: use None as the sentinel, create a fresh list inside the function body.

This pattern applies to all mutable defaults: dict, set, custom objects.

The ML Connection: Gradients, Optimisers, and In-Place Ops

In-Place Operations in PyTorch — When They Break the Graph

This is exactly the mutation vs. rebinding distinction, applied to automatic differentiation. The computation graph needs to see an unmodified version of each tensor to compute gradients correctly. In-place mutation destroys that history.

Optimiser Step is In-Place Mutation

optimizer.step() is an in-place mutation of all parameter tensors. It does not return new parameter tensors. This is intentional — parameters are tracked by the model and the optimiser by reference. Rebinding would sever those connections.

NumPy: In-Place Operations for Memory Efficiency

-= on a NumPy array calls __isub__, which modifies the existing data buffer. No new array is allocated. For large arrays in preprocessing pipelines this is the difference between fitting in RAM and not.

id() as a Diagnostic Tool

id(obj) returns the memory address of the object in CPython. Use it to verify whether two names point to the same object.

before call, id(lst) = 140234567890
  inside f, id(x) = 140234567890        ← same object
  inside f after append, id(x) = 140234567890  ← still same object
after call, id(lst) = 140234567890      ← unchanged address
[1, 2, 3, 99]

The address never changes. The object was mutated through two different labels pointing to the same address.

before call, id(lst) = 140234567890
  inside g, id(x) = 140234567890        ← same object at entry
  inside g after rebind, id(x) = 140234599999  ← NEW object
after call, id(lst) = 140234567890      ← caller unchanged
[1, 2, 3]

Summary

Python passes a reference to the object — not the value, not the address of the variable.

The parameter is a new label pointing to the same object as the caller's argument.

MUTATION of the object through the parameter  →  caller sees the change.
REBINDING the parameter to a new object       →  caller is completely unaffected.

Immutable types (int, str, tuple) cannot be mutated.
Every apparent "modification" creates a new object and rebinds the local label.
This is why immutables appear to behave like pass-by-value — but the mechanism is identical.

The mutable default argument trap is this mechanism applied to function definition time.
Use None as sentinel; create fresh mutable objects inside the function body.

lst += x  on a list  →  in-place mutation (caller sees it)
lst = lst + x        →  new object, rebind (caller does not)

In ML code: PyTorch in-place ops break autograd; NumPy in-place ops save memory.
Know which operations mutate and which rebind — the distinction is load-bearing.
