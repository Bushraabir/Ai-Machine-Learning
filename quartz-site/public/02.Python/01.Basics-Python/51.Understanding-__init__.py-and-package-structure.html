The Core Distinction: Module vs. Package

A module is a single .py file. A package is a directory that Python treats as a namespace — a container for modules and sub-packages.

The mechanism that makes a directory a package is the presence of __init__.py. Without it, Python (in most contexts) treats the directory as just a directory, not an importable namespace.

my_project/
├── utils.py          ← module   (importable as 'utils')
└── models/
    ├── __init__.py   ← this file makes 'models' a package
    ├── resnet.py     ← module inside the package
    └── vgg.py        ← module inside the package

Remove __init__.py from models/ and import models raises ModuleNotFoundError in Python 3 (unless namespace packages are in play — see below).

What __init__.py Actually Is

__init__.py is the initialisation code for the package. When Python imports a package, it executes __init__.py in that package’s namespace. Everything defined or imported inside __init__.py becomes an attribute of the package object.

__init__.py can be — and often is — completely empty. An empty __init__.py still makes the directory a package, but defines no attributes on the package object.

The __init__.py as a Public API Controller

The most important use of __init__.py is controlling what the package exposes. A package’s internal file layout is an implementation detail. The public API is what you define in __init__.py.

Consider this layout:

models/
├── __init__.py
├── _resnet.py      ← internal implementation
├── _vgg.py         ← internal implementation
└── _transformer.py ← internal implementation

__all__ — Controlling import *

__all__ is a list of strings that defines what from package import * exports. It also serves as explicit documentation of the public API:

Without __all__, import * exports everything not prefixed with _. With __all__, it exports exactly the listed names — nothing more. Even names imported into __init__.py that are not in __all__ are excluded from wildcard imports.

__all__ does not prevent direct access — from models import ResNet50 works regardless. It only governs import * and signals intent to readers and static analysis tools.

A Realistic ML Project Layout

This is the structure you should build and recognise in every serious ML project:

project/
│
├── src/                          ← source root (or project name)
│   ├── __init__.py
│   │
│   ├── data/                     ← data loading and preprocessing
│   │   ├── __init__.py
│   │   ├── dataset.py
│   │   ├── transforms.py
│   │   └── samplers.py
│   │
│   ├── models/                   ← model definitions
│   │   ├── __init__.py
│   │   ├── backbone.py
│   │   ├── heads.py
│   │   └── losses.py
│   │
│   ├── training/                 ← training logic
│   │   ├── __init__.py
│   │   ├── trainer.py
│   │   ├── optimizer.py
│   │   └── scheduler.py
│   │
│   └── utils/                    ← shared utilities
│       ├── __init__.py
│       ├── metrics.py
│       ├── logging.py
│       └── checkpointing.py
│
├── configs/                      ← configuration files (YAML/JSON)
│   ├── resnet50_baseline.yaml
│   └── transformer_large.yaml
│
├── tests/                        ← test suite
│   ├── __init__.py
│   ├── test_data.py
│   └── test_models.py
│
├── scripts/                      ← entry points
│   ├── train.py
│   ├── evaluate.py
│   └── export.py
│
├── notebooks/                    ← exploration (not imported)
│   └── eda.ipynb
│
├── setup.py  (or pyproject.toml) ← makes the package installable
└── README.md

Each __init__.py controls the public API of its sub-package. scripts/ contains entry points with if __name__ == "__main__" guards. notebooks/ is never imported. tests/ mirrors src/.

Absolute vs. Relative Imports Inside a Package

Once code lives inside a package, there are two ways to import between files within that package.

Absolute imports (preferred)

Absolute imports work from any context — scripts, tests, notebooks, the REPL. They are always unambiguous. PEP 8 and most style guides prefer them.

Relative imports

The dots encode directory traversal:

  • . → current package (src/training/)
  • .. → parent package (src/)
  • ... → grandparent package

Relative imports only work inside packages. If you run python src/training/trainer.py directly (not via -m), Python does not know the file is part of a package and raises ImportError: attempted relative import with no known parent package.

Namespace Packages — __init__.py-Free Packages (Python 3.3+)

PEP 420 introduced implicit namespace packages: directories without __init__.py can still be imported as packages in Python 3.3+. Python searches all entries on sys.path and assembles a namespace package from all matching directories.

site-packages/
├── mylib/          ← no __init__.py
│   ├── core.py
│   └── utils.py

When namespace packages are useful: splitting a single logical package across multiple directories or repositories (e.g., plugin systems, namespace packages like google.cloud, google.auth that ship separately but share the google namespace).

When to use explicit __init__.py: almost always. For application code, libraries, and ML projects, the explicit file gives you API control, initialisation logic, and unambiguous package identity. Use namespace packages only when you specifically need the split-directory behaviour.

The practical rule: if you intend to import it, give it an __init__.py.

The __init__.py Execution Order

When Python imports a nested package, it executes __init__.py files from the outermost level inward:

from src.models.resnet import ResNet50

Execution order:

  1. src/__init__.py
  2. src/models/__init__.py
  3. src/models/resnet.py — then binds ResNet50 in the caller’s namespace

Each __init__.py runs exactly once (cached in sys.modules as "src" and "src.models"). Subsequent imports of the same package skip re-execution.

Connection to AI / Machine Learning / Deep Learning

How PyTorch is structured — reading framework source

PyTorch’s package structure is the canonical example:

torch/
├── __init__.py          ← re-exports Tensor, nn, optim, etc.
├── nn/
│   ├── __init__.py      ← re-exports Module, Linear, Conv2d, etc.
│   ├── modules/
│   │   ├── __init__.py  ← re-exports all layer classes
│   │   ├── linear.py    ← defines Linear
│   │   ├── conv.py      ← defines Conv1d, Conv2d, Conv3d
│   │   └── ...
│   └── functional.py    ← stateless functions (relu, softmax, etc.)
├── optim/
│   ├── __init__.py      ← re-exports SGD, Adam, etc.
│   ├── sgd.py
│   ├── adam.py
│   └── ...
└── utils/
    └── data/
        ├── __init__.py  ← re-exports Dataset, DataLoader
        ├── dataset.py
        └── dataloader.py

When you write from torch.utils.data import DataLoader, you are not importing from torch/utils/data/__init__.py directly — DataLoader is defined in dataloader.py and re-exported through __init__.py. The __init__.py is the stable public API; the .py files inside are implementation details you can read but should not depend on.

This is why from torch.utils.data.dataloader import DataLoader also works but is considered bad practice — it couples you to the internal layout, which can change across versions.

Hugging Face transformers — the registry pattern via __init__.py

HuggingFace uses __init__.py to implement a lazy loading registry — a sophisticated pattern where the __init__.py defines placeholder objects that only load the real module when accessed:

When you write from transformers import BertModel, the lazy module intercepts the attribute access and only then imports models/bert/modeling_bert.py. This makes import transformers instantaneous even though the library contains hundreds of models.

This is an advanced application of the same principle: __init__.py controls the public API and can interpose arbitrary logic between the caller and the underlying modules.

pytest test discovery and __init__.py

pytest has two modes:

With __init__.py in tests/: pytest treats tests as part of a package. Imports are absolute and must be consistent with the installed package. This is the correct setup when you have a src/ layout with an editable install.

Without __init__.py in tests/: pytest uses its own import mechanism (rootdir insertion). This is simpler for small projects but can cause import conflicts when test files share names across directories.

The rule: if you have src/ with __init__.py, also put __init__.py in tests/ and use editable installs. Consistency throughout.

Common Mistakes and Pitfalls

1. Missing __init__.py and wondering why imports fail

src/
├── models/         ← NO __init__.py
│   └── resnet.py

Fix: add src/models/__init__.py (can be empty).

2. Circular imports through __init__.py

__init__.py imports resnet.py, which imports __init__.py, which is still being initialised. ResNet101 may not exist yet.

Fix: in resnet.py, import from the specific module, not from the package:

3. Doing heavy work in __init__.py

__init__.py runs on every import src.models. If it does slow or stateful work, every test, every import, every subprocess pays that cost. Keep __init__.py to re-exports and minimal initialisation. Move expensive work into functions called explicitly.

4. Relative imports in scripts run directly

Always use python -m for files that use relative imports.

5. Shadowing package names with local files

project/
├── torch.py        ← YOUR file, named after a package
└── train.py

sys.path puts the current directory first. Your torch.py shadows PyTorch. This produces AttributeError: module 'torch' has no attribute 'nn' with no obvious cause. Never name files after packages you import.

Summary

ConceptWhat to remember
__init__.pyMakes a directory a package; its code runs once on first import
Empty __init__.pyValid — marks the directory as a package with no extra attributes
API controlRe-export names in __init__.py to define a stable public interface
__all__Controls import *; documents the public API for tools and readers
Absolute importsAlways unambiguous; preferred for application code
Relative importsPackage-internal shorthand; requires -m execution, breaks in scripts
Namespace packagesNo __init__.py needed in Python 3.3+, but explicit is almost always better
Editable installpip install -e . — the right way to make your package importable everywhere
Execution orderOutermost __init__.py first, inward; all cached in sys.modules

The __init__.py is the boundary surface of your package — the only thing the outside world should need to know about. Define it carefully, keep it thin, and the internal structure of your package becomes freely refactorable without breaking any caller.
