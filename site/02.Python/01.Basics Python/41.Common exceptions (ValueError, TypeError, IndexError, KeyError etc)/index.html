    41. Common Exceptions (ValueError, TypeError, IndexError, KeyError etc.)¶

    "An exception is not an error in the moral sense. It is the runtime asserting a mathematical precondition has been violated. Read it as a proof that your assumptions were wrong."

    The Exception Hierarchy — Read This First¶

    Python exceptions are not a flat list. They form an inheritance tree. Understanding the tree tells you which except clauses catch which exceptions — and why catching Exception is almost always too broad.

    BaseException
├── SystemExit              ← raised by sys.exit()
├── KeyboardInterrupt       ← Ctrl+C
├── GeneratorExit           ← generator .close() called
└── Exception               ← everything you normally handle
    ├── ArithmeticError
    │   ├── ZeroDivisionError
    │   ├── OverflowError
    │   └── FloatingPointError
    ├── LookupError         ← the "wrong key/index" superclass
    │   ├── IndexError
    │   └── KeyError
    ├── TypeError
    ├── ValueError
    │   └── UnicodeError
    │       ├── UnicodeDecodeError
    │       └── UnicodeEncodeError
    ├── AttributeError
    ├── NameError
    │   └── UnboundLocalError
    ├── OSError             ← also aliased as IOError, EnvironmentError
    │   ├── FileNotFoundError
    │   ├── PermissionError
    │   └── TimeoutError
    ├── RuntimeError
    │   └── RecursionError
    ├── StopIteration
    ├── MemoryError
    └── NotImplementedError

    Critical design rule: except LookupError catches both IndexError and KeyError. except Exception catches almost everything. These are not equivalent choices — catch the most specific exception you can name.

    Reading an Exception¶

    Before cataloguing individual exceptions, know how to read a traceback. Every piece of it is information.

    Traceback (most recent call last):
  File "train.py", line 47, in load_batch
    x = dataset[idx]
  File "dataset.py", line 23, in __getitem__
    return self.samples[idx]
IndexError: list index out of range

    Reading order: bottom up. The last line is the actual error. The stack frames above it, from bottom to top, trace the call path from the site of the exception back to where your code entered. load_batch called __getitem__, which raised IndexError at self.samples[idx]. The bug is in load_batch passing an out-of-range idx.

    The Core Exceptions¶

    ValueError¶

    Raised when: an operation receives an argument of the correct type but an invalid value for that type.

    The type is right. The content is wrong.

    int("hello")          # ValueError: invalid literal for int() with base 10: 'hello'
int("3.14")           # ValueError — must do int(float("3.14"))
math.sqrt(-1)         # ValueError: math domain error
[1, 2, 3].index(99)   # ValueError: 99 is not in list
"abc".index("z")      # ValueError: substring not found

import numpy as np
np.array([1, 2, 3]).reshape(2, 2)   # ValueError: cannot reshape array of size 3 into shape (2,2)

    The distinction — ValueError vs TypeError:

    int(3.14)    # int — valid, truncates to 3. The type (float) is acceptable.
int("3.14")  # ValueError — the type (str) is acceptable for int(), but "3.14" is not a valid integer literal
int([1, 2])  # TypeError — the type (list) is not acceptable at all for int()

    Where you will raise it yourself:

    def set_learning_rate(lr):
    if lr <= 0 or lr >= 1:
        raise ValueError(f"Learning rate must be in (0, 1), got {lr}")
    self.lr = lr

    TypeError¶

    Raised when: an operation is applied to an object of the wrong type entirely.

    The operation does not know what to do with that type.

    "hello" + 5           # TypeError: can only concatenate str (not "int") to str
len(42)               # TypeError: object of type 'int' has no len()
1 + "1"               # TypeError: unsupported operand type(s) for +: 'int' and 'str'

def f(a, b): return a + b
f(1, 2, 3)            # TypeError: f() takes 2 positional arguments but 3 were given
f(1)                  # TypeError: f() missing 1 required positional argument: 'b'

None + 1              # TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'

    Forgetting to call a function:

    import math

math.sqrt            # This is the function object, not the result
type(math.sqrt)      # <class 'builtin_function_or_method'>

result = math.sqrt   # result is now the function itself, not a number
result + 1           # TypeError: unsupported operand type(s) for +: 'builtin_function_or_method' and 'int'

# Correct:
result = math.sqrt(4)   # 2.0

    This exact mistake appears when wiring up Keras/PyTorch callbacks — passing relu instead of relu().

    IndexError¶

    Raised when: a sequence (list, tuple, string) is accessed with an index that is outside its valid range.

    a = [10, 20, 30]

a[0]     # 10  — valid
a[2]     # 30  — valid
a[3]     # IndexError: list index out of range
a[-1]    # 30  — valid (negative indexing)
a[-4]    # IndexError: list index out of range

s = "hello"
s[10]    # IndexError: string index out of range

    Off-by-one — the canonical source:

    a = [10, 20, 30]    # length 3, valid indices: 0, 1, 2

for i in range(len(a) + 1):   # BUG: range goes 0, 1, 2, 3
    print(a[i])                # IndexError on i=3

    Empty list — the silent ambush:

    results = []
best = results[0]    # IndexError: list index out of range
# You assumed results was non-empty. It was not.

    Slicing never raises IndexError:

    a = [1, 2, 3]
a[10:20]    # []  — silently returns empty list
a[:100]     # [1, 2, 3]  — clamped to length

    This asymmetry is intentional but trips people up. a[10] raises; a[10:11] returns [].

    KeyError¶

    Raised when: a dictionary is accessed with a key that does not exist.

    d = {"name": "Alice", "age": 30}

d["name"]     # "Alice"  — exists
d["email"]    # KeyError: 'email'
d[0]          # KeyError: 0  — 0 is not a key here

    Safe alternatives:

    d = {"name": "Alice"}

# .get() — returns None if key absent, or a default
d.get("email")             # None
d.get("email", "unknown")  # "unknown"

# Membership test before access
if "email" in d:
    print(d["email"])

# defaultdict — supplies a default on first access
from collections import defaultdict
counts = defaultdict(int)
counts["unseen_key"]    # 0, not KeyError
counts["unseen_key"] += 1

    KeyError in ML — a common pattern:

    # Vocabulary lookup — the unknown word problem
vocab = {"cat": 0, "dog": 1, "fish": 2}
token = "elephant"

vocab[token]              # KeyError: 'elephant'
vocab.get(token, vocab["<UNK>"])   # correct pattern with unknown token

    AttributeError¶

    Raised when: you access an attribute or call a method that does not exist on an object.

    x = 42
x.append(1)      # AttributeError: 'int' object has no attribute 'append'

import numpy as np
arr = np.array([1, 2, 3])
arr.push(4)      # AttributeError: 'numpy.ndarray' object has no attribute 'push'
                 # (NumPy uses np.append, not .push)

    The None trap — the most common AttributeError in ML code:

    def get_model():
    # forgot to return something
    model = build_model()
    train(model)
    # no return statement

model = get_model()   # model is None
model.predict(X)      # AttributeError: 'NoneType' object has no attribute 'predict'

    Whenever you see AttributeError: 'NoneType' object has no attribute '...', the real question is: why did the variable get assigned None? A missing return in a function is the most common answer.

    Typo in method name:

    "hello".uper()    # AttributeError: 'str' object has no attribute 'uper'
"hello".upper()   # 'HELLO'  — correct

    NameError¶

    Raised when: a name (variable, function) is used before it has been defined in the current scope.

    print(x)    # NameError: name 'x' is not defined

def f():
    return result    # NameError if result not defined in scope

# Common: running cells out of order in Jupyter
model.fit(X, y)   # NameError: name 'model' is not defined
                  # because the cell that defines model hasn't been run yet

    UnboundLocalError — a subtle subcase:

    Python determines at compile time whether a name is local or global. If you assign to a name anywhere in a function, it is local for the entire function — even before the assignment.

    x = 10

def f():
    print(x)   # UnboundLocalError: local variable 'x' referenced before assignment
    x = 20     # this assignment makes x local for the whole function

f()

    This is not a runtime check. Python's bytecode compiler sees the assignment on line 3 and marks x as a local variable for all of f. The print then tries to read an unbound local.

    ZeroDivisionError¶

    Raised when: division or modulo by zero.

    10 / 0      # ZeroDivisionError: division by zero
10 // 0     # ZeroDivisionError: integer division or modulo by zero
10 % 0      # ZeroDivisionError: integer division or modulo by zero

    Float division by zero does not raise in NumPy:

    import numpy as np
np.float64(1.0) / np.float64(0.0)   # inf, with RuntimeWarning
np.float64(0.0) / np.float64(0.0)   # nan, with RuntimeWarning

    This is IEEE 754 behaviour. NumPy follows the standard; Python's built-in / does not. This matters when you are computing log-losses or normalisation factors.

    The divide-by-zero in normalisation:

    def softmax(x):
    exp_x = np.exp(x - x.max())
    return exp_x / exp_x.sum()    # fine as long as input is not all -inf

def normalize(x):
    norm = np.linalg.norm(x)
    if norm == 0:
        return x                  # or raise, depending on contract
    return x / norm

    StopIteration¶

    Raised when: next() is called on an exhausted iterator.

    it = iter([1, 2, 3])

next(it)    # 1
next(it)    # 2
next(it)    # 3
next(it)    # StopIteration

# Safe pattern — provide a default
next(it, None)   # None, not an exception

    StopIteration is the protocol by which Python's for loop knows when to stop. The loop calls next() internally and catches StopIteration to exit cleanly. You will rarely see it in normal code; when you do, it almost always means you tried to advance an iterator manually beyond its end.

    Inside generators — important subtlety:

    In Python 3.7+, if StopIteration propagates out of a generator function, it becomes RuntimeError: generator raised StopIteration. This was a deliberate language change (PEP 479). If you are manually raising StopIteration inside a generator to signal completion, use return instead.

    FileNotFoundError¶

    Raised when: a file or directory operation is attempted on a path that does not exist.

    open("nonexistent.txt")    # FileNotFoundError: [Errno 2] No such file or directory: 'nonexistent.txt'

    FileNotFoundError is a subclass of OSError. You can catch either, but catching the specific subclass is clearer intent.

    try:
    with open("config.json") as f:
        config = json.load(f)
except FileNotFoundError:
    config = {}    # use defaults if config file is absent

    RecursionError¶

    Raised when: the call stack exceeds Python's recursion limit (default: 1000 frames).

    def f():
    return f()

f()    # RecursionError: maximum recursion depth exceeded

    The missing base case:

    # BUG — base case never triggers for negative n
def factorial(n):
    if n == 0:
        return 1
    return n * factorial(n - 1)

factorial(-1)    # RecursionError — recurse forever toward -∞

    Checking and adjusting the limit:

    import sys
sys.getrecursionlimit()       # 1000
sys.setrecursionlimit(5000)   # increase — use with caution

    In Python, deep recursion on large inputs is a design smell. For production ML code — traversing deep trees, processing large graphs — convert to explicit stack-based iteration.

    MemoryError¶

    Raised when: an allocation fails because there is not enough memory.

    x = [0] * (10 ** 12)    # MemoryError — allocating 8 TB is not going to work

    In ML, this appears when:

    • Loading a dataset that does not fit in RAM
    • Allocating a full attention matrix for a very long sequence (\(O(n^2)\) space)
    • Creating an intermediate tensor that is larger than GPU VRAM
    # Bad: materialises the entire N×N attention matrix in memory
scores = Q @ K.T          # shape (N, N)

# Better for long sequences: chunked or sparse attention

    MemoryError is unrecoverable in most practical scenarios. The fix is architectural — use data generators, batching, memory-mapped files, or gradient checkpointing.

    NotImplementedError¶

    Raised when: an abstract method or intentionally unfinished functionality is called.

    class BaseModel:
    def forward(self, x):
        raise NotImplementedError("Subclasses must implement forward()")

class LinearModel(BaseModel):
    pass

m = LinearModel()
m.forward(x)    # NotImplementedError: Subclasses must implement forward()

    This is not an error condition in the conventional sense — it is a design contract. In PyTorch, nn.Module uses exactly this pattern for forward(). In Python 3.4+, you can also use abc.abstractmethod which enforces the contract at instantiation time rather than at call time.

    from abc import ABC, abstractmethod

class BaseModel(ABC):
    @abstractmethod
    def forward(self, x):
        pass

m = BaseModel()    # TypeError: Can't instantiate abstract class — caught earlier

    Exception Relationships: A Decision Table¶

    When you catch an exception, which class do you name?

    What went wrong Exception to catch
    Wrong value for a valid type ValueError
    Wrong type entirely TypeError
    List/string index out of range IndexError
    Dict key does not exist KeyError
    Either index or key problem LookupError
    Attribute or method missing AttributeError
    Name not defined in scope NameError
    Division by zero ZeroDivisionError
    Iterator exhausted StopIteration
    File not found FileNotFoundError
    Any OS/file-system error OSError
    Recursion too deep RecursionError
    Out of memory MemoryError
    Abstract method not implemented NotImplementedError
    Anything (catch-all, use sparingly) Exception

    The Right Way to Catch Multiple Exceptions¶

    # Catch multiple specific exceptions — different handlers
try:
    result = d[key] / count
except KeyError:
    print(f"Key {key!r} not in dict")
except ZeroDivisionError:
    print("count is zero")

# Catch multiple exceptions — same handler
try:
    result = d[key] / count
except (KeyError, ZeroDivisionError) as e:
    print(f"Computation failed: {e}")

# DON'T catch Exception unless you have a very good reason
try:
    ...
except Exception:
    pass    # silently swallowing errors — this hides bugs

    The __class__.__mro__ Trap¶

    Because exceptions inherit, you must order except clauses from most specific to most general. Python checks them in order and takes the first match.

    # WRONG — IndexError will never be reached; LookupError catches it first
try:
    x = lst[10]
except LookupError:
    print("lookup failed")
except IndexError:            # dead code — IndexError is a LookupError
    print("index out of range")

# CORRECT
try:
    x = lst[10]
except IndexError:
    print("index out of range")
except LookupError:
    print("some other lookup error")

    Connection to AI, Machine Learning, and Deep Learning¶

    Exceptions in ML code are not edge cases — they are the primary debugging mechanism. Understanding which exception maps to which failure mode saves hours.

    ValueError in ML — shape mismatches¶

    Shape errors in NumPy and PyTorch surface as ValueError. This is the single most common exception you will see when writing neural network code.

    import numpy as np

A = np.ones((3, 4))
B = np.ones((5, 4))

A @ B              # ValueError: matmul: Input operand 1 has a mismatch in its core dimension 0
                   # Expected (4,), got (5,) — the inner dimensions do not match

# In PyTorch, the same operation raises RuntimeError with a shape message
# but the cause is identical: you are trying to multiply incompatible matrices

    The weight matrix shape convention in ML:

    Linear layer: \(y = Wx + b\) where \(W \in \mathbb{R}^{d_{out} \times d_{in}}\), \(x \in \mathbb{R}^{d_{in}}\)

    # If you get the shapes backwards:
W = np.random.randn(3, 5)   # 3 output features, 5 input features
x = np.random.randn(3)      # 3-dimensional input — should be 5-dimensional

W @ x    # ValueError — 5 ≠ 3

    KeyError — vocabulary and configuration¶

    # Word embedding lookup
vocab = {"the": 0, "cat": 1, "sat": 2}
embedding_matrix = np.random.randn(3, 64)

def embed(word):
    return embedding_matrix[vocab[word]]    # KeyError if word not in vocab

embed("elephant")    # KeyError: 'elephant'

# Correct: handle unknown tokens
UNK_IDX = vocab.get("<UNK>", 0)
def embed_safe(word):
    return embedding_matrix[vocab.get(word, UNK_IDX)]

    IndexError — batch indexing and dataset access¶

    class Dataset:
    def __init__(self, samples):
        self.samples = samples

    def __getitem__(self, idx):
        return self.samples[idx]    # IndexError if idx >= len(samples)

    def __len__(self):
        return len(self.samples)

    The DataLoader calls __getitem__ with indices from a sampler. If your sampler generates indices without respecting len(dataset), you get IndexError. This is a real failure mode in custom samplers.

    AttributeError — the unbuilt model¶

    class Trainer:
    def __init__(self):
        self.model = None    # not yet built

    def train(self, X, y):
        self.model.fit(X, y)    # AttributeError: 'NoneType' object has no attribute 'fit'
                                # build() was never called

    RuntimeError in PyTorch — the GPU exception family¶

    PyTorch uses RuntimeError for most of its internal errors, including:

    RuntimeError: Expected all tensors to be on the same device
RuntimeError: CUDA out of memory
RuntimeError: Expected input batch_size (32) to match target batch_size (64)

    These are not in Python's standard library, but they follow the same principle: a precondition was violated. Read the message, check the shapes and devices.

    Exceptions as a debugging strategy¶

    In a training loop, wrapping the entire loop in a broad except catches everything but tells you nothing. The discipline is:

    for epoch in range(epochs):
    for batch_idx, (X, y) in enumerate(dataloader):
        try:
            loss = train_step(X, y)
        except ValueError as e:
            print(f"Shape error at batch {batch_idx}: {e}")
            print(f"X shape: {X.shape}, y shape: {y.shape}")
            raise   # re-raise after logging — don't swallow

    Catch specifically, log the context, then re-raise. Swallowing exceptions in ML training loops is how bugs become silent convergence failures that waste GPU hours.
