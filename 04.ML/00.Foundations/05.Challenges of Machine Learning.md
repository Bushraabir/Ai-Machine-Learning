## 1. Insufficient Data and Labelling

### What Is It?

Most ML algorithms require a large number of labelled examples to learn reliably. In supervised learning, every training example $(x_i, y_i)$ requires a label $y_i$ that was provided by a human or a trusted measurement system. Labels are expensive, slow, and sometimes impossible to obtain at scale.

**Why it matters formally.** From statistical learning theory: the generalisation gap between training and test error is bounded by $O!\left(\sqrt{\frac{\ln|\mathcal{H}|}{n}}\right)$ — it shrinks with more data $n$. With too few examples, even the best algorithm cannot close this gap.

**Real-world examples of the labelling bottleneck:**

- Medical imaging: a radiologist takes 10–30 minutes to annotate one CT scan
- Rare failure events: a factory machine fails 3 times per year — you cannot train on 3 examples
- Legal documents: legal labels require domain expertise that does not scale cheaply
- Low-resource languages: 7,000 languages exist; most have near-zero labelled NLP data

### Fixes

|Strategy|Mechanism|
|---|---|
|**Data augmentation**|Artificially expand the training set by applying label-preserving transformations (flips, crops, rotations, noise injection)|
|**Transfer learning**|Start from weights pretrained on a large dataset; fine-tune on your small labelled set|
|**Semi-supervised learning**|Leverage unlabelled data (abundant) alongside the small labelled set|
|**Active learning**|Query labels only for the examples the model is most uncertain about — maximise information per annotation dollar|
|**Synthetic data**|Generate artificial training examples from a simulator or generative model|
|**Self-supervised pretraining**|Pretrain on unlabelled data using automatically constructed supervision (BERT, GPT)|

> [!tip] Practical Rule Before collecting more data, exhaust augmentation. Before training from scratch, try fine-tuning a pretrained model. The marginal cost of labels usually exceeds the marginal cost of algorithm engineering.

## 2. Non-Representative Data

### What Is It?

The training set must be drawn from the **same distribution** as the deployment distribution. When this assumption fails — when training data is biased, skewed, or unrepresentative — the model learns a distorted picture of reality and fails systematically on underrepresented cases.

**Formally.** Standard PAC learning guarantees assume training examples are drawn i.i.d. from $P_{\mathcal{X} \times \mathcal{Y}}$, and test examples are drawn from the same $P$. If training and test distributions differ ($P_{\text{train}} \neq P_{\text{test}}$), generalisation guarantees break down. This is called **covariate shift** or **dataset shift**.

**Types of distribution mismatch:**

|Type|Description|Example|
|---|---|---|
|**Covariate shift**|$P(x)$ differs between train and test; $P(y \mid x)$ stays the same|Training on hospital A's patients, deploying at hospital B|
|**Label shift**|$P(y)$ differs; class prevalence changes|Training on balanced spam/ham; deployed where 98% is ham|
|**Concept drift**|$P(y \mid x)$ itself changes over time|Sentiment of the word "sick" changed (bad→good in slang)|
|**Sample selection bias**|Training data is collected through a non-random process|Training a hiring model on historical hires (already filtered)|

**Famous failure:** Face recognition systems trained predominantly on lighter-skinned faces achieved dramatically lower accuracy on darker-skinned faces — a direct consequence of non-representative training data.

### Fixes

- **Stratified sampling:** ensure all relevant subgroups are represented proportionally (or intentionally overrepresented)
- **Diversity audits:** explicitly measure subgroup performance before deployment
- **Importance weighting:** reweight training examples to match the target distribution $P_{\text{test}}$
- **Collect from underrepresented groups** deliberately — not as an afterthought
- **Distribution shift detection:** monitor feature statistics at inference time; trigger retraining when drift is detected

## 3. Poor Quality Data

### What Is It?

Even with sufficient, representative data, the presence of **errors in the data itself** degrades learning. Every real-world dataset contains:

- **Label noise:** human annotators make mistakes, especially on ambiguous cases. Agreement rates between annotators are often 70–85%, not 100%.
- **Missing values:** sensors fail, users skip form fields, database joins drop rows
- **Duplicate records:** the same entity appears multiple times with slightly different attributes
- **Measurement errors:** sensor drift, unit inconsistencies, transcription errors
- **Outliers:** extreme values that are either genuine or data entry mistakes

**Why noise hurts.** In classification, label noise converts a fraction $\epsilon$ of training labels to random noise. This is equivalent to adding irreducible error to the learning problem: no matter how good the algorithm, it cannot do better than the Bayes error $+,\epsilon$ on noisy labels. The model wastes capacity memorising noise.

### Fixes

|Fix|When to Apply|
|---|---|
|**Data cleaning pipelines**|Always — automate detection of duplicates, impossible values, format errors|
|**Outlier detection**|When outliers are likely errors, not genuine extremes|
|**Multiple annotators + majority vote**|When labels are subjective or human-generated|
|**Label smoothing**|Replace hard labels ${0,1}$ with soft targets ${\epsilon, 1-\epsilon}$ — reduces model confidence in noisy labels|
|**Robust loss functions**|Huber loss, trimmed loss — downweight the influence of outlier examples|
|**Missing value imputation**|Mean/median imputation, KNN imputation, model-based imputation|

```python
import pandas as pd
import numpy as np
from sklearn.impute import SimpleImputer

# ── Simulate dirty data ───────────────────────────────────────────
df = pd.DataFrame({
    'age':    [25, 30, np.nan, 999, 28, 35, np.nan],
    'income': [50000, np.nan, 60000, 75000, np.nan, 80000, 55000],
    'label':  [0, 1, 1, 0, 1, 0, 1]
})

print("Raw data:")
print(df)

# ── Step 1: Remove impossible values ─────────────────────────────
df['age'] = df['age'].where(df['age'] < 120, np.nan)

# ── Step 2: Impute missing values ─────────────────────────────────
imputer = SimpleImputer(strategy='median')
df[['age', 'income']] = imputer.fit_transform(df[['age', 'income']])

# ── Step 3: Remove duplicates ─────────────────────────────────────
df = df.drop_duplicates()

print("\nCleaned data:")
print(df)
```

## 4. Irrelevant Features

### What Is It?

Adding features that carry no signal about the target variable introduces noise into the learning problem. The model wastes capacity learning that these features are uninformative, and may latch onto spurious correlations present in the training data that do not generalise.

**The curse of dimensionality (revisited).** In high dimensions, every feature adds a new axis along which training examples become sparse. With $d$ features and $n$ examples, the density of data in the input space scales as $n^{1/d}$ — exponential in $d$. Adding irrelevant features expands $d$ without adding informative signal, making the learning problem strictly harder.

**Spurious correlations.** A model trained on hospital data might learn that "hospital ID" predicts patient survival — because wealthier hospitals have both better equipment and wealthier patients. This is not a causal feature; it is a confounder. In deployment, hospital ID might not be available, or might change meaning across populations.

### Fixes

|Method|Type|Mechanism|
|---|---|---|
|**Mutual information**|Filter|Measures statistical dependence between feature and target|
|**Correlation analysis**|Filter|Remove features with near-zero correlation with target|
|**LASSO regression**|Embedded|L1 regularisation shrinks irrelevant feature weights to exactly zero|
|**Recursive feature elimination**|Wrapper|Iteratively remove the least useful feature|
|**PCA**|Transformation|Project into lower-dimensional subspace of maximum variance|
|**Domain knowledge**|Manual|Consult subject-matter experts; remove features without causal rationale|

```python
from sklearn.feature_selection import mutual_info_classif
from sklearn.datasets import make_classification
import numpy as np

# 10 features, only 3 are informative
X, y = make_classification(n_samples=500, n_features=10,
                            n_informative=3, n_redundant=2,
                            n_repeated=0, random_state=42)

mi_scores = mutual_info_classif(X, y, random_state=42)

print("Mutual Information scores (higher = more informative):")
for i, score in enumerate(mi_scores):
    bar = '█' * int(score * 30)
    print(f"  Feature {i:2d}: {score:.3f}  {bar}")

# Keep only features with MI above a threshold
threshold = 0.05
selected = np.where(mi_scores > threshold)[0]
print(f"\nSelected features: {selected}")
X_selected = X[:, selected]
```

## 7. Data Collection

### What Is It?

Before any of the above issues can be addressed, data must first be **collected, stored, and made accessible**. This is frequently the largest time and cost investment in an ML project. Challenges include:

- **Privacy and legal constraints:** GDPR, HIPAA, CCPA limit what data can be collected, stored, and used. Consent, anonymisation, and data retention policies add engineering overhead.
- **Data silos:** data is distributed across departments, companies, or systems with no unified access layer
- **Annotation pipelines:** building tooling for human labellers, managing inter-annotator agreement, quality control
- **Sensor and infrastructure costs:** deploying sensors, APIs, or logging systems to generate future data
- **Cold start problem:** a new product has no historical data; the model cannot be trained before launch

### Fixes

|Strategy|Notes|
|---|---|
|**Web scraping + cleaning**|Large-scale data from public sources; requires legal review|
|**Data partnerships**|Share data between organisations under data use agreements|
|**Crowdsourcing**|Amazon Mechanical Turk, Scale AI, Labelbox for annotation at scale|
|**Synthetic data generation**|GANs, simulation, rule-based generators for rare events|
|**Federated learning**|Train on distributed private data without centralising it — each device trains locally, only model updates are shared|
|**Data flywheel**|Design the product to generate labelled data as a byproduct of usage (e.g., user corrections to autocomplete become training data)|

## 5. Overfitting

### What Is It?

The model has learned the **training data** rather than the **underlying pattern**. It achieves very low training error but high test error — it has memorised noise and idiosyncrasies of the training set that do not exist in the broader data distribution.

**Formally.** Let $\hat{R}(h)$ = training error, $R(h)$ = true generalisation error. Overfitting means:

$$\hat{R}(h) \ll R(h) \quad \Leftrightarrow \quad \text{large generalisation gap}$$

The generalisation gap grows when the hypothesis class $\mathcal{H}$ is too expressive relative to $n$. VC theory tells us this gap scales as $O!\left(\sqrt{d_{\text{VC}}/n}\right)$ — as VC dimension (model capacity) grows and $n$ stays fixed, generalisation degrades.

**Visual intuition:**

```
Training data:   ●  ●  ●   ●   ●
                 
Underfitting:    ─────────────────   (straight line, misses all)
Good fit:        ────╮─────╭────     (smooth curve, captures trend)
Overfitting:     ╰─╮╰╯╭─╯╭╰──╯      (wiggly, fits every point)
```

### Fixes

|Fix|Mechanism|
|---|---|
|**More training data**|Increasing $n$ shrinks the generalisation gap regardless of model capacity|
|**L2 regularisation (weight decay)**|Penalises large weights: $\mathcal{L}_{reg} = \mathcal{L} + \lambda\|w\|_2^2$|
|**L1 regularisation (LASSO)**|Penalises weight magnitude; induces sparsity: $\mathcal{L} + \lambda\|w\|_1$|
|**Dropout**|Randomly zero out neurons during training; prevents co-adaptation|
|**Early stopping**|Stop training when validation error starts increasing|
|**Simpler hypothesis class**|Fewer parameters, shallower network, lower-degree polynomial|
|**Cross-validation**|Detect the gap between training and validation performance early|
|**Data augmentation**|Increases effective $n$ without new data collection|

```python
from sklearn.linear_model import Ridge, Lasso
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import PolynomialFeatures
from sklearn.model_selection import train_test_split
import numpy as np

np.random.seed(42)
X = np.sort(np.random.randn(60, 1), axis=0)
y = 0.5 * X.squeeze()**2 + np.random.randn(60) * 0.4

X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.3)

# Overfit: degree-15 polynomial, no regularisation
from sklearn.linear_model import LinearRegression
pipe_overfit = Pipeline([
    ('poly', PolynomialFeatures(degree=15)),
    ('lin',  LinearRegression())
])
pipe_overfit.fit(X_train, y_train)

# Regularised: degree-15 polynomial + Ridge
pipe_ridge = Pipeline([
    ('poly',  PolynomialFeatures(degree=15)),
    ('ridge', Ridge(alpha=10.0))
])
pipe_ridge.fit(X_train, y_train)

print(f"{'Model':<20} {'Train R²':>10} {'Test R²':>10}")
print("-" * 42)
for name, pipe in [("Overfit (no reg)", pipe_overfit), ("Ridge (alpha=10)", pipe_ridge)]:
    tr = pipe.score(X_train, y_train)
    te = pipe.score(X_test,  y_test)
    print(f"{name:<20} {tr:>10.3f} {te:>10.3f}")

# High train R² + low test R² = overfitting
# Regularisation closes the gap
```

## 6. Underfitting

### What Is It?

The hypothesis class $\mathcal{H}$ is too restricted to capture the true complexity of $f^*$. Both training error and test error are high — the model fails even on data it has seen.

**Formally.** Let the **approximation error** be $\min_{h \in \mathcal{H}} R(h) - R(f^*)$ — the irreducible gap between the best model in $\mathcal{H}$ and the Bayes optimal. If $\mathcal{H}$ is too small, this gap is large regardless of $n$. More data cannot fix a fundamentally wrong hypothesis class.

**Example.** A degree-1 polynomial (linear model) trying to fit data generated by $y = x^3 + \epsilon$ will always underfit — the best possible linear model still cannot capture the cubic relationship, no matter how large $n$ is.

### Fixes

|Fix|Mechanism|
|---|---|
|**Richer hypothesis class**|Deeper network, higher-degree polynomial, more trees in an ensemble|
|**Better feature engineering**|Create features that capture the relevant structure (e.g., add $x^2$ manually)|
|**Remove excessive regularisation**|If $\lambda$ is too large, regularisation itself suppresses the model's capacity|
|**Train longer**|With SGD, early stopping might have halted training before convergence|
|**Reduce learning rate**|Allows finer convergence to the minimum of the training loss|

```python
from sklearn.linear_model import LinearRegression
from sklearn.preprocessing import PolynomialFeatures
from sklearn.pipeline import Pipeline
import numpy as np

np.random.seed(0)
X = np.linspace(-3, 3, 100).reshape(-1, 1)
y = X.squeeze()**3 - 2*X.squeeze() + np.random.randn(100) * 0.5

results = {}
for degree in [1, 2, 3, 5]:
    pipe = Pipeline([
        ('poly', PolynomialFeatures(degree=degree)),
        ('lin',  LinearRegression())
    ])
    pipe.fit(X, y)
    results[degree] = pipe.score(X, y)

print("Effect of model complexity on training fit:")
print(f"{'Degree':>8} | {'Train R²':>10} | {'Verdict'}")
print("-" * 42)
for d, r2 in results.items():
    verdict = "underfitting" if r2 < 0.9 else ("good fit" if r2 < 0.999 else "possible overfit")
    print(f"{d:>8} | {r2:>10.4f} | {verdict}")
```

## 8. Software Integration

### What Is It?

A model that works in a Jupyter notebook is not a product. Moving from research to production involves substantial engineering work that ML practitioners often underestimate:

- **Serving infrastructure:** REST or gRPC API, load balancing, autoscaling
- **Latency requirements:** a recommendation model must respond in <50ms; training took hours
- **Dependency management:** Python version, library versions, hardware drivers must be pinned and reproducible
- **Versioning:** model version, data version, code version must all be tracked and rollback-able
- **Monitoring:** detect when model performance degrades in production without ground-truth labels
- **A/B testing:** safely roll out a new model version to a fraction of traffic before full cutover

### Fixes

```
Research:     Jupyter notebook → Python script → Tests
      ↓
Packaging:    Docker container → Requirements pinned → Reproducible build
      ↓
Serving:      FastAPI / Flask → TorchServe / TF Serving → gRPC endpoint
      ↓
CI/CD:        GitHub Actions → automated test on every commit → deploy on merge
      ↓
Monitoring:   Data drift detectors → performance dashboards → alerting → rollback
```

**Key tools:**

|Problem|Tool|
|---|---|
|Experiment tracking|MLflow, Weights & Biases|
|Model serving|TorchServe, TF Serving, BentoML|
|Containerisation|Docker, Kubernetes|
|Pipeline orchestration|Kubeflow, Airflow, Prefect|
|Drift detection|Evidently AI, WhyLogs, Arize|

```python
# Minimal FastAPI model serving example
from fastapi import FastAPI
import numpy as np
from pydantic import BaseModel
import joblib

app = FastAPI()
model = joblib.load("model.pkl")          # load trained model once at startup

    features: list[float]
```

## 9. Offline Learning and Deployment Lag

### What Is It?

A model trained offline on historical data reflects the world at the time that data was collected. The moment the world changes — user behaviour shifts, products change, external events occur — the model's internal representation is stale. This is **concept drift**.

The longer the retraining cycle, the larger the gap between the model's world-view and reality. A model retrained annually may be catastrophically wrong by month 11.

**Types of drift:**

|Type|What Changes|Example|
|---|---|---|
|**Sudden drift**|Distribution shifts abruptly|COVID lockdowns changed e-commerce patterns overnight|
|**Gradual drift**|Distribution shifts slowly over time|User preferences evolve across months/years|
|**Recurring drift**|Seasonal or cyclic shifts|Christmas shopping spikes; flu season patterns|
|**Incremental drift**|Features shift continuously|Language evolves; new slang emerges|

### Fixes

|Fix|Notes|
|---|---|
|**Online learning**|Update parameters per example as new data arrives — see [[01. The Learning Problem#7. Batch Learning vs. Online Learning]]|
|**Scheduled retraining**|Retrain on a rolling window of recent data (daily, weekly)|
|**Drift detection**|Monitor feature statistics and prediction distributions; trigger retraining when drift exceeds a threshold|
|**Canary deployment**|Deploy new model to 5% of traffic; compare performance before full rollout|
|**Champion-challenger**|Run old and new model in parallel; switch when challenger is statistically better|

```python
import numpy as np
from scipy import stats

class DriftDetector:
    """
    Simple Population Stability Index (PSI) based drift detector.
    PSI < 0.1:  no significant drift
    PSI 0.1-0.2: moderate drift — monitor
    PSI > 0.2:  significant drift — retrain
    """

    def __init__(self, reference_data, n_bins=10):
        self.n_bins = n_bins
        self.ref_hist, self.bin_edges = np.histogram(
            reference_data, bins=n_bins, density=True
        )
        # Add small epsilon to avoid log(0)
        self.ref_hist = self.ref_hist + 1e-6

    def compute_psi(self, new_data):
        new_hist, _ = np.histogram(new_data, bins=self.bin_edges, density=True)
        new_hist = new_hist + 1e-6
        # PSI = sum((new - ref) * log(new / ref))
        psi = np.sum((new_hist - self.ref_hist) * np.log(new_hist / self.ref_hist))
        return psi

    def check(self, new_data):
        psi = self.compute_psi(new_data)
        if psi < 0.1:
            status = "stable — no action needed"
        elif psi < 0.2:
            status = "moderate drift — increase monitoring"
        else:
            status = "SIGNIFICANT DRIFT — trigger retraining"
        print(f"PSI = {psi:.4f} | {status}")
        return psi


# ── Demo ──────────────────────────────────────────────────────────
np.random.seed(1)
reference = np.random.normal(0, 1, 1000)    # original distribution
no_drift  = np.random.normal(0, 1, 200)     # same distribution
drift     = np.random.normal(2, 1.5, 200)   # shifted distribution

detector = DriftDetector(reference)
print("Checking stable data:   ", end=""); detector.check(no_drift)
print("Checking drifted data:  ", end=""); detector.check(drift)
```

## 10. Cost Involved

### What Is It?

Training and deploying ML models at scale is expensive. The cost has several components:

|Cost Component|Description|
|---|---|
|**Compute (training)**|GPU/TPU hours: GPT-4 training estimated at $50–100M. Even small fine-tuning runs can cost $10k–$100k.|
|**Compute (inference)**|Every prediction request costs money. At scale, inference cost exceeds training cost.|
|**Storage**|Datasets (terabytes to petabytes), model checkpoints, feature stores|
|**Engineering**|MLOps infrastructure, tooling, maintaining pipelines|
|**Data labelling**|Annotation at scale: $1–$10 per label × millions of labels|
|**Electricity**|Large training runs consume megawatt-hours; meaningful carbon footprint|

This creates a **barrier to entry** that favours large organisations and makes many problems economically unviable for smaller teams.

### Fixes

|Technique|How It Reduces Cost|
|---|---|
|**Knowledge distillation**|Train a small "student" model to mimic a large "teacher" model — student has much lower inference cost|
|**Quantisation**|Reduce weight precision from 32-bit float to 8-bit or 4-bit integers — 4× memory reduction, faster inference|
|**Pruning**|Remove weights close to zero — sparse model with fewer effective parameters|
|**Early stopping**|Stop training when validation performance plateaus — save compute|
|**Cloud spot instances**|Use preemptible cloud compute at 60–90% discount|
|**Caching**|Cache predictions for repeated or similar queries|
|**Efficient architectures**|MobileNet, DistilBERT, TinyLLaMA — designed for low compute without catastrophic accuracy loss|

```python
# Knowledge distillation — training a small student to mimic a large teacher
import numpy as np

def softmax(x, temperature=1.0):
    """Softmax with temperature scaling for soft targets."""
    x = x / temperature
    e_x = np.exp(x - np.max(x))
    return e_x / e_x.sum()

def distillation_loss(student_logits, teacher_logits, true_labels,
                      temperature=3.0, alpha=0.5):
    """
    Total loss = alpha * KL(soft teacher | soft student)
               + (1 - alpha) * CrossEntropy(student, true_labels)

    Soft targets (temperature > 1) reveal inter-class relationships
    the teacher has learned that hard one-hot labels do not carry.
    Higher temperature = softer probability distribution.
    """
    # Soft targets from teacher (high temperature → reveals uncertainty)
    teacher_soft = softmax(teacher_logits, temperature=temperature)
    student_soft = softmax(student_logits, temperature=temperature)

    # KL divergence: how different is student from teacher?
    kl_div = np.sum(teacher_soft * np.log(teacher_soft / (student_soft + 1e-8)))

    # Hard cross-entropy with true labels
    student_probs = softmax(student_logits, temperature=1.0)
    ce_loss = -np.log(student_probs[true_labels] + 1e-8)

    total_loss = alpha * (temperature**2) * kl_div + (1 - alpha) * ce_loss
    return total_loss, kl_div, ce_loss


# ── Demo ──────────────────────────────────────────────────────────
np.random.seed(42)
n_classes = 5
teacher_logits = np.array([2.1, 0.3, 0.8, 0.1, 0.4])  # large model output
student_logits = np.array([1.5, 0.1, 0.5, 0.2, 0.3])  # small model output
true_label = 0  # ground truth class

loss, kl, ce = distillation_loss(student_logits, teacher_logits, true_label,
                                  temperature=3.0, alpha=0.5)

print(f"Teacher soft probs: {softmax(teacher_logits, 3.0).round(3)}")
print(f"Student soft probs: {softmax(student_logits, 3.0).round(3)}")
print(f"\nKL divergence (student vs teacher): {kl:.4f}")
print(f"Cross-entropy (student vs true):    {ce:.4f}")
print(f"Total distillation loss:            {loss:.4f}")
print("\nStudent is trained to match the teacher's soft beliefs,")
print("not just the hard label — cheaper model, retained knowledge.")
```

## Code — Diagnosing Common Challenges

This single script detects several challenges at once — a useful first-pass diagnostic on any new dataset:

```python
import numpy as np
import pandas as pd
from sklearn.model_selection import train_test_split, cross_val_score
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.feature_selection import mutual_info_classif

def diagnose_dataset(X, y, feature_names=None):
    """
    Run a first-pass ML dataset diagnostic.
    Checks: data volume, missing values, class balance,
    feature relevance, and overfitting risk.
    """
    print("=" * 52)
    print("ML DATASET DIAGNOSTIC")
    print("=" * 52)

    n, d = X.shape
    print(f"\nDataset: {n} examples, {d} features")

    # ── 1. Data volume ─────────────────────────────────────────────
    if n < 100:
        print("  [WARN] Very few examples — high overfitting risk")
    elif n < 1000:
        print("  [INFO] Moderate dataset — consider augmentation")
    else:
        print("  [OK]   Dataset size looks reasonable")

    # ── 2. Missing values ──────────────────────────────────────────
    if isinstance(X, np.ndarray):
        missing = np.isnan(X).sum()
    else:
        missing = X.isnull().sum().sum()

    if missing > 0:
        pct = 100 * missing / (n * d)
        print(f"  [WARN] {missing} missing values ({pct:.1f}%) — imputation required")
    else:
        print("  [OK]   No missing values")

    # ── 3. Class balance ───────────────────────────────────────────
    classes, counts = np.unique(y, return_counts=True)
    min_pct = 100 * counts.min() / n
    if min_pct < 10:
        print(f"  [WARN] Class imbalance — smallest class is {min_pct:.1f}% of data")
    else:
        print(f"  [OK]   Class distribution: {dict(zip(classes, counts))}")

    # ── 4. Feature relevance (mutual information) ──────────────────
    mi = mutual_info_classif(X, y, random_state=0)
    n_irrelevant = (mi < 0.01).sum()
    if n_irrelevant > 0:
        print(f"  [WARN] {n_irrelevant}/{d} features have near-zero mutual information")
        if feature_names:
            bad = [feature_names[i] for i in np.where(mi < 0.01)[0]]
            print(f"         Irrelevant features: {bad}")
    else:
        print("  [OK]   All features have non-trivial mutual information")

    # ── 5. Overfitting check (train vs. CV gap) ────────────────────
    scaler = StandardScaler()
    X_s = scaler.fit_transform(X)
    model = LogisticRegression(max_iter=1000)
    model.fit(X_s, y)
    train_score = model.score(X_s, y)
    cv_score    = cross_val_score(model, X_s, y, cv=5).mean()
    gap = train_score - cv_score

    print(f"\n  Train accuracy: {train_score:.3f}")
    print(f"  CV accuracy:    {cv_score:.3f}")
    print(f"  Gap:            {gap:.3f}")

    if gap > 0.10:
        print("  [WARN] Large train/CV gap — likely overfitting")
    elif cv_score < 0.60:
        print("  [WARN] Low CV accuracy — possible underfitting or hard problem")
    else:
        print("  [OK]   Train/CV gap is reasonable")

    print("=" * 52)
```
