## 1. Intuition First

### The Core Idea

Read a sentence aloud that contains nested clauses — "The cat (which sat on the mat [that was blue]) slept." Your brain automatically tracks the nesting: open parenthesis, open bracket, close bracket (matches the inner one), close parenthesis (matches the outer one). You never mix them up because you instinctively maintain a _memory of what you opened most recently_ and verify that each closing symbol resolves the most recent unresolved opener.

That memory — "what did I open most recently?" — is precisely a stack.

The rule is deceptively simple: when you see an opener (`(`, `[`, `{`), remember it. When you see a closer (`)`, `]`, `}`), check that it matches the opener you remembered _most recently_. If it does, forget that opener (it is resolved). If it does not — or if there is no opener to resolve — the string is invalid. At the end, if any openers remain unresolved, the string is invalid.

The stack is the only data structure that answers "what did I see most recently?" in O(1) per query while supporting both push and pop — which is exactly why this problem and the stack are inseparable.

### Why This Exists

The naive approach — count opening and closing brackets — fails immediately on `)(` (counts are equal but it's invalid) and `([)]` (counts are equal but nesting is wrong). Counting destroys order information. You need a data structure that preserves order _and_ lets you access the most recent unmatched element instantly.

A stack costs $O(n)$ time and $O(n)$ space, and it is optimal: you must read every character (hence $\Omega(n)$ time), and in the worst case every character is an opener that must be remembered until the end (hence $\Omega(n)$ space). No algorithm can do better on both bounds simultaneously.

### The "Aha" Moment

**The stack is a machine for verifying nesting.** Any language with recursive structure — arithmetic expressions, HTML/XML tags, JSON, source code, file path operations — reduces to bracket matching at its core. The insight is that _nested structure collapses from the inside out_, and a stack processes exactly that: the most recently opened scope must be the next one closed.

Once you see "nesting" in a problem description, your first thought should be: "is there a stack hidden here?"

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

Bracket matching is one of the most frequent "warm-up" problems in contests — it appears in virtually every Div. 3 and as a sub-problem in harder Div. 2 problems. More importantly, it is the _pattern_ underlying a large class of harder problems.

**Signal patterns:**

- "Valid / balanced / well-formed" with any kind of paired symbols → stack
- "Minimum insertions/deletions to make balanced" → stack + greedy
- "Score of parentheses / weighted nesting" → stack accumulates values
- "Longest valid parentheses substring" → stack stores indices, not characters
- "Remove invalid parentheses" → BFS + stack validity check

**Common trap — the index-storing variant:** Problems like "longest valid parentheses" (LC 32) require storing _indices_ of unmatched openers in the stack, not the characters themselves. The stack starts with a sentinel `−1` on it. Forgetting the sentinel is the most common WA on this class.

**Second trap:** Empty string is always valid. Problems sometimes omit this edge case from examples. Your `isEmpty()` check at the end handles it automatically if you initialise the stack correctly.

**Third trap:** `std::stack::pop()` in C++ returns `void`. You must call `top()` before `pop()`. Calling `pop()` then using the return value is undefined behaviour.

### Machine Learning / AI

Bracket matching is not just a toy problem — it is embedded in the infrastructure of ML systems:

**1. Tokenisers and parsers in NLP pipelines.** Before a transformer ever sees text, a preprocessor must parse structured input: JSON metadata, HTML-scraped documents, code datasets (Python, Java, C++). All of these have bracket/brace structure that must be validated or repaired. HuggingFace's `tokenizers` library handles malformed bracket sequences in raw web-scraped text using stack-based repair heuristics.

**2. Code generation evaluation.** When evaluating LLM-generated code (e.g., HumanEval, MBPP benchmarks), one of the first syntactic checks is bracket balance. Models that generate code with unmatched brackets are penalised. Bracket validity is a fast $O(n)$ pre-filter before attempting to execute or compile generated code.

**3. Structured output parsing from LLMs.** Frameworks like LangChain, LlamaIndex, and Instructor parse LLM outputs as JSON or XML. When the model generates a partial or malformed JSON blob (a common failure mode), the repair strategy is stack-based: find the deepest unmatched opener, close it, propagate outward. This is bracket matching in reverse.

**4. Recursive neural networks and tree structures.** Models that process parse trees (Tree-LSTMs by Tai et al., 2015) implicitly use bracket structure to encode constituency. The bracket sequence of a parse tree (`(S (NP ...) (VP ...))`) is a linear encoding of tree structure — and recovering the tree from this sequence is exactly bracket matching with a stack.

Understanding the algorithm makes these systems debuggable rather than opaque.

## 3. Algorithm / Pattern

### Core Algorithm (Single Bracket Type)

For just `()`:

1. Scan left to right.
2. On `(`: push onto stack.
3. On `)`: if stack is empty → invalid. Else pop from stack.
4. After scanning: if stack is empty → valid. Else → invalid (unmatched openers remain).

### Full Algorithm (Three Bracket Types)

Build a **matching map**: `)→(`, `]→[`, `}→{`.

1. Scan left to right.
2. If character is an opener `(`, `[`, `{`: push it.
3. If character is a closer `)`, `]`, `}`:
    - If stack is empty → invalid (closer with no matching opener).
    - If `stack.top() ≠ match[closer]` → invalid (wrong type of opener).
    - Else: pop from stack (this closer resolves the most recent opener).
4. End of string: valid iff stack is empty.

### Complexity Derivation

**Time: $O(n)$.** Each character is processed exactly once. Each character triggers at most one push and one pop. Push and pop are both $O(1)$. Total: $n$ characters × $O(1)$ per character = $O(n)$.

**Space: $O(n)$.** Worst case: all characters are openers (e.g., `(((((`), so all $n$ characters are pushed. Stack holds $n$ elements.

**Can we do better?** For the decision problem (valid/invalid), $O(n)$ time is optimal — we must examine every character. For space, $O(1)$ is achievable only for a single bracket type (just track a counter), but for multiple types you cannot avoid a stack of $O(n)$ in the worst case without losing correctness.

### When to Use vs. Avoid

|Situation|Use stack?|
|---|---|
|Validate bracket balance|Yes — canonical use|
|Find longest valid substring|Yes — store indices in stack|
|Count min moves to make valid|Yes — two counters or stack|
|Single bracket type only|Optional — counter suffices|
|Bracket with wildcards (`*`)|Stack + greedy or DP|
|Only counting, no nesting check needed|Counter, not stack|

## 4. Pseudocode

```
function isValid(s: string) → bool:
    stack ← empty stack
    match ← { ')':'(', ']':'[', '}':'{' }
    openers ← set { '(', '[', '{' }

    for each character ch in s:
        if ch ∈ openers:
            push ch onto stack
            // We must remember this opener until its closer appears.
            // Stack ensures we remember the MOST RECENT one first.

        else:
            // ch is a closer; it must resolve the most recent opener
            if stack.isEmpty():
                return false    // closer with no corresponding opener
            if stack.peek() ≠ match[ch]:
                return false    // wrong bracket type, e.g. ( matched with ]
            stack.pop()         // this opener is now resolved

    // If any openers remain unresolved, the string is invalid
    return stack.isEmpty()
```

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <iostream>
#include <stack>
#include <string>
#include <unordered_map>

// ── Core: validate bracket balance ───────────────────────────────────────────
bool isValid(const std::string& s) {
    std::stack<char> stk;
    const std::unordered_map<char, char> match = {
        {')', '('},
        {']', '['},
        {'}', '{'}
    };

    for (char ch : s) {
        if (ch == '(' || ch == '[' || ch == '{') {
            stk.push(ch);
        } else {
            // ch is a closer
            if (stk.empty() || stk.top() != match.at(ch))
                return false;
            stk.pop();
        }
    }
    return stk.empty();
}

// ── Extension: longest valid parentheses substring (LC 32) ───────────────────
// Key insight: store INDICES in the stack, not characters.
// Sentinel -1 marks the base of the current valid window.
int longestValidParentheses(const std::string& s) {
    std::stack<int> stk;
    stk.push(-1);   // sentinel: "the position just before the current window"
    int maxLen = 0;

    for (int i = 0; i < (int)s.size(); ++i) {
        if (s[i] == '(') {
            stk.push(i);   // store index of unmatched opener
        } else {
            stk.pop();     // attempt to match
            if (stk.empty()) {
                stk.push(i);   // reset sentinel: this ')' is unmatched
            } else {
                // distance from current position to the bottom of the stack
                // gives the length of the current valid window
                maxLen = std::max(maxLen, i - stk.top());
            }
        }
    }
    return maxLen;
}

// ── Extension: minimum additions to make valid (LC 921) ──────────────────────
// Count unmatched '(' and unmatched ')' — each needs one insertion.
int minAddToMakeValid(const std::string& s) {
    int openCount = 0;   // unmatched '(' seen so far
    int closeCount = 0;  // unmatched ')' seen so far

    for (char ch : s) {
        if (ch == '(') {
            ++openCount;
        } else {
            if (openCount > 0)
                --openCount;   // this ')' matches an earlier '('
            else
                ++closeCount;  // unmatched ')'
        }
    }
    // openCount unmatched '(' each need a ')'
    // closeCount unmatched ')' each need a '('
    return openCount + closeCount;
}

int main() {
    std::cout << std::boolalpha;
    std::cout << isValid("()")     << "\n";  // true
    std::cout << isValid("()[]{}")  << "\n";  // true
    std::cout << isValid("(]")     << "\n";  // false
    std::cout << isValid("([)]")   << "\n";  // false
    std::cout << isValid("{[]}")   << "\n";  // true

    std::cout << longestValidParentheses(")()())")  << "\n";  // 4
    std::cout << longestValidParentheses("()()")    << "\n";  // 4
    std::cout << longestValidParentheses("(()")     << "\n";  // 2

    std::cout << minAddToMakeValid("())")   << "\n";  // 1
    std::cout << minAddToMakeValid("(((")   << "\n";  // 3
    return 0;
}
```

### Python (Readable + Pythonic)

```python
def is_valid(s: str) -> bool:
    """
    Validate bracket balance for '()', '[]', '{}'.
    
    Time:  O(n)
    Space: O(n) — stack holds at most n/2 openers in the worst case
    """
    stack: list[str] = []
    match: dict[str, str] = {')': '(', ']': '[', '}': '{'}

    for ch in s:
        if ch in '([{':
            stack.append(ch)
        else:
            # Guard: empty stack means no opener to match against
            if not stack or stack[-1] != match[ch]:
                return False
            stack.pop()

    return not stack  # valid iff no unresolved openers remain


def longest_valid_parentheses(s: str) -> int:
    """
    LC 32 — Longest Valid Parentheses.
    
    Store indices in the stack. Sentinel -1 is the base of the current window.
    When we find a match, the valid window length = current_index - stack_top.
    
    Time: O(n), Space: O(n)
    """
    stack: list[int] = [-1]   # sentinel
    max_len = 0

    for i, ch in enumerate(s):
        if ch == '(':
            stack.append(i)
        else:
            stack.pop()
            if not stack:
                stack.append(i)   # this ')' is unmatched; reset sentinel
            else:
                max_len = max(max_len, i - stack[-1])

    return max_len


def min_add_to_make_valid(s: str) -> int:
    """
    LC 921 — Minimum Add to Make Parentheses Valid.
    
    Counter approach: no stack needed for single bracket type.
    open_count  = unmatched '(' seen so far (need a ')' each)
    close_count = unmatched ')' seen so far (need a '(' each)
    
    Time: O(n), Space: O(1)
    """
    open_count = close_count = 0
    for ch in s:
        if ch == '(':
            open_count += 1
        else:
            if open_count:
                open_count -= 1   # match this ')' with the most recent '('
            else:
                close_count += 1  # unmatched ')'
    return open_count + close_count


def min_remove_to_make_valid(s: str) -> str:
    """
    LC 1249 — Minimum Remove to Make Valid Parentheses.
    
    Two passes: first mark indices of unmatched brackets, then rebuild string.
    Time: O(n), Space: O(n)
    """
    to_remove: set[int] = set()
    stack: list[int] = []   # stores indices of unmatched '('

    for i, ch in enumerate(s):
        if ch == '(':
            stack.append(i)
        elif ch == ')':
            if stack:
                stack.pop()   # matched
            else:
                to_remove.add(i)   # unmatched ')'

    # Any remaining indices in stack are unmatched '('
    to_remove |= set(stack)

    return ''.join(ch for i, ch in enumerate(s) if i not in to_remove)


if __name__ == "__main__":
    # Core validation
    assert is_valid("()")      is True
    assert is_valid("()[]{}")  is True
    assert is_valid("(]")      is False
    assert is_valid("([)]")    is False
    assert is_valid("{[]}")    is True
    assert is_valid("")        is True   # edge case: empty string

    # Longest valid
    assert longest_valid_parentheses(")()())")  == 4
    assert longest_valid_parentheses("()()")    == 4
    assert longest_valid_parentheses("(()")     == 2

    # Min additions
    assert min_add_to_make_valid("())")  == 1
    assert min_add_to_make_valid("(((")  == 3

    # Min removals
    assert min_remove_to_make_valid("lee(t(c)o)de)") in {"lee(t(c)o)de", "lee(t(co)de)"}

    print("All assertions passed.")
```

## 7. Common Variations & Extensions

### Variation 1: Minimum Insertions / Deletions to Balance

Two sub-problems appear frequently:

- **Minimum additions** (LC 921): count unmatched openers and closers. No stack needed for single bracket type — two counters suffice.
- **Minimum removals** (LC 1249): mark unmatched brackets via a two-pass stack approach (indices in, indices out), then rebuild the string.
- **Minimum insertions for `()`-only with `))` closing** (LC 1541): modified counter where each `(` needs two `)`.

All reduce to: track unresolved openers and closers, each needing one operation. Connects to [[169.Coin change — minimum coins and number of ways]] in the sense of "minimum operations to reach a target state."

### Variation 2: Score of Parentheses (LC 856)

Assign score 1 to every matched `()`, and for nested content, double the inner score. This is stack-based accumulation: push a 0 when you see `(`; when you see `)`, pop the top value `v`:

- If `v == 0`: this was an empty pair `()`, contribute 1.
- Else: this was nested content, contribute `2 * v`. Add the contribution to the new top of the stack. The score accumulates naturally through nesting depth.

### Variation 3: Parentheses with Wildcards (LC 678)

`*` can be `(`, `)`, or empty. Greedy with two counters: track the range of possible unmatched open counts `[lo, hi]`. On `(`, increment both. On `)`, decrement both. On `*`, decrement `lo` and increment `hi`. If `hi < 0` at any point, invalid. At the end, valid iff `lo == 0`. This eliminates the need for a stack entirely — the wildcard converts a structural problem into a range problem.

### Variation 4: Generate All Valid Parentheses (LC 22)

Reverse direction: instead of validating, _produce_ all valid strings of $n$ pairs. This is [[77.Backtracking template — choose, explore, unchoose]] applied to parentheses: at each step, you may add `(` if `open < n`, or `)` if `close < open`. The pruning condition (never more closers than openers at any prefix) is exactly the stack invariant, enforced implicitly by the counter constraint.

## 9. CP Contest Application

### Codeforces / AtCoder Problem Structure

**Archetype 1 — Direct validation.** Given a bracket string, determine if it is valid. Usually Div. 3 A / Div. 2 A. Stack solution is one-liner territory. Time limit 1s, $n \leq 10^6$. The only way to TLE here is using `std::string` concatenation in a loop — always use `std::stack` or `vector`.

**Archetype 2 — Count or find within a bracket string.** "How many valid substrings?" or "find the longest valid substring?" These are Div. 2 B–C problems. The index-storing stack with a sentinel solves them in $O(n)$.

**Archetype 3 — Bracket strings as sub-problems.** Harder problems (Div. 1 B–C) may require checking bracket validity as part of a larger algorithm — e.g., validating that a generated sequence is valid before counting it. The stack is called as a subroutine.

### Optimization for CP

For pure `()`-only problems, skip the stack entirely:

```cpp
// O(n) time, O(1) space — counter approach for single bracket type
bool isValidSingleType(const std::string& s) {
    int depth = 0;
    for (char ch : s) {
        depth += (ch == '(') ? 1 : -1;
        if (depth < 0) return false;  // closer before any opener
    }
    return depth == 0;
}
```

This is twice as fast in practice due to eliminating all heap allocation. Use it whenever the problem only involves `()`.
