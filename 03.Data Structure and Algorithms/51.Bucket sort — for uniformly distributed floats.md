## 1. Intuition First

### The Core Idea

Imagine you have 1,000 students whose exam scores are uniformly spread between 0 and 100. You want to rank them. A comparison sort would take O(n log n). But here's the key observation: **you already know something about the data** — it's uniform. You can exploit that knowledge.

Divide the range [0, 100] into 10 equal-width "buckets": [0,10), [10,20), ..., [90,100]. Toss each student into their bucket. Because scores are uniform, each bucket gets roughly 100 students. Now sort each bucket independently. Each bucket sort costs O(k log k) where k ≈ 10. Total: 10 buckets × O(10 log 10) = O(n). You've broken the comparison sort lower bound — not by magic, but by **using distributional information as a free preprocessing oracle**.

The geometry is clear: you're partitioning the value axis into equal intervals and using the known distribution to guarantee that no bucket is catastrophically overloaded.

### Why This Exists

Comparison-based sorting has a **fundamental lower bound of Ω(n log n)** — provable by the decision tree argument. Every comparison sort, no matter how clever, must make at least log₂(n!) ≈ n log n comparisons in the worst case.

Bucket sort sidesteps this by not being a pure comparison sort. It uses the **actual values** of elements to place them directly into positions. The cost of this shortcut: you must know (or assume) something about the distribution. If the input is adversarially non-uniform — say, all values cluster in one bucket — bucket sort degrades to O(n²) (or O(n log n) with a good inner sort). The algorithm is only fast when its distributional assumption holds.

Counting sort makes the same bargain but for integers. Radix sort makes it digit-by-digit. Bucket sort makes it for **real-valued data that is approximately uniform**.

### The "Aha" Moment

The insight is this: **sorting is hard only when you don't know where elements belong**. Every comparison you make is gathering information about relative order. Bucket sort cheats — it uses the value of a float to compute its approximate position in O(1). The comparison sort lower bound applies to algorithms that learn order only through comparisons. Bucket sort learns position from the value itself.

The assumption of uniformity isn't magic — in many real domains (normalised feature vectors, uniform random samples, hashed values mapped to [0,1)), it holds exactly or approximately. When it does, you get O(n) expected time.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**When it appears:** Bucket sort rarely appears directly in CP contest problems — the test cases are often adversarially designed to break distributional assumptions. However, it appears implicitly in two patterns:

1. **Range partitioning problems**: When elements have known bounded values and you need to count or sort them with minimum passes, bucket sort thinking leads to optimal solutions.
2. **Offline query problems**: When queries can be bucketed by time or value range and answered per-bucket, the bucket decomposition is the same algorithmic idea.

**The pattern signal:** If you see "values are drawn uniformly from [L, R]" or "floating point values guaranteed to be distinct and uniformly distributed" — think bucket sort. Also: "sort and process in O(n)" with real-valued data.

**Common trap:** Choosing too few buckets (one bucket = insertion sort on whole array = O(n²)) or too many (n buckets but data isn't uniform so some buckets are empty and some have many elements, wasting memory). The optimal is n buckets for n elements **when the distribution is truly uniform**. Misapplying this when data is skewed is a classic mistake.

**Gotcha that kills submissions:** Using bucket sort on non-uniform data. Strings, integers with heavy clustering, anything with adversarial structure — bucket sort explodes. Always check whether the problem guarantees or implies uniform distribution.

### Machine Learning / AI

Bucket sort is one of the most underappreciated algorithmic ideas in ML engineering. It appears in:

**1. Feature Discretisation / Binning (scikit-learn `KBinsDiscretizer`)** `sklearn.preprocessing.KBinsDiscretizer` with `strategy='uniform'` partitions a continuous feature range into equal-width bins — this is exactly bucket sort partitioning. The `strategy='quantile'` variant adapts the bin boundaries so each bin has equal occupancy (adaptive bucketing). Understanding bucket sort helps you reason about which strategy is appropriate: uniform bins work when features are approximately uniformly distributed; quantile bins are more robust to skew.

**2. Histogram computation in tree-based models (XGBoost, LightGBM)** Both XGBoost and LightGBM use **histogram-based split finding** as their core optimisation over classical CART. The key step is discretising continuous feature values into bins (typically 256 bins, controlled by `max_bin`). This is bucket sort applied to each feature column. LightGBM's paper (Ke et al., 2017) explicitly optimises this step: the histogram construction dominates training time, and its O(n × num_bins) complexity assumes the bin assignment is O(1) per element — the same assumption bucket sort makes.

**3. Data pipeline bucketing in `tf.data`** TensorFlow's `tf.data.experimental.bucket_by_sequence_length` groups variable-length sequences into buckets of similar length before batching. This minimises padding waste. The bucket assignment is O(1) per element (check which length range it falls in), and elements within a bucket are batched together. The algorithm is bucket sort applied to sequence lengths.

**4. Approximate nearest neighbour — LSH and HNSW bucket assignment** In [[219.Approximate nearest neighbour — LSH, HNSW, FAISS conceptual overview]], hash functions map high-dimensional vectors to buckets such that nearby vectors land in the same bucket with high probability. The bucket structure and O(1) assignment cost are directly bucket sort concepts.

**Understanding this makes you write better ML code:** When you see `max_bin=255` in LightGBM or `n_bins=10` in `KBinsDiscretizer`, you now know you're controlling the number of buckets in a bucket-sort-like histogram construction. Too few bins → information loss, poor splits. Too many bins → memory cost dominates, and the uniform distribution assumption may break. You can reason about this tradeoff from first principles instead of treating it as a black-box hyperparameter.

## 3. Algorithm / Pattern

### Step-by-step Logic

1. **Normalise** the input to [0, 1) if it isn't already. For general range [lo, hi], map x → (x - lo) / (hi - lo).
2. **Create n empty buckets** indexed 0 to n−1 (where n = number of elements).
3. **Scatter**: For each element x, compute its bucket index as ⌊x × n⌋ and insert x into bucket[index]. This is O(1) per element.
4. **Sort each bucket** using insertion sort (or any sort). Insertion sort is optimal here because each bucket is expected to have O(1) elements, and insertion sort is fast on small arrays (low constant, cache-friendly).
5. **Gather**: Concatenate all buckets in order to produce the sorted output.

### Decision Tree

```
Does the data have a known bounded range?
  ├─ No → Use comparison sort (quicksort / mergesort)
  └─ Yes → Are values integers in a small range?
              ├─ Yes → [[49.Counting sort — O(n + k) for integer keys]]
              └─ No (floats) → Is the distribution approximately uniform?
                                  ├─ No (clustered/skewed) → Quicksort or Radix sort
                                  └─ Yes → Bucket Sort ✓
```

### Complexity Derivation

Let n = number of elements, k = number of buckets (we set k = n for optimal performance).

**Expected time:**

- Scatter phase: O(n) — one bucket index computation per element.
- Sort phase: Let nᵢ be the number of elements in bucket i. Each bucket costs O(nᵢ²) with insertion sort (or O(nᵢ log nᵢ) with a better sort).
- Total sort cost: ∑ᵢ₌₀ⁿ⁻¹ O(nᵢ²)

Under the uniform distribution assumption, each element independently lands in each bucket with probability 1/n. So nᵢ ~ Binomial(n, 1/n). By linearity of expectation:

$$E\left[\sum_{i=0}^{n-1} n_i^2\right] = \sum_{i=0}^{n-1} E[n_i^2] = \sum_{i=0}^{n-1} \left(\text{Var}(n_i) + (E[n_i])^2\right)$$

For Binomial(n, 1/n): E[nᵢ] = 1, Var(nᵢ) = (1 - 1/n) ≈ 1.

So E[nᵢ²] ≈ 1 + 1 = 2, and the total expected sort cost = n × O(2) = **O(n)**.

- Gather phase: O(n)
- **Total expected time: O(n)**
- **Worst case: O(n²)** — all elements in one bucket (degenerate input)

**Space complexity: O(n + k) = O(n)**

### When to Use vs. Avoid

|Use|Avoid|
|---|---|
|Data is known to be uniformly distributed|Adversarial or skewed input|
|Floats in a known bounded range|Integer keys with small range (use counting sort)|
|Data is pre-normalised (e.g., ML feature vectors in [0,1))|Unknown distribution|
|n is large and O(n log n) is too slow|Need worst-case guarantees|

## 4. Pseudocode

```
BUCKET-SORT(A, lo, hi):
    """
    Sort array A of floats in range [lo, hi].
    Expected O(n) time under uniform distribution.
    """
    n ← length(A)
    
    // Create n empty buckets
    buckets ← array of n empty lists
    
    // SCATTER: distribute elements into buckets
    // The key: map [lo, hi) → [0, n) using linear interpolation
    for each x in A:
        if x == hi:
            index ← n - 1              // Handle upper boundary edge case
        else:
            index ← floor((x - lo) / (hi - lo) * n)
        buckets[index].append(x)
    
    // SORT: each bucket is small (O(1) expected elements)
    // Insertion sort is optimal for small arrays
    for each bucket in buckets:
        INSERTION-SORT(bucket)         // O(k²) but k ≈ 1 in expectation
    
    // GATHER: concatenate in order
    result ← []
    for each bucket in buckets:
        result.extend(bucket)
    
    return result
```

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <vector>
#include <algorithm>
#include <stdexcept>
#include <numeric>

/**
 * Bucket Sort for floating-point values.
 *
 * Preconditions:
 *   - All elements are in [lo, hi]
 *   - Distribution is approximately uniform for O(n) expected behaviour
 *
 * Time:  O(n) expected, O(n^2) worst case
 * Space: O(n)
 */
std::vector<double> bucketSort(std::vector<double> arr,
                                double lo = 0.0,
                                double hi = 1.0) {
    const int n = static_cast<int>(arr.size());
    if (n <= 1) return arr;

    if (lo >= hi) {
        throw std::invalid_argument("lo must be strictly less than hi");
    }

    // Validate that all elements are in [lo, hi]
    // (skip in production for speed; keep for debugging)
    // for (double x : arr) {
    //     if (x < lo || x > hi) throw std::out_of_range("Element out of range");
    // }

    // Create n buckets
    std::vector<std::vector<double>> buckets(n);

    // SCATTER: compute bucket index in O(1) per element
    const double range = hi - lo;
    for (double x : arr) {
        int idx = static_cast<int>((x - lo) / range * n);
        // Clamp to handle the upper boundary (x == hi maps to n, not n-1)
        idx = std::min(idx, n - 1);
        buckets[idx].push_back(x);
    }

    // SORT: each bucket independently
    // std::sort uses introsort (hybrid quicksort/heapsort/insertion sort)
    // which is optimal for small arrays and guarantees O(k log k) worst case
    for (auto& bucket : buckets) {
        std::sort(bucket.begin(), bucket.end());
    }

    // GATHER: write back into original array
    int pos = 0;
    for (const auto& bucket : buckets) {
        for (double x : bucket) {
            arr[pos++] = x;
        }
    }

    return arr;
}
```

**General range version (not just [0,1)):**

```cpp
// For data not in [0,1): auto-compute range
std::vector<double> bucketSortAuto(std::vector<double> arr) {
    if (arr.size() <= 1) return arr;
    auto [lo_it, hi_it] = std::minmax_element(arr.begin(), arr.end());
    double lo = *lo_it, hi = *hi_it;
    if (lo == hi) return arr;  // All elements equal
    // Extend hi slightly to avoid index == n for elements exactly at hi
    return bucketSort(arr, lo, hi + 1e-9);
}
```

### Python (Readable + Pythonic)

```python
from typing import Optional
import math


def bucket_sort(
    arr: list[float],
    lo: Optional[float] = None,
    hi: Optional[float] = None,
) -> list[float]:
    """
    Sort a list of floats using bucket sort.

    Assumes approximately uniform distribution in [lo, hi] for O(n) performance.
    Falls back gracefully (but slowly) for non-uniform data.

    Args:
        arr: Input list of floats.
        lo:  Lower bound of the range. Defaults to min(arr).
        hi:  Upper bound of the range. Defaults to max(arr).

    Returns:
        Sorted list.

    Time:  O(n) expected (uniform), O(n^2) worst case (all in one bucket)
    Space: O(n)
    """
    n = len(arr)
    if n <= 1:
        return list(arr)

    lo = min(arr) if lo is None else lo
    hi = max(arr) if hi is None else hi

    if lo == hi:
        return list(arr)  # All elements are identical

    # Extend hi slightly to handle boundary: floor((hi - lo) / range * n) == n
    range_val = hi - lo + 1e-12

    # SCATTER: O(n)
    buckets: list[list[float]] = [[] for _ in range(n)]
    for x in arr:
        idx = int((x - lo) / range_val * n)
        idx = min(idx, n - 1)  # Clamp for floating point safety
        buckets[idx].append(x)

    # SORT: each bucket — Python's sort (Timsort) is efficient for small lists
    # For expected O(1) elements per bucket, this is O(1) per bucket
    for bucket in buckets:
        bucket.sort()  # In-place; Timsort is O(k log k) but fast for k ≈ 1

    # GATHER: O(n)
    return [x for bucket in buckets for x in bucket]


# --- Demo ---
if __name__ == "__main__":
    import random
    random.seed(42)

    # Uniform floats in [0, 1)
    data = [random.random() for _ in range(10)]
    print("Input: ", [f"{x:.3f}" for x in data])
    print("Sorted:", [f"{x:.3f}" for x in bucket_sort(data)])

    # General range: uniform floats in [5.0, 15.0]
    data2 = [random.uniform(5.0, 15.0) for _ in range(8)]
    print("\nInput: ", [f"{x:.3f}" for x in data2])
    print("Sorted:", [f"{x:.3f}" for x in bucket_sort(data2)])
```

## 7. Common Variations & Extensions

### 7.1 Adaptive Bucket Sort (Quantile-Based Buckets)

Instead of equal-width buckets, use equal-frequency buckets. Compute the k-quantiles of the data first (O(n log n)), then assign each element to its quantile bucket. This guarantees exactly n/k elements per bucket regardless of distribution — turning the expected O(n) of uniform bucket sort into a **guaranteed O(n log(n/k))** algorithm (the inner sort cost dominates).

This is what `KBinsDiscretizer(strategy='quantile')` does in scikit-learn. Connect to [[52.Quickselect — k-th smallest in expected O(n)]] for efficient quantile computation.

### 7.2 Two-Pass Bucket Sort (Radix-Style)

For higher precision: first bucket into coarse bins (e.g., 16 buckets), then recursively bucket each bin into sub-bins. This is the connection to [[50.Radix sort — digit-by-digit, O(d(n+k))]]. You can think of radix sort as bucket sort applied to one digit at a time — the "digit" is a coarse hash of the value.

### 7.3 Parallel Bucket Sort

Because buckets are independent after scatter, Steps 2 (sort each bucket) and 3 (gather) are embarrassingly parallel. Each bucket can be sorted on a separate thread/core. This is why histogram-based tree building in XGBoost uses this structure for GPU acceleration — the bucket computation maps directly to GPU parallelism.

### 7.4 External Bucket Sort (Large Datasets)

When data doesn't fit in RAM: scatter elements into bucket files on disk (one file per bucket range). Then sort each bucket file independently (it fits in RAM). Merge (gather) by reading bucket files in order. This is the basis of MapReduce sorting — the "Map" phase is the scatter, the "Reduce" phase is the per-bucket sort. Connect to [[220.Data pipeline design — streaming vs batch, shuffling, prefetching]].

## 9. CP Contest Application

### Typical Problem Structure

**Problem:** You are given n floating-point measurements from a sensor, guaranteed to be uniformly distributed in [0.0, 1000.0]. Sort them and find the maximum gap between consecutive elements.

**Why bucket sort wins here:** LeetCode 164 (Maximum Gap) has a brilliant O(n) solution. By pigeonhole, if you have n elements in a range of size R, the maximum gap must be at least R/(n-1). So create n-1 buckets of this minimum width. The maximum gap **cannot occur within a bucket** — it must occur between a non-empty bucket's max and the next non-empty bucket's min. You only need to track (min, max) per bucket, not sort within it. This is O(n) time and O(n) space, beating any comparison sort.

### Time Limits and When This Matters

- Standard CP time limits: 1-2 seconds for n = 10⁶
- Comparison sort (O(n log n)): ~20M operations for n = 10⁶ → borderline
- Bucket sort (O(n)): ~1M operations → comfortable margin
- Bucket sort becomes relevant when: n > 10⁶ with float data and tight time limits, or when the problem guarantees uniform distribution as part of the constraints

### Common Optimisation Tricks

1. **Precompute the bucket index as integer arithmetic:** Avoid division by using multiplication when possible. `idx = (int)((x - lo) * inv_range * n)` where `inv_range = 1.0 / (hi - lo)` is precomputed.
    
2. **Use arrays of pairs instead of vectors of vectors:** For cache efficiency, use a single pre-allocated array and an index array for bucket boundaries.
    
3. **Avoid dynamic allocation in the hot path:** Pre-allocate all bucket storage to avoid repeated heap allocations during scatter.
    
4. **For the Maximum Gap variant:** Don't sort within buckets at all — just track (bucket_min, bucket_max) with two arrays of size n. This halves memory and eliminates the inner sort entirely.
    

```cpp
// Maximum Gap — O(n) bucket trick (no inner sort needed)
int maximumGap(vector<int>& nums) {
    int n = nums.size();
    if (n < 2) return 0;
    int lo = *min_element(nums.begin(), nums.end());
    int hi = *max_element(nums.begin(), nums.end());
    if (lo == hi) return 0;

    // Bucket width: ceil((hi-lo) / (n-1))
    // Guarantees max gap spans at least one bucket boundary
    int bw = max(1, (hi - lo + n - 2) / (n - 1));
    int nb = (hi - lo) / bw + 1;

    vector<int> bmin(nb, INT_MAX), bmax(nb, INT_MIN);
    for (int x : nums) {
        int idx = (x - lo) / bw;
        bmin[idx] = min(bmin[idx], x);
        bmax[idx] = max(bmax[idx], x);
    }

    int ans = 0, prev_max = lo;
    for (int i = 0; i < nb; i++) {
        if (bmin[i] == INT_MAX) continue;  // Empty bucket
        ans = max(ans, bmin[i] - prev_max);
        prev_max = bmax[i];
    }
    return ans;
}
```
