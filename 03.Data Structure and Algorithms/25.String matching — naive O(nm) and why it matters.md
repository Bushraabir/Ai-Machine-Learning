## 1. Intuition First

### The Core Idea

You have a text of length n and a pattern of length m. You want to find every position in the text where the pattern occurs as a contiguous substring.

The naive algorithm is exactly what a careful human would do by hand: place the pattern under the text at position 0, compare character by character left to right. If every character matches, record the position. If any character mismatches, slide the pattern one position to the right and repeat. Do this for every starting position from 0 to n-m.

There is no cleverness here. No preprocessing. No data structures. Just two nested loops — the outer iterates over starting positions in the text, the inner compares characters of the pattern. That's the entire algorithm.

### Why This Exists — and Why O(nm) Is Worth Understanding

The naive algorithm is not a stepping stone you learn and discard. It is the **specification** against which every faster algorithm is verified. KMP (see [[26.KMP algorithm — failure function and O(n+m) matching]]), Rabin-Karp (see [[27.Rabin-Karp — rolling hash for pattern matching]]), and Z-algorithm (see [[28.Z-algorithm — prefix-suffix matching]]) are all optimisations of this exact procedure — they eliminate redundant comparisons that naive makes.

You cannot understand _why_ those algorithms are correct without first understanding _what_ naive does wrong. Specifically: after a partial match of length j followed by a mismatch, naive throws away all information about those j matched characters and restarts from scratch. KMP is the algorithm that refuses to throw that information away. You won't appreciate that until you've sat with the naive approach.

**When O(nm) is actually fine:** For most practical text processing, n and m satisfy nm ≤ 10⁷ comfortably. Searching a 10 KB file (n ≈ 10⁴) for a 100-character pattern (m = 100) is 10⁶ operations — negligible. The algorithm matters only when either n or m is large _and_ you're in a worst-case environment (which in practice means: binary files, repetitive DNA sequences, or adversarial contest inputs).

### The "Aha" Moment

The naive algorithm is a **fixed-size sliding window** (see [[11.Fixed-size sliding window — maximum, minimum, sum]]) of size m over the text, where at each window position you perform a comparison of window contents against the pattern. The inner loop is the comparison; the outer loop is the slide.

This framing matters because it reveals exactly what naive wastes: after finding a mismatch at position j inside the window, it slides by exactly 1 and restarts the inner loop from j=0. A smarter algorithm would slide by more than 1 when the structure of the pattern permits it. The amount you _can_ safely slide — without missing any matches — is what the failure function in KMP computes.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

Naive string matching appears in contests in three roles:

**Role 1 — The direct solution for small inputs.** Any problem with n, m ≤ 10³ where you need to count or find pattern occurrences. Using KMP here is correct but overkill. Naive is faster to implement and less likely to have off-by-one bugs under contest pressure.

**Role 2 — The fallback when the pattern is very short.** If m ≤ 10, even for large n = 10⁶, naive runs in 10⁷ operations. This is within a 1-second time limit. Recognising this threshold saves you from implementing KMP unnecessarily.

**Role 3 — The correctness reference.** In any contest problem requiring string matching, implement naive first, test it on small cases, then upgrade to KMP or Rabin-Karp if needed. A naive solution that passes sample cases gives you confidence the logic is right before you introduce complexity.

**The signal for when naive is insufficient:** The problem has n ≥ 10⁵ and m ≥ 10², or — critically — the worst case is a text of all `a`s and a pattern like `aaa...ab`. In that case, every window position triggers a near-complete match before failing on the last character, giving the true O(nm) worst case instead of the typical O(n) average case on natural text.

**Common trap:** In problems where you need to check if a pattern is a substring of a large text, beginners use `find()` in C++ or `in` in Python, not realising these can be O(nm) in the worst case for pathological inputs. C++'s `std::string::find` is not guaranteed to use a linear algorithm (it's implementation-dependent; libstdc++ uses a two-way algorithm but MSVC's may not). For contest problems with adversarial string inputs, always use an explicitly linear algorithm.

### Machine Learning / AI

**Tokenisation preprocessing — exact substring search:** Before BPE (Byte Pair Encoding) tokenisation in modern LLMs (see [[29.Trie (prefix tree) — insert, search, startsWith]]), vocabularies are built by finding and merging the most frequent adjacent byte pairs in the training corpus. The initial step — counting occurrences of every adjacent pair — is a naive O(nm) scan over the corpus. When the corpus is hundreds of gigabytes, this step is a genuine bottleneck, and systems like HuggingFace `tokenizers` parallelise it across CPU cores.

**Sequence alignment in bioinformatics / genomics ML:** The naive algorithm is the baseline for local sequence alignment. Smith-Waterman (dynamic programming) and BLAST (heuristic) are optimisations that exist because naive O(nm) alignment of a 150 bp read against a 3×10⁹ bp human genome takes far too long. Understanding why naive fails here — and exactly what it wastes — is how you understand why BLAST's seed-and-extend heuristic works.

**Pattern matching in data validation pipelines:** ML pipelines often include regex-based validation of inputs (email formats, date strings, URL patterns). Python's `re` module compiles patterns to a finite automaton — effectively a generalisation of KMP — rather than using naive matching. Knowing the cost model of naive string search helps you predict when a regex with backtracking will pathologically slow down on adversarial inputs (catastrophic backtracking), which is a real security vulnerability in web ML APIs accepting user-provided regex patterns.

**Approximate string matching / edit distance (see [[171.Edit distance (Levenshtein) — string alignment DP]]):** Naive exact matching is the O(1)-error special case of edit distance. Understanding the comparison loop in naive makes the DP table for Levenshtein distance easier to read — each cell in the table is exactly the comparison that naive makes at that (i, j) position.

## 3. Algorithm / Pattern

### Step-by-Step Logic

1. For each starting position `i` from `0` to `n - m` (inclusive): a. For each offset `j` from `0` to `m - 1`:
    - If `text[i + j] != pattern[j]`: break inner loop (mismatch).
    - If `j == m - 1`: record match at position `i` (all m characters matched).
2. Return all recorded positions.

**Valid starting positions:** The last valid start is `i = n - m`, because the pattern of length m needs characters `text[i]` through `text[i + m - 1]`, requiring `i + m - 1 ≤ n - 1`, i.e., `i ≤ n - m`. Starting at `i = n - m + 1` would mean reading past the end of the text.

### Complexity Analysis

**Time — worst case O(nm):**

The worst case occurs when every window position triggers a full inner-loop run of m comparisons before mismatch on the last character. The canonical example: `text = "aaa...a"` (n a's), `pattern = "aaa...ab"` (m-1 a's followed by b). At each of the (n - m + 1) starting positions, the inner loop runs m - 1 comparisons before the mismatch on `b`. Total: (n - m + 1)(m - 1) ≈ nm for m ≪ n.

**Time — average case on natural text: O(n)**

For natural language text with a moderate alphabet (26 letters), the expected number of comparisons per window position is bounded by a geometric series. The probability of matching j characters and then mismatching on the (j+1)-th is (1/σ)^j × (1 - 1/σ) where σ is the alphabet size. Expected comparisons per position: ∑_{j=0}^{∞} (j+1) × (1/σ)^j × (1 - 1/σ) = σ/(σ-1) ≈ 1 for large σ. For σ = 26, this is about 1.04 — nearly constant. So on natural English text, naive runs in O(n) expected time.

This is why naive works fine in practice for most text search applications.

**Space: O(1)** — no preprocessing, no auxiliary data structures. Just two index variables. This is the primary advantage over KMP (O(m) space for the failure function) and Rabin-Karp (O(1) but with hash state).

### When to Use vs. When to Avoid

**Use naive when:**

- n × m ≤ 10⁷ (guaranteed to finish within time limits).
- m is very short (m ≤ 10) even for large n.
- You need a quick, debuggable implementation with zero preprocessing overhead.
- The text is natural language or has a large alphabet (σ ≥ 10): average case is nearly O(n).

**Avoid naive when:**

- Text is binary or has a small alphabet (σ = 2 or 4), especially for DNA/protein sequences.
- Pattern is long and the text is highly repetitive (worst case is achievable).
- n ≥ 10⁵ and m ≥ 10² with no alphabet size guarantee.
- You need all occurrences counted, not just the first (worst case amplified by number of matches).

## 4. Pseudocode

```
FUNCTION naive_string_match(text, pattern):
    n ← length(text)
    m ← length(pattern)
    matches ← empty list

    IF m == 0:
        RETURN [0, 1, 2, ..., n]   // Convention: empty pattern matches everywhere

    IF m > n:
        RETURN []                  // Pattern longer than text: impossible

    FOR i FROM 0 TO n - m (inclusive):    // i = candidate start position in text
        j ← 0
        WHILE j < m AND text[i + j] == pattern[j]:
            j ← j + 1             // Characters match; advance within pattern

        IF j == m:
            APPEND i TO matches   // All m characters matched

    RETURN matches

END FUNCTION
```

**Why the inner loop exits on `j == m`:** After the while loop, either `j < m` (mismatch at position j) or `j == m` (all characters matched). The check `j == m` distinguishes success from failure without needing a separate boolean flag.

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <iostream>
#include <string>
#include <vector>
#include <cassert>

// Naive string matching — all occurrences of pattern in text.
// Time: O(nm) worst case, O(n) average on natural text.
// Space: O(1) auxiliary (output list excluded).
std::vector<int> naive_search(const std::string& text, const std::string& pattern) {
    std::vector<int> matches;
    const int n = static_cast<int>(text.size());
    const int m = static_cast<int>(pattern.size());

    if (m == 0) {
        // Convention: empty pattern matches at every position
        for (int i = 0; i <= n; ++i) matches.push_back(i);
        return matches;
    }

    // Valid starting positions: 0 through n-m inclusive
    for (int i = 0; i <= n - m; ++i) {
        int j = 0;
        while (j < m && text[i + j] == pattern[j]) {
            ++j;
        }
        if (j == m) {
            matches.push_back(i);
        }
    }

    return matches;
}

// Variant: return only the first occurrence, or -1 if not found.
// Equivalent to std::string::find but explicit about the algorithm.
int naive_find_first(const std::string& text, const std::string& pattern) {
    const int n = static_cast<int>(text.size());
    const int m = static_cast<int>(pattern.size());

    if (m == 0) return 0;

    for (int i = 0; i <= n - m; ++i) {
        int j = 0;
        while (j < m && text[i + j] == pattern[j]) ++j;
        if (j == m) return i;
    }

    return -1;  // not found
}

// Worst-case demonstration: count comparisons on adversarial input.
// text = "aaa...a" (n times), pattern = "aaa...ab" (m-1 a's + 'b')
// Returns total character comparisons made.
int naive_count_comparisons(const std::string& text, const std::string& pattern) {
    const int n = static_cast<int>(text.size());
    const int m = static_cast<int>(pattern.size());
    int comparisons = 0;

    for (int i = 0; i <= n - m; ++i) {
        int j = 0;
        while (j < m) {
            ++comparisons;
            if (text[i + j] != pattern[j]) break;
            ++j;
        }
    }

    return comparisons;
}

int main() {
    // Basic correctness
    assert(naive_search("abcabc", "abc") == (std::vector<int>{0, 3}));
    assert(naive_search("aaaaaa", "aaa") == (std::vector<int>{0, 1, 2, 3}));
    assert(naive_search("hello", "world") == std::vector<int>{});
    assert(naive_search("a", "a") == (std::vector<int>{0}));
    assert(naive_search("", "a") == std::vector<int>{});
    assert(naive_search("abc", "") == (std::vector<int>{0, 1, 2, 3}));

    // Overlapping matches
    assert(naive_search("aaaa", "aa") == (std::vector<int>{0, 1, 2}));

    // Case sensitivity
    assert(naive_search("Hello", "hello") == std::vector<int>{});

    // Worst-case comparison count
    // text = "aaaa" (n=5), pattern = "aab" (m=3)
    // Each of (5-3+1)=3 positions runs 3 comparisons before mismatch
    // Total: 3 × 3 = 9 — approaching nm = 5×3 = 15
    std::string worst_text(8, 'a');
    std::string worst_pat(4, 'a');
    worst_pat.back() = 'b';
    int comps = naive_count_comparisons(worst_text, worst_pat);
    // (8-4+1) × 4 = 5 × 4 = 20 comparisons in the worst case
    assert(comps == 20);

    std::cout << "All tests passed.\n";
    std::cout << "Worst-case comparisons for n=8, m=4: " << comps << " (nm=" << 8*4 << ")\n";
    return 0;
}
```

### Python (Readable + Pythonic)

```python
def naive_search(text: str, pattern: str) -> list[int]:
    """
    Naive string matching — find all starting positions of pattern in text.

    Time:  O(nm) worst case (repetitive text, long pattern)
            O(n)  average case (natural language, large alphabet)
    Space: O(1) auxiliary — no preprocessing required

    Example:
        >>> naive_search("abcabc", "abc")
        [0, 3]
        >>> naive_search("aaaaaa", "aaa")
        [0, 1, 2, 3]
        >>> naive_search("hello", "world")
        []
    """
    n, m = len(text), len(pattern)

    if m == 0:
        return list(range(n + 1))  # empty pattern matches at every position

    matches = []

    for i in range(n - m + 1):           # i: candidate start in text
        j = 0
        while j < m and text[i + j] == pattern[j]:
            j += 1                        # advance while characters agree
        if j == m:
            matches.append(i)             # full pattern matched

    return matches


def naive_find_first(text: str, pattern: str) -> int:
    """
    Return index of first occurrence of pattern in text, or -1 if not found.
    Explicit O(nm) version of str.find() — use for understanding, not production.

    Example:
        >>> naive_find_first("abcabc", "bc")
        1
        >>> naive_find_first("abc", "xyz")
        -1
    """
    n, m = len(text), len(pattern)
    if m == 0:
        return 0
    for i in range(n - m + 1):
        if all(text[i + j] == pattern[j] for j in range(m)):
            return i
    return -1


def count_comparisons(text: str, pattern: str) -> int:
    """
    Count the exact number of character comparisons naive makes.
    Useful for empirically demonstrating worst vs. average case.

    Example:
        >>> # Worst case: text="aaaa", pattern="aab"
        >>> count_comparisons("aaaa", "aab")
        6   # (4-3+1)=2 positions × 3 comparisons each
    """
    n, m = len(text), len(pattern)
    comps = 0
    for i in range(n - m + 1):
        for j in range(m):
            comps += 1
            if text[i + j] != pattern[j]:
                break
    return comps


# ── Why it matters: worst vs. average comparison count ────────────────────────

def comparison_experiment(n: int = 1000, m: int = 50) -> None:
    """
    Empirically compare comparison counts for:
    1. Worst case: text='aaa...a', pattern='aaa...ab'
    2. Average case: random English-like text
    """
    import random
    import string

    # Worst case
    worst_text = 'a' * n
    worst_pattern = 'a' * (m - 1) + 'b'
    worst_comps = count_comparisons(worst_text, worst_pattern)

    # Average case (random alphabetic text)
    avg_text = ''.join(random.choices(string.ascii_lowercase, k=n))
    avg_pattern = ''.join(random.choices(string.ascii_lowercase, k=m))
    avg_comps = count_comparisons(avg_text, avg_pattern)

    print(f"n={n}, m={m}, nm={n*m}")
    print(f"Worst case comparisons: {worst_comps}  ({worst_comps/(n*m):.2%} of nm)")
    print(f"Average case comparisons: {avg_comps}  ({avg_comps/n:.2f} per text char)")


# ── Tests ──────────────────────────────────────────────────────────────────────

if __name__ == "__main__":
    # Correctness
    assert naive_search("abcabc", "abc") == [0, 3]
    assert naive_search("aaaaaa", "aaa") == [0, 1, 2, 3]
    assert naive_search("hello", "world") == []
    assert naive_search("a", "a") == [0]
    assert naive_search("", "a") == []
    assert naive_search("abc", "") == [0, 1, 2, 3]
    assert naive_search("aaaa", "aa") == [0, 1, 2]       # overlapping matches

    # Single character pattern
    assert naive_search("abacaba", "a") == [0, 2, 4, 6]

    # Pattern equals text
    assert naive_search("abc", "abc") == [0]

    # Pattern longer than text
    assert naive_search("ab", "abc") == []

    # Agreement with Python built-in
    for text, pat in [("abcabc", "bc"), ("aababab", "ab"), ("mississippi", "issi")]:
        builtin = [i for i in range(len(text)) if text.startswith(pat, i)]
        assert naive_search(text, pat) == builtin

    # Worst-case comparison count
    assert count_comparisons("aaaa", "aab") == 6   # 2 positions × 3 each

    comparison_experiment()
    print("All tests passed.")
```

## 6. Visual Explanation

### Sliding the Pattern Window

```
text:     a b a c a b a b
pattern:  a b a b
          ↑ start at i=0

i=0:  a b a c a b a b
      a b a b
          ✗ mismatch at j=3 (text[3]='c', pattern[3]='b')
          → slide by 1

i=1:  a b a c a b a b
        a b a b
        ✗ mismatch at j=0 (text[1]='b', pattern[0]='a')
          → slide by 1

i=2:  a b a c a b a b
          a b a b
            ✗ mismatch at j=1 (text[3]='c', pattern[1]='b')
          → slide by 1

i=3:  a b a c a b a b
            a b a b
            ✗ mismatch at j=0 (text[3]='c', pattern[0]='a')
          → slide by 1

i=4:  a b a c a b a b
                a b a b
                ✓ ✓ ✓ ✓  all 4 match → MATCH at position 4

Result: [4]
```

### The Worst Case — Where O(nm) Bites

```
text:     a a a a a a a a   (n=8)
pattern:  a a a b           (m=4)

i=0:  a a a a a a a a
      a a a b
            ✗  — 4 comparisons before mismatch

i=1:  a a a a a a a a
        a a a b
              ✗  — 4 comparisons before mismatch

i=2:  a a a a a a a a
          a a a b
                ✗  — 4 comparisons before mismatch

i=3:  a a a a a a a a
            a a a b
                  ✗  — 4 comparisons before mismatch

i=4:  a a a a a a a a
              a a a b
                    ✗  — 4 comparisons before mismatch

(5 positions × 4 comparisons = 20 total ≈ nm = 32)

Each time: the inner loop runs almost to the end of the pattern
before discovering the mismatch. All information about the matched
a's is thrown away and the next window starts from scratch.

KMP's insight: after matching "aaa" and failing on "b",
it knows the next window can start at i=1 (the second 'a')
already having matched 2 characters — no restart from zero.
```

### Average Case on Natural Text

```
text:     t h e   q u i c k   b r o w n   f o x
pattern:  f o x

i=0:  t h e ...
      f o x
      ✗   — 1 comparison (t≠f). Slide.

i=1:  h e   ...
      f o x
      ✗   — 1 comparison (h≠f). Slide.

...most positions fail on the FIRST character.

i=16: f o x
      f o x
      ✓ ✓ ✓  — match at position 16

For a 26-letter alphabet, the probability of matching
the first character is 1/26. Expected comparisons per window ≈ 1.04.
For n=1000, m=3: expected ~1040 comparisons vs. nm=3000.
This is why naive works fine in practice.
```

## 7. Common Variations & Extensions

### Variation 1: Case-Insensitive Matching

Normalise both text and pattern to lowercase before matching, or compare `tolower(text[i+j]) == tolower(pattern[j])` in the inner loop. The algorithm is identical; only the comparison changes. Cost: one extra function call per character comparison — negligible.

### Variation 2: Matching with a Wildcard Character

If the pattern can contain a wildcard `?` that matches any single character, change the inner-loop condition to:

```python
while j < m and (pattern[j] == '?' or text[i + j] == pattern[j]):
    j += 1
```

This still runs in O(nm) and requires no algorithmic change. Full wildcard matching with `*` (matching zero or more characters) requires dynamic programming (see [[171.Edit distance (Levenshtein) — string alignment DP]]) or a different approach entirely.

### Variation 3: Count Occurrences Without Collecting Positions

If you only need the count (not the positions), replace `matches.append(i)` with `count += 1`. Same algorithm, O(1) space for the output.

### Variation 4: Checking Substring Existence Only

If you only need a boolean answer ("does pattern appear in text?"), return `True` on the first match and `False` after exhausting all windows. This is what Python's `in` operator does for strings — it is essentially naive search (CPython's implementation uses a simplified two-way algorithm, but on small inputs it behaves like naive).

### Variation 5: Multi-Pattern Naive Search

To find occurrences of p patterns simultaneously using naive, run the algorithm once per pattern: O(p × nm) total. For p patterns of combined length M, Aho-Corasick runs in O(n + M + output size) — the trie-based automaton generalisation of KMP to multiple patterns. Naive multi-pattern search is the baseline that motivates Aho-Corasick exactly as single-pattern naive motivates KMP.

## 9. CP Contest Application

### When Naive Is the Intended Solution

**Codeforces Div. 3 / Div. 4, Educational rounds:** Problems with explicit constraints n, m ≤ 10³ or n × m ≤ 10⁶ are designed for naive. Implementing KMP here wastes implementation time and introduces more bug surface.

**Small pattern guarantee:** Any problem stating "the pattern length is at most 10" or "the alphabet is large (all printable ASCII)" — naive runs effectively in O(n) on average. Use it.

### When to Upgrade to Linear Algorithms

The threshold in contest practice: if n × m > 10⁷ or if the problem involves a binary/DNA alphabet with a repetitive text, upgrade to:

- **KMP** (see [[26.KMP algorithm — failure function and O(n+m) matching]]) — deterministic O(n+m), O(m) space, handles the worst case.
- **Rabin-Karp** (see [[27.Rabin-Karp — rolling hash for pattern matching]]) — randomised O(n+m) expected, O(1) space, easier to implement for multiple pattern lengths simultaneously.
- **Z-algorithm** (see [[28.Z-algorithm — prefix-suffix matching]]) — deterministic O(n+m), conceptually different from KMP but equivalent power.

### Recognising the Worst Case in Contest Problems

If the problem provides a test case generator or describes input as "all same characters," you are looking at a worst-case scenario for naive. The typical adversarial construction is:

```
text    = "a" × n
pattern = "a" × (m-1) + "b"
```

This forces (n - m + 1) × m comparisons — the true O(nm) case. If n = 10⁵ and m = 10³, that's 10⁸ comparisons — TLE at 1 second. The solution is KMP or Z-algorithm.

### A Note on `std::string::find` in C++

The C++ standard does not specify the algorithm used by `std::string::find`. In practice:

- **libstdc++ (GCC):** Uses a two-way string-matching algorithm, O(n + m) worst case.
- **libc++ (Clang/LLVM):** Similar guarantees.
- **MSVC:** Historically used naive O(nm) for `std::string::find`.

For Codeforces (typically GCC), `std::string::find` is safe. For portability and clarity, implementing naive explicitly or using KMP is always more defensible in competitive programming.
