## 1. Intuition First

### The Core Idea

Every time you write a recursive function, you are using a stack. You are just not the one managing it — the operating system and language runtime are doing it for you, invisibly. This is the deepest insight about recursion: **it is not a magical self-referential computation. It is an iterative computation over a stack that someone else allocated.**

Think of a dinner party where each guest hands their unfinished plate to the next guest to continue, then waits. The last guest finishes first, hands back the plate, then the second-to-last continues, and so on. The _order of return_ is the reverse of the _order of calling_. That "waiting line" is a stack — Last In, First Out. When you call a recursive function, the current function's state (local variables, return address, where it was in its computation) gets pushed onto a **call stack frame**. When the callee returns, that frame is popped and the caller resumes exactly where it paused.

Understanding this mechanically means you can always convert a recursive solution to an iterative one. The two programs are not different in kind — they are the same computation over the same stack, with the only difference being who allocated the stack memory and how the frames are structured.

### Why This Exists

The naive view of recursion treats it as a mathematical definition that "just works." This fails you in three ways:

1. **Stack overflow**: Python's default recursion limit is 1000 frames. A tree with depth 10⁵ will crash. If you understand the call stack, you understand why, and you know the fix (explicit stack, or increase the limit with `sys.setrecursionlimit`).
2. **Complexity analysis**: Recursive algorithms confuse students who can't see the total work. If you can see the call stack's height and width (the recursion tree), you can derive time and space complexity mechanically.
3. **Debugging**: Stack traces are a literal printout of the call stack at crash time. Reading them fluently — knowing that the bottom frame is `main` and the top frame is where the crash occurred — is a professional skill that comes directly from understanding the call stack.

### The "Aha" Moment

**Every recursive call is a push. Every return is a pop.** The base case is the point where the stack stops growing and begins to shrink. The "pending work" that accumulates on the way down the recursion (all the half-finished computations waiting for their child calls to return) is precisely the stack. When you write an iterative version, all you are doing is making that pending work explicit by maintaining your own stack data structure instead of relying on the language runtime's.

Once you see this, you can read any recursive function and immediately know:

- Its space complexity = the maximum depth of the call stack = O(depth of recursion tree).
- Converting it iteratively = replace recursive calls with `stack.push()`, base cases with loop termination, and returns with result propagation.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**When it appears:**

- Every DFS on a tree or graph uses the call stack implicitly. For trees of depth up to 10⁵, recursive DFS will overflow Python (limit ~1000) and may be borderline in C++ (default stack ~1–8 MB, each frame ~hundreds of bytes).
- Problems that ask for "iterative" DFS or BFS explicitly require you to manage your own stack.
- Backtracking and recursion-heavy DP memoisation: stack overflow is the silent killer when recursion depth exceeds limits.

**Pattern signal:**

> "When your recursive DFS crashes with `RecursionError` in Python, or you get a segfault in C++ on deep trees, the call stack overflowed. The fix is either: (a) raise the limit in Python, (b) rewrite iteratively with an explicit stack, or (c) convert the tree problem to a BFS."

**Common traps:**

1. **Python's 1000-frame default**: Any DFS on a tree with n = 10⁵ nodes and skewed structure (e.g., a linked-list-shaped tree) will crash. Always add `sys.setrecursionlimit(200_000)` at the top of competitive Python submissions, or rewrite iteratively.
2. **C++ stack size**: The OS gives each thread a stack (typically 1–8 MB). Each frame holds local variables, the return address, and saved registers. A recursive DFS with 6–8 local variables on a chain of 10⁵ nodes can use ~8 MB and segfault. The fix: `ulimit -s unlimited` on the judge, or iterative DFS.
3. **Forgetting the return value when rewriting iteratively**: The trickiest part of converting recursion to iteration is propagating results back up. You need to simulate the "return" step explicitly.

### Machine Learning / AI

**Autograd and Backpropagation:**  
The most important instance of "recursion as a stack" in ML is **backpropagation**. The forward pass builds up a computation graph (a DAG). The backward pass traverses it in reverse topological order — which is exactly what the call stack does during a postorder DFS. PyTorch's `autograd` engine maintains an explicit gradient tape (a list of operations in execution order) and replays it in reverse. This is the "iterative with explicit stack" pattern applied to the computation graph. See [[215.Gradient computation as a graph traversal — autograd intuition]].

**TensorFlow's `tf.function` and XLA compilation:**  
When you decorate a Python function with `@tf.function`, TensorFlow traces through the Python call stack once, recording the operations into a computation graph. Python's recursion (if any) is unrolled at trace time. The resulting graph is a flat, stack-free representation of what was recursive Python code. This is the compiler's version of "convert recursion to explicit representation."

**Recursive Neural Networks and Tree-LSTMs:**  
Tree-LSTM (Tai et al., 2015) processes tree-structured data by recursively composing child representations into parent representations — exactly the postorder DFS of a tree, using the call stack. In practice, implementations convert this to an iterative BFS/DFS over the tree structure with explicit state management, because deep trees overflow Python's stack and because batching recursive calls is hard.

**Recursive Model Architectures:**  
Recursive neural networks (not recurrent — recursive) apply the same weight matrix at each node of a parse tree. The gradient computation through them is a literal recursive call through the tree structure, handled by autograd's implicit stack (the gradient tape). Understanding that autograd IS a stack-based postorder traversal tells you exactly why very deep parse trees cause memory issues in these models.

## 3. Algorithm / Pattern

### What a Stack Frame Contains

When a function is called, the runtime pushes a **stack frame** (also called an activation record) containing:

```
┌─────────────────────────────────────┐
│  Return address                     │  ← where to resume in the caller
│  Caller's frame pointer             │  ← to restore the caller's frame
│  Local variables                    │  ← all variables declared in this call
│  Parameters                         │  ← copies of arguments passed in
│  Saved registers                    │  ← registers the callee must preserve
└─────────────────────────────────────┘
```

**Space per frame:** Proportional to the number of local variables. A function with 5 integer locals uses roughly 5 × 8 = 40 bytes of stack space per call, plus ~16 bytes of overhead. At depth 10⁵, that's ~5.6 MB — close to the default limit.

### Recursion Depth and Space Complexity

The **maximum call stack depth** at any point = space complexity of the recursion.

|Algorithm|Recursion depth|Space complexity|
|---|---|---|
|Binary search (recursive)|O(log n)|O(log n)|
|Merge sort|O(log n)|O(log n) recursion + O(n) merge buffers|
|DFS on balanced BST|O(log n)|O(log n)|
|DFS on skewed tree (linked list)|O(n)|O(n)|
|Naive Fibonacci|O(n)|O(n) — depth of the leftmost branch|
|Backtracking (n-queens)|O(n)|O(n)|

### Converting Recursion to Iteration: The General Template

Every recursive function that does work **before** and/or **after** the recursive call can be converted. The challenge is the "after" part — work that happens after the child call returns, which in the iterative version must be deferred until the child's result is available.

**Three patterns of recursive work:**

```
Pattern 1 — Tail recursion (work done BEFORE the call):
    f(x):
        do_work(x)
        return f(next(x))     ← last action is the recursive call
    → Trivially iterative: replace with a while loop

Pattern 2 — Head recursion (work done AFTER the call):
    f(x):
        result = f(next(x))   ← call first
        return combine(result, x)
    → Needs explicit stack to defer the "combine" step

Pattern 3 — Mixed (work before AND after):
    f(x):
        preprocess(x)
        result = f(next(x))
        return postprocess(result, x)
    → Needs explicit stack with a "phase" flag (CALL vs RETURN phase)
```

### The Two-Phase Iterative Template (for Pattern 3)

```
stack = [(CALL, root)]
results = {}

while stack:
    phase, node = stack.pop()

    if phase == CALL:
        if is_base_case(node):
            results[node] = base_value(node)
        else:
            # Push the RETURN phase first (it will execute after children)
            stack.append((RETURN, node))
            # Then push children (they execute first, being on top)
            for child in children(node):
                stack.append((CALL, child))

    elif phase == RETURN:
        # All children have been processed; their results are in results[]
        results[node] = combine(node, [results[c] for c in children(node)])
```

This pattern simulates the call stack exactly. `CALL` corresponds to "entering the function body." `RETURN` corresponds to "resuming after the recursive call returned."

### Time and Space Complexity

**Time:** Converting recursion to iteration does not change the time complexity. The same nodes are visited, the same work is done.

**Space:** Iterative conversion uses explicit heap-allocated stack space instead of the limited OS stack space. This avoids stack overflow, though the total memory used is the same O(depth) in the worst case.

## 4. Pseudocode

```
── RECURSIVE DFS (implicit call stack) ──────────────────────────────────────

FUNCTION dfs_recursive(node):
    IF node is None:
        RETURN 0                        ← base case: stack stops growing here

    left_val  = dfs_recursive(node.left)   ← PUSH frame, descend left
    right_val = dfs_recursive(node.right)  ← PUSH frame, descend right

    RETURN combine(node.val, left_val, right_val)   ← POP, return to parent
    # At any point, call stack depth = current depth in the tree


── ITERATIVE DFS (explicit stack, two-phase) ────────────────────────────────

FUNCTION dfs_iterative(root):
    IF root is None: RETURN 0

    stack   = [(CALL, root)]            ← explicit stack replaces call stack
    results = empty HashMap             ← replaces "return value" mechanism

    WHILE stack is not empty:
        phase, node = stack.pop()

        IF phase == CALL:
            IF node is None:
                results[node] = 0       ← base case
            ELSE:
                stack.push((RETURN, node))      ← deferred: run after children
                stack.push((CALL, node.right))  ← right child (runs after left)
                stack.push((CALL, node.left))   ← left child (runs first)

        ELIF phase == RETURN:
            left_val  = results[node.left]
            right_val = results[node.right]
            results[node] = combine(node.val, left_val, right_val)

    RETURN results[root]


── TAIL RECURSION → SIMPLE WHILE LOOP ───────────────────────────────────────

# Recursive:
FUNCTION factorial_tail(n, acc=1):
    IF n == 0: RETURN acc
    RETURN factorial_tail(n - 1, acc * n)   ← tail call

# Iterative (trivial conversion — no stack needed):
FUNCTION factorial_iter(n):
    acc = 1
    WHILE n > 0:
        acc = acc * n
        n   = n - 1
    RETURN acc
```

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <bits/stdc++.h>
using namespace std;

// ─────────────────────────────────────────────────────────────────────────────
// Binary tree node
// ─────────────────────────────────────────────────────────────────────────────
struct TreeNode {
    int val;
    TreeNode* left;
    TreeNode* right;
    TreeNode(int v, TreeNode* l = nullptr, TreeNode* r = nullptr)
        : val(v), left(l), right(r) {}
};

// ─────────────────────────────────────────────────────────────────────────────
// Example: Tree height — recursive (implicit call stack)
// Space: O(h) where h = height of tree (call stack depth)
// ─────────────────────────────────────────────────────────────────────────────
int height_recursive(TreeNode* node) {
    if (!node) return 0;  // base case: pops this frame immediately
    int left  = height_recursive(node->left);   // push frame → go left
    int right = height_recursive(node->right);  // push frame → go right
    return 1 + max(left, right);               // combine, pop frame
}

// ─────────────────────────────────────────────────────────────────────────────
// Example: Tree height — iterative with explicit stack (two-phase)
// Functionally identical to the recursive version.
// Space: O(h) — same asymptotically, but uses HEAP memory (no stack overflow)
// ─────────────────────────────────────────────────────────────────────────────
int height_iterative(TreeNode* root) {
    if (!root) return 0;

    // Each stack entry: (phase, node)
    // Phase 0 = CALL (first visit), Phase 1 = RETURN (children done)
    enum Phase { CALL, RETURN };
    stack<pair<Phase, TreeNode*>> stk;
    unordered_map<TreeNode*, int> heights;

    stk.push({CALL, root});

    while (!stk.empty()) {
        auto [phase, node] = stk.top(); stk.pop();

        if (phase == CALL) {
            if (!node) {
                heights[node] = 0;  // null node has height 0
            } else {
                stk.push({RETURN, node});         // deferred: run after children
                stk.push({CALL, node->right});    // right child
                stk.push({CALL, node->left});     // left child (processed first)
            }
        } else {  // RETURN phase
            int left  = heights[node->left];
            int right = heights[node->right];
            heights[node] = 1 + max(left, right);
        }
    }

    return heights[root];
}

// ─────────────────────────────────────────────────────────────────────────────
// Iterative inorder traversal — the "classic" explicit-stack pattern
// Push node, go left; when left is exhausted, visit, go right.
// Space: O(h)
// ─────────────────────────────────────────────────────────────────────────────
vector<int> inorder_iterative(TreeNode* root) {
    vector<int> result;
    stack<TreeNode*> stk;
    TreeNode* curr = root;

    while (curr || !stk.empty()) {
        // Descend all the way left (equivalent to the recursive dive)
        while (curr) {
            stk.push(curr);   // ← "call" to left subtree pending
            curr = curr->left;
        }
        // Left subtree exhausted — "return" from innermost call
        curr = stk.top(); stk.pop();
        result.push_back(curr->val);   // visit node (this is the "work after left")
        curr = curr->right;            // then go right
    }
    return result;
}

// ─────────────────────────────────────────────────────────────────────────────
// Simulating the call stack to understand stack overflow:
// How many recursive calls before crash on a skewed tree?
// This function counts frames until stack depth D is reached.
// ─────────────────────────────────────────────────────────────────────────────
int depth_counter = 0;
int max_safe_depth(int n) {
    if (n == 0) return 0;
    depth_counter++;
    return 1 + max_safe_depth(n - 1);  // linear recursion: depth = n
}

// ─────────────────────────────────────────────────────────────────────────────
// Tail-recursive factorial — compiler can optimise to iteration in C++
// (With -O2, GCC/Clang convert tail calls to jumps in C++)
// ─────────────────────────────────────────────────────────────────────────────
long long factorial_tail(int n, long long acc = 1) {
    if (n <= 1) return acc;
    return factorial_tail(n - 1, acc * n);  // tail position: last action
}

// ─────────────────────────────────────────────────────────────────────────────
// Test
// ─────────────────────────────────────────────────────────────────────────────
int main() {
    //   Build tree:       1
    //                    / \
    //                   2   3
    //                  / \
    //                 4   5
    TreeNode* root = new TreeNode(1,
        new TreeNode(2,
            new TreeNode(4),
            new TreeNode(5)),
        new TreeNode(3));

    cout << "Recursive height:  " << height_recursive(root) << "\n";  // 3
    cout << "Iterative height:  " << height_iterative(root) << "\n";  // 3

    auto inorder = inorder_iterative(root);
    cout << "Inorder: ";
    for (int v : inorder) cout << v << " ";  // 4 2 5 1 3
    cout << "\n";

    cout << "factorial_tail(10) = " << factorial_tail(10) << "\n";  // 3628800

    return 0;
}
```

### Python (Readable + Pythonic)

```python
from __future__ import annotations
import sys
from dataclasses import dataclass, field
from enum import Enum, auto
from typing import Optional

# ─────────────────────────────────────────────────────────────────────────────
# IMPORTANT for CP: always set this at the top of Python submissions
# that use recursive DFS on graphs or trees.
# ─────────────────────────────────────────────────────────────────────────────
sys.setrecursionlimit(200_000)


@dataclass
class TreeNode:
    val: int
    left: Optional[TreeNode] = None
    right: Optional[TreeNode] = None


# ─────────────────────────────────────────────────────────────────────────────
# Tree height — recursive (uses Python call stack implicitly)
# Each call pushes a frame: {val, left, right, local vars left_h, right_h}
# Crashes on trees of depth > ~990 without setrecursionlimit
# ─────────────────────────────────────────────────────────────────────────────
def height_recursive(node: Optional[TreeNode]) -> int:
    """
    Implicit stack version. Clean but limited by Python's stack depth.
    Space: O(h) — h frames on the call stack simultaneously.
    """
    if node is None:
        return 0                         # base case: pop this frame
    left_h  = height_recursive(node.left)   # push → descend left
    right_h = height_recursive(node.right)  # push → descend right
    return 1 + max(left_h, right_h)         # combine, pop


# ─────────────────────────────────────────────────────────────────────────────
# Tree height — iterative, two-phase explicit stack
# This is the mechanical translation of the recursive version.
# Works on trees of any depth. No stack overflow risk.
# ─────────────────────────────────────────────────────────────────────────────
class Phase(Enum):
    CALL   = auto()
    RETURN = auto()

def height_iterative(root: Optional[TreeNode]) -> int:
    """
    Explicit stack version. Mechanically equivalent to height_recursive.

    The key insight: push (RETURN, node) BEFORE pushing children.
    Since it's a LIFO stack, children execute first, RETURN runs last.
    This mimics the call stack's postorder execution.

    Space: O(h) — same asymptotically, but on the HEAP (safe for deep trees).
    """
    if root is None:
        return 0

    stack: list[tuple[Phase, Optional[TreeNode]]] = [(Phase.CALL, root)]
    heights: dict[Optional[TreeNode], int] = {None: 0}  # base case pre-loaded

    while stack:
        phase, node = stack.pop()

        if phase == Phase.CALL:
            if node is None:
                pass  # heights[None] = 0 already set
            else:
                # Deferred: run AFTER both children are processed
                stack.append((Phase.RETURN, node))
                # Push right first (so left is processed first — LIFO)
                stack.append((Phase.CALL, node.right))
                stack.append((Phase.CALL, node.left))

        else:  # RETURN phase — children are done
            heights[node] = 1 + max(heights[node.left], heights[node.right])

    return heights[root]


# ─────────────────────────────────────────────────────────────────────────────
# Iterative inorder traversal — the "classic" single-pointer pattern
# Simulates the call stack without needing the two-phase approach,
# because inorder's left-visit-right structure maps cleanly to
# "push node, go left; when stuck, visit, go right".
# ─────────────────────────────────────────────────────────────────────────────
def inorder_iterative(root: Optional[TreeNode]) -> list[int]:
    """
    Iterative inorder traversal.

    Mental model: the stack holds "nodes whose left subtrees we've fully
    descended into but haven't visited yet." Popping = visiting + going right.

    Time: O(n)   Space: O(h)
    """
    result: list[int] = []
    stack:  list[TreeNode] = []
    curr = root

    while curr or stack:
        # Descend left — equivalent to the recursive dive into the left subtree
        while curr:
            stack.append(curr)  # "pending: visit this node after its left subtree"
            curr = curr.left

        # Left exhausted: visit the node (this is the "after left call returns" work)
        curr = stack.pop()
        result.append(curr.val)

        # Then process right subtree (equivalent to the recursive right call)
        curr = curr.right

    return result


# ─────────────────────────────────────────────────────────────────────────────
# Demonstration: what a stack frame contains
# Python's inspect module lets us observe the call stack live
# ─────────────────────────────────────────────────────────────────────────────
import inspect

def demonstrate_call_stack(n: int) -> int:
    """Recursively counts down, printing the call stack depth at each level."""
    frame = inspect.currentframe()
    depth = 0
    f = frame
    while f is not None:
        depth += 1
        f = f.f_back
    print(f"  n={n}: call stack depth = {depth}, "
          f"local vars in this frame = {list(frame.f_locals.keys())}")
    if n == 0:
        return 0
    return 1 + demonstrate_call_stack(n - 1)


# ─────────────────────────────────────────────────────────────────────────────
# Tail recursion in Python — NOT optimised (CPython limitation)
# Both versions below build O(n) stack frames in Python.
# In C++ with -O2, the tail-recursive version compiles to a loop.
# ─────────────────────────────────────────────────────────────────────────────
def factorial_tail_recursive(n: int, acc: int = 1) -> int:
    """
    Tail-recursive factorial.
    Python does NOT optimise tail calls — this still uses O(n) stack frames.
    Use factorial_iterative for any n > ~900 in Python.
    """
    if n <= 1:
        return acc
    return factorial_tail_recursive(n - 1, acc * n)  # tail position

def factorial_iterative(n: int) -> int:
    """The loop Python should (but doesn't) compile the above to."""
    acc = 1
    while n > 1:
        acc *= n
        n   -= 1
    return acc


# ─────────────────────────────────────────────────────────────────────────────
# Test
# ─────────────────────────────────────────────────────────────────────────────
if __name__ == "__main__":
    #   Tree:     1
    #            / \
    #           2   3
    #          / \
    #         4   5
    root = TreeNode(1,
        TreeNode(2, TreeNode(4), TreeNode(5)),
        TreeNode(3))

    print(f"Recursive height:  {height_recursive(root)}")   # 3
    print(f"Iterative height:  {height_iterative(root)}")   # 3
    print(f"Inorder iterative: {inorder_iterative(root)}")  # [4, 2, 5, 1, 3]

    print(f"\nfactorial_tail(10) = {factorial_tail_recursive(10)}")  # 3628800
    print(f"factorial_iter(10) = {factorial_iterative(10)}")         # 3628800

    print("\n── Call stack observation ──")
    demonstrate_call_stack(3)
    # Shows increasing call stack depth and local variables at each frame
```

## 7. Common Variations & Extensions

### 7.1 Iterative Preorder and Postorder Traversals

Inorder's clean "descend-left, visit, go-right" pattern doesn't generalise directly. Preorder (visit, left, right) uses a simple loop: push right then left, pop and visit. Postorder (left, right, visit) is trickiest: it requires either the two-phase approach above, or a two-stack trick (push to output stack instead of visiting, then reverse). These traversals appear constantly in compiler construction and expression tree evaluation. See [[85.Evaluating expressions — infix to postfix, postfix evaluation]].

### 7.2 DFS on General Graphs (Not Just Trees)

Graph DFS needs a `visited` set to avoid infinite loops (trees have no cycles). The iterative version pushes neighbours; the two-phase technique applies when you need postorder actions (e.g., computing finish times for topological sort or SCC). See [[112.Depth-First Search (DFS) — recursive and iterative]].

### 7.3 Memoisation = Caching Return Values by Frame Identity

Top-down DP memoises recursive calls using a hashmap keyed on the function arguments. This is equivalent to caching by (function, frame arguments) — exactly the information in a stack frame. When you call `f(n)` and it's already in the memo, you skip pushing a new frame and return the cached result instantly. See [[70.Memoisation — converting naive recursion to top-down DP]].

### 7.4 Continuation-Passing Style (CPS)

Advanced compilers transform recursive functions into **continuation-passing style** (CPS), where instead of returning a value, each function calls a "continuation" function with the result. CPS makes the implicit control flow (the call stack) explicit as first-class function arguments. This is the theoretical foundation behind how PyTorch's autograd transforms a forward computation into a backward one — each operation registers a "backward continuation" that gets called when gradients flow through. See [[215.Gradient computation as a graph traversal — autograd intuition]].

## 9. CP Contest Application

### Typical Problem Structures

**Pattern 1 — Deep tree with recursive DFS (Python TLE/RE risk):**  
Given a tree with up to 10⁵ nodes, compute some subtree aggregate (sum, max, count). Recursive DFS is the natural solution; the iterative two-phase version is the safe CP solution. In C++, recursion is fine for balanced trees but risks segfault on skewed inputs.

**Pattern 2 — "Convert recursion to iteration" as the problem:**  
Explicit stack simulation is tested in problems like LC 341 (Flatten Nested List Iterator) — the iterator must lazily simulate a recursive traversal without actually calling recursion.

**Pattern 3 — Stack overflow as a subtlety:**  
CF problems with constraints like n ≤ 5×10⁵ and tree-structure input are implicitly testing whether you handle deep recursion. Any solution that recurses to depth n on a line graph (chain) will fail. The fix is always: iterative DFS with an explicit stack.

### C++ Stack Size Tricks for CP

```cpp
// Method 1: Increase stack size via a thread with custom stack (Linux/CF judges)
#include <bits/stdc++.h>
using namespace std;

void solve() {
    // your actual solution here
}

int main() {
    // Run solve() in a thread with 256 MB stack
    const size_t STACK_SIZE = 256 * 1024 * 1024;
    char* stack_mem = new char[STACK_SIZE];
    // (Platform-specific; usually just write iterative DFS instead)
    solve();
    return 0;
}

// Method 2: Simply rewrite the DFS iteratively (always the cleanest solution)
// Use the two-phase (CALL/RETURN) pattern above.

// Method 3: For tail-recursive DFS (e.g., simple graph traversal),
// the compiler's -O2 flag often handles tail-call optimisation automatically.
```

### Timing Context

- Recursive DFS at depth 10⁵ in Python: crashes (RecursionError) without `sys.setrecursionlimit`.
- Recursive DFS at depth 10⁵ in C++ (debug build): may segfault (default stack ~1–8 MB).
- Recursive DFS at depth 10⁵ in C++ (release, small frames): usually fine (~a few MB).
- Iterative DFS with explicit stack: safe at any depth on any judge (heap memory, typically GBs available).

**Rule of thumb:** In competitive Python, always prefer iterative DFS for trees/graphs with n > 1000. In C++, prefer iterative when the tree could be a chain (skewed input is a common adversarial test case).
