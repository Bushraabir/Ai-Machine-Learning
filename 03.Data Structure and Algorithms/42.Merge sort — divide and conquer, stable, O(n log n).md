## 1. Intuition First

### The Core Idea

You have a stack of 1,000 exam papers to sort by student ID. Sorting the full stack directly is overwhelming. But here is a procedure that always works:

Split the stack in half. Hand one half to a colleague and sort the other half yourself. When you both finish, you each have a sorted stack. Now merge the two sorted stacks into one: repeatedly take the smaller top card from either stack and place it face-down. One pass through both stacks, and you're done.

Of course your colleague applies the same trick — splits their half, delegates, merges. And so does their delegate. This recursion bottoms out when each sub-stack has one paper (trivially sorted). The whole procedure is merge sort.

The algorithm has two phases that are conceptually opposite in difficulty:

**Divide:** Trivially split the array at the midpoint. No comparisons, no work. Just find `mid = (left + right) / 2`. This costs O(1) per level.

**Conquer (Merge):** Given two sorted halves, produce one sorted whole. Walk two pointers — one per half — always picking the smaller front element. This costs O(n) per level.

The insight: **splitting is free; merging is where all the real work happens.** And merging two sorted arrays is the simplest possible O(n) operation — just compare front elements and advance.

### Why This Exists — The Complexity Gap

Insertion sort is O(n²) because each element potentially travels across the entire sorted prefix. Merge sort eliminates this by never moving an element more than O(log n) times. An element participates in exactly one merge at each level of the recursion tree, and there are log n levels. Each merge costs O(n) total across all merges at that level. Total: O(n log n).

This is not merely better in practice — it is **provably optimal** for comparison-based sorting. Any algorithm that sorts by comparing elements must make at least Ω(n log n) comparisons in the worst case (information-theoretic argument: there are n! possible orderings, and each comparison halves the remaining possibilities, so you need at least log₂(n!) ≈ n log n comparisons). Merge sort achieves this lower bound.

### The "Aha" Moment

The merge step is the entire algorithm. Everything else — the recursion, the divide — exists only to create two sorted halves for merge to consume. Once you deeply understand how to merge two sorted arrays in O(n), the rest is scaffolding.

And merging has a beautiful property: it is **stable** by construction. When two elements are equal, you always take from the _left_ array first (since the left array comes earlier in the original). This preserves relative order without any extra bookkeeping — stability is free in merge sort, while it requires care in quicksort and heapsort.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**When it appears:**

Merge sort in CP is almost never used _just_ to sort — `std::sort` handles that. Its CP value lies in three patterns where the merge structure itself is the solution:

1. **Counting inversions.** The number of swaps an adjacent-swap sort performs equals the number of inversions — pairs (i, j) with i < j but A[i] > A[j]. Merge sort counts these for free: during the merge step, every time you take an element from the _right_ half before all remaining elements from the _left_ half, each of those remaining left elements forms an inversion with the right element. This gives an O(n log n) inversion counter with zero extra space beyond the merge buffer. This is the intended solution for LC 315, 493, 775 and Codeforces problems asking for "minimum adjacent swaps to sort."
    
2. **Divide-and-conquer on pairs across a midpoint.** A large class of problems ask: "Among all pairs (i, j) with i in left half and j in right half, find/count those satisfying some condition." After sorting both halves, a two-pointer merge can answer this in O(n) per level. Classic example: "Count pairs with A[i] + A[j] > target" or "Count reverse pairs where A[i] > 2·A[j]" (LC 493).
    
3. **External sort base case.** When data exceeds memory (CP problems with file I/O, or interview questions about sorting 1TB of data), merge sort is the natural external sorting algorithm: sort chunks that fit in memory, then k-way merge the sorted chunks. Quicksort cannot do this.
    

**Pattern signal:** "Count pairs satisfying a condition across two halves" → merge sort with augmented merge step. "Minimum adjacent swaps" → inversion count → merge sort.

**Common trap:** Off-by-one in the merge. When `left = 0, right = n-1`, the midpoint is `mid = left + (right - left) / 2` (not `(left + right) / 2`, which overflows for large indices in C++). The left subarray is `[left, mid]`, right is `[mid+1, right]`. Getting this wrong produces infinite recursion or misses one element.

---

### Machine Learning / AI

**Where merge sort's ideas live in ML systems — five concrete locations:**

1. **Timsort — Python's sort, NumPy, Pandas.** Timsort is a hybrid of insertion sort and merge sort. After using insertion sort to build natural runs of minimum length 32–64, timsort merges these runs exactly as merge sort does — but with an optimization called _galloping_ that skips ahead when one run is consistently winning the merge. `list.sort()`, `sorted()`, `np.sort(kind='stable')`, `pd.DataFrame.sort_values()` all run timsort. The merge phase of timsort is textbook merge sort. Understanding merge sort means understanding the backbone of every sort call in Python's data stack.
    
2. **External sorting for large ML datasets.** Training data pipelines often involve sorting records that exceed RAM. The standard approach: (1) read chunks of size M into memory, sort each chunk with `std::sort` (introsort), write to disk → produces k sorted runs; (2) k-way merge the runs using a min-heap of size k. This is merge sort at the file-system level. Apache Spark's `sortBy()`, TensorFlow's `tf.data` pipeline sorting, and Hadoop's MapReduce shuffle-sort phase all implement this pattern. The merge step is identical to merge sort's merge.
    
3. **Merge sort recurrence as a template for ML complexity analysis.** The Master Theorem (see [[43.Merge sort — full derivation of the recurrence]]) derived from merge sort's recurrence T(n) = 2T(n/2) + O(n) is the standard tool for analysing divide-and-conquer ML algorithms: k-d tree construction, ball tree construction for k-NN, PCA via divide-and-conquer SVD. Every time you see "split in half, recurse, combine in linear time," the complexity is O(n log n) by the same argument.
    
4. **Stable sort in Pandas multi-key sorting.** `df.sort_values(['key1', 'key2'], stable=True)` requires a stable sort to correctly implement multi-key sorting by repeated single-key sorts. Merge sort's inherent stability is why it (via timsort) is the right tool. Unstable sort would scramble the secondary key ordering. See [[48.Stable vs unstable sort — when stability matters in ML pipelines]].
    
5. **Inversion count as a ranking quality metric.** Kendall's τ (tau) distance between two rankings is proportional to the number of inversions between them. Merge sort computes this in O(n log n). In learning-to-rank (LambdaMART, LambdaRank), the training signal is related to pairwise inversion counts between the predicted ranking and ground truth. Understanding merge sort's inversion-counting capability connects directly to how these models are evaluated.

## 3. Algorithm / Pattern

### Step-by-Step Logic

```
MergeSort(A, left, right):
  1. Base case: if left >= right, return  (single element is sorted)
  2. mid = left + (right - left) / 2     (midpoint, no overflow)
  3. MergeSort(A, left, mid)             (sort left half)
  4. MergeSort(A, mid+1, right)          (sort right half)
  5. Merge(A, left, mid, right)          (combine two sorted halves)

Merge(A, left, mid, right):
  1. Copy A[left..mid] → L[], A[mid+1..right] → R[]
  2. i = 0, j = 0, k = left             (pointers into L, R, A)
  3. While i < len(L) and j < len(R):
       if L[i] <= R[j]: A[k++] = L[i++]  (≤ not <: preserves stability)
       else:             A[k++] = R[j++]
  4. Copy remaining L[i..] or R[j..] into A[k..]
```

**The stability rule:** In step 3, use `L[i] <= R[j]` (take from left when equal). This ensures equal elements from the left half always precede equal elements from the right half — preserving their original relative order.

### Complexity Derivation

The full recurrence derivation is in [[43.Merge sort — full derivation of the recurrence]]. Summary:

$$T(n) = 2T(n/2) + O(n)$$

- **2T(n/2):** Two recursive calls on halves.
- **O(n):** The merge step scans both halves once.

By the Master Theorem (case 2: f(n) = O(n^{log_b a}) = O(n^1)):

$$T(n) = O(n \log n)$$

**Recursion tree view:** There are log n levels. At level k, there are 2^k subproblems each of size n/2^k. Work at level k = 2^k · O(n/2^k) = O(n). Total work = O(n) × log n levels = **O(n log n)**.

This holds for worst, average, and best case — merge sort has **no bad inputs**. Reverse-sorted, already-sorted, all-equal — all cost O(n log n).

**Space:** O(n) auxiliary for the merge buffer. The recursion stack costs O(log n). This is merge sort's main disadvantage vs. quicksort's O(log n) space.

### When to Use vs. Avoid

|Use merge sort|Avoid merge sort|
|---|---|
|Stability required|Space is constrained (O(1) needed → heapsort)|
|Worst-case O(n log n) guaranteed|Cache performance is critical (quicksort wins in practice)|
|Linked lists (no random access needed)|Small n (insertion sort wins for n ≤ 20)|
|External sorting (data exceeds RAM)|In-place sort strictly required|
|Counting inversions or pairs across halves|Adversarial inputs not a concern (quicksort faster avg)|

## 4. Pseudocode

```
Algorithm: MergeSort
Input:  Array A[0..n-1], indices left, right
Output: A[left..right] sorted in-place (uses auxiliary buffer)

MergeSort(A, left, right):
    if left >= right then
        return                    // Base case: 0 or 1 element, already sorted

    mid ← left + (right - left) / 2   // Avoid integer overflow vs (left+right)/2

    MergeSort(A, left, mid)       // Recursively sort left half
    MergeSort(A, mid + 1, right)  // Recursively sort right half
    Merge(A, left, mid, right)    // Merge the two sorted halves


Algorithm: Merge
Input:  Array A, indices left, mid, right
        A[left..mid] and A[mid+1..right] are each sorted
Output: A[left..right] is sorted (stable)

Merge(A, left, mid, right):
    // Copy both halves into auxiliary arrays
    // Copying into L and R lets us overwrite A in place
    L ← A[left .. mid]          // length: mid - left + 1
    R ← A[mid+1 .. right]       // length: right - mid

    i ← 0                       // pointer into L
    j ← 0                       // pointer into R
    k ← left                    // pointer into A (write position)

    while i < len(L) and j < len(R) do
        if L[i] ≤ R[j] then     // ≤ (not <) → stable: left wins ties
            A[k] ← L[i]
            i ← i + 1
        else
            A[k] ← R[j]
            j ← j + 1
        k ← k + 1

    // Drain whichever half has remaining elements
    while i < len(L) do
        A[k] ← L[i];  i ← i + 1;  k ← k + 1

    while j < len(R) do
        A[k] ← R[j];  j ← j + 1;  k ← k + 1


Algorithm: MergeSort with Inversion Count
Input:  Array A[0..n-1]
Output: A sorted; returns total number of inversions

MergeSortCount(A, left, right) → inversions:
    if left >= right then return 0

    mid ← left + (right - left) / 2
    inv ← 0
    inv ← inv + MergeSortCount(A, left, mid)
    inv ← inv + MergeSortCount(A, mid + 1, right)
    inv ← inv + MergeCount(A, left, mid, right)
    return inv

MergeCount(A, left, mid, right) → inversions:
    L ← A[left..mid],  R ← A[mid+1..right]
    i ← 0,  j ← 0,  k ← left,  inv ← 0

    while i < len(L) and j < len(R) do
        if L[i] ≤ R[j] then
            A[k] ← L[i];  i ← i + 1
        else
            // R[j] < L[i]: R[j] is smaller than all remaining L[i..end]
            // Each of those (len(L) - i) elements forms an inversion with R[j]
            inv ← inv + (len(L) - i)
            A[k] ← R[j];  j ← j + 1
        k ← k + 1

    // Drain remaining elements (no new inversions)
    ... copy remaining L and R into A ...
    return inv
```

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <algorithm>
#include <cassert>
#include <iostream>
#include <vector>

// ============================================================
// Merge Sort — three variants
// ============================================================

// ----------------------------------------------------------
// Core merge step. Merges A[left..mid] and A[mid+1..right].
// Stable: left wins ties (L[i] <= R[j] takes from left).
// Uses a single pre-allocated auxiliary buffer to avoid
// repeated allocation — critical for performance.
// ----------------------------------------------------------
template <typename T, typename Compare = std::less_equal<T>>
void merge(std::vector<T>& A, std::vector<T>& buf,
           int left, int mid, int right,
           Compare cmp = Compare{})
{
    // Copy [left, right] into buf
    for (int i = left; i <= right; ++i) buf[i] = A[i];

    int i = left, j = mid + 1, k = left;
    while (i <= mid && j <= right) {
        // cmp is <=: take from left on ties → stable
        if (cmp(buf[i], buf[j])) A[k++] = buf[i++];
        else                      A[k++] = buf[j++];
    }
    while (i <= mid)   A[k++] = buf[i++];
    while (j <= right) A[k++] = buf[j++];
}

// ----------------------------------------------------------
// Variant 1: Top-down recursive merge sort.
// The "textbook" version. Clear, correct, O(n log n).
// ----------------------------------------------------------
template <typename T>
void merge_sort_recursive(std::vector<T>& A, std::vector<T>& buf,
                           int left, int right)
{
    if (left >= right) return;                         // Base case

    int mid = left + (right - left) / 2;              // No overflow
    merge_sort_recursive(A, buf, left, mid);
    merge_sort_recursive(A, buf, mid + 1, right);
    merge(A, buf, left, mid, right);
}

template <typename T>
void merge_sort(std::vector<T>& A) {
    if (A.size() <= 1) return;
    std::vector<T> buf(A.size());                     // Single allocation
    merge_sort_recursive(A, buf, 0, (int)A.size() - 1);
}

// ----------------------------------------------------------
// Variant 2: Bottom-up iterative merge sort.
// No recursion stack. Better cache behaviour for large n.
// Merges runs of size 1, then 2, then 4, then 8, ...
// ----------------------------------------------------------
template <typename T>
void merge_sort_iterative(std::vector<T>& A) {
    int n = (int)A.size();
    if (n <= 1) return;
    std::vector<T> buf(n);

    // width: current run size (1, 2, 4, 8, ...)
    for (int width = 1; width < n; width *= 2) {
        // Merge pairs of runs of this width
        for (int left = 0; left < n - width; left += 2 * width) {
            int mid   = left + width - 1;
            int right = std::min(left + 2 * width - 1, n - 1);
            merge(A, buf, left, mid, right);
        }
    }
}

// ----------------------------------------------------------
// Variant 3: Merge sort that counts inversions.
// An inversion is a pair (i,j) with i<j but A[i]>A[j].
// When we take R[j] before L[i..mid], those (mid-i+1)
// elements of L are all > R[j] → each is one inversion.
// O(n log n) time, O(n) space.
// ----------------------------------------------------------
template <typename T>
long long merge_count(std::vector<T>& A, std::vector<T>& buf,
                      int left, int mid, int right)
{
    for (int i = left; i <= right; ++i) buf[i] = A[i];

    int i = left, j = mid + 1, k = left;
    long long inv = 0;

    while (i <= mid && j <= right) {
        if (buf[i] <= buf[j]) {
            A[k++] = buf[i++];
        } else {
            // buf[j] < buf[i]: buf[j] is smaller than ALL of buf[i..mid]
            inv += (long long)(mid - i + 1);  // All remaining left elements
            A[k++] = buf[j++];
        }
    }
    while (i <= mid)   A[k++] = buf[i++];
    while (j <= right) A[k++] = buf[j++];
    return inv;
}

template <typename T>
long long count_inversions(std::vector<T>& A, std::vector<T>& buf,
                           int left, int right)
{
    if (left >= right) return 0;
    int mid = left + (right - left) / 2;
    long long inv = 0;
    inv += count_inversions(A, buf, left, mid);
    inv += count_inversions(A, buf, mid + 1, right);
    inv += merge_count(A, buf, left, mid, right);
    return inv;
}

template <typename T>
long long count_inversions(std::vector<T> A) {   // Pass by value: sorts a copy
    std::vector<T> buf(A.size());
    return count_inversions(A, buf, 0, (int)A.size() - 1);
}

// ----------------------------------------------------------
// Variant 4: Hybrid — insertion sort for small ranges.
// Matches what std::sort (introsort) and timsort do.
// Threshold of 16 is empirically good for ints on modern CPUs.
// ----------------------------------------------------------
template <typename T>
void insertion_sort_range(std::vector<T>& A, int left, int right) {
    for (int i = left + 1; i <= right; ++i) {
        T key = std::move(A[i]);
        int j = i - 1;
        while (j >= left && A[j] > key) { A[j+1] = std::move(A[j]); --j; }
        A[j+1] = std::move(key);
    }
}

template <typename T>
void hybrid_merge_sort(std::vector<T>& A, std::vector<T>& buf,
                       int left, int right, int threshold = 16)
{
    if (right - left + 1 <= threshold) {
        insertion_sort_range(A, left, right);  // Fast for small n
        return;
    }
    int mid = left + (right - left) / 2;
    hybrid_merge_sort(A, buf, left, mid, threshold);
    hybrid_merge_sort(A, buf, mid + 1, right, threshold);

    // Early exit: if A[mid] <= A[mid+1], already sorted — skip merge
    if (A[mid] <= A[mid + 1]) return;

    merge(A, buf, left, mid, right);
}

// ============================================================
// Tests
// ============================================================
int main() {
    // --- merge_sort ---
    {
        std::vector<int> A = {5, 2, 8, 1, 9, 3, 7, 4, 6};
        merge_sort(A);
        assert(std::is_sorted(A.begin(), A.end()));
    }

    // Already sorted (still O(n log n) — no best-case speedup without check)
    {
        std::vector<int> A = {1, 2, 3, 4, 5};
        merge_sort(A);
        assert(std::is_sorted(A.begin(), A.end()));
    }

    // Reverse sorted
    {
        std::vector<int> A = {5, 4, 3, 2, 1};
        merge_sort(A);
        assert(std::is_sorted(A.begin(), A.end()));
    }

    // Stability: equal keys preserve original index order
    {
        using P = std::pair<int,int>;  // {key, original_index}
        std::vector<P> A = {{3,0},{1,1},{3,2},{2,3},{1,4}};
        // Custom merge sort with <=: left wins ties → stable
        std::vector<P> buf(A.size());
        merge_sort_recursive(A, buf, 0, (int)A.size()-1);
        // Equal keys (1,1),(1,4) must stay in this order
        assert(A[0] == P(1,1) && A[1] == P(1,4));
        assert(A[3] == P(3,0) && A[4] == P(3,2));
    }

    // --- merge_sort_iterative ---
    {
        std::vector<int> A = {9, 3, 7, 1, 5, 8, 2, 6, 4};
        merge_sort_iterative(A);
        assert(std::is_sorted(A.begin(), A.end()));
    }

    // --- count_inversions ---
    {
        // [3,1,2]: inversions (3,1),(3,2) → 2
        assert(count_inversions(std::vector<int>{3,1,2}) == 2);
        // [4,3,2,1]: C(4,2)=6 inversions
        assert(count_inversions(std::vector<int>{4,3,2,1}) == 6);
        // Already sorted: 0 inversions
        assert(count_inversions(std::vector<int>{1,2,3,4}) == 0);
        // [2,4,1,3,5]: inversions (2,1),(4,1),(4,3) → 3
        assert(count_inversions(std::vector<int>{2,4,1,3,5}) == 3);
    }

    std::cout << "All tests passed.\n";
    return 0;
}
```

### Python (Readable + Pythonic)

```python
"""
Merge Sort — Divide and Conquer, Stable, O(n log n)

Variants:
  merge_sort_recursive    — top-down, classic
  merge_sort_iterative    — bottom-up, no recursion stack
  merge_sort_inversion    — returns (sorted_list, inversion_count)
  merge_sort_hybrid       — insertion sort base case, like timsort

Time:  O(n log n) — worst, average, and best case
Space: O(n) auxiliary buffer + O(log n) recursion stack
Stable: Yes — left half wins ties in merge step (L[i] <= R[j])
"""

from __future__ import annotations
from typing import TypeVar, Callable, Any

T = TypeVar("T")


# ---------------------------------------------------------------------------
# Core merge operation — the heart of the algorithm
# ---------------------------------------------------------------------------

def _merge(left: list, right: list, key: Callable = lambda x: x) -> list:
    """
    Merge two sorted lists into one sorted list.

    Stable: when keys are equal, elements from `left` come first.
    Time: O(len(left) + len(right)).
    """
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        # <= (not <): take from left on ties → stable
        if key(left[i]) <= key(right[j]):
            result.append(left[i]); i += 1
        else:
            result.append(right[j]); j += 1
    # One of these will be empty; extend handles both
    result.extend(left[i:])
    result.extend(right[j:])
    return result


# ---------------------------------------------------------------------------
# Variant 1: Top-down recursive merge sort
# ---------------------------------------------------------------------------

def merge_sort_recursive(
    arr: list,
    key: Callable[[Any], Any] = lambda x: x,
) -> list:
    """
    Classic top-down merge sort. Returns a new sorted list.

    Args:
        arr: Input list (not modified).
        key: Key function, same semantics as sorted().

    Returns:
        New sorted list.

    Complexity:
        Time:  O(n log n) — all cases identical.
        Space: O(n log n) — each level creates new sublists.
                           (Bottom-up avoids this: see iterative variant.)
        Stable: Yes.
    """
    if len(arr) <= 1:
        return list(arr)                    # Base case: already sorted

    mid   = len(arr) // 2
    left  = merge_sort_recursive(arr[:mid], key)
    right = merge_sort_recursive(arr[mid:], key)
    return _merge(left, right, key)


# ---------------------------------------------------------------------------
# Variant 2: Bottom-up iterative merge sort (in-place on a copy)
# ---------------------------------------------------------------------------

def merge_sort_iterative(arr: list) -> list:
    """
    Bottom-up merge sort. No recursion stack.

    Merges runs of width 1, then 2, then 4, ... until the whole array.
    Slightly better cache behaviour for very large arrays.

    Returns a new sorted list. Original is not modified.
    """
    a = list(arr)
    n = len(a)
    width = 1
    while width < n:
        for i in range(0, n, 2 * width):
            left  = a[i : i + width]
            right = a[i + width : i + 2 * width]
            merged = _merge(left, right)
            a[i : i + len(merged)] = merged
        width *= 2
    return a


# ---------------------------------------------------------------------------
# Variant 3: Merge sort that counts inversions
# ---------------------------------------------------------------------------

def merge_sort_inversion(arr: list) -> tuple[list, int]:
    """
    Sort arr and count inversions simultaneously.

    An inversion is a pair (i, j) with i < j but arr[i] > arr[j].
    The inversion count equals the number of adjacent swaps needed to sort arr.
    This is also proportional to Kendall's τ distance between arr and sorted(arr).

    Returns:
        (sorted_list, inversion_count)

    Complexity: O(n log n) time, O(n) space.

    Example:
        merge_sort_inversion([3, 1, 2]) → ([1, 2, 3], 2)
        # Inversions: (3,1) and (3,2)
    """
    if len(arr) <= 1:
        return list(arr), 0

    mid = len(arr) // 2
    left,  left_inv  = merge_sort_inversion(arr[:mid])
    right, right_inv = merge_sort_inversion(arr[mid:])

    # Merge and count cross-inversions
    merged = []
    i = j = 0
    cross_inv = 0

    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            merged.append(left[i]); i += 1
        else:
            # right[j] < left[i]: right[j] is smaller than ALL left[i:]
            # Each of those forms an inversion with right[j]
            cross_inv += len(left) - i
            merged.append(right[j]); j += 1

    merged.extend(left[i:])
    merged.extend(right[j:])

    return merged, left_inv + right_inv + cross_inv


# ---------------------------------------------------------------------------
# Variant 4: Hybrid merge sort (insertion sort for small runs)
# ---------------------------------------------------------------------------

def _insertion_sort(arr: list, key: Callable = lambda x: x) -> list:
    """In-place insertion sort on a list. Returns the same list."""
    for i in range(1, len(arr)):
        current = arr[i]
        j = i - 1
        while j >= 0 and key(arr[j]) > key(current):
            arr[j + 1] = arr[j]
            j -= 1
        arr[j + 1] = current
    return arr


def merge_sort_hybrid(
    arr: list,
    key: Callable[[Any], Any] = lambda x: x,
    threshold: int = 16,
) -> list:
    """
    Hybrid merge sort: insertion sort for len <= threshold, merge sort otherwise.

    This mirrors what timsort does (threshold = 32-64 in CPython).
    Faster than pure merge sort for real-world data with small runs.

    Returns a new sorted list.
    """
    if len(arr) <= threshold:
        return _insertion_sort(list(arr), key)

    mid   = len(arr) // 2
    left  = merge_sort_hybrid(arr[:mid], key, threshold)
    right = merge_sort_hybrid(arr[mid:], key, threshold)

    # Early exit: if left[-1] <= right[0], already in order — skip merge work
    if key(left[-1]) <= key(right[0]):
        return left + right

    return _merge(left, right, key)

if __name__ == "__main__":
```

## 7. Common Variations & Extensions

### Variation 1: Natural Merge Sort (Timsort's Skeleton)

Instead of always splitting at the midpoint, natural merge sort scans the array for existing sorted runs and merges those. On already-sorted or nearly-sorted data this reduces to O(n). On random data it behaves like standard merge sort. This is the key idea in timsort — extend natural runs to minimum size using insertion sort (see [[41.Insertion sort — when O(n^2) is the right answer]]), then merge using a stack-based strategy that maintains invariants to ensure O(n log n) total merge work.

### Variation 2: K-Way Merge

Instead of merging two sorted lists, merge k sorted lists simultaneously using a min-heap of size k. At each step, extract the minimum from the heap, output it, and insert the next element from that list. Total time: O(n log k) where n is the total number of elements. This is the external sort merge phase — applied whenever sorted data chunks exceed RAM. Also used in [[153.Merge k sorted lists — min-heap of size k]] and in Apache Spark's shuffle merge.

### Variation 3: In-Place Merge Sort

Standard merge sort requires O(n) auxiliary space. True in-place merge (merging without extra buffer) is possible but complex — the classic algorithm by Kronrod (1969) runs in O(n log² n) due to the overhead of in-place rotation. A simpler approach: use block merge sort (O(n log n), O(√n) space). In practice, if O(n) space is unavailable, use heapsort instead — it's O(n log n), O(1) space, but unstable. See [[46.Heapsort — in-place, O(n log n), not cache-friendly]].

### Variation 4: Parallel Merge Sort

Merge sort parallelises naturally: sort left and right halves on separate threads. The merge step requires a parallel merge algorithm (e.g., binary-search-based parallel merge in O(n/p + log n) with p processors). This is the basis for parallel sorting in NumPy with OpenMP and in GPU-based sorting (thrust::sort on CUDA uses a variant of this). The recursion tree becomes a task DAG — the foundation of work-stealing schedulers in Intel TBB and C++ execution policies.

## 9. CP Contest Application

**Codeforces / AtCoder problem types:**

**Type 1 — Inversion count (very common, Div. 2 C/D level):**  
Direct prompt: "Minimum number of adjacent swaps to sort the array." Indirect prompt: "Count pairs (i,j) with i<j and A[i]>A[j]." Both reduce to the augmented merge sort in Variant 3. Implementation: the `merge_count` function above, accumulated across all merge calls. Time: O(n log n), fits n=10⁵ comfortably in 1s.

**Type 2 — Count pairs satisfying a cross-condition (Div. 2 D/E):**  
Pattern: "Count pairs (i,j) with i < j and A[i] > 2·A[j]" (LC 493 / Codeforces analogues). During the merge of sorted left and right halves, use a two-pointer to count valid pairs in O(n) per level. Total O(n log n). The merge structure gives you the sorted halves for free; the counting is the augmentation.

**Type 3 — External sort (ICPC-style, rare in CF):**  
"Sort n numbers that don't fit in memory." Answer: describe the k-way merge procedure. Not asked to implement in CF, but appears in system design rounds and ICPC problems with large file I/O.

**Time limit guidance:**  
n=10⁵: O(n log n) ≈ 1.7×10⁶ ops — trivially fast.  
n=10⁶: O(n log n) ≈ 2×10⁷ ops — fast, use iterative bottom-up to avoid stack overhead.  
n=10⁷: O(n log n) ≈ 2.3×10⁸ ops — tight at 1s. Use `std::sort` (introsort) instead of hand-rolled merge sort; its cache efficiency wins by 2-3× in practice.

**The standard CP inversion count template** (memorise this):

```cpp
long long merge_count(vector<int>& a, vector<int>& tmp, int l, int m, int r) {
    for (int i = l; i <= r; i++) tmp[i] = a[i];
    int i = l, j = m+1, k = l; long long inv = 0;
    while (i <= m && j <= r)
        if (tmp[i] <= tmp[j]) a[k++] = tmp[i++];
        else { inv += m - i + 1; a[k++] = tmp[j++]; }
    while (i <= m) a[k++] = tmp[i++];
    while (j <= r) a[k++] = tmp[j++];
    return inv;
}
```
