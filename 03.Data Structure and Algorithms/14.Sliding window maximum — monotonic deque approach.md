## The Problem

Given an array $a[0..n-1]$ and a window of size $k$, compute

$$ M[i] = \max(a[i],, a[i+1],, \ldots,, a[i+k-1]) \quad \text{for } i = 0, 1, \ldots, n-k $$

There are $n - k + 1$ windows. The naive solution evaluates $\max$ over $k$ elements per window: $O(nk)$ total. For $n = 10^6$, $k = 10^3$, that is $10^9$ operations — too slow.

**We want $O(n)$.**

---

## The Key Insight: What Makes an Element Useless?

Fix a window $[i, i+k-1]$. Suppose $j < \ell$ and $a[j] \leq a[\ell]$. Then:

- $a[j]$ can never be the maximum of any future window that also contains $a[\ell]$, because $a[\ell]$ dominates it.
- Once $a[\ell]$ enters the window, $a[j]$ becomes **permanently useless**.

We should discard $a[j]$ immediately when $a[\ell]$ arrives.

This is the **monotonic decreasing deque** invariant:

> **Invariant.** At every step, the deque stores indices in increasing order, and their corresponding values in _strictly decreasing_ order. The front of the deque is always the index of the current window maximum.

---

## The Data Structure: `collections.deque`

A double-ended queue supporting $O(1)$ append and pop from both ends.

```python
from collections import deque
dq = deque()   # stores indices, not values
```

We store **indices** (not values) so we can check whether the front element has expired (slid out of the window).

---

## The Algorithm — Step by Step

```
For each new element a[r] arriving at the right end:

  STEP 1 — Maintain the invariant (pop from the right):
    While dq is non-empty AND a[dq[-1]] <= a[r]:
        dq.pop()          # a[dq[-1]] is now dominated and useless
    dq.append(r)          # r is a candidate for future maxima

  STEP 2 — Evict expired elements (pop from the left):
    If dq[0] < r - k + 1:
        dq.popleft()      # front has slid out of the window

  STEP 3 — Record the answer (once the first full window is formed):
    If r >= k - 1:
        result.append(a[dq[0]])   # front is always the window max
```

---

## Full Implementation

```python
from collections import deque
from typing import List

def sliding_window_maximum(a: List[int], k: int) -> List[int]:
    """
    Returns the maximum of each sliding window of size k.

    Time:  O(n)  — each index enters and leaves the deque at most once
    Space: O(k)  — deque holds at most k indices at any time
    """
    n = len(a)
    if n == 0 or k == 0:
        return []

    result = []
    dq: deque = deque()   # monotonic decreasing deque of indices

    for r in range(n):
        # Step 1: maintain decreasing invariant
        while dq and a[dq[-1]] <= a[r]:
            dq.pop()
        dq.append(r)

        # Step 2: evict elements outside the window
        if dq[0] < r - k + 1:
            dq.popleft()

        # Step 3: record answer once window is full
        if r >= k - 1:
            result.append(a[dq[0]])

    return result
```

## Correctness Proof (Invariant Maintenance)

**Claim.** After processing index $r$, the deque contains indices $i_1 < i_2 < \ldots < i_m$ with $a[i_1] > a[i_2] > \ldots > a[i_m]$, and $i_1 \geq r - k + 1$ (all indices are in the current window).

**Proof by induction.**

_Base case:_ $r = 0$. The deque contains only ${0}$. Trivially satisfied.

_Inductive step:_ Assume the invariant holds after $r - 1$.

- Step 1 removes all indices $j$ from the right with $a[j] \leq a[r]$, then appends $r$. The resulting sequence of values is strictly decreasing (since any remaining element $a[j]$ satisfies $a[j] > a[r]$, and $r$ is appended last). Indices remain increasing since $r > $ all existing indices.
- Step 2 removes the front if it has index $< r - k + 1$, preserving the window constraint.

Therefore the invariant holds after $r$. $\blacksquare$

**Corollary.** The front index is always in the window and corresponds to the maximum value in the deque. Since all window candidates are in the deque (we only evict dominated elements), the front is the window maximum.

---

## Complexity Analysis

**Time — $O(n)$:**

Each index $r$ is appended to the deque exactly once and popped at most once (either from the right when dominated, or from the left when expired). Total operations across all $n$ steps: at most $2n$ push/pop operations. Each is $O(1)$. Total: $O(n)$.

This is an **amortised** argument — a single step may pop many elements, but each pop corresponds to a unique push that was paid for earlier.

**Space — $O(k)$:**

The deque contains only indices within the active window, so $|\text{dq}| \leq k$.

## Common Mistakes

```python
# ❌ MISTAKE 1: storing values instead of indices
# You lose the ability to check if front has expired
dq.append(a[r])   # wrong — can't check dq[0] < r - k + 1

# ❌ MISTAKE 2: strict inequality in the pop condition
while dq and a[dq[-1]] < a[r]:   # wrong — equal values survive, bloating the deque
    dq.pop()
# Use <=  to evict equal or smaller elements (duplicates are useless too)

# ❌ MISTAKE 3: evicting before maintaining the invariant
if dq[0] < r - k + 1:    # eviction first
    dq.popleft()
while dq and a[dq[-1]] <= a[r]:  # then pop — ORDER IS WRONG
    dq.pop()
# Correct order: maintain invariant (right), then evict (left), then record

# ❌ MISTAKE 4: recording before the window is full
if r >= k:        # off-by-one — should be r >= k - 1
    result.append(a[dq[0]])
```

## Variations

### Sliding Window Minimum

Flip the inequality in Step 1: maintain an **increasing** deque.

```python
while dq and a[dq[-1]] >= a[r]:   # >= instead of <=
    dq.pop()
```

Front of the deque is now always the window minimum.

### Fixed Window → Variable Window

The deque technique generalises to variable-size windows where you want the max/min under a constraint — the eviction condition in Step 2 changes from index-based to constraint-based.

### "Jump Game" Style Problems

Many problems reduce to: _what is the optimal value reachable from some prior position within distance $k$?_ — this is exactly sliding window maximum/minimum on a DP array. Example: LeetCode 1696 (Jump Game VI).

## Connection to AI / ML / Deep Learning

This pattern appears more often in ML infrastructure than most students expect.

### 1. Feature Engineering on Time Series

Sliding window max/min/mean are standard features for time-series ML (sensor data, stock prices, EEG signals). The $O(n)$ deque approach makes this tractable at scale.

```python
# Generating rolling-max features for tabular ML
def rolling_max_feature(series: List[float], k: int) -> List[float]:
    return sliding_window_maximum(series, k)
```

### 2. Temporal Attention — Efficient Softmax Over Windows

Transformers compute attention over all pairs, $O(n^2)$. Local attention variants (Longformer, BigBird) restrict each token to attend only to its $k$-nearest neighbours. Within each window, computing the max (for numerically stable softmax via log-sum-exp) is exactly this problem.

$$ \text{softmax}(z)_i = \frac{e^{z_i - \max_j z_j}}{\sum_j e^{z_j - \max_j z_j}} $$

Efficient local attention implementations maintain a sliding max using this exact deque technique.

### 3. Convolutional Neural Networks — Max Pooling

**Max pooling** is the learned-feature analogue of sliding window max. In a 1D max-pool layer with kernel size $k$ and stride 1:

$$ y[i] = \max(x[i], x[i+1], \ldots, x[i+k-1]) $$

The CPU fallback in frameworks like PyTorch uses exactly this deque algorithm when stride = 1. Understanding it demystifies what `nn.MaxPool1d` is doing under the hood.

```python
import torch
import torch.nn as nn

pool = nn.MaxPool1d(kernel_size=3, stride=1)
x = torch.tensor([[3., 1., -1., 5., 3., 6., 7.]]).unsqueeze(0)  # (1, 1, 7)
print(pool(x))  # tensor([[[3., 5., 5., 6., 7.]]])  ← same as our function
```

### 4. Beam Search Pruning in Sequence Models

During beam search (decoding in language models, translation systems), at each step you maintain the top-$k$ candidate sequences by score. Efficiently updating a running maximum over a window of scores uses the same invariant structure.

### 5. Reward Normalisation in Reinforcement Learning

PPO and other RL algorithms often normalise rewards using a running max/min over a recent window of episodes to prevent reward scale drift. The deque approach gives $O(1)$ per update.
