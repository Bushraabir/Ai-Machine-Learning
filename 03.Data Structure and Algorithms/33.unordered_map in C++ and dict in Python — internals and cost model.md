## 1. Intuition First

### The Core Idea

Every time you write `mp[key]` in C++ or `d[key]` in Python, you're invoking a non-trivial piece of machinery — a hash table whose internal structure, memory layout, and performance characteristics differ significantly between the two languages. They are both hash maps. They are not the same hash map.

The difference is not academic. `std::unordered_map` is a **chained hash table** backed by a node-based allocator — every key-value pair is a separately heap-allocated node. Python's `dict` is an **open-addressed compact table** with a perturbation-based probe sequence — every key-value pair lives in a single flat array. The first has better worst-case memory predictability and supports load factors above 1.0. The second has dramatically better cache behaviour for small-to-medium tables and is the reason Python dict lookups at $n = 10^4$ can beat C++ `unordered_map` lookups in wall-clock time despite Python's interpreter overhead.

Understanding this distinction is not trivia — it determines when to reserve capacity, when pointer invalidation breaks your code, when rehashing triggers, and why a 10× performance gap between two "O(1)" operations is not a paradox.

### Why This Exists

The standard library designers made a deliberate tradeoff. C++'s `unordered_map` prioritises **iterator and pointer stability**: after any insertion (that doesn't trigger a rehash), pointers to elements remain valid. This requires node-based storage — each element is an independent allocation. The cost is pointer chasing on every lookup.

Python's `dict` prioritises **memory compactness and cache performance**: all keys, values, and hashes live in a single contiguous block. Iteration is fast; resizing copies everything. The cost is that you cannot hold raw pointers into a dict (Python doesn't expose them), and resize operations are more expensive per-element.

Both are correct engineering decisions for their target use cases. Knowing which you're using — and when each breaks down — is what separates competent from expert use of these containers.

### The "Aha" Moment

**The cost of `mp[key]` in C++ is not the hash computation — it's the pointer chase into a heap-allocated node that almost certainly lives outside your CPU's L1 cache.** At $n = 10^6$ entries in `unordered_map`, each lookup is typically 1 hash + 1–2 cache misses (64–200ns each). The hash itself takes ~5ns. You are paying 10–40× overhead for the memory access pattern, not the algorithm.

This single insight explains: why `reserve()` exists, why `max_load_factor()` matters for performance (not just correctness), why flat hash maps (absl, robin_hood) exist, and why Python's dict — implemented in C with a flat layout — can match or beat `unordered_map` on lookup benchmarks despite running in an interpreted language.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**The most common source of unexpected TLE in hash-heavy problems is using `unordered_map` without reserving capacity and without understanding rehashing cost.**

Signal patterns:

> `n ≤ 10^6`, `Q ≤ 10^6` queries, each doing a map lookup → potential TLE with default `unordered_map` due to cache thrashing. Profile: if your solution is $O(n)$ theoretically but takes 3–4× the expected time, suspect cache misses from unchained lookups.

> "Memory limit exceeded" with `unordered_map<string, int>` at $n = 10^5$ → each `std::list` node for a string key allocates separately; string small-buffer optimisation doesn't help here. Switch to sorted `vector<pair<string,int>>` + binary search, or hash the strings to integers first.

**The rehashing trap:** Default `unordered_map` rehashes when $n/m > \text{max_load_factor}$ (default 1.0). Rehashing rebuilds the entire table: $O(n)$ time. If you insert $n$ elements one by one without `reserve()`, you trigger $O(\log n)$ rehashes, each copying the current contents. Total insertion cost: $O(n \log n)$ instead of $O(n)$. **Fix: always call `mp.reserve(n)` before bulk insertion.**

**The anti-hash hack:** On Codeforces, the hash function for integers is deterministic and known. An adversary can craft $n$ keys that all map to the same bucket, degrading every operation to $O(n)$. This is not theoretical — hack submissions exist that specifically target `unordered_map`. Fix: use the `splitmix64` custom hash from [[31.Hash function design — properties, uniformity, avalanche]].

**Pointer invalidation (CP bug):** If you store `auto& ref = mp[key]` and then insert another key, a rehash may occur, invalidating `ref`. This causes silent undefined behaviour — one of the hardest bugs to diagnose in CP. Fix: always `reserve` first, or don't store references into `unordered_map`.

### Machine Learning / AI

**Python `dict` as the backbone of every ML pipeline:**

- **Vocabulary indexing (`word2idx`):** A `dict[str, int]` mapping tokens to embedding indices. At vocabulary size $V = 10^5$, this dict has $V$ entries at load factor ~0.67, occupying roughly $V \times 8 \times 3 \approx 2.4$ MB (hash, key pointer, value pointer per slot). For $V = 10^6$ (byte-pair encoding vocabularies in GPT-scale models), the dict itself is ~24 MB — fits comfortably in L3 cache on modern hardware.
    
- **Batch collation in DataLoaders:** PyTorch's `DataLoader` with `collate_fn` uses dicts to aggregate per-sample metadata. Each `__getitem__` returns a `dict`; the collator merges them. Understanding that dict merging (`{**a, **b}`) triggers a resize if $|a| + |b|$ exceeds 2/3 of `b`'s capacity is relevant when writing memory-efficient collators.
    
- **Feature store lookups in recommendation systems:** Production recommendation systems (Meta DLRM, Google Wide & Deep) do billions of embedding lookups per second. At this scale, `dict` is replaced by sharded hash tables with custom cache-aware layouts — but the design principles are identical. Understanding why Python dict is faster than a naive chained table at small scale helps you understand why FAISS uses inverted file indexes (chains) at billion-vector scale: different $n$, different optimal strategy.
    
- **`defaultdict`, `Counter`, `OrderedDict` — cost implications:**
    
    - `defaultdict(list)`: same underlying dict, plus a `__missing__` call overhead per new key. Negligible.
    - `Counter`: subclass of `dict`; `Counter.update()` is optimised in C for string keys. Faster than manual dict increment for frequency counting.
    - `OrderedDict` (pre-Python 3.7): maintained a separate doubly-linked list for insertion order. **Post-Python 3.7, regular `dict` is insertion-ordered** — `OrderedDict` is now only needed for `move_to_end()` and `popitem(last=False)`.
- **`numba.typed.Dict` and `cuDF` hash tables:** For GPU-accelerated ML pipelines, CUDA hash tables (open addressing, no pointer chasing on GPU threads) are used for groupby operations and embedding lookups. The design choice — open addressing — is directly motivated by GPU memory access patterns: scatter/gather over a flat array is vectorisable; pointer chasing is not.

## 3. Algorithm / Pattern

### C++ `std::unordered_map` — Full Internal Model

**Structure:**

```
unordered_map<K, V>
├── float max_load_factor_   (default: 1.0)
├── size_t bucket_count_     (m, number of buckets)
├── size_t size_             (n, number of elements)
└── vector<__detail::_Hash_node*>  buckets_  (size m)
         │
         └── each bucket → linked list of _Hash_node:
                  struct _Hash_node {
                      _Hash_node* next;       // 8 bytes (pointer)
                      size_t      hash_code;  // 8 bytes (cached hash)
                      pair<K,V>   value;      // sizeof(K) + sizeof(V) bytes
                  };
```

Every node is a **separate heap allocation** via `operator new`. This is why:

- Iterators remain valid across insertions (pointer to node is stable)
- Pointers to `value_type` are stable (as long as no rehash)
- Lookups require dereferencing a pointer (cache miss if node is cold)
- Deleting elements is $O(1)$ (splice node out of list)

**Rehashing trigger and cost:** $$\text{rehash when } \frac{n}{m} > \text{max_load_factor}$$ On rehash: allocate new bucket array of size $\approx 2m$; re-hash all $n$ nodes into new buckets (nodes themselves are reused — no reallocation of node memory, just pointer relinking). Cost: $O(n)$ for relinking + $O(m)$ for new bucket array allocation. Amortised per-insertion cost: $O(1)$ with doubling.

**The `reserve(n)` call:**  
`mp.reserve(n)` sets $m \leftarrow \lceil n / \text{max_load_factor} \rceil$. This pre-allocates the bucket array to avoid future rehashes. It does **not** pre-allocate nodes — those are still allocated one-by-one on insertion. For $n = 10^6$ elements: `reserve` costs $O(m)$ time and $O(m)$ space for the bucket array; node allocation still costs $O(n)$ total.

**`max_load_factor(α)` for performance:**  
Reducing max_load_factor below 1.0 forces more buckets per element → shorter chains → fewer pointer chases per lookup. At $\alpha = 0.25$: average chain length 0.25, most lookups touch zero or one node. The tradeoff: $4 \times$ more memory for bucket array.

**Key operations and their actual cost:**

|Operation|Expected|Worst Case|Hidden Cost|
|---|---|---|---|
|`mp[key]` (lookup)|$O(1)$|$O(n)$|1 hash + 1 ptr deref + chain walk|
|`mp[key] = v` (insert)|$O(1)$ amortised|$O(n)$ rehash|`new` allocation per insert|
|`mp.erase(key)`|$O(1)$|$O(n)$|Node `delete`, chain splice|
|`mp.reserve(n)`|$O(m)$|$O(m)$|Bucket array realloc|
|Iteration (range-for)|$O(n + m)$|Same|Scans all $m$ buckets even if mostly empty|

**Iteration is $O(n + m)$, not $O(n)$.** If you insert 10 elements into a default `unordered_map`, it has $m = 11$ (next prime). Iterating scans all 11 buckets. If you `reserve(10^6)` but only insert 10 elements, iteration scans $10^6$ buckets. This is the most commonly overlooked cost.

### Python `dict` — Full Internal Model

**Structure (CPython 3.6+):**

```
dict object
├── ma_used       (n: number of live entries)
├── ma_version_tag (monotonically increasing, detects modifications)
├── ma_keys → dictkeys object:
│       ├── dk_size      (m: number of slots, always power of 2)
│       ├── dk_nentries  (number of used+dummy slots)
│       ├── dk_indices[] (compact index table, 1/2/4 bytes per slot depending on m)
│       └── dk_entries[] (array of (hash, key, value) triples — the "entries" array)
└── (for split-table dicts: ma_values → separate values array)
```

**The two-level structure (Python 3.6+ "compact dict"):**

Before Python 3.6, dict used a single flat array of `(hash, key, value)` triples with open addressing. 33% of slots were empty on average (load factor 2/3), wasting memory on both hash and key/value storage.

Python 3.6 introduced the **compact dict** (designed by Raymond Hettinger):

1. `dk_indices`: a small array of integers (indices into `dk_entries`). Size = $m$ (power of 2). Each slot stores an index or a sentinel (-1 for empty, -2 for deleted). Width: 1 byte if $m \leq 128$, 2 bytes if $m \leq 32768$, 4 bytes for larger.
2. `dk_entries`: a dense array of `(hash, key, value)` triples, only for inserted entries. No holes. Entries are added sequentially.

This separation means:

- **Iteration order = insertion order** (iterate `dk_entries` sequentially — dense, cache-friendly)
- **Memory savings**: empty slots waste only 1–4 bytes (index entry) instead of 24 bytes (hash + key + value)
- **Dict is insertion-ordered since Python 3.7** — this is the data structure reason, not a language spec change

**Probe sequence (not linear probing):**

```python
# CPython probe sequence for slot i, perturb derived from full hash:
i = hash(key) % m        # initial slot
perturb = hash(key)      # full hash value
while slot[i] is not empty and slot[i].key != key:
    i = (5 * i + 1 + perturb) % m
    perturb >>= PERTURB_SHIFT   # PERTURB_SHIFT = 5
```

The `perturb` term ensures that two keys with the same `hash % m` take _different_ probe paths — eliminating secondary clustering while remaining cache-friendly (most probes are within a small neighbourhood). After ~5 probe steps, `perturb` reaches 0 and the sequence degenerates to `(5i+1) % m`, which visits all slots if $m$ is a power of 2.

**Rehashing trigger:**  
Resize when $n_used + n_dummy > \frac{2}{3} m$ (where `n_dummy` = tombstoned slots).  
New size: smallest power of 2 such that $n \times 3 \leq \text{new_size} \times 2$ (equivalently, new load factor ≈ 1/2 after rehash).  
On resize: reallocate `dk_indices` and `dk_entries`; re-probe all entries into new index table. Cost: $O(n)$.

**Key operations and their actual cost:**

|Operation|Expected|Hidden Cost|
|---|---|---|
|`d[key]` lookup|$O(1)$|1 hash + probe sequence into contiguous index array|
|`d[key] = v` insert|$O(1)$ amortised|Append to `dk_entries`, update `dk_indices`|
|`del d[key]`|$O(1)$|Mark index slot as dummy (-2), entry as cleared|
|`d.items()` iteration|$O(n)$|Sequential scan of `dk_entries` — cache-friendly|
|`key in d`|$O(1)$|Same as lookup, no value retrieval|
|`{**a, **b}` merge|$O(|a|

**Iteration is $O(n)$ in Python, not $O(n + m)$.** This is a direct consequence of the compact dict design — `dk_entries` is dense. C++ `unordered_map` iteration is $O(n + m)$.

### Decision Tree: When to Use What

```
Need a key→value mapping?
├── In C++:
│   ├── Keys are integers or small structs?
│   │   ├── n < 10^4: std::unordered_map (fine, overhead negligible)
│   │   ├── n < 10^6: unordered_map + reserve(n) + custom hash
│   │   └── n ≥ 10^6 or cache-critical: absl::flat_hash_map or robin_hood::unordered_map
│   ├── Need sorted order or range queries?
│   │   └── std::map (RB-tree, O(log n), cache-unfriendly but ordered)
│   └── Need pointer/iterator stability across inserts?
│       └── std::unordered_map (node-based, guaranteed stable)
│
└── In Python:
    ├── General purpose → dict (always, it's the best general hash map)
    ├── Counting frequencies → collections.Counter (optimised C path)
    ├── Missing key handling → collections.defaultdict
    ├── Need ordered operations (move_to_end, FIFO eviction)?
    │   └── collections.OrderedDict
    └── Huge n, performance critical → numpy structured arrays or
        pandas categorical + hash table backend, or numba.typed.Dict
```

## 4. Pseudocode

```
// ─────────────────────────────────────────────────────────────────────────
// C++ unordered_map internal model — what mp[key] actually does
// ─────────────────────────────────────────────────────────────────────────

FUNCTION unordered_map_lookup(mp, key):
    h ← hash(key)                        // O(|key|) for strings, O(1) for ints
    i ← h mod mp.bucket_count            // bucket index
    node ← mp.buckets[i]                 // pointer into array → fast
    WHILE node != NULL:                  // walk the chain
        IF node.hash_code == h           // fast pre-check (cached hash)
            AND node.value.first == key: // actual key comparison
            RETURN &node.value.second    // pointer to value
        node ← node.next                 // POINTER CHASE → likely cache miss
    RETURN NULL                          // not found

// Cost breakdown for cold cache:
//   hash(key):              ~5ns
//   mp.buckets[i]:          ~5ns (array index, buckets likely in cache if small)
//   node.value.first == key: ~100ns (node is on heap, likely cache miss)
//   node.next:               ~100ns if chain length > 1 (another cache miss)

// ─────────────────────────────────────────────────────────────────────────
// Python dict internal model — what d[key] actually does
// ─────────────────────────────────────────────────────────────────────────

FUNCTION dict_lookup(d, key):
    h ← hash(key)                        // O(1) for ints (identity), O(|key|) strings
                                         // BUT: Python caches hash(str) on the str object
    i ← h & (d.ma_keys.dk_size - 1)     // fast bitmask (dk_size is power of 2)
    perturb ← h

    WHILE TRUE:
        index ← d.ma_keys.dk_indices[i] // 1-4 bytes, very likely in cache
        IF index == EMPTY: RETURN NULL   // definitive miss
        IF index == DUMMY:               // tombstone — skip
            i ← (5*i + 1 + perturb) & mask
            perturb >>= 5
            CONTINUE
        entry ← d.ma_keys.dk_entries[index]  // jump to entries array
        IF entry.hash == h AND entry.key IS key:
            RETURN entry.value           // fast path: identity check
        IF entry.hash == h AND entry.key == key:
            RETURN entry.value           // slow path: equality check
        i ← (5*i + 1 + perturb) & mask
        perturb >>= 5

// Key difference from C++:
//   dk_indices is tiny (1-4 bytes per slot) → entire index table fits in L1 cache
//   dk_entries is dense → sequential access pattern → hardware prefetcher helps
//   No heap allocation per entry → no pointer chasing
//   Python caches str hash → repeated lookups of same key avoid rehashing

// ─────────────────────────────────────────────────────────────────────────
// Python hash caching (critical for repeated lookups)
// ─────────────────────────────────────────────────────────────────────────

FUNCTION hash_with_caching(obj):
    IF obj is str or bytes or int:
        IF obj.__hash_cache__ is SET:
            RETURN obj.__hash_cache__    // O(1) — already computed
        h ← compute_hash(obj)           // O(|obj|) first time
        obj.__hash_cache__ ← h
        RETURN h
    ELSE:
        RETURN type(obj).__hash__(obj)   // custom __hash__, no caching

// Implication: in a tight loop doing d[same_string_key] many times,
// Python only hashes the string ONCE. C++ hashes it every time
// (unless you manually cache the hash value, which std::unordered_map
// does in the node — but you still pay for node allocation).
```

## 5. Implementation

### C++ — The Full Cost Model in Code

```cpp
#include <bits/stdc++.h>
#include <chrono>
using namespace std;
using namespace chrono;

// ─────────────────────────────────────────────────────────────────────────────
// Custom hash for anti-hack safety in competitive programming
// (same as note 31, repeated here for completeness)
// ─────────────────────────────────────────────────────────────────────────────
struct SafeHash {
    static uint64_t splitmix64(uint64_t x) {
        x += 0x9e3779b97f4a7c15ULL;
        x = (x ^ (x >> 30)) * 0xbf58476d1ce4e5b9ULL;
        x = (x ^ (x >> 27)) * 0x94d049bb133111ebULL;
        return x ^ (x >> 31);
    }
    size_t operator()(uint64_t x) const {
        static const uint64_t FIXED_RANDOM =
            steady_clock::now().time_since_epoch().count();
        return splitmix64(x + FIXED_RANDOM);
    }
    // Pair hash for 2D grid problems
    size_t operator()(pair<int,int> p) const {
        return operator()(((uint64_t)p.first << 32) ^ (uint32_t)p.second);
    }
};

// ─────────────────────────────────────────────────────────────────────────────
// Demonstrating the exact cost difference between:
//   1. Default unordered_map (no reserve)
//   2. Reserved unordered_map with custom hash
//   3. Flat hash map simulation (sorted vector + binary search, for comparison)
// ─────────────────────────────────────────────────────────────────────────────
template<typename F>
double benchmark(const string& name, F&& fn, int reps = 3) {
    double best = 1e18;
    for (int r = 0; r < reps; ++r) {
        auto t0 = high_resolution_clock::now();
        fn();
        auto t1 = high_resolution_clock::now();
        best = min(best, duration<double, milli>(t1 - t0).count());
    }
    printf("%-45s %.2f ms\n", name.c_str(), best);
    return best;
}

// ─────────────────────────────────────────────────────────────────────────────
// 1. Correct usage patterns with full annotations
// ─────────────────────────────────────────────────────────────────────────────

void demonstrate_correct_usage() {
    const int N = 500'000;

    // ── Pattern 1: Bulk insertion — always reserve first ──────────────────
    {
        unordered_map<int, int, SafeHash> mp;
        mp.reserve(N);          // pre-allocate bucket array for N elements
                                // prevents O(log N) rehash events during insertion
        mp.max_load_factor(0.5);// 2× more buckets than elements → shorter chains
        for (int i = 0; i < N; ++i) mp[i] = i * 2;
        // Verify
        assert(mp[42] == 84);
        assert(mp.size() == N);
    }

    // ── Pattern 2: Frequency counting ────────────────────────────────────
    {
        vector<int> data(N);
        for (int i = 0; i < N; ++i) data[i] = rand() % 1000;

        unordered_map<int, int, SafeHash> freq;
        freq.reserve(1000);  // at most 1000 distinct values
        for (int x : data) ++freq[x];  // operator[] default-inserts 0 if missing

        // Find most frequent element
        auto it = max_element(freq.begin(), freq.end(),
                              [](auto& a, auto& b){ return a.second < b.second; });
        printf("Most frequent: %d (count=%d)\n", it->first, it->second);
    }

    // ── Pattern 3: Checking existence without inserting ───────────────────
    {
        unordered_map<string, int> mp = {{"alpha", 1}, {"beta", 2}};

        // WRONG: mp["gamma"] inserts gamma→0 if not present!
        // if (mp["gamma"]) { ... }   // ← BAD: now mp has "gamma" key

        // CORRECT: use count() or find()
        if (mp.count("gamma")) { printf("found gamma\n"); }
        auto it = mp.find("alpha");
        if (it != mp.end()) { printf("alpha = %d\n", it->second); }
    }

    // ── Pattern 4: Pointer invalidation — the silent UB trap ─────────────
    {
        unordered_map<int, string> mp;
        mp[1] = "one";
        mp[2] = "two";

        // DANGEROUS: storing reference before potential rehash
        // string& ref = mp[3];  // inserts key 3, may trigger rehash
        // mp[4] = "four";       // if rehash occurs, ref is dangling!

        // SAFE: use at() after all insertions complete
        mp.reserve(100);        // no more rehashes if n < 100
        mp[3] = "three";
        mp[4] = "four";
        string& safe_ref = mp.at(3);  // safe: reserve guarantees no rehash
        mp[5] = "five";               // safe: within reserved capacity
        printf("safe_ref = %s\n", safe_ref.c_str());
    }

    // ── Pattern 5: Iterating while tracking bucket distribution ──────────
    {
        unordered_map<int, int, SafeHash> mp;
        mp.reserve(20);
        for (int i = 0; i < 10; ++i) mp[i * 7] = i;

        printf("\nBucket distribution (bucket count = %zu):\n", mp.bucket_count());
        for (size_t b = 0; b < mp.bucket_count(); ++b) {
            if (mp.bucket_size(b) > 0) {
                printf("  Bucket %zu: %zu elements\n", b, mp.bucket_size(b));
            }
        }
        printf("Load factor: %.3f\n", mp.load_factor());
    }
}

// ─────────────────────────────────────────────────────────────────────────────
// 2. The iteration O(n + m) cost — demonstrated concretely
// ─────────────────────────────────────────────────────────────────────────────
void demonstrate_iteration_cost() {
    // Small map but large bucket array (via reserve)
    unordered_map<int, int> mp;
    mp.reserve(1 << 20);  // 1M buckets
    mp[1] = 1; mp[2] = 2; mp[3] = 3;  // only 3 elements

    auto t0 = high_resolution_clock::now();
    int sum = 0;
    for (auto& [k, v] : mp) sum += v;  // scans ~1M buckets to find 3 elements!
    auto t1 = high_resolution_clock::now();

    printf("\nIterating 3 elements over %zu buckets: %.3f ms, sum=%d\n",
           mp.bucket_count(),
           duration<double, milli>(t1 - t0).count(), sum);

    // Compare with no reserve
    unordered_map<int, int> mp2;
    mp2[1] = 1; mp2[2] = 2; mp2[3] = 3;

    t0 = high_resolution_clock::now();
    sum = 0;
    for (auto& [k, v] : mp2) sum += v;  // scans ~8 buckets
    t1 = high_resolution_clock::now();

    printf("Iterating 3 elements over %zu buckets: %.3f ms, sum=%d\n",
           mp2.bucket_count(),
           duration<double, milli>(t1 - t0).count(), sum);
}

// ─────────────────────────────────────────────────────────────────────────────
// 3. Structured bindings and C++17 idioms
// ─────────────────────────────────────────────────────────────────────────────
void demonstrate_cpp17_idioms() {
    unordered_map<string, vector<int>> graph;

    // C++17: insert_or_assign returns {iterator, bool}
    auto [it, inserted] = graph.insert_or_assign("a", vector<int>{1, 2, 3});
    printf("Inserted 'a': %s\n", inserted ? "yes" : "no (updated)");

    // try_emplace: construct in-place only if key absent (avoids copy on hit)
    graph.try_emplace("b", initializer_list<int>{4, 5, 6});
    graph.try_emplace("a", initializer_list<int>{7, 8, 9}); // no-op: 'a' exists

    // C++17 structured bindings in range-for
    for (auto& [node, neighbours] : graph) {
        printf("Node %s: neighbours = [", node.c_str());
        for (int nb : neighbours) printf("%d ", nb);
        printf("]\n");
    }

    // emplace vs operator[]: emplace does NOT default-construct
    // operator[] default-constructs if key absent:
    unordered_map<int, vector<int>> mp;
    mp[99];         // inserts key 99 with empty vector (!) even if you don't assign
    mp.emplace(100, vector<int>{1,2}); // constructs in-place, no default-construct
    printf("mp[99] size: %zu (was default-constructed)\n", mp[99].size());
}

int main() {
    demonstrate_correct_usage();
    demonstrate_iteration_cost();
    demonstrate_cpp17_idioms();
    return 0;
}
```

```python
"""

T1 Core — 2. Hashing

  - Resize triggers and cost
  - Hash caching on strings
  - Performance-critical dict patterns for ML pipelines
  - Counter, defaultdict, OrderedDict cost model

All timings are illustrative; run on your hardware for actuals.
"""

import sys
import time

# ─────────────────────────────────────────────────────────────────────────────
# 1. Dict memory layout — measuring the compact dict structure
# ─────────────────────────────────────────────────────────────────────────────
def measure_dict_memory():
    """
    Observe dict memory usage as n grows.
    Key insight: memory grows in discrete jumps (resize events),
    not continuously. Between jumps, memory is constant even as n grows.
    """
    sizes = []
    d = {}
    for i in range(200):
        d[i] = i
        sizes.append(sys.getsizeof(d))

    # Find resize events (memory jumps)
    resize_events = [(i, sizes[i]) for i in range(1, len(sizes))
                     if sizes[i] > sizes[i-1]]

    print("Dict resize events (n_at_resize, new_size_bytes):")
    for n, sz in resize_events[:12]:
        # Approximate dk_size (slot count) from memory:
        # Each slot: ~8 bytes (index) + 24 bytes (hash+key+val) = 32 bytes
        approx_slots = (sz - 200) // 8  # rough estimate
        print(f"  n={n:4d}: {sz:6d} bytes (≈{approx_slots} slots, "
              f"load_before_resize≈{n/approx_slots:.2f})")

    print("\nConclusion: resize at ~2/3 load factor, consistent with CPython source")


# ─────────────────────────────────────────────────────────────────────────────
# 2. Hash caching on strings — Python's hidden optimisation
# ─────────────────────────────────────────────────────────────────────────────
def demonstrate_hash_caching():
    """
    Python caches hash(str) in the str object after first computation.
    This means repeated dict lookups of the same string key are faster
    than the first lookup — the hash is not recomputed.

    Consequence for ML:
      - vocab lookup in a hot loop: first miss is slower, subsequent are O(1) pure
      - using id(obj) as key (integers) is always O(1) hash, no caching needed
      - using long strings as keys: first lookup expensive, cache saves subsequent
    """
    key = "transformer_encoder_layer_attention_weights"  # long string

    d = {key: 42}

    # Time 1M lookups
    N = 1_000_000
    t0 = time.perf_counter()
    total = 0
    for _ in range(N):
        total += d[key]
    t1 = time.perf_counter()
    print(f"1M dict lookups of same string key: {(t1-t0)*1000:.1f}ms "
          f"({(t1-t0)/N*1e9:.1f}ns each)")

    # Integer key — hash is identity (for small ints), always O(1)
    d2 = {0: 42}
    t0 = time.perf_counter()
    total = 0
    for _ in range(N):
        total += d2[0]
    t1 = time.perf_counter()
    print(f"1M dict lookups of integer key:     {(t1-t0)*1000:.1f}ms "
          f"({(t1-t0)/N*1e9:.1f}ns each)")
    # Integer lookup is usually 1.5-2x faster due to trivial hash


# ─────────────────────────────────────────────────────────────────────────────
# 3. The operator[] footgun — Python vs C++ difference
# ─────────────────────────────────────────────────────────────────────────────
def demonstrate_missing_key_behaviour():
    """
    Python: d[missing_key] raises KeyError — does NOT insert.
    C++:    mp[missing_key] VALUE-INITIALISES and inserts — silent mutation!

    This is the single most common semantic difference between the two.
    """
    d = {"a": 1}

    # Safe access patterns in Python:
    val = d.get("b", 0)                    # returns 0 if missing — no insertion
    val = d["a"]                           # direct access — KeyError if missing
    val = d.setdefault("c", [])            # inserts default only if missing, returns it

    # The C++ trap translated to Python (what NOT to do):
    # In C++, mp["new_key"] inserts with default value.
    # Python equivalent would be: d["new_key"]  -- but this RAISES, doesn't insert.
    # To replicate C++ behaviour: d.setdefault("new_key", default_value)

    # defaultdict — inserts default on first access (closest to C++ operator[])
    dd = collections.defaultdict(int)
    dd["x"] += 1   # inserts "x"→0, then increments to 1. No KeyError.
    dd["y"] += 5
    print(f"defaultdict: {dict(dd)}")

    # Counter — optimised for frequency counting
    text = "abracadabra"
    c = collections.Counter(text)          # O(n), fully in C
    print(f"Counter: {c}")
    print(f"Most common 3: {c.most_common(3)}")

    # Counter arithmetic (not available in plain dict)
    c2 = collections.Counter("aabbcc")
    print(f"c - c2: {c - c2}")            # subtract counts, floor at 0
    print(f"c & c2: {c & c2}")            # min of counts (intersection)
    print(f"c | c2: {c | c2}")            # max of counts (union)


# ─────────────────────────────────────────────────────────────────────────────
# 4. Iteration: O(n) in Python, O(n + m) in C++
# ─────────────────────────────────────────────────────────────────────────────
def demonstrate_iteration_cost():
    """
    Python dict iterates dk_entries — a DENSE array of live entries only.
    Iteration is exactly O(n), not O(n + m).

    C++ unordered_map iterates all bucket slots — O(n + m).
    If you reserved 1M buckets but have 3 entries, iteration scans 1M slots.

    For ML: iterating a large vocabulary dict is O(n), predictable.
    For ML: iterating a sparsely-populated C++ map is slow — avoid in hot path.
    """
    # Python: sparse dict (simulate large reserve, few inserts)
    d = {}
    for i in range(10):
        d[i * 100_000] = i   # keys far apart in value space

    N = 100_000
    t0 = time.perf_counter()
    for _ in range(N):
        total = sum(d.values())   # O(10) per iter — only 10 entries
    t1 = time.perf_counter()
    print(f"Python: iterating 10-entry dict {N}x: {(t1-t0)*1000:.1f}ms")
    # Constant regardless of key magnitude — compact dk_entries


# ─────────────────────────────────────────────────────────────────────────────
# 5. Pre-sizing for ML pipelines — avoiding mid-operation rehashes
# ─────────────────────────────────────────────────────────────────────────────
def presizing_for_ml():
    """
    Python dict resizes at 2/3 load. For a vocabulary of n tokens,
    the final dict has ~1.5n slots. During construction, multiple resizes occur.

    For large vocabularies (n > 10^5), pre-size using dict comprehension
    (CPython optimises this: allocates final-size table upfront).
    """
    vocab_tokens = [f"token_{i}" for i in range(100_000)]

    # Slow: incremental insertion, triggers O(log n) resizes
    t0 = time.perf_counter()
    slow_vocab = {}
    for i, tok in enumerate(vocab_tokens):
        slow_vocab[tok] = i
    t1 = time.perf_counter()
    slow_ms = (t1 - t0) * 1000

    # Fast: dict comprehension — CPython pre-allocates
    t0 = time.perf_counter()
    fast_vocab = {tok: i for i, tok in enumerate(vocab_tokens)}
    t1 = time.perf_counter()
    fast_ms = (t1 - t0) * 1000

    print(f"Incremental vocab build: {slow_ms:.1f}ms")
    print(f"Comprehension vocab build: {fast_ms:.1f}ms")
    print(f"Speedup: {slow_ms/fast_ms:.2f}x")
    print(f"Memory (both): {sys.getsizeof(slow_vocab):,} vs {sys.getsizeof(fast_vocab):,} bytes")
    assert slow_vocab == fast_vocab


# ─────────────────────────────────────────────────────────────────────────────
# 6. When to leave dict behind for ML workloads
# ─────────────────────────────────────────────────────────────────────────────
def when_to_use_alternatives():
    """
    Python dict: best for n < 10^6, mixed key types, arbitrary key lookup.

    For ML-specific patterns with large n:

    1. Token ID → embedding: use torch.nn.Embedding (direct array index, O(1))
       or numpy array if IDs are dense integers.

    2. String key → integer: for huge fixed vocabularies, consider:
       - dict (fine for n < 500k)
       - numpy searchsorted on sorted array (cache-friendly, O(log n) but simple)
       - Trie for prefix lookups (see [[29.Trie (prefix tree)]])

    3. Frequency counting over streaming data:
       - Counter: fast, but holds all keys in memory
       - CMS (Count-Min Sketch): probabilistic, O(1) space, see [[ML layer]]

    4. Deduplication of large datasets:
       - set/frozenset: same internal structure as dict (open addressing)
       - BloomFilter: probabilistic, O(1) memory, zero false negatives
       - MinHash for near-duplicate: see [[39.MinHash]]
    """
    import array

    # Dense integer → value mapping: array beats dict
    N = 100_000
    dense_keys = list(range(N))
    values = list(range(N))

    # Dict approach
    d = dict(zip(dense_keys, values))

    # Array approach (when keys are dense 0..N-1)
    arr = array.array('i', values)   # typed C array, 4 bytes/element

    print(f"\nFor dense integer keys 0..{N-1}:")
    print(f"  dict size:  {sys.getsizeof(d):>10,} bytes")
    print(f"  array size: {sys.getsizeof(arr):>10,} bytes")
    print(f"  Ratio: {sys.getsizeof(d)/sys.getsizeof(arr):.1f}x more memory for dict")

    # Timing
    key = 42_000
    M = 1_000_000
    t0 = time.perf_counter()
    for _ in range(M): _ = d[key]
    t1 = time.perf_counter()
    dict_ns = (t1 - t0) / M * 1e9

    t0 = time.perf_counter()
    for _ in range(M): _ = arr[key]
    t1 = time.perf_counter()
    arr_ns = (t1 - t0) / M * 1e9

    print(f"  dict lookup: {dict_ns:.1f}ns")
    print(f"  array index: {arr_ns:.1f}ns")
    print(f"  Array is {dict_ns/arr_ns:.1f}x faster for dense integer keys")


# ─────────────────────────────────────────────────────────────────────────────
# 7. Thread safety — critical for DataLoader workers
# ─────────────────────────────────────────────────────────────────────────────
def thread_safety_note():
    """
    Python dict is NOT thread-safe for concurrent writes.
    Reading from a dict that another thread may be writing to is UB in CPython.

    The GIL protects individual bytecode operations (LOAD_ATTR, STORE_SUBSCR)
    but NOT compound operations like:
        if key not in d: d[key] = value   ← TOCTOU race condition

    For PyTorch DataLoader with num_workers > 1:
    - Each worker gets its OWN copy of the dataset (fork() on Unix)
    - Shared vocab dict is READ-ONLY in workers → safe
    - Do NOT write to a shared dict from worker processes

    Thread-safe alternatives:
    - collections.OrderedDict: not thread-safe either
    - threading.Lock + dict: explicit locking
    - multiprocessing.Manager().dict(): process-safe but very slow
    - Avoid shared mutable state across workers entirely (preferred)
    """
    print("Thread safety: dict reads are safe; concurrent writes require explicit locking.")


if __name__ == "__main__":
    print("=== 1. Dict Memory Layout ===")
    measure_dict_memory()

    print("\n=== 2. Hash Caching ===")
    demonstrate_hash_caching()

    print("\n=== 3. Missing Key Behaviour ===")
    demonstrate_missing_key_behaviour()

    print("\n=== 4. Iteration Cost ===")
    demonstrate_iteration_cost()

    print("\n=== 5. Pre-sizing ===")
    presizing_for_ml()

    print("\n=== 6. When to Leave dict ===")
    when_to_use_alternatives()

    print("\n=== 7. Thread Safety ===")
    thread_safety_note()
```

## 7. Common Variations & Extensions

### 1. `std::map` vs `std::unordered_map` — When Ordering Wins

`std::map` uses a red-black tree (see [[148.Red-Black tree — insertion rules and colour invariants]]): $O(\log n)$ all operations, but supports `lower_bound`, `upper_bound`, ordered iteration, and range queries. Use `std::map` when: you need the $k$ nearest keys, you need to iterate keys in sorted order, or your access pattern is cache-unfriendly for any hash table. Use `unordered_map` when: you need pure O(1) lookup and have no ordering requirements.

### 2. Flat Hash Maps — The Practical Upgrade

`absl::flat_hash_map` (Google Abseil), `robin_hood::unordered_map`, and `tsl::robin_map` all use open-addressing with flat storage — the same layout as Python dict. They are drop-in replacements for `std::unordered_map` with 2–4× better lookup performance on large tables. In competitive programming where you control the build environment, `#include "robin_hood.h"` and `robin_hood::unordered_map<int,int>` is strictly better than `std::unordered_map`. In production C++ (ML inference engines, feature servers), Abseil is the standard choice.

### 3. `collections.OrderedDict` — Now Mostly Obsolete

Since Python 3.7, `dict` maintains insertion order. `OrderedDict` is only needed for `move_to_end(key, last=True/False)` (move key to front or back) and `popitem(last=False)` (FIFO pop). These operations implement an LRU cache — see LC 146. For all other uses, plain `dict` is equivalent and slightly faster.

### 4. `__slots__` and Custom Key Objects

If you use custom objects as dict keys, Python calls `__hash__` and `__eq__`. Without `__slots__`, each object has a `__dict__` (another hash table!), adding per-object overhead. Define `__slots__ = ('field1', 'field2')` on keys to eliminate their internal dicts. For ML: embedding lookup with named token objects — `__slots__` reduces memory by 40–60% per token object.

### The Standard CP Hash Map Setup (Copy-Paste Ready)

```cpp
// Drop this at the top of any CP solution using hash maps
#include <bits/stdc++.h>
using namespace std;

struct custom_hash {
    static uint64_t splitmix64(uint64_t x) {
        x += 0x9e3779b97f4a7c15ULL;
        x = (x ^ (x >> 30)) * 0xbf58476d1ce4e5b9ULL;
        x = (x ^ (x >> 27)) * 0x94d049bb133111ebULL;
        return x ^ (x >> 31);
    }
    // Required: support for all key types you use
    size_t operator()(uint64_t x) const {
        static const uint64_t R = chrono::steady_clock::now()
                                      .time_since_epoch().count();
        return splitmix64(x + R);
    }
    size_t operator()(pair<int,int> p) const {
        return operator()(((uint64_t)(uint32_t)p.first << 32) | (uint32_t)p.second);
    }
    size_t operator()(pair<long long, long long> p) const {
        return operator()((uint64_t)p.first) ^ (operator()((uint64_t)p.second) * 2654435761ULL);
    }
};

// Use this instead of unordered_map<K, V>:
```

### When This Appears in Contests

**Codeforces Div. 2 C–D / Div. 1 A–B:** Frequency map or seen-before set with $n \leq 2 \times 10^6$.  
**Time limit sensitivity:** At $n = 10^6$, well-set time limits (1–2s) often catch `unordered_map` without `reserve`. The gap between reserved + low load factor vs. default is 3–5× in wall-clock time.  
**Adversarial inputs:** Any problem on Codeforces with "integer keys" and public test cases has potential for hack submissions targeting the default hash. The `FIXED_RANDOM` salt eliminates this.
