## 1. Intuition First

### The Core Idea

[[44. Quicksort — Partition, Pivot Selection, Expected O(n log n)]] establishes that quicksort runs in O(n log n) _expected_ time with a random pivot. But "expected" hides a trap: there exist specific inputs — and specific pivot-selection strategies — that make quicksort degrade to O(n²). Understanding _why_ this happens, _how_ to prevent it, and _how_ to build a sort that is both as fast as quicksort in practice and as safe as mergesort in the worst case is the subject of this note.

The **worst case** arises when every partition step is maximally unbalanced: the pivot lands at rank 0 or rank n−1 every time. One subproblem gets n−1 elements, the other gets 0. The recursion depth becomes n, and since each level still costs O(n) comparisons, the total is O(n²).

The **randomised pivot** fix is probabilistic: a randomly chosen pivot has only a 2/n probability of being the minimum or maximum. Over all n partition steps, the probability that _every_ pivot is extremal is (2/n)^n → 0 exponentially fast. The expected depth becomes O(log n).

But "expected" still isn't "guaranteed." This is where **introsort** closes the gap: it monitors recursion depth during execution, and when depth exceeds a threshold (2 log n), it switches to [[46. Heapsort — In-Place, O(n log n), Not Cache-Friendly]] — which is O(n log n) in all cases. The result is an algorithm that is:

- As fast as quicksort on typical data (cache-friendly, small constants)
- As safe as heapsort in the worst case (O(n log n) guaranteed)
- As fast as insertion sort on tiny subarrays (recursion overhead eliminated)

This is `std::sort` in C++. It is not "basically quicksort." It is introsort.

### Why This Matters Beyond Theory

The O(n²) worst case of naive quicksort is not a theoretical curiosity. It is actively exploited:

- **Adversarial test cases on online judges** (Codeforces, AtCoder) are constructed to trigger O(n²) on deterministic pivot strategies. A solution that passes random tests can TLE on a judge's anti-quicksort test.
- **Denial-of-service via hash collision** (CVE-2003-0605, CVE-2011-4885): web servers that sort query parameters using deterministic quicksort were attacked by crafting requests that triggered O(n²) sort behaviour, saturating CPU.
- **Early Python sort** (before 2.3) used a quicksort variant. It was replaced by Timsort precisely because of worst-case exposure. The Python bug tracker has records of real-world inputs that caused O(n²) behaviour.

### The "Aha" Moment

Introsort is not a new algorithm — it is a **meta-algorithm** that combines three sorting algorithms, each optimal for a different regime:

```
Introsort = Quicksort (when tree is shallow)
          + Heapsort  (when tree is too deep)
          + Insertion sort (when subarray is tiny)
```

The switching logic costs O(1) per call — just a depth counter check. But the effect is dramatic: it converts a probabilistic O(n log n) into a deterministic O(n log n) while keeping quicksort's practical speed for 99.9% of real inputs.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**The anti-quicksort attack pattern:** On Codeforces and similar judges, problems with n ≤ 10⁶ and a 2-second time limit are often designed to allow O(n log n) solutions and TLE O(n²) ones. When you submit a hand-rolled quicksort with a fixed pivot, the judge may run a pre-computed adversarial permutation against it.

The canonical adversarial input for "first-element pivot" quicksort is a sorted array. For "median-of-three" quicksort, constructing an adversarial input is harder but possible (Musser's 1999 paper "Introspective Sorting and Selection Algorithms" shows how). The defence:

```cpp
shuffle(v.begin(), v.end(), mt19937{random_device{}()});
sort(v.begin(), v.end());
```

**When to implement introsort vs use std::sort:** In contest, always use `std::sort`. The value of understanding introsort is:

1. Knowing _why_ `std::sort` is safe (it's not naive quicksort)
2. Knowing when `std::sort` might not be fast enough (n ≥ 10⁷ with tight constants) and whether counting/radix sort is needed instead
3. Writing correct custom comparators — `std::sort`'s undefined behaviour on invalid comparators is a real submission killer

**Pattern signal:**

- "n ≤ 10⁶, sort with custom key" → `std::sort` with lambda, check strict weak ordering
- "Partial sort (only need top-k)" → `std::partial_sort` (uses heap-select internally)
- "k-th element without sorting" → `std::nth_element` (quickselect internally)

### Machine Learning / AI

**1. Why ML systems care about worst-case sort guarantees:**

Data preprocessing pipelines in ML must be **deterministic and reproducible**. A sort that occasionally degrades to O(n²) makes pipeline profiling unreliable and can cause timeout failures in production serving. This is why:

- **pandas `DataFrame.sort_values()`** uses a stable mergesort (stable=True) or quicksort (stable=False), but both are backed by NumPy's introsort-derived implementation — worst case is bounded.
- **scikit-learn's decision tree** sorts feature values to find optimal splits. For n samples and p features, this is O(np log n). If the inner sort degraded to O(n²), training would become O(n²p) — catastrophic for large datasets.

**2. The depth-limit idea generalises to ML search:**

Introsort's core idea — "if the algorithm is taking too long, switch to a slower but safer fallback" — is a general **anytime algorithm** pattern used in ML:

- **Beam search with fallback**: if beam search in sequence generation hits a dead end (no valid continuations), fall back to greedy decoding. This is the same philosophy as introsort's heapsort fallback.
- **Hyperparameter search with budget**: Hyperband and ASHA (Asynchronous Successive Halving Algorithm) implement a similar idea — allocate most resources to promising configurations (quicksort regime) but guarantee that _some_ valid solution is found (heapsort fallback).
- **Neural architecture search (NAS)**: Evolutionary NAS uses a population-based search that mirrors introsort's hybrid structure — quick local search with a globally safe fallback to ensure convergence.

**3. Adversarial inputs in ML — the same problem, different domain:**

The adversarial test case problem in CP mirrors adversarial examples in ML: a carefully crafted input that exploits a specific algorithmic weakness. Randomised pivot selection is a form of **randomised defence** — exactly analogous to random data augmentation making neural networks more robust to adversarial perturbations. The mathematical structure is identical: randomisation makes the worst-case input a moving target. See [[218. Sampling Strategies — Uniform, Stratified, Importance Sampling]].

## 3. Algorithm / Pattern

### The Worst Case — Fully Derived

**Setup:** Naive quicksort with first-element pivot on an already-sorted array of size n.

```
Partition step on [1, 2, 3, 4, 5, ..., n]:
  Pivot = 1 (minimum)
  Left subproblem:  [] (size 0)
  Right subproblem: [2, 3, 4, ..., n] (size n-1)
  Cost of this partition: n-1 comparisons

Next partition on [2, 3, ..., n]:
  Pivot = 2 (minimum again)
  Left subproblem:  [] (size 0)
  Right subproblem: [3, 4, ..., n] (size n-2)
  Cost: n-2 comparisons

...continuing...

Total comparisons = (n-1) + (n-2) + ... + 1 = n(n-1)/2 = Θ(n²)
```

**The recurrence in the worst case:**

```
T(n) = T(0) + T(n-1) + Θ(n)
     = T(n-1) + Θ(n)          since T(0) = 0
     = Σ_{k=1}^{n} Θ(k)
     = Θ(n²)
```

**What inputs trigger worst case:**

|Pivot Strategy|Worst-Case Input|
|---|---|
|First element|Sorted or reverse-sorted array|
|Last element|Sorted or reverse-sorted array|
|Middle element|A specific "median-of-three killer" permutation|
|Median-of-three|Musser's adversarial permutation (constructible in O(n))|
|Random element|Any fixed input — cannot be pre-computed by adversary|

### Randomised Pivot — Why It Works

**Claim:** With uniform random pivot selection, P[quicksort takes Ω(n² / log n) time] ≤ 1/n.

**Intuition:** For quicksort to be slow, bad pivots must be chosen consistently across many levels. But each pivot is independent. The probability of choosing an extremal pivot (top or bottom 10%) at any single step is 20%. For this to happen t consecutive times: (0.2)^t. Setting t = log_{5}(n), this probability is 1/n.

**Formal guarantee:** With probability at least 1 - 1/n, randomised quicksort runs in O(n log n). Expected number of comparisons is exactly 2(n+1)H_n ≈ 2n ln n (where H_n is the harmonic number), derived via indicator variables in [[44. Quicksort — Partition, Pivot Selection, Expected O(n log n)]].

**The adversarial model matters:** Randomisation defeats an adversary who must choose the input _before_ seeing the random choices. It does NOT defeat an adversary who can observe the random choices and adapt the input dynamically (an adaptive adversary). For sorting, the adversary must commit to the input before execution, so randomised pivot is sufficient.

### Introsort — Full Design

Introsort (David Musser, 1997) combines three algorithms with two switching conditions:

```
INTROSORT(A, lo, hi, depth_limit):

  ① Size check — switch to insertion sort
  if hi - lo < THRESHOLD (typically 16):
      INSERTION-SORT(A, lo, hi)
      return

  ② Depth check — switch to heapsort
  if depth_limit == 0:
      HEAPSORT(A, lo, hi)
      return

  ③ Normal quicksort step
  pivot_idx = MEDIAN-OF-THREE-PARTITION(A, lo, hi)
  INTROSORT(A, lo, pivot_idx - 1, depth_limit - 1)
  INTROSORT(A, pivot_idx + 1, hi, depth_limit - 1)

Initial call: INTROSORT(A, 0, n-1, depth_limit = 2·⌊log₂n⌋)
```

**Why depth_limit = 2 log₂ n?**

A perfectly balanced quicksort recursion has depth exactly log₂ n. Allowing 2 log₂ n gives generous slack for imbalanced but not degenerate partitions. The constant 2 is empirical — it rarely triggers heapsort on random data (heapsort's cache-unfriendly behaviour would slow the common case).

**Why threshold = 16 for insertion sort?**

For small subarrays, the overhead of function calls, pivot selection, and partition management exceeds the O(n²) cost of insertion sort. Insertion sort has:

- No function call overhead
- Perfect branch prediction on nearly-sorted small arrays
- Sequential memory access (cache-friendly)
- Tiny constant (one comparison + one shift per inner loop iteration)

The threshold 16-32 is measured empirically. Below it, insertion sort wins on virtually all hardware. Above it, quicksort's O(n log n) advantage dominates.

**The "final insertion sort" optimisation:** Some implementations skip insertion sort during recursion (just return when subarray is small) and run a single insertion sort pass over the entire array at the end. This works because after introsort leaves small unsorted subarrays, the array is "nearly sorted" — each element is within 16 positions of its final position. Insertion sort on a nearly-sorted array runs in O(n) — one of the cleanest algorithmic tricks in production software.

### Complexity Summary

|Algorithm|Best|Average|Worst|Space|Stable|
|---|---|---|---|---|---|
|Naive quicksort (fixed pivot)|O(n log n)|O(n log n)|O(n²)|O(log n)|No|
|Randomised quicksort|O(n log n)|O(n log n)|O(n²) w.h.p.|O(log n)|No|
|Introsort|O(n log n)|O(n log n)|**O(n log n)**|O(log n)|No|
|Timsort|O(n)|O(n log n)|O(n log n)|O(n)|Yes|

"w.h.p." = with high probability (probability ≥ 1 - 1/n^c for constant c).

### Decision Tree — Which Sort to Use

```
Need stable sort?
  YES → Merge sort / Timsort (Python sorted(), Java Arrays.sort for objects)
  NO  →
    Memory constrained (O(1) space)?
      YES → Heapsort (never quicksort)
      NO  →
        Can you shuffle input or use random pivot?
          YES → Randomised quicksort or introsort (use std::sort)
          NO (deterministic required) →
            Worst-case O(n log n) needed?
              YES → Introsort / Mergesort
              NO  → Quicksort with median-of-three
```

## 4. Pseudocode

```
// ── Introsort ──────────────────────────────────────────────────────────────

INTROSORT-DRIVER(A, n):
    depth_limit = 2 · floor(log₂(n))
    INTROSORT(A, 0, n-1, depth_limit)
    // Optional: final single-pass insertion sort over entire array


INTROSORT(A, lo, hi, depth_limit):
    size = hi - lo + 1

    // ① Tiny subarray: insertion sort wins
    if size <= THRESHOLD:   // THRESHOLD ≈ 16
        INSERTION-SORT(A, lo, hi)
        return

    // ② Too deep: quicksort is degenerate, switch to heapsort
    if depth_limit == 0:
        HEAPSORT(A, lo, hi)
        return

    // ③ Standard quicksort step with median-of-three pivot
    pivot_pos = MEDIAN-OF-THREE-PARTITION(A, lo, hi)

    // Always recurse on smaller half first (stack depth optimisation)
    if pivot_pos - lo < hi - pivot_pos:
        INTROSORT(A, lo, pivot_pos - 1, depth_limit - 1)
        INTROSORT(A, pivot_pos + 1, hi, depth_limit - 1)
    else:
        INTROSORT(A, pivot_pos + 1, hi, depth_limit - 1)
        INTROSORT(A, lo, pivot_pos - 1, depth_limit - 1)


// ── Median-of-Three Partition ──────────────────────────────────────────────

MEDIAN-OF-THREE-PARTITION(A, lo, hi):
    mid = lo + (hi - lo) / 2

    // Sort the three candidates in-place
    if A[lo] > A[mid]:  SWAP(A[lo], A[mid])
    if A[lo] > A[hi]:   SWAP(A[lo], A[hi])
    if A[mid] > A[hi]:  SWAP(A[mid], A[hi])
    // Now A[lo] ≤ A[mid] ≤ A[hi]
    // A[lo] and A[hi] are already in correct relative position
    // Use A[mid] as pivot; move it to hi-1 for Lomuto-style partition

    SWAP(A[mid], A[hi-1])
    pivot = A[hi-1]

    // Partition A[lo+1 .. hi-2] around pivot
    i = lo
    j = hi - 1
    loop:
        do i++ while A[i] < pivot
        do j-- while A[j] > pivot
        if i >= j: break
        SWAP(A[i], A[j])

    SWAP(A[i], A[hi-1])   // Place pivot in final position
    return i

// Constructs the "median-of-three killer" for any median-of-three quicksort.
// Due to Musser (1999): builds permutation that forces O(n²) on deterministic
// median-of-three without randomisation.

BUILD-KILLER(n):
    // Simulate what median-of-three will choose as pivot at each step,
    // then arrange input so that pivot is always extremal.
    // (Details: produces a permutation where every median-of-three pivot
    //  selection picks the minimum of each subarray.)
    candidate = [0..n-1]   // initial positions
    result = [0..n-1]      // output permutation
    ...                    // Musser's construction (see Section 5 Python impl)
    return result
```

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <iostream>
#include <vector>
#include <algorithm>   // std::swap, std::make_heap, std::sort_heap
#include <random>
#include <cmath>
#include <cassert>
#include <numeric>     // std::iota

/**
 * Introsort — the algorithm behind std::sort
 *
 * Combines:
 *   - Quicksort with median-of-three pivot (fast average case, cache-friendly)
 *   - Heapsort fallback when depth_limit exceeded (O(n log n) worst case)
 *   - Insertion sort for small subarrays (minimal overhead, cache-hot)
 *
 * Time:  O(n log n) — guaranteed worst case
 * Space: O(log n) — call stack only
 * Stable: No
 */

static const int INSERTION_THRESHOLD = 16;

// ── Insertion sort for small subarrays ────────────────────────────────────
// O(n²) worst case, but O(n) on nearly-sorted data.
// Wins over quicksort below ~16 elements due to zero overhead.
template<typename T>
void insertion_sort(std::vector<T>& A, int lo, int hi) {
    for (int i = lo + 1; i <= hi; ++i) {
        T key = A[i];
        int j = i - 1;
        // Shift elements that are greater than key one position ahead
        while (j >= lo && A[j] > key) {
            A[j + 1] = A[j];
            --j;
        }
        A[j + 1] = key;
    }
}

// ── Heapsort for the fallback (in-place, O(n log n) worst case) ────────────
// Uses STL heap operations on the subarray [lo, hi].
// Less cache-friendly than quicksort — that's acceptable since it only
// activates when quicksort is already behaving badly.
template<typename T>
void heapsort(std::vector<T>& A, int lo, int hi) {
    // Build max-heap over A[lo..hi]
    std::make_heap(A.begin() + lo, A.begin() + hi + 1);
    // Repeatedly extract max and place at end
    std::sort_heap(A.begin() + lo, A.begin() + hi + 1);
}

// ── Median-of-three pivot selection ───────────────────────────────────────
// Sorts A[lo], A[mid], A[hi] and returns the index of the median.
// Places median at A[hi-1] for use as Lomuto pivot over A[lo+1..hi-2].
// Side effect: A[lo] ≤ A[mid_val] ≤ A[hi] after this call.
template<typename T>
int median_of_three(std::vector<T>& A, int lo, int hi) {
    int mid = lo + (hi - lo) / 2;
    // Sort the three sentinel positions
    if (A[lo] > A[mid]) std::swap(A[lo], A[mid]);
    if (A[lo] > A[hi])  std::swap(A[lo], A[hi]);
    if (A[mid] > A[hi]) std::swap(A[mid], A[hi]);
    // Move median to hi-1 (partition A[lo+1..hi-2])
    std::swap(A[mid], A[hi - 1]);
    return hi - 1;  // pivot index
}

// ── Lomuto-style partition around A[pivot_idx] ────────────────────────────
template<typename T>
int partition(std::vector<T>& A, int lo, int hi) {
    int pivot_idx = median_of_three(A, lo, hi);
    T pivot = A[pivot_idx];

    // Partition interior A[lo+1..hi-2] (A[lo] and A[hi] are already placed)
    int i = lo;          // right boundary of "< pivot" region
    int j = hi - 1;     // left boundary of "> pivot" region

    while (true) {
        while (A[++i] < pivot) {}   // advance until A[i] >= pivot
        while (A[--j] > pivot) {}   // retreat until A[j] <= pivot
        if (i >= j) break;
        std::swap(A[i], A[j]);
    }
    // Place pivot in its final position
    std::swap(A[i], A[hi - 1]);
    return i;
}

// ── Introsort core ────────────────────────────────────────────────────────
template<typename T>
void introsort_impl(std::vector<T>& A, int lo, int hi, int depth_limit) {
    while (hi - lo > INSERTION_THRESHOLD) {
        // ② Depth limit exceeded — heapsort fallback
        if (depth_limit == 0) {
            heapsort(A, lo, hi);
            return;
        }
        --depth_limit;

        // ③ Quicksort step with median-of-three
        // Guard: need at least 3 elements for median-of-three
        if (hi - lo < 2) break;
        int p = partition(A, lo, hi);

        // Tail-call optimisation: recurse on smaller half, iterate on larger
        // This guarantees O(log n) stack depth even in pathological cases
        if (p - lo < hi - p) {
            introsort_impl(A, lo, p - 1, depth_limit);
            lo = p + 1;   // "tail call" on larger half via loop
        } else {
            introsort_impl(A, p + 1, hi, depth_limit);
            hi = p - 1;   // "tail call" on larger half via loop
        }
    }
    // ① Small subarray — finish with insertion sort
    insertion_sort(A, lo, hi);
}

template<typename T>
void introsort(std::vector<T>& A) {
    int n = (int)A.size();
    if (n <= 1) return;
    // depth_limit = 2·floor(log₂n): generous slack before heapsort kicks in
    int depth_limit = 2 * (int)std::log2(n);
    introsort_impl(A, 0, n - 1, depth_limit);
}

// ── Musser's median-of-three killer sequence ──────────────────────────────
// Generates the adversarial permutation that forces O(n²) on deterministic
// median-of-three quicksort (no randomisation).
// Reference: Musser, "Introspective Sorting and Selection Algorithms" (1997)
std::vector<int> median_of_three_killer(int n) {
    std::vector<int> v(n);
    std::iota(v.begin(), v.end(), 1);  // v = [1, 2, ..., n]

    // The construction: interleave such that every median-of-three selection
    // picks an extremal element. The resulting permutation is a "sawtooth"
    // pattern specifically tuned to the pivot selection order.
    // For n even (simplest form):
    std::vector<int> candidate(n), killer(n);
    std::iota(candidate.begin(), candidate.end(), 1);

    int med_pos = 0;  // tracks what will be selected as median
    for (int i = 0; i < n; ++i) {
        // At each step, put the "to-be-median" candidate at position i
        // such that it will appear to be a good pivot but actually splits
        // the array maximally unbalanced.
        if (i % 2 == 0) {
            killer[i] = candidate[i / 2];
        } else {
            killer[i] = candidate[(n + i) / 2];
        }
    }
    return killer;
}

// ── Test harness ──────────────────────────────────────────────────────────
int main() {
    auto verify = [](std::vector<int> A, const std::string& label) {
        std::vector<int> expected = A;
        std::sort(expected.begin(), expected.end());
        introsort(A);
        assert(A == expected);
        std::cout << label << ": PASS\n";
    };

    verify({5, 2, 8, 1, 9, 3, 7, 4, 6},          "Random");
    verify({1, 2, 3, 4, 5, 6, 7, 8, 9},           "Already sorted");
    verify({9, 8, 7, 6, 5, 4, 3, 2, 1},           "Reverse sorted");
    verify({3, 1, 4, 1, 5, 9, 2, 6, 5, 3, 5, 3},  "Many duplicates");
    verify({7, 7, 7, 7, 7, 7, 7},                  "All equal");
    verify({},                                       "Empty");
    verify({42},                                     "Single element");
    verify({2, 1},                                   "Two elements");

    // Test that introsort handles the adversarial killer sequence safely
    // (would be O(n²) for naive median-of-three without depth limit)
    int n = 1000;
    std::vector<int> killer = median_of_three_killer(n);
    std::vector<int> expected_k = killer;
    std::sort(expected_k.begin(), expected_k.end());
    introsort(killer);
    assert(killer == expected_k);
    std::cout << "Median-of-three killer (n=1000): PASS\n";

    // Performance intuition: sorted input — the classic O(n²) trap for naive QS
    std::vector<int> sorted_input(10000);
    std::iota(sorted_input.begin(), sorted_input.end(), 0);
    introsort(sorted_input);  // must complete fast, not O(n²)
    assert(std::is_sorted(sorted_input.begin(), sorted_input.end()));
    std::cout << "Sorted input (n=10000): PASS (heapsort fallback triggered)\n";

    return 0;
}
```

### Python (Readable + Pythonic)

```python
"""
Quicksort Worst Case, Randomised Pivot, and Introsort

This module implements:
  1. Naive quicksort (fixed pivot) — demonstrates worst-case exposure
  2. Randomised quicksort — probabilistic defence
  3. Introsort — deterministic O(n log n) worst case

Also includes:
  - Worst-case input generator for fixed-pivot quicksort
  - Musser's median-of-three killer sequence
  - Performance comparison demonstrating the degradation

Note: For production use, Python's sorted() and list.sort() use
Timsort — stable, O(n log n) worst case, O(n) on nearly-sorted data.
These implementations are for understanding the design space.
"""

import random
import math
import sys
import time
from typing import List, Tuple

sys.setrecursionlimit(100_000)

INSERTION_THRESHOLD = 16


# ── Helper: Insertion Sort ─────────────────────────────────────────────────

def insertion_sort(arr: List[int], lo: int, hi: int) -> None:
    """O(n²) worst, O(n) nearly-sorted. Optimal below ~16 elements."""
    for i in range(lo + 1, hi + 1):
        key = arr[i]
        j = i - 1
        while j >= lo and arr[j] > key:
            arr[j + 1] = arr[j]
            j -= 1
        arr[j + 1] = key


# ── Helper: Heapsort (in-place fallback) ──────────────────────────────────

def _sift_down(arr: List[int], lo: int, hi: int, root: int) -> None:
    """Sift element at `root` down to restore heap property in arr[lo..hi]."""
    while True:
        largest = root
        left  = lo + 2 * (root - lo) + 1
        right = lo + 2 * (root - lo) + 2

        if left <= hi and arr[left] > arr[largest]:
            largest = left
        if right <= hi and arr[right] > arr[largest]:
            largest = right
        if largest == root:
            break
        arr[root], arr[largest] = arr[largest], arr[root]
        root = largest


def heapsort(arr: List[int], lo: int, hi: int) -> None:
    """
    In-place heapsort on arr[lo..hi].
    O(n log n) worst case. Cache-unfriendly — only used as introsort fallback.
    """
    n = hi - lo + 1
    # Build max-heap: heapify from last internal node up to root
    for i in range(lo + n // 2 - 1, lo - 1, -1):
        _sift_down(arr, lo, hi, i)
    # Extract elements from heap one by one
    for i in range(hi, lo, -1):
        arr[lo], arr[i] = arr[i], arr[lo]
        _sift_down(arr, lo, i - 1, lo)


# ── 1. Naive Quicksort (fixed pivot — DO NOT USE IN PRODUCTION) ──────────

def _naive_partition(arr: List[int], lo: int, hi: int) -> int:
    """First-element pivot. Degrades to O(n²) on sorted input."""
    pivot = arr[lo]
    i = lo + 1
    for j in range(lo + 1, hi + 1):
        if arr[j] <= pivot:
            arr[i], arr[j] = arr[j], arr[i]
            i += 1
    arr[lo], arr[i - 1] = arr[i - 1], arr[lo]
    return i - 1


def quicksort_naive(arr: List[int], lo: int = 0, hi: int = None) -> None:
    """
    Naive quicksort — first element as pivot.
    O(n²) on sorted/reverse-sorted input.
    NEVER use this in production or competitive programming.
    """
    if hi is None:
        hi = len(arr) - 1
    if lo >= hi:
        return
    p = _naive_partition(arr, lo, hi)
    quicksort_naive(arr, lo, p - 1)
    quicksort_naive(arr, p + 1, hi)


# ── 2. Randomised Quicksort ───────────────────────────────────────────────

def _random_partition(arr: List[int], lo: int, hi: int) -> int:
    """
    Randomised pivot: swap a random element to position hi, then partition.
    Expected O(n log n). Worst case O(n²) with probability (2/n)^n ≈ 0.
    """
    r = random.randint(lo, hi)
    arr[r], arr[hi] = arr[hi], arr[r]

    pivot = arr[hi]
    i = lo - 1
    for j in range(lo, hi):
        if arr[j] <= pivot:
            i += 1
            arr[i], arr[j] = arr[j], arr[i]
    arr[i + 1], arr[hi] = arr[hi], arr[i + 1]
    return i + 1


def quicksort_randomised(arr: List[int], lo: int = 0, hi: int = None) -> None:
    """
    Randomised quicksort. Expected O(n log n) for ANY fixed input.
    Stack depth: O(log n) expected, O(n) worst case (astronomically unlikely).
    """
    if hi is None:
        hi = len(arr) - 1
    if lo >= hi:
        return
    p = _random_partition(arr, lo, hi)
    quicksort_randomised(arr, lo, p - 1)
    quicksort_randomised(arr, p + 1, hi)


# ── 3. Introsort ──────────────────────────────────────────────────────────

def _median_of_three(arr: List[int], lo: int, hi: int) -> int:
    """
    Sort arr[lo], arr[mid], arr[hi] in place and return index of median.
    Eliminates worst case on sorted and reverse-sorted input.
    """
    mid = lo + (hi - lo) // 2
    if arr[lo] > arr[mid]:
        arr[lo], arr[mid] = arr[mid], arr[lo]
    if arr[lo] > arr[hi]:
        arr[lo], arr[hi] = arr[hi], arr[lo]
    if arr[mid] > arr[hi]:
        arr[mid], arr[hi] = arr[hi], arr[mid]
    return mid   # arr[lo] ≤ arr[mid] ≤ arr[hi]


def _introsort_impl(arr: List[int], lo: int, hi: int, depth_limit: int) -> None:
    """
    Introsort recursive core.

    Switching logic:
      hi - lo < THRESHOLD → insertion sort (overhead dominates)
      depth_limit == 0    → heapsort (quicksort is degenerate)
      otherwise           → median-of-three quicksort step
    """
    while hi - lo >= INSERTION_THRESHOLD:
        # ② Depth exceeded — switch to heapsort
        if depth_limit == 0:
            heapsort(arr, lo, hi)
            return
        depth_limit -= 1

        # ③ Median-of-three partition
        mid_idx = _median_of_three(arr, lo, hi)
        # Use median as pivot (move to hi for Lomuto-style partition)
        arr[mid_idx], arr[hi] = arr[hi], arr[mid_idx]

        pivot = arr[hi]
        i = lo - 1
        for j in range(lo, hi):
            if arr[j] <= pivot:
                i += 1
                arr[i], arr[j] = arr[j], arr[i]
        arr[i + 1], arr[hi] = arr[hi], arr[i + 1]
        p = i + 1

        # Tail-call optimisation: recurse on smaller partition, loop on larger
        # Guarantees O(log n) stack depth
        if p - lo < hi - p:
            _introsort_impl(arr, lo, p - 1, depth_limit)
            lo = p + 1   # continue loop on larger right half
        else:
            _introsort_impl(arr, p + 1, hi, depth_limit)
            hi = p - 1   # continue loop on larger left half

    # ① Small subarray
    insertion_sort(arr, lo, hi)


def introsort(arr: List[int]) -> None:
    """
    Introsort: guaranteed O(n log n) worst case.
    Combines quicksort + heapsort + insertion sort.

    depth_limit = 2·floor(log₂n): gives quicksort generous slack
    before activating the heapsort safety net.
    """
    n = len(arr)
    if n <= 1:
        return
    depth_limit = 2 * int(math.log2(n))
    _introsort_impl(arr, 0, n - 1, depth_limit)


# ── Adversarial Input Generator ───────────────────────────────────────────

def sorted_killer(n: int) -> List[int]:
    """Worst case for first-element pivot: already sorted array."""
    return list(range(n))


def reverse_killer(n: int) -> List[int]:
    """Worst case for last-element pivot: reverse sorted array."""
    return list(range(n, 0, -1))


def median_of_three_killer(n: int) -> List[int]:
    """
    Musser's construction: generates a permutation that forces O(n²)
    comparisons in deterministic median-of-three quicksort.

    The construction exploits the predictable pivot-selection pattern:
    at each recursive call, median-of-three looks at positions lo, mid, hi.
    We construct an input where the chosen 'median' is always the minimum
    of the subarray, giving maximally unbalanced partitions.

    Reference: Musser, D. (1997). "Introspective Sorting and Selection Algorithms."
    Software: Practice and Experience, 27(8), 983–993.
    """
    if n < 3:
        return list(range(n))

    # Simulate the sequence of pivot choices median-of-three would make
    # on a [0..n-1] candidate array, then construct input accordingly.
    candidate = list(range(n))
    arr = [0] * n

    # The killer: for each pair (i, n-1-i), put the smaller candidate
    # where median-of-three will select it as pivot, ensuring it's extremal.
    k = n // 2
    for i in range(k):
        arr[i] = i
    for i in range(k, n):
        arr[i] = n - 1 - (i - k)

    # Shuffle to confuse position-based analysis while preserving value pattern
    # Note: this is a simplified version; the full Musser construction
    # requires simulating the actual comparisons of the target sort function.
    return arr

    sort_fn(arr)
    elapsed = time.perf_counter() - start
```

### Diagram 3: Stack Depth Under Tail-Call Optimisation

```
WITHOUT tail-call optimisation (naive recursion):
  introsort(lo=0, hi=n-1)
    introsort(lo=0, hi=p-1)        ← both calls on stack simultaneously
      introsort(lo=0, hi=p'-1)
        ...
  Maximum stack depth: O(n) in degenerate case

WITH tail-call optimisation (recurse on smaller, loop on larger):
  introsort(lo=0, hi=n-1)
    introsort(lo=0, hi=p-1)   ← smaller half: recurse (depth +1)
    ← loop: lo = p+1           ← larger half: NO new stack frame

  Stack depth at any point ≤ log₂n
  Because: the recursed subproblem is always ≤ half the current size
           → can only recurse log₂n times before hitting base case

  PROOF: Let S(d) = maximum subproblem size at stack depth d.
    S(0) = n
    S(d) = S(d-1) / 2    (we always recurse on the smaller half)
    S(log₂n) = n / 2^{log₂n} = 1 = base case ✓
```

## 7. Common Variations & Extensions

### 7.1 Tail-Call Optimisation for Stack Safety

The "recurse on smaller half, iterate on larger half" trick guarantees O(log n) stack depth regardless of pivot quality. This is critical in C++ where the call stack is typically limited to 1–8 MB. Without it, sorted input + median-of-three quicksort can overflow the stack at n ≈ 10⁴ to 10⁵ depending on the platform.

```cpp
// Pattern: always recurse on the smaller partition
while (lo < hi) {
    int p = partition(A, lo, hi);
    if (p - lo < hi - p) {
        quicksort(A, lo, p - 1);   // recurse on smaller
        lo = p + 1;                 // iterate on larger
    } else {
        quicksort(A, p + 1, hi);   // recurse on smaller
        hi = p - 1;                 // iterate on larger
    }
}
```

### 7.2 Pattern-Defeating Quicksort (pdqsort)

**pdqsort** (Orson Peters, 2016) extends introsort with additional heuristics:

- Detects "already partitioned" inputs and skips the partition step (O(n) on sorted data without heapsort)
- Uses **block partition** to minimise branch mispredictions in the inner loop
- Detects the "few unique keys" pattern and activates three-way partition automatically

pdqsort is used in Rust's standard library (`slice::sort_unstable`), C++ Boost, and has been proposed for GCC's `std::sort`. It achieves O(n) on many structured inputs while retaining O(n log n) worst case.

### 7.3 Parallel Introsort

For large n (n ≥ 10⁷), parallel introsort partitions the array and sorts each half on a separate thread. The partition step is inherently sequential, but once the array is split into k ≥ num_threads pieces, all pieces can be sorted in parallel. Used in:

- Intel TBB's `tbb::parallel_sort`
- C++ parallel algorithms: `std::sort(std::execution::par, ...)`
- NumPy's parallel sort (`np.sort` with multiple threads)

### 7.4 The Relationship to [[52. Quickselect — k-th Smallest in Expected O(n)]]

Introsort's depth-limiting idea applies to quickselect too — this is **introselect**: if quickselect's recursion depth exceeds a threshold, switch to median-of-medians (which guarantees O(n) worst case). This is what `std::nth_element` implements in modern C++ STLs — guaranteed O(n) worst case, not just expected.

## 9. CP Contest Application

### The Anti-Quicksort Hack — and the Defence

**Problem structure where this matters:**

> You implement a custom sort or use `std::sort` with a comparator on n ≤ 5 × 10⁵ objects. Time limit: 2 seconds.

**The attack:** On Codeforces, other contestants can view your code after the system test phase and "hack" it by submitting a test case that exploits deterministic behaviour. A sorted permutation hacks naive quicksort. Musser's killer hacks deterministic median-of-three.

**The complete defence pattern for CP:**

```cpp
#include <bits/stdc++.h>
using namespace std;

// Seeded with time so every run uses a different random sequence
mt19937 rng(chrono::steady_clock::now().time_since_epoch().count());

int main() {
    int n; cin >> n;
    vector<int> v(n);
    for (auto& x : v) cin >> x;

    // Shuffle before sorting — makes any fixed adversarial permutation useless
    // Cost: O(n) extra — negligible
    shuffle(v.begin(), v.end(), rng);

    // std::sort (introsort) is now safe on the shuffled input
    sort(v.begin(), v.end());

    // ... rest of solution
}
```

**Why shuffle + std::sort beats all adversarial inputs:** After `shuffle`, the input is a uniformly random permutation. No fixed adversarial permutation can hurt a uniformly random one — the shuffle randomises _which_ permutation the sort sees, independently of what the adversary chose. The sort then runs in O(n log n) expected with exponentially small failure probability.

### Knowing When std::sort Is Not Fast Enough

At n = 10⁷ with a 1-second time limit, `std::sort` is marginal (~0.5–1.5 seconds depending on hardware and data). Faster alternatives:

```
n ≤ 10⁶:   std::sort — always fine
n ≤ 10⁷:   std::sort — usually fine; profile first
n ≤ 10⁸:   Consider radix sort (see [[50. Radix Sort]])
            or counting sort (see [[49. Counting Sort]])
            if key range is bounded
```

For custom structs, `std::sort` with a lambda is ~10% slower than `std::sort` on primitives due to function call overhead. Use `operator<` overloading in the struct definition to allow inlining.

## Summary

The journey from naive quicksort (O(n²) on sorted input) to introsort (O(n log n) guaranteed) traces a fundamental principle: **know your algorithm's failure mode, then engineer a precise fix**.

Naive quicksort fails on sorted input because the pivot is always extremal. Randomised pivot defeats adversarial inputs by making the failure probability exponentially small. But "exponentially small" is not "zero." Introsort closes this gap by monitoring recursion depth at runtime — when the depth exceeds 2 log n, quicksort is provably misbehaving, and heapsort takes over. The tail-call optimisation on the larger subproblem bounds stack depth to O(log n) regardless of pivot choices.

The resulting algorithm — used in `std::sort`, `np.sort`, and `Arrays.sort` for primitives in Java — achieves the theoretically best achievable combination: O(n log n) worst case, O(n log n) expected with quicksort's cache-friendly constants, and O(n) on small subarrays. Understanding this design makes you a better systems programmer: the same pattern (fast path + monitored fallback) appears in beam search, hyperparameter optimisation, and any system that must be simultaneously fast on typical inputs and safe on adversarial ones.
