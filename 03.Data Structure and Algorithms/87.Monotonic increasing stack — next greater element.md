## 1. Intuition First

### The Core Idea

Imagine you are standing in a line of people of varying heights, and for each person you want to know: _who is the next taller person to my right?_

The naive approach: for every person, scan everyone to their right until you find someone taller. That is O(n²) — scanning the entire crowd for every single person.

The insight: **you only need to remember people who are still "waiting" for their answer.** Once someone finds a person taller than them, they are done — remove them from consideration.

A **monotonic increasing stack** maintains a stack of elements in strictly increasing order from bottom to top (in terms of the values of elements we haven't "resolved" yet). As you walk left-to-right through the array, you ask: _"Does the current element beat the top of the stack?"_ If yes, the current element is the **next greater element** for the stack top — pop it, record the answer, and check the new top. If no, push the current element and keep walking.

The stack is a "holding area" for elements whose next greater element hasn't been seen yet. The key invariant: **everything in the stack is waiting, and everything waiting is in increasing order so we can process them greedily.**

### Why This Exists

The brute-force O(n²) approach fails for arrays of size 10⁵–10⁶, which is routine in both production and contests. The monotonic stack achieves O(n) by ensuring **every element is pushed and popped at most once** — a classic amortised argument. You trade the nested loop for a careful maintenance of a data structure invariant.

### The "Aha" Moment

**Each element is processed exactly twice: once when pushed, once when popped.** This is the entire complexity argument. The stack doesn't shrink and grow arbitrarily — elements exit in the exact moment they find their answer, and the total number of exits equals the total number of entrances, which is n. That's O(n) total work.

The monotonicity is not a constraint you enforce for its own sake — it is the _consequence_ of greedy resolution. When a larger element arrives, it resolves all smaller waiting elements below it in one sweep, because if `arr[j] > arr[i]` for `i < j`, then `j` is the answer for `i`.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**When it appears:** Any problem asking for "next greater/smaller element", "how many days until a warmer temperature", "stock span", "visible buildings", "range of dominance", or "nearest element satisfying a monotone condition."

**Pattern signal:**

```
"For each index i, find the nearest j > i such that arr[j] > arr[i]"  →  monotonic increasing stack
"For each index i, find the nearest j > i such that arr[j] < arr[i]"  →  monotonic decreasing stack
"For each index i, find the nearest j < i such that arr[j] > arr[i]"  →  process right-to-left with increasing stack
```

**Common trap:** Forgetting to handle elements still in the stack after the array is exhausted — they have _no_ next greater element (answer = -1 or 0 depending on problem). Many incorrect solutions produce garbage for the suffix of the array.

**Second trap:** Off-by-one when storing indices vs values. Store **indices** in the stack, not values, so you can compute distances and fill answer arrays by position.

### Machine Learning / AI

**Feature engineering on time series:** The next greater element pattern is the algorithmic core of `pandas.DataFrame.expanding().max()` and resistance-level detection in financial ML. When building features like "days since last price high" or "next time the signal exceeded threshold θ," you are computing a next-greater-element query. Implementing this naively O(n²) is a common bottleneck in feature pipelines on datasets with millions of timesteps.

**Attention mechanisms — causal masking:** The monotonic stack logic appears in efficient implementations of _relative position encoding_ and _causal sparse attention_. In Longformer and BigBird, the attention patterns use structured sparsity; maintaining valid attention windows as tokens arrive resembles the push/pop logic of a monotonic stack.

**Online learning and streaming:** When processing data streams (Kafka, Flink, real-time ML inference), computing rolling maximums or "time until next anomaly" queries require O(1)-amortised solutions. The monotonic deque (a generalisation of the monotonic stack) is the exact structure used internally in Apache Flink's window aggregation operators for `MAX` and `MIN` functions.

**Histogram / density estimation:** The largest rectangle in histogram problem (built on monotonic stack) is structurally equivalent to computing the _maximum rectangular support_ under an empirical PDF histogram — relevant in distribution visualisation and anomaly bounding.

## 3. Algorithm / Pattern

### Step-by-Step Logic

1. Initialise an empty stack. It will hold **indices** of unresolved elements.
2. Initialise `result[0..n-1] = -1` (default: no next greater element found).
3. For each index `i` from `0` to `n-1`:
    - **While** the stack is non-empty **and** `arr[stack.top()] < arr[i]`:
        - Pop index `j` from the stack.
        - `result[j] = arr[i]` (or `= i` if the problem wants the index).
    - Push `i` onto the stack.
4. Elements remaining in the stack have no next greater element; `result[j] = -1` for all remaining `j`.

### Decision Tree

```
Need next element satisfying monotone condition on the right?
  ├─ Greater → monotonic increasing stack (pops when new element is larger)
  └─ Smaller → monotonic decreasing stack (pops when new element is smaller)

Need nearest element to the LEFT?
  └─ Traverse right-to-left, same stack logic

Problem involves circular array?
  └─ Traverse 2n indices with modular indexing (see Variations)

Problem asks for the SPAN or distance, not just the value?
  └─ Store indices in the stack and compute i - stack.top() on pop
```

### Complexity

**Time:** O(n)  
Every element enters the stack exactly once (one push per iteration) and leaves the stack at most once (one pop, when its NGE is found). Total operations = 2n → O(n).

**Space:** O(n)  
Worst case: a strictly decreasing array. Every element is pushed and never popped until after the loop (e.g., `[5, 4, 3, 2, 1]`). The stack holds all n elements.

**When to avoid:** When you need the _k_-th greater element, or the greater element within a window of size w — the pure monotonic stack doesn't directly support these without modification. Use a segment tree or sparse table for those variants.

## 4. Pseudocode

```
function nextGreaterElement(arr[0..n-1]):
    result[0..n-1] ← -1          // Default: no NGE exists
    stack ← empty stack of indices

    for i from 0 to n-1:
        // Current element arr[i] is a candidate NGE for everything in the stack
        // that is strictly less than it. Pop and resolve them.
        while stack is not empty AND arr[stack.top()] < arr[i]:
            j ← stack.pop()
            result[j] ← arr[i]   // arr[i] is the next greater element for index j

        // arr[i] has not found its NGE yet; enqueue it for future resolution
        stack.push(i)

    // Remaining elements in stack have no NGE; result already initialised to -1
    return result
```

**Edge cases handled:**

- **Empty array:** loop doesn't execute, return empty result.
- **All equal elements:** nothing is ever strictly less, so nothing is popped; all results stay -1.
- **Strictly decreasing array:** nothing pops until end of traversal; all results = -1.
- **Strictly increasing array:** every element pops everything before it; the stack never holds more than one element at any time.

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <vector>
#include <stack>
#include <iostream>
#include <cassert>
using namespace std;

/**
 * Next Greater Element (to the right)
 *
 * For each index i, returns the value of the nearest element to the right
 * that is strictly greater than arr[i]. Returns -1 if none exists.
 *
 * Time:  O(n) amortised — each element pushed/popped at most once
 * Space: O(n) — stack holds at most n indices
 */
vector<int> nextGreaterElement(const vector<int>& arr) {
    int n = arr.size();
    vector<int> result(n, -1);   // -1 = no next greater element
    stack<int> stk;              // stores indices, not values

    for (int i = 0; i < n; ++i) {
        // While the element at stack top is smaller than current,
        // the current element is its Next Greater Element.
        while (!stk.empty() && arr[stk.top()] < arr[i]) {
            result[stk.top()] = arr[i];
            stk.pop();
        }
        stk.push(i);
    }
    // Remaining indices in stk already have result = -1 (no NGE found)
    return result;
}

/**
 * Next Greater Element — circular array variant
 *
 * Treats the array as circular: after the last element, wraps back to index 0.
 * Standard trick: traverse 2n indices with modular indexing.
 *
 * Time:  O(n)
 * Space: O(n)
 */
vector<int> nextGreaterElementCircular(const vector<int>& arr) {
    int n = arr.size();
    vector<int> result(n, -1);
    stack<int> stk;  // stores original indices

    for (int i = 0; i < 2 * n; ++i) {
        int idx = i % n;
        while (!stk.empty() && arr[stk.top()] < arr[idx]) {
            result[stk.top()] = arr[idx];
            stk.pop();
        }
        // Only push indices in the first pass; second pass only resolves
        if (i < n) stk.push(idx);
    }
    return result;
}

// ─── Tests ────────────────────────────────────────────────────────────────────
int main() {
    // Basic case
    vector<int> a = {2, 1, 5, 3, 4};
    vector<int> nge = nextGreaterElement(a);
    assert((nge == vector<int>{5, 5, -1, 4, -1}));

    // All equal
    vector<int> b = {3, 3, 3};
    assert((nextGreaterElement(b) == vector<int>{-1, -1, -1}));

    // Strictly increasing
    vector<int> c = {1, 2, 3};
    assert((nextGreaterElement(c) == vector<int>{2, 3, -1}));

    // Strictly decreasing
    vector<int> d = {5, 4, 3, 2, 1};
    assert((nextGreaterElement(d) == vector<int>{-1, -1, -1, -1, -1}));

    // Circular
    vector<int> e = {1, 2, 1};
    assert((nextGreaterElementCircular(e) == vector<int>{2, -1, 2}));

    cout << "All tests passed.\n";
    return 0;
}
```

### Python (Readable + Pythonic)

```python
from typing import List


def next_greater_element(arr: List[int]) -> List[int]:
    """
    For each index i, find the nearest element to the right strictly greater
    than arr[i]. Returns -1 if no such element exists.

    Algorithm: Monotonic increasing stack (stores indices).
    Time:  O(n) — each element pushed and popped at most once.
    Space: O(n) — stack size bounded by n.

    Args:
        arr: Input array of integers.
    Returns:
        result[i] = next greater value for arr[i], or -1 if none.
    """
    n = len(arr)
    result = [-1] * n
    stack: List[int] = []  # indices of unresolved elements

    for i, val in enumerate(arr):
        # Pop all elements for which arr[i] is the answer
        while stack and arr[stack[-1]] < val:
            j = stack.pop()
            result[j] = val
        stack.append(i)

    # Remaining elements in stack: result already -1
    return result


def next_greater_element_circular(arr: List[int]) -> List[int]:
    """
    Circular variant: the array wraps around.
    Traverse 2n positions using modular indexing.

    Time:  O(n)
    Space: O(n)
    """
    n = len(arr)
    result = [-1] * n
    stack: List[int] = []

    for i in range(2 * n):
        idx = i % n
        while stack and arr[stack[-1]] < arr[idx]:
            result[stack.pop()] = arr[idx]
        if i < n:
            stack.append(idx)

    return result


def next_greater_index(arr: List[int]) -> List[int]:
    """
    Variant: returns the INDEX of the next greater element, not its value.
    Returns -1 if none exists. Useful for distance/span computations.
    """
    n = len(arr)
    result = [-1] * n
    stack: List[int] = []

    for i, val in enumerate(arr):
        while stack and arr[stack[-1]] < val:
            j = stack.pop()
            result[j] = i          # store index, not value
        stack.append(i)

    return result


# ─── Tests ────────────────────────────────────────────────────────────────────
if __name__ == "__main__":
    assert next_greater_element([2, 1, 5, 3, 4]) == [5, 5, -1, 4, -1]
    assert next_greater_element([3, 3, 3]) == [-1, -1, -1]
    assert next_greater_element([1, 2, 3]) == [2, 3, -1]
    assert next_greater_element([5, 4, 3]) == [-1, -1, -1]
    assert next_greater_element([]) == []

    assert next_greater_element_circular([1, 2, 1]) == [2, -1, 2]
    assert next_greater_element_circular([3, 1, 2]) == [-1, 2, 3]

    assert next_greater_index([2, 1, 5, 3, 4]) == [2, 2, -1, 4, -1]

    print("All tests passed.")
```

### Diagram 2: Amortised Push/Pop Argument (Why O(n))

```
Array of length n=6: each element has one push (→) and at most one pop (←)

Element:  A   B   C   D   E   F
Push:     →   →   →   →   →   →     (exactly n pushes total)
Pop:      ←       ←   ←       ←     (at most n pops total)

Total operations ≤ 2n → O(n)

Worst cases:
  Strictly increasing [1,2,3,4,5]: every element pops everything before it
    → n pushes + (n-1) pops = O(n) ✓

  Strictly decreasing [5,4,3,2,1]: nothing ever pops during traversal
    → n pushes + 0 pops during loop = O(n) ✓
```

## 7. Common Variations & Extensions

### Variation 1: Next Smaller Element

Flip the comparison: pop when `arr[stack.top()] > arr[i]`. The stack now maintains a **decreasing** order (monotonic decreasing stack). See [[88.Monotonic decreasing stack — next smaller element]].

### Variation 2: Previous Greater Element

Traverse **right-to-left** using the same increasing stack. At each step, the stack top (before popping) is the previous greater element for the current index. Alternatively, traverse left-to-right but query the stack top before pushing — the current top is the previous greater element already.

```python
def previous_greater_element(arr):
    n = len(arr)
    result = [-1] * n
    stack = []
    for i in range(n):
        while stack and arr[stack[-1]] <= arr[i]:
            stack.pop()
        if stack:
            result[i] = arr[stack[-1]]
        stack.append(i)
    return result
```

### Variation 3: Largest Rectangle in Histogram

For each bar, find the _previous smaller_ and _next smaller_ bar simultaneously — these define the left and right bounds of the maximal rectangle with that bar's height. This uses two monotonic stack passes (or one combined pass) and is the foundation of [[89.Largest rectangle in histogram — the canonical monotonic stack problem]].

### Variation 4: Sliding Window Maximum

Generalise to a **deque** (double-ended queue) to maintain the maximum over a sliding window of size k. The back of the deque acts like a monotonic decreasing stack, and the front gives the current window maximum in O(1). See [[95.Sliding window maximum with monotonic deque]] and [[14.Sliding window maximum — monotonic deque approach]].

### Variation 5: Stock Span

"How many consecutive days before today had a price ≤ today's price?" This is equivalent to computing `i - (index of previous greater element)`. One pass with the index-storing stack gives spans in O(n). See [[91.Stock span and daily temperature problems]].

## 9. CP Contest Application

### Typical Codeforces Problem Structure

**Problem shape:** "Given array A of length n (up to 2×10⁵), for each index i compute f(i) where f depends on the nearest index j satisfying a monotone condition relative to A[i]." The answer is often the sum of all f(i), or the product, or just the array itself.

**Canonical disguised forms:**

- _"Buildings and sunlight"_ → each building sees the sun if no taller building is to its left → previous greater element.
- _"Sum of (max of all subarrays containing index i as their maximum)"_ → for each element, find its left and right bounds as max using two monotonic stack passes, then contribute `arr[i] × (left_dist) × (right_dist)`.
- _"Number of valid pairs (i,j) such that arr[j] is the NGE of arr[i]"_ → just count pops.

**Time limits:** At n = 2×10⁵ to 10⁶, O(n log n) is usually acceptable but O(n²) will TLE. The monotonic stack is the intended O(n) solution. On AtCoder, time limits are often tight enough (1–2 seconds) that even O(n log n) with large constants can fail; O(n) with a simple stack is safe.

**Optimisation tricks for CP:**

- Use an `int[]` array as a manual stack instead of `std::stack<int>` to avoid function-call overhead. This can give 2–3× speedup in tight problems.
- When the problem asks for both left and right bounds simultaneously, do two passes and store results in prefix/suffix arrays rather than a combined pass, for clarity and cache efficiency.
- For the circular variant in a CP setting, always 2n traversal — it is cleaner and avoids off-by-one bugs compared to two-pass approaches.

```cpp
// CP-speed manual stack (avoids std::stack overhead)
int stk[200005], top = 0;  // top=0 means empty
for (int i = 0; i < n; ++i) {
    while (top > 0 && arr[stk[top-1]] < arr[i]) {
        result[stk[--top]] = arr[i];
    }
    stk[top++] = i;
}
```
