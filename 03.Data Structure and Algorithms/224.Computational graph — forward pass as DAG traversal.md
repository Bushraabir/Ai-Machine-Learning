## 1. Intuition First

### The Core Idea

Imagine you are baking a multi-layer cake, and each ingredient depends on the result of a previous preparation step. You cannot frost the cake before it's baked. You cannot bake it before you've mixed the batter. You cannot mix the batter before you've measured the flour. Every neural network forward pass follows this exact constraint structure — and the data structure that encodes it is a **Directed Acyclic Graph (DAG)**.

A **computational graph** is a DAG where:

- **Nodes** represent values (tensors, scalars, intermediate results)
- **Directed edges** represent data dependencies — an edge from $u \to v$ means "the value of $v$ depends on the value of $u$"
- **No cycles** exist, because a cycle would mean some computation depends on its own output — mathematical nonsense

When you write `z = relu(W @ x + b)` in PyTorch, you are not executing those operations immediately in a vacuum. You are constructing a graph. Evaluating that expression top-to-bottom in the correct dependency order **is** a topological traversal of that graph.

### Why This Exists

A naive sequential execution model works for simple expressions, but breaks down the moment you need:

1. **Automatic differentiation** — to compute $\frac{\partial L}{\partial W}$, you must traverse the same graph in _reverse_ (the backward pass). Without the graph structure, there is no "reverse" to traverse.
2. **Parallel execution** — nodes with no dependency between them can execute concurrently. A sequential model cannot express this; a graph model makes it explicit.
3. **Optimisation** — graph compilers (XLA, TorchScript, TVM) can fuse operations, eliminate dead nodes, and reorder computations for cache efficiency. None of this is possible without the graph.
4. **Hardware targeting** — the graph serves as an intermediate representation (IR) that can be compiled to CPU, GPU, or TPU backends independently of the Python code that constructed it.

The naive approach — just run Python line by line — gives you none of these. Complexity-wise, a naïve approach cannot even express which operations can run in parallel: you would need $O(n^2)$ dependency checks across $n$ operations versus $O(V + E)$ in a proper graph traversal.

### The "Aha" Moment

**The forward pass _is_ a topological sort traversal.** Every deep learning framework, at its core, answers the question: "in what order do I evaluate the nodes of this DAG so that every node's inputs are ready before that node executes?" That is precisely the definition of topological ordering. Understand topological sort on a DAG, and you understand the execution model of PyTorch, JAX, TensorFlow, and every other framework that has ever existed or will ever exist.

## 2. Why We Need It — ML Dual Context

### Machine Learning / AI

**Where it appears:**

The computational graph is not one feature of ML frameworks — it _is_ the framework's execution model. Every framework implements a variation:

|Framework|Graph Style|When Built|
|---|---|---|
|PyTorch (eager)|Dynamic, per-call|At Python runtime|
|PyTorch 2.0 (`torch.compile`)|Static, traced|At first call, then cached|
|JAX (`jit`)|Static, traced via `jaxpr`|At first call|
|TensorFlow 1.x|Static, declared|Before any execution|
|TensorFlow 2.x / Keras|Eager by default, `tf.function` for static|Mixed|
|ONNX|Static, exported|Post-training|

**Specific mechanisms:**

- **PyTorch autograd engine:** Every `Tensor` with `requires_grad=True` carries a `grad_fn` attribute — a reference to the node in the graph that produced it. The `.backward()` call walks this graph in reverse topological order, accumulating gradients via the chain rule. The `AccumulateGrad` leaf nodes terminate the traversal.
    
- **JAX `jaxpr`:** When you call `jax.jit(f)(x)`, JAX traces `f` with abstract values to produce a `jaxpr` — a pure functional IR that is literally a list of equations in topological order. Execution is a linear scan through this list.
    
- **TorchScript / `torch.compile`:** The `torch.fx` symbolic tracer walks your Python code and records operations into a `Graph` object (a `torch.fx.Graph`). The nodes in this graph are already in topological order. Passes like operator fusion work by pattern-matching subgraphs and replacing them.
    
- **ONNX:** An exported model is a serialised DAG. The ONNX runtime performs a topological sort at load time, then executes in that order.
    

**How understanding this improves your ML code:**

1. If you accidentally create a computation that retains a reference to a large intermediate tensor (e.g., holding onto an intermediate activation in a list), you are keeping a graph node alive — causing a GPU memory leak. Understanding the graph makes this visible.
2. `with torch.no_grad():` disables graph construction entirely — no edges are recorded, no `grad_fn` is set. Inference is faster because the graph is never built.
3. `tensor.detach()` cuts an edge in the graph — it returns a tensor with no `grad_fn`, effectively saying "stop gradient here." This is the implementation mechanism behind techniques like stop-gradient in contrastive learning (SimSiam, BYOL).
4. Gradient checkpointing (`torch.utils.checkpoint`) re-runs subgraphs during the backward pass instead of storing all activations — it discards graph nodes and recomputes them. This is only possible because the graph is explicit.

## 3. Algorithm / Pattern

### The Forward Pass as Topological Traversal

**Formal definition:** A topological ordering of a DAG $G = (V, E)$ is a linear ordering of all nodes such that for every directed edge $(u, v)$, node $u$ comes before node $v$ in the ordering.

The forward pass algorithm:

```
1. Build the graph (either eagerly or via tracing)
2. Compute in-degree for each node
3. Initialise a queue with all source nodes (in-degree = 0) — these are the inputs (data, weights)
4. While the queue is non-empty:
   a. Dequeue a node
   b. Execute its computation: output = op(inputs)
   c. Store the output value at this node
   d. For each successor: decrement its in-degree
   e. If a successor's in-degree reaches 0, enqueue it
5. The final node's stored value is the forward pass output
```

This is Kahn's algorithm applied to expression evaluation. See [[121.Topological sort — Kahn's algorithm (BFS-based)]].

### Decision Tree

```
Is there a data dependency between two ops?
├── YES → add a directed edge, they must execute in sequence
└── NO  → no edge, they can execute in parallel

Does the graph have a cycle?
├── YES → invalid: circular dependency, model definition is wrong
└── NO  → valid DAG, proceed with topological sort

Do you need gradients?
├── YES → record graph (PyTorch: requires_grad=True)
│         backward() will traverse in reverse topological order
└── NO  → torch.no_grad() — skip graph construction entirely
```

### Complexity

Let $V$ = number of operations (nodes), $E$ = number of tensor dependencies (edges).

|Operation|Complexity|Why|
|---|---|---|
|Graph construction|$O(V + E)$|One pass through the computation|
|Topological sort|$O(V + E)$|Kahn's or DFS-based, each node and edge visited once|
|Forward pass execution|$O(V + E)$ + actual op cost|Traversal overhead is linear; op cost dominates|
|Backward pass|$O(V + E)$ + gradient op cost|Same graph, reverse direction|

In practice, $E = O(V)$ for most feed-forward architectures (each op has a bounded number of inputs), so both passes are $O(V)$ in traversal overhead. The actual compute cost of the tensor operations (matrix multiplications, convolutions) completely dominates.

### When to Think in Graph Terms

- Debugging memory leaks: draw the graph and find which node holds a reference to a large tensor
- Implementing custom backward passes: `torch.autograd.Function` adds a custom node to the graph
- Gradient stopping: `detach()` removes an edge
- Gradient scaling: gradient clipping operates on the accumulated gradients after the backward traversal completes
- Model parallelism: assign different subgraphs to different devices — the graph makes the partition explicit

## 4. Pseudocode

```
PROCEDURE BuildComputationalGraph(model, x):
    # Nodes: (operation, [input_node_ids], output_value)
    # Edges: implicit via input_node_ids
    
    graph = empty DAG
    
    # Source nodes: inputs and parameters
    x_node = graph.add_node(op=IDENTITY, inputs=[], value=x)
    for each parameter W in model:
        w_node = graph.add_node(op=IDENTITY, inputs=[], value=W)
    
    # Interior nodes added during forward specification
    # (In eager mode, this happens as Python executes)
    return graph

PROCEDURE ForwardPass(graph):
    # Kahn's algorithm for expression evaluation
    
    in_degree = {v: 0 for v in graph.nodes}
    for each edge (u → v) in graph.edges:
        in_degree[v] += 1
    
    # Source nodes are inputs and parameters
    queue = [v for v in graph.nodes if in_degree[v] == 0]
    
    values = {}  # node → computed tensor
    for source in queue:
        values[source] = source.value  # initialise from stored data
    
    topo_order = []
    
    while queue is not empty:
        node = queue.dequeue()
        topo_order.append(node)
        
        if node.op is not IDENTITY:
            # Retrieve input values (all guaranteed ready — in_degree was 0)
            input_vals = [values[inp] for inp in node.inputs]
            
            # Execute the operation
            values[node] = node.op(*input_vals)
            
            # Optionally: save for backward pass (activation checkpointing skips this)
            node.saved_value = values[node]
        
        for successor in graph.successors(node):
            in_degree[successor] -= 1
            if in_degree[successor] == 0:
                queue.enqueue(successor)
    
    # Return value at the single sink node (loss or output)
    return values[graph.sink]

PROCEDURE BackwardPass(graph, topo_order):
    # Reverse topological order — guaranteed correct by construction
    
    grad = {v: zeros_like(v.value) for v in graph.nodes}
    grad[graph.sink] = ones_like(graph.sink.value)  # dL/dL = 1
    
    for node in reversed(topo_order):
        if node.op is IDENTITY:
            continue  # leaf: gradient already accumulated
        
        # Compute local Jacobian-vector products (vjp)
        input_grads = node.op.backward(grad[node], node.saved_value)
        
        for inp, g in zip(node.inputs, input_grads):
            grad[inp] += g  # accumulate (handles fan-out correctly)
    
    return {param: grad[param] for param in graph.parameter_nodes}
```

## 5. Implementation

### Python (PyTorch-Faithful, Readable)

```python
"""
Minimal computational graph engine demonstrating forward pass as DAG traversal.
Implements:
  - Graph construction with explicit nodes and edges
  - Forward pass via Kahn's topological sort
  - Backward pass via reverse topological traversal
  - Gradient accumulation for fan-out nodes

Complexity: O(V + E) traversal, where V = ops, E = tensor dependencies.
"""

from __future__ import annotations
from typing import Callable, Optional
from collections import deque
import numpy as np


class Tensor:
    """A node in the computational graph."""

    def __init__(
        self,
        data: np.ndarray,
        requires_grad: bool = False,
        _op: Optional[str] = None,
        _children: tuple["Tensor", ...] = (),
    ):
        self.data = np.asarray(data, dtype=np.float64)
        self.requires_grad = requires_grad
        self.grad: Optional[np.ndarray] = None

        # Graph bookkeeping
        self._op = _op                  # which operation produced this node
        self._children = _children      # predecessor nodes (incoming edges)
        self._backward: Callable = lambda: None  # local vjp function

    # ── Arithmetic ────────────────────────────────────────────────────────────

    def __matmul__(self, other: "Tensor") -> "Tensor":
        out = Tensor(
            self.data @ other.data,
            requires_grad=self.requires_grad or other.requires_grad,
            _op="matmul",
            _children=(self, other),
        )

        def _backward():
            # d/dA (A @ B) applied to upstream grad G → G @ B.T
            # d/dB (A @ B) applied to upstream grad G → A.T @ G
            if self.requires_grad:
                if self.grad is None:
                    self.grad = np.zeros_like(self.data)
                self.grad += out.grad @ other.data.T
            if other.requires_grad:
                if other.grad is None:
                    other.grad = np.zeros_like(other.data)
                other.grad += self.data.T @ out.grad

        out._backward = _backward
        return out

    def __add__(self, other: "Tensor") -> "Tensor":
        out = Tensor(
            self.data + other.data,
            requires_grad=self.requires_grad or other.requires_grad,
            _op="add",
            _children=(self, other),
        )

        def _backward():
            if self.requires_grad:
                if self.grad is None:
                    self.grad = np.zeros_like(self.data)
                # Handle broadcasting: sum over broadcast dims
                g = out.grad
                for _ in range(g.ndim - self.data.ndim):
                    g = g.sum(axis=0)
                self.grad += g
            if other.requires_grad:
                if other.grad is None:
                    other.grad = np.zeros_like(other.data)
                g = out.grad
                for _ in range(g.ndim - other.data.ndim):
                    g = g.sum(axis=0)
                other.grad += g

        out._backward = _backward
        return out

    def relu(self) -> "Tensor":
        out = Tensor(
            np.maximum(0, self.data),
            requires_grad=self.requires_grad,
            _op="relu",
            _children=(self,),
        )

        def _backward():
            if self.requires_grad:
                if self.grad is None:
                    self.grad = np.zeros_like(self.data)
                self.grad += out.grad * (self.data > 0)

        out._backward = _backward
        return out

    def sum(self) -> "Tensor":
        out = Tensor(
            self.data.sum(),
            requires_grad=self.requires_grad,
            _op="sum",
            _children=(self,),
        )

        def _backward():
            if self.requires_grad:
                if self.grad is None:
                    self.grad = np.zeros_like(self.data)
                self.grad += np.ones_like(self.data) * out.grad

        out._backward = _backward
        return out

    # ── Graph traversal ───────────────────────────────────────────────────────

    def _build_topo(self) -> list["Tensor"]:
        """
        Build topological ordering via DFS post-order.
        Equivalent to Kahn's on the reverse graph.
        Post-order DFS on the forward graph gives reverse topological order —
        reversing it gives topological order. We use it for backward() directly.
        """
        visited: set[int] = set()
        topo: list["Tensor"] = []

        def dfs(node: "Tensor") -> None:
            if id(node) in visited:
                return
            visited.add(id(node))
            for child in node._children:
                dfs(child)
            topo.append(node)  # post-order: after all children

        dfs(self)
        return topo  # topo[-1] = self (the loss); topo[0] = leaves

    def backward(self) -> None:
        """
        Backward pass: reverse topological traversal of the DAG.
        Each node's _backward() computes local vjp and accumulates into children.
        """
        assert self.data.shape == (), "backward() called on non-scalar — call .sum() first"
        topo = self._build_topo()

        # Seed: dL/dL = 1
        self.grad = np.ones_like(self.data)

        # Traverse in reverse topological order (sink → sources)
        for node in reversed(topo):
            node._backward()

    def __repr__(self) -> str:
        return f"Tensor({self.data}, op={self._op!r}, grad={self.grad})"


# ── Example: one-layer network forward + backward ────────────────────────────

if __name__ == "__main__":
    np.random.seed(42)

    # Input: batch of 4 samples, 3 features
    x = Tensor(np.random.randn(4, 3), requires_grad=False)

    # Parameters
    W = Tensor(np.random.randn(3, 5), requires_grad=True)
    b = Tensor(np.zeros(5), requires_grad=True)

    # Forward pass: x @ W + b → relu → sum (scalar loss)
    # This builds the computational graph as a side-effect of Python execution.
    # Each operation creates a new Tensor node with _children pointing to inputs.
    h = (x @ W + b).relu()  # shape (4, 5)
    loss = h.sum()           # scalar

    print(f"Forward pass complete. Loss = {loss.data:.4f}")
    print(f"Graph depth: input → matmul → add → relu → sum")

    # Backward pass: reverse topological traversal
    loss.backward()

    print(f"\nGradients computed:")
    print(f"  W.grad shape: {W.grad.shape}")  # (3, 5)
    print(f"  b.grad shape: {b.grad.shape}")  # (5,)
    print(f"  W.grad (first row): {W.grad[0]}")
```

### C++ (Structural, Production-Style)

```cpp
/**
 * Computational Graph — Forward Pass as DAG Traversal
 *
 * Demonstrates: graph construction, Kahn's topological sort for forward pass,
 * reverse traversal for backward pass.
 *
 * Compile: g++ -std=c++17 -O2 comp_graph.cpp -o comp_graph
 *
 * Design notes:
 *   - shared_ptr for graph ownership (nodes are shared between graph and edges)
 *   - std::function for flexible operation and backward hooks
 *   - Kahn's algorithm for execution order (explicit in-degree tracking)
 */

#include <cassert>
#include <cmath>
#include <functional>
#include <iostream>
#include <memory>
#include <numeric>
#include <queue>
#include <unordered_map>
#include <unordered_set>
#include <vector>

// ── Node ─────────────────────────────────────────────────────────────────────

struct Node {
    int id;                                     // unique node identifier
    std::string op;                             // operation name (for debugging)
    float value = 0.0f;                         // forward pass output
    float grad  = 0.0f;                         // accumulated gradient

    // Graph structure
    std::vector<std::shared_ptr<Node>> inputs;  // predecessor nodes (edges in)

    // Backward hook: computes vjp and accumulates into input.grad
    std::function<void()> backward_fn = [](){};

    explicit Node(int id, std::string op = "")
        : id(id), op(std::move(op)) {}
};

using NodePtr = std::shared_ptr<Node>;

// ── Graph ─────────────────────────────────────────────────────────────────────

class ComputationalGraph {
public:
    // Add a leaf node (input or parameter — no predecessors)
    NodePtr leaf(float val, const std::string& name = "leaf") {
        auto n = std::make_shared<Node>(next_id_++, name);
        n->value = val;
        all_nodes_.push_back(n);
        return n;
    }

    // Add an op node: result = op(a, b), with backward hook
    NodePtr op(
        const std::string& name,
        std::vector<NodePtr> inputs,
        float result,
        std::function<void()> bwd
    ) {
        auto n = std::make_shared<Node>(next_id_++, name);
        n->value   = result;
        n->inputs  = std::move(inputs);
        n->backward_fn = std::move(bwd);
        all_nodes_.push_back(n);
        return n;
    }

    // ── Kahn's topological sort ───────────────────────────────────────────────
    // Returns nodes in valid execution order (sources first, sink last).
    // O(V + E): each node enqueued once, each edge traversed once.
    std::vector<NodePtr> topo_sort() const {
        // Build successors and in-degree
        std::unordered_map<int, std::vector<NodePtr>> succ;
        std::unordered_map<int, int> in_deg;

        for (auto& n : all_nodes_) {
            if (!in_deg.count(n->id)) in_deg[n->id] = 0;
            for (auto& inp : n->inputs) {
                succ[inp->id].push_back(n);
                in_deg[n->id]++;
            }
        }

        // Seed: nodes with no predecessors (inputs and parameters)
        std::queue<NodePtr> q;
        for (auto& n : all_nodes_) {
            if (in_deg[n->id] == 0) q.push(n);
        }

        std::vector<NodePtr> order;
        order.reserve(all_nodes_.size());

        while (!q.empty()) {
            auto node = q.front(); q.pop();
            order.push_back(node);

            for (auto& s : succ[node->id]) {
                if (--in_deg[s->id] == 0) q.push(s);
            }
        }

        assert(order.size() == all_nodes_.size() &&
               "Cycle detected in computational graph!");
        return order;
    }

    // ── Forward pass ──────────────────────────────────────────────────────────
    // Values are already computed during graph construction (eager execution).
    // In a traced/static graph, this is where you'd evaluate each node.
    void forward_display(const std::vector<NodePtr>& topo) const {
        std::cout << "Forward pass (topological order):\n";
        for (auto& n : topo) {
            std::cout << "  [" << n->op << "] id=" << n->id
                      << " value=" << n->value << "\n";
        }
    }

    // ── Backward pass ─────────────────────────────────────────────────────────
    // Traverse in reverse topological order.
    // O(V + E): same complexity as forward pass.
    void backward(NodePtr loss, const std::vector<NodePtr>& topo) {
        // Seed gradient
        loss->grad = 1.0f;

        for (int i = static_cast<int>(topo.size()) - 1; i >= 0; --i) {
            topo[i]->backward_fn();
        }
    }

    const std::vector<NodePtr>& nodes() const { return all_nodes_; }

private:
    std::vector<NodePtr> all_nodes_;
    int next_id_ = 0;
};

// ── Helpers: simple scalar ops with backward hooks ────────────────────────────

NodePtr add(ComputationalGraph& g, NodePtr a, NodePtr b) {
    float val = a->value + b->value;
    auto out = g.op("add", {a, b}, val, []{});
    out->backward_fn = [a, b, out]() {
        a->grad += out->grad;  // d(a+b)/da = 1
        b->grad += out->grad;  // d(a+b)/db = 1
    };
    return out;
}

NodePtr mul(ComputationalGraph& g, NodePtr a, NodePtr b) {
    float val = a->value * b->value;
    auto out = g.op("mul", {a, b}, val, []{});
    out->backward_fn = [a, b, out]() {
        a->grad += b->value * out->grad;  // d(ab)/da = b
        b->grad += a->value * out->grad;  // d(ab)/db = a
    };
    return out;
}

NodePtr relu_op(ComputationalGraph& g, NodePtr a) {
    float val = std::max(0.0f, a->value);
    auto out = g.op("relu", {a}, val, []{});
    out->backward_fn = [a, out]() {
        a->grad += (a->value > 0 ? 1.0f : 0.0f) * out->grad;
    };
    return out;
}

// ── Main: build and evaluate a small expression graph ─────────────────────────

int main() {
    ComputationalGraph g;

    // Inputs and parameters (leaf nodes)
    auto x1 = g.leaf(2.0f, "x1");
    auto x2 = g.leaf(3.0f, "x2");
    auto w1 = g.leaf(0.5f, "w1");
    auto w2 = g.leaf(-1.0f, "w2");
    auto b  = g.leaf(1.0f, "b");

    // Forward: loss = relu(w1*x1 + w2*x2 + b)
    // Graph structure:
    //   x1, w1 → mul1 ─┐
    //   x2, w2 → mul2 ──┤→ add_wb → relu → loss
    //   b      ─────────┘
    auto m1   = mul(g, w1, x1);
    auto m2   = mul(g, w2, x2);
    auto sum1 = add(g, m1, m2);
    auto z    = add(g, sum1, b);
    auto loss = relu_op(g, z);

    // Topological sort (Kahn's): O(V + E)
    auto topo = g.topo_sort();

    // Display forward pass
    g.forward_display(topo);
    std::cout << "\nLoss value: " << loss->value << "\n";

    // Backward pass: reverse topological traversal
    g.backward(loss, topo);

    std::cout << "\nGradients (dL/d_param):\n";
    for (auto& n : g.nodes()) {
        if (!n->inputs.empty()) continue;  // show only leaf gradients
        std::cout << "  " << n->op << ": grad=" << n->grad << "\n";
    }

    return 0;
}
```

## 6. Visual Explanation

### Diagram 1: A Forward Pass as DAG Traversal

For the expression `loss = relu(w1*x1 + w2*x2 + b)`:

```
   Leaves (in-degree 0)           Interior nodes              Sink
   ─────────────────────          ──────────────────          ────

   [x1 = 2.0]──┐
               ├──▶[mul1 = 1.0]──┐
   [w1 = 0.5]──┘                 │
                                 ├──▶[add = -1.0]──┐
   [x2 = 3.0]──┐                 │                 │
               ├──▶[mul2 =-3.0]──┘                 ├──▶[add_b = 0.0]──▶[relu = 0.0] = loss
   [w2 =-1.0]──┘                                   │
                                                   │
   [b  = 1.0]──────────────────────────────────────┘

   Topological order: x1, w1, x2, w2, b, mul1, mul2, add, add_b, relu
   In-degree sequence: [0,  0,  0,  0, 0,   2,    2,   2,     2,    1]
```

**Kahn's queue evolution:**

```
Initial queue (in-degree 0): [x1, w1, x2, w2, b]

Step 1: Dequeue x1 → process → decrement mul1's in-degree: 2→1
Step 2: Dequeue w1 → process → decrement mul1's in-degree: 1→0 → enqueue mul1
Step 3: Dequeue x2 → process → decrement mul2's in-degree: 2→1
Step 4: Dequeue w2 → process → decrement mul2's in-degree: 1→0 → enqueue mul2
Step 5: Dequeue b  → process → decrement add_b's in-degree: 2→1
Step 6: Dequeue mul1 → process → decrement add's in-degree: 2→1
Step 7: Dequeue mul2 → process → decrement add's in-degree: 1→0 → enqueue add
Step 8: Dequeue add  → process → decrement add_b's in-degree: 1→0 → enqueue add_b
Step 9: Dequeue add_b → process → decrement relu's in-degree: 1→0 → enqueue relu
Step 10: Dequeue relu → process → DONE (no successors)
```

### Diagram 2: Backward Pass as Reverse Traversal

The reverse topological order gives the backward pass. Gradients flow from sink to sources:

```
   BACKWARD (reverse of forward order)

   loss.grad = 1.0  (seed: dL/dL = 1)
        │
        ▼
   [relu] → d(relu)/dz = 0 (since z=0.0 ≤ 0) → add_b.grad += 0
        │
        ▼
   [add_b] → d/d(add) = 1, d/db = 1 → add.grad += 0, b.grad += 0
        │
        ▼
   [add] → d/d(mul1) = 1, d/d(mul2) = 1 → mul1.grad += 0, mul2.grad += 0
        │
        ▼
   [mul1] → d/dw1 = x1 = 2.0, d/dx1 = w1 = 0.5 → w1.grad += 0, x1.grad += 0
   [mul2] → d/dw2 = x2 = 3.0, d/dx2 = w2 = -1.0 → w2.grad += 0, x2.grad += 0

   Final gradients: w1.grad=0, w2.grad=0, b.grad=0
   (All zero because relu blocked the gradient — z=0.0 is at the kink!)
```

This zero-gradient situation is exactly the "dying ReLU" problem — a neuron with pre-activation exactly at 0 (or below) receives no gradient signal.

## 7. Common Variations & Extensions

### 7.1 Dynamic vs. Static Graphs

PyTorch builds the graph _during_ Python execution (eager/define-by-run). TensorFlow 1.x required you to first declare the full graph, then feed data into it (define-then-run). JAX's `jit` traces once, then re-uses the compiled graph (trace-then-cache).

The trade-off: dynamic graphs are easier to debug (Python control flow works naturally) but cannot be pre-optimised. Static graphs are harder to write but enable whole-program optimisation (operation fusion, memory planning, hardware targeting).

**Adaptation:** In PyTorch 2.0, `torch.compile` bridges this gap by tracing the dynamic graph lazily and compiling it, falling back to eager execution for any part the compiler cannot handle.

### 7.2 Gradient Checkpointing (Recompute vs. Store)

Standard backward pass stores every forward activation (graph node value) to compute local gradients. For a model with $L$ layers, this is $O(L)$ memory.

Gradient checkpointing divides the graph into segments. Only checkpoint activations are stored ($O(\sqrt{L})$ segments). During the backward pass, each segment is _recomputed_ from its checkpoint. Memory drops from $O(L)$ to $O(\sqrt{L})$ at the cost of one extra forward pass.

This is only possible because the computational graph is explicit — you can always re-execute any subgraph. See [[215.Gradient computation as a graph traversal — autograd intuition]].

### 7.3 Operator Fusion

A graph compiler can identify patterns like `matmul → add → relu` (a linear layer followed by activation) and replace them with a single fused CUDA kernel that reads inputs once, computes all three operations in registers, and writes the output once. This eliminates the intermediate tensor writes that would otherwise occur between the three separate kernels.

Libraries: XLA (JAX/TF), TorchInductor (PyTorch 2.0), TensorRT (inference), Triton (custom kernels). All of these work on the graph IR, not on Python source.

### 7.4 The `stop_gradient` Primitive

In contrastive learning (SimSiam, BYOL, Bootstrap Your Own Latent), one branch of the network should not receive gradients through the other branch. This is implemented by calling `.detach()` (PyTorch) or `jax.lax.stop_gradient()`, which removes the edge between two subgraphs in the DAG. The forward pass is unaffected; the backward pass simply has no edge to traverse.

See also: [[123.Dependency resolution — ML computation graph connection]].

### 7.5 Multi-Device Graphs (Model Parallelism)

The graph can be partitioned across multiple GPUs: assign different nodes to different devices. An edge crossing device boundaries becomes an explicit `send`/`recv` operation. Frameworks like DeepSpeed and Megatron-LM implement this partitioning on the graph IR. The topological ordering determines which cross-device transfers must happen before which computations.

## 9. CP Contest Application

Computational graphs as an explicit topic rarely appear in CP. The underlying algorithmic content — topological sort, DAG DP, cycle detection — appears constantly.

**Typical problem structure (Codeforces/AtCoder):**

_"You have N tasks. Task $i$ depends on a set of prerequisites. Find the minimum cost to complete all tasks, where completing task $i$ after task $j$ has cost $c_{ij}$."_

This is DAG DP on a topological ordering. The forward pass analogy is direct: evaluate each node's DP state only after all its predecessors are evaluated.

**Time limits where this matters:**

- $N \leq 10^5$: Kahn's topological sort must be $O(V + E)$, not $O(V^2)$
- $N \leq 10^3$: Floyd-Warshall-style all-pairs DP is acceptable ($O(V^3)$)

**Common trick — "virtual source node":** When multiple nodes have in-degree 0, add a virtual source connected to all of them with zero-weight edges. This converts a multi-source traversal into a clean single-source traversal.

**Common gotcha:** Forgetting that a problem with a cycle has _no_ valid topological ordering — detecting this via Kahn's (processed nodes < total nodes) is the standard check.
