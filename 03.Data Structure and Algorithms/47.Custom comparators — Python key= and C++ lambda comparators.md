## 1. Intuition First

### The Core Idea

Sorting is fundamentally about answering one question repeatedly: **given two elements, which comes first?** By default, every language has an opinion — integers sort by magnitude, strings by lexicographic order, tuples lexicographically by first element then second. Custom comparators let you **override that opinion** without touching the data.

Think of it like a judging panel at a competition. The competitors (data) don't change. What changes is the _judging criteria_ — first by score, then by name as tiebreaker, then by age. A custom comparator is the scoring rubric handed to the judges.

Two mechanisms accomplish this:

**Python's `key=` function:** Transform each element into a _sort key_ before comparison. The sort then compares keys instead of original elements. The transformation runs once per element (O(n) calls total), then standard comparison applies to the keys. This is the **Schwartzian transform** — decorate, sort, undecorate.

**C++ comparators (lambda / `std::function` / functor):** Provide a strict weak ordering function `comp(a, b)` that returns `true` if `a` should come _before_ `b`. Every comparison in the sort algorithm calls this function. Unlike Python's key=, there's no preprocessing — the comparator is called O(n log n) times.

### Why This Exists

Without custom comparators, sorting non-primitive objects requires either:

1. Storing data in a different form (lossy, invasive)
2. Implementing `__lt__` or `operator<` in the class definition (couples sort logic to data model — bad separation of concerns)
3. Writing your own sort (wasteful)

Custom comparators solve this cleanly: the sort algorithm is a black box, the data model is unchanged, and the ordering logic lives exactly where the sort is called. This is the **Open/Closed Principle** applied to algorithms.

### The "Aha" Moment

Python's `key=` is _not_ a comparator — it's a **projection**. You're not saying "a comes before b if..."; you're saying "represent a as X, then sort Xs normally." This means `key=` can only express total orderings reducible to a single comparable value or tuple. It cannot express orderings that require mutual inspection of two elements simultaneously.

C++ comparators _are_ true pairwise comparators — they receive both elements and can do anything. But they must satisfy **strict weak ordering**: irreflexivity (`comp(a,a) == false`), asymmetry (`comp(a,b)` implies `!comp(b,a)`), and transitivity. Violating these causes undefined behaviour — the sort may crash, loop infinitely, or silently produce wrong output.

This distinction — projection vs. pairwise comparison — is the single most important thing to understand about this topic.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**When it appears:** Almost every non-trivial sorting problem in contests requires a custom comparator. Patterns include:

- Sort intervals by start time, break ties by end time descending (greedy interval problems)
- Sort strings by length first, then lexicographically (string grouping)
- Sort pairs `(value, index)` to track original positions after sorting
- Sort by a derived quantity: e.g., sort points by polar angle for convex hull ([[Convex hull trick for DP optimisation]])
- Coordinate compression: sort unique values to assign ranks

**Pattern signal:**

```
"Sort by X, then by Y as tiebreaker"        → Python: key=lambda e: (e.x, e.y)
                                               C++:    [](auto& a, auto& b){ return a.x != b.x ? a.x < b.x : a.y < b.y; }

"Sort descending"                            → Python: key=lambda e: -e  OR  reverse=True
                                               C++:    [](auto& a, auto& b){ return a > b; }

"Sort strings by length then lexicographic" → Python: key=lambda s: (len(s), s)
                                               C++:    [](auto& a, auto& b){ return a.size() != b.size() ? a.size() < b.size() : a < b; }
```

**Common traps that kill submissions:**

1. **Returning `<=` instead of `<` in C++:** `comp(a, b) = (a <= b)` violates strict weak ordering when `a == b` (irreflexivity). `std::sort` with this comparator is **undefined behaviour** — may pass sample cases, crash on judge.
    
2. **Python's `functools.cmp_to_key` misuse:** When you _must_ use a pairwise comparator in Python (e.g., sorting strings where `"9" > "10"` as numbers but "10" > "9" lexicographically for concatenation — the classic largest-number problem), use `cmp_to_key`. Forgetting this and trying to encode the logic in `key=` leads to subtle bugs.
    
3. **Mutating elements during sort:** If your key function has side effects or if you modify the container during sort, results are undefined in both languages.
    
4. **Floating point keys:** `key=lambda p: math.atan2(p[1], p[0])` for polar angle sorting accumulates floating point error. In C++ precision-critical problems, use cross-product comparison instead.
    

### Machine Learning / AI

Custom comparators are not just a sorting nicety — they appear at the infrastructure layer of several ML systems:

**1. Beam search candidate ordering (NLP):**  
Beam search maintains a priority queue of partial hypotheses. The ordering is by log-probability, but with length normalisation penalties applied: `score(seq) = log_prob(seq) / len(seq)^α`. This is a custom comparator applied on every heap operation in the beam. HuggingFace `transformers` encodes this in `BeamSearchScorer._process()` — the `length_penalty` parameter directly controls the comparator's scoring function.

**2. Dataset curriculum learning:**  
Training ML models with curriculum learning (easy examples first, gradually harder) requires sorting the dataset by a difficulty metric — loss on a pretrained model, gradient magnitude, annotation confidence. `torch.utils.data.Sampler` subclasses sort indices using custom keys derived from these metrics. The `key=` function IS the curriculum.

**3. Feature importance ranking:**  
`sklearn`'s `SelectKBest` sorts features by a test statistic (χ², F-score, mutual information). Internally this is `np.argsort(scores)[::-1][:k]` — a custom ordering on derived statistical quantities, not on the features themselves. Understanding that this is a projection (key= style) explains why you can swap scoring functions freely without changing the selector's structure.

**4. Top-k sampling in language models:**  
Top-k and top-p sampling require partially sorting logit distributions. PyTorch's `torch.topk` uses an internal partial sort with a custom comparator on `(logit_value, token_id)` pairs — the secondary sort by token_id breaks ties deterministically for reproducibility. This is exactly the "sort by X, tiebreak by Y" pattern from CP.

**5. `np.lexsort` — the NumPy custom comparator:**  
`np.lexsort((keys[-1], keys[-2], ..., keys[0]))` sorts by the last key first, using earlier keys as tiebreakers. This is Python's `key=lambda x: tuple(reversed(keys))` applied to arrays without Python-level loops. For large ML datasets (millions of rows), this runs at C speed and is ~100× faster than Python `sorted` with `key=`. Knowing this saves real training time.

## 3. Algorithm / Pattern

### How `key=` Works Internally (Python)

Python's sort (Timsort) with `key=f` internally does:

```
decorated = [(f(x), i, x) for i, x in enumerate(arr)]   # i breaks ties stably
decorated.sort()                                           # standard tuple comparison
result = [x for _, _, x in decorated]
```

The index `i` is included to preserve stability — equal keys maintain original order. This is the **Schwartzian transform** from Perl/functional programming.

**Cost model:** `f` is called exactly **n times** (once per element). Comparison cost is then the cost of comparing key objects, not original objects. If `f` is expensive (e.g., computing a hash), this is a major advantage over C++ comparators which call the function O(n log n) times.

### How C++ `std::sort` with Comparator Works

`std::sort(begin, end, comp)` (introsort under the hood) calls `comp(a, b)` approximately `O(n log n)` times. The comparator must satisfy **strict weak ordering**:

|Property|Meaning|Violation consequence|
|---|---|---|
|Irreflexivity|`comp(a, a) == false`|UB: sort may loop|
|Asymmetry|`comp(a,b)` → `!comp(b,a)`|UB: inconsistent ordering|
|Transitivity|`comp(a,b) && comp(b,c)` → `comp(a,c)`|UB: corrupted result|
|Transitivity of equivalence|`!comp(a,b) && !comp(b,a) && !comp(b,c) && !comp(c,b)` → `!comp(a,c) && !comp(c,a)`|UB|

### Decision Tree

```
Need to sort with non-default order?
│
├─ Python?
│   ├─ Ordering expressible as a projection (single value or tuple)?
│   │   └─ Use key=lambda x: (primary, secondary, ...)
│   │       └─ Descending on one field? Use -value for numbers, wrap with custom class for strings
│   └─ Ordering requires comparing TWO elements simultaneously?
│       └─ Use functools.cmp_to_key(comparator_fn)
│           └─ comparator_fn(a, b): return negative / 0 / positive
│
└─ C++?
    ├─ One-off sort in function?
    │   └─ Lambda: [](const T& a, const T& b){ return ...; }
    ├─ Reused across multiple sorts?
    │   └─ Named struct with operator(): struct Cmp { bool operator()(const T& a, const T& b){...} };
    └─ Sorting by member of struct?
        └─ Lambda capturing nothing: [](const auto& a, const auto& b){ return a.field < b.field; }
```

### Complexity

|Language|Mechanism|Comparator calls|Key function calls|
|---|---|---|---|
|Python `sorted(key=f)`|Timsort|O(n log n) on keys|O(n) — once per element|
|Python `sorted(cmp_to_key(f))`|Timsort|O(n log n) calls to f|—|
|C++ `std::sort(comp)`|Introsort|O(n log n) calls to comp|—|
|C++ `std::stable_sort(comp)`|Merge sort|O(n log² n) calls to comp|—|

## 4. Pseudocode

### Python `key=` Pattern

```
SORT_WITH_KEY(arr, key_function):
    # Phase 1: decorate (O(n) calls to key_function)
    decorated ← [(key_function(x), original_index, x) for each x in arr]

    # Phase 2: sort by keys using standard comparison (O(n log n))
    TIMSORT(decorated)   # compares tuples: (key, index, x)

    # Phase 3: undecorate
    return [x for (key, index, x) in decorated]

# Usage patterns:
SORT_BY_LENGTH_THEN_LEX(strings):
    return SORT_WITH_KEY(strings, key=lambda s: (len(s), s))

SORT_DESCENDING(numbers):
    return SORT_WITH_KEY(numbers, key=lambda x: -x)
    # alternative: sorted(numbers, reverse=True)
```

### Python `cmp_to_key` Pattern

```
COMPARATOR(a, b):
    # Must return: negative if a < b, 0 if a == b, positive if a > b
    if a should come before b:  return -1
    if b should come before a:  return +1
    return 0

# Example: sort strings so their concatenation is maximised
LARGEST_NUMBER_CMP(a, b):
    if a + b > b + a:   return -1   # a before b (a is "larger" in this sense)
    if a + b < b + a:   return +1
    return 0

SORT_WITH_CMP(arr, comparator):
    return sorted(arr, key=functools.cmp_to_key(comparator))
```

### C++ Lambda Comparator Pattern

```
SORT_WITH_LAMBDA(arr):
    # Lambda captures nothing; takes two elements by const reference
    comp ← [](const T& a, const T& b) -> bool:
        # PRIMARY: sort by field1 ascending
        if a.field1 != b.field1:
            return a.field1 < b.field1
        # SECONDARY: tiebreak by field2 descending
        return a.field2 > b.field2

    std::sort(arr.begin(), arr.end(), comp)

# STRICT WEAK ORDERING CHECK before submitting:
# 1. comp(a, a) must return false  [check: if a.field1 == a.field1, falls through to a.field2 > a.field2 = false ✓]
# 2. if comp(a,b) then !comp(b,a)  [check manually for your logic]
# 3. Transitivity: verify no cycles possible
```

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <algorithm>
#include <functional>
#include <iostream>
#include <string>
#include <vector>

// ─── Example struct ───────────────────────────────────────────────────────────
struct Student {
    std::string name;
    int         grade;   // higher = better
    double      gpa;
};

// ─── 1. Lambda comparator (inline, most common) ───────────────────────────────
void sort_by_grade_then_name(std::vector<Student>& students) {
    std::sort(students.begin(), students.end(),
        [](const Student& a, const Student& b) {
            if (a.grade != b.grade) return a.grade > b.grade;  // descending grade
            return a.name < b.name;                             // ascending name tiebreak
        });
}

// ─── 2. Named functor (reusable, preferred for complex logic) ─────────────────
struct StudentCmp {
    bool operator()(const Student& a, const Student& b) const {
        // Sort by GPA descending; tiebreak by name ascending
        if (a.gpa != b.gpa) return a.gpa > b.gpa;
        return a.name < b.name;
    }
};

void sort_by_gpa(std::vector<Student>& students) {
    std::sort(students.begin(), students.end(), StudentCmp{});
}

// ─── 3. Comparator in priority_queue (min-heap of students by grade) ──────────
void demo_priority_queue(std::vector<Student>& students) {
    // CRITICAL: priority_queue's comp is INVERTED — comp(a,b)=true means b has higher priority
    // To get a min-heap by grade, use greater-than:
    auto cmp = [](const Student& a, const Student& b) {
        return a.grade > b.grade;  // 'true' means a has LOWER priority than b → min-heap
    };
    std::priority_queue<Student, std::vector<Student>, decltype(cmp)> pq(cmp);
    for (const auto& s : students) pq.push(s);
    // pq.top() is now the student with the lowest grade
}

// ─── 4. Stable sort (preserves relative order of equal elements) ───────────────
void sort_stable_by_grade(std::vector<Student>& students) {
    // Use std::stable_sort when the relative order of ties must be preserved
    // Cost: O(n log² n) time, O(n) space (vs std::sort's O(1) space)
    std::stable_sort(students.begin(), students.end(),
        [](const Student& a, const Student& b) {
            return a.grade > b.grade;  // ties preserve original order
        });
}

// ─── 5. Partial sort — top-k only ────────────────────────────────────────────
void top_k_students(std::vector<Student>& students, int k) {
    // O(n log k) — much faster than full sort when k << n
    std::partial_sort(students.begin(), students.begin() + k, students.end(),
        [](const Student& a, const Student& b) {
            return a.grade > b.grade;
        });
    // Only students[0..k-1] are correctly sorted; rest are unordered
}

// ─── 6. Dangerous anti-pattern: <= comparator (UB) ───────────────────────────
// NEVER do this:
// std::sort(v.begin(), v.end(), [](int a, int b){ return a <= b; });
// comp(a,a) = true violates irreflexivity → undefined behaviour

// ─── Demo ─────────────────────────────────────────────────────────────────────
int main() {
    std::vector<Student> students = {
        {"Alice", 90, 3.8},
        {"Bob",   90, 3.9},
        {"Carol", 85, 3.7},
        {"Dave",  90, 3.8},
    };

    sort_by_grade_then_name(students);
    for (const auto& s : students) {
        std::cout << s.name << " " << s.grade << " " << s.gpa << "\n";
    }
    // Alice 90 3.8
    // Bob   90 3.9
    // Dave  90 3.8
    // Carol 85 3.7

    sort_by_gpa(students);
    for (const auto& s : students) {
        std::cout << s.name << " " << s.gpa << "\n";
    }
    // Bob   3.9
    // Alice 3.8
    // Dave  3.8
    // Carol 3.7

    return 0;
}
```

### Python (Readable + Pythonic)

```python
import functools
from dataclasses import dataclass, field
from typing import Any


@dataclass
class Student:
    name:  str
    grade: int     # higher = better
    gpa:   float


# ─── 1. key= with tuple (most common pattern) ────────────────────────────────
def sort_by_grade_then_name(students: list[Student]) -> list[Student]:
    """
    Sort descending by grade, then ascending by name as tiebreaker.
    Tuple keys: Python compares element-by-element, left to right.
    Negate grade for descending order (works for numbers).
    """
    return sorted(students, key=lambda s: (-s.grade, s.name))


# ─── 2. key= for descending strings (can't negate strings) ───────────────────
class ReverseStr(str):
    """Wrapper that reverses string comparison — for descending string sort."""
    def __lt__(self, other): return str.__gt__(self, other)
    def __gt__(self, other): return str.__lt__(self, other)
    def __le__(self, other): return str.__ge__(self, other)
    def __ge__(self, other): return str.__le__(self, other)

def sort_by_grade_desc_name_desc(students: list[Student]) -> list[Student]:
    return sorted(students, key=lambda s: (-s.grade, ReverseStr(s.name)))


# ─── 3. cmp_to_key — when two elements must be compared simultaneously ─────────
def largest_number(nums: list[int]) -> str:
    """
    LC 179: arrange integers so their concatenation forms the largest number.
    Cannot express with key= because comparison is mutual: '9' vs '19'
    depends on whether '919' > '199' — requires seeing both.

    Comparator returns negative if a should come BEFORE b.
    """
    def cmp(a: str, b: str) -> int:
        return -1 if a + b > b + a else (1 if a + b < b + a else 0)

    strs = [str(n) for n in nums]
    strs.sort(key=functools.cmp_to_key(cmp))
    result = "".join(strs)
    return "0" if result[0] == "0" else result


# ─── 4. np.lexsort for large arrays (ML-relevant) ────────────────────────────
def sort_dataframe_analog(names: list[str], grades: list[int], gpas: list[float]):
    """
    np.lexsort sorts by LAST key first, then earlier keys as tiebreakers.
    This is the opposite of Python's tuple key= convention — easy to mix up.

    np.lexsort((tiebreaker, primary)) = sort by primary, tiebreak by tiebreaker
    """
    import numpy as np
    # Sort by grade descending (negate), tiebreak by name ascending
    # np.lexsort: last key = primary sort key
    idx = np.lexsort((names, [-g for g in grades]))
    return [(names[i], grades[i], gpas[i]) for i in idx]


# ─── 5. Sorting with @dataclass's __lt__ (alternative to custom comparators) ──
@dataclass(order=True)  # auto-generates __lt__, __le__, __gt__, __ge__ from fields in order
class SortableStudent:
    grade: int   # compared first (negated for descending)
    name:  str   # compared second
    # original fields stored but not compared:
    original_grade: int = field(compare=False)
    gpa:           float = field(compare=False)


# ─── Demo ─────────────────────────────────────────────────────────────────────
if __name__ == "__main__":
    students = [
        Student("Alice", 90, 3.8),
        Student("Bob",   90, 3.9),
        Student("Carol", 85, 3.7),
        Student("Dave",  90, 3.8),
    ]

    ranked = sort_by_grade_then_name(students)
    for s in ranked:
        print(f"{s.name:6} grade={s.grade} gpa={s.gpa}")
    # Alice  grade=90 gpa=3.8
    # Bob    grade=90 gpa=3.9
    # Dave   grade=90 gpa=3.8
    # Carol  grade=85 gpa=3.7

    print()
    print(largest_number([10, 2]))     # "210"
    print(largest_number([3, 30, 34, 5, 9]))  # "9534330"
    print(largest_number([0, 0]))      # "0"
```

## 6. Visual Explanation

### How `key=` Transforms the Sort

```
Original list:   [Student("Bob", 90), Student("Alice", 90), Student("Carol", 85)]
                         │                    │                      │
key=lambda s: (-s.grade, s.name)
                         ▼                    ▼                      ▼
Decorated:       (-90, "Bob", 0)    (-90, "Alice", 1)    (-85, "Carol", 2)
                 ────────────────────────────────────────────────────────
                         │           Sort by decorated tuples           │
                         ▼                                              ▼
Sorted keys:     (-90, "Alice", 1)  (-90, "Bob", 0)      (-85, "Carol", 2)
                         │                    │                      │
Undecorate:              ▼                    ▼                      ▼
Result:          Student("Alice",90) Student("Bob",90)  Student("Carol",85)

Note: -90 == -90, so "Alice" < "Bob" lexicographically → Alice comes first ✓
```

### Strict Weak Ordering — Why `<=` is Fatal

```
Suppose comp(a, b) = (a <= b), and we sort [1, 1]:

std::sort checks: should arr[0] come before arr[1]?
  comp(1, 1) = (1 <= 1) = true  → arr[0] before arr[1]  ✓ (so far)

std::sort (introsort) may then check: should arr[1] come before arr[0]?
  comp(1, 1) = (1 <= 1) = true  → arr[1] before arr[0]  ✗ CONTRADICTION

Algorithm interprets this as: a < b AND b < a simultaneously.
Result: undefined behaviour. In practice: infinite loop, segfault, or wrong output.

Correct:  comp(a, b) = (a < b)
  comp(1, 1) = false  → no swap needed, algorithm terminates ✓
```

### `cmp_to_key` — The Largest Number Problem

```
nums = ["9", "19"]

Option A: concatenate 9 first  →  "9" + "19" = "919"
Option B: concatenate 19 first →  "19" + "9" = "199"

"919" > "199" → "9" should come BEFORE "19"
Comparator returns: cmp("9", "19") = -1  (negative = "9" first)

This is impossible to express with key= alone because:
- key("9")  = ???   There's no single number that places "9" correctly
  relative to ALL other strings.
  ("9" should come before "19" but after "91")
- The comparison is intrinsically pairwise.
```

## 7. Common Variations & Extensions

### 7.1 Coordinate Compression via Sorted Index

A ubiquitous CP pattern: you have values that span [−10⁹, 10⁹] but there are only n ≤ 10⁵ distinct values. Compress them to [0, n−1]:

```python
values = [100, 50, 200, 50, 100]
sorted_unique = sorted(set(values))
rank = {v: i for i, v in enumerate(sorted_unique)}
compressed = [rank[v] for v in values]
# [1, 0, 2, 0, 1]
```

The `key=` here is identity — the sort itself creates the rank mapping. This feeds into [[06.1D prefix sum — construction and range query in O(1)]], [[155.Segment tree — range query and point update O(log n)]], and [[156.Fenwick tree (BIT) — prefix sum with updates O(log n)]] which require dense integer indices.

### 7.2 Sorting with `__lt__` Override on Dataclasses

When the same ordering is used everywhere, bake it into the class with Python's `@functools.total_ordering` or dataclass `order=True`. Use `field(compare=False)` to exclude fields from comparison. This makes the object directly usable in `heapq` without a custom comparator — directly relevant to [[149.Min-heap and max-heap — heap property and array representation]].

### 7.3 Polar Angle Sort (Convex Hull Prerequisite)

Sorting points by polar angle relative to a pivot is a classic CP pattern:

```cpp
// Correct: cross product avoids float precision issues
auto polar_cmp = [&pivot](const Point& a, const Point& b) {
    long long cross = (long long)(a.x - pivot.x) * (b.y - pivot.y)
                    - (long long)(a.y - pivot.y) * (b.x - pivot.x);
    return cross > 0;  // a comes before b if cross product is positive
};
```

Never use `atan2` for this — floating point comparison of angles fails on collinear points. The cross product comparator is exact over integers.

### 7.4 `std::nth_element` — Partial Sort with Custom Comparator

Like `std::partial_sort` but faster: guarantees only that `arr[k]` is what it would be in a fully sorted array, and elements before it are ≤ it, elements after are ≥ it. O(n) average. Used when you need the k-th element or a partition, not a full sort. Directly analogous to [[52.Quickselect — k-th smallest in expected O(n)]]:

```cpp
std::nth_element(arr.begin(), arr.begin() + k, arr.end(),
    [](const Student& a, const Student& b){ return a.gpa > b.gpa; });
// arr[k] is now the student with the (k+1)-th highest GPA
```

## 9. CP Contest Application

### Typical Codeforces Problem Structure

**Greedy + custom sort** is one of the most frequent patterns in Codeforces Div. 2 C/D problems:

```
Given n jobs with (deadline[i], profit[i]), select jobs to maximise total profit
such that no two selected jobs overlap.

→ Sort by deadline ascending.
→ Process in deadline order using DP or greedy.

Comparator: [](auto& a, auto& b){ return a.deadline < b.deadline; }
```

**Multi-key sort for tiebreaking** appears constantly in constructive problems:

```
Sort n strings: primary by length ascending, tiebreak by lexicographic order.
key=lambda s: (len(s), s)   [Python]
[](auto& a, auto& b){ return a.size() != b.size() ? a.size() < b.size() : a < b; }  [C++]
```

### Time Limit Considerations

- `std::sort` with a lambda comparator: approximately 100–150 ns per comparison on n = 10⁶. Budget ~10⁸ comparisons per second.
- Python `sorted` with `key=`: ~50 ns per key call, then C-speed comparison. For n = 10⁵, total ~5 ms — fine.
- Python `sorted` with `cmp_to_key`: ~200 ns per comparison call (Python function overhead). For n = 10⁵, total ~200 ms × log(10⁵) ≈ 3 seconds. **Can TLE.** Prefer `key=` when possible.

### Optimisation Tricks

1. **Precompute keys:** If your key function is expensive (e.g., counting bits, computing hash), precompute `[(key(x), x) for x in arr]` explicitly, sort the pairs, then extract. This is what `key=` does internally, but explicit precomputation helps in C++ where you control the sort.
    
2. **Avoid captures in C++ lambdas:** A capturing lambda may prevent certain compiler optimisations. If you only need element fields, prefer `[](const auto& a, const auto& b)` with zero captures.
    
3. **`std::ranges::sort` (C++20):** Cleaner syntax with projections analogous to Python's `key=`:
    
    ```cpp
    std::ranges::sort(students, std::greater{}, &Student::gpa);
    // sorts by gpa descending — projection + standard comparator
    ```
    
    This is C++20's native answer to Python's `key=`.
