## 1. Intuition First

### The Core Idea

You've built a perfect hash function — it maps every key to a slot in $[0, m)$ in $O(1)$. But then two keys hash to the same slot. This is not a bug; it's mathematically inevitable once $n > m$ (and statistically likely well before that, by the [[40.The birthday paradox and collision probability|birthday paradox]]). The hash function's job is to _minimise_ collisions; the collision resolution strategy's job is to _handle_ them when they occur.

There are exactly two philosophically distinct answers to the question "where does the second key go?":

**Chaining:** Build a secondary data structure _at_ the colliding slot. Both keys live at the same slot, connected by a pointer. The slot becomes a bucket — a mini-container, typically a linked list.

**Open addressing:** Keep _everything inside the array_. The second key probes elsewhere in the same array using a deterministic sequence until it finds an empty slot. No pointers, no external memory — just index arithmetic.

The mental model: chaining is like a city block (address = slot, building = bucket, apartment = key), while open addressing is like a hotel with no reservation system — if your assigned room is taken, you try the next one, then the one after, until you find an empty bed. The hotel has a fixed number of rooms; it _will_ fill up. The city block has buildings that can grow.

### Why This Exists

Both strategies exist because no single strategy dominates across all access patterns, memory constraints, and hardware architectures. The na naive approach — "always use chaining because it's simpler" — misses 30–50% of real-world performance on workloads where cache locality dominates (embedding lookups in neural network forward passes, vocabulary indexing in tokenisers). Conversely, "always use open addressing" breaks catastrophically when load factor exceeds ~0.7 — the probe sequences become arbitrarily long and the expected lookup cost diverges.

### The "Aha" Moment

**Cache lines are 64 bytes. Pointer chasing is a cache miss.** This single hardware reality explains 80% of why Python's `dict` (open addressing) is faster than a textbook chained hash table at small-to-medium load, and why Redis (chained, pointer-based) is slower per lookup but easier to scale across machines where cache coherence doesn't apply.

Every design choice in collision resolution — probe sequence type, max load factor, bucket structure — is an engineering answer to the question: _how do we keep our access pattern inside the CPU's cache hierarchy?_

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**When it appears:** Essentially always when you use `unordered_map` or `unordered_set` — you are implicitly depending on the collision resolution strategy baked into the standard library. You need to understand this to predict and control performance.

**Signal that collision resolution is the bottleneck:**

> "My solution uses `unordered_map` and passes most test cases but TLEs on large random inputs" → Check load factor and rehashing cost.  
> "My solution is correct but gets hacked on Codeforces" → Adversarial keys, not random inputs. Hash function problem (see [[31.Hash function design — properties, uniformity, avalanche]]), not collision resolution.  
> "I'm inserting 10⁶ elements and my map is slow" → Rehashing kicks in multiple times. Reserve capacity upfront: `mp.reserve(1 << 21)`.

**The critical gotcha:** C++ `std::unordered_map` uses **chaining**. This means each bucket is a `std::list<pair<K,V>>` node — every lookup for a key in a populated bucket requires pointer traversal with random memory access. At high $n$ ($\geq 10^6$ entries), this causes L2/L3 cache thrashing. The fix: use a flat open-addressing hash map (like `absl::flat_hash_map` or a hand-rolled Robin Hood map) for cache performance, or pre-reserve enough buckets to keep chains short.

**Rehashing cost matters:** `std::unordered_map` resizes when load factor $\alpha > 1.0$ (implementation-defined, but typically between 1.0 and 2.0). Each resize copies all $n$ entries — $O(n)$ amortised. If you insert without reserving, you trigger $O(\log n)$ rehashes, each costing $O(n)$, for $O(n \log n)$ total insertion cost instead of $O(n)$.

```cpp
// Always reserve for competitive programming when n is known:
unordered_map<int, int> mp;
mp.reserve(1 << 20);   // next power of 2 above your n
mp.max_load_factor(0.25);  // reduce to prevent long chains
```

### Machine Learning / AI

**Python `dict` is open addressing — and you use it constantly.** Every time you build a vocabulary (`word2idx`), cache embeddings, or use `defaultdict` for frequency counting, you are running open-addressed hash tables. Python's load factor threshold is 2/3 — once 2/3 of slots fill, the dict resizes (doubles in CPython). Understanding this prevents silent performance cliffs.

**PyTorch `nn.Embedding` — the embedding table as a hash table:** An embedding table is conceptually a hash table from integer token IDs to float vectors. In practice it's a dense array (direct addressing, no collision), but when you switch to **sparse embeddings** or **hash embeddings** (used in recommendation systems to handle vocabularies of billions of items), you're explicitly choosing a collision resolution strategy. The Facebook DLRM paper uses hash-based embedding tables where collisions are deliberately allowed — multiple tokens share a slot, and the model learns to disambiguate. This is "chaining" at the semantic level, where the "chain" is an average or concatenation of colliding embeddings.

**FAISS and approximate nearest neighbour:** FAISS's `IndexIVF` (Inverted File Index) is literally chaining applied to vector search. Each cluster centroid is a "bucket" (slot), and all vectors assigned to that centroid form the "chain." Query: hash the query vector to its nearest centroid, then scan the chain. This is the exact chaining data structure, applied to high-dimensional geometry.

**Feature hashing in large-scale ML:** `sklearn.feature_extraction.text.HashingVectorizer` uses open addressing internally (via Python's hash tables). Collisions here are intentional and accepted — the model overfits to the combined feature if two features always appear together. Knowing the collision rate (birthday paradox, $O(n^2/m)$ expected collisions for $n$ features and $m$ slots) lets you set `n_features` intelligently.

**The specific insight for ML engineers:** Python dict uses open addressing with **random probing** (derived from the hash value, not linear), which dramatically reduces clustering. When you profile a training loop and find dictionary lookups in the hot path, the bottleneck is often the probe sequence length — which is controlled by load factor. Pre-sizing dicts (initialise with `{k: v for k, v in zip(keys, values)}` in one pass) avoids mid-run rehashing.

## 3. Algorithm / Pattern

### Strategy 1: Chaining

**Structure:** Array of $m$ buckets; each bucket is a linked list (or other container) of all keys that hash to that slot.

**Operations:**

- **Insert($k$, $v$):** Compute $h(k)$. Prepend $(k, v)$ to the list at slot $h(k)$. $O(1)$ time.
- **Search($k$):** Compute $h(k)$. Walk the list at slot $h(k)$ until key found or end. Expected $O(1 + \alpha)$ where $\alpha = n/m$.
- **Delete($k$):** Search, then splice the node out. Expected $O(1 + \alpha)$.

**Load factor analysis:**  
Expected chain length = $n/m = \alpha$. Lookup cost = $O(1 + \alpha)$. To maintain $O(1)$ expected, keep $\alpha = O(1)$, i.e., $m = \Theta(n)$. When $n$ grows, rehash (double $m$, reinsert all keys) — $O(n)$ amortised, $O(1)$ amortised per insertion.

**Advantage:** Load factor can exceed 1.0. Simple to implement. Deletion is clean (no tombstones). Works well with a bad hash (long chains are just slower linked lists, not catastrophic failures).

**Disadvantage:** Pointer per node = extra memory. Each node is a separate heap allocation = cache miss per chain traversal. For a chain of length $k$, you access $k$ different memory locations.

---

### Strategy 2: Open Addressing

**Structure:** A single flat array of $m$ slots. Each slot holds one key-value pair (or is empty/tombstone).

**The probe sequence:** When slot $h(k)$ is occupied, you follow a deterministic sequence of alternative slots until you find an empty one. Three variants:

**Linear Probing:** Probe $h(k), h(k)+1, h(k)+2, \ldots \pmod{m}$

- Cache-friendly: sequential memory access
- Suffers from **primary clustering**: occupied slots form long runs, making later insertions probe through the entire run
- Expected probes on successful search: $\frac{1}{2}\left(1 + \frac{1}{1-\alpha}\right)$
- Expected probes on unsuccessful search: $\frac{1}{2}\left(1 + \frac{1}{(1-\alpha)^2}\right)$
- These blow up as $\alpha \to 1$. Keep $\alpha \leq 0.7$ for linear probing.

**Quadratic Probing:** Probe $h(k), h(k)+1^2, h(k)+2^2, h(k)+3^2, \ldots \pmod{m}$

- Reduces primary clustering (spread-out probes)
- Suffers from **secondary clustering**: keys with same initial hash follow same probe sequence
- Does not always visit all slots — requires $m$ to be prime or power of 2 to guarantee termination

**Double Hashing:** Probe $h(k), h(k)+h_2(k), h(k)+2h_2(k), \ldots \pmod{m}$

- Eliminates both clustering types
- Probe sequence depends on key, not just slot — two keys with same $h(k)$ take different paths
- $h_2(k)$ must be coprime to $m$ (if $m$ is prime: $h_2(k) = 1 + (k \bmod (m-1))$)
- Best expected performance among open-addressing variants

**Deletion in open addressing — the tombstone problem:**  
You cannot simply clear a deleted key's slot. Consider inserting $A \to$ slot 3, $B \to$ slot 4 (slot 3 taken, probed to 4). If you delete $A$ and clear slot 3, searching for $B$ finds slot 3 empty and concludes $B$ doesn't exist — wrong. Solution: mark deleted slots as **tombstones** (a special sentinel value). Searches skip tombstones; insertions can reclaim them.

**Tombstone accumulation:** Tombstones count as occupied during search but as empty during insert. Over time, tombstones degrade search performance without freeing space. Periodic rehashing clears them.

---

### Robin Hood Hashing — The Modern Default

Robin Hood hashing is open addressing with a twist: when inserting a key $k$ at a probed slot currently occupied by key $k'$, if $k$ has probed _farther from its home_ than $k'$ has, steal $k'$'s slot and continue probing for $k'$. This **equalises probe lengths** across all keys — the variance in probe length drops dramatically.

Key property: the maximum probe length is $O(\log n)$ with high probability, versus $O(n)$ for standard linear probing in adversarial cases.

Used by: `absl::flat_hash_map`, Rust's `std::collections::HashMap`, `ska::flat_hash_map`.

**Complexity Summary:**

|Strategy|Expected Lookup|Expected Insert|Space Overhead|Cache Behaviour|
|---|---|---|---|---|
|Chaining|$O(1 + \alpha)$|$O(1)$|$\Theta(n)$ pointers|Poor (pointer chasing)|
|Linear probing|$O!\left(\frac{1}{1-\alpha}\right)$|Same|None|Excellent|
|Quadratic probing|$O!\left(\frac{1}{1-\alpha}\right)$|Same|None|Good|
|Double hashing|$O!\left(\frac{1}{1-\alpha}\right)$|Same|None|Good|
|Robin Hood|$O(1)$ low-variance|$O(1)$ amortised|None|Excellent|

**When to use which:**

```
Need to support α > 1.0?
  └─ Yes → Chaining only (open addressing cannot do this)

Memory-constrained, need zero allocation per entry?
  └─ Yes → Open addressing (linear or Robin Hood)

Frequent deletions?
  └─ Yes → Chaining (tombstones degrade open addressing)
  └─ No → Open addressing fine

Performance critical, cache matters?
  └─ Yes → Robin Hood or linear probing (flat arrays)
  └─ No → Chaining is simpler to implement correctly

Using C++ std::unordered_map?
  └─ Chaining (library choice). Reserve capacity upfront.

Using Python dict?
  └─ Open addressing (language choice). You don't control it.
```

## 4. Pseudocode

```
// ─────────────────────────────────────────────────────────────────────────
// CHAINING HASH TABLE
// ─────────────────────────────────────────────────────────────────────────

DATA HashMap_Chained:
    buckets: Array[m] of LinkedList<(Key, Value)>
    n: int = 0          // current number of entries
    m: int              // number of buckets

FUNCTION insert(key, value):
    i ← hash(key) mod m
    FOR each (k, v) in buckets[i]:
        IF k == key:
            v ← value         // update existing — walk chain to find key
            RETURN
    buckets[i].prepend((key, value))  // prepend: O(1), no search needed
    n ← n + 1
    IF n / m > MAX_LOAD:       // typically MAX_LOAD = 1.0 for chaining
        rehash(m * 2)

FUNCTION search(key) → Value or NULL:
    i ← hash(key) mod m
    FOR each (k, v) in buckets[i]:
        IF k == key: RETURN v
    RETURN NULL

FUNCTION delete(key):
    i ← hash(key) mod m
    remove first node with k == key from buckets[i]
    n ← n - 1

// ─────────────────────────────────────────────────────────────────────────
// OPEN-ADDRESSING HASH TABLE (Linear Probing)
// ─────────────────────────────────────────────────────────────────────────

SENTINEL_EMPTY ← ⊥        // slot has never been used
SENTINEL_DELETED ← ⊤      // slot held a key that was deleted (tombstone)

DATA HashMap_Open:
    slots: Array[m] of (Key | EMPTY | DELETED, Value)
    n: int = 0
    m: int

FUNCTION insert(key, value):
    IF n / m >= MAX_LOAD:    // MAX_LOAD ≈ 0.7 for linear probing
        rehash(m * 2)
    i ← hash(key) mod m
    first_tombstone ← -1
    LOOP:
        IF slots[i] is EMPTY:
            // Safe to insert: no key with this value exists further in probe sequence
            target ← (first_tombstone != -1) ? first_tombstone : i
            slots[target] ← (key, value)
            n ← n + 1
            RETURN
        IF slots[i] is DELETED:
            IF first_tombstone == -1: first_tombstone ← i
            // Do NOT stop: the key might exist further down the probe sequence
        ELSE IF slots[i].key == key:
            slots[i].value ← value    // update
            RETURN
        i ← (i + 1) mod m             // linear probe step

FUNCTION search(key) → Value or NULL:
    i ← hash(key) mod m
    LOOP:
        IF slots[i] is EMPTY: RETURN NULL   // key definitely not present
        IF slots[i] is DELETED:             // skip tombstone, keep probing
            i ← (i + 1) mod m; CONTINUE
        IF slots[i].key == key: RETURN slots[i].value
        i ← (i + 1) mod m
        // Termination guaranteed if α < 1 (at least one EMPTY slot exists)

FUNCTION delete(key):
    i ← hash(key) mod m
    LOOP:
        IF slots[i] is EMPTY: RETURN       // key not found
        IF slots[i].key == key:
            slots[i] ← DELETED             // tombstone, NOT clear to EMPTY
            // Why not EMPTY? Future searches for keys beyond this slot would break
            n ← n - 1
            RETURN
        i ← (i + 1) mod m

// ─────────────────────────────────────────────────────────────────────────
// ROBIN HOOD PROBING (extension of open addressing)
// ─────────────────────────────────────────────────────────────────────────

FUNCTION probe_distance(slot_idx, key):
    // How far has this key probed from its home slot?
    home ← hash(key) mod m
    RETURN (slot_idx - home + m) mod m    // handles wraparound

FUNCTION robin_hood_insert(key, value):
    i ← hash(key) mod m
    current_key ← key; current_val ← value
    current_dist ← 0

    LOOP:
        IF slots[i] is EMPTY:
            slots[i] ← (current_key, current_val)
            RETURN
        existing_dist ← probe_distance(i, slots[i].key)
        IF current_dist > existing_dist:
            // Rob from the rich (short-probed key), give to the poor (long-probed key)
            SWAP (current_key, current_val) with slots[i]
            current_dist ← existing_dist
            // Now continue probing to find a home for the displaced key
        i ← (i + 1) mod m
        current_dist ← current_dist + 1
```

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <bits/stdc++.h>
using namespace std;

// ─────────────────────────────────────────────────────────────────────────────
// 1. Chaining Hash Table — textbook implementation
//    Uses vector<list<pair<K,V>>> as buckets
//    O(1 + α) expected lookup; O(1) insert (amortised with rehash)
// ─────────────────────────────────────────────────────────────────────────────
template<typename K, typename V>
class ChainingHashMap {
    static constexpr double MAX_LOAD = 1.0;  // allow chains up to length ~1
    vector<list<pair<K, V>>> buckets_;
    size_t n_ = 0;
    size_t m_;

    size_t slot(const K& key) const {
        return hash<K>{}(key) % m_;
    }

    void rehash(size_t new_m) {
        vector<list<pair<K,V>>> old = move(buckets_);
        m_ = new_m;
        buckets_.assign(m_, {});
        n_ = 0;
        for (auto& bucket : old)
            for (auto& [k, v] : bucket)
                insert(k, v);
    }

public:
    explicit ChainingHashMap(size_t initial = 16) : m_(initial) {
        buckets_.resize(m_);
    }

    void insert(const K& key, const V& val) {
        if ((double)n_ / m_ >= MAX_LOAD) rehash(m_ * 2);
        auto& bucket = buckets_[slot(key)];
        for (auto& [k, v] : bucket) {
            if (k == key) { v = val; return; }  // update existing
        }
        bucket.emplace_front(key, val);
        ++n_;
    }

    V* find(const K& key) {
        auto& bucket = buckets_[slot(key)];
        for (auto& [k, v] : bucket)
            if (k == key) return &v;
        return nullptr;
    }

    bool erase(const K& key) {
        auto& bucket = buckets_[slot(key)];
        for (auto it = bucket.begin(); it != bucket.end(); ++it) {
            if (it->first == key) {
                bucket.erase(it);
                --n_;
                return true;
            }
        }
        return false;
    }

    size_t size() const { return n_; }
    double load_factor() const { return (double)n_ / m_; }
};

// ─────────────────────────────────────────────────────────────────────────────
// 2. Open Addressing Hash Table — Linear Probing with Tombstones
//    Flat array, zero allocations per entry
//    Cache-friendly: sequential probe = prefetchable memory access
// ─────────────────────────────────────────────────────────────────────────────
template<typename K, typename V>
class LinearProbingHashMap {
    static constexpr double MAX_LOAD = 0.65;  // MUST be < 1.0 for open addressing

    enum class SlotState : uint8_t { EMPTY, OCCUPIED, DELETED };

    struct Slot {
        K key;
        V val;
        SlotState state = SlotState::EMPTY;
    };

    vector<Slot> slots_;
    size_t n_ = 0;   // live entries
    size_t d_ = 0;   // tombstone count
    size_t m_;

    size_t home(const K& key) const {
        return hash<K>{}(key) % m_;
    }

    void rehash(size_t new_m) {
        // Rehashing also clears all tombstones — critical for long-running maps
        vector<Slot> old = move(slots_);
        m_ = new_m;
        slots_.assign(m_, Slot{});
        n_ = 0; d_ = 0;
        for (auto& s : old)
            if (s.state == SlotState::OCCUPIED)
                insert(s.key, s.val);
    }

public:
    explicit LinearProbingHashMap(size_t initial = 16) : m_(initial) {
        slots_.resize(m_);
    }

    void insert(const K& key, const V& val) {
        // Rehash on high load OR too many tombstones (tombstones degrade search)
        if ((double)(n_ + d_) / m_ >= MAX_LOAD) rehash(m_ * 2);

        size_t i = home(key);
        int first_tomb = -1;

        for (size_t probe = 0; probe < m_; ++probe, i = (i + 1) % m_) {
            if (slots_[i].state == SlotState::EMPTY) {
                // Found empty slot — insert here, or at first tombstone if seen
                size_t target = (first_tomb >= 0) ? (size_t)first_tomb : i;
                if (slots_[target].state == SlotState::DELETED) --d_;
                slots_[target] = {key, val, SlotState::OCCUPIED};
                ++n_;
                return;
            }
            if (slots_[i].state == SlotState::DELETED) {
                if (first_tomb < 0) first_tomb = (int)i;
                // Keep probing — key might exist further in the sequence
            } else if (slots_[i].key == key) {
                slots_[i].val = val;  // update
                return;
            }
        }
        // Should never reach here if load factor is kept below 1.0
        assert(false && "Hash table full — invariant violated");
    }

    V* find(const K& key) {
        size_t i = home(key);
        for (size_t probe = 0; probe < m_; ++probe, i = (i + 1) % m_) {
            if (slots_[i].state == SlotState::EMPTY) return nullptr; // definitive miss
            if (slots_[i].state == SlotState::OCCUPIED && slots_[i].key == key)
                return &slots_[i].val;
            // DELETED: skip tombstone, keep probing
        }
        return nullptr;
    }

    bool erase(const K& key) {
        size_t i = home(key);
        for (size_t probe = 0; probe < m_; ++probe, i = (i + 1) % m_) {
            if (slots_[i].state == SlotState::EMPTY) return false;
            if (slots_[i].state == SlotState::OCCUPIED && slots_[i].key == key) {
                slots_[i].state = SlotState::DELETED;  // tombstone — NOT EMPTY
                ++d_; --n_;
                return true;
            }
        }
        return false;
    }

    size_t size() const { return n_; }
    double load_factor() const { return (double)n_ / m_; }
};

// ─────────────────────────────────────────────────────────────────────────────
// 3. Robin Hood Hashing — best-in-class open addressing
//    Equalises probe lengths, dramatically improves cache behaviour
//    Used by: absl::flat_hash_map, Rust HashMap, ska::flat_hash_map
// ─────────────────────────────────────────────────────────────────────────────
template<typename K, typename V>
class RobinHoodHashMap {
    static constexpr double MAX_LOAD = 0.75;  // Robin Hood handles higher load well

    struct Slot {
        K key; V val;
        int dist = -1;  // probe distance from home slot; -1 = empty
    };

    vector<Slot> slots_;
    size_t n_ = 0, m_;

    size_t home(const K& key) const { return hash<K>{}(key) % m_; }

    int probe_dist(size_t idx, const K& key) const {
        return (int)((idx - home(key) + m_) % m_);
    }

    void rehash(size_t new_m) {
        vector<Slot> old = move(slots_);
        m_ = new_m; n_ = 0;
        slots_.assign(m_, Slot{});
        for (auto& s : old)
            if (s.dist >= 0) insert(s.key, s.val);
    }

public:
    explicit RobinHoodHashMap(size_t initial = 16) : m_(initial) {
        slots_.resize(m_);
    }

    void insert(const K& key, const V& val) {
        if ((double)n_ / m_ >= MAX_LOAD) rehash(m_ * 2);

        K cur_key = key; V cur_val = val;
        int cur_dist = 0;
        size_t i = home(key);

        for (;;) {
            if (slots_[i].dist < 0) {
                // Empty slot — place here
                slots_[i] = {cur_key, cur_val, cur_dist};
                ++n_;
                return;
            }
            if (slots_[i].key == cur_key) {
                slots_[i].val = cur_val;  // update
                return;
            }
            if (slots_[i].dist < cur_dist) {
                // Robin Hood: steal from the rich (small dist), give to the poor (large dist)
                swap(cur_key, slots_[i].key);
                swap(cur_val, slots_[i].val);
                swap(cur_dist, slots_[i].dist);
                // Now continue inserting the displaced element
            }
            i = (i + 1) % m_;
            ++cur_dist;
        }
    }

    V* find(const K& key) {
        size_t i = home(key);
        for (int dist = 0; dist <= (int)m_; ++dist, i = (i + 1) % m_) {
            if (slots_[i].dist < 0 || slots_[i].dist < dist) return nullptr;
            // Key insight: if current slot's dist < dist, key cannot exist further
            // (Robin Hood guarantees any key present would have been placed by now)
            if (slots_[i].key == key) return &slots_[i].val;
        }
        return nullptr;
    }

    size_t size() const { return n_; }
};

// ─────────────────────────────────────────────────────────────────────────────
// 4. Demo + Benchmarking
// ─────────────────────────────────────────────────────────────────────────────
int main() {
    ios_base::sync_with_stdio(false);

    // Test all three implementations
    ChainingHashMap<int, string> chain_map;
    LinearProbingHashMap<int, string> lp_map;
    RobinHoodHashMap<int, string> rh_map;

    vector<pair<int,string>> data = {
        {1, "one"}, {17, "seventeen"}, {33, "thirty-three"},  // 1, 17, 33 mod 16 = all slot 1!
        {5, "five"}, {21, "twenty-one"}, {100, "hundred"}
    };

    for (auto& [k, v] : data) {
        chain_map.insert(k, v);
        lp_map.insert(k, v);
        rh_map.insert(k, v);
    }

    // Lookup test
    auto* p = chain_map.find(17);
    cout << "Chaining find(17): " << (p ? *p : "NOT FOUND") << "\n";
    p = lp_map.find(17);
    cout << "Linear probe find(17): " << (p ? *p : "NOT FOUND") << "\n";
    p = rh_map.find(17);
    cout << "Robin Hood find(17): " << (p ? *p : "NOT FOUND") << "\n";

    // Deletion test (validates tombstone logic)
    lp_map.erase(1);           // delete key 1 (home slot for 17 and 33 too)
    p = lp_map.find(17);       // must still find 17 despite slot 1 being tombstone
    cout << "After deleting 1, linear probe find(17): " << (p ? *p : "NOT FOUND") << "\n";

    // Update test
    chain_map.insert(5, "FIVE_UPDATED");
    p = chain_map.find(5);
    cout << "After update, chain find(5): " << (p ? *p : "NOT FOUND") << "\n";

    // Load factor check
    cout << "\nLoad factors after 6 insertions:\n";
    cout << "  Chaining: " << chain_map.load_factor() << "\n";
    cout << "  Linear:   " << lp_map.load_factor() << "\n";
    cout << "  RobinHood:" << rh_map.load_factor() << "\n";

    // Demonstrate std::unordered_map's reserve() — critical for CP
    unordered_map<int,int> std_map;
    std_map.reserve(1 << 20);           // pre-allocate for 1M entries
```

### Python (Readable + Pythonic)

```python
"""
Collision Resolution — Chaining vs Open Addressing
T1 Core — 2. Hashing

Implements:
  1. Chaining hash table (list of lists)
  2. Open-addressing with linear probing + tombstones
  3. Robin Hood hashing
  4. Analysis of Python dict's open addressing behaviour

Complexity:
  Chaining:      O(1 + α) lookup/insert/delete, α = n/m
  Open addressing: O(1/(1-α)) expected, requires α < 1
  Robin Hood:    O(1) with low variance, α ≤ 0.75
"""

from __future__ import annotations
from typing import TypeVar, Generic, Optional
import sys

K = TypeVar('K')
V = TypeVar('V')

_EMPTY = object()     # sentinel: slot never used
_DELETED = object()   # sentinel: slot tombstoned


# ─────────────────────────────────────────────────────────────────────────────
# 1. Chaining Hash Table
# ─────────────────────────────────────────────────────────────────────────────
class ChainingHashMap:
    """
    Hash table with separate chaining using Python lists as buckets.
    
    Properties:
      - α can exceed 1.0 (buckets grow as lists)
      - O(1 + α) expected lookup
      - No tombstone issues — deletion is clean list removal
      - Poor cache behaviour: each bucket element may be at a random address
    """
    MAX_LOAD = 1.0

    def __init__(self, initial_size: int = 8):
        self._m = initial_size
        self._buckets: list[list[tuple]] = [[] for _ in range(self._m)]
        self._n = 0

    def _slot(self, key) -> int:
        return hash(key) % self._m

    def _rehash(self):
        old_buckets = self._buckets
        self._m *= 2
        self._buckets = [[] for _ in range(self._m)]
        self._n = 0
        for bucket in old_buckets:
            for k, v in bucket:
                self[k] = v

    def __setitem__(self, key, value):
        if self._n / self._m >= self.MAX_LOAD:
            self._rehash()
        bucket = self._buckets[self._slot(key)]
        for i, (k, v) in enumerate(bucket):
            if k == key:
                bucket[i] = (key, value)  # update in place
                return
        bucket.append((key, value))        # prepend is O(1) but append is equivalent
        self._n += 1

    def __getitem__(self, key):
        for k, v in self._buckets[self._slot(key)]:
            if k == key:
                return v
        raise KeyError(key)

    def get(self, key, default=None):
        try:
            return self[key]
        except KeyError:
            return default

    def __delitem__(self, key):
        bucket = self._buckets[self._slot(key)]
        for i, (k, _) in enumerate(bucket):
            if k == key:
                bucket.pop(i)
                self._n -= 1
                return
        raise KeyError(key)

    def __len__(self): return self._n
    def load_factor(self): return self._n / self._m

    def bucket_lengths(self) -> list[int]:
        """Diagnostic: show chain length distribution."""
        return [len(b) for b in self._buckets if b]


# ─────────────────────────────────────────────────────────────────────────────
# 2. Open Addressing — Linear Probing with Tombstones
# ─────────────────────────────────────────────────────────────────────────────
class LinearProbingHashMap:
    """
    Open addressing with linear probing.
    
    Properties:
      - Single flat array — excellent cache locality
      - α MUST stay < 1.0 (otherwise table is full and search loops forever)
      - Deletions require tombstones — cannot mark as EMPTY
      - Primary clustering: runs of occupied slots form and lengthen over time
      - Expected lookup: (1 + 1/(1-α)²) / 2 for unsuccessful search
    
    When α = 0.7 (our MAX_LOAD):
      Expected probes (miss) = (1 + 1/0.09) / 2 ≈ 5.7 — still fast
    When α = 0.9:
      Expected probes (miss) = (1 + 1/0.01) / 2 = 50.5 — terrible
    """
    MAX_LOAD = 0.65

    def __init__(self, initial_size: int = 8):
        self._m = initial_size
        self._keys   = [_EMPTY] * self._m
        self._values = [None]   * self._m
        self._n = 0      # live entries
        self._d = 0      # tombstone count

    def _home(self, key) -> int:
        return hash(key) % self._m

    def _rehash(self):
        """Rehash doubles size AND clears tombstones — essential for long-lived maps."""
        old_keys, old_vals = self._keys, self._values
        self._m *= 2
        self._keys   = [_EMPTY] * self._m
        self._values = [None]   * self._m
        self._n = 0; self._d = 0
        for k, v in zip(old_keys, old_vals):
            if k is not _EMPTY and k is not _DELETED:
                self[k] = v

    def __setitem__(self, key, value):
        # Rehash if (live + tombstones) / capacity is too high
        # Tombstones count toward load because they block EMPTY terminators
        if (self._n + self._d) / self._m >= self.MAX_LOAD:
            self._rehash()

        i = self._home(key)
        first_tomb = -1

        for _ in range(self._m):
            if self._keys[i] is _EMPTY:
                # Either insert at first tombstone (recycling space) or here
                target = first_tomb if first_tomb >= 0 else i
                if self._keys[target] is _DELETED:
                    self._d -= 1  # recycling a tombstone
                self._keys[target]   = key
                self._values[target] = value
                self._n += 1
                return
            if self._keys[i] is _DELETED:
                if first_tomb < 0:
                    first_tomb = i
                # Do NOT stop here — key might exist further in probe sequence
            elif self._keys[i] == key:
                self._values[i] = value  # update
                return
            i = (i + 1) % self._m

        raise RuntimeError("Table full — invariant violated (should not happen)")

    def __getitem__(self, key):
        i = self._home(key)
        for _ in range(self._m):
            if self._keys[i] is _EMPTY:
                raise KeyError(key)   # definitive: no key past an EMPTY slot
            if self._keys[i] is not _DELETED and self._keys[i] == key:
                return self._values[i]
            i = (i + 1) % self._m
        raise KeyError(key)

    def get(self, key, default=None):
        try:
            return self[key]
        except KeyError:
            return default

    def __delitem__(self, key):
        i = self._home(key)
        for _ in range(self._m):
            if self._keys[i] is _EMPTY:
                raise KeyError(key)
            if self._keys[i] is not _DELETED and self._keys[i] == key:
                self._keys[i] = _DELETED   # tombstone — NOT _EMPTY
                self._d += 1
                self._n -= 1
                return
            i = (i + 1) % self._m
        raise KeyError(key)

    def __len__(self): return self._n
    def load_factor(self): return self._n / self._m
    def tombstone_fraction(self): return self._d / self._m


# ─────────────────────────────────────────────────────────────────────────────
# 3. Robin Hood Hashing
# ─────────────────────────────────────────────────────────────────────────────
class RobinHoodHashMap:
    """
    Open addressing with Robin Hood probe-length equalisation.
    
    Insight: if an incoming key has probed farther from its home than the
    key currently occupying the slot, swap them. This keeps the maximum
    probe length O(log n) w.h.p. and dramatically reduces variance.
    
    Early termination in search: if current slot's probe distance is less
    than the distance we've traveled, the key cannot exist further
    (Robin Hood would have placed it earlier). This makes unsuccessful
    search faster than standard linear probing.
    
    Used by: Rust std HashMap, abseil flat_hash_map, ska::flat_hash_map
    """
    MAX_LOAD = 0.75  # Robin Hood tolerates higher load than standard LP

    _EMPTY_DIST = -1  # sentinel: slot is unoccupied

    def __init__(self, initial_size: int = 8):
        self._m = initial_size
        self._keys   = [None] * self._m
        self._values = [None] * self._m
        self._dists  = [self._EMPTY_DIST] * self._m  # probe distances
        self._n = 0

    def _home(self, key) -> int:
        return hash(key) % self._m

    def _probe_dist(self, idx: int, key) -> int:
        return (idx - self._home(key)) % self._m

    def _rehash(self):
        old = list(zip(self._keys, self._values, self._dists))
        self._m *= 2
        self._keys   = [None] * self._m
        self._values = [None] * self._m
        self._dists  = [self._EMPTY_DIST] * self._m
        self._n = 0
        for k, v, d in old:
            if d != self._EMPTY_DIST:
                self[k] = v

    def __setitem__(self, key, value):
        if self._n / self._m >= self.MAX_LOAD:
            self._rehash()

        cur_key, cur_val, cur_dist = key, value, 0
        i = self._home(key)

        while True:
            if self._dists[i] == self._EMPTY_DIST:
                self._keys[i]   = cur_key
                self._values[i] = cur_val
                self._dists[i]  = cur_dist
                self._n += 1
                return
            if self._keys[i] == cur_key:
                self._values[i] = cur_val  # update
                return
            # Robin Hood: if resident has smaller probe distance, swap
            if self._dists[i] < cur_dist:
                (self._keys[i], cur_key)     = (cur_key, self._keys[i])
                (self._values[i], cur_val)   = (cur_val, self._values[i])
                (self._dists[i], cur_dist)   = (cur_dist, self._dists[i])
            i = (i + 1) % self._m
            cur_dist += 1

    def __getitem__(self, key):
        i = self._home(key)
        dist = 0
        while True:
            d = self._dists[i]
            if d == self._EMPTY_DIST or d < dist:
                # Early termination: Robin Hood guarantees key is not here
                raise KeyError(key)
            if self._keys[i] == key:
                return self._values[i]
            i = (i + 1) % self._m
            dist += 1

    def get(self, key, default=None):
        try: return self[key]
        except KeyError: return default

    def __len__(self): return self._n


# ─────────────────────────────────────────────────────────────────────────────
# 4. Python dict internals — open addressing in the wild
# ─────────────────────────────────────────────────────────────────────────────
def python_dict_analysis():
    """
    CPython dict uses open addressing with a perturbation-based probe sequence:
    
      slot = (5 * slot + 1 + perturb) % m
      perturb >>= 5
    
    This is NOT linear probing. The perturb term (derived from the hash value)
    means two keys with the same home slot take different probe paths —
    eliminating secondary clustering while maintaining cache-friendliness.
    
    Load factor threshold: 2/3 (≈ 0.667). When exceeded, dict resizes to
    approximately (n * 4 / 3) rounded up to next power of 2.
    
    Implication for ML pipelines:
      - Pre-populate dicts in one pass to avoid mid-operation rehashing
      - dict.fromkeys(keys) is more efficient than repeated dict[k] = v
      - Large vocabs (100k+ tokens): use array-based lookup instead of dict
    """
    import sys

    d = {}
    sizes = []
    for i in range(100):
        d[i] = i
        sizes.append(sys.getsizeof(d))

    # Find resize points (where memory jumps)
    resize_at = [i for i in range(1, len(sizes)) if sizes[i] > sizes[i-1]]
    print("Python dict resize points (n entries when resize triggered):")
    print(resize_at[:10])
    # Typical output: [6, 11, 22, 43, 86, ...] — each ≈ 2/3 of allocated slots

    # Pre-sizing for performance
    vocab = ["token_" + str(i) for i in range(10000)]
    
    # Slow: repeated insertions trigger multiple rehashes
    slow_dict = {}
    for i, t in enumerate(vocab): slow_dict[t] = i

    # Fast: dict comprehension builds in one shot (CPython optimises this)
    fast_dict = {t: i for i, t in enumerate(vocab)}

    print(f"\nBoth dicts have same content: {slow_dict == fast_dict}")
    print(f"Memory (slow): {sys.getsizeof(slow_dict):,} bytes")
    print(f"Memory (fast): {sys.getsizeof(fast_dict):,} bytes")
    # Often identical, but the comprehension avoids intermediate resize copies
```

```
Initial state after inserting keys A(hash=2), B(hash=2), C(hash=2):
(All three hash to slot 2; linear probing places them at 2, 3, 4)

Idx │  2  │  3  │  4  │  5  │ ...
    │  A  │  B  │  C  │ --- │

─────────────────────────────────────────────────────────────────────

Step 1: Delete A from slot 2.

WRONG approach — mark slot 2 as EMPTY:
Idx │  2  │  3  │  4  │  5  │
    │ --- │  B  │  C  │ --- │

  hash(C) = 2 → check slot 2 → EMPTY → return "not found"  ✗ WRONG!
  C is at slot 4 but we gave up at slot 2.

─────────────────────────────────────────────────────────────────────

CORRECT approach — mark slot 2 as DELETED (tombstone):
Idx │  2  │  3  │  4  │  5  │
    │ 🪦  │  B  │  C  │ --- │
    ↑
  Tombstone: "something was here, keep probing"

Search for C:
  hash(C) = 2 → slot 2 is TOMBSTONE → keep probing
              → slot 3 is B ≠ C    → keep probing
              → slot 4 is C = C    → FOUND ✓

Search for X (not inserted):
  hash(X) = 2 → slot 2 is TOMBSTONE → keep probing
              → slot 3 is B ≠ X    → keep probing
              → slot 4 is C ≠ X    → keep probing
              → slot 5 is EMPTY    → return NOT FOUND ✓

─────────────────────────────────────────────────────────────────────

Tombstone accumulation problem over time:
After many inserts and deletes:

Idx │  0  │  1  │  2  │  3  │  4  │  5  │  6  │  7  │
    │ 🪦  │  X  │ 🪦  │ 🪦  │  Y  │ 🪦  │  Z  │ 🪦  │

Searching for any key requires scanning tombstones.
3 live keys, 5 tombstones, load_factor = 3/8 = 0.375 but feels like 8/8 = 1.0
```

### Diagram 3: Robin Hood — Equalising Probe Lengths

```
Table size m=8. Keys with home slots and current probe distances (dist):
Robin Hood invariant: no key has a shorter dist than its predecessor in the probe chain.

─────────────────────────────────────────────────────────────────────
INSERT order: P(home=0), Q(home=0), R(home=0)

After P:   [P|d=0] [   ] [   ] [   ] [   ] [   ] [   ] [   ]
After Q:   [P|d=0] [Q|d=1][   ] [   ] [   ] [   ] [   ] [   ]
After R:   [P|d=0] [Q|d=1][R|d=2][   ] [   ] [   ] [   ] [   ]

Standard linear probing result:
  P: probe 0 (at home)
  Q: probe 1 (1 away from home)
  R: probe 2 (2 away from home)
  Max probe: 2. This is fine for 3 keys.

─────────────────────────────────────────────────────────────────────
Now insert S(home=1):

Standard LP: S tries slot 1 (Q is there), then slot 2 (R is there), then slot 3. dist(S) = 2.

Robin Hood LP: S tries slot 1.
  dist(Q at slot 1) = 1. dist(S wanting slot 1) = 0.
  S has dist 0 < Q's dist 1 → Q is "richer" (shorter probe), S does not steal.
  S moves to slot 2. dist(R at slot 2) = 2. dist(S at slot 2) = 1.
  S has dist 1 < R's dist 2 → R is "richer" → STEAL. S takes slot 2, evict R.
  
Robin Hood result:
  Slot 0: [P|d=0]   Slot 1: [Q|d=1]   Slot 2: [S|d=1]   Slot 3: [R|d=2]
                                        ↑
                                   S "stole" slot 2 from R

Why is this better?
  Standard: P=0, Q=1, R=2, S=2 → max_dist=2, but two keys have dist 2.
  Robin Hood: P=0, Q=1, S=1, R=2 → max_dist=2, but more equitable distribution.

Key benefit: search for absent key terminates EARLY.
  Searching for T(home=0): probe 0, 1, 2...
  At slot 3, R has dist=2. If T were inserted with dist=3, Robin Hood
  would have placed it by now. Since dist(current slot) < our dist → STOP.
  This early termination is Robin Hood's search advantage over standard LP.
```

## 7. Common Variations & Extensions

### 1. Cuckoo Hashing

Two hash functions $h_1, h_2$; two tables $T_1, T_2$. Key $k$ lives either at $T_1[h_1(k)]$ or $T_2[h_2(k)]$. On collision, evict the current occupant and reinsert it using its _other_ table. **Worst-case $O(1)$ lookup** (only two positions to check). The "cuckoo" eviction can cascade — if it cycles, rehash. Used in hardware packet classification (IPv4 routing tables). Not common in software but the $O(1)$ worst-case guarantee is theoretically important.

### 2. Hopscotch Hashing

A hybrid: key $k$ must live within $H$ slots of its home (a "neighbourhood"). If the target slot is occupied, swap with a closer neighbour to make room. Designed for concurrent hash tables — each neighbourhood maps to a single word, enabling atomic updates. Used in Java's `ConcurrentHashMap` prior to Java 8.

### 3. Extendible Hashing (for Databases)

When the hash table must live on disk and doesn't fit in RAM, pages cannot be rehashed freely. Extendible hashing uses a directory of page pointers; when a page overflows, split that page and update only affected directory entries. PostgreSQL's `pg_hash` uses a variant of this. Connects to [[220.Data pipeline design — streaming vs batch, shuffling, prefetching]].

### 4. Choosing Bucket Structure in Chaining

Standard chaining uses a linked list (each chain element on the heap). Modern implementations use:

- **Array-based buckets:** When expected chain length is short, a small `vector<pair<K,V>>` inside each bucket avoids pointer overhead and improves cache behaviour for short chains.
- **Self-balancing BST buckets:** Java 8's `HashMap` converts chains longer than 8 elements to a red-black tree (see [[148.Red-Black tree — insertion rules and colour invariants]]), giving $O(\log n)$ worst-case per bucket instead of $O(n)$.

## 9. CP Contest Application

### Typical Contest Pattern

**Codeforces Div. 1 C / Div. 2 D:** Given $n \leq 10^6$ strings or integers, process queries with $O(1)$ per query. Using `unordered_map` naively TLEs due to cache thrashing from chaining. Solution: either use `reserve + max_load_factor` or switch to a flat open-addressing map.

```cpp
// CP-standard pattern: safe unordered_map that won't get hacked or thrash cache
struct custom_hash {
    static uint64_t splitmix64(uint64_t x) {
        x += 0x9e3779b97f4a7c15; x = (x^(x>>30))*0xbf58476d1ce4e5b9;
        x = (x^(x>>27))*0x94d049bb133111eb; return x^(x>>31);
    }
    size_t operator()(uint64_t x) const {
        static const uint64_t FIXED_RANDOM =
            chrono::steady_clock::now().time_since_epoch().count();
        return splitmix64(x + FIXED_RANDOM);
    }
};

// ALWAYS do this before inserting n elements:
unordered_map<long long, int, custom_hash> mp;
mp.reserve(1 << 21);        // round up to next power of 2 above n
mp.max_load_factor(0.25);   // force 4x more buckets than entries
                             // → average chain length ≈ 0.25 → near O(1) guaranteed
```

**Why `max_load_factor(0.25)` instead of the default 1.0?** C++ `unordered_map` is chained. At load factor 1.0, the average chain is 1 element — but the _variance_ is high (birthday paradox → some chains are $O(\log n / \log \log n)$). At load factor 0.25, average chain is 0.25 — almost all lookups touch exactly one element, no pointer chasing.

**Time complexity impact in practice:**

|Setup|$n = 10^6$ inserts|$10^6$ lookups|
|---|---|---|
|`unordered_map` default|~400ms|~350ms|
|`unordered_map` with `reserve` + `max_load_factor(0.25)`|~120ms|~80ms|
|`absl::flat_hash_map` (Robin Hood)|~90ms|~60ms|

The 3–5x gap is purely collision resolution + cache behaviour. No algorithmic change.
