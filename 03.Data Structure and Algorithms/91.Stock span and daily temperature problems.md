## 1. Intuition First

### The Core Idea

Two problems. One pattern. Both are instances of the same underlying question: **"Looking backward from position $i$, how far can you extend before the sequence breaks a condition?"**

**Stock Span:** On day $i$, the stock price is $p[i]$. The _span_ is the maximum number of consecutive days ending at today where the price was less than or equal to today's price — including today itself. You're measuring a streak of non-decreasing dominance.

**Daily Temperatures:** Given temperatures $T[i]$, for each day find how many days you must wait until a strictly warmer day. You're measuring forward distance to the next event that breaks the current state.

The naive approach for both scans backward/forward from each position: $O(n^2)$. The insight that makes both $O(n)$ is identical: **you don't need to re-examine every past element — elements that have already been "dominated" by something closer can be skipped entirely.** A monotonic stack maintains exactly the set of unresolved candidates, discarding the dominated ones as they are resolved.

### Why This Exists

These are not niche problems. They are the entry point to a family of "nearest event" queries:

- Next greater element
- Previous greater or equal element
- Next smaller element
- First day with higher temperature
- Stock span (previous greater element, distance version)

Each is a one-pass $O(n)$ solution once you recognise the monotonic stack pattern. Without it, every query requires a nested scan — $O(n^2)$ total, which fails for $n = 10^5$ in any 2-second time limit.

The "span" framing is particularly important: it packages _both_ the value condition and the distance into a single number, which is what financial technical indicators do. Understanding this algorithmically is the bridge to implementing rolling window statistics efficiently.

### The "Aha" Moment

**For stock span:** If the stack contains the indices of prices that haven't been beaten yet (in decreasing order of price, i.e., a monotonic decreasing stack), then when today's price $p[i]$ comes in, we pop everything it dominates. The span is `i - index_of_first_undominated_element_left`. The stack isn't storing history for its own sake — it's storing the _unresolved left boundaries_.

**For daily temperatures:** The stack holds indices of days that are _waiting_ for a warmer day. When day $i$ arrives with temperature $T[i]$, it resolves every waiting day $j$ where $T[j] < T[i]$. The answer for each resolved day is `i - j`. The stack is a queue of open questions; each new element answers as many as it can.

**Unifying insight:** A monotonic stack is an $O(n)$ algorithm for answering "nearest element satisfying condition $X$" for all positions simultaneously. The condition determines stack direction (increasing vs decreasing); the popping event is the answer to each waiting query.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**When it appears:**

- Any problem asking for "span", "streak", "dominance window" in a sequence.
- "For each element, find the nearest greater/smaller/equal element" in any direction.
- Problems involving stock prices, temperature records, or any time-series with threshold-crossing events.
- Problems where $O(n^2)$ is too slow and the query is monotone in some direction.

**Signal patterns:**

> "For each position $i$, find the closest $j < i$ such that $a[j] > a[i]$" → monotonic decreasing stack, push indices, answer is stack top at time of query.

> "For each position $i$, find how many consecutive previous elements satisfy condition on $a[i]$" → span pattern, store (value, cumulative_span) pairs on stack.

> "Process elements online (one by one), answering queries about past elements" → stack resolves past queries as new elements arrive.

**Common traps:**

1. **Stack stores values vs. indices.** For daily temperatures you need the _distance_ `i - j`, so you must store indices, not values. Beginners store values and lose the position information.
    
2. **Span accumulation in the stock span problem.** A naive stack stores individual past indices. But when you pop a dominated element, you can skip directly to the _boundary it already represents_ — store `(price, span)` pairs instead of raw indices. This gives $O(1)$ per pop rather than redundant work on already-merged spans. Miss this and your solution is still correct but harder to reason about.
    
3. **Strict vs. non-strict inequalities.** Stock span uses `<=` (today dominates past equal prices). Daily temperatures use `<` (need _strictly_ warmer). Getting this wrong produces off-by-one answers on flat sequences. Always check the problem statement's exact condition.
    
4. **Online vs. offline.** Stock span is naturally _online_ — you process prices one at a time and answer each query immediately. Daily temperatures require seeing future values, so it's inherently offline (process the full array). Don't apply the online stock-span approach to daily temperatures without modification.
    

### Machine Learning / AI

**1. Technical Indicators in Quantitative Finance / Forecasting:**  
The stock span is the algorithmic core of several technical indicators. The _Relative Strength Index_ (RSI) requires counting consecutive up/down days; that counting operation is the span problem. The _Average True Range_ (ATR) uses rolling max/min over a window — the same monotonic structure. Libraries like `pandas-ta` and `TA-Lib` implement these as rolling operations; understanding that the underlying algorithm is $O(n)$ (not $O(n \cdot k)$ for window size $k$) tells you why they scale.

**2. Event-Driven Time Series in ML Pipelines:**  
The daily temperatures pattern — "how long until the next event exceeding a threshold?" — is the exact computation for **time-to-event features** in survival analysis and clickstream modelling. In `scikit-survival` and hazard modelling, the "time until next conversion" feature for a user session is algorithmically identical to daily temperatures: scan forward, find the nearest day where the engagement metric crosses a threshold. A naïve $O(n^2)$ implementation in a feature engineering pipeline on $10^7$ events is a 10-second bottleneck; the stack solution is 50ms.

**3. Sequence Labelling and CRF Decoding:**  
In Conditional Random Fields (CRFs) used for NER and POS tagging, the Viterbi algorithm propagates "dominance" forward through a trellis. The monotonic structure — only keeping the best path at each position — is the same pruning principle as the stack discarding dominated elements. Understanding the span/temperature algorithms builds the intuition for why Viterbi doesn't need to track all $O(n \cdot K^2)$ paths explicitly. See [[186.Viterbi algorithm — DP for HMM decoding]].

**4. `pandas` `shift()` and `where()` Patterns:**  
The daily temperatures result — for each index, the distance to the next value exceeding a threshold — can be vectorised in Pandas:

```python
# Naive O(n^2) — what most analysts write first
result = [next((j-i for j in range(i+1,len(T)) if T[j]>T[i]), 0) for i in range(len(T))]

# Stack O(n) — what the pipeline should use
# Understanding the algorithm lets you recognise when to replace nested loops
```

The gap between these two is the gap between a feature engineering pipeline that runs in seconds versus minutes on real datasets.

## 3. Algorithm / Pattern

### Problem 1 — Stock Span

**Input:** Prices $p[0..n-1]$ arriving one at a time (online).  
**Output:** For each day $i$, the span $s[i]$ = largest $k$ such that $p[i-k+1], \ldots, p[i]$ are all $\leq p[i]$.

**Stack invariant:** Maintain a monotonic decreasing stack of `(price, span)` pairs. When processing day $i$:

- Accumulated span starts at 1 (today itself).
- While stack top price $\leq p[i]$: pop the top, add its span to the accumulated span.
- Push `(p[i], accumulated_span)`.
- $s[i]$ = accumulated span.

**Why `(price, span)` not just indices?** When you pop a dominated element, you don't need to revisit what _it_ dominated — its span already encodes that. You're merging spans greedily. This is the key optimisation.

### Problem 2 — Daily Temperatures

**Input:** Temperatures $T[0..n-1]$, full array available (offline).  
**Output:** For each day $i$, $\text{ans}[i]$ = smallest $d > 0$ such that $T[i+d] > T[i]$, or 0 if none exists.

**Stack invariant:** Maintain a monotonic decreasing stack of indices (temperatures decrease from bottom to top). When processing day $i$:

- While stack top index $j$ satisfies $T[j] < T[i]$: pop $j$, set $\text{ans}[j] = i - j$.
- Push $i$.
- After full pass: any index remaining in the stack gets answer 0 (no warmer day found).

### Unified Decision Tree

```
Query type?
│
├── "Distance/count to NEXT element satisfying condition"
│   (daily temperatures, next greater element)
│   → Offline scan left-to-right
│   → Monotonic stack of INDICES
│   → Pop when current element satisfies the condition for the stack top
│   → Answer[popped index] = current index - popped index
│
├── "How many consecutive PREVIOUS elements satisfy condition"
│   (stock span, streak counting)
│   → Online scan left-to-right
│   → Monotonic stack of (VALUE, CUMULATIVE_SPAN) pairs
│   → Pop and accumulate span when current value dominates stack top
│   → Push merged span
│
└── "Nearest element to the LEFT satisfying condition"
    (previous greater element)
    → At each position, stack top AFTER popping dominated elements
      is the answer (don't pop; just peek)
    → See [[87.Monotonic increasing stack — next greater element]]
```

### Complexity

Both problems: each element is pushed once and popped at most once.

$$T(n) = O(n) \quad \text{amortised} \qquad S(n) = O(n) \text{ (stack)}$$

Worst case for stack size: strictly decreasing prices → all elements pushed, none popped until the very end of a traversal. Stack fills to size $n$.

## 4. Pseudocode

### Stock Span

```
function stockSpan(prices):
    stack = empty stack of (price, span) pairs
    result = []

    for each price p in prices:
        span = 1                          // today counts as 1

        // Merge all dominated past spans into current span
        while stack not empty and stack.top().price <= p:
            span += stack.pop().span      // absorb the dominated span

        stack.push((p, span))
        result.append(span)

    return result
```

### Daily Temperatures

```
function dailyTemperatures(T):
    n = length(T)
    ans = array of zeros, length n        // default: 0 = no warmer day ahead
    stack = empty stack of indices        // indices with unanswered "warmer day" queries

    for i from 0 to n-1:
        // Current day i resolves all waiting days cooler than T[i]
        while stack not empty and T[stack.top()] < T[i]:
            j = stack.pop()
            ans[j] = i - j                // days waited = distance

        stack.push(i)
        // i stays on stack until a warmer day arrives (or end of array)

    // Remaining stack elements: no warmer day found → ans stays 0
    return ans
```

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <bits/stdc++.h>
using namespace std;

// ============================================================
// Problem 1: Stock Span
// ============================================================
class StockSpanner {
    // Each entry: {price, span accumulated by this price and all it dominated}
    stack<pair<int,int>> stk_;

public:
    StockSpanner() = default;

    /**
     * Process the next stock price and return its span.
     * Online: call next() once per trading day as prices arrive.
     *
     * Span = max consecutive days (ending today) where price <= today's price.
     * Time per call: O(1) amortised (each price pushed/popped at most once)
     * Space: O(n) total across all calls
     */
    int next(int price) {
        int span = 1;

        // Absorb all dominated past prices into the current span
        while (!stk_.empty() && stk_.top().first <= price) {
            span += stk_.top().second;
            stk_.pop();
        }

        stk_.push({price, span});
        return span;
    }
};

// ============================================================
// Problem 2: Daily Temperatures
// ============================================================

/**
 * For each day, returns the number of days until a strictly warmer day.
 * Returns 0 if no warmer day exists.
 *
 * Time:  O(n) — each index pushed and popped at most once
 * Space: O(n) — stack of pending indices
 */
vector<int> dailyTemperatures(const vector<int>& T) {
    int n = T.size();
    vector<int> ans(n, 0);
    stack<int> stk;  // indices of days awaiting a warmer future day

    for (int i = 0; i < n; ++i) {
        // Today (i) resolves all pending days that are cooler than T[i]
        while (!stk.empty() && T[stk.top()] < T[i]) {
            int j = stk.top();
            stk.pop();
            ans[j] = i - j;
        }
        stk.push(i);
        // Days remaining in stack at the end get ans = 0 (already initialised)
    }

    return ans;
}

// ============================================================
// Extension: Next Greater Element (offline, two arrays)
// ============================================================

/**
 * For each element in nums1, find the next greater element in nums2.
 * -1 if none exists.
 * Time: O(|nums2| + |nums1|)
 */
vector<int> nextGreaterElement(
    const vector<int>& nums1,
    const vector<int>& nums2
) {
    // Build next-greater map for nums2 in one pass
    unordered_map<int,int> next_greater;
    stack<int> stk;  // values (nums2 has distinct elements)

    for (int val : nums2) {
        while (!stk.empty() && stk.top() < val) {
            next_greater[stk.top()] = val;
            stk.pop();
        }
        stk.push(val);
    }
    // Remaining in stack: no greater element → mapped to -1 implicitly

    vector<int> ans;
    ans.reserve(nums1.size());
    for (int x : nums1) {
        ans.push_back(next_greater.count(x) ? next_greater[x] : -1);
    }
    return ans;
}

// ============================================================
// Test harness
// ============================================================
int main() {
    // --- Stock Span ---
    {
        StockSpanner spanner;
        vector<int> prices  = {100, 80, 60, 70, 60, 75, 85};
        vector<int> expected = {1,   1,  1,  2,  1,  4,  6};
        bool ok = true;
        for (int i = 0; i < (int)prices.size(); ++i) {
            int got = spanner.next(prices[i]);
            if (got != expected[i]) ok = false;
        }
        cout << (ok ? "✓" : "✗") << "  Stock span\n";
    }

    // --- Daily Temperatures ---
    {
        struct Case { vector<int> T; vector<int> expected; };
        vector<Case> tests = {
            {{73,74,75,71,69,72,76,73}, {1,1,4,2,1,1,0,0}},
            {{30,40,50,60},             {1,1,1,0}},
            {{30,60,90},                {1,1,0}},
            {{90,80,70,60},             {0,0,0,0}},   // strictly decreasing
        };

        bool all_ok = true;
        for (auto& [T, exp] : tests) {
            auto got = dailyTemperatures(T);
            bool ok = (got == exp);
            if (!ok) all_ok = false;
            cout << (ok ? "✓" : "✗") << "  Daily temps T=" << T[0] << "...\n";
        }
        cout << (all_ok ? "✓" : "✗") << "  All daily temp tests\n";
    }

    // --- Next Greater Element ---
    {
        vector<int> n1 = {4,1,2};
        vector<int> n2 = {1,3,4,2};
        auto got      = nextGreaterElement(n1, n2);
        vector<int> exp = {-1,3,-1};
        cout << (got == exp ? "✓" : "✗") << "  Next greater element\n";
    }

    return 0;
}
```

### Python (Readable + Pythonic)

```python
from typing import List
from collections import deque


# ============================================================
# Problem 1: Stock Span
# ============================================================

class StockSpanner:
    """
    Online stock span calculator.

    Maintains a monotonic decreasing stack of (price, span) pairs.
    Each call to next() processes one incoming price in O(1) amortised time.

    The span stored with each stack entry is the merged span of all prices
    it dominated — so popping one entry absorbs all its history in O(1).
    """

    def __init__(self):
        # Stack entries: (price, cumulative_span)
        self._stack: List[tuple] = []

    def next(self, price: int) -> int:
        """
        Returns the span for today's price.
        Span = # consecutive days (ending today) with price <= today's price.
        """
        span = 1
        while self._stack and self._stack[-1][0] <= price:
            span += self._stack.pop()[1]   # absorb dominated span
        self._stack.append((price, span))
        return span


def stock_span_batch(prices: List[int]) -> List[int]:
    """
    Batch version: process all prices at once.
    Same logic as StockSpanner but for offline use.
    Time: O(n), Space: O(n)
    """
    spanner = StockSpanner()
    return [spanner.next(p) for p in prices]


# ============================================================
# Problem 2: Daily Temperatures
# ============================================================

def daily_temperatures(T: List[int]) -> List[int]:
    """
    For each day, returns days until next strictly warmer day (0 if none).

    Stack stores indices of days waiting for their warmer-day resolution.
    Invariant: temperatures at stacked indices are non-increasing.
    When T[i] > T[stack top j], day j is resolved: ans[j] = i - j.

    Time: O(n) — each index pushed/popped at most once
    Space: O(n) — stack
    """
    n = len(T)
    ans = [0] * n
    stack: List[int] = []   # indices, T[stack[i]] non-increasing

    for i in range(n):
        # Resolve all days cooler than today
        while stack and T[stack[-1]] < T[i]:
            j = stack.pop()
            ans[j] = i - j
        stack.append(i)
    # Remaining indices in stack: no warmer day → ans stays 0

    return ans


# ============================================================
# Extension: Next Greater Element I & II
# ============================================================

def next_greater_element(nums1: List[int], nums2: List[int]) -> List[int]:
    """
    For each element in nums1, find next greater element in nums2.
    Returns -1 if none. nums2 contains distinct values.
    Time: O(|nums1| + |nums2|), Space: O(|nums2|)
    """
    next_greater: dict[int, int] = {}
    stack: List[int] = []  # values (distinct in nums2)

    for val in nums2:
        while stack and stack[-1] < val:
            next_greater[stack.pop()] = val
        stack.append(val)
    # Remaining in stack map to -1 (not in next_greater dict)

    return [next_greater.get(x, -1) for x in nums1]


def next_greater_element_circular(nums: List[int]) -> List[int]:
    """
    Next greater element in a circular array (LC 503).
    Trick: simulate two passes over the array using modular indexing.
    Do NOT actually double the array — just iterate 2n times with i % n.

    Time: O(n), Space: O(n)
    """
    n = len(nums)
    ans = [-1] * n
    stack: List[int] = []  # indices

    for i in range(2 * n):
        idx = i % n
        while stack and nums[stack[-1]] < nums[idx]:
            j = stack.pop()
            ans[j] = nums[idx]
        # Only push in first pass (avoid re-pushing resolved indices)
        if i < n:
            stack.append(idx)

    return ans


# ============================================================
# Test harness
# ============================================================

if __name__ == "__main__":
    print("=== Stock Span ===")
    prices   = [100, 80, 60, 70, 60, 75, 85]
    expected = [1,   1,  1,  2,  1,  4,  6]
    got = stock_span_batch(prices)
    ok  = got == expected
    print(f"{'✓' if ok else '✗'}  prices={prices}")
    print(f"   expected={expected}")
    print(f"   got     ={got}")

    print("\n=== Daily Temperatures ===")
    dt_cases = [
        ([73,74,75,71,69,72,76,73], [1,1,4,2,1,1,0,0]),
        ([30,40,50,60],             [1,1,1,0]),
        ([30,60,90],                [1,1,0]),
        ([90,80,70,60],             [0,0,0,0]),
        ([70,70,70],                [0,0,0]),   # equal temps: no strictly warmer
    ]
    for T, exp in dt_cases:
        got = daily_temperatures(T)
        ok  = got == exp
        print(f"{'✓' if ok else '✗'}  T={T}  expected={exp}  got={got}")

    print("\n=== Next Greater Element ===")
    got = next_greater_element([4,1,2], [1,3,4,2])
    print(f"{'✓' if got == [-1,3,-1] else '✗'}  got={got}  expected=[-1, 3, -1]")

    print("\n=== Next Greater Element Circular ===")
    got = next_greater_element_circular([1,2,1])
    print(f"{'✓' if got == [2,-1,2] else '✗'}  got={got}  expected=[2, -1, 2]")
```

### Diagram 3 — Span Merging vs. Index Storage

```
WHY store (price, span) pairs instead of raw indices for stock span:

Prices: [100, 80, 60, 70, 60, 75, 85]

With RAW INDEX storage — at Day 6 (p=85):
  Stack contains indices [2, 3, 5] with prices [60, 70, 75]
  Need to pop index 5 (span=1), then 3 (span=1), then 2 (span=1)
  Must also account for index 4 (p=60) which was already popped
  → Reconstructing span=6 requires external tracking of what was discarded

With (PRICE, SPAN) pairs — at Day 6 (p=85):
  Stack contains [(100,1),(80,1),(75,4)]
  Pop (75,4) → span accumulates 4 (includes days 2,3,4,5 already)
  Pop (80,1) → span accumulates 1 (day 1)
  Span = 1 (today) + 4 + 1 = 6  ← correct in 2 pops, no external tracking

The span stored in (75,4) encodes all 4 days that 75 dominated.
Popping it costs O(1) regardless of how many days it represents.
This is the key difference between O(n) amortised and O(n²) worst-case
for index-based reconstruction.
```

## 7. Common Variations & Extensions

### Variation 1 — Next Greater Element II: Circular Array (LC 503)

Circular arrays mean element $0$ can see elements from the end. Simulate two passes: iterate indices $0$ to $2n-1$ with `i % n` for array access, but only push real indices ($i < n$) onto the stack. This prevents double-counting of resolved indices in the second virtual pass. The core resolution logic is identical.

### Variation 2 — Previous Greater Element

A symmetric variant: for each position, find the nearest greater element to its _left_. Process left-to-right; the stack top _after popping dominated elements_ (but before pushing the current element) is the answer. No pop-and-record step — just peek. This is the direct stack-based solution for the histogram problem's left boundary computation in [[89.Largest rectangle in histogram — the canonical monotonic stack problem]].

### Variation 3 — Online Sliding Window Maximum (LC 239)

Extend the "unresolved candidates" idea to a fixed window of size $k$: maintain a monotonic decreasing deque of indices; eject the front when it falls outside the window. This is the deque generalisation of the same monotonic structure, covered in [[95.Sliding window maximum with monotonic deque]].

### Variation 4 — Sum of Subarray Minimums / Stock Span Weighted (LC 907)

Weight each span by the bar's value: $\sum_i p[i] \times \text{span}[i]$. The stock span algorithm already computes the span; multiply and accumulate. The harder version (LC 907) requires careful handling of duplicate values to avoid double-counting subarrays — use strict inequality on one boundary and non-strict on the other (the canonical anti-duplication trick for monotonic stacks).

## 9. CP Contest Application

### Typical Codeforces/AtCoder Problem Structure

**Template A — Span/Dominance:**

> Given a sequence, for each element find the length of the maximal contiguous window ending at that element where the element is the maximum (or minimum). Sum, multiply, or filter these spans.

**Template B — Next Event:**

> An array of values arrives. For each index, find the first future index where the value exceeds a threshold or changes by more than $\delta$. Answer all $n$ queries in $O(n)$.

**Template C — Online Query:**

> Prices arrive one at a time. After each price, answer a query about the current streak or dominance window. Must be $O(1)$ per query (online, no preprocessing over future values).

These appear in Codeforces Div. 2 C through Div. 1 B range. The "span" structure also underlies hard combinatorial counting problems (Div. 1 C–D) where you count subarrays by their minimum or maximum element.

### Time Limit Considerations

- $n \leq 10^6$: both algorithms are fast enough. Prefer `vector<int>` over `std::stack` in C++ (contiguous memory, ~30% faster in tight loops).
- Online problems with $q = 10^6$ queries: the `StockSpanner` pattern handles each in $O(1)$ amortised. Total $O(q)$.

### CP Optimisation Tricks

**1. `vector` as stack in C++:**

```cpp
vector<pair<int,int>> stk;
stk.reserve(n);
// Use stk.back(), stk.pop_back(), stk.push_back() — faster than std::stack
```

**2. Sentinel values:** Append a sentinel price of `INT_MAX` at the start for stock span (ensures nothing is ever larger, so the stack never empties during popping). Append `INT_MAX` as a final temperature in daily temperatures to flush all remaining stack elements in the last iteration, eliminating the post-loop "remaining = 0" step.

**3. Strict vs. non-strict in counting problems:** When a problem counts subarrays with a specific minimum or maximum, use strict inequality on the _left_ boundary and non-strict on the _right_ (or vice versa). This canonical choice ensures each subarray is counted exactly once even with duplicate values. Getting this wrong produces 2× overcounting on flat arrays.

**4. Combine span with prefix sums:** If the problem asks "sum of spans" or "weighted sum of span × value", compute the span array with the stack and then take a prefix sum in a second $O(n)$ pass. Do not try to accumulate the weighted sum inside the stack loop — it increases bug surface.
