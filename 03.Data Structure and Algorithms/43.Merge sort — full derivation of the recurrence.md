## 1. Intuition First

### The Core Idea

Imagine you're a librarian handed two already-sorted piles of books and asked to merge them into one sorted pile. You don't re-sort either pile — you simply look at the top of each stack, take the smaller book, and repeat. This merge step costs exactly as many comparisons as books in the combined pile — linear time, every time, guaranteed.

Merge sort exploits this observation recursively: if you have an unsorted array of n elements, split it in half, sort each half (by recursively applying the same idea), then merge the two sorted halves. The genius is that you never pay more than O(n) work per level of recursion — and there are exactly log₂n levels.

### Why This Exists — The Complexity Gap

Insertion sort costs O(n²) in the worst case because every new element may have to travel past all previously sorted elements. The fundamental problem: a single comparison can only establish a local ordering. Merge sort escapes this by being **globally informed** at each merge step — every element's final position is settled through a clean linear sweep over already-sorted data.

The gap: O(n²) vs O(n log n) is not merely academic. At n = 10⁶:

- Insertion sort: ~10¹² operations → ≈ 16 minutes at 10⁹ ops/sec
- Merge sort: ~2 × 10⁷ operations → ≈ 0.02 seconds

This is the difference between "runs on a test case" and "runs in production."

### The "Aha" Moment

The recurrence **T(n) = 2T(n/2) + Θ(n)** captures the entire algorithm in one line. The `2T(n/2)` is the cost of recursively sorting two halves. The `Θ(n)` is the merge. Once you see that the merge is always linear — regardless of what the data looks like — you realise that merge sort has **no bad inputs**. Unlike [[44. Quicksort — Partition, Pivot Selection, Expected O(n log n)]], merge sort's worst case equals its best case: always O(n log n).

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**When it appears:** Merge sort itself appears directly when you need a guaranteed O(n log n) sort, but its recurrence structure appears in problems involving:

- Counting inversions in an array (classic divide-and-conquer problem)
- External sort problems where you can't load all data into memory
- Any problem whose editorial says "split and conquer"

**Pattern signal:** When you see "count the number of pairs (i, j) where i < j but A[i] > A[j]" — think merge sort with an augmented merge step. The merge step naturally processes cross-subarray pairs.

**The Master Theorem shortcut:** Most contestants apply the Master Theorem without deriving it. This note is about building the derivation machinery so you can handle non-standard recurrences like T(n) = 3T(n/3) + O(n log n) from scratch — which the Master Theorem handles but you need to understand _why_ it gives what it gives.

**Common trap:** Merge sort requires O(n) auxiliary space. In problems with tight memory constraints (e.g., 256 MB for n = 10⁷ integers), merge sort's hidden constant matters. Each recursive call doesn't allocate a new array in place — you need exactly one auxiliary array of size n.

### Machine Learning / AI

**Where the recurrence appears in ML systems:**

1. **Timsort in Python/Pandas:** Python's built-in `sorted()` and `list.sort()` use Timsort, which is a hybrid of merge sort and insertion sort. When you call `df.sort_values()` in pandas, you're running an evolved merge sort. Understanding the merge operation explains why Timsort detects "runs" and merges them — it's exploiting pre-existing sorted structure to skip the recursive splitting step.
    
2. **External sort for large-scale ML pipelines:** When your training dataset doesn't fit in RAM (a common situation in industry-scale ML), you sort by key using a k-way merge — the same merge step generalised to k sorted streams. Apache Spark's `sortBy()` operation is architecturally a distributed merge sort: each partition is sorted locally, then a merge-like reduce step combines them. See [[220. Data Pipeline Design — Streaming vs Batch, Shuffling, Prefetching]].
    
3. **Merge sort recurrence as a template for model complexity analysis:** When analysing recursive neural architectures (e.g., divide-and-conquer attention in Longformer-style models), the recurrence T(n) = 2T(n/2) + O(n) is the _same structural equation_ that describes how computation is distributed across recursive decomposition layers. Understanding how to solve this recurrence gives you intuition for why such models achieve O(n log n) attention complexity instead of O(n²).
    
4. **Fenwick tree and segment tree construction:** Building a [[156. Fenwick Tree (BIT) — Prefix Sum with Updates O(log n)]] or [[155. Segment Tree — Range Query and Point Update O(log n)]] uses a bottom-up merge-style construction that solves the same T(n) = 2T(n/2) + O(1) recurrence (giving O(n) build time), a direct sibling of the merge sort recurrence.

## 3. Algorithm / Pattern

### Step-by-Step Logic

1. **Base case:** If the array has 0 or 1 elements, it's already sorted. Return immediately.
2. **Divide:** Find the midpoint `mid = (lo + hi) / 2`. Split into left subarray `[lo, mid]` and right subarray `[mid+1, hi]`.
3. **Conquer:** Recursively sort the left half. Recursively sort the right half.
4. **Merge:** Use two pointers — one at the start of each sorted half. Repeatedly pick the smaller element and advance its pointer. Write results into a temporary buffer. Copy back.

### Decision Tree

```
See a sorting problem →
  Is worst-case O(n log n) required? → Use merge sort (not quicksort)
  Is stability required? → Use merge sort (not heapsort)
  Is memory constrained (O(1) space)? → Use heapsort or in-place quicksort
  Is data partially sorted? → Timsort exploits this; pure merge sort doesn't
  Need to count inversions while sorting? → Augment the merge step
```

### Complexity Derivation (the full derivation — not just the answer)

Let T(n) = number of comparisons to sort n elements.

**Setting up the recurrence:**

```
T(1) = 0                          (base case: nothing to compare)
T(n) = 2·T(n/2) + n - 1          (exact form)
     ≈ 2·T(n/2) + n               (asymptotic form used hereafter)
```

The `n - 1` in the exact form comes from: merging two sorted arrays of size n/2 requires at most n - 1 comparisons (in the worst case you interleave every element from both halves before one runs out).

**Method 1: Recursion Tree (the most intuitive)**

Unroll the recurrence level by level:

```
Level 0:  T(n)              → cost = n
Level 1:  2·T(n/2)          → cost = 2·(n/2) = n
Level 2:  4·T(n/4)          → cost = 4·(n/4) = n
Level 3:  8·T(n/8)          → cost = 8·(n/8) = n
...
Level k:  2^k · T(n/2^k)   → cost = 2^k · (n/2^k) = n
```

At each level, the total work is exactly n. How many levels are there? We stop when n/2^k = 1, i.e., when k = log₂n.

Total cost = n · log₂n = **O(n log n)** ✓

**Method 2: Substitution Method (rigorous proof)**

Guess T(n) = cn·log₂n for some constant c. Prove by induction.

_Base case:_ T(1) = 0 ≤ c·1·log₂1 = 0. ✓ (holds with equality)

_Inductive step:_ Assume T(n/2) ≤ c·(n/2)·log₂(n/2). Then:

```
T(n) = 2·T(n/2) + n
     ≤ 2·[c·(n/2)·log₂(n/2)] + n
     = c·n·log₂(n/2) + n
     = c·n·(log₂n - log₂2) + n
     = c·n·(log₂n - 1) + n
     = c·n·log₂n - cn + n
     = c·n·log₂n + n(1 - c)
     ≤ c·n·log₂n         (provided c ≥ 1)
```

Therefore T(n) = **O(n log n)** ✓

**Method 3: Master Theorem (fast, but requires understanding)**

The Master Theorem applies to recurrences of the form T(n) = a·T(n/b) + f(n).

For merge sort: a = 2, b = 2, f(n) = n.

Compare f(n) = n against n^(log_b a) = n^(log₂2) = n^1 = n.

Since f(n) = Θ(n^(log_b a)) — they are the same polynomial — we are in **Case 2**:

```
T(n) = Θ(n^(log_b a) · log n) = Θ(n · log n) = Θ(n log n)
```

**Why understanding the derivation matters beyond the answer:**  
The substitution method and recursion tree give you the machinery to handle variants the Master Theorem can't:

- T(n) = 2T(n/2) + n·log n → Case 2 with a log factor: T(n) = Θ(n log² n)
- T(n) = T(n/3) + T(2n/3) + n → Unbalanced split (quicksort worst case analog), requires Akra-Bazzi method

**Space complexity:**  
The auxiliary array for merging requires O(n) space at each level. However, because the recursive calls are sequential (not parallel), only one level's worth of merge buffers exists at a time. Total space: O(n) for the merge buffer + O(log n) for the call stack = **O(n)**.

### When to Use vs. When to Avoid

|Use merge sort when...|Avoid merge sort when...|
|---|---|
|Stability is required|O(1) extra space is required|
|Worst-case O(n log n) is non-negotiable|Data fits in cache and quicksort's constants win|
|Data is on disk (external sort)|n is small (insertion sort wins below ~32 elements)|
|You need to count inversions|You need in-place sorting|

## 4. Pseudocode

```
MERGE-SORT(A, lo, hi):
    // Base case: a subarray of size 0 or 1 is already sorted
    if lo >= hi:
        return

    // Divide: find midpoint without integer overflow
    mid = lo + (hi - lo) / 2

    // Conquer: sort both halves recursively
    MERGE-SORT(A, lo, mid)
    MERGE-SORT(A, mid + 1, hi)

    // Combine: merge the two sorted halves
    MERGE(A, lo, mid, hi)


MERGE(A, lo, mid, hi):
    // Copy both halves into a temporary buffer
    left  = A[lo .. mid]       // size: mid - lo + 1
    right = A[mid+1 .. hi]     // size: hi - mid

    i = 0  // pointer into left
    j = 0  // pointer into right
    k = lo // pointer into original array A

    // Two-pointer merge: always take the smaller element
    while i < len(left) AND j < len(right):
        if left[i] <= right[j]:   // <= ensures stability
            A[k] = left[i]
            i = i + 1
        else:
            A[k] = right[j]
            j = j + 1
        k = k + 1

    // Drain the remaining elements from whichever half is non-empty
    while i < len(left):
        A[k] = left[i]; i++; k++

    while j < len(right):
        A[k] = right[j]; j++; k++

    // No need to return; A is modified in-place via the buffer
```

**Edge cases handled:**

- `lo >= hi`: subarray of size 0 or 1 — returns immediately (no segfault on empty range)
- Odd-length arrays: `mid = lo + (hi - lo) / 2` floors the midpoint; left half gets the extra element, right half is one element shorter. Both are valid inputs to MERGE-SORT.
- Stability: `left[i] <= right[j]` (not `<`) ensures equal elements from the left half always appear before equal elements from the right half — preserving original relative order.

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <iostream>
#include <vector>
#include <algorithm>  // std::merge, for comparison only
#include <cassert>

/**
 * Merge Sort — Full implementation with recurrence derivation commentary
 *
 * Time:  O(n log n) — all cases (best, average, worst)
 * Space: O(n) auxiliary for merge buffer + O(log n) call stack
 * Stable: Yes — equal elements maintain their original relative order
 */

// Internal merge helper: merges A[lo..mid] and A[mid+1..hi] in-place
// using a temporary buffer. This is the Θ(n) "combine" step in the recurrence.
template<typename T>
void merge(std::vector<T>& A, int lo, int mid, int hi) {
    // Copy both halves into temporary storage
    // This is the O(n) space cost that makes the recurrence T(n) = 2T(n/2) + n
    std::vector<T> left(A.begin() + lo, A.begin() + mid + 1);
    std::vector<T> right(A.begin() + mid + 1, A.begin() + hi + 1);

    int i = 0, j = 0, k = lo;

    // Two-pointer merge: O(|left| + |right|) = O(n) comparisons per call
    while (i < (int)left.size() && j < (int)right.size()) {
        // '<=' preserves stability: left element wins ties
        if (left[i] <= right[j]) {
            A[k++] = left[i++];
        } else {
            A[k++] = right[j++];
        }
    }

    // Drain remaining elements — at most one of these loops runs
    while (i < (int)left.size())  A[k++] = left[i++];
    while (j < (int)right.size()) A[k++] = right[j++];
}

// Recursive merge sort: T(n) = 2T(n/2) + Θ(n) → T(n) = Θ(n log n)
template<typename T>
void mergeSort(std::vector<T>& A, int lo, int hi) {
    // Base case: subarray of size ≤ 1 is already sorted
    if (lo >= hi) return;

    // Integer-overflow-safe midpoint: avoids (lo + hi) overflow for large indices
    int mid = lo + (hi - lo) / 2;

    // Conquer: sort each half — this is the 2T(n/2) term
    mergeSort(A, lo, mid);
    mergeSort(A, mid + 1, hi);

    // Combine: merge the two sorted halves — this is the Θ(n) term
    merge(A, lo, mid, hi);
}

// Public interface
template<typename T>
void mergeSort(std::vector<T>& A) {
    if (A.empty()) return;
    mergeSort(A, 0, (int)A.size() - 1);
}

// Augmented version: count inversions while sorting
// An inversion is a pair (i, j) where i < j but A[i] > A[j]
// This exploits the merge step: every time we pick right[j] before left[i],
// all remaining left elements form inversions with right[j]
template<typename T>
long long mergeCount(std::vector<T>& A, int lo, int hi) {
    if (lo >= hi) return 0;

    int mid = lo + (hi - lo) / 2;
    long long count = 0;

    count += mergeCount(A, lo, mid);
    count += mergeCount(A, mid + 1, hi);

    // Count cross-inversions during merge
    std::vector<T> left(A.begin() + lo, A.begin() + mid + 1);
    std::vector<T> right(A.begin() + mid + 1, A.begin() + hi + 1);
    int i = 0, j = 0, k = lo;

    while (i < (int)left.size() && j < (int)right.size()) {
        if (left[i] <= right[j]) {
            A[k++] = left[i++];
        } else {
            // right[j] < left[i], and left[i..end] are all > right[j]
            // So right[j] forms an inversion with all remaining left elements
            count += (long long)(left.size() - i);
            A[k++] = right[j++];
        }
    }
    while (i < (int)left.size())  A[k++] = left[i++];
    while (j < (int)right.size()) A[k++] = right[j++];

    return count;
}

// --- Minimal test harness ---
int main() {
    // Basic sort test
    std::vector<int> A = {5, 2, 8, 1, 9, 3, 7, 4, 6};
    mergeSort(A);
    assert((A == std::vector<int>{1, 2, 3, 4, 5, 6, 7, 8, 9}));
    std::cout << "Sort: PASS\n";

    // Edge cases
    std::vector<int> empty_v = {};
    mergeSort(empty_v);
    assert(empty_v.empty());

    std::vector<int> single = {42};
    mergeSort(single);
    assert(single[0] == 42);

    // Inversion count: [2, 4, 1, 3, 5] has 3 inversions: (2,1),(4,1),(4,3)
    std::vector<int> B = {2, 4, 1, 3, 5};
    long long inv = mergeCount(B, 0, (int)B.size() - 1);
    assert(inv == 3);
    std::cout << "Inversion count: PASS (count=" << inv << ")\n";

    // Stability test: sort pairs by first element, ensure second element order preserved
    std::vector<std::pair<int,int>> pairs = {{1,2},{2,1},{1,3},{2,4}};
    mergeSort(pairs);
    // After stable sort by pair: (1,2),(1,3),(2,1),(2,4)
    assert(pairs[0].second == 2 && pairs[1].second == 3);  // (1,2) before (1,3)
    std::cout << "Stability: PASS\n";

    return 0;
}
```

### Python (Readable + Pythonic)

```python
"""
Merge Sort — Full derivation and implementation

Recurrence: T(n) = 2T(n/2) + n
Solution:   T(n) = O(n log n)  [via recursion tree or Master Theorem Case 2]

Key insight: the merge step is ALWAYS O(n) regardless of input structure.
This is why merge sort has no bad inputs — worst case = best case = O(n log n).
"""

from typing import TypeVar, List, Tuple
import sys

T = TypeVar('T')


def merge_sort(arr: List) -> List:
    """
    Top-level merge sort. Returns a new sorted list (not in-place).

    Time:  O(n log n) — all cases
    Space: O(n) — merge buffers + O(log n) call stack
    Stable: Yes

    Note: Python's built-in sorted() uses Timsort, which is a hybrid merge sort.
    This implementation is pedagogically pure — it shows the recurrence structure
    directly. For production, always prefer sorted() or list.sort().
    """
    if len(arr) <= 1:           # Base case: T(1) = 0
        return arr[:]

    mid = len(arr) // 2         # Divide: O(1)
    left  = merge_sort(arr[:mid])    # Conquer: T(n/2)
    right = merge_sort(arr[mid:])    # Conquer: T(n/2)
    return _merge(left, right)       # Combine: Θ(n)


def _merge(left: List, right: List) -> List:
    """
    Merge two sorted lists into one sorted list.
    This is the Θ(n) step that makes the whole recurrence T(n) = 2T(n/2) + Θ(n).

    The two-pointer technique: always advance the pointer of the list whose
    current element is smaller. Total comparisons: at most len(left) + len(right) - 1.
    """
    result = []
    i = j = 0

    while i < len(left) and j < len(right):
        if left[i] <= right[j]:   # <= ensures stability
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1

    # Extend with whichever half still has elements — no comparisons needed
    result.extend(left[i:])
    result.extend(right[j:])
    return result


def count_inversions(arr: List[int]) -> Tuple[List[int], int]:
    """
    Count inversions (pairs i < j where arr[i] > arr[j]) while sorting.

    This augments the merge step: when we pick right[j] over left[i],
    right[j] is smaller than all remaining left elements,
    so it forms (len(left) - i) new inversions.

    Time: O(n log n) — same recurrence as merge sort
    Returns: (sorted array, inversion count)
    """
    if len(arr) <= 1:
        return arr[:], 0

    mid = len(arr) // 2
    left_sorted,  left_inv  = count_inversions(arr[:mid])
    right_sorted, right_inv = count_inversions(arr[mid:])

    merged = []
    cross_inv = 0
    i = j = 0

    while i < len(left_sorted) and j < len(right_sorted):
        if left_sorted[i] <= right_sorted[j]:
            merged.append(left_sorted[i])
            i += 1
        else:
            # right[j] forms an inversion with left[i..end]
            cross_inv += len(left_sorted) - i
            merged.append(right_sorted[j])
            j += 1

    merged.extend(left_sorted[i:])
    merged.extend(right_sorted[j:])

    return merged, left_inv + right_inv + cross_inv


def merge_sort_inplace(arr: List, lo: int = 0, hi: int = None) -> None:
    """
    In-place merge sort: avoids creating new lists at every recursive call.
    Uses a single auxiliary buffer of size n, reused across merge operations.

    This matches the C++ implementation's memory model more closely.
    Time: O(n log n), Space: O(n) for aux buffer + O(log n) call stack.
    """
    if hi is None:
        hi = len(arr) - 1

    def _merge_inplace(aux: List, lo: int, mid: int, hi: int) -> None:
        # Copy to auxiliary buffer
        aux[lo:hi+1] = arr[lo:hi+1]
        i, j, k = lo, mid + 1, lo
        while i <= mid and j <= hi:
            if aux[i] <= aux[j]:
                arr[k] = aux[i]; i += 1
            else:
                arr[k] = aux[j]; j += 1
            k += 1
        while i <= mid:
            arr[k] = aux[i]; i += 1; k += 1
        # Remaining right elements are already in place — no need to copy

    def _sort(aux: List, lo: int, hi: int) -> None:
        if lo >= hi:
            return
        mid = lo + (hi - lo) // 2
        _sort(aux, lo, mid)
        _sort(aux, mid + 1, hi)
        _merge_inplace(aux, lo, mid, hi)

    aux = arr[:]  # Allocate once — this is the O(n) space
    _sort(aux, lo, hi)


# --- Recursion depth guard for Python ---
sys.setrecursionlimit(100_000)


if __name__ == "__main__":
    # Basic sort
    A = [5, 2, 8, 1, 9, 3, 7, 4, 6]
    sorted_A = merge_sort(A)
    assert sorted_A == sorted(A), f"Expected {sorted(A)}, got {sorted_A}"
    print(f"Sort: PASS → {sorted_A}")

    # Inversion count
    B = [2, 4, 1, 3, 5]
    _, inv = count_inversions(B)
    assert inv == 3, f"Expected 3 inversions, got {inv}"
    print(f"Inversion count: PASS → {inv} inversions")

    # Stability: tuples sorted by first element; second element order must be preserved
    pairs = [(1, 'b'), (2, 'a'), (1, 'a'), (2, 'b')]
    sorted_pairs = merge_sort(pairs)
    assert sorted_pairs == [(1, 'b'), (1, 'a'), (2, 'a'), (2, 'b')]
    print(f"Stability: PASS → {sorted_pairs}")

    # Edge cases
    assert merge_sort([]) == []
    assert merge_sort([42]) == [42]
    assert merge_sort([3, 1]) == [1, 3]
    print("Edge cases: PASS")

    # In-place version
    C = [5, 3, 1, 4, 2]
    merge_sort_inplace(C)
    assert C == [1, 2, 3, 4, 5]
    print(f"In-place: PASS → {C}")
```

### Diagram 2: The Merge Step in Detail

The `Θ(n)` term in the recurrence comes from this two-pointer merge. Notice: **every element is written exactly once**.

```
Merging [1, 2, 5, 8] and [3, 4, 7, 9]:
                                           Result
 left:  [ 1 | 2 | 5 | 8 ]
          ↑                               []
 right: [ 3 | 4 | 7 | 9 ]
          ↑

Step 1: 1 < 3 → take from left           [1]
Step 2: 2 < 3 → take from left           [1, 2]
Step 3: 5 > 3 → take from right          [1, 2, 3]
Step 4: 5 > 4 → take from right          [1, 2, 3, 4]
Step 5: 5 < 7 → take from left           [1, 2, 3, 4, 5]
Step 6: 8 > 7 → take from right          [1, 2, 3, 4, 5, 7]
Step 7: 8 < 9 → take from left           [1, 2, 3, 4, 5, 7, 8]
Step 8: left exhausted, drain right      [1, 2, 3, 4, 5, 7, 8, 9]

Total comparisons: 7 = n - 1 (worst case)
Each element written exactly once → cost = Θ(n) ✓
```

### Diagram 3: Recurrence Unrolling — Why the Math Works

This makes the substitution method concrete. Each row is one expansion.

```
T(n) = 2T(n/2)  +  n
                                         ← expand T(n/2) = 2T(n/4) + n/2
     = 2[2T(n/4) + n/2]  +  n
     = 4T(n/4)  +  n + n
                                         ← expand T(n/4) = 2T(n/8) + n/4
     = 4[2T(n/8) + n/4]  +  2n
     = 8T(n/8)  +  n + n + n
     ⋮
     = 2^k · T(n/2^k)  +  k·n

     Set k = log₂n so that n/2^k = 1:

     = n · T(1)  +  n·log₂n
     = n · 0    +  n log n
     = n log n ✓
```

## 7. Common Variations & Extensions

### 7.1 Bottom-Up (Iterative) Merge Sort

Instead of recursing top-down, iterate over subarray widths 1, 2, 4, 8, ..., n. Merge adjacent subarrays of the current width. This eliminates the call stack entirely — O(1) stack space — and is how Timsort works internally.

```python
def merge_sort_iterative(arr):
    n = len(arr)
    width = 1
    while width < n:
        for lo in range(0, n, 2 * width):
            mid = min(lo + width - 1, n - 1)
            hi  = min(lo + 2 * width - 1, n - 1)
            if mid < hi:
                arr[lo:hi+1] = _merge(arr[lo:mid+1], arr[mid+1:hi+1])
        width *= 2
```

Recurrence is unchanged: the same O(n) work happens at each "width doubling" — exactly log n doublings.

### 7.2 K-Way Merge

Merge k sorted arrays simultaneously using a **min-heap of size k**. Used in:

- Merging k sorted files in external sort (Spark, Hadoop MapReduce shuffle phase)
- [[153. Merge K Sorted Lists — Min-Heap of Size k]]

Each element is pushed and popped from the heap once: O(n log k) total. The recurrence generalises to T(n) = k·T(n/k) + n·log k.

### 7.3 Counting Inversions

Augment the merge step to count cross-inversions: when you pick `right[j]` over `left[i]`, all remaining elements in `left[i:]` form inversions with `right[j]`. Count = `len(left) - i`. This is the canonical O(n log n) inversion counting algorithm. See [[168. Longest Increasing Subsequence (LIS)]] for related patience sorting ideas.

### 7.4 Natural Merge Sort (Timsort precursor)

Instead of splitting at the midpoint, detect "runs" (already-sorted subarrays) and merge them. If the input is nearly sorted, the number of runs is small and the algorithm approaches O(n). Timsort additionally enforces a minimum run length (~32-64 elements) and uses insertion sort within runs — matching [[41. Insertion Sort — When O(n²) is the Right Answer]] perfectly to the regime where it wins.

## 9. CP Contest Application

### Typical Codeforces/AtCoder Problem Structure

**Direct merge sort usage** is rare in high-level CP — the standard library sort handles it. Where merge sort _recurrence intuition_ appears in contests:

**Problem type 1 — Inversion counting:**

> "Given array A, count pairs (i, j) where i < j and A[i] > A[j]." _Signal:_ O(n²) naive is TLE for n ≤ 10⁶. Think augmented merge sort or BIT.

**Problem type 2 — Divide and conquer optimisation:**

> "Find the maximum/minimum over all subarrays where the answer satisfies a split property." _Signal:_ If f(lo, hi) = f(lo, mid) + f(mid+1, hi) + cross(lo, mid, hi) and cross is cheap, write a merge-sort-style D&C. This gives O(n log n) vs O(n²) brute force.

**Problem type 3 — External / multi-way merge in graph problems:**

> DSU on trees (small-to-large merging) has the same recurrence. When merging a set of size s into a set of size S (S ≥ s), each element moves at most O(log n) times → O(n log n) total. See [[131. DSU on Trees (Small-to-Large Merging)]].

### Time Limits and Optimisation

At n = 10⁶: merge sort runs in ~0.5 seconds in C++ with constant ~20ns per operation. The hidden constants in merge sort are roughly 2–3× worse than quicksort due to cache-unfriendly memory access patterns (two separate buffers being read alternately). For tight time limits:

1. **Use iterative bottom-up** to eliminate function call overhead (~15% speedup)
2. **Switch to insertion sort below threshold 32** — the same optimisation Timsort uses
3. **Avoid `std::vector` temporaries** — pre-allocate a single global auxiliary buffer of size n

```cpp
// Pre-allocated buffer — avoids per-call heap allocation
int aux[1000005];

void merge(int* A, int lo, int mid, int hi) {
    for (int i = lo; i <= hi; i++) aux[i] = A[i];
    int i = lo, j = mid + 1, k = lo;
    while (i <= mid && j <= hi)
        A[k++] = (aux[i] <= aux[j]) ? aux[i++] : aux[j++];
    while (i <= mid) A[k++] = aux[i++];
    // Right half already in place
}
```

This single change — eliminating per-merge vector allocation — typically halves the constant factor.

## Summary

The recurrence T(n) = 2T(n/2) + Θ(n) is not just a formula — it is a geometric fact: the recursion tree has log n levels, each contributing exactly n units of work, yielding n log n total. Proving this three ways (recursion tree, substitution, Master Theorem) gives you the pattern-matching muscle to handle any divide-and-conquer recurrence you encounter.

Merge sort's O(n) merge step is the template for a family of algorithms that process cross-subproblem interactions in linear time — from inversion counting to k-way merge in distributed ML pipelines to the small-to-large merging trick in advanced tree algorithms. Every time you see a problem with "merge two sorted structures," you are touching the same Θ(n) combine step that lives at the heart of this recurrence.
