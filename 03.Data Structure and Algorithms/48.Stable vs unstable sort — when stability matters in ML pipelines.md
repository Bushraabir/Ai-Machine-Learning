## 1. Intuition First

### The Core Idea

Every sort algorithm answers: "given two elements that compare as _equal_, which one goes first in the output?" An **unstable sort** says: "I don't care — whichever is convenient for me." A **stable sort** says: "the one that appeared earlier in the input."

That single sentence is the entire definition. But its consequences are enormous.

Think of a spreadsheet of students sorted first by grade, then by name. You sort by name first (alphabetically), then sort by grade. If the second sort is stable, students with the same grade remain alphabetically ordered from the first pass — you get a two-level sort for free. If the second sort is unstable, the alphabetical ordering is destroyed. This chained-sort pattern — sort by secondary key, then stably sort by primary key — is how every multi-key sort can be decomposed into a sequence of single-key stable sorts. Radix sort ([[50.Radix sort — digit-by-digit, O(d(n+k))]]) is the canonical example of this.

### Why This Exists

The need arises whenever **sort keys are not unique identifiers**. If every element has a distinct key, stable and unstable sorts produce identical results — stability is vacuous. But in practice, keys collide constantly:

- Students with the same grade
- Transactions with the same timestamp
- Model predictions with the same probability bucket
- Features with the same importance score

In all these cases, the output of an unstable sort is **nondeterministic** — it depends on implementation details, input ordering, and even memory layout. This is catastrophic for reproducibility in ML pipelines, where you need the same preprocessing to produce the same training set every run.

### The "Aha" Moment

Stability is not a property of the _algorithm's logic_ — it's a property of how the algorithm handles _tie-breaking_. Merge sort is stable because when it merges two halves and finds equal elements, it always takes from the left half first (the element that appeared earlier). Quicksort's partition step moves elements past each other in ways that don't respect original order — it's inherently unstable. Heapsort is unstable because heapification destroys the original relative ordering immediately during `build_heap`.

The key insight: **making any sort stable is possible by augmenting the key with the original index**. Sort by `(key, original_index)` instead of just `key`. Equal keys now resolve by index — earlier elements win. Python's `sorted()` does exactly this internally. This costs O(n) extra space for the indices and O(log n) extra comparisons per element for the tiebreak — the price of stability.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**When stability matters in contests:**

Stability is rarely the _point_ of a CP problem — it's usually a **correctness prerequisite** that isn't stated explicitly. If you use `std::sort` (unstable) where the problem requires stable behaviour, your output may differ from the expected output on cases with ties.

Classic patterns where stability matters:

- **Multi-key sort via successive passes:** Radix sort correctness depends entirely on stability. If digit-sort passes are unstable, higher digits don't correctly override lower ones for equal prefixes.
- **Preserving insertion order for equal-priority items:** Scheduling problems where tasks with equal priority must be processed in submission order.
- **Reconstructing permutations:** Some problems require tracking which original index each element came from. A stable sort on a decorated `(value, index)` array makes index reconstruction trivial; an unstable sort on the same array may give the wrong index assignment for equal values.

**Pattern signal:** If the problem statement says "if multiple answers exist, output the lexicographically smallest" or "preserve the original order for ties" — you need a stable sort. In C++, use `std::stable_sort`. In Python, `sorted()` is always stable — no action needed.

**Common trap:** `std::sort` in C++ is **not guaranteed stable**. It uses introsort (quicksort + heapsort fallback), both of which are unstable. Using `std::sort` when the problem requires stability is a silent wrong-answer bug — not a compile error, not a crash.

### Machine Learning / AI

This is where stability stops being academic and becomes **production-critical**.

**1. Reproducibility in data preprocessing:**  
A preprocessing pipeline that loads data, sorts by timestamp, and assigns fold indices must produce identical fold assignments every run. If `pandas.DataFrame.sort_values()` defaulted to unstable sort, rows with identical timestamps would shuffle between runs, producing different train/validation splits and making experiments unreproducible. Pandas uses mergesort (stable) by default precisely for this reason. The `kind` parameter defaults to `'quicksort'` in name but actually dispatches to a stable introsort variant — this is a documented and deliberate naming quirk.

**2. `np.argsort` and feature ranking:**  
`sklearn.feature_selection.SelectKBest` ranks features by score and selects the top k. When two features have identical scores (common with discrete data), an unstable sort produces different feature subsets across runs — breaking experiment reproducibility. `np.argsort` defaults to `kind='quicksort'` (unstable). Passing `kind='stable'` ensures tied features are always broken by their original column index. This is not hypothetical: any dataset with binary or categorical features will have many tied importance scores.

**3. Gradient-based curriculum learning:**  
Training with hard-example mining sorts training examples by loss magnitude after each epoch, selecting the top-k hardest. If the sort is unstable, examples with nearly identical losses swap positions unpredictably across epochs, making the curriculum noisy. A stable sort ensures that among examples with equal loss, the one seen earlier in the dataset is prioritised — a weak but consistent signal that reduces variance in the curriculum.

**4. Timsort — Python and Java's production stable sort:**  
Python's `list.sort()` and `sorted()` use Timsort, a hybrid mergesort/insertion sort designed explicitly to be stable and to exploit natural runs in real-world data. Java's `Arrays.sort()` for objects uses Timsort for the same reason. NumPy's `np.sort(..., kind='stable')` also uses Timsort. Understanding that Timsort is not a theoretical curiosity but the default production sort in the two most widely used ML languages is foundational.

**5. `torch.sort` and determinism:**  
`torch.sort` is stable by default (since PyTorch 1.9). Before 1.9, it was unstable, causing nondeterministic behaviour in attention mechanisms that sort key-value pairs and in beam search implementations that sort by score. The PyTorch team added the `stable=True` parameter specifically because ML reproducibility requires it. If you're using an older checkpoint or codebase, this is a real source of subtle, hard-to-diagnose nondeterminism.

## 3. Algorithm / Pattern

### Stability Classification of Common Sorts

|Algorithm|Stable?|Reason|
|---|---|---|
|Insertion sort|✅ Yes|Only shifts elements right; equal elements never swap|
|Merge sort|✅ Yes|Merge step takes left element first on tie|
|Timsort|✅ Yes|Built on merge sort; designed explicitly stable|
|Bubble sort|✅ Yes|Only swaps adjacent elements when strictly less; ties → no swap|
|Counting sort|✅ Yes (if implemented correctly)|Must iterate right-to-left when placing; common to get wrong|
|Quicksort|❌ No|Partition moves elements across each other arbitrarily|
|Heapsort|❌ No|`build_heap` immediately destroys original order|
|Selection sort|❌ No|Swaps non-adjacent elements|
|Introsort (`std::sort`)|❌ No|Inherits quicksort and heapsort instability|

### The Stable-by-Augmentation Pattern

Any unstable sort becomes stable by augmenting the key:

```
Original key:    k(x)
Augmented key:   (k(x), original_index(x))
```

Equal `k(x)` values now resolve by index — earlier element wins — which is exactly the definition of stability. Cost: O(n) extra space for indices. Python does this internally for `sorted()`. This is also why Python's `sorted()` is **always** stable with zero performance cost for distinct keys — the index tiebreak is computed once and stored.

### When Stability is Vacuous (Optimisation Opportunity)

If all sort keys are distinct, stable and unstable sort produce identical results. Use the faster unstable sort:

- `std::sort` over `std::stable_sort` in C++ when keys are unique
- `np.sort(kind='quicksort')` over `kind='stable'` in NumPy when keys are unique
- `kind='mergesort'` adds O(n) space overhead — avoid when unnecessary

`std::stable_sort` costs O(n log² n) time (O(n log n) if extra memory available) vs `std::sort`'s O(n log n). The difference is a constant factor in practice but measurable at n > 10⁶.

### Decision Tree

```
Does the sort output need to be reproducible across runs?
  └─ Yes → Use stable sort. Period.

Are sort keys guaranteed unique?
  └─ Yes → Stable and unstable give identical results. Use unstable for speed.
  └─ No  → Do equal-key elements need to preserve original order?
              └─ Yes → Stable sort
              └─ No  → Either works; prefer unstable for speed

Are you doing multi-pass sort (sort by secondary, then primary)?
  └─ Yes → Each pass MUST be stable. Use stable sort.

C++ environment?
  └─ std::sort          = unstable (introsort)
  └─ std::stable_sort   = stable (adaptive merge sort)
  └─ std::ranges::sort  = unstable by default

Python environment?
  └─ sorted() / list.sort() = always stable (Timsort)
  └─ np.sort(kind='stable') = stable (Timsort)
  └─ np.sort(kind='quicksort') = unstable (pdqsort)
  └─ pd.sort_values()         = stable by default
```

### Complexity Comparison

|Sort|Time|Space|Stable|
|---|---|---|---|
|`std::sort`|O(n log n)|O(log n) stack|No|
|`std::stable_sort` (enough memory)|O(n log n)|O(n)|Yes|
|`std::stable_sort` (low memory)|O(n log² n)|O(1)|Yes|
|Python `sorted()` / Timsort|O(n log n)|O(n)|Yes|
|`np.sort(kind='stable')`|O(n log n)|O(n)|Yes|

## 4. Pseudocode

### Stable Merge Sort (the reference stable sort)

```
MERGE_SORT_STABLE(arr, left, right):
    if left >= right:
        return                  # Base case: single element, trivially sorted

    mid ← (left + right) / 2
    MERGE_SORT_STABLE(arr, left, mid)
    MERGE_SORT_STABLE(arr, mid + 1, right)
    MERGE_STABLE(arr, left, mid, right)

MERGE_STABLE(arr, left, mid, right):
    # Copy both halves into temporary arrays
    L ← arr[left  .. mid]       # left half
    R ← arr[mid+1 .. right]     # right half

    i ← 0,  j ← 0,  k ← left

    while i < len(L) AND j < len(R):
        # CRITICAL: use <= not < here would make this UNSTABLE
        # Take from L when L[i] <= R[j] — left (earlier) element wins on tie
        if L[i] <= R[j]:
            arr[k] ← L[i]
            i ← i + 1
        else:
            arr[k] ← R[j]
            j ← j + 1
        k ← k + 1

    # Drain remaining elements
    while i < len(L): arr[k++] ← L[i++]
    while j < len(R): arr[k++] ← R[j++]
```

**Why `<=` guarantees stability:** when `L[i] == R[j]`, we take from `L` (the earlier half). Elements in `L` came before elements in `R` in the original array. So equal elements always maintain their original left-to-right order. Changing `<=` to `<` would take from `R` on ties — correct output, but unstable.

### Stable Counting Sort (the subtle one)

```
COUNTING_SORT_STABLE(arr, k):
    # arr contains integers in [0, k-1]
    count ← array of zeros, length k

    # Phase 1: count occurrences
    for x in arr:
        count[x] ← count[x] + 1

    # Phase 2: prefix sum → starting position of each value
    for i from 1 to k-1:
        count[i] ← count[i] + count[i-1]

    # Phase 3: place elements — MUST iterate RIGHT TO LEFT for stability
    output ← array of length n
    for i from len(arr)-1 DOWN TO 0:    # ← right to left is the key
        x ← arr[i]
        count[x] ← count[x] - 1
        output[count[x]] ← arr[i]

    return output

# Why right-to-left? When two elements have the same value x,
# the one with larger original index i is placed first (into the
# highest available slot for x), and the one with smaller i is
# placed into the next slot. Result: smaller index → earlier in output.
# Left-to-right iteration would reverse this, making the sort unstable.
```

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <algorithm>
#include <iostream>
#include <string>
#include <vector>

struct Record {
    std::string name;
    int         score;
    int         original_index;  // for verification
};

// ─── Stable sort: preserves relative order of equal elements ──────────────────
void demo_stable_sort(std::vector<Record>& records) {
    // std::stable_sort: O(n log n) with O(n) buffer; O(n log² n) without
    std::stable_sort(records.begin(), records.end(),
        [](const Record& a, const Record& b) {
            return a.score > b.score;  // descending score; equal scores → original order
        });
}

// ─── Unstable sort: faster, but ties are implementation-defined ───────────────
void demo_unstable_sort(std::vector<Record>& records) {
    std::sort(records.begin(), records.end(),
        [](const Record& a, const Record& b) {
            return a.score > b.score;  // equal scores → order UNDEFINED
        });
}

// ─── Make any sort stable by augmenting with original index ───────────────────
void stable_sort_via_augmentation(std::vector<Record>& records) {
    // Augment: pair (score, original_index) — index breaks ties
    std::vector<std::pair<int, int>> keys;
    keys.reserve(records.size());
    for (int i = 0; i < (int)records.size(); ++i)
        keys.emplace_back(records[i].score, i);

    // Sort augmented keys: ties resolved by original_index ascending
    std::sort(keys.begin(), keys.end(),
        [](const auto& a, const auto& b) {
            return a.first != b.first ? a.first > b.first   // descending score
                                      : a.second < b.second; // ascending original index
        });

    // Rearrange records according to sorted order
    std::vector<Record> sorted_records;
    sorted_records.reserve(records.size());
    for (const auto& [score, idx] : keys)
        sorted_records.push_back(records[idx]);
    records = std::move(sorted_records);
}

// ─── Multi-pass sort: sort secondary first, then primary (must be stable) ─────
void multi_key_sort(std::vector<Record>& records) {
    // Goal: sort by score desc, then by name asc for equal scores.
    // Approach: sort by name asc first, then STABLY sort by score desc.
    // The stable second pass preserves name order within each score group.

    std::sort(records.begin(), records.end(),           // pass 1: name asc (unstable ok here)
        [](const Record& a, const Record& b) {
            return a.name < b.name;
        });

    std::stable_sort(records.begin(), records.end(),    // pass 2: score desc (MUST be stable)
        [](const Record& a, const Record& b) {
            return a.score > b.score;
        });
    // Equal scores now retain alphabetical order from pass 1 ✓
}

// ─── Demo ─────────────────────────────────────────────────────────────────────
int main() {
    std::vector<Record> records = {
        {"Charlie", 90, 0},
        {"Alice",   90, 1},
        {"Bob",     85, 2},
        {"Dave",    90, 3},
    };

    auto print = [](const std::vector<Record>& v) {
        for (const auto& r : v)
            std::cout << r.name << "(" << r.original_index << ") ";
        std::cout << "\n";
    };

    demo_stable_sort(records);
    print(records);
    // Charlie(0) Alice(1) Dave(3) Bob(2)  ← original order preserved within score=90

    // Reset
    records = {{"Charlie",90,0},{"Alice",90,1},{"Bob",85,2},{"Dave",90,3}};
    multi_key_sort(records);
    print(records);
    // Alice(1) Charlie(0) Dave(3) Bob(2)  ← score=90 group is alphabetically ordered

    return 0;
}
```

### Python (Readable + Pythonic)

```python
from dataclasses import dataclass
import numpy as np


@dataclass
class Record:
    name:           str
    score:          int
    original_index: int


# ─── Python sorted() is ALWAYS stable — no action required ───────────────────
def demo_python_stability():
    records = [
        Record("Charlie", 90, 0),
        Record("Alice",   90, 1),
        Record("Bob",     85, 2),
        Record("Dave",    90, 3),
    ]

    # Stable by default — equal scores preserve input order
    result = sorted(records, key=lambda r: -r.score)
    names = [r.name for r in result]
    assert names == ["Charlie", "Alice", "Dave", "Bob"], f"Got {names}"
    print("Python sorted() is stable ✓:", names)


# ─── Multi-pass sort — sort secondary key first, then primary stably ──────────
def multi_key_sort(records: list[Record]) -> list[Record]:
    """
    Goal: sort by score desc, tiebreak by name asc.

    Approach A (idiomatic): single-pass with tuple key
    Approach B (multi-pass): sort secondary, then stably sort primary
    Both produce identical results. A is preferred; B illustrates stability.
    """
    # Approach A — idiomatic, single pass
    result_a = sorted(records, key=lambda r: (-r.score, r.name))

    # Approach B — multi-pass (shows why stability is required)
    step1 = sorted(records, key=lambda r: r.name)        # secondary: name asc
    step2 = sorted(step1,   key=lambda r: -r.score)      # primary: score desc (stable)
    result_b = step2

    assert [r.name for r in result_a] == [r.name for r in result_b]
    return result_a


# ─── NumPy: unstable by default; stable when required ────────────────────────
def numpy_stability_demo():
    """
    np.argsort default kind='quicksort' is UNSTABLE.
    For reproducible feature ranking, use kind='stable'.
    """
    scores = np.array([0.9, 0.85, 0.9, 0.85, 0.9])
    # Feature indices: 0, 1, 2, 3, 4

    # Unstable argsort — tied scores may resolve in arbitrary order
    unstable_idx = np.argsort(scores)[::-1]
    print("Unstable:", unstable_idx)
    # Could be [0,2,4,1,3] or [4,2,0,3,1] or any permutation of tied groups

    # Stable argsort — tied scores resolve by original index (smaller index first)
    stable_idx = np.argsort(scores, kind='stable')[::-1]
    print("Stable:  ", stable_idx)
    # Always [0, 2, 4, 1, 3] — indices 0,2,4 have score=0.9; 1,3 have 0.85
    # Within each tied group, smaller original index comes first

    return stable_idx


# ─── Counting sort — stable only if right-to-left placement ──────────────────
def counting_sort_stable(arr: list[int], k: int) -> list[int]:
    """
    Stable counting sort for integers in [0, k-1].
    O(n + k) time, O(n + k) space.

    The right-to-left placement loop is what makes this stable.
    Replacing it with left-to-right would produce correct values
    but in reverse-stable (last-occurrence-wins) order.
    """
    count = [0] * k
    for x in arr:
        count[x] += 1

    # Prefix sum: count[i] = number of elements <= i
    for i in range(1, k):
        count[i] += count[i - 1]

    output = [0] * len(arr)
    for i in range(len(arr) - 1, -1, -1):   # RIGHT TO LEFT — stability key
        x = arr[i]
        count[x] -= 1
        output[count[x]] = arr[i]

    return output


# ─── Pandas: stable by default, but verify for older versions ─────────────────
def pandas_stability_demo():
    """
    pd.DataFrame.sort_values() uses mergesort (stable) by default.
    Explicit: df.sort_values('col', kind='mergesort')
    'quicksort' in pandas is actually introsort — stable in modern pandas.
    Always specify kind='stable' for production pipelines.
    """
    import pandas as pd
    df = pd.DataFrame({
        'name':  ['Charlie', 'Alice', 'Bob', 'Dave'],
        'score': [90,        90,      85,    90     ],
    })
    result = df.sort_values('score', ascending=False, kind='stable')
    print(result['name'].tolist())
    # ['Charlie', 'Alice', 'Dave', 'Bob'] — input order preserved within score=90


if __name__ == "__main__":
    demo_python_stability()
    numpy_stability_demo()
    pandas_stability_demo()

    arr = [3, 1, 4, 1, 5, 9, 2, 6, 5, 3]
    print(counting_sort_stable(arr, 10))  # [1, 1, 2, 3, 3, 4, 5, 5, 6, 9]
```

## 6. Visual Explanation

### Stability: What It Means Concretely

```
Input (name, score):
  [Charlie/90, Alice/90, Bob/85, Dave/90]
   index: 0     index: 1   index: 2   index: 3

Sort by score descending:

STABLE sort — equal elements retain original left-to-right order:
  [Charlie/90, Alice/90, Dave/90, Bob/85]
   idx:0        idx:1     idx:3    idx:2
   ↑ original order within score=90 group is 0→1→3 ✓

UNSTABLE sort — equal elements may appear in any order:
  [Dave/90, Charlie/90, Alice/90, Bob/85]   ← possible output A
  [Alice/90, Dave/90, Charlie/90, Bob/85]   ← possible output B
  [Charlie/90, Dave/90, Alice/90, Bob/85]   ← possible output C
  (implementation-defined; may differ between runs or compiler versions)
```

### Why Merge Step Guarantees Stability

```
Merging two sorted halves:
  Left  = [Alice/90, Charlie/90]    (earlier in original array)
  Right = [Dave/90]                 (later in original array)

Step 1: L[0]=Alice/90 vs R[0]=Dave/90
  Scores equal. Rule: take from LEFT (≤ condition).
  Output: [Alice/90]

Step 2: L[1]=Charlie/90 vs R[0]=Dave/90
  Scores equal. Take from LEFT.
  Output: [Alice/90, Charlie/90]

Step 3: Right exhausted, drain Left — but Left is empty.
  Drain Right.
  Output: [Alice/90, Charlie/90, Dave/90]

Alice and Charlie (from Left) precede Dave (from Right).
Within each half, recursion already sorted stably.
Result: original order preserved for equal elements. ✓

If we had taken from RIGHT on ties:
  Step 1: Dave/90 taken → [Dave/90]
  Step 2: Alice/90 taken → [Dave/90, Alice/90]
  ...
  Dave (idx 3) before Alice (idx 1) — WRONG, unstable.
```

### Multi-Pass Radix Sort — Stability as Correctness Prerequisite

```
Sort 3-digit numbers: [329, 457, 657, 839, 436, 720, 355]
by last digit, then middle digit, then first digit.

Pass 1 (last digit): stable sort by units digit
  720, 355, 436, 457, 657, 329, 839
   ^0   ^5   ^6   ^7   ^7   ^9   ^9
  Note: 457 before 657 (both end in 7; 457 came first in input ✓)
        329 before 839 (both end in 9; 329 came first in input ✓)

Pass 2 (middle digit): STABLY sort by tens digit
  720, 329, 436, 839, 355, 457, 657
   ^2   ^2   ^3   ^3   ^5   ^5   ^5
  Note: 720 before 329 (both have 2 in tens; 720 came first after Pass 1 ✓)
        355 before 457 before 657 (all have 5 in tens; order from Pass 1 preserved ✓)

Pass 3 (first digit): STABLY sort by hundreds digit
  329, 355, 436, 457, 657, 720, 839  ← fully sorted ✓

If Pass 2 were UNSTABLE: 329 and 720 might swap → Pass 3 would produce wrong order.
Stability is not a nicety here — it is what makes radix sort correct.
```

## 7. Common Variations & Extensions

### 7.1 Timsort — Why Python Chose It

Timsort (Tim Peters, 2002) is a hybrid of merge sort and insertion sort. It identifies natural _runs_ (already-sorted subsequences) in the input and merges them. On real-world data (which has significant partial order), Timsort achieves O(n) on nearly-sorted input — much better than merge sort's unconditional O(n log n). It is stable by construction (merges take left on ties) and uses O(n) space. Python's `list.sort()`, Java's `Arrays.sort()` for objects, and NumPy's `kind='stable'` all use Timsort. For any ML preprocessing pipeline running in Python or JVM, Timsort is the _actual_ sort happening — understanding it means you can predict when it will be fast (nearly-sorted feature tables) and when it won't (random noise).

### 7.2 Pdqsort — C++'s Modern Unstable Sort

Pattern-defeating quicksort (pdqsort, Orson Peters, 2021) is the sort behind `std::sort` in many modern C++ standard libraries (libstdc++, libc++) and Rust's `slice::sort_unstable`. It combines median-of-three quicksort, insertion sort for small subarrays, and heapsort fallback — achieving O(n log n) worst case, O(n) on nearly-sorted data, and excellent cache behaviour. It is **unstable** by design — preserving original order would require tracking indices, which conflicts with in-place cache-friendly operation. `std::stable_sort` sacrifices in-place property to gain stability.

### 7.3 `np.lexsort` — Stable Multi-Key Sort for Arrays

`np.lexsort((key2, key1))` sorts by `key1` primarily, `key2` as tiebreaker — stably, at C speed:

```python
names  = np.array(['Charlie', 'Alice', 'Bob', 'Dave'])
scores = np.array([90, 90, 85, 90])
# Sort by score desc, tiebreak by name asc
idx = np.lexsort((names, -scores))
# idx = [1, 0, 3, 2] → Alice, Charlie, Dave, Bob
```

For large ML datasets (millions of rows), `np.lexsort` runs at C speed while guaranteeing stability. This is the NumPy equivalent of Python's `key=lambda r: (-r.score, r.name)` but 100× faster on large arrays. See [[47.Custom comparators — Python key= and C++ lambda comparators]].

### 7.4 Stability in `torch.sort` and Determinism

`torch.sort(tensor, stable=True)` (default since PyTorch 1.9) is required for deterministic model behaviour. Attention mechanisms that sort key-value pairs by score must be stable to produce the same output on the same input across forward passes — critical for debugging and for saved/loaded model consistency. If you're using `torch.argsort` for token selection in a custom decoder, pass `stable=True` explicitly to be safe with older PyTorch versions.

## 9. CP Contest Application

### When Stability Decides Correctness

**Codeforces pattern — "sort and output, ties by input order":**  
These problems explicitly require stability: "if two elements have equal priority, output the one that appeared earlier in the input first." In C++, `std::stable_sort` is the direct answer. Many contestants use `std::sort` with a tiebreaker on original index — equivalent, but verbose:

```cpp
// Explicit tiebreaker — makes unstable sort behave stably
std::vector<std::pair<int,int>> v(n);      // (value, original_index)
for (int i = 0; i < n; ++i) v[i] = {a[i], i};
std::sort(v.begin(), v.end());             // ties resolved by original index ✓
```

**AtCoder pattern — radix sort correctness:**  
String problems that require radix sort (suffix array construction, string ranking) depend on stable passes. If you implement your own radix sort in a contest, every single digit-sort pass must be stable. Using counting sort with right-to-left placement (as in the pseudocode above) is the standard approach.

### Time Limit Considerations

`std::stable_sort` is 2–3× slower than `std::sort` in practice at n = 10⁶ due to O(n) buffer allocation and worse cache access. If TL is 1 second and n = 10⁶, check whether stability is actually required or whether a tiebreaker in the comparator suffices (and thus `std::sort` can be used). For n ≤ 10⁵, the difference is negligible — always use `std::stable_sort` when in doubt about correctness.

### The Augmented Key Trick in Contest Code

The most contest-efficient pattern when stability is needed but `std::stable_sort` is too slow:

```cpp
// O(n log n) with std::sort, achieves stability via index tiebreaker
std::vector<int> idx(n);
std::iota(idx.begin(), idx.end(), 0);     // idx = [0, 1, 2, ..., n-1]
std::sort(idx.begin(), idx.end(),
    [&](int i, int j) {
        if (a[i] != a[j]) return a[i] < a[j];   // primary: value
        return i < j;                             // tiebreak: original index
    });
// idx is now a sorted permutation of original indices — stable ✓
```

This is faster than `std::stable_sort` (introsort vs merge sort), uses O(n) space for the index array, and is guaranteed to produce a stable ordering because the tiebreak is a total order (indices are unique).
