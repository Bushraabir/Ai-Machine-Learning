## 1. Intuition First

### The Core Idea

Imagine a country where every citizen votes, and one political party holds more than half the total votes. Now strip away the election machinery — no ballot boxes, no counts — and run this thought experiment instead: pair up every voter from Party A with one voter from Party B, and eliminate both. Keep doing this until you can't make more pairs.

What's left at the end? The majority party. Because they had strictly more than half the votes, they have members who survive all the cancellations.

Boyer-Moore encodes exactly this idea. You walk through the array maintaining two variables: a `candidate` and a `count`. When you see an element that matches the candidate, you increment the count — a vote in favour. When you see something different, you decrement the count — a cancellation. If count ever hits zero, you discard the old candidate and adopt whoever you're looking at now.

At the end of one linear scan, `candidate` holds the majority element. There's no hash map, no extra array, no sorting. Just two variables and one pass.

### Why This Exists — The Complexity Gap

The naive approach maintains a frequency map (see [[21.HashMap frequency counting — arbitrary keys]]) and scans the map for any entry exceeding `n/2`. That's O(n) time but also O(n) space — you might store up to n distinct keys.

Boyer-Moore achieves O(n) time with **O(1) space**. This is not a minor constant-factor improvement. It's a categorical difference that becomes critical in two contexts:

1. **Streaming / online algorithms**: You're receiving elements one at a time from a stream you cannot rewind. You can't store them all. Boyer-Moore processes each element in O(1) and requires no storage proportional to input size.
2. **Read-only memory constraints**: Embedded systems, FPGA implementations, kernel-level code — contexts where heap allocation is expensive or forbidden.

### The "Aha" Moment

The single insight that makes everything click: **majority elements cannot be fully cancelled out.** A majority element by definition appears more than ⌊n/2⌋ times. Even if every non-majority element strategically paired up against a majority-element occurrence, the majority element would still have leftover survivors. The vote-cancellation scheme is not arbitrary — it's a proof by the pigeonhole principle in algorithmic clothing (see [[192.Pigeonhole principle — and its use in hashing collision arguments]]).

But here's the critical nuance Boyer-Moore beginners always miss: the algorithm does **not** guarantee that `candidate` is a majority element. It guarantees that **if a majority element exists, it will be `candidate`**. The existence check is a separate verification pass. Forget this and you'll have a bug that's almost impossible to catch without adversarial test cases.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

Boyer-Moore appears in contests whenever you see one of these signals:

- "Find the element that appears more than n/2 times" — this is the direct problem.
- "Strict memory limit (O(1) space) with an O(n) time requirement" — sorting is ruled out, HashMap is ruled out.
- "Stream of integers, answer online" — you can't store the stream.
- "Majority element guaranteed to exist" — problems that guarantee existence skip the verification pass, simplifying the solution slightly.

**The canonical trap:** The problem guarantees a majority element exists, you return `candidate`, and you're done. But on the next problem, existence is **not** guaranteed — you still return `candidate` without verifying, and you get WA on a case like `[1, 2, 3]` where `candidate` ends up as `3` but `3` is not a majority element. Always check whether the problem guarantees existence. If it doesn't, always do a second pass.

**Common extension to T2:** "Find all elements appearing more than n/k times" (e.g., LeetCode 229). The generalisation maintains at most k-1 candidates simultaneously, each with a count, and the logic becomes: when all counts are nonzero and the new element matches none, decrement all counts. This is sometimes called the **Misra-Gries algorithm**.

### Machine Learning / AI

**Ensemble voting (Hard voting classifiers):** In `sklearn.ensemble.VotingClassifier` with `voting='hard'`, the final prediction is the class that receives the most votes from base classifiers. Boyer-Moore isn't used internally here (classifier count is small, O(k) space is fine), but the conceptual model is identical. The "majority element" is the winning class.

**Federated Learning — Coordinate-wise majority voting:** In Byzantine-robust federated learning, where some clients may be adversarial, one common aggregation strategy is to take a coordinate-wise median or majority of gradient updates. The intuition that "a majority of honest clients cannot be outvoted by a minority of adversaries" is the Boyer-Moore invariant stated in gradient space. Papers in this line include Blanchard et al. (2017) _Machine Learning with Adversaries: Byzantine Tolerant Gradient Descent_.

**Data deduplication pipelines (see [[36.HashMap for O(1) deduplication — ML pipeline application]]):** When preprocessing training corpora, you often need to identify near-dominant tokens or patterns in streaming fashion. Boyer-Moore's streaming property — process-and-forget — maps directly to single-pass corpus scanning without buffering.

**Quantised model inference:** In model compression (see [[107.Quantisation and model compression — ML connection to bit ops]]), after quantising weights to 2-bit or 4-bit representations, mode-finding (finding the most frequent quantised value per filter) can be done in O(1) space per filter using Boyer-Moore. This appears in some FPGA deployment pipelines where SRAM is precious.

Understanding Boyer-Moore makes you better at these ML systems not because you'll implement it verbatim, but because you'll recognise when "I need a majority" problems can be solved without a frequency map — and that instinct carries over to every resource-constrained ML context.

## 3. Algorithm / Pattern

### Step-by-Step Logic

**Phase 1 — Candidate Finding (Single Pass)**

1. Initialise `candidate = arr[0]`, `count = 1`.
2. For each element `x` from index 1 to n-1:
    - If `x == candidate`: `count += 1` (reinforce the candidate).
    - Else if `count == 0`: `candidate = x`, `count = 1` (no survivor, adopt new candidate).
    - Else: `count -= 1` (cancel one occurrence of candidate against x).
3. After the loop, `candidate` is the **answer if a majority element exists**.

**Phase 2 — Verification (Single Pass, only if existence is not guaranteed)**

4. Count actual occurrences of `candidate` in the array.
5. If `count > n // 2`, return `candidate`. Otherwise, no majority element exists.

### Decision Tree

```
Does the problem guarantee a majority element exists?
├── YES → Run Phase 1, return candidate. Done.
└── NO  → Run Phase 1, then Phase 2 to verify.

Can the input be a stream (single pass only)?
├── YES → Boyer-Moore is the correct tool. O(1) space.
└── NO  → HashMap works too (simpler code), but wastes O(n) space.

Is the threshold n/2 or n/k for k > 2?
├── n/2  → Boyer-Moore with 1 candidate.
└── n/k  → Misra-Gries with k-1 candidates.
```

### Complexity Analysis

**Time:** O(n) — two linear scans in the worst case (Phase 1 + Phase 2), each touching every element exactly once.

**Space:** O(1) — only `candidate` and `count` are maintained, regardless of n. No auxiliary data structure.

**Why not O(n log n)?** Sorting would give us the majority element at position n/2 (the median), but sorting is Ω(n log n) by comparison lower bounds (see [[42.Merge sort — divide and conquer, stable, O(n log n)]]). Boyer-Moore beats this lower bound because it doesn't sort — it exploits problem-specific structure (majority threshold) that generic sorting cannot use.

### When to Use vs. When to Avoid

**Use Boyer-Moore when:**

- O(1) space is required.
- You need a streaming, online solution.
- The majority threshold is exactly n/2 (or you're prepared to implement Misra-Gries for n/k).

**Avoid Boyer-Moore when:**

- You need the second-most-frequent element — the algorithm gives you no information about other elements.
- The threshold is not majority (e.g., "find elements appearing more than n/3 times but not more than n/2" — Misra-Gries handles this, not Boyer-Moore directly).
- Code clarity is the only constraint and space isn't tight — a HashMap is easier to reason about and extend.

## 4. Pseudocode

```
FUNCTION find_majority_element(arr):
    // Phase 1: Candidate selection via vote cancellation
    candidate ← arr[0]
    count ← 1

    FOR i FROM 1 TO len(arr) - 1:
        x ← arr[i]
        IF x == candidate:
            count ← count + 1        // x reinforces the current candidate
        ELSE IF count == 0:
            candidate ← x            // previous candidate fully cancelled; adopt x
            count ← 1
        ELSE:
            count ← count - 1        // x cancels one instance of candidate

    // Phase 2: Verification (skip if existence is guaranteed by problem statement)
    occurrences ← 0
    FOR each element x IN arr:
        IF x == candidate:
            occurrences ← occurrences + 1

    IF occurrences > len(arr) / 2:
        RETURN candidate
    ELSE:
        RETURN -1  // No majority element exists

END FUNCTION
```

**Why the order of conditions matters:** The `count == 0` check must come before the `else` decrement. If you check `count == 0` last, you'd decrement to -1 and corrupt the invariant. The candidate is only replaced when count is already zero — meaning the current candidate has been fully cancelled by previous mismatches.

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <iostream>
#include <vector>
#include <optional>
#include <cassert>

// Boyer-Moore Voting Algorithm
// Time: O(n) | Space: O(1)
// Returns the majority element if it exists (appears > n/2 times), else nullopt.
std::optional<int> find_majority_element(const std::vector<int>& arr) {
    if (arr.empty()) return std::nullopt;

    // Phase 1: Find the candidate
    int candidate = arr[0];
    int count = 1;

    for (std::size_t i = 1; i < arr.size(); ++i) {
        if (arr[i] == candidate) {
            ++count;
        } else if (count == 0) {
            candidate = arr[i];
            count = 1;
        } else {
            --count;
        }
    }

    // Phase 2: Verify the candidate is actually a majority element
    // (Remove this pass if the problem guarantees a majority element exists)
    int occurrences = 0;
    for (int x : arr) {
        if (x == candidate) ++occurrences;
    }

    if (occurrences > static_cast<int>(arr.size()) / 2) {
        return candidate;
    }
    return std::nullopt;
}

// Misra-Gries generalisation: elements appearing more than n/k times
// Returns at most k-1 candidates (unverified); caller must verify counts.
std::vector<int> find_top_k_candidates(const std::vector<int>& arr, int k) {
    // Use a map to track up to k-1 candidates with their counts
    std::unordered_map<int, int> counts;

    for (int x : arr) {
        if (counts.count(x)) {
            ++counts[x];
        } else if (static_cast<int>(counts.size()) < k - 1) {
            counts[x] = 1;
        } else {
            // Decrement all counts by 1; remove zero-count entries
            for (auto it = counts.begin(); it != counts.end(); ) {
                if (--it->second == 0) it = counts.erase(it);
                else ++it;
            }
        }
    }

    std::vector<int> candidates;
    candidates.reserve(counts.size());
    for (auto& [val, _] : counts) candidates.push_back(val);
    return candidates;
}

int main() {
    // Basic test cases
    assert(find_majority_element({3, 2, 3}) == 3);
    assert(find_majority_element({2, 2, 1, 1, 1, 2, 2}) == 2);
    assert(find_majority_element({1}) == 1);
    assert(find_majority_element({1, 2}) == std::nullopt);  // No majority (each appears once)
    assert(find_majority_element({1, 2, 3}) == std::nullopt);

    // Edge: all same element
    assert(find_majority_element({5, 5, 5, 5}) == 5);

    // Misra-Gries: elements appearing more than n/3 times (k=3)
    std::vector<int> candidates = find_top_k_candidates({1, 2, 1, 3, 1, 4, 1}, 3);
    // Candidate 1 should be in the result (appears 4/7 > 1/3 times)
    assert(std::find(candidates.begin(), candidates.end(), 1) != candidates.end());

    std::cout << "All tests passed.\n";
    return 0;
}
```

### Python (Readable + Pythonic)

```python
from typing import Optional


def find_majority_element(arr: list[int]) -> Optional[int]:
    """
    Boyer-Moore Voting Algorithm.

    Finds the element appearing strictly more than n/2 times.
    Returns None if no such element exists.

    Time:  O(n) — two linear scans
    Space: O(1) — only candidate and count variables

    Example:
        >>> find_majority_element([3, 2, 3])
        3
        >>> find_majority_element([1, 2, 3]) is None
        True
    """
    if not arr:
        return None

    # Phase 1: Vote cancellation — find the candidate
    candidate = arr[0]
    count = 1

    for x in arr[1:]:
        if x == candidate:
            count += 1
        elif count == 0:
            # Current candidate was fully cancelled; adopt this element
            candidate = x
            count = 1
        else:
            count -= 1

    # Phase 2: Verify (omit if problem guarantees a majority element exists)
    # A majority element appears more than n//2 times by definition
    if arr.count(candidate) > len(arr) // 2:
        return candidate

    return None


def find_majority_element_naive(arr: list[int]) -> Optional[int]:
    """
    Naive approach using a frequency map.
    Time: O(n) | Space: O(n)
    Shown for comparison — Boyer-Moore trades this O(n) space for O(1).
    """
    from collections import Counter
    counts = Counter(arr)
    threshold = len(arr) // 2
    for val, freq in counts.items():
        if freq > threshold:
            return val
    return None


def misra_gries(arr: list[int], k: int) -> list[int]:
    """
    Generalisation of Boyer-Moore for elements appearing more than n/k times.
    Returns at most k-1 unverified candidates. Caller must verify counts.

    Time:  O(n * k) worst case (due to inner decrement loop), O(n) amortised
    Space: O(k)

    Example: k=3 finds elements appearing more than n/3 times.
        >>> misra_gries([1, 2, 1, 3, 1, 4, 1], 3)  # 1 appears 4/7 > 1/3
        [1]  # (plus possibly other candidates that fail verification)
    """
    counts: dict[int, int] = {}

    for x in arr:
        if x in counts:
            counts[x] += 1
        elif len(counts) < k - 1:
            counts[x] = 1
        else:
            # Decrement all counts; remove any that reach zero
            counts = {val: cnt - 1 for val, cnt in counts.items() if cnt > 1}

    # Verify which candidates actually exceed n/k
    threshold = len(arr) // k
    return [val for val in counts if arr.count(val) > threshold]


# ── Tests ──────────────────────────────────────────────────────────────────────

if __name__ == "__main__":
    # Boyer-Moore correctness
    assert find_majority_element([3, 2, 3]) == 3
    assert find_majority_element([2, 2, 1, 1, 1, 2, 2]) == 2
    assert find_majority_element([1]) == 1
    assert find_majority_element([1, 2]) is None      # 1 and 2 each appear once
    assert find_majority_element([1, 2, 3]) is None   # adversarial: candidate=3, but not majority
    assert find_majority_element([5, 5, 5, 5]) == 5

    # Verify naive matches Boyer-Moore on all cases above
    for test in [[3, 2, 3], [2, 2, 1, 1, 1, 2, 2], [1], [1, 2], [1, 2, 3], [5, 5, 5, 5]]:
        assert find_majority_element(test) == find_majority_element_naive(test)

    # Misra-Gries (k=3)
    result = misra_gries([1, 2, 1, 3, 1, 4, 1], k=3)
    assert 1 in result  # 1 appears 4 times out of 7 > 7/3

    print("All tests passed.")
```

## 6. Visual Explanation

### The Vote Cancellation Trace

Walk through `arr = [2, 2, 1, 1, 1, 2, 2]` step by step:

```
Index:     0    1    2    3    4    5    6
Element:   2    2    1    1    1    2    2

Step 0: candidate=2, count=1   (initialise)
Step 1: x=2, matches → count=2
Step 2: x=1, no match → count=1
Step 3: x=1, no match → count=0
Step 4: x=1, count==0 → NEW candidate=1, count=1
Step 5: x=2, no match → count=0
Step 6: x=2, count==0 → NEW candidate=2, count=1

Final candidate: 2
Verification: 2 appears 4 times > 7/2 = 3.5 ✓  → return 2
```

### The Adversarial Case — Why Verification is Mandatory

Walk through `arr = [1, 2, 3]`:

```
Index:     0    1    2
Element:   1    2    3

Step 0: candidate=1, count=1
Step 1: x=2, no match → count=0
Step 2: x=3, count==0 → NEW candidate=3, count=1

Final candidate: 3
Verification: 3 appears 1 time, NOT > 3/2 = 1.5  → return None
```

If you returned `3` without verifying, that's a wrong answer. `3` was adopted purely because it was last, not because it dominated.

### Intuitive Picture — The Bucket Cancellation Model

```
Input: [A, A, B, C, A, B, A, A]   (A appears 5/8 times — majority)

Think of it as: every non-A element can "cancel" one A.
Non-A elements: B, C, B  →  3 cancellations available
A elements:     5
Net survivors:  5 - 3 = 2 A's remain

Even in the worst case where all B's and C's pair against A's,
A has 2 survivors. Boyer-Moore's candidate will be A.

Visually (pairs crossed out):
  A A B C A B A A
  ×   × ×   ×          ← non-A elements cancel A's
        A   A          ← A survivors

Candidate will be A at the end. ✓
```

## 7. Common Variations & Extensions

### Variation 1: Majority Element II — Elements Appearing > n/3 Times (Misra-Gries, k=3)

The problem changes the threshold to n/3. By the pigeonhole principle, at most two such elements can exist. Maintain two candidates with counts. The decrement step decrements both counts simultaneously when neither matches. This is LeetCode 229 and is covered by the Misra-Gries framework shown in the C++ and Python implementations above.

See also: [[21.HashMap frequency counting — arbitrary keys]] for the O(n) space alternative.

### Variation 2: Streaming Majority with Rolling Windows

In time-series data, you might want "the majority element in the last k elements." Boyer-Moore doesn't extend cleanly to sliding windows because removing the oldest element can require re-running the algorithm from scratch. The correct tool here is a sliding window with a frequency map (see [[13.Sliding window with frequency map — character problems]]) or a monotonic deque variant. Boyer-Moore is a **global** streaming algorithm, not a windowed one.

### Variation 3: Weighted Majority Voting

Each element has a weight. An element is a "majority" if its total weight exceeds half the sum of all weights. Extend by replacing `count += 1` and `count -= 1` with `count += weight[i]` and `count -= weight[i]`. The rest of the algorithm is identical. This appears in weighted ensemble methods in ML.

### Variation 4: Bit-Position Majority (ML quantisation use case)

For a sequence of binary vectors, the "majority element" at each bit position is the bit value appearing in more than half the vectors. Apply Boyer-Moore independently at each bit position. This is equivalent to the coordinate-wise sign of the sum, but computable in O(1) space per coordinate — relevant in gradient sign aggregation for Byzantine-robust federated learning.

## 9. CP Contest Application

### Typical Contest Problem Structure

**Codeforces pattern:** "Given an array of n integers (n ≤ 10^6), determine whether there exists an element appearing strictly more than n/2 times. If yes, output it; otherwise output -1."

The constraint n ≤ 10^6 with a 256 MB memory limit still allows a HashMap, but 64 MB limits (which appear in some Codeforces Div. 3 problems) do not. Boyer-Moore is the intended solution when memory is tight.

**AtCoder pattern:** Often appears embedded inside a harder problem — e.g., after partitioning an array by some criterion, check if the majority of each partition satisfies a condition. Here Boyer-Moore's O(1) space lets you check each partition without extra allocation.

### Time Limit Considerations

Boyer-Moore has a smaller constant factor than HashMap: no hashing, no bucket traversal, no memory allocation. At n = 10^7, the wall-clock difference between HashMap and Boyer-Moore in C++ is typically 50-150 ms — enough to matter at a 500 ms time limit.

### Optimization Tricks

**Early termination:** If at any point `count > (n - i) / 2` where i is the current index (i.e., even if every remaining element cancels the candidate, it would still survive), you can return `candidate` immediately without finishing Phase 1 or running Phase 2.

```cpp
// Inside the Phase 1 loop, after updating count:
int remaining = static_cast<int>(arr.size()) - static_cast<int>(i) - 1;
if (count > remaining) return candidate; // Cannot be overtaken
```

This is a constant-factor speedup on average but doesn't change the worst-case O(n) bound.

**Branchless variant (micro-optimisation, rarely needed):**

```cpp
// Branchless update using the fact that (x == candidate) is 0 or 1
count += (arr[i] == candidate) ? 1 : -1;
if (count < 0) { candidate = arr[i]; count = 1; }
```

This reduces branch mispredictions on adversarial inputs. Only relevant in time-critical competitive programming with extremely tight limits.
