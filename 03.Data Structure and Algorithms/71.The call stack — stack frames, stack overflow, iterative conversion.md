## 1. Intuition First

### The Core Idea

Every time your program calls a function, the operating system allocates a small block of memory called a **stack frame** — a record containing the function's local variables, its parameters, and a return address (where execution resumes when the function finishes). These frames are placed on a region of memory called the **call stack**, which grows with each call and shrinks as functions return.

The call stack is not heap memory. It is a fixed-size contiguous region allocated to your process at startup — typically 1–8 MB depending on OS and configuration. It operates as a literal stack data structure: last-in, first-out. The most recently called function sits at the top; when it returns, its frame is popped, and execution jumps back to the caller whose frame is now on top.

Think of it as a stack of sticky notes on a desk. Each note records what you were doing when you got interrupted. When you get a phone call while cooking, you write "pasta, 3 minutes remaining, medium heat" on a note, handle the call, then pick up the note and resume. Recursion writes a new note for every level of depth. A stack overflow is the moment you run out of desk space — you have more pending notes than physical room.

### Why This Exists

The call stack exists because functions need **local state** — variables and parameters that belong to one invocation, isolated from all others. Without per-invocation storage, a recursive function like DFS would have every call clobbering the same variables. The stack makes each activation independent.

The problem: the stack is small by design. Heap memory can grow to gigabytes; the stack cannot. This asymmetry is intentional — heap allocation is managed (garbage collected or explicitly freed), while stack allocation is automatic and O(1) precisely _because_ it never fragments or requires management. That O(1) guarantee breaks if the stack could grow arbitrarily.

The consequence for recursion: every level of recursion depth consumes one frame. A recursion of depth n consumes O(n) stack space. For n = 10,000 in Python (default limit: 1,000) or n = 10^6 in C++ (stack ~8 MB, each frame ~100–200 bytes), you hit the ceiling.

### The "Aha" Moment

A recursive algorithm and an iterative algorithm using an explicit stack are **computationally identical**. The only difference is _where_ the stack lives:

> **Recursive:** stack lives in the operating system's call stack (implicit, fixed-size, automatic) **Iterative with explicit stack:** stack lives on the heap (explicit, unbounded, manual)

Converting recursive DFS to iterative DFS is not a different algorithm — it is the same algorithm with the stack moved from a hidden OS resource to a Python list or C++ `std::stack`. The transformation is always mechanical. Once you understand this, iterative conversion becomes a routine operation, not a creative challenge.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**When it appears:** Every recursive solution that could face input size n > 10,000 in Python, or n > ~100,000 in C++ on a contest judge with default stack. Tree traversals, DFS on large graphs, recursive DP — all of these can crash with a runtime error (RE) at depth limits.

**The Python recursion limit is 1,000 by default.** This is not a soft guideline — it is an enforced hard ceiling via `sys.setrecursionlimit`. A binary tree with 1,000 nodes has depth at most 1,000 (in the degenerate case); a balanced tree of 10^6 nodes has depth ~20. The limit bites hardest on:

- Linked-list-style problems (depth = length = n)
- Degenerate trees (e.g., a BST built from a sorted array)
- Recursive DFS on a path graph (depth = n)
- Recursive DP where `f(n)` depends on `f(n-1)` in a long chain

**What actually happens at overflow:**

- Python: `RecursionError: maximum recursion depth exceeded` — clean, catchable
- C++: undefined behaviour — typically a segmentation fault or silent memory corruption
- Java: `StackOverflowError` — catchable but almost never the right response

**Pattern signals that demand iterative conversion:**

- Graph/tree with n up to 10^5–10^6
- Recursive DP with a chain dependency (`f(n)` → `f(n-1)` → ... → `f(0)`)
- Problem statement says "n ≤ 10^5" and your solution is recursive DFS

**The `sys.setrecursionlimit` trap:** Increasing the limit to 10^6 does not give you unlimited recursion — it just moves the crash point. Each frame still consumes memory. At 10^6 frames × ~200 bytes/frame, you're allocating ~200 MB of stack, which will segfault on most systems before the Python limit triggers. The correct answer is iterative conversion.

### Machine Learning / AI

**Deep computation graphs and recursive traversal.** PyTorch's `Module.apply(fn)` traverses the model's submodule tree recursively (see [[70.Memoisation — converting naive recursion to top-down DP]]). For standard architectures this is shallow (depth < 100), but custom recursive architectures (TreeRNNs, recursive autoencoders, fractal networks) can reach depths proportional to input structure. PyTorch's implementation uses Python recursion — a 500-layer recursive architecture over a deep parse tree could approach Python's limit.

**Recursive data structure processing in ML pipelines.** JSON feature trees, nested configuration dictionaries, and hierarchically structured datasets are common in production ML systems. Recursive traversal is the natural solution — but production code processing documents with deep nesting (legal contracts, XML schemas, ASTs) should use iterative traversal to avoid crashes on adversarial or unusual inputs.

**Abstract Syntax Tree (AST) traversal in ML compilers.** TVM, XLA (the compiler backend behind JAX and TensorFlow), and Triton all represent computation as ASTs or IRs (Intermediate Representations) that are traversed for optimisation passes. These compilers use iterative tree traversal internally — a recursive traversal of a large neural network's computation graph would overflow. The `ast` module in Python's standard library (used for code analysis, symbolic differentiation libraries like SymPy) also uses iterative traversal for production robustness.

**Iterative DFS in graph-based ML.** Graph algorithms used in recommendation systems (e.g., Pinterest's PinSage, Uber's DeepETA) traverse graphs with millions of nodes. DFS over such graphs must be iterative — the depth of a social graph component can reach hundreds of thousands of hops.

**The explicit stack as a data structure for ML state.** Beam search in sequence generation (language models, machine translation) maintains a priority queue of partial sequences — conceptually a bounded explicit stack of "pending states to explore." Understanding how explicit stacks simulate recursion is a prerequisite for understanding beam search's pruned tree traversal.

## 3. Algorithm / Pattern

### Anatomy of a Stack Frame

A stack frame for a function call contains:

```
┌─────────────────────────────┐
│ Return address              │  where to jump when this function returns
│ Saved registers             │  caller's register state to restore
│ Function parameters         │  values passed in
│ Local variables             │  variables declared inside the function
│ (Sometimes) frame pointer   │  pointer to caller's frame
└─────────────────────────────┘
```

Frame size varies: a function with 3 int locals uses ~50–100 bytes in C++; a Python frame is heavier (~1–2 KB) due to Python's dynamic object model. This is why Python hits its limit faster than C++.

### The General Iterative Conversion Pattern

Every recursive DFS-style function (process node, recurse on children) converts to an explicit stack loop by the following mechanical steps:

```
Step 1: Replace the function call with "push to explicit stack"
Step 2: Replace the return with "continue the loop"
Step 3: The base case becomes "if stack is empty, exit loop"
Step 4: Any state that lived in local variables between the recursive
        call and the return must be pushed onto the stack explicitly
```

Step 4 is the only non-trivial part. For **pre-order** traversal (process before recursing), the state push is trivial — just push the node. For **post-order** traversal (process after all children), you must track whether a node's children have been processed, which requires storing that bookkeeping state explicitly on the stack.

### When Iterative Conversion Is Straightforward vs Hard

|Recursion type|Conversion difficulty|Reason|
|---|---|---|
|Tail recursion|Trivial → becomes a `while` loop|No state needed between call and return — [[69.Tail recursion and why Python does not optimise it]]|
|Pre-order traversal|Easy — push children in reverse order|Process before recursing; no state needed between calls|
|In-order traversal|Medium — requires tracking "left done" state|Must return to parent after left subtree|
|Post-order traversal|Medium-hard — requires two-pass or visited flag|Must process after both children return|
|General DFS with complex state|Hard — all local variables become explicit frame objects|Full simulation of the call stack|

### Stack Overflow: When It Happens

```
Stack size limit: L bytes
Frame size: F bytes
Maximum safe recursion depth: ⌊L / F⌋

Python (CPython):
  Enforced limit: 1,000 frames (sys.getrecursionlimit())
  Actual stack memory: ~8–80 MB depending on frame complexity

C++ (typical contest judge):
  Stack size: 1–8 MB
  Frame size: ~50–500 bytes depending on local variables
  Maximum depth: ~2,000 – 160,000 frames

Java:
  Default thread stack: 512 KB – 1 MB
  Maximum depth: ~5,000 – 10,000 frames
```

## 4. Pseudocode

```
# Recursive DFS — the starting point
FUNCTION dfs_recursive(node):
    IF node is null: RETURN          # base case

    process(node)                    # pre-order: process before children

    FOR each child of node:
        dfs_recursive(child)         # recursive call


# Iterative DFS — mechanical conversion
FUNCTION dfs_iterative(root):
    IF root is null: RETURN

    stack ← [root]                   # explicit stack replaces call stack

    WHILE stack is not empty:
        node ← stack.pop()           # LIFO: replaces function return

        process(node)                # same processing logic

        FOR each child of node in REVERSE order:
            stack.push(child)        # push instead of recurse
                                     # reverse order preserves left-to-right processing


# Post-order iterative — requires explicit state tracking
FUNCTION postorder_iterative(root):
    IF root is null: RETURN

    stack ← [(root, visited=False)]  # stack stores (node, state) pairs

    WHILE stack is not empty:
        node, visited ← stack.peek()  # look without popping

        IF visited:
            stack.pop()
            process(node)             # post-order: process after children
        ELSE:
            mark top as visited=True
            FOR each child of node in REVERSE order:
                stack.push((child, visited=False))


# General pattern for converting recursion with state between calls
FUNCTION general_iterative(root):
    # Each "frame" object holds what local variables would hold
    # in the corresponding recursive invocation
    stack ← [Frame(node=root, stage=0, local_vars...)]

    WHILE stack is not empty:
        frame ← stack.top()

        IF frame.stage == 0:         # first entry: before first recursive call
            ... do pre-call work ...
            frame.stage ← 1
            stack.push(Frame(frame.first_child))

        ELIF frame.stage == 1:       # returned from first child
            ... do inter-call work ...
            frame.stage ← 2
            stack.push(Frame(frame.second_child))

        ELIF frame.stage == 2:       # returned from second child
            ... do post-call work ...
            stack.pop()              # this frame is done
```

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <iostream>
#include <stack>
#include <vector>
#include <cassert>
#include <functional>

// ─────────────────────────────────────────────────────────────────────────────
// Binary tree node
// ─────────────────────────────────────────────────────────────────────────────
struct TreeNode {
    int val;
    TreeNode* left;
    TreeNode* right;
    TreeNode(int v, TreeNode* l = nullptr, TreeNode* r = nullptr)
        : val(v), left(l), right(r) {}
};

// ─────────────────────────────────────────────────────────────────────────────
// Example 1: Inorder traversal — recursive vs iterative
// Inorder is the canonical "medium difficulty" conversion because you must
// return to the parent node AFTER the left subtree but BEFORE the right.
// The recursive call stack holds this "pending right subtree" work implicitly.
// The iterative version must hold it explicitly.
// ─────────────────────────────────────────────────────────────────────────────

// Recursive: O(n) time, O(h) stack space where h = tree height
// Crashes for h > ~100,000 (C++) or h > ~997 (Python equivalent)
std::vector<int> inorder_recursive(TreeNode* root) {
    std::vector<int> result;
    std::function<void(TreeNode*)> dfs = [&](TreeNode* node) {
        if (!node) return;
        dfs(node->left);         // recurse left — OS stack holds "process node + right" work
        result.push_back(node->val);
        dfs(node->right);
    };
    dfs(root);
    return result;
}

// Iterative: O(n) time, O(h) explicit stack space — safe for any depth
// Key insight: the while loop simulates "go as far left as possible,
// then process, then move to right subtree"
std::vector<int> inorder_iterative(TreeNode* root) {
    std::vector<int> result;
    std::stack<TreeNode*> stk;
    TreeNode* curr = root;

    while (curr || !stk.empty()) {
        // Phase 1: push all left children — going as deep left as possible
        while (curr) {
            stk.push(curr);      // "remember to come back here after left subtree"
            curr = curr->left;
        }
        // Phase 2: pop and process — left subtree exhausted
        curr = stk.top(); stk.pop();
        result.push_back(curr->val);
        // Phase 3: move to right subtree
        curr = curr->right;
    }
    return result;
}

// ─────────────────────────────────────────────────────────────────────────────
// Example 2: Postorder traversal — the hardest standard conversion
// Must process node AFTER both children return.
// Two-pass trick: collect reverse postorder (root, right, left) using a
// modified preorder stack, then reverse the result.
// ─────────────────────────────────────────────────────────────────────────────

std::vector<int> postorder_recursive(TreeNode* root) {
    std::vector<int> result;
    std::function<void(TreeNode*)> dfs = [&](TreeNode* node) {
        if (!node) return;
        dfs(node->left);
        dfs(node->right);
        result.push_back(node->val);  // process AFTER children
    };
    dfs(root);
    return result;
}

std::vector<int> postorder_iterative(TreeNode* root) {
    if (!root) return {};
    std::vector<int> result;
    std::stack<TreeNode*> stk;
    stk.push(root);

    // This collects root → right → left (reverse of left → right → root)
    while (!stk.empty()) {
        TreeNode* node = stk.top(); stk.pop();
        result.push_back(node->val);
        // Push left first so right is processed first (LIFO)
        if (node->left)  stk.push(node->left);
        if (node->right) stk.push(node->right);
    }
    // Reverse to get left → right → root (true postorder)
    std::reverse(result.begin(), result.end());
    return result;
}

// ─────────────────────────────────────────────────────────────────────────────
// Example 3: DFS on a graph — iterative with visited set
// Critical for large graphs where recursive DFS would stack overflow
// ─────────────────────────────────────────────────────────────────────────────
std::vector<int> dfs_graph_iterative(
    int start, const std::vector<std::vector<int>>& adj) {

    int n = adj.size();
    std::vector<bool> visited(n, false);
    std::vector<int> order;
    std::stack<int> stk;

    stk.push(start);
    visited[start] = true;

    while (!stk.empty()) {
        int node = stk.top(); stk.pop();
        order.push_back(node);

        // Push neighbours in reverse to maintain consistent traversal order
        for (int i = adj[node].size() - 1; i >= 0; --i) {
            int nb = adj[node][i];
            if (!visited[nb]) {
                visited[nb] = true;   // mark before pushing to avoid duplicates
                stk.push(nb);
            }
        }
    }
    return order;
}

// ─────────────────────────────────────────────────────────────────────────────
// Demo
// ─────────────────────────────────────────────────────────────────────────────
int main() {
    //        4
    //       / \
    //      2   6
    //     / \ / \
    //    1  3 5  7
    TreeNode* root = new TreeNode(4,
        new TreeNode(2, new TreeNode(1), new TreeNode(3)),
        new TreeNode(6, new TreeNode(5), new TreeNode(7)));

    auto rec_in  = inorder_recursive(root);
    auto iter_in = inorder_iterative(root);
    assert(rec_in == iter_in);
    assert(rec_in == std::vector<int>({1,2,3,4,5,6,7}));

    auto rec_post  = postorder_recursive(root);
    auto iter_post = postorder_iterative(root);
    assert(rec_post == iter_post);
    assert(rec_post == std::vector<int>({1,3,2,5,7,6,4}));

    // Graph DFS
    // 0 - 1 - 3
    //  \  |
    //   2 |
    //    \|
    //     (1 connects 0,2,3)
    std::vector<std::vector<int>> adj = {
        {1, 2},     // 0
        {0, 2, 3},  // 1
        {0, 1},     // 2
        {1}         // 3
    };
    auto order = dfs_graph_iterative(0, adj);
    assert(order[0] == 0);   // starts at 0
    assert(order.size() == 4); // visits all nodes

    std::cout << "All tests passed.\n";
    return 0;
}
```

### Python (Readable + Pythonic)

```python
import sys
from collections import deque
from typing import Optional

# ─────────────────────────────────────────────────────────────────────────────
# Binary tree node
# ─────────────────────────────────────────────────────────────────────────────
class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val = val
        self.left = left
        self.right = right

# ─────────────────────────────────────────────────────────────────────────────
# Example 1: Inorder — recursive vs iterative
# ─────────────────────────────────────────────────────────────────────────────

def inorder_recursive(root: Optional[TreeNode]) -> list[int]:
    """O(n) time, O(h) call stack. Crashes for h > ~997 in Python."""
    if not root:
        return []
    return inorder_recursive(root.left) + [root.val] + inorder_recursive(root.right)


def inorder_iterative(root: Optional[TreeNode]) -> list[int]:
    """
    O(n) time, O(h) explicit stack. Safe for any depth.

    The stack holds the "pending right subtree" work that the OS call stack
    would hold in the recursive version. Each node on the stack means:
    "I've processed your left subtree; now process you, then your right."

    >>> inorder_iterative(build_tree([4,2,6,1,3,5,7]))
    [1, 2, 3, 4, 5, 6, 7]
    """
    result, stack = [], []
    curr = root

    while curr or stack:
        # Descend left as far as possible — pushing "pending" nodes
        while curr:
            stack.append(curr)
            curr = curr.left
        # Pop: left subtree exhausted — process this node
        curr = stack.pop()
        result.append(curr.val)
        # Move to right subtree — next iteration will descend left from here
        curr = curr.right

    return result


# ─────────────────────────────────────────────────────────────────────────────
# Example 2: Postorder — two-pass reverse trick
# ─────────────────────────────────────────────────────────────────────────────

def postorder_iterative(root: Optional[TreeNode]) -> list[int]:
    """
    Postorder (left, right, root) via reverse of modified preorder.

    Observation: if you do preorder visiting right before left,
    you get root → right → left. Reversing that gives left → right → root.
    This is a cleaner alternative to the visited-flag approach.

    Time:  O(n)
    Space: O(n) for result + O(h) stack
    """
    if not root:
        return []

    stack, result = [root], []
    while stack:
        node = stack.pop()
        result.append(node.val)
        if node.left:  stack.append(node.left)   # left pushed first
        if node.right: stack.append(node.right)  # right processed first (LIFO)

    return result[::-1]   # reverse: root,right,left → left,right,root


# ─────────────────────────────────────────────────────────────────────────────
# Example 3: General recursive-to-iterative with explicit frame state
# This is the full simulation pattern — handles ANY recursive function
# State machine: each "stage" corresponds to a point between recursive calls
# ─────────────────────────────────────────────────────────────────────────────

def flatten_tree_recursive(root: Optional[TreeNode]) -> list[int]:
    """
    Returns all values in pre+in+post combined — a contrived example
    that does work BEFORE and AFTER recursive calls, forcing explicit state.
    """
    if not root:
        return []
    result = [root.val]                           # pre-order work
    result += flatten_tree_recursive(root.left)
    result += [root.val * 10]                     # inter-call work (between left and right)
    result += flatten_tree_recursive(root.right)
    result += [root.val * 100]                    # post-order work
    return result


def flatten_tree_iterative(root: Optional[TreeNode]) -> list[int]:
    """
    Iterative equivalent using explicit frame objects.

    Each frame is a dict capturing:
      - node: which node this frame corresponds to
      - stage: which point in the execution we're at
        0 = just entered (pre-order work done, recurse left next)
        1 = returned from left (inter-call work done, recurse right next)
        2 = returned from right (post-order work done, pop frame)

    This pattern generalises to ANY recursive function — replace the
    work blocks with your actual algorithm's logic.

    Time:  O(n)  — same as recursive
    Space: O(h)  — explicit stack, not call stack
    """
    if not root:
        return []

    result = []
    # Each frame: (node, stage)
    stack = [(root, 0)]

    while stack:
        node, stage = stack[-1]   # peek, don't pop yet

        if stage == 0:
            # Pre-order work: process before any recursive call
            result.append(node.val)
            stack[-1] = (node, 1)   # advance stage

            # "Recurse" left: push left child as a new frame
            if node.left:
                stack.append((node.left, 0))

        elif stage == 1:
            # Inter-call work: returned from left, before recursing right
            result.append(node.val * 10)
            stack[-1] = (node, 2)

            # "Recurse" right: push right child as a new frame
            if node.right:
                stack.append((node.right, 0))

        else:  # stage == 2
            # Post-order work: returned from right
            result.append(node.val * 100)
            stack.pop()   # this frame is complete

    return result


# ─────────────────────────────────────────────────────────────────────────────
# Example 4: Recursive DP to iterative — eliminating call stack risk
# fib(n) via memoised recursion has call stack depth O(n).
# Bottom-up iterative eliminates it entirely.
# ─────────────────────────────────────────────────────────────────────────────

def fib_recursive_memo(n: int) -> int:
    """
    O(n) time via memoisation, but O(n) CALL STACK depth.
    For n > 997 in Python: RecursionError.
    See [[70.Memoisation — converting naive recursion to top-down DP]]
    """
    from functools import lru_cache

    @lru_cache(maxsize=None)
    def dp(k: int) -> int:
        if k <= 1: return k
        return dp(k - 1) + dp(k - 2)

    return dp(n)


def fib_iterative(n: int) -> int:
    """
    O(n) time, O(1) space, zero call stack usage.
    Safe for any n.

    This is what tail recursion + TCO would produce automatically
    in a TCO-capable language (see [[69.Tail recursion...]]).
    In Python, we perform the conversion manually.
    """
    if n <= 1:
        return n
    a, b = 0, 1
    for _ in range(2, n + 1):
        a, b = b, a + b
    return b


# ─────────────────────────────────────────────────────────────────────────────
# Helper: build a tree from level-order list (None = missing node)
# ─────────────────────────────────────────────────────────────────────────────
def build_tree(vals: list) -> Optional[TreeNode]:
    if not vals or vals[0] is None:
        return None
    root = TreeNode(vals[0])
    queue = deque([root])
    i = 1
    while queue and i < len(vals):
        node = queue.popleft()
        if i < len(vals) and vals[i] is not None:
            node.left = TreeNode(vals[i])
            queue.append(node.left)
        i += 1
        if i < len(vals) and vals[i] is not None:
            node.right = TreeNode(vals[i])
            queue.append(node.right)
        i += 1
    return root


# ─────────────────────────────────────────────────────────────────────────────
# Tests
# ─────────────────────────────────────────────────────────────────────────────
if __name__ == "__main__":
    #      4
    #     / \
    #    2   6
    #   / \ / \
    #  1  3 5  7
    root = build_tree([4, 2, 6, 1, 3, 5, 7])

    # Inorder
    assert inorder_recursive(root) == [1, 2, 3, 4, 5, 6, 7]
    assert inorder_iterative(root) == [1, 2, 3, 4, 5, 6, 7]
    assert inorder_iterative(None) == []
    assert inorder_iterative(build_tree([1])) == [1]   # single node

    # Postorder
    rec_post  = [1, 3, 2, 5, 7, 6, 4]
    assert postorder_iterative(root) == rec_post
    assert postorder_iterative(None) == []

    # Explicit frame simulation — recursive and iterative must match
    assert flatten_tree_recursive(root) == flatten_tree_iterative(root)
    assert flatten_tree_iterative(None) == []
    assert flatten_tree_iterative(build_tree([1])) == [1, 10, 100]

    # Fibonacci — iterative safe for large n
    assert fib_iterative(0)  == 0
    assert fib_iterative(1)  == 1
    assert fib_iterative(10) == 55
    assert fib_iterative(50) == 12586269025
    # This would RecursionError with fib_recursive_memo(10_000):
    assert fib_iterative(10_000) > 0   # just verify it runs

    print("All tests passed.")
    print(f"Python recursion limit: {sys.getrecursionlimit()}")
```

```
      → inorder(3)               [inorder(4), inorder(2), inorder(3)]
          ...
      ← returns [3]              [inorder(4), inorder(2)]
  ← returns [1,2,3]             [inorder(4)]
  emit 4
  → inorder(6)  ...
  ← returns [5,6,7]             [inorder(4)]
← returns [1,2,3,4,5,6,7]      []

Maximum stack depth = tree height h = 3 (for this tree)
For a degenerate tree (sorted array → BST): depth = n → O(n) frames
```

### Explicit Frame State Machine: The General Pattern

```
Recursive function with work at stages A, B, C:

def f(node):
    do_A(node)           ← stage 0 work
    f(node.left)         ← "recurse": push (left, stage=0)
    do_B(node)           ← stage 1 work
    f(node.right)        ← "recurse": push (right, stage=0)
    do_C(node)           ← stage 2 work (post-order)

Iterative state machine:

stack: [(node, stage=0)]
          │
    ┌─────▼──────┐
    │  stage=0   │──→ do_A(node), push (left, 0), advance to stage=1
    └─────┬──────┘
          │ (left child done, back to this frame)
    ┌─────▼──────┐
    │  stage=1   │──→ do_B(node), push (right, 0), advance to stage=2
    └─────┬──────┘
          │ (right child done, back to this frame)
    ┌─────▼──────┐
    │  stage=2   │──→ do_C(node), pop frame (done)
    └────────────┘

This state machine precisely simulates the OS call stack.
Every recursive function — no matter how complex — can be
converted this way. Complexity is unchanged; only the stack location moves.
```

## 7. Common Variations & Extensions

**Iterative DFS vs BFS.** The only difference between iterative DFS and BFS is the data structure used: a stack (LIFO) gives DFS; a queue (FIFO) gives BFS. The rest of the loop body is identical. See [[113.Breadth-First Search (BFS) — level-order, shortest path in unweighted graph]] for the queue-based variant. Understanding both as "explicit data structure traversal" unifies them conceptually.

**Iterative DFS on graphs vs trees.** Trees have no cycles — you never revisit a node. Graphs require a `visited` set to avoid infinite loops. In the iterative graph DFS, mark nodes as visited _before_ pushing to the stack (not when popping), to prevent the same node being pushed multiple times from different neighbours. This is a subtle but important distinction from tree DFS. See [[112.Depth-First Search (DFS) — recursive and iterative]].

**Morris traversal — O(1) space inorder without any stack.** For binary tree inorder traversal specifically, Morris traversal uses the tree's null right pointers as temporary links to thread the tree, achieving O(1) space with no explicit stack and no OS call stack. It is the most space-efficient approach but modifies the tree temporarily. Worth knowing as an interview answer to "can you do inorder in O(1) space?"

**Recursive DP → iterative bottom-up.** Converting memoised top-down DP to bottom-up tabulation eliminates the call stack entirely — not just the overflow risk, but also the function call overhead per subproblem. The conversion rule: fill the table in the reverse topological order of the dependency graph (usually increasing index). This is covered in [[162.Bottom-up DP — tabulation with iteration]]. For large n in Python, this is always preferable to memoised recursion.

## 9. CP Contest Application

**The practical contest checklist for any recursive solution in Python:**

```
n ≤ 1,000     → recursive is fine, within default limit
n ≤ 10,000    → add sys.setrecursionlimit(20_000); monitor
n ≤ 100,000   → convert to iterative; do not rely on setrecursionlimit
n ≤ 10^6      → iterative only; also consider O(1)-space approaches
```

**C++ contest stack expansion trick:** On Codeforces, some contestants add this pragma to increase stack size on Windows judges, but it is not portable and not reliable across all judges:

```cpp
// Unreliable — prefer iterative solutions for deep recursion
int main() {
    // ... your solution
}
// For genuinely deep recursion in C++: use iterative DFS
```

**The explicit stack DFS template** is worth memorising for contests because it applies identically to: connected components, cycle detection, topological sort, tree diameter, and any other DFS-based algorithm. The template is:

```python
def solve(graph, start):
    visited = set()
    stack = [start]
    while stack:
        node = stack.pop()
        if node in visited:
            continue
        visited.add(node)
        # process node here
        for neighbour in graph[node]:
            if neighbour not in visited:
                stack.append(neighbour)
```

This 10-line template replaces every recursive DFS in Python contest solutions and never overflows regardless of graph size.
