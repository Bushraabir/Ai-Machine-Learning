## 1. Intuition First

### The Core Idea

A recursive function is a promise: _"I can solve the big problem if someone solves the smaller one."_ The base case is where that promise cashes out — it's the smallest instance that can be answered directly, without delegation.

Think of a recursive function as a chain of managers at a company. Every manager passes the hard part of the job down to a subordinate — _except_ the intern at the bottom, who actually does the work and hands back a result. The base case is the intern. Without one, every manager just passes the work down forever. The chain never terminates. You get a stack overflow.

A better physical analogy: a **mirror facing a mirror**. With no base case, recursion produces infinite reflections. The base case is placing your hand between them — it absorbs the reflection and terminates the sequence.

### Why This Exists

Recursion derives its power from **self-similarity**: a problem of size n reduces to one of size n−1 (or n/2, or some smaller substructure). But self-similarity without a stopping condition is not an algorithm — it's an infinite loop expressed as function calls.

The naive approach of not defining base cases explicitly produces one of two failures:

- **Stack overflow** at runtime (each call consumes a stack frame; without termination, you exhaust memory)
- **Wrong answer** — a subtly wrong base case that returns an incorrect value, poisoning every result that builds on it

The insidious cost is that the second failure is worse than the first. A crash is obvious. A silently incorrect base case propagates corruption upward through every call that uses its return value. In DP, a single wrong cell poisons all cells that depend on it.

### The "Aha" Moment

Every recursive problem has two parts: **what the recursion does** and **where it stops**. Most people write the recursion first and patch in the base case as an afterthought. The correct mental model is the opposite:

> **Define the base case first. Recursion is just the rule for reducing towards it.**

If you cannot clearly state which input(s) require no further reduction, you do not yet understand the problem well enough to write the recursive step.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**When it appears:** Every recursive solution — DFS on graphs, tree traversals, divide-and-conquer, backtracking, memoised DP — requires correct base cases. In contests, this is not a separate topic; it is the precondition for every recursive technique working.

**Pattern signals:**

- Tree problems: base case = null node or leaf node
- Divide and conquer: base case = array of size 0 or 1
- Combinatorial generation: base case = current combination/permutation is complete
- DP recursion: base case = boundary indices (i=0, j=0, empty string, etc.)

**Common traps that kill submissions:**

1. **Off-by-one on boundary indices.** In string DP like [[171.Edit distance (Levenshtein) — string alignment DP]], missing the base case for `i=0` (empty first string) or `j=0` (empty second string) corrupts the entire table. The code compiles, runs, and returns a wrong number — often close to the right answer, which is the most dangerous kind of bug.
    
2. **Missing the empty input case.** Tree problems where the root can be `null` crash if you forget `if (node == null) return 0;`. This kills fast at runtime, which is actually kinder.
    
3. **Multiple base cases, only one written.** The Fibonacci sequence has _two_ base cases: `f(0) = 0` and `f(1) = 1`. Writing only `f(0) = 0` and calling `f(1)` reduces to `f(0) + f(-1)` — undefined behaviour or infinite recursion depending on your bounds check.
    
4. **Wrong return value in base case.** In a "count paths" problem, the base case when you reach the destination should return `1` (one valid path found). Returning `0` means you silently count nothing. The code is structurally correct but semantically inverted.
    

### Machine Learning / AI

**Autograd and computation graphs.** In PyTorch's autograd engine, backpropagation is recursive: compute the gradient of a node from the gradients of its consumers. The base case is the loss scalar (a leaf with `grad = 1.0`). The recursion propagates gradients backward through the DAG (see [[215.Gradient computation as a graph traversal — autograd intuition]]). Leaf tensors with `requires_grad=False` are additional base cases — autograd stops accumulating there.

**Recursive data structures in ML pipelines.** Decision trees (see [[158.Decision tree structure — how CART maps to a binary tree]]) are built recursively. The base case is: stop splitting when the node is pure, or when max depth / min samples thresholds are reached. Scikit-learn's `DecisionTreeClassifier` with no `max_depth` set is a tree with only the purity base case — it will overfit by growing until every leaf is a single sample. That missing constraint is a practical consequence of a too-weak base case.

**Recursive tensor operations.** The `torch.nn.Module.apply()` method recursively walks a model's submodule tree. Its base case is a module with no children (a leaf layer like `nn.Linear`). Understanding this is why `model.apply(init_weights)` correctly initialises all layers — including nested ones — without you writing a loop.

**Divide-and-conquer in data preprocessing.** External merge sort — used to sort datasets larger than RAM — is divide and conquer where the base case is a chunk that fits in memory. This appears in Apache Spark's sort shuffle and in the external sort phase of database query engines.

## 3. Algorithm / Pattern

### What a Base Case Is

A base case is a condition under which the function returns a value **directly**, without any recursive call. It must satisfy three properties:

1. **Reachable:** the recursive step must be guaranteed to move toward the base case (decreasing argument, shrinking input, advancing index)
2. **Correct:** the value returned must be the actual answer for that input, not a convenient stub
3. **Complete:** all possible minimal inputs must be covered — not just one

### How to Find Base Cases Systematically

**Decision tree:**

```
What is the simplest possible input to this function?
├── Empty collection ([], "", null tree node)?  → handle it
├── Single element?                             → handle it if recursion on 1 breaks
├── Boundary index (i=0, i=n, j=0, j=m)?      → handle it for 2D DP
└── Boolean condition (found, complete)?        → handle it for backtracking
```

Ask: _"What happens if I call this function with the smallest legal input?"_ If the recursive step still works, the smaller input is not a base case — it's just a small case. If the recursive step would call itself with an invalid or undefined input, you found a missing base case.

### Cost Analysis of Missing Base Cases

|Missing base case type|Runtime behaviour|Debugging difficulty|
|---|---|---|
|No termination condition|Stack overflow (immediate crash)|Easy|
|Wrong return value at boundary|Silently wrong output|Hard|
|Off-by-one boundary|Wrong output for most inputs|Medium|
|Missing one of two base cases|Crash on specific inputs only|Medium-Hard|

### When to Avoid Deep Recursion Entirely

When the recursion depth can reach O(n) and n > ~10,000 (Python default stack ~1000 frames, C++ ~millions but not infinite), prefer iterative implementations. See [[71.The call stack — stack frames, stack overflow, iterative conversion]].

**Time and Space:**

- Correct base case: no added cost — O(1) comparison per call
- Missing base case (crash): O(stack depth) wasted before the crash
- Wrong base case: no added cost, but correctness O(total wrong answers)

## 4. Pseudocode

```
FUNCTION solve(input):
    # Step 1: Check all base cases FIRST, before any recursive step
    IF input meets termination condition 1:
        RETURN base_value_1            # must be the provably correct answer here

    IF input meets termination condition 2:
        RETURN base_value_2            # handle all distinct minimal cases

    # Step 2: Reduce the problem toward the base case
    smaller_input ← reduce(input)      # guaranteed to be strictly closer to base case

    # Step 3: Recursive call
    sub_result ← solve(smaller_input)

    # Step 4: Combine sub-result into the answer for this input
    RETURN combine(sub_result, input)
```

**Checklist before finalising any recursive function:**

```
[ ] Can this function be called with an empty input?  → covered?
[ ] Can this function be called with a single-element input?  → covered?
[ ] Does every recursive call use a strictly smaller/simpler argument?
[ ] Is the return value at each base case the CORRECT answer, not just 0 or null?
[ ] Are there multiple distinct base cases?  → all written?
```

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <iostream>
#include <vector>
#include <string>
#include <cassert>

// ─────────────────────────────────────────────────────────────────────────────
// Example 1: Binary search — base cases are the termination of the search
// Missing either base case causes infinite recursion or wrong answer.
// ─────────────────────────────────────────────────────────────────────────────
int binary_search(const std::vector<int>& arr, int target, int lo, int hi) {
    // BASE CASE 1: search space exhausted — element not found
    // Without this, we recurse with lo > hi forever (or until UB with lo=hi-1)
    if (lo > hi) return -1;

    int mid = lo + (hi - lo) / 2;  // avoids overflow vs (lo + hi) / 2

    // BASE CASE 2: found the element
    if (arr[mid] == target) return mid;

    // Recursive step: guaranteed to shrink [lo, hi] interval
    if (arr[mid] < target)
        return binary_search(arr, target, mid + 1, hi);
    else
        return binary_search(arr, target, lo, mid - 1);
}

// ─────────────────────────────────────────────────────────────────────────────
// Example 2: Count nodes in a binary tree
// The classic missing-base-case crash: forgetting to handle null nodes.
// ─────────────────────────────────────────────────────────────────────────────
struct TreeNode {
    int val;
    TreeNode* left;
    TreeNode* right;
    TreeNode(int v) : val(v), left(nullptr), right(nullptr) {}
};

int count_nodes(TreeNode* root) {
    // BASE CASE: null node — no subtree here, contributes 0 to count
    // Without this: root->left on a null ptr → segfault
    if (root == nullptr) return 0;

    // Recursive step: left subtree + right subtree + this node
    return 1 + count_nodes(root->left) + count_nodes(root->right);
}

// ─────────────────────────────────────────────────────────────────────────────
// Example 3: Edit distance — the poisoned-table example
// Base cases initialise the first row and column of the DP table.
// Missing them leaves garbage in dp[i][0] and dp[0][j], corrupting everything.
// ─────────────────────────────────────────────────────────────────────────────
int edit_distance(const std::string& s, const std::string& t) {
    int m = s.size(), n = t.size();
    // dp[i][j] = edit distance between s[0..i-1] and t[0..j-1]
    std::vector<std::vector<int>> dp(m + 1, std::vector<int>(n + 1, 0));

    // BASE CASE: transforming s[0..i-1] to empty string requires i deletions
    for (int i = 0; i <= m; ++i) dp[i][0] = i;
    // BASE CASE: transforming empty string to t[0..j-1] requires j insertions
    for (int j = 0; j <= n; ++j) dp[0][j] = j;

    for (int i = 1; i <= m; ++i) {
        for (int j = 1; j <= n; ++j) {
            if (s[i-1] == t[j-1])
                dp[i][j] = dp[i-1][j-1];  // no operation needed
            else
                dp[i][j] = 1 + std::min({dp[i-1][j],    // delete from s
                                          dp[i][j-1],    // insert into s
                                          dp[i-1][j-1]}); // replace
        }
    }
    return dp[m][n];
}

// ─────────────────────────────────────────────────────────────────────────────
// Demo
// ─────────────────────────────────────────────────────────────────────────────
int main() {
    // Binary search tests
    std::vector<int> arr = {1, 3, 5, 7, 9, 11};
    assert(binary_search(arr, 7, 0, arr.size()-1) == 3);
    assert(binary_search(arr, 4, 0, arr.size()-1) == -1);
    assert(binary_search(arr, 1, 0, arr.size()-1) == 0);   // left boundary
    assert(binary_search(arr, 11, 0, arr.size()-1) == 5);  // right boundary

    // Tree tests
    TreeNode* root = new TreeNode(1);
    root->left = new TreeNode(2);
    root->right = new TreeNode(3);
    root->left->left = new TreeNode(4);
    assert(count_nodes(root) == 4);
    assert(count_nodes(nullptr) == 0);  // base case directly

    // Edit distance tests
    assert(edit_distance("kitten", "sitting") == 3);
    assert(edit_distance("", "abc") == 3);     // hits base case: empty s
    assert(edit_distance("abc", "") == 3);     // hits base case: empty t
    assert(edit_distance("", "") == 0);        // both empty
    assert(edit_distance("a", "a") == 0);

    std::cout << "All tests passed.\n";
    return 0;
}
```

### Python (Readable + Pythonic)

```python
from functools import lru_cache
from typing import Optional


# ─────────────────────────────────────────────────────────────────────────────
# Example 1: Fibonacci — TWO base cases required, one is never enough
# ─────────────────────────────────────────────────────────────────────────────
def fib_wrong(n: int) -> int:
    """
    WRONG: only one base case.
    fib_wrong(1) → fib_wrong(0) + fib_wrong(-1)
    fib_wrong(-1) → fib_wrong(-2) + fib_wrong(-3) → ... infinite recursion
    """
    if n == 0:
        return 0
    return fib_wrong(n - 1) + fib_wrong(n - 2)  # crashes for n=1


def fib_correct(n: int) -> int:
    """
    Correct: both base cases present.

    Time:  O(2^n) — exponential without memoisation
    Space: O(n) — call stack depth
    """
    if n == 0:
        return 0   # base case 1
    if n == 1:
        return 1   # base case 2: without this, n=1 recurses into n=-1
    return fib_correct(n - 1) + fib_correct(n - 2)


@lru_cache(maxsize=None)
def fib_memo(n: int) -> int:
    """
    Memoised version — same base cases, O(n) time.
    Note: base cases are STILL required even with memoisation.
    lru_cache does not inject them.
    """
    if n == 0:
        return 0
    if n == 1:
        return 1
    return fib_memo(n - 1) + fib_memo(n - 2)


# ─────────────────────────────────────────────────────────────────────────────
# Example 2: Flatten a nested list — base case is non-list element
# This is a real pattern in ML data loading (e.g., nested JSON features).
# ─────────────────────────────────────────────────────────────────────────────
def flatten(nested: list) -> list:
    """
    Flatten an arbitrarily nested list.
    Base case: element is not a list → yield it directly.

    Time:  O(n) where n = total number of non-list elements
    Space: O(d) where d = maximum nesting depth (call stack)

    >>> flatten([1, [2, [3, 4], 5], 6])
    [1, 2, 3, 4, 5, 6]
    """
    result = []
    for item in nested:
        # BASE CASE: item is not a list — it's a leaf value
        if not isinstance(item, list):
            result.append(item)
        else:
            # Recursive step: item is a sublist — flatten it
            result.extend(flatten(item))
    return result


# ─────────────────────────────────────────────────────────────────────────────
# Example 3: Demonstrating the "wrong return value" failure
# This is the most dangerous base case error — silent wrong answers.
# ─────────────────────────────────────────────────────────────────────────────
def count_paths_wrong(grid: list[list[int]], i: int, j: int) -> int:
    """
    WRONG: base case returns 0 instead of 1 when destination reached.
    All paths to the bottom-right are found but counted as 0.
    Result is always 0 regardless of grid size.
    """
    m, n = len(grid), len(grid[0])
    if i == m - 1 and j == n - 1:
        return 0  # BUG: should return 1 — "I found a valid path"
    total = 0
    if i + 1 < m:
        total += count_paths_wrong(grid, i + 1, j)
    if j + 1 < n:
        total += count_paths_wrong(grid, i, j + 1)
    return total


def count_paths_correct(grid: list[list[int]], i: int, j: int) -> int:
    """
    Correct: base case returns 1 to register the found path.

    Time:  O(2^(m+n)) naive; O(m*n) with memoisation
    Space: O(m+n) call stack depth
    """
    m, n = len(grid), len(grid[0])
    # BASE CASE: reached destination — this IS one valid path
    if i == m - 1 and j == n - 1:
        return 1
    total = 0
    if i + 1 < m:
        total += count_paths_correct(grid, i + 1, j)
    if j + 1 < n:
        total += count_paths_correct(grid, i, j + 1)
    return total


# ─────────────────────────────────────────────────────────────────────────────
# Tests
# ─────────────────────────────────────────────────────────────────────────────
if __name__ == "__main__":
    # Fibonacci
    assert fib_correct(0) == 0
    assert fib_correct(1) == 1
    assert fib_correct(10) == 55
    assert fib_memo(10) == 55

    # Flatten
    assert flatten([1, [2, [3, 4], 5], 6]) == [1, 2, 3, 4, 5, 6]
    assert flatten([]) == []           # empty list: loop body never runs
    assert flatten([1, 2, 3]) == [1, 2, 3]  # no nesting: all base cases

    # Count paths
    grid = [[0] * 3 for _ in range(3)]
    assert count_paths_wrong(grid, 0, 0) == 0   # always 0 — silent bug
    assert count_paths_correct(grid, 0, 0) == 6  # correct: C(4,2) = 6

    print("All tests passed.")
```

## 6. Visual Explanation

### The Missing Base Case: Infinite Call Chain

```
fib(3)
├── fib(2)
│   ├── fib(1)              ← hits base case n==1: return 1  ✓
│   └── fib(0)              ← hits base case n==0: return 0  ✓
└── fib(1)                  ← hits base case n==1: return 1  ✓

Without base case n==1:
fib(1)
└── fib(0) + fib(-1)        ← fib(-1) begins
    └── fib(-2) + fib(-2)   ← fib(-2) begins
        └── ...              ← never terminates → stack overflow
```

### The Wrong Return Value: Poisoned DP Table

Edit distance between "ac" and "bc" — comparing a correctly initialised table vs one with missing base cases:

```
CORRECT initialisation          MISSING base cases (dp[i][0], dp[0][j] left as 0)

     ""  b   c                       ""  b   c
  ""  0   1   2                   ""  0   1   2
  a   1   1   2                   a   0   0   1    ← row 1 wrong (used dp[i][0]=0)
  c   2   2   1  ✓                c   0   0   0    ← all 0s propagate down

Final answer: 1 (one substitution)    Final answer: 0 (wrong — "no edits needed")
```

The wrong table returned 0 — confidently, silently, incorrectly. The base case `dp[i][0] = i` encodes: _"cost to delete i characters from s to reach empty string."_ Without it, the algorithm believes deleting everything costs nothing.

### Backtracking Base Case: When to Accept vs Reject

```
generate_subsets([1, 2, 3]), current = []

index=0: include 1  →  [1]
  index=1: include 2  →  [1,2]
    index=2: include 3  →  [1,2,3]
      index=3: BASE CASE (index == len)  → emit [1,2,3]  ✓
    index=2: skip 3    →  [1,2]
      index=3: BASE CASE                → emit [1,2]     ✓
  index=1: skip 2    →  [1]
    ... (continues)

Without base case at index==len:
  index=3 would try arr[3] → IndexError, or silently emit partial states
```

## 7. Common Variations & Extensions

**Multiple interdependent base cases.** Some DP problems need an entire _row_ or _column_ of base cases, not a single value. In [[172.Longest Common Subsequence (LCS)]], `dp[i][0] = 0` for all `i` and `dp[0][j] = 0` for all `j` must be initialised before the main loop. Missing one row while setting the other gives a triangularly-correct, triangularly-wrong table.

**Base cases in backtracking: accept vs reject.** [[77.Backtracking template — choose, explore, unchoose]] has two base cases at the bottom of the recursion: one for _"this partial solution is complete and valid — emit it"_ and one for _"this path is invalid — prune immediately."_ Both are base cases. The pruning one is optional for correctness but mandatory for performance.

**Mutual recursion: both functions need base cases.** When function A calls B and B calls A (e.g., even/odd parity checkers, some grammar parsers), each function needs its own base case independently. Missing the base case in B while A's looks fine still causes infinite recursion.

**Base cases in divide and conquer.** In [[42.Merge sort — divide and conquer, stable, O(n log n)]], the base case is an array of size ≤ 1 (already sorted). In [[44.Quicksort — partition, pivot selection, expected O(n log n)]], it's similarly the empty or single-element subarray. Both are cases where the recursive step — partitioning/merging — would produce zero work, so the base case simply returns early.

## 9. CP Contest Application

**Typical contest structure:** Base case errors almost never appear as a standalone problem — they appear as the reason your correct recursive algorithm gets WA or RE. In Codeforces Div. 2 B/C problems involving trees or DP, wrong answers from base case errors are extremely common and hard to debug under time pressure.

**Timing discipline:** Before submitting any recursive solution, run it mentally on the _smallest legal input_: empty array, null tree, `n=0`, `n=1`, a 1×1 grid, two equal strings. If it produces the correct output on all of them, your base cases are likely sound.

**Common contest optimisations around base cases:**

- In competitive DP, initialise the entire `dp` array to a sentinel value (`INT_MAX/2` for min problems, `0` for count problems) and only write explicit base case assignments where the sentinel is wrong. This avoids missing boundary cells.
- For tree problems, use a helper that checks `if (!node) return identity_value;` as the very first line. The `identity_value` is problem-specific: `0` for sums, `INT_MIN` for max, `true` for "all nodes satisfy" — the mistake is always using `0` as a universal identity.
