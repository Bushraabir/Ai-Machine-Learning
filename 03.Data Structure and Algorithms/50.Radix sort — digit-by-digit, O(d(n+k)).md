## 1. Intuition First

### The Core Idea

Imagine sorting a deck of punched cards by a 3-digit number printed on each. A human would look at all three digits simultaneously and reason about their combined value. A card-sorting machine from the 1950s — the literal origin of this algorithm — does something counterintuitive: it sorts by the rightmost digit only, collects the cards in order, then sorts by the middle digit only, then sorts by the leftmost digit only. Three passes, each ignoring all but one digit. The result is a correctly sorted deck.

This works because of one non-obvious property: each single-digit sort is stable. When you sort by the middle digit and two cards have the same middle digit, their relative order from the previous pass (sorted by rightmost digit) is preserved. So after the second pass, cards are correctly ordered by the combination of middle digit first, rightmost digit as tiebreaker — even though you never explicitly sorted by that combination. By the third pass, all three digits are correctly accounted for through the accumulation of stable single-digit sorts.

This is LSD radix sort — Least Significant Digit first. There is also MSD (Most Significant Digit first), which recurses and is structurally different. LSD is far more common in practice and is what "radix sort" means unless otherwise specified.

### Why This Exists

Counting sort ([[49.Counting sort — O(n + k) for integer keys]]) runs in O(n + k) but requires k to be small relative to n. When sorting 32-bit integers, k = 2³² — a count array of 4 billion entries is infeasible. Radix sort solves this by decomposing the large key range into d smaller passes, each with a tractable range.

Sort 32-bit integers using base 256 (one byte per pass): d = 4 passes, k = 256 per pass. Total cost: O(4 × (n + 256)) = O(n). Compare to O(n log n) for any comparison sort. For n = 10⁷, this is the difference between 230 million operations and 10 million — a factor of 23.

The comparison sort lower bound (O(n log n)) is avoided for the same reason counting sort avoids it: keys are integers used directly as indices, not as opaque objects compared pairwise.

### The "Aha" Moment

The correctness of LSD radix sort is entirely dependent on stability of the inner sort. This is not a detail — it is the entire mechanism. If any single pass uses an unstable sort, later passes will overwrite the correct relative ordering from earlier passes, and the final result will be wrong. The algorithm does not check whether a number is globally smaller; it relies on the accumulation of locally correct stable orderings across digit positions.

Formally: after pass i (sorting by digit position i, 0-indexed from least significant), the array is sorted by the i-digit suffix of each number. This invariant holds if and only if each pass is stable. By the final pass (digit position d-1), the array is sorted by the entire d-digit number.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

Radix sort appears in contests as a speed optimisation when comparison-based sorts are too slow, and as a correctness requirement in problems that explicitly require O(n) sorting.

When it appears:

- Sorting large arrays (n up to 10⁷ or 10⁸) where the 5× constant factor of radix sort over `std::sort` determines whether the solution passes within the time limit
- Suffix array construction — SA-IS and DC3 algorithms use radix sort internally to sort suffixes in O(n); this is the dominant context for radix sort in Div. 1 D/E string problems
- Sorting strings of fixed or bounded length over a small alphabet, where treating each character as a digit of a base-|alphabet| number gives O(d × n) with d = max string length
- Problems that require sorting followed by many queries, where the O(n) sort leaves more budget for the query processing

Pattern signal: n > 5 × 10⁶ with integer keys bounded by 10⁹, and the time limit is 1–2 seconds. `std::sort` at 10⁸ operations per second will take 50× log₂(5×10⁶) ≈ 1.1 seconds — marginal. Radix sort at similar constant will take ~0.2 seconds.

Common trap: assuming radix sort is always faster than `std::sort`. For n < 10⁵, the constant factor of allocating the output buffer and running multiple passes makes radix sort slower than cache-friendly introsort. The crossover point on modern hardware is roughly n = 10⁵ to 10⁶ depending on key size.

A second trap: using MSD radix sort when LSD is needed, or vice versa, without understanding which is appropriate. LSD is the standard for fixed-width integer keys. MSD is appropriate for variable-length strings where short strings should sort before long ones with the same prefix (standard lexicographic order).

### Machine Learning / AI

**Suffix arrays in NLP preprocessing:** Suffix array construction is used to build FM-indexes for efficient substring search over large text corpora — a component of some information retrieval systems. The SA-IS algorithm, which constructs a suffix array in O(n), uses radix sort internally on character values (k = alphabet size, often 256). Any system that builds a compressed full-text index over a large corpus (BWT transform, compressed pattern matching) depends on O(n) suffix array construction, which depends on radix sort.

**GPU-accelerated sorting in ML systems:** NVIDIA's Thrust library (the GPU equivalent of the C++ STL) provides `thrust::sort` which internally uses radix sort for integer keys. When sorting large arrays of integer indices on GPU — common in operations like argsort for attention score ranking, top-k selection in beam search, or reordering embeddings by cluster assignment — Thrust radix sort achieves near-peak memory bandwidth. CUB (CUDA UnBound), which underlies PyTorch's CUDA operations, uses radix sort for GPU-side integer sorting. Understanding that GPU sort is radix sort explains why `torch.sort` on integer tensors is dramatically faster than on float tensors (floats require sign-bit manipulation to be radix-sortable).

**Radix sort for float tensors:** IEEE 754 floating point can be sorted with radix sort using a bit-level trick: for positive floats, the bit representation is already in the correct lexicographic order (sign + exponent + mantissa, all in the right positions). For negative floats, the bits must be flipped. This means any float array can be sorted with radix sort after a bitwise transformation, achieving O(n) on floating point. PyTorch's GPU sort exploits this. Understanding the trick requires [[106.Floating point bit representation — IEEE 754 intuition]].

**Counting sort as a special case:** Counting sort ([[49.Counting sort — O(n + k) for integer keys]]) is radix sort with d = 1 pass. Any analysis or implementation of counting sort generalises directly to radix sort. When you use `np.bincount` for label frequency counting, you are performing one digit of radix sort. When you chain two `np.bincount` calls to sort 2D integer keys (row index, column index), you are performing LSD radix sort with d = 2 passes.

## 3. Algorithm / Pattern

### LSD Radix Sort — Step-by-Step

Given n integers, each with d digits in base k:

Pass 1: Extract digit at position 0 (least significant) from each element. Apply stable counting sort using this digit as the key. Key range is [0, k−1].

Pass 2: Extract digit at position 1 from each element of the output of Pass 1. Apply stable counting sort. The stability preserves the Pass 1 ordering for equal digits at position 1.

Continue for passes 3 through d.

After pass d (most significant digit), the array is fully sorted.

### Base and Digit Extraction

For base k, the digit at position i of integer x is:

```
digit(x, i, k) = (x / k^i) mod k
```

Common choices of k and their tradeoffs:

|Base k|Passes d (32-bit int)|Count array size|Cache behaviour|
|---|---|---|---|
|10|10|10 entries|Excellent|
|16|8|16 entries|Excellent|
|256|4|256 entries|Good — fits in cache|
|65536|2|65536 entries|Poor — count array too large|

Base 256 (extracting one byte per pass, d = 4 for 32-bit integers) is the standard choice in practice. It minimises the number of passes while keeping the count array small enough to fit in L1 cache.

### Correctness Invariant

After processing digit positions 0 through i, the array is sorted by the i+1 digit suffix (digits 0..i) of each element. Proof by induction: the base case (i=0) holds because stable counting sort on digit 0 produces a correct sort by digit 0. The inductive step: stable counting sort on digit i+1 sorts by digit i+1 and, for ties in digit i+1, preserves the existing order from the inductive hypothesis — which is sort by digits 0..i. Combined: sort by digits 0..i+1.

### Complexity Derivation

Each pass is stable counting sort: O(n + k) time, O(n + k) space. d passes total: O(d(n + k)) time, O(n + k) space (output buffer reused).

When is this better than O(n log n)?

d(n + k) < n log n d × n < n log n (assuming k << n) d < log n

For 32-bit integers sorted in base 256: d = 4. log₂(n) = 4 when n = 16. For any n > 16, radix sort wins. For n = 10⁶, log₂(n) ≈ 20, so radix sort does roughly 5× fewer operations.

### When to Use vs When to Avoid

Use radix sort when:

- Keys are fixed-width integers or strings over a small alphabet
- n is large enough that the constant factor of multiple passes is amortised (n > 10⁵ approximately)
- O(n) is required by the algorithm (suffix array construction, external sort)
- GPU sorting of integer tensors (Thrust/CUB use radix sort internally)

Avoid radix sort when:

- Keys are arbitrary objects (floating point without the bit trick, complex structs)
- n is small — the constant of allocating buffers and running multiple passes dominates
- In-place sorting is required — radix sort needs an O(n) output buffer
- The key range within each digit varies wildly (though this is rarely an issue in practice)

## 4. Pseudocode

```
RADIX_SORT_LSD(arr, d, k):
    # arr: array of n integers, each with d digits in base k
    # Perform d stable counting sort passes, least significant digit first

    for i from 0 to d-1:
        # Extract digit i from each element as the sort key
        key_fn ← lambda x: (x / k^i) mod k
        arr ← COUNTING_SORT_STABLE(arr, k, key_fn)
        # arr is now sorted by digits 0..i (i+1 digit suffix)

    return arr


COUNTING_SORT_STABLE(arr, k, key_fn):
    n ← len(arr)
    count  ← array of zeros, length k
    output ← array of length n

    # Phase 1: count
    for x in arr:
        count[key_fn(x)] += 1

    # Phase 2: prefix sum
    for i from 1 to k-1:
        count[i] += count[i-1]

    # Phase 3: place RIGHT TO LEFT (stability requirement)
    for i from n-1 DOWN TO 0:
        d_i ← key_fn(arr[i])
        count[d_i] -= 1
        output[count[d_i]] ← arr[i]

    return output


# Digit extraction for base 256 (byte-by-byte, 32-bit integers):
BYTE_OF(x, byte_position):
    return (x >> (8 * byte_position)) & 0xFF
    # byte_position 0 = least significant byte
    # byte_position 3 = most significant byte
```

Edge cases:

- All elements equal: every pass leaves the array unchanged. Correct.
- d = 1: reduces exactly to counting sort. Correct.
- n = 0 or n = 1: inner counting sort handles these. Correct.
- Negative integers: two approaches. Either treat as unsigned (works for two's complement if you flip the sign bit after the final pass), or shift all values by subtracting the minimum before sorting and add it back afterward. See implementation for the sign-bit approach.

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <algorithm>
#include <array>
#include <cstdint>
#include <iostream>
#include <vector>

// Single stable counting sort pass on one byte of each element.
// byte_pos: 0 = least significant, 3 = most significant (for 32-bit values).
// Time: O(n + 256)   Space: O(n)
static void counting_pass(std::vector<uint32_t>& src,
                           std::vector<uint32_t>& dst,
                           int byte_pos) {
    const int k = 256;
    std::array<int, k> count{};

    // Phase 1: count
    for (uint32_t x : src)
        count[(x >> (8 * byte_pos)) & 0xFF]++;

    // Phase 2: prefix sum (exclusive — starting position of each bucket)
    // Transform count[i] to be the starting index of bucket i in output.
    // This is equivalent to the "exclusive prefix sum" variant.
    int total = 0;
    for (int i = 0; i < k; ++i) {
        int c = count[i];
        count[i] = total;
        total += c;
    }

    // Phase 3: place LEFT TO RIGHT using exclusive prefix sum.
    // With exclusive prefix sum, left-to-right placement is stable:
    // count[d] is the next available slot for digit d, incremented after use.
    for (uint32_t x : src) {
        int d = (x >> (8 * byte_pos)) & 0xFF;
        dst[count[d]++] = x;
    }
}

// LSD radix sort for 32-bit unsigned integers.
// 4 passes over base-256 digits (one byte per pass).
// Time: O(4n)   Space: O(n)
void radix_sort(std::vector<uint32_t>& arr) {
    int n = static_cast<int>(arr.size());
    if (n <= 1) return;

    std::vector<uint32_t> buf(n);   // output buffer, alternated with arr

    counting_pass(arr, buf, 0);     // sort by byte 0 (LSB)
    counting_pass(buf, arr, 1);     // sort by byte 1
    counting_pass(arr, buf, 2);     // sort by byte 2
    counting_pass(buf, arr, 3);     // sort by byte 3 (MSB) — result in arr
    // After 4 passes (even number), result ends up back in arr.
    // If d were odd, swap arr and buf at the end.
}

// Signed 32-bit integer radix sort via sign-bit flip.
// IEEE two's complement: flip the sign bit to make signed order match
// unsigned order, sort as unsigned, then flip back.
void radix_sort_signed(std::vector<int32_t>& arr) {
    // Reinterpret as uint32_t, flip sign bit
    auto* u = reinterpret_cast<uint32_t*>(arr.data());
    int n = static_cast<int>(arr.size());
    for (int i = 0; i < n; ++i)
        u[i] ^= 0x80000000u;

    std::vector<uint32_t> v(u, u + n);
    radix_sort(v);

    // Flip sign bit back and copy result
    for (int i = 0; i < n; ++i) {
        v[i] ^= 0x80000000u;
        arr[i] = static_cast<int32_t>(v[i]);
    }
}

// Radix sort for strings of equal length over ASCII alphabet.
// d = string length, k = 256.
// Time: O(d * n)   Space: O(n)
void radix_sort_strings(std::vector<std::string>& arr) {
    if (arr.empty()) return;
    int d = static_cast<int>(arr[0].size());
    int n = static_cast<int>(arr.size());

    std::vector<std::string> buf(n);
    std::vector<std::string>* src = &arr;
    std::vector<std::string>* dst = &buf;

    for (int pos = d - 1; pos >= 0; --pos) {   // LSD: rightmost character first
        std::array<int, 256> count{};
        for (const auto& s : *src)
            count[static_cast<unsigned char>(s[pos])]++;

        int total = 0;
        for (int i = 0; i < 256; ++i) {
            int c = count[i];
            count[i] = total;
            total += c;
        }

        for (const auto& s : *src) {
            int d_i = static_cast<unsigned char>(s[pos]);
            (*dst)[count[d_i]++] = s;
        }

        std::swap(src, dst);
    }

    if (src != &arr)
        arr = *src;
}

int main() {
    // Unsigned integers
    std::vector<uint32_t> v = {329, 457, 657, 839, 436, 720, 355};
    radix_sort(v);
    for (uint32_t x : v) std::cout << x << ' ';
    std::cout << '\n';
    // 329 355 436 457 657 720 839

    // Signed integers (with negatives)
    std::vector<int32_t> sv = {3, -1, 4, -1, 5, -9, 2, 6};
    radix_sort_signed(sv);
    for (int32_t x : sv) std::cout << x << ' ';
    std::cout << '\n';
    // -9 -1 -1 2 3 4 5 6

    // Equal-length strings
    std::vector<std::string> words = {"bca", "aab", "bab", "aaa", "baa"};
    radix_sort_strings(words);
    for (const auto& w : words) std::cout << w << ' ';
    std::cout << '\n';
    // aaa aab baa bab bca

    return 0;
}
```

### Python (Readable + Pythonic)

```python
def counting_pass(arr: list[int], byte_pos: int) -> list[int]:
    """
    One stable counting sort pass extracting byte byte_pos from each element.
    Uses exclusive prefix sum with left-to-right placement for stability.
    Time: O(n + 256)   Space: O(n + 256)
    """
    k = 256
    count = [0] * k

    # Phase 1: count
    for x in arr:
        count[(x >> (8 * byte_pos)) & 0xFF] += 1

    # Phase 2: exclusive prefix sum
    # count[i] becomes the starting output index for bucket i
    total = 0
    for i in range(k):
        count[i], total = total, total + count[i]

    # Phase 3: place left to right (stable with exclusive prefix sum)
    output = [0] * len(arr)
    for x in arr:
        d = (x >> (8 * byte_pos)) & 0xFF
        output[count[d]] = x
        count[d] += 1

    return output


def radix_sort(arr: list[int]) -> list[int]:
    """
    LSD radix sort for non-negative integers up to 2^32 - 1.
    4 passes, base 256 (one byte per pass).
    Time: O(4n)   Space: O(n)
    """
    if len(arr) <= 1:
        return arr[:]

    result = arr[:]
    for byte_pos in range(4):          # bytes 0, 1, 2, 3 (LSB to MSB)
        result = counting_pass(result, byte_pos)
    return result


def radix_sort_signed(arr: list[int]) -> list[int]:
    """
    LSD radix sort for signed integers using sign-bit flip.
    Flipping the most significant bit maps two's complement signed order
    onto unsigned order: most negative -> 0, most positive -> 2^31 - 1.
    """
    # Shift to unsigned: add 2^31 maps [-2^31, 2^31-1] -> [0, 2^32-1]
    shifted = [x + (1 << 31) for x in arr]
    sorted_shifted = radix_sort(shifted)
    return [x - (1 << 31) for x in sorted_shifted]


def radix_sort_strings_fixed(strings: list[str]) -> list[str]:
    """
    LSD radix sort for fixed-length strings.
    Sorts by rightmost character first, leftmost last.
    Time: O(d * n)  where d = string length
    Space: O(n)
    """
    if not strings:
        return []
    d = len(strings[0])
    result = strings[:]

    for pos in range(d - 1, -1, -1):      # rightmost character first
        count = [0] * 256
        for s in result:
            count[ord(s[pos])] += 1

        total = 0
        for i in range(256):
            count[i], total = total, total + count[i]

        output = [''] * len(result)
        for s in result:
            c = ord(s[pos])
            output[count[c]] = s
            count[c] += 1

        result = output

    return result


if __name__ == '__main__':
    # Non-negative integers
    arr = [329, 457, 657, 839, 436, 720, 355]
    print(radix_sort(arr))
    # [329, 355, 436, 457, 657, 720, 839]

    # Signed integers
    arr_signed = [3, -1, 4, -1, 5, -9, 2, 6]
    print(radix_sort_signed(arr_signed))
    # [-9, -1, -1, 2, 3, 4, 5, 6]

    # Fixed-length strings
    words = ['bca', 'aab', 'bab', 'aaa', 'baa']
    print(radix_sort_strings_fixed(words))
    # ['aaa', 'aab', 'baa', 'bab', 'bca']
```

### The Stability Dependency — What Breaks Without It

```
Same input: [329, 457, 657, 839, 436, 720, 355]

Pass 1 (stable): [720, 355, 436, 457, 657, 329, 839]
  457 before 657 (both end in 7, 457 came first in input)

Pass 2 (UNSTABLE — suppose 457 and 657 swap arbitrarily):
  Output might be: [720, 329, 436, 839, 355, 657, 457]  <- 657 before 457

Pass 3 (stable, sorting by hundreds):
  hundreds of 657=6, 457=4
  Output: [..., 436, 457, ..., 657, 720, ...]

  But now 436 and 457 are sorted by hundreds only. Their 2-digit suffix
  "36" vs "57" would require 436 before 457 — and 436 IS before 457 here.
  But 329 vs 355: both hundreds=3. In Pass 2, they appeared as 720,329,436,839,355,...
  After unstable Pass 3, 329 and 355 may appear in wrong order.

The point: with unstable inner passes, the invariant
  "array is sorted by i+1 digit suffix after pass i"
breaks, and no later pass can recover the lost ordering information.
```

### Exclusive vs Inclusive Prefix Sum — Two Stable Placement Styles

```
count after counting phase: [0, 2, 1, 2, 1, 2]  (k=6)
                              key: 0  1  2  3  4  5

INCLUSIVE prefix sum (standard counting sort from note 49):
  count: [0, 2, 3, 5, 6, 8]
  count[x] = exclusive upper bound of x's block
  Placement: RIGHT TO LEFT, decrement before indexing.
    output[--count[d]] = element

EXCLUSIVE prefix sum (used in C++ implementation above):
  count: [0, 0, 2, 3, 5, 6]
  count[x] = starting index of x's block
  Placement: LEFT TO RIGHT, increment after indexing.
    output[count[d]++] = element

Both are correct and stable. The exclusive variant is slightly cleaner
for left-to-right placement. The inclusive variant matches the
derivation in note 49 exactly. Either can be used in radix sort.
Choose one and be consistent within an implementation.
```

## 7. Common Variations and Extensions

### 7.1 MSD Radix Sort

Most Significant Digit radix sort processes digits from left to right. After sorting by the first digit, elements are partitioned into k buckets by their first digit, and each bucket is recursively sorted by the remaining digits. This is structurally similar to quicksort's partition step.

MSD is advantageous for variable-length strings (you can stop recursing when a bucket has one element or when you reach the end of the string), and for situations where you only need partial sorting (the first bucket is fully sorted without touching the others). MSD is the basis for string radix sort in applications like trie construction.

MSD is more complex to implement correctly — empty bucket handling, recursion termination, and the interaction with variable-length keys all add implementation surface area. For fixed-width integers, LSD is almost always preferable.

### 7.2 Radix Sort for Floating Point

IEEE 754 positive floats sort in the same order as their bit representations interpreted as unsigned integers. This is by design: the exponent occupies the high bits, mantissa the low bits, and the encoding is monotone with respect to numeric value for positive numbers. For negative floats, the encoding is reversed — larger negative numbers have smaller bit representations. The fix: XOR all bits of negative floats (flip all bits of the mantissa and exponent), and XOR only the sign bit of positive floats. After this transformation, the bit representations sort in the same order as the original float values. Apply unsigned radix sort. Reverse the transformation on output. This allows O(n) sorting of float arrays at the cost of two O(n) passes for the bit manipulation. See [[106.Floating point bit representation — IEEE 754 intuition]] for the encoding details.

### 7.3 American Flag Sort

American Flag sort is an in-place variant of MSD radix sort. Instead of allocating separate buckets, it partitions the array in-place using a two-pass MSD approach (count, then permute). Space is O(k) for the count array rather than O(n) for an output buffer. The tradeoff: more complex implementation and slightly worse cache behaviour. Used in embedded systems where O(n) auxiliary space is unavailable.

### 7.4 Radix Sort in Suffix Array Construction

The SA-IS algorithm (Suffix Array — Induced Sorting) constructs a suffix array in O(n) time and space. It uses radix sort (specifically, counting sort on character values) as its core primitive for sorting suffixes by their first character and for sorting LMS substrings. The character alphabet is used as the digit space (k = alphabet size). This is the primary context in which radix sort appears in competitive programming at the Div. 1 D/E level — implementing it correctly requires a solid understanding of both LSD radix sort and its stability properties.

## 9. CP Contest Application

### When Radix Sort Determines AC vs TLE

The canonical scenario: n = 10⁷, values up to 10⁹, time limit 2 seconds. `std::sort` runs at roughly 10⁸ comparisons/second — 10⁷ × 23 ≈ 2.3 × 10⁸ operations, borderline. Radix sort (4 passes, base 256) runs 4 × 10⁷ = 4 × 10⁷ operations at higher throughput (no branch mispredictions in the inner loop) — roughly 0.3 seconds. The difference is AC vs TLE.

### Implementation Template for Contests

```cpp
// Contest-ready radix sort: 32-bit unsigned integers, base 256, 4 passes.
// Fastest version: precompute all 4 count arrays in a single pass over input
// (reduces cache misses from 4 passes to 2).
void radix_sort_fast(std::vector<uint32_t>& a) {
    int n = a.size();
    if (n <= 1) return;

    // Count all 4 bytes in one pass
    std::array<std::array<int,256>, 4> cnt{};
    for (uint32_t x : a)
        for (int b = 0; b < 4; ++b)
            cnt[b][(x >> (8*b)) & 0xFF]++;

    std::vector<uint32_t> buf(n);
    auto* src = a.data();
    auto* dst = buf.data();

    for (int b = 0; b < 4; ++b) {
        // Exclusive prefix sum
        int t = 0;
        for (int i = 0; i < 256; ++i) { int c = cnt[b][i]; cnt[b][i] = t; t += c; }
        // Place
        for (int i = 0; i < n; ++i) {
            int d = (src[i] >> (8*b)) & 0xFF;
            dst[cnt[b][d]++] = src[i];
        }
        std::swap(src, dst);
    }

    // After 4 (even) passes, result is back in a.data()
    if (src != a.data()) std::copy(buf.begin(), buf.end(), a.begin());
}
```

The key optimisation: precomputing all four count arrays in a single pass halves the number of times the input array is read from memory, reducing cache pressure significantly at large n.

### Suffix Array via Radix Sort

For hard string problems (suffix array construction, Lyndon factorisation, string matching at O(n)):

The standard competitive programming approach is the O(n log n) doubling algorithm using counting sort at each step. Each step doubles the comparison length, requiring a stable sort of (rank[i], rank[i + len]) pairs — a 2-key radix sort with k = n (current rank values). This is two passes of counting sort per doubling step, giving O(n log n) total for the full suffix array. For O(n), SA-IS is required — substantially more complex but achievable in a contest with a pre-written template.
