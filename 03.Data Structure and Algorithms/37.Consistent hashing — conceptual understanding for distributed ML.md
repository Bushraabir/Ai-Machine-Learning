## 1. Intuition First

### The Core Idea

Imagine you have n servers and you want to distribute requests evenly across them. The obvious answer: `server = hash(request_key) % n`. Simple, fast, works perfectly — until you add or remove a server.

When n changes to n+1, nearly every key remaps. If you had 1,000,000 keys across 10 servers, adding an 11th server remaps ≈909,090 keys — about 91% of all keys. Every one of those remapped keys requires either a cache miss (in a caching system) or a data migration (in a storage system). This is catastrophic at scale.

**Consistent hashing** solves this with a geometric insight. Instead of mapping keys to servers directly, map _both keys and servers_ onto the same abstract circle — a **hash ring** — with positions in the range [0, 2³²). A key is owned by the **first server clockwise** from its position on the ring. When you add or remove a server, only the keys that fall between the new/removed server and its predecessor on the ring need to remigrate — roughly n/k keys for n total keys and k servers. All other keys are untouched.

**The "Aha" Moment:** Classic modulo hashing is a linear mapping: key → slot index. Consistent hashing is a _circular_ mapping: key and server both become points on the same space, and ownership is defined geometrically. By putting keys and servers in the same coordinate system, a server change only disturbs its local neighbourhood, not the global assignment.

### Why This Exists

The complexity gap is stark. For a system with n keys and k servers:

|Operation|Modulo hashing|Consistent hashing|
|---|---|---|
|Key → server lookup|O(1)|O(log k) with binary search on sorted ring|
|Add/remove server|O(n) remaps|O(n/k) remaps|
|Load balance (uniform)|Perfect (in theory)|Uneven without virtual nodes|
|Load balance (with vnodes)|N/A|Near-uniform, O(v·k) ring entries|

For a 100-node cluster serving 100M keys, adding one node under modulo hashing remaps ~99M keys. Under consistent hashing, it remaps ~1M keys. That is the gap between a multi-hour reshuffling outage and a seamless rebalancing in seconds.

### Real-World Stakes

This is not a theoretical curiosity. Amazon's Dynamo (2007 paper) invented consistent hashing for production use. Apache Cassandra, Amazon DynamoDB, Riak, and Akamai's CDN all use variants of it. In ML infrastructure, it determines how model parameter shards are routed across parameter servers, how distributed caches (Redis Cluster, Memcached) avoid thundering-herd invalidations, and how feature partitions are assigned to workers in distributed training.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

Consistent hashing is **not a CP topic** in the classical sense — you will not find it in Codeforces problems. However, the _underlying data structure_ — a sorted array with binary search for range queries — appears constantly:

- **Sorted ring as a sorted array:** The hash ring is just a sorted array of (position, server_id) pairs. Finding the responsible server for a key is `lower_bound(ring, hash(key))` — the exact same binary search template from [[56.lower_bound and upper_bound — first and last occurrence]].
- **Interval ownership problems:** "Given a set of points on a circle, assign each query point to its nearest clockwise neighbour" is a binary search on a sorted circular array — a T1 CP pattern.
- **Segment tree / BIT connection:** In problems requiring dynamic server addition/removal with efficient range queries, the ring can be maintained in a Fenwick tree — see [[156.Fenwick tree (BIT) — prefix sum with updates O(log n)]].

**The CP insight:** consistent hashing is binary search on a circular sorted structure. Recognise this abstraction and the implementation is straightforward.

### Machine Learning / AI

This is where consistent hashing earns deep study. It is load-balancing infrastructure for every large-scale ML system.

**1. Parameter Server Architecture (Distributed Training)**

In data-parallel training with a parameter server (PS) architecture — used historically in systems like DistBelief (Google, 2012) and current systems like BytePS — model parameters are partitioned across PS workers. Each PS worker owns a shard of the parameter space. When a gradient worker needs to push/pull a specific parameter, it must route the request to the correct PS node.

Consistent hashing on the parameter key (layer name + parameter index) determines which PS node owns it. When a PS node fails or is added during elastic training, only ~1/k of parameters need to remigrate — the model continues training on the surviving parameters while the disrupted shard recovers.

**2. Distributed Feature Stores and Embedding Tables**

Recommendation systems at Meta, Google, and ByteDance use embedding tables with O(10⁹) entries that cannot fit on a single machine. The table is sharded across dozens of embedding servers. When a training worker needs to look up `embedding[user_id]`, consistent hashing on `user_id` routes the request to the correct shard server.

Meta's DLRM paper (2019) and Baidu's PaddlePaddle describe consistent-hashing-based embedding routing. When an embedding server is added during traffic surge, only ~1/k entries remigrate — the rest continue serving without interruption.

**3. Distributed Caching for Inference**

LLM inference is expensive. Caching prompt-KV pairs (KV cache) across multiple inference servers requires knowing which server cached which prompt. Consistent hashing on the prompt hash ensures that the same prompt always routes to the same server (cache locality), while server additions/removals cause minimal cache invalidation.

Systems like vLLM (for LLM serving) and Triton Inference Server in multi-replica deployments benefit from consistent hashing for request routing to maximise KV cache reuse.

**4. Data Pipeline Sharding**

In distributed data preprocessing (Apache Beam, Spark), consistent hashing partitions dataset shards across workers. A worker joining or leaving the pipeline needs to receive or shed exactly its ring-neighbour's shard — not a global reshuffle. This makes pipeline autoscaling feasible during training data preparation.

**Why understanding this makes you a better ML engineer:**

When you debug a thundering-herd cache invalidation after a Kubernetes pod restart, or investigate why adding a feature server caused a training throughput spike, or understand why Cassandra's `vnodes` setting exists — you are debugging consistent hashing. Knowing the algorithm gives you the mental model to diagnose these failures before they become multi-hour incidents.

## 3. Algorithm / Pattern

### Core Hash Ring Construction

**Setup:**

1. Choose a hash function H that maps strings/bytes to [0, 2³²). MurmurHash3 or xxHash are standard.
2. For each server `s_i`, compute `H(s_i)` and place it at that position on the ring.
3. Maintain the ring as a **sorted array** of (position, server_id) pairs.

**Key lookup:**

1. Compute `pos = H(key)`.
2. Binary search the sorted ring for the first server position ≥ pos (`lower_bound`).
3. If no such position exists (pos > all server positions), wrap around to the first server (circular).
4. Time: O(log k) where k = number of server entries on the ring.

**Server addition:**

1. Compute `pos = H(new_server)`.
2. Insert into the sorted ring at the correct position.
3. Find the server that previously owned `pos` (the clockwise successor of `pos`).
4. Transfer the keys in range `(predecessor_of_new_server, pos]` from successor to new server.
5. Remigrated key count: ~n/k (expected).

**Server removal:**

1. Remove the server's entry from the sorted ring.
2. Its clockwise successor now owns its keys — transfer keys `(predecessor, removed_pos]` to successor.

### Virtual Nodes (Vnodes) — Why They Are Mandatory

With k physical servers and no virtual nodes, load distribution is highly uneven — the arc lengths between consecutive server positions on the ring vary enormously due to hash function randomness. One server might own 40% of the key space, another 2%.

**Virtual nodes:** Each physical server `s_i` is placed at `v` positions on the ring: `H("s_i#0")`, `H("s_i#1")`, ..., `H("s_i#(v-1)")`. With v = 100–200 vnodes per server, the law of large numbers ensures arc lengths converge toward 1/k each. Load imbalance falls from O(log k / k) worst case to O(√(log k / (v·k))) with vnodes.

Cassandra defaults to v = 256 vnodes per node. Dynamo used v = 100-200.

### Decision Tree

```
Do keys need to be distributed across multiple nodes?
├── Fixed number of nodes, no scaling expected
│   └── Modulo hashing: server = hash(key) % n   [O(1), simpler]
└── Dynamic number of nodes (add/remove expected)
    └── Consistent hashing on hash ring            [O(log k) lookup]
        ├── Is load balance critical?
        │   ├── Yes → Use virtual nodes (v = 100-256 per server)
        │   └── No  → Physical nodes only (simpler, less uniform)
        └── Is the key space bounded?
            ├── Yes (e.g., user IDs) → Direct hash ring
            └── No  (arbitrary strings) → Hash to fixed range first
```

### Complexity Summary

|Operation|Time|Space|
|---|---|---|
|Ring construction (k servers, v vnodes)|O(k·v · log(k·v))|O(k·v)|
|Key → server lookup|O(log(k·v))|O(1)|
|Add server|O(v · log(k·v) + n/k)|O(v) new ring entries|
|Remove server|O(v · log(k·v) + n/k)|O(v) entries freed|
|Remapped keys on change|O(n/k) expected|—|

The O(n/k) remapping guarantee is the core theorem of consistent hashing, proved by Karger et al. (1997). With n keys and k servers, adding or removing one server remaps at most O(n/k) keys _in expectation_ — the minimum possible given that each server should hold ~n/k keys.

## 4. Pseudocode

```
// ─── HASH RING CONSTRUCTION ───────────────────────────────────────────────────
class ConsistentHashRing:
    ring   ← sorted list of (position: int, server_id: string)
    vnodes ← number of virtual nodes per server (default: 150)

    function add_server(server_id):
        for replica_id from 0 to vnodes - 1:
            key     ← server_id + "#" + str(replica_id)
            pos     ← hash(key)                      // map to [0, 2^32)
            insert (pos, server_id) into ring         // maintain sorted order
            // O(log(k·v)) with binary search insertion

    function remove_server(server_id):
        for replica_id from 0 to vnodes - 1:
            key ← server_id + "#" + str(replica_id)
            pos ← hash(key)
            remove (pos, server_id) from ring
            // keys previously owned by this vnode now belong to clockwise successor


// ─── KEY LOOKUP ───────────────────────────────────────────────────────────────
    function get_server(key) → server_id:
        if ring is empty:
            raise Error("No servers available")

        pos   ← hash(key)                            // hash the key to ring position
        idx   ← lower_bound(ring, pos)               // first ring entry with position ≥ pos
                                                      // binary search: O(log(k·v))

        if idx == len(ring):
            idx ← 0                                  // wrap around: circular ring

        return ring[idx].server_id


// ─── SERVER ADDITION TRACE ────────────────────────────────────────────────────
// Before: ring = [..., (1200, "S1"), (3500, "S2"), (7800, "S3"), ...]
// Add S4 with hash position 4500.
// After:  ring = [..., (1200, "S1"), (3500, "S2"), (4500, "S4"), (7800, "S3"), ...]
//
// Keys in (3500, 4500] previously belonged to S3 (clockwise from S2).
// Now they belong to S4. Only these keys remigrate.
// Keys outside this arc: unchanged.
```

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <algorithm>
#include <cstdint>
#include <functional>
#include <map>
#include <optional>
#include <stdexcept>
#include <string>
#include <vector>
#include <iostream>

// ─── FNV-1a 32-bit hash (illustrative; use MurmurHash3 in production) ─────────
static uint32_t fnv1a_32(const std::string& s) {
    constexpr uint32_t OFFSET = 2166136261u;
    constexpr uint32_t PRIME  = 16777619u;
    uint32_t h = OFFSET;
    for (unsigned char c : s) {
        h ^= c;
        h *= PRIME;
    }
    return h;
}

// ─── CONSISTENT HASH RING ─────────────────────────────────────────────────────
// Uses std::map<uint32_t, string> as the ring — keys are ring positions,
// values are server IDs. std::map is a sorted BST: O(log n) insert/find.
// For very large rings (k*v > 10^6), switch to sorted std::vector + binary search.
class ConsistentHashRing {
public:
    explicit ConsistentHashRing(int vnodes = 150)
        : vnodes_(vnodes) {}

    // Add a server to the ring with `vnodes_` virtual positions.
    void add_server(const std::string& server_id) {
        for (int i = 0; i < vnodes_; ++i) {
            std::string vnode_key = server_id + "#" + std::to_string(i);
            uint32_t pos = fnv1a_32(vnode_key);
            ring_[pos] = server_id;       // insert vnode at this ring position
        }
        servers_.insert(server_id);
    }

    // Remove a server and all its virtual nodes from the ring.
    void remove_server(const std::string& server_id) {
        for (int i = 0; i < vnodes_; ++i) {
            std::string vnode_key = server_id + "#" + std::to_string(i);
            uint32_t pos = fnv1a_32(vnode_key);
            ring_.erase(pos);
        }
        servers_.erase(server_id);
    }

    // Return the server responsible for this key.
    // Finds the first ring position >= hash(key), wrapping around if needed.
    // Time: O(log(k * v))
    std::optional<std::string> get_server(const std::string& key) const {
        if (ring_.empty()) return std::nullopt;

        uint32_t pos = fnv1a_32(key);

        // lower_bound: first entry with ring position >= pos
        auto it = ring_.lower_bound(pos);

        // Wrap around to beginning of ring if past the end
        if (it == ring_.end()) {
            it = ring_.begin();
        }

        return it->second;
    }

    // Return all keys' server assignments — useful for load analysis.
    std::map<std::string, int> load_distribution(
        const std::vector<std::string>& keys
    ) const {
        std::map<std::string, int> dist;
        for (const auto& s : servers_) dist[s] = 0;
        for (const auto& key : keys) {
            auto server = get_server(key);
            if (server) ++dist[*server];
        }
        return dist;
    }

    size_t ring_size()   const { return ring_.size(); }
    size_t server_count() const { return servers_.size(); }

private:
    std::map<uint32_t, std::string> ring_;    // ring position → server_id
    std::set<std::string>           servers_; // active physical servers
    int                             vnodes_;  // virtual nodes per server
};


// ─── TESTS ────────────────────────────────────────────────────────────────────
#include <cassert>
#include <set>
#include <cmath>

int main() {
    ConsistentHashRing ring(150);

    // Add 3 servers
    ring.add_server("server-A");
    ring.add_server("server-B");
    ring.add_server("server-C");
    assert(ring.ring_size() == 450);  // 3 servers * 150 vnodes

    // Every key must map to one of the 3 servers
    std::vector<std::string> keys;
    for (int i = 0; i < 1000; ++i) keys.push_back("key:" + std::to_string(i));

    std::set<std::string> assigned_servers;
    for (const auto& k : keys) {
        auto s = ring.get_server(k);
        assert(s.has_value());
        assigned_servers.insert(*s);
    }
    assert(assigned_servers == std::set<std::string>{"server-A", "server-B", "server-C"});

    // Record assignments before adding server-D
    std::map<std::string, std::string> before;
    for (const auto& k : keys) before[k] = *ring.get_server(k);

    // Add a 4th server — count remapped keys
    ring.add_server("server-D");
    int remapped = 0;
    for (const auto& k : keys) {
        if (*ring.get_server(k) != before[k]) ++remapped;
    }

    // Expect ~25% of keys remapped (1/4), not ~75% as with modulo hashing
    double remapped_frac = static_cast<double>(remapped) / keys.size();
    std::cout << "Remapped fraction: " << remapped_frac
              << " (expected ~0.25)\n";
    assert(remapped_frac < 0.45);  // generous bound; vnodes reduce variance

    // Remove server-B — keys it owned should now go to other servers
    ring.remove_server("server-B");
    for (const auto& k : keys) {
        auto s = ring.get_server(k);
        assert(s.has_value() && *s != "server-B");
    }

    // Load distribution should be roughly uniform
    auto dist = ring.load_distribution(keys);
    for (auto& [srv, cnt] : dist) {
        std::cout << srv << ": " << cnt << " keys\n";
    }

    std::cout << "All tests passed.\n";
    return 0;
}
```

### Python (Readable + Pythonic)

```python
from __future__ import annotations

import hashlib
import bisect
from collections import defaultdict
from typing import Optional


# ─── CONSISTENT HASH RING ─────────────────────────────────────────────────────
class ConsistentHashRing:
    """
    Hash ring with virtual nodes for uniform load distribution.

    Uses sorted list + bisect for O(log(k*v)) key lookup.
    Suitable for understanding and medium-scale use; for production,
    use sorted array in C++ or a library like `uhashring` (Python).

    Parameters
    ----------
    vnodes : int
        Number of virtual nodes per physical server.
        Higher = better load balance, more memory.
        Cassandra default: 256. Dynamo: 100-200. Good general value: 150.

    Time:  O(log(k*v)) per lookup, O(v * log(k*v)) per server add/remove
    Space: O(k * v) for the ring
    """

    def __init__(self, vnodes: int = 150) -> None:
        self._vnodes = vnodes
        self._ring: dict[int, str] = {}       # position → server_id
        self._sorted_keys: list[int] = []     # sorted ring positions (for bisect)
        self._servers: set[str] = set()

    @staticmethod
    def _hash(key: str) -> int:
        """Map a string key to a position in [0, 2^32).

        Uses MD5 truncated to 32 bits for portability.
        In production: use mmh3.hash() (MurmurHash3) for better avalanche.
        """
        digest = hashlib.md5(key.encode(), usedforsecurity=False).digest()
        # Take first 4 bytes, interpret as big-endian uint32
        return int.from_bytes(digest[:4], "big")

    def add_server(self, server_id: str) -> None:
        """Place `vnodes` virtual positions for server_id on the ring."""
        self._servers.add(server_id)
        for i in range(self._vnodes):
            pos = self._hash(f"{server_id}#{i}")
            self._ring[pos] = server_id
            bisect.insort(self._sorted_keys, pos)  # O(v * log(k*v)) total

    def remove_server(self, server_id: str) -> None:
        """Remove all virtual nodes for server_id from the ring."""
        self._servers.discard(server_id)
        for i in range(self._vnodes):
            pos = self._hash(f"{server_id}#{i}")
            if pos in self._ring:
                del self._ring[pos]
                # O(log n) search + O(n) deletion — acceptable for infrequent removes
                idx = bisect.bisect_left(self._sorted_keys, pos)
                if idx < len(self._sorted_keys) and self._sorted_keys[idx] == pos:
                    self._sorted_keys.pop(idx)

    def get_server(self, key: str) -> Optional[str]:
        """
        Return the server responsible for this key.

        Finds the first ring position >= hash(key), wrapping around if needed.
        This is the core O(log(k*v)) binary search.
        """
        if not self._ring:
            return None

        pos = self._hash(key)

        # bisect_right gives insertion point; we want first position >= pos
        idx = bisect.bisect_right(self._sorted_keys, pos - 1)

        # Wrap around to start of ring if past the end
        if idx >= len(self._sorted_keys):
            idx = 0

        ring_pos = self._sorted_keys[idx]
        return self._ring[ring_pos]

    def load_distribution(self, keys: list[str]) -> dict[str, int]:
        """Count how many keys map to each server — for load analysis."""
        dist: dict[str, int] = defaultdict(int)
        for key in keys:
            server = self.get_server(key)
            if server:
                dist[server] += 1
        return dict(dist)

    @property
    def server_count(self) -> int:
        return len(self._servers)

    @property
    def ring_size(self) -> int:
        return len(self._sorted_keys)


# ─── REMAPPING ANALYSIS ───────────────────────────────────────────────────────
def compare_remapping(
    keys: list[str],
    servers_before: list[str],
    servers_after: list[str],
) -> dict:
    """
    Compare key remapping between modulo hashing and consistent hashing
    when transitioning from servers_before to servers_after.

    Demonstrates the core advantage of consistent hashing.
    """
    # Modulo hashing
    def modulo_assign(key: str, servers: list[str]) -> str:
        idx = int(hashlib.md5(key.encode(), usedforsecurity=False).hexdigest(), 16)
        return servers[idx % len(servers)]

    modulo_before = {k: modulo_assign(k, servers_before) for k in keys}
    modulo_after  = {k: modulo_assign(k, servers_after)  for k in keys}
    modulo_remapped = sum(1 for k in keys if modulo_before[k] != modulo_after[k])

    # Consistent hashing
    ring_before = ConsistentHashRing(vnodes=150)
    for s in servers_before:
        ring_before.add_server(s)

    ring_after = ConsistentHashRing(vnodes=150)
    for s in servers_after:
        ring_after.add_server(s)

    consistent_before  = {k: ring_before.get_server(k) for k in keys}
    consistent_after   = {k: ring_after.get_server(k)  for k in keys}
    consistent_remapped = sum(
        1 for k in keys if consistent_before[k] != consistent_after[k]
    )

    return {
        "total_keys":           len(keys),
        "modulo_remapped":      modulo_remapped,
        "consistent_remapped":  consistent_remapped,
        "modulo_fraction":      modulo_remapped / len(keys),
        "consistent_fraction":  consistent_remapped / len(keys),
        "expected_consistent":  1 / len(servers_after),  # theoretical ~1/k
    }


# ─── TESTS ────────────────────────────────────────────────────────────────────
if __name__ == "__main__":
    import random

    random.seed(42)
    keys = [f"key:{i}" for i in range(10_000)]

    # Basic ring operations
    ring = ConsistentHashRing(vnodes=150)
    ring.add_server("server-A")
    ring.add_server("server-B")
    ring.add_server("server-C")

    assert ring.ring_size == 450      # 3 * 150 vnodes
    assert ring.server_count == 3

    # All keys must be assigned
    for k in keys[:100]:
        assert ring.get_server(k) in {"server-A", "server-B", "server-C"}

    # Load distribution should be roughly uniform
    dist = ring.load_distribution(keys)
    print("Load distribution (3 servers, 150 vnodes):")
    for srv, cnt in sorted(dist.items()):
        print(f"  {srv}: {cnt} keys ({cnt/len(keys)*100:.1f}%)")

    # Stability: adding a server should remap ~1/4 of keys
    before = {k: ring.get_server(k) for k in keys}
    ring.add_server("server-D")
    after  = {k: ring.get_server(k) for k in keys}
    remapped = sum(1 for k in keys if before[k] != after[k])
    frac = remapped / len(keys)
    print(f"\nAdded server-D: {remapped} keys remapped ({frac*100:.1f}%), expected ~25%")
    assert 0.10 < frac < 0.45, f"Unexpected remapping fraction: {frac}"

    # Removal: keys from removed server reassigned to others, not lost
    ring.remove_server("server-B")
    for k in keys[:100]:
        assert ring.get_server(k) in {"server-A", "server-C", "server-D"}

    # Remapping comparison
    result = compare_remapping(
        keys,
        servers_before=["s0", "s1", "s2", "s3", "s4",
                        "s5", "s6", "s7", "s8", "s9"],
        servers_after= ["s0", "s1", "s2", "s3", "s4",
                        "s5", "s6", "s7", "s8", "s9", "s10"],  # +1 server
    )
    print(f"\nRemapping comparison (10→11 servers, {result['total_keys']} keys):")
    print(f"  Modulo hashing:     {result['modulo_remapped']} keys "
          f"({result['modulo_fraction']*100:.1f}%) remapped")
    print(f"  Consistent hashing: {result['consistent_remapped']} keys "
          f"({result['consistent_fraction']*100:.1f}%) remapped")
    print(f"  Theoretical minimum: ~{result['expected_consistent']*100:.1f}%")

    # Consistent hashing must remap far fewer keys than modulo
    assert result["consistent_fraction"] < result["modulo_fraction"] * 0.5

    print("\nAll tests passed.")
```

```
    S2 ────┤ pos=4800
           │
   [S4]────┤ pos=5500    ← NEW server inserted between S2 and S3

    S4 now owns arc (S2_pos, S4_pos] = (4800, 5500]
    S3 now owns arc (S4_pos, S3_pos] = (5500, 7200]   ← SHRUNK

    Only keys with hashes in (4800, 5500] remigrate from S3 → S4.
    K1 (3000): still → S2  ✓  (unchanged)
    K2 (6000): still → S3  ✓  (unchanged)
    K3 (8000): still → S1  ✓  (unchanged)
```

### Virtual Nodes: Why Load Balance Needs Them

```
WITHOUT VIRTUAL NODES (3 servers, random ring positions):

    Physical positions chosen by hash of server name — highly non-uniform:
    S1 at 900,   S2 at 3100,  S3 at 9700   (out of 10000 max)

    Arc lengths:
    S1 owns: (9700, 900]  wrap  →  10000-9700 + 900  = 1200 units  (12%)
    S2 owns: (900, 3100]         →  2200 units                       (22%)
    S3 owns: (3100, 9700]        →  6600 units                       (66%)

    → S3 handles 66% of traffic! Severely imbalanced.

WITH VIRTUAL NODES (150 per server):

    Each server gets 150 hash positions spread across [0, 10000).
    By the law of large numbers, each server's total arc ≈ 1/3 of ring.

    S1: ~33.2%  ✓
    S2: ~33.5%  ✓
    S3: ~33.3%  ✓

    The more vnodes, the tighter the concentration around 1/k.
    Variance of load ∝ 1/v — doubling vnodes halves load variance.
```

### Modulo Hashing vs Consistent Hashing on Server Addition

```
MODULO HASHING: 10 servers → 11 servers

    Key assignment: server = hash(key) % n

    hash(K) = 1234:
      Before: 1234 % 10 = 4   → Server-4
      After:  1234 % 11 = 2   → Server-2   ← REMAPPED

    hash(K) = 5678:
      Before: 5678 % 10 = 8   → Server-8
      After:  5678 % 11 = 6   → Server-6   ← REMAPPED

    Expected remapped fraction:  1 - 10/11 ≈ 90.9%

CONSISTENT HASHING: 10 servers → 11 servers

    New server S10 inserted at its hash position on ring.
    Only keys in the arc (S10_predecessor, S10_position] remigrate.
    Arc length ≈ 1/11 of the ring.

    Expected remapped fraction:  ≈ 1/11 ≈ 9.1%

    ┌─────────────────────────────────────────────────────────┐
    │  10 servers → 11:  modulo remaps 90.9% of keys         │
    │                    consistent remaps  ~9.1% of keys     │
    │  Ratio: 10× fewer remaps with consistent hashing        │
    └─────────────────────────────────────────────────────────┘
```

## 7. Common Variations & Extensions

### 7.1 Rendezvous Hashing (Highest Random Weight)

An alternative to ring hashing. For each key K and each server S, compute `score(K, S) = hash(K + S)`. Assign K to the server with the highest score. When a server is removed, only its keys need reassignment — each finds the next-highest-scoring server. No ring data structure needed; O(k) per lookup (must score against all servers), but zero coordination overhead. Used in Varnish Cache and some CDN systems. Simpler to implement than ring hashing but O(k) vs O(log k) per lookup.

### 7.2 Jump Consistent Hash

A Google algorithm (2014) that maps a key to a server index in [0, k) using only arithmetic — no ring data structure at all. Produces perfectly uniform load distribution. Limitation: only supports adding servers at the _end_ (increment k by 1); cannot remove arbitrary servers or handle heterogeneous weights. Used in Google's internal storage systems where the cluster grows monotonically. O(log k) time, O(1) space.

### 7.3 Bounded Load Consistent Hashing

Standard consistent hashing can still create hot spots when keys are non-uniform (some keys are queried far more than others). Bounded-load hashing (Mirrokni et al., Google 2017) adds a constraint: no server handles more than `(1 + ε) * n/k` keys. When a key's assigned server is overloaded, it is redirected to the next server clockwise. Adds O(1) amortised overhead per lookup. Used in Google's load balancer.

### 7.4 Connection to Binary Search Patterns

The ring lookup is `lower_bound` on a circular sorted array — the same binary search template in [[56.lower_bound and upper_bound — first and last occurrence]]. For CP problems involving "assign each query point to its nearest clockwise neighbour on a circle of fixed points", reach for `lower_bound` on a sorted vector of server positions. The wrap-around is handled by taking `index % ring.size()`. This is consistent hashing reduced to its CP essence.

## 9. CP Contest Application

Consistent hashing itself is not a contest topic. However, the **binary search on a sorted circular structure** that underlies it appears in:

**Pattern:** "Given k fixed points on a circle [0, M), assign each of n query points to its clockwise successor among the fixed points."

```cpp
// CP implementation: binary search on sorted ring (no vnodes needed)
#include <algorithm>
#include <vector>
using ll = long long;

// fixed_points: sorted server positions on ring [0, M)
// query:        position to look up
// Returns index into fixed_points of the responsible server.
int ring_lookup(const std::vector<ll>& fixed_points, ll query) {
    // First fixed point with position >= query
    auto it = std::lower_bound(fixed_points.begin(), fixed_points.end(), query);
    if (it == fixed_points.end()) {
        return 0;  // wrap around to first server
    }
    return static_cast<int>(it - fixed_points.begin());
}
```

This template solves Codeforces problems involving circular interval ownership, rotating assignment problems, and "nearest clockwise point" queries — all in O(log k) per query after O(k log k) sorting.

**Time limit guidance:** For k ≤ 10⁶ fixed points and n ≤ 10⁶ queries, the binary search approach runs in O((n+k) log k) ≈ 4×10⁷ operations — comfortably within a 2s limit. For k·v ≤ 10⁷ (with virtual nodes), the same bound applies.
