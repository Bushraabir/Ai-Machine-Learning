# 08. Suffix Sum — and When to Use It Over Prefix Sum

> _"Prefix asks: what came before? Suffix asks: what's left?"_

---

## The Core Idea

A **suffix sum** at index $i$ is the sum of all elements from position $i$ to the end of the array.

$$S[i] = A[i] + A[i+1] + \cdots + A[n-1]$$

It is the mirror image of a prefix sum — instead of accumulating from the left, you accumulate from the right.

```
Array:        A = [3, 1, 4, 1, 5, 9, 2, 6]
Index:             0  1  2  3  4  5  6  7

Prefix P[i] = sum of A[0..i-1]     (left → right)
P =           [0, 3, 4, 8, 9, 14, 23, 25, 31]

Suffix S[i] = sum of A[i..n-1]     (right → left)
S =           [31, 28, 27, 23, 22, 17, 8, 6]
```

Notice: `P[n] == S[0] == total sum`. They both equal the grand total — just approached from opposite ends.

---

## Building the Suffix Sum Table

### Definition (0-indexed)

$$S[i] = \sum_{k=i}^{n-1} A[k]$$

With the convention $S[n] = 0$ (empty suffix, just like $P[0] = 0$ for prefix).

### The Recurrence

$$S[i] = A[i] + S[i+1]$$

Read it: "the suffix starting at $i$ is the current element plus the suffix starting at $i+1$."

You fill it **right to left**, starting from the base case $S[n] = 0$.

```python
def build_suffix(A):
    n = len(A)
    S = [0] * (n + 1)          # S[n] = 0 by convention
    for i in range(n - 1, -1, -1):
        S[i] = A[i] + S[i + 1]
    return S

# NumPy vectorised version
import numpy as np

def build_suffix_np(A):
    A = np.array(A, dtype=np.int64)
    return np.concatenate(([0], np.cumsum(A[::-1])[::-1]))
    # cumsum on the reversed array, then reverse back, prepend 0

A = [3, 1, 4, 1, 5, 9, 2, 6]
S = build_suffix_np(A)
# S = [31, 28, 27, 23, 22, 17, 8, 6, 0]
```

> The NumPy trick: reverse the array, take `cumsum`, reverse again. This gives $S[0], S[1], \ldots, S[n-1]$. Append 0 at the end for the sentinel.

## Querying a Range with Suffix Sum

Like prefix sums, you can answer range sum queries using suffix sums:

$$\text{sum}(A[i \ldots j]) = S[i] - S[j+1]$$

Compare to the prefix formula: $\text{sum}(A[i \ldots j]) = P[j+1] - P[i]$.

Both work. The choice of which to build depends on the _type of query_, not just range queries — more on this below.

```python
def query_suffix(S, i, j):
    return S[i] - S[j + 1]

# sum of A[2..5] = 4+1+5+9 = 19
print(query_suffix(S, 2, 5))   # 19 ✓
```

## Prefix vs Suffix — The Mental Model

Think of them as answering different natural questions:

|Question structure|Use|
|---|---|
|"How much has accumulated up to position $i$?"|Prefix sum|
|"How much remains from position $i$ onwards?"|Suffix sum|
|"What is the sum from $i$ to $j$?"|Either (both give $O(1)$)|
|"What is the total minus what came before $i$?"|Suffix: $S[i] = \text{total} - P[i]$|
|"What is the total minus what remains after $i$?"|Prefix: $P[i+1] = \text{total} - S[i+1]$|

**The relationship:**

$$S[i] = P[n] - P[i] \qquad \text{and} \qquad P[i] = P[n] - S[i]$$

Where $P[n] = S[0] = \text{total sum}$.

So technically, you can always convert one into the other. But **the natural direction of reasoning** matters enormously for code clarity and correctness.

---

## When to Prefer Suffix Sum Over Prefix Sum

This is the key question. Here are the four concrete scenarios:

### Scenario 1 — You process or iterate right-to-left

If your algorithm naturally scans from right to left (e.g., you're looking at "what's left after this point"), build a suffix table. Forcing a prefix table here means constantly computing `total - P[i]`, which adds cognitive load and introduces off-by-one error risk.

```python
# How many elements to the right of i are positive?
# Easier with suffix count table built right-to-left
```

### Scenario 2 — "Cost of choosing position $i$" = sum of remaining elements

Classic example: you're partitioning an array at some index. The cost of the left part is naturally a prefix sum; the cost of the right part is naturally a suffix sum. You want **both tables simultaneously**.

```python
# Find the index i that minimises |prefix_sum[i] - suffix_sum[i+1]|
# (balancing the array around a pivot)

def best_pivot(A):
    n = len(A)
    P = build_prefix(A)    # P[i] = sum of A[0..i-1]
    S = build_suffix(A)    # S[i] = sum of A[i..n-1]
    best_i, best_diff = 0, float('inf')
    for i in range(n):
        diff = abs(P[i] - S[i])
        if diff < best_diff:
            best_diff, best_i = diff, i
    return best_i
```

This pattern — **prefix + suffix simultaneously** — is extremely common in competitive programming and ML preprocessing. You could do it with prefix alone, but having both tables makes the code read exactly like the problem statement.

### Scenario 3 — You only need suffix queries, never prefix

If every query in your problem is of the form "sum from $i$ to end", build only the suffix table. No reason to build a prefix table that you'll never use. This is an engineering clarity argument, not a performance one.

### Scenario 4 — The problem is defined in terms of "remaining" semantics

Some problems are stated inherently in suffix terms:

- "For each shop, what is the total demand still to be served after this shop?" → suffix sum of demands.
- "For each character in a string, how many characters of this type appear later?" → suffix count.
- "After processing token $i$ in a sequence, how much total score remains?" → suffix score.

In all these cases, forcing prefix framing requires subtracting from the total at every step. Use the suffix; the code will match the problem.

## Concrete Problem — Equal Partition

> Given array `A`, find an index `i` such that the sum of elements to the left equals the sum to the right.

This is **LeetCode 724** and a classic interview problem. It is the canonical example where you _need_ both prefix and suffix — or equivalently, prefix and total sum.

```python
def pivot_index(A):
    total = sum(A)
    left_sum = 0
    for i, v in enumerate(A):
        # right_sum = total - left_sum - A[i]
        if left_sum == total - left_sum - v:
            return i
        left_sum += v
    return -1
```

The trick `total - left_sum - A[i]` is computing the suffix sum on the fly without building the table. But if you need to answer multiple such queries, or the computation is more complex, you build both tables.

```python
def pivot_index_tables(A):
    P = build_prefix(A)
    S = build_suffix(A)
    n = len(A)
    for i in range(n):
        if P[i] == S[i + 1]:    # left == right
            return i
    return -1
```

The two-table version reads exactly like the problem statement: _left sum at $i$_ equals _right sum at $i$_. Perfect clarity.

## 2D Suffix Sum

Just as prefix sums extend to 2D (see [[07.2D prefix sum]]), so do suffix sums.

$$S2[i][j] = \sum_{r \geq i} \sum_{c \geq j} A[r][c]$$

The recurrence (fill from bottom-right to top-left):

$$S2[i][j] = A[i][j] + S2[i+1][j] + S2[i][j+1] - S2[i+1][j+1]$$

Notice it uses the **same inclusion-exclusion** as the 2D prefix sum — just mirrored. You subtract the bottom-right corner that gets double-counted.

```python
def build_2d_suffix(A):
    A = np.array(A, dtype=np.int64)
    N, M = A.shape
    S = np.zeros((N + 1, M + 1), dtype=np.int64)
    S[:N, :M] = A
    # Two reversed cumulative sums
    S = S[::-1, :].cumsum(axis=0)[::-1, :]
    S = S[:, ::-1].cumsum(axis=1)[:, ::-1]
    return S

# Query: sum of A[r1..r2, c1..c2]
def query_2d_suffix(S, r1, c1, r2, c2):
    return S[r1][c1] - S[r2+1][c1] - S[r1][c2+1] + S[r2+1][c2+1]
```

**When do you actually use 2D suffix sums?** When the natural question is "sum of the bottom-right rectangle starting at $(i,j)$" — e.g., "how many events remain after time $i$ and position $j$?" or complement-based queries on 2D grids. In practice this is rarer than 2D prefix, but the pattern is identical.

---

## Proof of the Suffix Recurrence

**Claim:** $S[i] = A[i] + S[i+1]$

**Proof:** By definition,

$$S[i] = \sum_{k=i}^{n-1} A[k] = A[i] + \sum_{k=i+1}^{n-1} A[k] = A[i] + S[i+1] \qquad \blacksquare$$

The base case $S[n] = \sum_{k=n}^{n-1} A[k] = 0$ (empty sum). $\blacksquare$

## Common Mistakes

```python
# Mistake 1: filling left-to-right instead of right-to-left
# WRONG
S = [0] * (n + 1)
for i in range(n):
    S[i] = A[i] + S[i - 1]   # This builds a prefix, not a suffix!

# CORRECT
S = [0] * (n + 1)
for i in range(n - 1, -1, -1):
    S[i] = A[i] + S[i + 1]

# Mistake 2: off-by-one in range query
# sum of A[i..j]
wrong  = S[i] - S[j]       # excludes A[j]!
correct = S[i] - S[j + 1]  # includes A[j] ✓

# Mistake 3: not using S[n] = 0 sentinel
# If you build S of length n (not n+1), querying S[n] crashes.
# Always allocate n+1 slots and set S[n] = 0.

# Mistake 4: using suffix when prefix is more natural
# If you keep writing "total - S[i]", you probably want a prefix table.
# The formula total - S[i] = P[i], so just build P.
```

## Complexity

|Operation|Time|Space|
|---|---|---|
|Build suffix table|$O(n)$|$O(n)$|
|Single range query|$O(1)$|—|
|$Q$ queries|$O(n + Q)$|$O(n)$|

Identical to prefix sum — the only difference is the direction of accumulation.

## Decision Guide — Prefix or Suffix?

```
Does the query ask about "what came before i"?
    → Prefix

Does the query ask about "what remains from i onwards"?
    → Suffix

Does the algorithm need both simultaneously (partition / balance)?
    → Build both tables

Is the problem stated as "total minus prefix"?
    → Use suffix directly (avoid the subtraction at every step)

Are you iterating right-to-left?
    → Suffix (fills naturally in that direction)

Can you derive one from the other?
    → Yes: S[i] = total - P[i]
    → But clarity and error-resistance favour the natural choice
```

## Full Working Example

```python
import numpy as np

def build_prefix(A):
    A = np.array(A, dtype=np.int64)
    P = np.zeros(len(A) + 1, dtype=np.int64)
    P[1:] = np.cumsum(A)
    return P

def build_suffix(A):
    A = np.array(A, dtype=np.int64)
    S = np.zeros(len(A) + 1, dtype=np.int64)
    S[:-1] = np.cumsum(A[::-1])[::-1]
    return S

A = [3, 1, 4, 1, 5, 9, 2, 6]
P = build_prefix(A)
S = build_suffix(A)

print("P:", P)   # [ 0  3  4  8  9 14 23 25 31]
print("S:", S)   # [31 28 27 23 22 17  8  6  0]

# Range sum A[2..5]
print(P[6] - P[2])   # 19  (prefix method)
print(S[2] - S[6])   # 19  (suffix method)

# Find pivot index (sum left == sum right)
for i in range(len(A)):
    if P[i] == S[i + 1]:
        print(f"Pivot at index {i}")
        break
```

## Connection to AI / ML / Deep Learning

**Sequence modelling and attention masks:** When building causal masks in Transformers (where token $i$ can only attend to positions $\leq i$), the complement — "positions not yet seen" — is a suffix structure. The cumulative attention budget from each position to the end of the context window is a suffix sum.

**Dynamic programming on sequences:** Many DP optimisations (e.g., "minimum cost to split array into $k$ parts") use both a prefix and a suffix DP table. The suffix table captures "optimal cost from position $i$ to end", which is computed right-to-left — identical to a suffix sum conceptually, just with a `min` or `max` aggregation instead of `+`.

**Loss weighting in sequence-to-sequence models:** When you weight the loss of each predicted token by "how many tokens remain to predict", you need a suffix count. This shows up in scheduled sampling and curriculum learning strategies.

**Suffix sums over reward sequences (reinforcement learning):** The return $G_t$ at timestep $t$ in RL is defined as:

$$G_t = R_t + \gamma R_{t+1} + \gamma^2 R_{t+2} + \cdots = \sum_{k=0}^{T-t} \gamma^k R_{t+k}$$

This is a **discounted suffix sum** of rewards, computed right-to-left:

```python
def compute_returns(rewards, gamma=0.99):
    """Standard RL return computation — a discounted suffix sum."""
    n = len(rewards)
    G = np.zeros(n)
    G[-1] = rewards[-1]
    for t in range(n - 2, -1, -1):
        G[t] = rewards[t] + gamma * G[t + 1]
    return G
```

This is **exactly the suffix sum recurrence** $S[i] = A[i] + \lambda \cdot S[i+1]$ with $\lambda = \gamma$. Every RL implementation you ever write will use this pattern. The connection is not accidental — the Bellman equation _is_ a suffix recurrence.

## Summary

||Prefix Sum|Suffix Sum|
|---|---|---|
|Accumulates|Left → right|Right → left|
|$P[i]$ means|Sum of $A[0..i-1]$|Sum of $A[i..n-1]$|
|Base case|$P[0] = 0$|$S[n] = 0$|
|Recurrence|$P[i] = P[i-1] + A[i-1]$|$S[i] = A[i] + S[i+1]$|
|Range query|$P[j+1] - P[i]$|$S[i] - S[j+1]$|
|Natural question|"How much before $i$?"|"How much from $i$ onwards?"|
|RL connection|Cumulative reward so far|Discounted return $G_t$|
|Prefer when|Processing left-to-right|Processing right-to-left|

**The deepest insight:** Prefix and suffix sums are not two different data structures. They are the same idea — linear precomputation for $O(1)$ range queries — applied in two directions. Choose the direction that makes your code read like the problem statement. If you're writing `total - prefix[i]` everywhere, flip to a suffix table.
