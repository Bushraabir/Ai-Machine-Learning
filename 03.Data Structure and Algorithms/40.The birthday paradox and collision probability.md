## 1. Intuition First

### The Core Idea

Here is the question that surprises nearly everyone the first time: **How many people do you need in a room before the probability that two of them share a birthday exceeds 50%?**

The intuitive answer is somewhere around 183 — half of 365. The correct answer is **23**.

This gap between intuition and reality is the birthday paradox, and understanding _why_ the gap exists is one of the most practically important insights in probability theory for engineers.

The reason intuition fails: we instinctively think about the probability that _someone specific_ shares a birthday with _us_. That probability is indeed low — about 1/365 per person. But the question is about _any_ pair among all people in the room. With 23 people, there are C(23,2) = **253 pairs**. Each pair has a 1/365 chance of matching. 253 independent chances at a 1/365 event is quite likely to produce at least one hit.

More precisely: let n be the number of people, d = 365 be the number of days. The probability that **no** two people share a birthday (all birthdays distinct) is:

$$P(\text{no collision}) = \frac{d}{d} \cdot \frac{d-1}{d} \cdot \frac{d-2}{d} \cdots \frac{d-n+1}{d} = \prod_{k=0}^{n-1} \frac{d-k}{d}$$

The complementary probability — that at least one collision exists — exceeds 0.5 when n ≈ √(2d ln 2) ≈ **1.177√d**.

For d = 365: n ≈ 1.177 × √365 ≈ **22.5**, confirming 23.

### Why This Exists — The Complexity Gap

The naive mental model is linear: to have a 50% chance of a collision, you need ~d/2 samples. The correct answer is ~√d. This is a **quadratic gap** — for a hash table with d = 2³² ≈ 4 billion buckets, you expect a collision after only ~65,000 insertions, not 2 billion.

This gap is catastrophic for security systems (birthday attacks on hash functions), surprising for data engineers (hash collisions in pipelines far earlier than expected), and essential for algorithm designers (why universal hashing guarantees are tight).

### The "Aha" Moment

The number of _pairs_ grows as O(n²), while the table size is d. A collision becomes likely when the number of pairs approaches d — i.e., when n² ≈ d, so n ≈ √d. **The collision threshold is the square root of the space.** This single sentence explains birthday attacks, why k-independent hash families are constructed the way they are, and why cryptographic hash outputs need to be at least 256 bits to resist 2^128-strength attacks.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**When it appears:**

The birthday paradox surfaces in two distinct CP contexts:

1. **Hashing-based solutions that must prove correctness.** When you use a rolling hash or polynomial hash to compare strings or sequences, the probability of a false positive (two different strings hashing to the same value) is the birthday collision probability. For a hash modulus M and n strings, the expected number of false collisions is O(n²/M). Choosing M = 10⁹+7 with n = 10⁵ gives ~10¹⁰/10⁹ ≈ 10 expected false positives — dangerous. This is why experienced CP contestants use **double hashing** (two independent moduli) or a 64-bit hash (reducing false positive rate to ~n²/2⁶⁴ ≈ 10⁻⁹).
    
2. **Probability/expected value problems.** Problems that ask "expected number of draws before a repeat" or "probability that all n coupons are distinct" are birthday-paradox calculations in disguise.
    

**Pattern signal:** Whenever your solution generates random identifiers, hashes keys into a table, or checks equality via hashing, ask: _"How many items am I hashing into a space of size M?"_ If n > √M, your false-positive rate is non-negligible.

**Common trap — the double-hash false sense of security:** Using two hashes with moduli p₁ and p₂ gives effective space p₁·p₂. But both must be independent and large. Using `(hash1, hash2)` where hash2 is just `hash1 + salt` does not give independence — the effective space is not p₁·p₂.

**Specific Codeforces pattern:** String matching problems where the editorial says "use hashing" — the correct implementation requires choosing a random base and a large prime to push the collision probability below 1/n.

---

### Machine Learning / AI

**Where it appears — five concrete locations:**

1. **SHA-256 in model checkpointing / dataset fingerprinting.** Git and DVC use SHA-1/SHA-256 to fingerprint model checkpoints and dataset versions. The birthday bound tells you when you need to worry: SHA-1 produces 160-bit digests. With n objects, collision probability ≈ n²/2¹⁶⁰. Even with 10¹² objects, P ≈ 10⁻²⁴. Safe. But SHA-1 has _structural weaknesses_ that reduce effective bits — which is why Git migrated to SHA-256.
    
2. **Feature hashing (the hashing trick) in scikit-learn / Vowpal Wabbit.** `sklearn.feature_extraction.text.HashingVectorizer` maps text features to a fixed-size vector of dimension m using a hash function. Two different features that hash to the same bucket create a **feature collision** — the model cannot distinguish them. With n distinct features and m buckets, the expected number of collisions is n²/(2m) (birthday bound). The default m = 2²⁰ ≈ 10⁶. For NLP tasks with n ~ 10⁵ features, this gives ~5 expected collisions — acceptable. For n ~ 10⁷ features (large-scale NLP), increase m to 2²⁵ or higher.
    
3. **Random seed collisions in data augmentation.** When spawning n parallel data loader workers each seeded with `worker_id`, different workers may reach the same random state through birthday-paradox dynamics if the seed space is small. PyTorch's `worker_init_fn` documentation warns about this explicitly.
    
4. **LSH bucket collisions.** In [[39.MinHash — estimating Jaccard similarity at scale]], the banding step hashes band values into buckets. The expected number of _false_ bucket collisions (unrelated documents landing in the same bucket) is a birthday calculation: with n documents and B buckets, expect n²/(2B) false collisions. This directly informs how to size the hash table in `datasketch.MinHashLSH`.
    
5. **UUIDs for experiment tracking (MLflow, Weights & Biases).** 128-bit UUIDs. Birthday threshold: collisions expected after ~2⁶⁴ ≈ 10¹⁹ experiments. Safe for any conceivable ML workload.
    

**How this makes you write better ML code:** When you see `hash(key) % table_size` in a caching layer, feature store, or embedding lookup, you immediately ask: _"How many distinct keys, and how large is table_size?"_ If keys² > table_size, you have a collision problem that will silently corrupt outputs.

## 3. Algorithm / Pattern

### The Exact Formula

The probability that n items drawn uniformly from {1, ..., d} are **all distinct**:

$$P(\text{no collision} \mid n, d) = \prod_{k=0}^{n-1}\left(1 - \frac{k}{d}\right) = \frac{d!}{(d-n)! \cdot d^n}$$

The probability of **at least one collision**:

$$P(\text{collision} \mid n, d) = 1 - \prod_{k=0}^{n-1}\left(1 - \frac{k}{d}\right)$$

### The Approximation (far more useful)

Using ln(1 - x) ≈ -x for small x:

$$\ln P(\text{no collision}) = \sum_{k=0}^{n-1} \ln\left(1 - \frac{k}{d}\right) \approx -\sum_{k=0}^{n-1} \frac{k}{d} = -\frac{n(n-1)}{2d} \approx -\frac{n^2}{2d}$$

Therefore:

$$P(\text{no collision}) \approx e^{-n^2 / (2d)}$$

$$P(\text{collision}) \approx 1 - e^{-n^2 / (2d)}$$

Setting P(collision) = 0.5:

$$e^{-n^2/(2d)} = 0.5 \implies n^2 = 2d\ln 2 \implies \boxed{n \approx 1.177\sqrt{d}}$$

### Expected Number of Collisions

The expected number of _colliding pairs_ (linearity of expectation):

$$E[\text{collisions}] = \binom{n}{2} \cdot \frac{1}{d} \approx \frac{n^2}{2d}$$

This is the most useful formula for engineers: given n items in a table of size d, expect n²/(2d) collisions. When this exceeds 1, collisions are routine. When it exceeds n, the table is critically overloaded.

### Decision Tree

```
Need to reason about hash collisions?
│
├─ "How many items before first collision is likely?"
│   └─ n ≈ 1.177 · √d   (birthday threshold)
│
├─ "Expected number of collisions given n items in table of size d?"
│   └─ E[collisions] ≈ n² / (2d)
│
├─ "Probability that all n items are collision-free?"
│   └─ P ≈ exp(-n² / 2d)
│
├─ "What table size d do I need for P(collision) < ε with n items?"
│   └─ d > n² / (2 · ln(1/(1-ε)))  ≈  n² / (2ε) for small ε
│
└─ "Is my hash function safe against birthday attacks?"
    └─ Need output bits b such that 2^(b/2) >> expected_queries
       For 128-bit security: need b ≥ 256 bits
```

### Complexity

Computing P(collision) exactly: O(n) multiplications.  
Computing E[collisions]: O(1) with the formula n²/(2d).  
Finding the collision threshold: O(1) with n ≈ 1.177√d.

## 4. Pseudocode

```
Algorithm: Exact Birthday Collision Probability
Input:  n (number of items drawn), d (hash space size)
Output: P(at least one collision)

  // Use log-space to avoid underflow for large n, d
  log_p_no_collision ← 0.0

  for k = 0 to n-1:
      // Probability that k-th item doesn't match any previous k items
      log_p_no_collision += log(1 - k/d)

  p_no_collision ← exp(log_p_no_collision)
  return 1 - p_no_collision


Algorithm: Find Minimum n for P(collision) ≥ target
Input:  d (space size), target (e.g., 0.5)
Output: Smallest n such that P(collision) ≥ target

  // Use approximation: n ≈ sqrt(-2d · ln(1 - target))
  n_approx ← ceil(sqrt(-2 * d * log(1 - target)))

  // Refine by scanning near the approximation
  n ← max(1, n_approx - 2)
  while exact_collision_prob(n, d) < target:
      n ← n + 1

  return n


Algorithm: Expected Collisions (O(1) approximation)
Input:  n (items), d (table size)
Output: Expected number of colliding pairs

  // From linearity of expectation over C(n,2) pairs
  return n * (n - 1) / (2 * d)


Algorithm: Minimum Table Size for Safety
Input:  n (items), epsilon (max acceptable collision probability)
Output: Minimum d such that P(collision) ≤ epsilon

  // Invert: exp(-n^2 / 2d) ≥ 1 - epsilon
  // => n^2 / 2d ≤ -ln(1-epsilon) ≈ epsilon  (for small epsilon)
  // => d ≥ n^2 / (2 * epsilon)
  return ceil(n * n / (2 * epsilon))
```

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <cmath>
#include <cstdint>
#include <iostream>
#include <stdexcept>
#include <vector>

// ============================================================
// Birthday Paradox — Collision Probability Analysis
// ============================================================

namespace birthday {

// Exact P(at least one collision) for n items in space of size d.
// Uses log-space arithmetic to avoid floating-point underflow.
// Time: O(n). Numerically stable for d up to ~10^15, n up to ~10^6.
//
// Note: d is passed as double to handle hash spaces > 2^63.
// For cryptographic hash spaces (d = 2^256), use the approximation below.
double exact_collision_prob(uint64_t n, double d) {
    if (n <= 1) return 0.0;
    if (static_cast<double>(n) > d) return 1.0;  // Pigeonhole: guaranteed collision

    double log_p_no_collision = 0.0;
    for (uint64_t k = 1; k < n; ++k) {
        log_p_no_collision += std::log(1.0 - static_cast<double>(k) / d);
        // Early exit: once p_no_collision < 1e-15, it rounds to 0
        if (log_p_no_collision < -34.5) return 1.0;
    }
    return 1.0 - std::exp(log_p_no_collision);
}

// Fast approximation: P(collision) ≈ 1 - exp(-n*(n-1) / (2*d))
// Accurate to within 1% when n ≪ d (which is always the useful regime).
double approx_collision_prob(double n, double d) {
    return 1.0 - std::exp(-n * (n - 1.0) / (2.0 * d));
}

// Expected number of colliding pairs: C(n,2) / d = n*(n-1) / (2d)
// From linearity of expectation — exact, not approximate.
double expected_collisions(double n, double d) {
    return n * (n - 1.0) / (2.0 * d);
}

// Minimum n such that P(collision) ≥ target_prob.
// Uses closed-form approximation, then refines exactly.
uint64_t threshold_n(double d, double target_prob = 0.5) {
    if (target_prob <= 0.0 || target_prob >= 1.0)
        throw std::domain_error("target_prob must be in (0, 1)");

    // Approximation: n ≈ sqrt(-2d * ln(1 - target_prob))
    uint64_t n = static_cast<uint64_t>(
        std::ceil(std::sqrt(-2.0 * d * std::log(1.0 - target_prob)))
    );

    // Walk back to start of refinement
    if (n > 2) n -= 2;

    // Refine upward
    while (exact_collision_prob(n, d) < target_prob) ++n;
    return n;
}

// Minimum hash space size d so that P(collision) ≤ epsilon with n items.
// Derived from: exp(-n^2 / 2d) ≥ 1 - epsilon => d ≥ -n^2 / (2 ln(1-epsilon))
double min_space_for_safety(double n, double epsilon) {
    if (epsilon <= 0.0 || epsilon >= 1.0)
        throw std::domain_error("epsilon must be in (0, 1)");
    return -n * n / (2.0 * std::log(1.0 - epsilon));
}

// Number of hash output bits needed to resist a birthday attack
// where an adversary makes q queries and we want P(collision) ≤ epsilon.
// q^2 / 2^b ≤ epsilon  =>  b ≥ 2 * log2(q / sqrt(epsilon))
double bits_for_collision_resistance(double q, double epsilon = 1e-6) {
    return 2.0 * std::log2(q / std::sqrt(epsilon));
}

} // namespace birthday


// ============================================================
// Demonstration
// ============================================================
int main() {
    // Classic birthday problem: d = 365 days
    double d = 365.0;
    std::cout << "=== Birthday Problem (d=365) ===\n";
    for (uint64_t n : {10u, 23u, 30u, 50u, 70u}) {
        double p = birthday::exact_collision_prob(n, d);
        std::cout << "n=" << n << ": P(collision) = " << p << "\n";
    }
    std::cout << "50% threshold at n = " << birthday::threshold_n(d, 0.5) << "\n\n";

    // Hash table with 32-bit keys (d = 2^32)
    double d32 = std::pow(2.0, 32);
    std::cout << "=== 32-bit hash space (d=2^32 ≈ 4.3B) ===\n";
    std::cout << "50% threshold at n = "
              << birthday::threshold_n(d32, 0.5) << " (~77k)\n";
    std::cout << "E[collisions] for n=10^5: "
              << birthday::expected_collisions(1e5, d32) << "\n";
    std::cout << "Min space for n=10^6, epsilon=0.01: "
              << birthday::min_space_for_safety(1e6, 0.01) << "\n\n";

    // Security: how many bits for 2^64 queries with epsilon=10^-6?
    std::cout << "=== Cryptographic Security ===\n";
    double q = std::pow(2.0, 64);
    std::cout << "Bits needed for 2^64-query resistance (eps=1e-6): "
              << birthday::bits_for_collision_resistance(q, 1e-6) << "\n";
    // Answer: ~148 bits. SHA-256 (256 bits) provides 128-bit birthday security. ✓

    return 0;
}
```

### Python (Readable + Pythonic)

```python
"""
Birthday Paradox — Collision Probability Analysis

Core results:
  P(collision | n, d) ≈ 1 - exp(-n² / 2d)
  Threshold n for 50% collision: n ≈ 1.177 * sqrt(d)
  E[collisions] = n*(n-1) / (2d)  [exact, from linearity of expectation]

All functions handle large d (e.g., 2^256) via log-space or direct formula.
"""

from __future__ import annotations
import math
from typing import Generator


def exact_collision_prob(n: int, d: float) -> float:
    """
    P(at least one collision) when n items are drawn uniformly from {1..d}.

    Uses log-space arithmetic for numerical stability.
    Exact result — not an approximation.

    Args:
        n: Number of items drawn.
        d: Size of the hash space (can be float for d > 2^63, e.g., 2**256).

    Returns:
        Float in [0.0, 1.0].
    """
    if n <= 1:
        return 0.0
    if n > d:
        return 1.0  # Pigeonhole: at least one collision is guaranteed

    log_p_no_collision = 0.0
    for k in range(1, n):
        log_p_no_collision += math.log(1.0 - k / d)
        if log_p_no_collision < -80:   # exp(-80) ≈ 0, treat as certain collision
            return 1.0

    return 1.0 - math.exp(log_p_no_collision)


def approx_collision_prob(n: float, d: float) -> float:
    """
    Fast approximation: P(collision) ≈ 1 - exp(-n(n-1) / 2d).

    Accurate to within 1% when n ≪ d. Use this for large d (e.g., crypto).
    """
    return 1.0 - math.exp(-n * (n - 1) / (2 * d))


def expected_collisions(n: float, d: float) -> float:
    """
    Expected number of colliding pairs: C(n,2) * (1/d) = n(n-1)/(2d).

    This is EXACT (not an approximation) — from linearity of expectation.
    A value > 1 means collisions are routine. A value > n means the table
    is critically overloaded.
    """
    return n * (n - 1) / (2 * d)


def threshold_n(d: float, target_prob: float = 0.5) -> int:
    """
    Minimum n such that P(at least one collision) >= target_prob.

    The '50% birthday threshold' is threshold_n(d, 0.5) ≈ 1.177 * sqrt(d).

    Uses closed-form approximation then exact refinement.
    """
    if not 0 < target_prob < 1:
        raise ValueError("target_prob must be in (0, 1)")

    # Closed-form starting point
    n = max(2, math.ceil(math.sqrt(-2 * d * math.log(1 - target_prob))) - 2)

    # Exact refinement (walks at most ~5 steps)
    while exact_collision_prob(n, d) < target_prob:
        n += 1
    return n


def min_space_for_safety(n: float, epsilon: float) -> float:
    """
    Minimum hash space d such that P(collision) <= epsilon with n items.

    Derived from: 1 - exp(-n^2/2d) <= epsilon
    =>  d >= -n^2 / (2 * ln(1-epsilon))
    """
    if not 0 < epsilon < 1:
        raise ValueError("epsilon must be in (0, 1)")
    return -n**2 / (2 * math.log(1 - epsilon))


def bits_for_birthday_resistance(q: float, epsilon: float = 1e-6) -> float:
    """
    Hash output bits needed so that P(collision) <= epsilon after q queries.

    q^2 / 2^b <= epsilon  =>  b >= 2*log2(q/sqrt(epsilon))

    Example: q=2^64 queries, epsilon=1e-6 => b >= ~148 bits.
    SHA-256 (256 bits) provides 128-bit birthday security (adversary needs 2^128 queries).
    """
    return 2 * math.log2(q / math.sqrt(epsilon))


def collision_table(d: float, ns: list[int] | None = None) -> None:
    """
    Print a table of collision probabilities for given d and various n.
    """
    if ns is None:
        # Sample n values from 0 to 3x the birthday threshold
        thresh = int(threshold_n(d, 0.5))
        ns = sorted(set(
            [1, 5, 10] +
            list(range(thresh - 5, thresh + 6)) +
            [thresh * 2, thresh * 3]
        ))
    print(f"{'n':>8}  {'P(collision)':>14}  {'E[collisions]':>15}  {'Approx':>10}")
    print("-" * 55)
    for n in ns:
        if n < 1: continue
        p_exact = exact_collision_prob(n, d)
        e_coll  = expected_collisions(n, d)
        p_approx = approx_collision_prob(n, d)
        print(f"{n:>8}  {p_exact:>14.6f}  {e_coll:>15.4f}  {p_approx:>10.6f}")


# ---------------------------------------------------------------------------
# Feature hashing collision analysis — practical ML use case
# ---------------------------------------------------------------------------

def feature_hash_collision_analysis(
    n_features: int,
    hash_dim: int,
    epsilon: float = 0.05
) -> dict:
    """
    Analyse collision risk in sklearn's HashingVectorizer.

    Args:
        n_features: Number of distinct input features (vocabulary size).
        hash_dim:   Hash space size (HashingVectorizer's n_features param).
        epsilon:    Acceptable collision probability.

    Returns:
        Dict with analysis results and recommendations.
    """
    e_coll  = expected_collisions(n_features, hash_dim)
    p_coll  = approx_collision_prob(n_features, hash_dim)
    safe_d  = min_space_for_safety(n_features, epsilon)
    safe_bits = math.ceil(math.log2(safe_d))

    return {
        "n_features":             n_features,
        "hash_dim":               hash_dim,
        "expected_collisions":    e_coll,
        "collision_probability":  p_coll,
        "is_safe":                p_coll <= epsilon,
        "recommended_hash_dim":   2 ** safe_bits,
        "recommended_bits":       safe_bits,
    }


# ---------------------------------------------------------------------------
# Demo
# ---------------------------------------------------------------------------

if __name__ == "__main__":
    print("=" * 55)
    print("Classic Birthday Problem (d=365 days)")
    print("=" * 55)
    collision_table(365.0, ns=[10, 15, 20, 22, 23, 25, 30, 40, 50, 70])
    print(f"\n50% threshold: n = {threshold_n(365, 0.5)}")

    print("\n" + "=" * 55)
    print("32-bit hash space (d = 2^32 ≈ 4.3 billion)")
    print("=" * 55)
    d32 = 2**32
    n_thresh = threshold_n(d32, 0.5)
    print(f"50% threshold: n = {n_thresh:,}  (≈ {n_thresh/1000:.1f}k)")
    print(f"E[collisions] for n=100,000: {expected_collisions(1e5, d32):.2f}")
    print(f"Min space for n=10^6, ε=1%: {min_space_for_safety(1e6, 0.01):.2e}")

    print("\n" + "=" * 55)
    print("Feature Hashing Collision Analysis (ML use case)")
    print("=" * 55)
    # sklearn HashingVectorizer default: hash_dim = 2^20
    result = feature_hash_collision_analysis(
        n_features=100_000,   # ~100k unique tokens (medium NLP task)
        hash_dim=2**20,       # sklearn default
    )
    for k, v in result.items():
        print(f"  {k:<28}: {v}")

    print("\n" + "=" * 55)
    print("Cryptographic Hash Security")
    print("=" * 55)
    for bits in [128, 160, 256]:
        d = 2.0 ** bits
        thresh = 2.0 ** (bits / 2)
        print(f"  SHA-{bits}: 50% collision after ~2^{bits//2} = {thresh:.1e} hashes")

    q = 2.0**64
    b = bits_for_birthday_resistance(q, epsilon=1e-6)
    print(f"\n  Bits needed for 2^64-query resistance (ε=10⁻⁶): {b:.1f}")
    print(f"  SHA-256 provides: {256/2:.0f}-bit birthday security ✓")
```

### Diagram 3: Security Bits — Birthday Attack on Hash Functions

```
Hash output: b bits  →  hash space d = 2^b

An adversary hashing q messages expects a collision when q ≈ √d = 2^(b/2).
This is the "birthday attack" — it halves the effective security level.

Security level:       b bits output → b/2 bits of birthday security

  b=128 bits (MD5):    50% collision after q ≈ 2^64  ← Feasible for state actors
  b=160 bits (SHA-1):  50% collision after q ≈ 2^80  ← Marginal, deprecated
  b=256 bits (SHA-256):50% collision after q ≈ 2^128 ← 128-bit security ✓
  b=512 bits (SHA-512):50% collision after q ≈ 2^256 ← 256-bit security ✓✓

  For a system claiming "128-bit security":
  → Need hash output ≥ 256 bits (birthday resistance at 2^128 queries)

  Feature hashing (32-bit):  50% collision after 2^16 ≈ 65k features
                              Safe for n < 10k, problematic for n > 100k

  Practical rule: if your hash is b bits, your effective collision
  resistance is 2^(b/2) operations — not 2^b.

  ┌──────────────────────────────────────────────────────┐
  │  b bits → b/2 bits of security (birthday halving)   │
  │  Want k bits of security → need 2k bits of output   │
  └──────────────────────────────────────────────────────┘
```

## 7. Common Variations & Extensions

### Variation 1: The Coupon Collector Problem

The birthday paradox asks: "When does the first collision happen?" The **coupon collector** problem asks the dual question: "When have I seen _all_ d outcomes at least once?"

Expected draws to collect all d coupons: $E[T] = d \cdot H_d \approx d \ln d + \gamma d$ where $H_d$ is the d-th harmonic number and $\gamma \approx 0.5772$ is the Euler–Mascheroni constant.

For d = 365: E[T] ≈ 365 · ln(365) ≈ 2153 days — nearly 6 years to see every birthday.

**ML connection:** How many training examples do you need before every class appears at least once? For C classes with uniform distribution: E[examples] ≈ C·ln(C). For imbalanced classes, this is a much harder problem — see stratified sampling in [[218.Sampling strategies — uniform, stratified, importance sampling]].

### Variation 2: Near-Collision and the Distance Birthday Problem

Instead of exact collisions (h(a) = h(b)), what if we ask for _near-collisions_ — pairs where |h(a) - h(b)| ≤ r? The threshold shifts to n ≈ √(d/r). This is the foundation of **locality-sensitive hashing** — tuning r controls the similarity threshold. See [[38.Locality-sensitive hashing (LSH) — approximate nearest neighbour]].

### Variation 3: Double Hashing and Its Limits

To reduce collision probability, use two independent hash functions (h₁, h₂) and declare a collision only if _both_ match. The effective space is d₁·d₂. For two 32-bit hashes: effective space = 2⁶⁴, threshold ≈ 2³². For two 64-bit hashes: threshold ≈ 2⁶⁴ — safe for essentially all applications.

**The trap:** h₂(x) = h₁(x) XOR seed is **not** independent of h₁ — an adversary who can craft inputs to collide in h₁ can often craft inputs that also collide in h₂. True independence requires independently parameterised hash families.

### Variation 4: Non-Uniform Distributions Worsen Everything

All results above assume **uniform** draw from {1..d}. If the distribution is skewed (some keys much more frequent), collisions happen earlier. The birthday threshold under non-uniform distribution p = (p₁, ..., p_d) is governed by $\sum_i p_i^2$ — the **collision probability** of the distribution. Uniform gives $\sum p_i^2 = 1/d$ (minimum). Any deviation increases it, lowering the effective d.

**ML relevance:** Real-world feature distributions are heavily skewed (Zipfian). Feature hashing into m buckets with a skewed vocabulary will see more collisions than the uniform birthday bound predicts. This is why high-frequency features should be preserved as explicit one-hot features outside the hash, not mixed into the hash bucket.

## 9. CP Contest Application

**Codeforces / AtCoder problem types:**

1. **String hashing correctness (very common):** Any solution using polynomial rolling hash must defend against anti-hash tests (adversarial inputs that cause collisions). In Codeforces rounds, a weak hash (single mod ~10⁹) on string comparison problems is a common hack target. The birthday bound tells you: with n = 10⁵ strings, single hash gives E[false collisions] ≈ (10⁵)²/(10⁹) = 10. **Fix:** double hash with two moduli (~10⁹+7 and ~10⁹+9), giving E[false] ≈ 10¹⁰/10¹⁸ = 10⁻⁸.
    
2. **Expected value problems:** Problems of the form "expected number of draws before a repeat in array of size d" — direct birthday calculation. Typically appears as sub-problems in probability-themed Div. 2 D/E problems.
    
3. **Anti-hash test construction (meta-skill):** Knowing the birthday bound helps you _construct_ inputs that break opponents' weak hash solutions. With d = 10⁹+7, a birthday attack needs ~44,000 random strings to likely find a collision. Generating these is feasible.
    

**Time limit relevance:** The exact_collision_prob function is O(n) — trivially fast. The relevant constraint is that your hash-based solution must not TLE due to collision-induced worst-case chain length in chaining-based hash tables. If adversarial inputs are possible, use `std::unordered_map` with a custom hash (splitmix64) to randomise the hash function and break anti-hash tests.

**Splitmix64 — the standard CP anti-hack hash:**

```cpp
struct custom_hash {
    static uint64_t splitmix64(uint64_t x) {
        x += 0x9e3779b97f4a7c15;
        x = (x ^ (x >> 30)) * 0xbf58476d1ce4e5b9;
        x = (x ^ (x >> 27)) * 0x94d049bb133111eb;
        return x ^ (x >> 31);
    }
    size_t operator()(uint64_t x) const {
        static const uint64_t FIXED_RANDOM =
            chrono::steady_clock::now().time_since_epoch().count();
        return splitmix64(x + FIXED_RANDOM);
    }
};
// unordered_map<int, int, custom_hash> mp;
```

This randomises the hash at runtime, making it infeasible for adversaries to precompute collisions. The birthday bound still applies — but now to a _random_ hash function unknown to the adversary.
