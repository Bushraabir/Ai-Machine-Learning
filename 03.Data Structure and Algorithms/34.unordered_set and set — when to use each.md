## 1. Intuition First

### The Core Idea

Both `set` and `unordered_set` solve the same logical problem: maintaining a collection of _unique_ elements with fast membership queries. The difference is entirely in _how_ they organise memory internally — and that choice cascades into wildly different performance profiles.

Think of a **library catalogue** as the analogy. If you need to find any book _instantly_ and you don't care what order the shelves are in, you use a hash-indexed filing system — every book has a code, you compute a shelf number from the code and walk straight to it. That is `unordered_set`. But if you also need to answer questions like "give me all books published between 1950 and 1970" or "what is the next book after this one alphabetically," you need shelves organised in sorted order — even if each individual lookup is a little slower. That is `set`.

The deeper insight: **`set` is a balanced BST (Red-Black tree) in disguise; `unordered_set` is a hash table in disguise.** Every performance implication of each data structure applies directly.

### Why This Exists

The naive approach — a sorted `vector` with binary search — gives $O(\log n)$ lookups and $O(n)$ inserts. That $O(n)$ insert cost is why these specialised containers exist. Both offer $O(\log n)$ or better for all operations with no shifting of elements.

The critical complexity gap that motivates the split:

|Question asked|Best structure|Why naive vector fails|
|---|---|---|
|"Does X exist?" (membership)|`unordered_set`|Binary search on sorted vector is $O(\log n)$; hash is $O(1)$ amortised|
|"What is the smallest element ≥ X?"|`set`|Requires sorted order; hash table cannot answer this|
|"Iterate in sorted order"|`set`|Hash buckets are unordered by value|

### The "Aha" Moment

`unordered_set` wins on _point queries_ (does X exist?) by giving up _order information_. `set` preserves order at the cost of a constant multiplicative factor — every operation is $O(\log n)$ instead of $O(1)$. The entire decision reduces to: **do you ever need to exploit the sorted structure?** If yes, pay the $\log n$ overhead. If no, use the hash table and take $O(1)$ expected.

The second "aha": $O(1)$ expected hides a dangerous worst case. An adversary who knows your hash function can craft inputs that push every element into one bucket — degenerate to $O(n)$ per operation. `std::set` has no such vulnerability: its $O(\log n)$ is _guaranteed_, not just expected.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**When `unordered_set` appears:**

- Deduplication of a stream of values where you only need "seen before?" — e.g., finding duplicates in an array
- Membership testing in the inner loop of a BFS/DFS where the visited set is queried millions of times and speed matters
- Any problem where the set of values has no structure you need to exploit

**Pattern signal:** "Check if X has been seen" with a very high query count → `unordered_set`. The $O(1)$ vs $O(\log n)$ gap becomes meaningful above ~$10^6$ total operations.

**When `set` appears:**

- Problems requiring the _next greater element that exists in a collection_ — `lower_bound` / `upper_bound` on a `set` in $O(\log n)$ is the critical primitive here
- Maintaining a sorted window (the sliding window maximum variation using a multiset)
- Finding the $k$-th smallest element dynamically via `order_statistics_tree` (policy-based, built on the same structure)
- Interval problems where you query "does any stored interval overlap [a,b]?"

**Pattern signal:** "For each query, find the smallest stored value ≥ X" → `set::lower_bound`. This is irreplaceable; `unordered_set` cannot do it.

**Critical traps in CP:**

1. **Worst-case hash collision attack.** On Codeforces especially, judges sometimes craft anti-hash tests. `unordered_set<int>` with the default hash can be hacked. Fix: use a custom hash (e.g., splitmix64) or use `set` when $O(\log n)$ is acceptable. This is a real source of runtime errors on otherwise correct solutions.
    
2. **`unordered_set` constant factor.** Despite $O(1)$ amortised complexity, the hidden constant is large — pointer chasing into hash buckets is cache-unfriendly. In tight time limits, a `set` with $O(\log n)$ but excellent cache behaviour can be faster for small $n$ (roughly $n < 10^4$).
    
3. **`multiset` is not `set`.** If you need to store multiple copies of the same value, you need `multiset`. `set` silently deduplicates — inserting 3 into `{1,2,3}` does nothing.
    

### Machine Learning / AI

**Where this matters in ML engineering:**

- **Vocabulary construction (NLP):** Building a vocabulary over a corpus deduplicated with `unordered_set` — each unique token is inserted once. Python's `set` type is the direct equivalent. Token-ID mapping then uses `unordered_map`. This is the core primitive behind every tokeniser's vocabulary-building pass.
    
- **Feature deduplication in ML pipelines:** When computing feature sets from raw data (e.g., unique user IDs seen in a click log), `unordered_set` enables $O(n)$ deduplication vs $O(n \log n)$ with a sorted approach. At the scale of web-scale logs (billions of rows), this matters.
    
- **Graph construction:** Building adjacency sets for sparse graphs — checking if an edge already exists before adding it. In PyTorch Geometric and DGL, the internal edge-list deduplication uses hash sets internally.
    
- **`set` in ML — the sorted case:** When building a BPE (Byte-Pair Encoding) tokeniser (used in GPT-2, LLaMA, etc.), the merge priority queue is conceptually a sorted set of `(frequency, pair)` tuples. Hugging Face's tokenisers library maintains this as a sorted structure so that the highest-frequency pair can always be found in $O(\log n)$.
    
- **`std::set` as a sliding-window structure in time-series:** When computing rolling statistics and you need to track which elements are currently in the window with the ability to query the median or percentile, a sorted multiset (or two heaps — see [[153.Merge k sorted lists — min-heap of size k]]) is the right abstraction.
    

**Frameworks/libraries that use this internally:**

- `scikit-learn`'s `LabelEncoder` uses Python's `sorted(set(y))` — explicitly combining deduplication (`set`) with sort ordering (`sorted`) to build the class index.
- PyTorch's `torch.unique()` sorts first, then deduplicates — equivalent to building a sorted set — because it needs a canonical ordering for the output.
- NumPy's `np.unique()` returns a _sorted_ array of unique values — it chooses the `set` semantics (sorted) over `unordered_set` semantics because most downstream uses need order.

**How understanding this improves your ML code:**

When you write `list(set(my_list))` in Python to deduplicate, you get random ordering — Python's `set` is an `unordered_set`. If downstream code assumes a stable ordering (e.g., you're building a vocabulary and want reproducible index assignments), you must write `sorted(set(my_list))`. This is one of the most common reproducibility bugs in ML pipelines.

## 3. Algorithm / Pattern

### Internal Structure

**`std::set` (Red-Black Tree):**

- A self-balancing BST. Every node stores one element. The tree maintains the invariant that for any node $v$: all elements in its left subtree are `< v`, all in right subtree are `> v`.
- Height is always $O(\log n)$ — rebalancing via rotations after insert/delete keeps this guarantee.
- Iterator order is in-order traversal → elements come out sorted.
- Every node is a separate heap allocation. Cache-unfriendly for large sets.

**`std::unordered_set` (Hash Table with Separate Chaining):**

- An array of "buckets," each bucket being a linked list of elements that hash to the same index.
- For element `x`: compute `hash(x) % bucket_count` → index → walk the linked list at that bucket to find/insert/erase.
- When load factor (`size / bucket_count`) exceeds a threshold (default 1.0), the table rehashes — allocates a larger bucket array, re-inserts all elements. Amortised $O(1)$ per operation.
- Cache-unfriendly: each element is a separate heap allocation (linked list node). The bucket array itself is contiguous, but following pointers into chains is not.

### Operation Complexity

|Operation|`set`|`unordered_set` (avg)|`unordered_set` (worst)|
|---|---|---|---|
|`insert(x)`|$O(\log n)$|$O(1)$ amortised|$O(n)$|
|`find(x)` / `count(x)`|$O(\log n)$|$O(1)$ expected|$O(n)$|
|`erase(x)`|$O(\log n)$|$O(1)$ expected|$O(n)$|
|`lower_bound(x)`|$O(\log n)$|**Not supported**|—|
|`begin()` (min element)|$O(1)$|$O(n)$ scan|—|
|Iterate in order|$O(n)$|$O(n)$ but unordered|—|
|Memory per element|$\approx 40$ bytes (node + pointers + RB colour)|$\approx 40$–$60$ bytes (node + bucket ptr)|—|

### Decision Tree: `set` vs `unordered_set`

```
Do you need any of these?
  - lower_bound / upper_bound (range queries, successor queries)
  - iterate in sorted order
  - guaranteed O(log n) worst case (adversarial inputs)
  - min/max element in O(1)
│
├── YES to any → use std::set
│
└── NO to all
    │
    ├── Are inputs potentially adversarial (CP hack test)?
    │   ├── YES → use std::set OR custom-hashed unordered_set
    │   └── NO  → use std::unordered_set
    │
    ├── Is n very small (< ~500)?
    │   └── Both are fine; set may even be faster due to cache
    │
    └── Is lookup in a hot inner loop with n >> 10^4?
        └── unordered_set wins — O(1) vs O(log n) matters here
```

### Python Equivalents

|C++|Python|Notes|
|---|---|---|
|`unordered_set<T>`|`set()`|Hash table, O(1) expected, unordered|
|`set<T>`|`sortedcontainers.SortedList`|Third-party; `bisect` module for sorted lists|
|`set<T>` (read-only)|`frozenset()`|Immutable hash set; slightly faster for lookups|
|`multiset<T>`|`collections.Counter` or `sortedcontainers.SortedList`|With duplicates|

Python has no built-in sorted set. `set()` is always an `unordered_set`. For sorted-set operations (lower_bound equivalent), use `bisect.bisect_left` on a sorted list maintained manually, or `sortedcontainers.SortedList`.

## 4. Pseudocode

```
PROCEDURE SetVsUnorderedSet_Decision(operations):
    needs_order ← False
    for each op in operations:
        if op is LOWER_BOUND or UPPER_BOUND or SORTED_ITERATION:
            needs_order ← True
    
    if needs_order:
        use RedBlackTree (std::set)
        # All ops: O(log n) guaranteed
        # Extra power: lower_bound(x) → first element ≥ x in O(log n)
    else:
        use HashTable (std::unordered_set)
        # Expected O(1) insert/find/erase
        # WARNING: default hash vulnerable to adversarial input in CP


PROCEDURE HashTableInsert(table, x):
    bucket_idx ← hash(x) % table.bucket_count
    chain ← table.buckets[bucket_idx]
    
    for each element e in chain:
        if e == x:
            return  # already present — set semantics, no duplicates
    
    chain.append(x)
    table.size++
    
    if table.size / table.bucket_count > LOAD_FACTOR_THRESHOLD:
        Rehash(table)  # double bucket count, re-insert all — amortised O(1)


PROCEDURE RBTreeInsert(tree, x):
    # Standard BST insert → O(log n) traversal
    node ← BSTInsert(tree.root, x)
    # Restore Red-Black properties via rotations — O(log n)
    FixRBViolations(tree, node)


PROCEDURE SetLowerBound(tree, x):
    # Find first element ≥ x via BST traversal
    result ← NULL
    current ← tree.root
    while current ≠ NULL:
        if current.value >= x:
            result ← current     # candidate: might find smaller one on left
            current ← current.left
        else:
            current ← current.right
    return result  # O(log n)
    # unordered_set CANNOT implement this — there is no analogue
```

#include <algorithm>
#include <cassert>
#include <chrono>
#include <iostream>
#include <set>

#include <vector>
#include <random>

// ── Anti-hack custom hash for CP (splitmix64) ──────────────────────────────
// Use this in place of default hash to defeat adversarial test cases.
// Replace unordered_set<int> with unordered_set<int, SafeHash> everywhere.
struct SafeHash {
    static uint64_t splitmix64(uint64_t x) {
        x += 0x9e3779b97f4a7c15ULL;
        x = (x ^ (x >> 30)) * 0xbf58476d1ce4e5b9ULL;
        x = (x ^ (x >> 27)) * 0x94d049bb133111ebULL;
        return x ^ (x >> 31);
    }
    size_t operator()(uint64_t x) const {
        static const uint64_t FIXED_RANDOM =
            std::chrono::steady_clock::now().time_since_epoch().count();
        return splitmix64(x + FIXED_RANDOM);
    }
    // For int keys — cast to uint64_t
    size_t operator()(int x) const { return operator()((uint64_t)(unsigned)x); }
};

using SafeIntSet = std::unordered_set<int, SafeHash>;

// ── 1. Core API comparison ────────────────────────────────────────────────

void demo_api() {
    std::cout << "=== API comparison ===\n";

    std::set<int>          ordered   = {5, 1, 3, 2, 4};
    std::unordered_set<int> unordered = {5, 1, 3, 2, 4};

    // Both: insert, find, erase, size, count
    ordered.insert(6);
    unordered.insert(6);

    std::cout << "set contains 3: " << ordered.count(3) << "\n";       // 1
    std::cout << "uset contains 3: " << unordered.count(3) << "\n";    // 1
    std::cout << "set contains 9: " << ordered.count(9) << "\n";       // 0

    // ONLY set: ordered iteration
    std::cout << "set in order: ";
    for (int x : ordered) std::cout << x << " ";  // 1 2 3 4 5 6
    std::cout << "\n";

    std::cout << "uset order (arbitrary): ";
    for (int x : unordered) std::cout << x << " ";  // some permutation
    std::cout << "\n";
}

// ── 2. The lower_bound pattern — set's killer feature ────────────────────
//
// Problem: given a dynamic set S and queries "find smallest x in S >= q",
// solve each query in O(log n). This is impossible with unordered_set.

void demo_lower_bound() {
    std::cout << "\n=== lower_bound (set only) ===\n";

    std::set<int> S = {10, 20, 30, 40, 50};

    // lower_bound: first element >= query
    auto it = S.lower_bound(25);
    std::cout << "smallest >= 25: " << *it << "\n";   // 30

    it = S.lower_bound(20);
    std::cout << "smallest >= 20: " << *it << "\n";   // 20 (exact match)

    // upper_bound: first element > query
    it = S.upper_bound(20);
    std::cout << "smallest > 20: " << *it << "\n";    // 30

    // Predecessor: largest element < query
    it = S.lower_bound(35);
    if (it != S.begin()) {
        --it;
        std::cout << "largest < 35: " << *it << "\n"; // 30
    }

    // "Find if any element in [L, R] exists in S"
    int L = 22, R = 38;
    it = S.lower_bound(L);
    bool any_in_range = (it != S.end() && *it <= R);
    std::cout << "any in [" << L << "," << R << "]: " << any_in_range << "\n"; // 1 (30 is there)
}

// ── 3. Sliding window with multiset ──────────────────────────────────────
//
// LC 480: sliding window median.
// Keep a multiset of the current window — O(log n) insert/erase,
// O(1) median access (iterator to middle maintained manually).
// Impossible with unordered structures.

double sliding_window_median_demo(std::vector<int>& nums, int k) {
    std::multiset<int> window(nums.begin(), nums.begin() + k);

    // Point the "mid" iterator at the median position
    auto mid = std::next(window.begin(), (k - 1) / 2);

    double median = (k % 2 == 1)
        ? *mid
        : (*mid + *std::next(mid)) / 2.0;

    std::cout << "\n=== Sliding window median (k=" << k << ") ===\n";
    std::cout << "First window median: " << median << "\n";

    for (int i = k; i < (int)nums.size(); ++i) {
        // Insert new element, maintaining mid
        int incoming = nums[i], outgoing = nums[i - k];
        window.insert(incoming);

        if (incoming < *mid) --mid;          // new element went left of mid
        if (outgoing <= *mid) ++mid;         // outgoing was at or left of mid → slide right

        // Erase outgoing
        window.erase(window.find(outgoing));

        // Recompute median
        median = (k % 2 == 1)
            ? *mid
            : (*mid + *std::next(mid)) / 2.0;
    }
    return median;
}

    std::generate(vals.begin(), vals.end(), rng);

### Python (Readable + Pythonic)

```python
"""
set vs sorted alternatives in Python — when and how to use each.

Python's built-in set = C++'s unordered_set (hash table, O(1) expected).
Python has NO built-in sorted set. Options:
  - bisect module on a sorted list: O(log n) search, O(n) insert
  - sortedcontainers.SortedList: O(log n) all ops, third-party

Complexity summary:
  set:           insert O(1), find O(1), no ordering
  SortedList:    insert O(log n), find O(log n), supports lower_bound
"""

from __future__ import annotations
import bisect
from typing import TypeVar

T = TypeVar("T")


# ── Python set (= unordered_set) ──────────────────────────────────────────

def demo_python_set() -> None:
    # O(1) expected for all membership operations
    seen: set[int] = set()

    data = [3, 1, 4, 1, 5, 9, 2, 6, 5, 3, 5]

    # Deduplication: canonical ML-pipeline pattern
    unique = list(set(data))          # order NOT preserved — random
    unique_stable = list(dict.fromkeys(data))  # order preserved (Python 3.7+)

    print(f"set dedup (arbitrary order): {sorted(unique)}")
    print(f"dict.fromkeys dedup (stable): {unique_stable}")

    # Membership test: O(1)
    seen = {1, 2, 3, 4, 5}
    print(f"3 in seen: {3 in seen}")   # True
    print(f"9 in seen: {9 in seen}")   # False

    # Set operations — all O(len(s) + len(t))
    a = {1, 2, 3, 4}
    b = {3, 4, 5, 6}
    print(f"union: {a | b}")           # {1,2,3,4,5,6}
    print(f"intersection: {a & b}")    # {3,4}
    print(f"difference: {a - b}")      # {1,2}
    print(f"symmetric diff: {a ^ b}")  # {1,2,5,6}

    # frozenset: immutable, hashable — can be used as dict key
    immutable = frozenset([1, 2, 3])
    d = {immutable: "value"}
    print(f"frozenset as key: {d[frozenset([1,2,3])]}")


# ── Sorted list with bisect (manual sorted-set) ───────────────────────────

class SortedSet:
    """
    A sorted set backed by a list + bisect for O(log n) searches.
    Insert/delete: O(n) due to list shifting — acceptable for small n.
    For large n, use sortedcontainers.SortedList instead.

    This implements the interface that C++ std::set provides but Python lacks.
    """

    def __init__(self) -> None:
        self._data: list[int] = []

    def insert(self, x: int) -> None:
        i = bisect.bisect_left(self._data, x)
        if i == len(self._data) or self._data[i] != x:
            self._data.insert(i, x)          # O(n) shift — use SortedList for perf

    def __contains__(self, x: int) -> bool:
        i = bisect.bisect_left(self._data, x)
        return i < len(self._data) and self._data[i] == x   # O(log n)

    def lower_bound(self, x: int) -> int | None:
        """First element >= x, or None. Equivalent to std::set::lower_bound."""
        i = bisect.bisect_left(self._data, x)
        return self._data[i] if i < len(self._data) else None

    def upper_bound(self, x: int) -> int | None:
        """First element > x, or None. Equivalent to std::set::upper_bound."""
        i = bisect.bisect_right(self._data, x)
        return self._data[i] if i < len(self._data) else None

    def predecessor(self, x: int) -> int | None:
        """Largest element < x, or None."""
        i = bisect.bisect_left(self._data, x)
        return self._data[i - 1] if i > 0 else None

    def erase(self, x: int) -> None:
        i = bisect.bisect_left(self._data, x)
        if i < len(self._data) and self._data[i] == x:
            self._data.pop(i)

    def __iter__(self):
        return iter(self._data)

    def __len__(self):
        return len(self._data)

    def __repr__(self):
        return f"SortedSet({self._data})"


def demo_sorted_set() -> None:
    ss = SortedSet()
    for x in [5, 1, 3, 2, 4]:
        ss.insert(x)

    print(f"\nSortedSet: {ss}")              # SortedSet([1, 2, 3, 4, 5])
    print(f"lower_bound(3): {ss.lower_bound(3)}")   # 3
    print(f"lower_bound(2.5 → 3): {ss.lower_bound(3)}")  # 3
    print(f"upper_bound(3): {ss.upper_bound(3)}")   # 4
    print(f"predecessor(3): {ss.predecessor(3)}")   # 2
    print(f"4 in ss: {4 in ss}")            # True
    print(f"9 in ss: {9 in ss}")            # False

    ss.erase(3)
    print(f"after erase(3): {ss}")         # SortedSet([1, 2, 4, 5])


# ── The ML pipeline deduplication pattern ────────────────────────────────

def build_vocabulary(corpus: list[str]) -> dict[str, int]:
    """
    Standard NLP vocabulary construction.
    - set() for O(n) deduplication (unordered_set semantics)
    - sorted() to get a stable, reproducible ordering (set semantics on output)
    - Then index-map to integers

    If you skip sorted(), different runs may produce different vocab indices
    — a reproducibility bug in ML pipelines.
    """
    unique_tokens: set[str] = set()
    for sentence in corpus:
        for token in sentence.split():
            unique_tokens.add(token)   # O(1) per insert

    # sorted() applies set-like ordering to the unordered_set output
    sorted_vocab = sorted(unique_tokens)          # O(V log V)
    vocab = {tok: idx for idx, tok in enumerate(sorted_vocab)}
    return vocab


if __name__ == "__main__":
    demo_python_set()
    demo_sorted_set()

    corpus = ["the cat sat on the mat", "the dog sat on the log"]
    vocab = build_vocabulary(corpus)
    print(f"\nVocabulary (stable): {vocab}")
    # {'cat': 0, 'dog': 1, 'log': 2, 'mat': 3, 'on': 4, 'sat': 5, 'the': 6}

                                     3 comparisons, O(log n)

lower_bound(23):
  ✗ IMPOSSIBLE with hash table      ✓ Walk BST — answer is 25
```

## 7. Common Variations & Extensions

### 7.1 `multiset` — Allowing Duplicates

When you need a sorted container that holds multiple copies of the same value, use `std::multiset<T>`. The canonical CP use case is maintaining a sorted sliding window where elements can repeat. Erasing from a `multiset` requires `s.erase(s.find(x))` — not `s.erase(x)`, which deletes _all_ copies of `x`. This is one of the most common multiset bugs in CP.

```cpp
std::multiset<int> ms = {1, 2, 2, 3};
ms.erase(ms.find(2));      // removes ONE copy → {1, 2, 3} ✓
// ms.erase(2);            // would remove ALL 2s → {1, 3} ✗
```

### 7.2 `unordered_set` with Custom Hash (Essential for CP)

When keys are not plain integers — e.g., `pair<int,int>`, `string`, or custom structs — you must provide a hash function. The standard library does not hash pairs. Use the splitmix64 approach from the implementation above, or combine hashes with XOR-shift:

```cpp
struct PairHash {
    size_t operator()(const pair<int,int>& p) const {
        return hash<long long>()(((long long)p.first << 32) | (unsigned)p.second);
    }
};
unordered_set<pair<int,int>, PairHash> visited;
```

### 7.3 `std::set` as a Sorted Deque for Scheduling

In simulation problems, `std::set<pair<int,int>>` where the first element is a timestamp allows efficient "pop the earliest event" (`begin()`, then `erase(begin())`) and "schedule at time t" (`insert({t, id})`). Both in $O(\log n)$. This pattern appears in priority-queue problems where you also need cancellation (erase by value — impossible in a heap). See [[149.Min-heap and max-heap — heap property and array representation]].

### 7.4 Python `sortedcontainers.SortedList`

The `sortedcontainers` library provides a pure-Python sorted list with $O(\log n)$ insert and binary search. It is available in most competitive programming judges and in standard Python environments. Its `SortedList.bisect_left(x)` is the equivalent of `std::set::lower_bound`. For ML engineering, `sortedcontainers.SortedDict` gives a sorted-key dictionary — equivalent to `std::map`. No C extension needed; the pure-Python implementation achieves competitive performance via a B-tree-like structure.

### 7.5 Order-Statistics Tree (C++ Policy Extension)

GCC's `<ext/pb_ds>` (policy-based data structures) provides an augmented Red-Black tree that supports two additional operations in $O(\log n)$: `find_by_order(k)` (k-th smallest element) and `order_of_key(x)` (rank of x). This is the standard tool for LC 315 / LC 493 type problems requiring dynamic rank queries. It has exactly the interface of `std::set` plus these two methods.

```cpp
#include <ext/pb_ds/assoc_container.hpp>
#include <ext/pb_ds/tree_policy.hpp>
using namespace __gnu_pbds;
using OrderedSet = tree<int, null_type, less<int>,
                        rb_tree_tag, tree_order_statistics_node_update>;

OrderedSet s;
s.insert(1); s.insert(3); s.insert(5);
cout << *s.find_by_order(1);   // 3 (0-indexed 2nd smallest)
cout << s.order_of_key(4);     // 2 (two elements < 4)
```

## 9. CP Contest Application

**Typical Codeforces/AtCoder structures using `set`:**

_Pattern 1 — Dynamic predecessor/successor:_

```
"Maintain a set of active positions on a number line.
 For each new point, find its nearest active neighbour."
→ set + lower_bound + iterator arithmetic. O(log n) per query.
```

_Pattern 2 — Greedy with sorted invariant:_

```
"Assign tasks to machines. Always assign the next task to the
 machine with the earliest available time that can still fit it."
→ multiset of (available_time, machine_id). lower_bound for assignment,
  erase + re-insert to update. O(log n) per task.
```

_Pattern 3 — Interval scheduling with set:_

```
"Given n intervals, find all pairs that overlap."
→ sweep line: sort by left endpoint, maintain a set of active
  right endpoints. For each new interval, query lower_bound on
  the active set. O(n log n) total.
```

**Time limits where the choice matters:**

- $n = 10^6$, $q = 10^6$ queries, time limit 1s: `unordered_set` is borderline; `set` will TLE. Use `unordered_set` with `SafeHash`.
- $n = 10^5$, need `lower_bound`: `set` is the only option. $O(n \log n)$ comfortably within 1s.
- $n = 10^6$, adversarial judge (e.g., Codeforces Div. 1D): default `unordered_set` will get hacked. Use `SafeHash` or switch to `set`.

**The reserve trick** — if you know the final size of your `unordered_set` ahead of time, call `s.reserve(n)` before inserting. This pre-allocates bucket array and prevents rehash events, cutting constant factors by ~2×.

```cpp
unordered_set<int, SafeHash> s;
s.reserve(1 << 20);  // pre-allocate for ~10^6 elements
s.max_load_factor(0.25);  // lower load factor → fewer collisions, more memory
```
