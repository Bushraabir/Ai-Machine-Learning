## 1. Intuition First

### The Core Idea

Imagine you run a library with exactly 100 shelves, and books arrive with arbitrary titles — some short, some long, some in Urdu, some in English. Your job: given any title, always point to the _same_ shelf for that title, and do so without reading the entire book. That is hashing. A **hash function** is the rule that maps an arbitrarily-sized key to a fixed-size slot in your table.

The na naive version is: assign every book to shelf 1. Constant time to store, but retrieving "Moby Dick" means scanning every book on shelf 1. That's O(n) — you've rebuilt a linked list with extra steps.

The good version: the mapping rule must be _deterministic_ (same key → same shelf, always), _fast to compute_ (the shelf number should be derivable without examining the full key), and _spread-out_ (books distribute uniformly across shelves so no shelf becomes a bottleneck).

### Why This Exists

Sorted data structures like BSTs give you O(log n) lookup. The question "can we do O(1) average?" is answered only if you can map any key to an array index in O(1) time, and do so without creating catastrophic clustering. Hashing is the _only_ known general-purpose technique that achieves expected O(1) insertion, lookup, and deletion for arbitrary keys.

The gap matters: at n = 10⁸ records, O(log n) ≈ 27 comparisons per lookup versus O(1). In a system making 10⁹ lookups/second — embedding table lookups in a neural network forward pass, vocabulary indexing in a tokeniser, deduplication in a data pipeline — that gap is the difference between a viable system and an infeasible one.

### The "Aha" Moment

**The goal of a hash function is not to be clever — it is to be indistinguishable from random.** A hash function that outputs values that _look_ random (even though it's fully deterministic) achieves uniform distribution and makes collision probability predictable via the birthday paradox. Every desirable property — uniformity, avalanche effect, independence — is just a way of saying: "your hash function should behave as if you drew the output uniformly at random."

This insight connects hash functions to pseudorandom number generators (PRNGs), to the theoretical framework of **universal hash families**, and to why cryptographic hash functions like SHA-256 are the extreme end of the same spectrum.

## 2. Why We Need It — CP + ML Dual Context

### Competitive Programming

**When it appears:** Any problem requiring O(1) lookup on custom keys — frequency counting, set membership, string equality without sorting, rolling hash for pattern matching ([[27.Rabin-Karp — rolling hash for pattern matching]]).

**Signal pattern:**

> "You need to check if something has been seen before in O(1)" → HashMap → you need to trust the hash function.  
> "String matching with multiple patterns" → rolling hash → you need the hash to be collision-resistant over the string length.  
> "Two different strings hash to the same value" → anti-hash test case → you need randomised hash functions.

**The killing gotcha:** Competitive programmers often use `unordered_map<string, int>` and get **TLE or WA** on problems where the judge constructs adversarial inputs. When a hash function is deterministic and publicly known, an adversary can craft keys that all map to the same bucket — degrading O(1) to O(n) per operation. The canonical defense: use a **randomised hash** (add a random salt at runtime). In C++:

```cpp
struct custom_hash {
    static uint64_t splitmix64(uint64_t x) {
        x += 0x9e3779b97f4a7c15;
        x = (x ^ (x >> 30)) * 0xbf58476d1ce4e5b9;
        x = (x ^ (x >> 27)) * 0x94d049bb133111eb;
        return x ^ (x >> 31);
    }
    size_t operator()(uint64_t x) const {
        static const uint64_t FIXED_RANDOM =
            chrono::steady_clock::now().time_since_epoch().count();
        return splitmix64(x + FIXED_RANDOM);
    }
};
unordered_map<long long, int, custom_hash> safe_map;
```

This is essential knowledge for Codeforces Div. 1–2 problems with string or integer hashmap requirements.

---

### Machine Learning / AI

**Embedding lookup tables:** The single most frequent use of hashing in ML. In `torch.nn.Embedding`, a vocabulary of size V is stored as a matrix of shape `(V, d)`. The token ID is the hash key; the row index is the hash value. The hash function here is the identity (token IDs are pre-assigned integers), but the design of that assignment — which tokens map to which IDs — is exactly the hash function design problem applied to discrete vocabularies.

**Feature hashing (hashing trick):** Used in `sklearn.feature_extraction.text.HashingVectorizer` and historically in Vowpal Wabbit. Instead of building a fixed vocabulary (which requires a full pass over data), you hash feature strings directly to integer indices in a fixed-size vector. The hash function _is_ the feature engineering step. A poor hash function → feature collisions → model degradation. A good hash with a large output space → negligible collision rate.

**Deduplication in data pipelines:** Training dataset construction for LLMs (e.g., RedPajama, The Pile) uses MinHash (built on hash functions, see [[39.MinHash — estimating Jaccard similarity at scale]]) to detect near-duplicate documents at scale. The quality of the underlying hash function determines the false positive rate of deduplication.

**Random projection and LSH:** [[38.Locality-sensitive hashing (LSH) — approximate nearest neighbour]] uses hash functions specifically designed to _violate_ uniformity — similar inputs should collide. Understanding when uniformity is a goal versus when it's the wrong goal is a direct application of understanding hash function properties deeply.

**Practical takeaway:** When you call `dict[token]` in Python or do an embedding lookup in PyTorch, you're paying the cost of a hash function on every forward pass. Understanding hash function design tells you why Python dicts are O(1) average but not O(1) worst case, and why hash collisions in feature hashing reduce model capacity in a quantifiable, predictable way.

## 3. Algorithm / Pattern

### Formal Properties of a Good Hash Function

Let $h: U \to {0, 1, \ldots, m-1}$ map a universe $U$ of keys to $m$ slots.

**1. Determinism**  
$h(k)$ must always return the same value for the same $k$. Trivial but violated if you use random state inside the function (a common bug).

**2. Uniformity (Uniform Distribution)**  
For a randomly chosen key $k$ from the universe, $h(k)$ should be approximately uniformly distributed over ${0, \ldots, m-1}$. Formally, for each slot $j$: $$\Pr[h(k) = j] \approx \frac{1}{m}$$ This minimises expected collision count. Proof: if $n$ keys are inserted and the hash is perfectly uniform, the expected number of keys per bucket is $n/m$ (the **load factor** $\alpha$). Expected lookup time is $O(1 + \alpha)$.

**3. Avalanche Effect**  
A single-bit change in the input should flip approximately half the output bits. Formally, for all keys $k$ and all bit positions $i$: $$\Pr[\text{bit } j \text{ of } h(k) \neq \text{bit } j \text{ of } h(k \oplus 2^i)] \approx 0.5 \quad \forall j$$ Without this, nearby keys cluster into nearby buckets, destroying uniformity for structured input (e.g., consecutive integers, IP addresses).

**4. Efficiency**  
$h(k)$ must run in $O(|k|)$ time or $O(1)$ for fixed-size keys. A hash function taking $O(n^2)$ time defeats the purpose.

**5. (For hash tables) Universality**  
A family $\mathcal{H}$ of hash functions is **universal** if for any two distinct keys $x \neq y$: $$\Pr_{h \in \mathcal{H}}[h(x) = h(y)] \leq \frac{1}{m}$$ where the probability is over the random choice of $h$ from the family. Universal hashing _guarantees_ O(1) expected lookup regardless of input distribution — the cornerstone of hash table theory (CLRS Ch. 11.3).

---

### The Standard Construction Methods

**Division method:** $h(k) = k \bmod m$. Simple. Fails if keys share common factors with $m$. Use a prime $m$ far from powers of 2.

**Multiplication method:** $h(k) = \lfloor m \cdot (kA \bmod 1) \rfloor$ where $A = (\sqrt{5}-1)/2 \approx 0.618$ (Knuth's constant). Works for any $m$, but slow due to floating-point multiply.

**Bitwise mixing (modern practice):** Apply a sequence of XOR-shift-multiply operations to scatter bits. This is what `splitmix64` and `FNV-1a` do. Extremely fast, strong avalanche.

**For strings — FNV-1a:** $$h_0 = \text{offset_basis}$$ $$h_i = (h_{i-1} \oplus \text{byte}_i) \times \text{FNV_prime}$$ The XOR before multiply ensures each byte affects all bits of the hash (avalanche). The prime is chosen to maximise bit mixing. FNV is used in Go's `map` implementation.

**Decision tree:**

```
Is key a fixed-size integer?
  └─ Yes → Use splitmix64 / Wang hash (bitwise mixing, O(1))
Is key a variable-length string?
  └─ Yes, need speed → FNV-1a or xxHash
  └─ Yes, need collision resistance → SHA-256 (cryptographic, slow)
  └─ Yes, for rolling hash in string matching → Polynomial hash mod prime
Need locality sensitivity (similar keys → same bucket)?
  └─ No → Any of the above
  └─ Yes → LSH family (see [[38.Locality-sensitive hashing (LSH)]])
```

**Complexity:**

- Computing: $O(|k|)$ for strings, $O(1)$ for integers
- Expected lookup in hash table: $O(1 + \alpha)$ where $\alpha = n/m$
- Worst case with bad hash (all to one bucket): $O(n)$
- With universal hashing: $O(1)$ expected, independent of input

## 4. Pseudocode

```
// Universal hash family for integers (Carter-Wegman)
// Pick random a, b at construction time (not per-call)
// Guarantees: Pr[h(x) == h(y)] <= 1/m for x != y

FUNCTION make_universal_hash(m: prime integer) -> HashFunction:
    p ← large prime > |U|   // e.g. 2^61 - 1
    a ← random integer in [1, p-1]
    b ← random integer in [0, p-1]
    
    RETURN function h(k):
        RETURN ((a * k + b) mod p) mod m
    // Why two mod operations:
    //   First mod p: maps into [0, p-1], universality proof works here
    //   Second mod m: maps into table slots [0, m-1]
    //   The composition preserves the 1/m collision probability

---

// FNV-1a for strings (non-cryptographic, fast, good avalanche)
FUNCTION fnv1a(key: string, table_size: int) -> int:
    hash ← 14695981039346656037   // FNV offset basis (64-bit)
    prime ← 1099511628211         // FNV prime (64-bit)
    
    FOR each byte b in key:
        hash ← hash XOR b         // XOR first: byte affects ALL bits
        hash ← hash * prime       // Multiply: propagates change through all bits
        // Why XOR before multiply, not after?
        // XOR after multiply would only affect lower bits before multiplication
        // XOR before ensures every byte influences the full 64-bit state
    
    RETURN hash mod table_size

---

// Avalanche test (verify your hash function is good)
FUNCTION test_avalanche(h: HashFunction, sample_key: int) -> float:
    total_bit_flips ← 0
    output_bits ← 64
    
    FOR i in 0..63:                        // flip each input bit
        flipped_key ← sample_key XOR (1 << i)
        diff ← h(sample_key) XOR h(flipped_key)
        total_bit_flips ← total_bit_flips + popcount(diff)
    
    // Perfect avalanche: flipping 1 input bit flips 32 output bits on average
    RETURN total_bit_flips / (64 * output_bits)  // should be ≈ 0.5
```

## 5. Implementation

### C++ (Production-Ready)

```cpp
#include <bits/stdc++.h>
using namespace std;

// ─────────────────────────────────────────────────────────────────────────────
// 1. splitmix64 — fast integer hash with strong avalanche
//    Used internally by many competitive programmers' safe unordered_map
//    Passes strict avalanche criteria (each bit flip → ~50% output bit changes)
// ─────────────────────────────────────────────────────────────────────────────
uint64_t splitmix64(uint64_t x) {
    // Three rounds of XOR-shift-multiply
    // Each round: shift disperses high bits into low, multiply cascades changes
    x += 0x9e3779b97f4a7c15ULL;                 // additive constant (golden ratio)
    x = (x ^ (x >> 30)) * 0xbf58476d1ce4e5b9ULL;
    x = (x ^ (x >> 27)) * 0x94d049bb133111ebULL;
    return x ^ (x >> 31);
}

// ─────────────────────────────────────────────────────────────────────────────
// 2. Randomised hash for unordered_map (anti-hack in competitive programming)
//    The FIXED_RANDOM salt is chosen at runtime → adversary cannot precompute
//    worst-case inputs
// ─────────────────────────────────────────────────────────────────────────────
struct SafeHash {
    static const uint64_t FIXED_RANDOM;

    size_t operator()(uint64_t x) const {
        return splitmix64(x + FIXED_RANDOM);
    }

    // Overload for pair<int,int> — useful for grid problems
    size_t operator()(pair<int,int> p) const {
        uint64_t combined = ((uint64_t)p.first << 32) | (uint32_t)p.second;
        return splitmix64(combined + FIXED_RANDOM);
    }
};

// Static member: initialise once at program start with high-entropy source
const uint64_t SafeHash::FIXED_RANDOM =
    chrono::steady_clock::now().time_since_epoch().count();

// Usage: drop-in replacement for unordered_map<long long, V>
// unordered_map<long long, int, SafeHash> mp;

// ─────────────────────────────────────────────────────────────────────────────
// 3. FNV-1a for strings
//    O(|key|) time. Strong avalanche. Not cryptographic.
//    Suitable for: hash tables, Rabin-Karp, rolling hash seeds
// ─────────────────────────────────────────────────────────────────────────────
uint64_t fnv1a(const string& key) {
    constexpr uint64_t FNV_OFFSET_BASIS = 14695981039346656037ULL;
    constexpr uint64_t FNV_PRIME        = 1099511628211ULL;

    uint64_t hash = FNV_OFFSET_BASIS;
    for (unsigned char c : key) {
        hash ^= c;          // XOR byte into hash — mixes byte into all 64 bits
        hash *= FNV_PRIME;  // multiply — cascades the XOR change through all bits
    }
    return hash;
}

// ─────────────────────────────────────────────────────────────────────────────
// 4. Universal hash family (Carter-Wegman construction)
//    Mathematically guaranteed: Pr[h(x)==h(y)] <= 1/m for distinct x,y
//    Use when you need a provable collision bound, not just empirical goodness
// ─────────────────────────────────────────────────────────────────────────────
class UniversalHash {
    static constexpr uint64_t P = (1ULL << 61) - 1;  // Mersenne prime 2^61 - 1
    uint64_t a_, b_, m_;

    // Modular multiplication without 128-bit overflow (for P = 2^61 - 1)
    static uint64_t mod_mul(uint64_t a, uint64_t b, uint64_t mod) {
        return (__uint128_t)a * b % mod;
    }

public:
    UniversalHash(uint64_t table_size) : m_(table_size) {
        mt19937_64 rng(chrono::steady_clock::now().time_since_epoch().count());
        a_ = uniform_int_distribution<uint64_t>(1, P - 1)(rng);
        b_ = uniform_int_distribution<uint64_t>(0, P - 1)(rng);
    }

    uint64_t operator()(uint64_t k) const {
        // h(k) = ((a*k + b) mod P) mod m
        // The mod-P step is where universality is proved
        uint64_t t = (mod_mul(a_, k, P) + b_) % P;
        return t % m_;
    }
};

// ─────────────────────────────────────────────────────────────────────────────
// 5. Avalanche quality test — measure how good your hash is
//    Ideal: ~0.5 (flipping 1 input bit flips ~50% of output bits on average)
// ─────────────────────────────────────────────────────────────────────────────
double avalanche_score(uint64_t (*h)(uint64_t), int samples = 1000) {
    mt19937_64 rng(42);
    long long total_flipped = 0;
    int tests = samples * 64;  // 64 input bit positions

    for (int s = 0; s < samples; ++s) {
        uint64_t key = rng();
        uint64_t hk = h(key);
        for (int bit = 0; bit < 64; ++bit) {
            uint64_t flipped_key = key ^ (1ULL << bit);
            uint64_t h_flipped = h(flipped_key);
            total_flipped += __builtin_popcountll(hk ^ h_flipped);
        }
    }
    // Each test has 64 output bits. Perfect avalanche → 32 flipped per test.
    return (double)total_flipped / (tests * 64);
}

// ─────────────────────────────────────────────────────────────────────────────
// Demo main
// ─────────────────────────────────────────────────────────────────────────────
int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(nullptr);

    // Test FNV-1a
    cout << "FNV-1a(\"hello\") = " << fnv1a("hello") << "\n";
    cout << "FNV-1a(\"hello\") = " << fnv1a("hello") << "  (same → deterministic)\n";
    cout << "FNV-1a(\"hfllo\") = " << fnv1a("hfllo") << "  (1 char diff → large change)\n";

    // Test avalanche quality of splitmix64
    auto splitmix_wrapper = [](uint64_t x) -> uint64_t { return splitmix64(x); };
    // Can't pass lambda to function pointer directly in C++17 without casting
    // Demonstrate inline:
    long long total = 0; int tests = 1000 * 64;
    mt19937_64 rng(42);
    for (int s = 0; s < 1000; s++) {
        uint64_t k = rng();
        uint64_t hk = splitmix64(k);
        for (int b = 0; b < 64; b++)
            total += __builtin_popcountll(hk ^ splitmix64(k ^ (1ULL << b)));
    }
    printf("splitmix64 avalanche score: %.4f (ideal=0.500)\n",
           (double)total / ((long long)tests * 64));

    // Demonstrate SafeHash with unordered_map
    unordered_map<long long, int, SafeHash> safe_map;
    for (int i = 0; i < 100; i++) safe_map[i * 1000007LL] = i;
    cout << "safe_map[42000000] = " << safe_map[42LL * 1000007LL] << "\n";

    // Universal hash
    UniversalHash uh(1000003);  // prime table size
    cout << "Universal h(42) = " << uh(42) << "\n";
    cout << "Universal h(42) = " << uh(42) << "  (same key → same slot)\n";

    return 0;
}
```

### Python (Readable + Pythonic)

```python
"""
Hash Function Design — Properties, Uniformity, Avalanche
T1 Core — 2. Hashing

Covers:
  - splitmix64 integer hash
  - FNV-1a string hash
  - Universal (Carter-Wegman) hash family
  - Avalanche quality measurement
  - Python's own hash internals

Complexity:
  - Integer hash: O(1)
  - String hash FNV-1a: O(|key|)
  - Universal hash construction: O(1), evaluation O(1)
"""

import random
import struct
import time
from typing import Callable


# ─────────────────────────────────────────────────────────────────────────────
# 1. splitmix64 — integer hash with strong avalanche
# ─────────────────────────────────────────────────────────────────────────────
def splitmix64(x: int) -> int:
    """
    Maps any 64-bit integer to a pseudo-random 64-bit integer.
    Three rounds of XOR-shift-multiply give excellent bit mixing.
    The constants are carefully chosen for maximum diffusion.
    """
    MASK64 = (1 << 64) - 1
    x = (x + 0x9e3779b97f4a7c15) & MASK64
    x = ((x ^ (x >> 30)) * 0xbf58476d1ce4e5b9) & MASK64
    x = ((x ^ (x >> 27)) * 0x94d049bb133111eb) & MASK64
    return (x ^ (x >> 31)) & MASK64


# ─────────────────────────────────────────────────────────────────────────────
# 2. FNV-1a string hash
#    XOR before multiply: each byte influences ALL subsequent bits
# ─────────────────────────────────────────────────────────────────────────────
def fnv1a(key: str | bytes, table_size: int | None = None) -> int:
    """
    FNV-1a hash for strings/bytes.
    
    Args:
        key: input string or bytes
        table_size: if given, return hash mod table_size; else return raw 64-bit hash
    
    Returns:
        Hash value in [0, table_size) or raw 64-bit hash
        
    Properties:
        - Deterministic: same input → same output always
        - Fast: one XOR + one multiply per byte
        - Good avalanche: 1-byte change → completely different hash
        - NOT cryptographic: don't use for security
    """
    FNV_OFFSET_BASIS = 14695981039346656037  # 64-bit
    FNV_PRIME = 1099511628211               # 64-bit
    MASK64 = (1 << 64) - 1

    if isinstance(key, str):
        key = key.encode('utf-8')

    h = FNV_OFFSET_BASIS
    for byte in key:
        h ^= byte          # XOR byte into hash FIRST
        h = (h * FNV_PRIME) & MASK64  # then multiply — cascades the XOR

    return h if table_size is None else h % table_size


# ─────────────────────────────────────────────────────────────────────────────
# 3. Universal Hash Family (Carter-Wegman, 1979)
#    Mathematically proven: Pr[h(x) == h(y)] <= 1/m for x != y
#    The random a, b are chosen at construction, not per-call
# ─────────────────────────────────────────────────────────────────────────────
class UniversalHash:
    """
    Universal hash family using the Carter-Wegman construction.
    h(k) = ((a*k + b) mod P) mod m
    
    where P = 2^61 - 1 (Mersenne prime) and a, b chosen uniformly at random.
    
    Collision guarantee: for distinct x, y: Pr[h(x) == h(y)] <= 1/m
    This holds regardless of the input distribution — it's a WORST-CASE guarantee
    over the random choice of (a, b), not an average-case assumption.
    """
    P = (1 << 61) - 1  # Mersenne prime: fast modular arithmetic

    def __init__(self, table_size: int):
        assert table_size <= self.P, "Table size must be < 2^61 - 1"
        self.m = table_size
        self.a = random.randint(1, self.P - 1)
        self.b = random.randint(0, self.P - 1)

    def __call__(self, k: int) -> int:
        # Python's arbitrary-precision ints make this exact (no overflow)
        return ((self.a * k + self.b) % self.P) % self.m

    def collision_bound(self) -> float:
        """Returns the theoretical maximum collision probability."""
        return 1.0 / self.m


# ─────────────────────────────────────────────────────────────────────────────
# 4. Avalanche score measurement
#    Quantifies hash quality: flip 1 input bit, measure output bit changes
#    Ideal score = 0.5 (half the output bits change per input bit flip)
# ─────────────────────────────────────────────────────────────────────────────
def avalanche_score(h: Callable[[int], int], samples: int = 500) -> float:
    """
    Strict Avalanche Criterion (SAC) test.
    
    For each sample key and each input bit position:
      - Flip that bit
      - Count how many output bits differ
    
    Average should be ~0.5 for a good hash.
    < 0.4 or > 0.6: poor avalanche, keys will cluster in hash table.
    """
    total_flipped = 0
    total_tests = samples * 64  # 64 input bits

    rng = random.Random(42)
    for _ in range(samples):
        key = rng.getrandbits(64)
        hk = h(key)
        for bit in range(64):
            flipped = key ^ (1 << bit)
            h_flipped = h(flipped)
            # Count differing bits in output
            total_flipped += bin(hk ^ h_flipped).count('1')

    return total_flipped / (total_tests * 64)


# ─────────────────────────────────────────────────────────────────────────────
# 5. Python hash internals — what hash() actually does
# ─────────────────────────────────────────────────────────────────────────────
def demonstrate_python_hash_internals():
    """
    Python's hash() for integers: identity for small ints, sys.hash_info for large.
    Python's hash() for strings: SipHash-1-3 with PYTHONHASHSEED (randomised).
    
    Key point: hash(x) in Python is randomised per-process run (since Python 3.3)
    to prevent HashDoS attacks — exactly the same principle as the competitive
    programming anti-hack trick.
    """
    import sys
    print(f"Python hash info: {sys.hash_info}")
    # hash_info.modulus = 2^61 - 1 (same Mersenne prime as Carter-Wegman!)
    
    # Integers: hash(n) == n for n in [-5, 256] (CPython small int cache)
    print(f"hash(0) = {hash(0)}")
    print(f"hash(1) = {hash(1)}")
    print(f"hash(2**61 - 1) = {hash(2**61 - 1)}")  # = -2 due to mod structure
    
    # Strings: RANDOMISED (different every process run)
    # This is why you cannot use hash("string") across processes in ML pipelines!
    print(f"hash('hello') = {hash('hello')}  (changes every Python restart)")
    print("IMPORTANT: Do not use Python's hash() for persistence. Use FNV-1a or xxhash.")

# ─────────────────────────────────────────────────────────────────────────────

    # Avalanche check on splitmix64

    print(f"splitmix64 avalanche score: {score:.4f}  (ideal: 0.5000)")

    # FNV-1a demo

    print(f'FNV-1a("hfllo")  = {fnv1a("hfllo")}  # 1 char diff → totally different')
    print(f'FNV-1a("Hello")  = {fnv1a("Hello")}  # case change → totally different')

    print(f"Collision upper bound: {uh.collision_bound():.2e}")

    # Python internals
    print("\n--- Python hash internals ---")

    # ML context: feature hashing demo
    print("\n--- Feature hashing (ML context) ---")
    def feature_hash(feature_name: str, n_features: int = 2**18) -> int:
        """The core of sklearn's HashingVectorizer."""
        return fnv1a(feature_name, table_size=n_features)

    features = ["word=apple", "word=banana", "word=cherry", "bigram=apple_pie"]
    n = 2**18  # 262144 feature dimensions
    for f in features:
        idx = feature_hash(f, n)
        print(f"  '{f}' → index {idx}")
    print(f"Collision probability per pair ≈ {1/n:.2e}")
```

### Diagram 1: Avalanche Effect — Why Bit Mixing Matters

```
Input key (64-bit integer):

NAIVE HASH:  h(k) = k mod m
─────────────────────────────────────────────────────────
Key A:  0000 0000 0000 0000 0000 0000 0000 0101  (= 5)
Key B:  0000 0000 0000 0000 0000 0000 0000 0110  (= 6)  ← 1 bit flip

Output A: 5 mod 1000 = 005  →  binary: ...000000101
Output B: 6 mod 1000 = 006  →  binary: ...000000110
                                         └─── only 2 bits differ

Problem: consecutive integers → consecutive slots → clustering!
With 10^6 sequential keys: all land in slots 0–999 (mod 1000)
Range [1000, ∞) is completely empty. Terrible uniformity.

─────────────────────────────────────────────────────────────────────

SPLITMIX64 HASH: Three XOR-shift-multiply rounds
─────────────────────────────────────────────────────────────────────
Key A:  ...0000 0101  (= 5)
        │
        ▼ Step 1: x += golden_ratio_constant
        1001 1110 0011 0111 0111 1001 1011 1010   ← already spread
        │
        ▼ Step 2: x ^= (x >> 30); x *= prime1
        0111 1011 1100 0001 0100 1101 1111 0010   ← 30-bit shift mixes
        │
        ▼ Step 3: x ^= (x >> 27); x *= prime2
        1010 0011 1110 1001 0100 1010 1100 1101   ← final output for 5

Key B:  ...0000 0110  (= 6)
        → (after splitmix64)
        0001 1100 0101 0111 1011 0010 1110 1000   ← output for 6

XOR difference (bits that changed):
        1011 1111 1011 1110 1111 1000 0010 0101
        └──────────────────────────────────────┘
        popcount = 31 bits changed out of 64   ← ≈ 48% (close to ideal 50%)

1-bit input change → ~half the output bits change. That's avalanche.
```

### Diagram 3: Universal Hashing — Why Randomisation Defeats Adversaries

```
DETERMINISTIC HASH:  h(k) = k mod 7

Adversary knows this function. Adversary crafts:
  keys = {0, 7, 14, 21, 28, 35, 42}
  All hash to slot 0. Your O(1) table is now O(n).

          Before adversarial input:        After adversarial input:
          ┌───┐                            ┌───┐
    Slot 0│   │ ← 1 item                Slot 0│●→●→●→●→●→●→●│ ← 7 items!
          ├───┤                            ├───┤
    Slot 1│ ● │                       Slot 1│   │
          ├───┤                            ├───┤
         ...                              ...
          └───┘                            └───┘

═══════════════════════════════════════════════════════════════════

UNIVERSAL HASH:  h(k) = ((a*k + b) mod P) mod 7
                         where a, b are SECRET random values

Adversary does NOT know a, b. Even if adversary submits {0,7,14,...}:
  h(0)  = ((a*0  + b) mod P) mod 7  → some random slot
  h(7)  = ((a*7  + b) mod P) mod 7  → different random slot
  h(14) = ((a*14 + b) mod P) mod 7  → different random slot

With probability 1 - 1/7 ≈ 86%: each pair lands in different slots.
Expected max chain length: O(log n / log log n) — near optimal.

This is why unordered_map with a fixed hash is hackable,
but with a random salt (FIXED_RANDOM in splitmix64) it is not.
```

## 7. Common Variations & Extensions

### 1. Polynomial Rolling Hash for Strings

Used in [[27.Rabin-Karp — rolling hash for pattern matching]]. Instead of FNV-1a, compute: $$h(s) = s[0] \cdot B^{n-1} + s[1] \cdot B^{n-2} + \cdots + s[n-1] \pmod{P}$$ for base $B$ (typically 31 or 131) and prime $P$. The "rolling" property lets you compute $h(s[i+1..i+m])$ from $h(s[i..i+m-1])$ in $O(1)$, making substring hashing $O(n)$ total instead of $O(nm)$.

### 2. Double Hashing (for Collision Reduction in String Matching)

Compute two independent hashes $h_1(s)$ and $h_2(s)$ using different bases/primes. Report a match only when both agree. The false positive probability drops from $1/P$ to $1/(P_1 \cdot P_2) \approx 10^{-18}$ — effectively zero. Critical for competitive programming where single-hash Rabin-Karp fails anti-hash tests.

### 3. Cryptographic vs. Non-Cryptographic Hashes

FNV-1a and splitmix64 are fast but **not cryptographically secure**: given the output, you can infer the input structure. SHA-256 adds many more mixing rounds to make inversion computationally infeasible. For hash tables: use non-cryptographic (speed matters). For password storage, digital signatures: use cryptographic (security matters). Understanding this distinction is essential when choosing hash functions in ML data pipelines.

### 4. Locality-Sensitive Hashing (LSH) — The Deliberate Inversion

In [[38.Locality-sensitive hashing (LSH) — approximate nearest neighbour]], the goal is the _opposite_ of uniformity: similar inputs should hash to the _same_ bucket. LSH families are designed to be "bad" hash functions (by the uniformity criterion) in a controlled way, so that collisions signal semantic similarity. This is used in FAISS, approximate nearest-neighbour search for embedding retrieval, and MinHash for document deduplication.

## 9. CP Contest Application

### Typical Problem Structure

Codeforces Div. 2 C/D, Div. 1 B: "Given $n$ strings, group those that are equal under some transformation" → hash the canonical form, group by hash. Time limit: 1–2 seconds, $n \leq 10^5$, key length up to $10^3$.

### Anti-Hack Drill

In Codeforces, `unordered_map` with default hash is hackable. If your solution uses `unordered_map<long long, V>` or `unordered_map<string, V>`:

```cpp
// Step 1: Replace the hash with SafeHash (defined above in C++ section)
unordered_map<long long, int, SafeHash> mp;

// Step 2: If using string keys, hash them to uint64_t first with FNV-1a
// then use SafeHash on the integer
auto string_to_key = [](const string& s) -> uint64_t { return fnv1a(s); };
unordered_map<uint64_t, int, SafeHash> string_map;
// Insert: string_map[string_to_key(s)] = val;
// Lookup: auto it = string_map.find(string_to_key(query));
```

This pattern is safe against all known Codeforces anti-hash hacks as of 2024.

### When Hash Beats Sorted Order

|Operation|`std::map` (RB tree)|`unordered_map` (hash)|
|---|---|---|
|Lookup|$O(\log n)$|$O(1)$ expected|
|Insert|$O(\log n)$|$O(1)$ amortised|
|Range query|$O(\log n + k)$|❌ Not supported|
|Ordered iteration|$O(n)$|❌ Not guaranteed|

Use `unordered_map` when you need O(1) lookup and do not need ordering or range queries. In tight time limits ($n = 10^6$, TL = 1s), the difference between $O(\log n)$ and $O(1)$ is often the margin between AC and TLE.
